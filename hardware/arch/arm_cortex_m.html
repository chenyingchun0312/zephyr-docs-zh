操作系统特性

线程

线程栈对齐

每个 Zephyr 线程都定义有自己的栈内存。默认情况下，Cortex-M 强制线程栈按双字对齐，见 CONFIG_STACK_ALIGN_DOUBLE_WORD。如果启用了基于 MPU 的硬件辅助栈溢出检测（CONFIG_MPU_STACK_GUARD），线程栈需要按更大的值对齐，该值由 CONFIG_ARM_MPU_REGION_MIN_ALIGN_AND_SIZE 表示。在 Arm v6-M 和 Arm v7-M 架构变体中，对于需要支持用户模式（CONFIG_USERSPACE）的应用程序，还要求线程栈按与其大小相等的值对齐。这种情况下线程栈大小必须是 2 的幂。所有这些都由 CONFIG_MPU_REQUIRES_POWER_OF_TWO_ALIGNMENT 体现，在支持用户模式的 Arm v6-M 和 Arm v7-M 构建中会强制启用该选项。

栈指针

在线程模式下执行时，处理器使用进程栈指针（PSP）。在处理程序模式下执行时，即处理异常和硬件中断时，处理器使用主栈指针（MSP）。在线程模式下使用 PSP，便于 在线程上下文切换期间 操作线程栈指针，而不会影响处理程序模式下当前的执行上下文流。

在 Arm Cortex-M 构建中，异常和中断共享同一块中断栈内存。选择中断栈大小时需要考虑嵌套中断，每次嵌套都会压入一个额外的栈帧。开发者可以使用 CONFIG_ISR_STACK_SIZE 修改中断栈大小。

中断栈也会在早期启动期间使用，以便内核在切换到 main 线程之前初始化 main 线程的栈。

线程上下文切换

在 Arm Cortex-M 构建中，使用 PendSV 异常来触发到另一个线程的上下文切换。PendSV 异常在所有 Cortex-M 实现中都存在。在所有 Cortex-M 变体中，PendSV 都被配置为可能的最低中断优先级。这样设计的主要原因是：

  • 利用 Cortex-M 处理器的尾链（tail chaining）特性，从而限制上下文切换操作的发生次数。

  • 不影响硬件中断所观测到的中断延迟。

因此，Cortex-M 中的上下文切换是非原子的，即它可能被硬件中断 抢占，但一次上下文切换操作必须完成后，才能开始新的线程上下文切换。

线程上下文切换通常执行以下操作：

  • 换出当前线程时，处理器会保存：

    • 被调用者保存寄存器（R4 - R11），存入该线程位于内核内存中的被调用者保存寄存器容器

    • 线程当前的操作 模式

      • 用户或特权执行模式

      • 是否存在活动的浮点上下文

      • 当前处理程序上下文（PendSV）的 EXC_RETURN 值

    • 浮点被调用者保存寄存器（S16 - S31），如果当前线程有活动的浮点上下文，则存入该线程的浮点被调用者保存寄存器容器

    • 当前线程的 PSP，它指向当前线程异常栈帧的起始位置。该栈帧包含被换出线程的调用者保存上下文和返回地址。

  • 换入新线程时，处理器会：

    • 从该线程的被调用者保存寄存器容器中恢复新线程的被调用者保存寄存器

    • 恢复新线程的操作 模式

    • 如果被换入的线程在被换出之前有活动的浮点上下文，则恢复浮点被调用者保存寄存器

    • 重新编程动态 MPU 区域，使用户线程能够访问其栈和应用程序内存，和/或在线程特权栈的底部编程一个栈溢出 MPU 保护区

    • 恢复换入线程的 PSP，并重新编程栈指针界限寄存器（如适用，见 CONFIG_BUILTIN_STACK_GUARD）

    • 如果启用了基于哨兵（sentinel）的栈界限检查（见 CONFIG_STACK_SENTINEL），可选地对换入的线程进行栈界限检查。

PendSV 异常返回序列在弹出异常栈帧的过程中，恢复新线程的调用者保存寄存器和返回地址。

上下文切换机制的实现位于 arch/arm/core/cortex_m/swap_helper.S 中。

栈界限检查（Arm v8-M）

Armv8-M 和 Armv8.1-M 变体支持使用 MSPLIM 和 PSPLIM 内核寄存器进行栈界限检查。设置 CONFIG_BUILTIN_STACK_GUARD 后即启用该功能。启用栈界限检查后，线程的特权栈或用户栈以及中断栈分别由 PSPLIM 和 MSPLIM 寄存器保护。MSPLIM 在内核启动期间只配置 一次，而 PSLIM 则在每次线程上下文切换时重新编程，或者在系统调用期间、线程从使用默认栈切换为使用特权栈（以及反向切换）时重新编程。PSPLIM 的重新编程：

  • 运行时开销相对较低（使用 MSR 指令进行编程）

  • 不影响中断延迟

  • 不需要为栈保护区预留任何内存区域

  • 不使用 MPU 区域

因此，它被视为 Cortex-M 应用程序中一种轻量但非常高效的栈溢出检测机制。

栈溢出会触发 Arm v8-M 提供的专用 UsageFault 异常。

中断处理特性

本节介绍 Arm Cortex-M 中与异常和中断处理相关的若干方面。

中断优先级

可用（可配置）的中断优先级数量由 NVIC 中实现的中断优先级位数决定；每个 Cortex-M 平台都需要使用设备树描述这一点：

&nvic {
        arm,num-irq-priority-bits = <#priority-bits>;
};

保留的优先级

有若干中断优先级是为操作系统保留的。

按照设计，系统故障异常具有最高的优先级。在 Baseline Cortex-M 中，这实际上由硬件强制保证，因为 HardFault 是唯一可用的处理器故障异常，其优先级高于任何可配置的异常优先级。

在 Mainline Cortex-M 中，可用的故障异常（例如 MemManageFault、UsageFault 等）被分配为最高的 可配置 优先级。（CONFIG_CPU_CORTEX_M_HAS_PROGRAMMABLE_FAULT_PRIOS 明确表示该 Cortex-M 实现支持可配置的故障优先级。）

该优先级从不与硬件中断共享（下文介绍了这一规则的一个例外）。因此，在常规 ISR 中发生的处理器故障将由相应的故障处理程序处理，而不会升级为 HardFault，这与在线程模式下发生的处理器故障类似。

SVC 异常通常被配置为最高的可配置优先级（下文将介绍这一规则的一个例外）。Zephyr 内核使用 SVC 来分派系统调用、触发运行时系统错误（例如内核 oops 或 panic），或实现 IRQ 卸载（offloading）。

在 Baseline Cortex-M 中，SVC 的优先级可能与其他同样被赋予最高可配置优先级的异常或硬件中断共享（因此，中断处理期间发生的内核运行时错误会升级为 HardFault。故障处理例程中的额外逻辑可确保成功检测到此类运行时错误）。

然而，在 Mainline Cortex-M 中，SVC 优先级是 保留的，因此通常只与可配置优先级的故障异常共享。这简化了 Mainline Cortex-M 架构中的故障处理例程，因为内核运行时错误由 SVC 处理程序处理（即不会升级为 HardFault，即使内核错误发生在 ISR 上下文中也是如此）。

在 Mainline Cortex-M 构建中，硬件中断被分配的优先级低于 SVC。

上述规则的一个例外是 Zephyr 应用程序支持零延迟中断（Zero Latency Interrupt，ZLI）的情况。此类中断被设计为具有高于任何硬件中断或系统中断的优先级。如果在 Mainline Cortex-M 构建中启用了 ZLI 功能（见 CONFIG_ZERO_LATENCY_IRQS），则：

  • ZLI 被分配最高的可配置优先级

  • SVC 被分配第二高的可配置优先级

  • 常规硬件中断被分配低于 SVC 的优先级。

Cortex-M 中的优先级配置实现于 include/zephyr/arch/arm/cortex_m/exception.h。

锁定和解锁 IRQ

在 Baseline Cortex-M 中，锁定中断是通过 PRIMASK 寄存器实现的。

arch_irq_lock()

会将 PRIMASK 寄存器设置为 1，最终屏蔽所有具有可配置优先级的 IRQ。虽然这满足了操作系统锁定中断的要求，但其后果是内核运行时错误（会触发 SVC）将升级为 HardFault。

在 Mainline Cortex-M 中，锁定中断是通过 BASEPRI 寄存器实现的（Mainline Cortex-M 构建会选择 CONFIG_CPU_CORTEX_M_HAS_BASEPRI，以表示实现了 BASEPRI 寄存器）。通过修改 BASEPRI（或 BASEPRI_MAX），arch_irq_lock() 会屏蔽所有系统中断和硬件中断，但以下各项除外：

  • SVC

  • 处理器故障

  • ZLI

这使得零延迟中断可以在操作系统临界区内被触发。此外，无论错误发生时 IRQ 是否已被锁定，Zephyr 都能以 完全相同的方式 处理系统（处理器和内核）故障。它还允许在 IRQ 被锁定时分派系统调用。

备注

Mainline Cortex-M 的故障处理在设计和配置上保证所有处理器故障和内核故障都由相应的异常处理程序处理，绝不会升级为 HardFault。换言之，只有修改了默认故障处理配置的 Zephyr 应用程序才可能发生 HardFault。这样设计的主要原因是为安全关键型应用程序保留 HardFault 异常，用于处理异常的错误情况。

动态直接中断

Cortex-M 构建支持在运行时安装直接中断服务例程。直接中断是为性能关键的中断处理而设计的，不会经过 Zephyr 的全部通用中断处理代码。

通过启用 CONFIG_DYNAMIC_DIRECT_INTERRUPTS 来启用动态直接中断。

注意，启用动态直接中断还需要在内核中启用对动态中断的支持（见 CONFIG_DYNAMIC_INTERRUPTS）。

零延迟中断

如上所述，在 Mainline Cortex-M 应用程序中，Zephyr 内核会保留最高的可配置中断优先级供自身使用（SVC）。SVC 不会被中断锁定屏蔽。零延迟中断可用于在最高中断优先级上设置一个不会被中断锁定阻塞的中断。要使用 ZLI 功能，需要启用 CONFIG_ZERO_LATENCY_IRQS。

零延迟 IRQ 的中断延迟最小，因为它们总是会抢占常规硬件中断或系统中断。

但需要注意，由于 ZLI 的 ISR 运行在高于内核异常的优先级上，它们不能使用任何内核功能。此外，由于 ZLI 中断优先级等于处理器故障优先级，ZLI 的 ISR 中发生的故障会升级为 HardFault，而不会像常规处理器故障那样被处理。开发者需要了解这一限制。

CPU 空闲

Cortex-M 架构移植同时实现了 k_cpu_idle() 和 k_cpu_atomic_idle()。实现位于 arch/arm/core/cortex_m/cpu_idle.c 中。

在这两种实现中，处理器都会尝试让内核进入低功耗模式。在 k_cpu_idle() 中，处理器最终执行 WFI（Wait For Interrupt，等待中断）指令；而在 k_cpu_atomic_idle() 中，处理器会执行 WFE（Wait For Event，等待事件）指令。

在 Cortex-M 中使用 CPU 空闲 API 时，需要注意以下几点：

  • k_cpu_idle() 和 k_cpu_atomic_idle() 都 假定 是在中断已锁定的情况下被调用的。如果这些 API 由空闲线程调用，内核会负责处理这一点。

  • 从低功耗模式唤醒后，这两个函数都会无条件地 恢复 中断，也就是说，与调用 CPU 空闲 API 之前的中断锁定状态无关。

Zephyr 的 CPU 空闲机制详见 CPU 空闲。

内存保护特性

本节介绍 Arm Cortex-M 应用程序中与内存保护特性相关的若干方面。

用户模式系统调用

实现了标准（Arm）MPU 或类似的内核外设逻辑（用于配置和控制内存访问策略，例如 Kinetis 平台上的 NXP MPU）的 Cortex-M 平台支持用户模式。（目前，如果用户在开发板默认 Kconfig 设置中启用了 CONFIG_ARM_MPU，就会选择 CONFIG_ARCH_HAS_USERSPACE。）

线程通过触发一个（同步的）SVC 异常来执行系统调用，其中：

  • 最多 5 个参数放在寄存器 R1 - R5 中

  • 系统调用 ID 放在寄存器 R6 中。

SVC 处理程序会跳转到系统调用准备逻辑，该逻辑执行以下操作：

  • 将线程的 PSP 切换为指向线程特权栈区域的起始位置；如果启用了栈界限检查，还可选地重新编程 PSPLIM

  • 修改 CONTROL 寄存器以切换到特权模式

  • 修改 SVC 异常栈帧中的返回地址，使异常返回后执行系统调用分派器（在线程特权模式下）

系统调用执行完成后，系统调用分派器会恢复用户原来的 PSP 和 PSPLIM，并将 CONTROL 寄存器切换回非特权模式，然后返回到系统调用的调用者。

系统调用在线程模式下执行，随时可能被中断抢占。线程在执行系统调用期间也可能被上下文切换换出；一旦线程再次被换入，系统调用就会继续执行。

系统调用分派器以 SVC 优先级执行，因此不会被硬件中断抢占（ZLI 除外）；如果硬件中断发生在系统调用准备期间，可能会观察到一些额外的中断延迟。

MPU 辅助的栈溢出检测

带有 MPU 的 Cortex-M 平台可以启用 CONFIG_MPU_STACK_GUARD，以启用基于 MPU 的栈溢出检测机制。启用 MPU 栈保护区时需要考虑以下几点：

  • 栈溢出一旦发生就会立即触发处理器故障

  • 该机制对于检测监督者（supervisor）线程或处于特权模式的用户线程中的栈溢出至关重要；无论是否设置了 CONFIG_MPU_STACK_GUARD，处于用户模式的线程中的栈溢出总是会被检测到。

  • 栈溢出总能被检测到，但当监督者线程的栈内存溢出时，该机制并不能保证不发生内存损坏

  • CONFIG_MPU_STACK_GUARD 通常会保留一个 MPU 区域用于编程栈保护区（在启用了 CONFIG_MPU_GAP_FILLING 的某些 Arm v8-M 配置中，实现保护区功能需要 2 个 MPU 区域）

  • 每次上下文切换时都会重新编程 MPU 保护区，这会给线程切换例程带来少量开销。不过，与 CONFIG_BUILTIN_STACK_GUARD 功能相比，系统调用期间不会进行重新编程。

  • 在 Arm v8-M 平台上启用 CONFIG_HW_STACK_PROTECTION 时，默认使用原生的栈界限检查机制，而不是基于 MPU 的栈溢出检测机制；在这些场景下，用户可以通过手动启用 CONFIG_MPU_STACK_GUARD 来覆盖这一设置。

指针认证和分支目标识别（PACBTI）

Armv8.1-M 指针认证和分支目标识别（Pointer Authentication and Branch Target Identification，PACBTI）扩展是 Armv8.1-M 架构配置文件的一个可选扩展，由以下控制流完整性方法的实现组成：

  • 返回地址签名和认证（PAC-RET），用于缓解面向返回编程（Return Oriented Programming，ROP）类攻击。

  • BTI 指令放置（BTI），用于缓解面向跳转编程（Jump Oriented Programming，JOP）类攻击。

当存在硬件支持（例如 Cortex-M85）并且编译器支持可用时，可以在构建时通过选择以下配置之一在 Zephyr 中启用 PACBTI：

  • CONFIG_ARM_PACBTI_STANDARD

  • CONFIG_ARM_PACBTI_PACRET

  • CONFIG_ARM_PACBTI_PACRET_LEAF

  • CONFIG_ARM_PACBTI_BTI

  • CONFIG_ARM_PACBTI_PACRET_BTI

  • CONFIG_ARM_PACBTI_PACRET_LEAF_BTI

  • CONFIG_ARM_PACBTI_NONE

这些配置选项确保在构建中添加启用 PACBTI 指令的编译器标志，具体为：

  • 对于 GCC 工具链，为 -mbranch-protection=。

此外，CONFIG_ARM_PAC 和 CONFIG_ARM_BTI 会根据为 CONFIG_ARM_PACBTI 选择的分支保护选项自动选中。这些配置选项通过在 CONTROL 寄存器和 FVP 中启用相应的 PACBTI 位来强制启用 PACBTI。

为了进一步增强指针认证，Zephyr 支持通过启用 CONFIG_ARM_PAC_PER_THREAD 来使用密码学安全的、每线程独立的 PAC 密钥。有关密钥生成来源和配置的更多详细信息，请参阅 CONFIG_ARM_PAC_PER_THREAD 的 Kconfig 帮助。

限制：

  • 只有面向具备 PACBTI 硬件支持的 Armv8.1-M Mainline 处理器（例如 Cortex-M85）的构建才能完整使用该功能。

  • Zephyr 集成的 SDK 目前包含的是 GCC 12.2，它不支持 PACBTI，因此必须使用外部 GCC 工具链（推荐 14.3 或更高版本）来获得 PACBTI 支持。有关如何设置工具链，请参阅此文档。

有关 PACBTI 的更多信息，请参阅官方 Arm 文档 以及 Arm 社区博客

内存映射和 MPU 注意事项

固定 MPU 区域

默认情况下，启用 CONFIG_ARM_MPU 后，会在系统启动期间编程一组 固定 的 MPU 区域。

  • 一个 MPU 区域将整个 Flash 区域编程为可读可执行。用户可以通过启用 CONFIG_MPU_ALLOW_FLASH_WRITE 覆盖该设置，此时 Flash 会以 RWX 权限进行编程。如果启用了 CONFIG_USERSPACE，则允许对整个 Flash 区域进行非特权访问。

  • 一个 MPU 区域将整个 SRAM 区域编程为仅特权模式可读写（RW）。也就是说，使用一个 MPU 区域来禁止 SRAM 上的执行权限。（此设置的一个例外是禁用了 CONFIG_MPU_GAP_FILLING 的情况（仅限 Arm v8-M）；此时不会对 SRAM 进行 MPU 编程，访问权限由默认的 Arm 内存映射策略决定，即 SRAM 上允许仅特权模式的 RWX 权限。）

  • 设备树中所有带有 zephyr,memory-attr 属性的内存区域，该属性定义了该内存区域的 MPU 权限。更多详细信息请参阅下一节。

上述 MPU 区域定义在 arch/arm/core/mpu/arm_mpu_regions.c 中。可以通过启用 CONFIG_CPU_HAS_CUSTOM_FIXED_SOC_MPU_REGIONS 来使用其他 MPU 配置。启用该选项表示 Cortex-M SoC 将在 SoC 定义中定义并配置自己的固定 MPU 区域。

设备树中定义的固定 MPU 区域

当内存节点中存在 zephyr,memory-attr 属性时，会在系统启动期间分配并编程一个新的 MPU 区域。当与 zephyr,memory-region 设备树 compatible 一起使用时，还会生成一个与该 MPU 区域关联的链接器段。

例如，在设备树中定义一个新的不可缓存内存区域：

sram_no_cache: memory@20300000 {
     compatible = "zephyr,memory-region", "mmio-sram";
     reg = <0x20300000 0x100000>;
     zephyr,memory-region = "SRAM_NO_CACHE";
     zephyr,memory-attr = <DT_MEM_ARM_MPU_RAM_NOCACHE>;
};

这会自动创建一个新的 MPU 条目，其名称、基地址、大小和属性都直接从设备树中获取。更多详细信息请参阅 缓存基础 和 内存属性。

静态 MPU 区域

可以在系统启动期间额外编程一次一些 静态 MPU 区域。启用某些功能需要这些区域。更多详细信息请参阅 缓存基础。

  • 当启用了 CONFIG_ARCH_HAS_RAMFUNC_SUPPORT 并且用户定义了要从 SRAM 执行的函数时，一个允许从 SRAM 执行的 RX 区域。

  • 当启用了 CONFIG_CODE_DATA_RELOCATION_SRAM 时，一个用于将代码（text）段重定位到 SRAM 的 RX 区域

  • 当启用了 CONFIG_NOCACHE_MEMORY 时，一个用于提供不可缓存 SRAM 区域的 nocache 区域

  • 当启用了 CONFIG_COVERAGE_GCOV 时，一个用于 GCOV 代码覆盖率统计区域的、可能允许非特权访问的 RW 区域

  • 当启用了 CONFIG_NULL_POINTER_EXCEPTION_DETECTION_MPU 时，一个用于实现空指针解引用检测的禁止访问区域

这些静态 MPU 区域的边界由链接器在 include/linker/linker-defs.h 中导出的符号得出。

动态 MPU 区域

某些线程专属的 MPU 区域可能会在每次线程上下文切换时动态重新编程：

  • 一个用于当前线程栈区域的非特权 RW 区域（针对用户线程）

  • 一个用于 MPU 栈保护区的只读区域

  • 用于当前线程应用程序内存域中各分区的非特权 RW 区域。

注意事项

Cortex-M 平台上可用的 MPU 区域数量是有限的资源。大多数平台有 8 个 MPU 区域，而某些 Cortex-M33 或 Cortex-M7 平台最多可有 16 个 MPU 区域。因此，可以同时编程的固定、静态和动态 MPU 区域数量受到相对严格的限制。对于有 8 个可用 MPU 区域的平台，可能无法启用上述所有需要编程 MPU 区域的功能。不过，在大多数实际应用中只需要其中的一部分功能，很多情况下 8 个 MPU 区域就足够了。

在 Arm v8-M 处理器中，MPU 架构不允许已编程的 MPU 区域相互重叠。CONFIG_MPU_GAP_FILLING 控制是否编程覆盖整个 SRAM 的固定 MPU 区域。如果编程该区域，就需要对整个 SRAM 区域进行分区，才能编程静态和动态 MPU 区域，这会增加所需 MPU 区域的总数。如果未启用 CONFIG_MPU_GAP_FILLING，则不会编程覆盖整个 SRAM 的固定 MPU 区域，静态和动态区域只需编程在始终存在的背景区域之上即可（无需对整个 SRAM 进行分区）。但需要注意，背景 SRAM 区域允许从 SRAM 执行代码，因此当未设置 CONFIG_MPU_GAP_FILLING 时，Zephyr 无法防御试图从 SRAM 执行恶意代码的攻击。

浮点服务

Cortex-M 同时支持非共享和共享浮点寄存器模式（更多详细信息请参阅 浮点服务）。

当构建中启用了 FPU 支持（启用了 CONFIG_FPU）时，默认会启用共享浮点寄存器模式（CONFIG_FPU_SHARING）。这是因为某些编译器配置可能会为任何线程生成浮点指令，从而激活浮点上下文，而不管该线程是否执行浮点计算；在换入和换出这类线程时，必须保留该上下文。

如果能够保证镜像代码只在允许（并且预期）生成浮点指令的单个线程上下文中生成浮点指令，开发者仍然可以在其应用程序项目中禁用浮点共享模式，并切换到非共享浮点寄存器模式。

在 FPU 共享模式下，如果相应线程有活动的浮点上下文，则会在上下文切换时保存和恢复被调用者保存的 FPU 寄存器。这会给切换例程增加一些运行时开销。除了运行时开销之外，共享 FPU 模式还：

  • 需要为每个线程额外分配内存，用于保存被调用者保存的浮点寄存器

  • 需要为每个线程额外分配栈内存，以便在浮点上下文处于活动状态时，在进入异常时压栈调用者保存的浮点寄存器。但需要注意，由于启用了惰性压栈（lazy stacking），常规中断中不存在浮点上下文压栈的运行时开销（浮点状态的保存只在 PendSV 中断的切换例程中激活）。

其他

可链式加载的镜像

Cortex-M 应用程序既可以是独立镜像，也可以是可链式加载的镜像，例如由引导加载程序加载。可由引导加载程序（或其他应用程序）链式加载的应用程序镜像，通常占用 Flash 中一块特定的区域，称为其 代码分区。CONFIG_USE_DT_CODE_PARTITION 可确保 Zephyr 可链式加载的镜像被链接到设备树中指定的代码分区中。

启动时的硬件初始化

为了正常启动，被链式加载的应用程序可能要求 Arm 内核硬件寄存器和外设被初始化为复位值。启用 CONFIG_INIT_ARCH_HW_AT_BOOT 会使 Zephyr 在启动期间强制将 Cortex-M 内部架构状态初始化为相应 Arm 架构手册中规定的复位值。

软件向量转发

在实现了 VTOR 寄存器的 Cortex-M 平台上（见 CONFIG_CPU_CORTEX_M_HAS_VTOR），可链式加载的镜像通过将镜像向量表的偏移量写入 VTOR 寄存器来重定位 Cortex-M 向量表。

没有 VTOR 寄存器的 Baseline Cortex-M 平台可能无法重定位其向量表，向量表始终位于固定位置。因此，可链式加载的镜像需要另一种方式将硬件中断和系统异常路由到自己的向量表；这是通过软件向量转发实现的。

当引导加载程序镜像启用 CONFIG_SW_VECTOR_RELAY 时，它能够根据可链式加载的应用程序所设置的向量表指针转发异常和中断。后者会设置 CONFIG_SW_VECTOR_RELAY_CLIENT 选项，指示启动序列在 SRAM 中设置向量表指针，以便引导加载程序将异常和中断转发到可链式加载镜像的软件向量表。

虽然该功能是为没有 VTOR 寄存器的处理器设计的，但它也可以用于 Mainline Cortex-M 平台。

代码重定位

Cortex-M 支持代码重定位功能。选择 CONFIG_CODE_DATA_RELOCATION_SRAM 后，Zephyr 会将指定文件中的 .text、data 和 .bss 段重定位并放入 SRAM。可以只将部分代码段重定位到 SRAM，而无需重定位整个镜像的代码和数据段。有关代码重定位功能的更多详细信息，请参阅 代码和数据重定位。

链接 Cortex-M 应用程序

大多数 Cortex-M 平台使用 include/zephyr/arch/arm/cortex_m/scripts/linker.ld 中默认的 Cortex-M GCC 链接器脚本，不过平台也可以使用自定义链接器脚本。

CMSIS

Cortex-M CMSIS 头文件通过独立的模块仓库提供：

  • CMSIS 5：zephyrproject-rtos/cmsis

  • CMSIS 6：zephyrproject-rtos/CMSIS_6

Zephyr 已开始过渡到以 CMSIS 6 作为 Cortex-M 内核头文件的默认来源。不过，目前 Zephyr 会同时包含 CMSIS 6 和旧版 CMSIS 5 模块中的头文件。

旧版 CMSIS 5 头文件主要是为了与厂商 HAL 保持兼容而保留的，所有新的架构级开发都应尽可能使用 CMSIS 6 头文件。

CONFIG_CPU_CORTEX_M 会选择 CONFIG_HAS_CMSIS_CORE，以表示所有受支持的 Cortex-M 变体都可以使用 CMSIS 头文件。

测试

tests/arch/arm/ 中提供了一系列针对 Cortex-M 移植和其他功能的单元测试。这些测试套件在持续扩充，并不断添加新的测试套件，以提高 Zephyr 中 Cortex-M 架构支持的覆盖率。
