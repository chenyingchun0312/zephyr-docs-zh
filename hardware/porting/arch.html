架构移植指南

要让 Zephyr 运行在目前尚不支持的 ISA 或 ABI 上，就需要进行架构移植。

以下是 Zephyr 支持的 ISA 和 ABI 的一些示例：

  • 采用 System V ABI 的 x86_32 ISA

  • 采用 Thumb2 指令集和 ARM 嵌入式 ABI（aeabi）的 ARMv7-M ISA

  • ARCv2 ISA

有关 Kconfig 配置的信息，请参阅 设置 Kconfig 配置值。架构使用与开发板类似的 Kconfig 配置方案。

架构移植可以分为若干部分，大部分是必需的，少数是可选的：

  • 早期启动序列：CPU 退出复位时，每种架构都有各自必须执行的步骤（必需）。

  • 中断和异常处理：每种架构都以特定的方式处理异步事件和非请求事件（必需）。

  • 线程上下文切换：Zephyr 的上下文切换依赖于 ABI，而每种 ISA 需要保存的寄存器集合各不相同（必需）。

  • 线程创建和终止：线程的初始栈帧与 ABI 和架构相关，线程中止可能也是如此（必需）。

  • 设备驱动：系统时钟定时器和中断控制器通常与架构紧密相关（部分必需，部分可选）。

  • 工具库：出于性能考虑，一些常用的内核 API 依赖于特定于架构的实现（必需）。

  • CPU 空闲/电源管理：大多数架构都实现了让 CPU 进入睡眠的指令（部分可选，但很可能非常需要）。

  • 故障管理：用于实现特定于架构的调试辅助，以及处理线程中的致命错误（部分可选）。

  • 链接器脚本和工具链：构建系统和链接镜像时很可能需要特定于架构的细节（必需）。

  • 内存管理和内存映射：关于支持内存管理和内存映射的特定于架构的细节。

  • 栈对象：关于栈对象相关内存保护硬件的特定于架构的细节。

  • 用户模式线程：用于支持用户模式下的线程。

  • GDB Stub：用于支持 GDB stub，以实现远程调试。

早期启动序列

早期启动序列的目标是将系统从复位后的状态带到能够运行 C 代码的状态，从而可以执行通用的内核初始化序列。大多数情况下只需要很少的步骤，但有些架构需要做更多的工作。

所有架构的通用步骤：

  • 设置初始栈。

  • 如果运行的是 XIP 内核，则将已初始化的数据从 ROM 复制到 RAM。

  • 如果没有使用 ELF 加载器，则将 BSS 段清零。

  • 跳转到早期内核初始化函数 z_cstart()

    • z_cstart() 负责从启动时运行的伪上下文切换到 main 线程。

必须执行的特定于架构的步骤示例：

  • 在 x86_32 上，如果以实模式获得控制权，则切换到 32 位保护模式。

  • 在 x86_32 上设置段寄存器，以应对引导加载程序将其留在未知或损坏状态的情况。

  • 在 Cortex-M3/4 上初始化开发板特定的看门狗。

  • 在 Cortex-M 上将栈从 MSP 切换到 PSP。

  • 在 Cortex-M 上采用不同于调用 z_swap() 的方式，以避免竞态条件。

  • 在 ARCv2 上设置 FIRQ 和常规 IRQ 处理。

早期启动序列钩子

Zephyr 提供了若干钩子（见 include/zephyr/platform/hooks.h），允许在启动过程的特定时刻执行 SoC 或开发板特定的代码。

大部分钩子由内核在与架构无关的代码中调用。但有些钩子必须在早期启动序列中调用；由于该序列是在特定于架构的代码中实现的，这些钩子的调用也必须在那里完成。下面粗略概述了早期启动序列，以及特定于架构的代码应在何时调用这些钩子：

  1. 执行从一个特定于架构的入口点开始，其名称与 CONFIG_KERNEL_ENTRY 一致。

  2. 立即重新初始化特定于架构的状态（如果启用了 CONFIG_INIT_ARCH_HW_AT_BOOT）。

  3. 调用 soc_early_reset_hook()。

    备注

    调用此钩子之前无需设置有效的栈。不过，该钩子可以在返回前覆盖栈指针。特定于架构的代码不得假定栈指针寄存器的值在调用 soc_early_reset_hook() 前后保持不变。

    在具有多个栈指针的架构上，通常有一个可直接访问的 “主” 栈指针，以及一个或多个 “辅助” 栈指针寄存器。soc_early_reset_hook() 的实现可以覆盖 “主” 栈指针，但 不得 读取或修改任何 “辅助” 栈指针的值。（这样特定于架构的代码就可以在调用 soc_early_reset_hook() 之前按需设置任何 “辅助” 栈指针。）

    例如，ARM Cortex-A 架构定义了多种执行模式，每种模式都有自己的栈指针寄存器 sp_mode。处理器在模式 X 下执行时，涉及通用寄存器 sp 的操作作用于 sp_X。在该架构上，假设调用 soc_early_reset_hook() 时处理器正在模式 M 下执行，则该钩子可以覆盖 sp_M（通过 sp 访问），但 不得 读取或覆盖任何其他 sp_mode（其中 mode != M）。

    soc_early_reset_hook() 的实现可以不把执行权交还给特定于架构的代码，此时它们会“接管”系统。这类钩子不受上述规则约束，可以读取或覆盖任何栈指针。不过，提供这样的实现时，早期启动序列的其余部分显然就不会执行了。

  4. 为早期启动序列的后续步骤设置初始栈。

  5. 执行特定于架构的“从挂起到 RAM 恢复”逻辑

    备注

    详情请参阅 CONFIG_PM_S2RAM 以及特定于架构的实现，但请注意，如果该逻辑判定正在从挂起到 RAM 状态退出，早期启动序列的其余部分将不会执行。

  6. 调用 soc_reset_hook()。

  7. 在此执行特定于架构的操作（汇编）……

  8. 调用 z_prep_c()。这个特定于架构的函数用 C 实现。

  9. z_prep_c() 立即调用 soc_prep_hook()。

  10. 在此执行特定于架构的操作（C）……

  11. 调用 z_cstart()。开始执行与架构无关的代码。

中断和异常处理

每种架构对中断和异常处理的定义各不相同。

当设备想要通知处理器有一些工作需要代为处理时，它会触发一个中断。当线程执行了软件自身顺序流程无法处理的操作时，会触发一个异常。中断和异常都会把控制权交给一个处理程序。对于中断，该处理程序称为 ISR。处理程序完成异常或中断所要求的工作。对于中断，这些工作是设备特定的。对于异常，则取决于具体的异常，但大多数情况下由内核本身负责提供处理程序。

除了处理程序本身执行的工作外，内核还必须执行一些工作。例如：

  • 在把控制权交给处理程序之前：

    • 保存当前正在执行的上下文。

    • 可能需要退出省电模式，包括唤醒设备。

    • 如果正在退出无节拍（tickless）空闲模式，则更新内核运行时间。

  • 从处理程序重新获得控制权之后：

    • 决定是否执行上下文切换。

    • 执行上下文切换时，恢复要切换进来的上下文。

这些工作在各种架构上概念相同，但细节完全不同：

  • 需要保存和恢复的寄存器。

  • 执行这些工作的处理器指令。

  • 异常的编号。

  • 等等。

因此需要一个特定于架构的实现，称为中断/异常桩（stub）。

另一个问题是，内核将 ISR 的签名定义为：

void (*isr)(void *parameter)

各种架构在向 ISR 传递参数方面没有一致的或原生的方式。因此，处理该参数常用的方法有两种。

  • 利用某种架构定义的机制，在桩中强制设置参数值。这在基于 X86 的架构中很常见。

  • 通过一个单独的表插入和跟踪 ISR 的参数，这要求架构在运行时判断正在执行的是哪个中断。为真实中断向量表的所有条目安装一个通用的中断处理程序分发器，再由它从单独的表中取出设备的 ISR 和参数。ARC 和 ARM 架构通过 CONFIG_GEN_ISR_TABLES 实现普遍采用这种方法。桩的示例可以参考 x86 中的 _interrupt_enter()、ARM 中的 _isr_wrapper()，或 arch/arc/core/isr_wrapper.S 中对 ARC 完整实现的说明。

每种架构还必须实现中断控制原语：

  • 锁定中断：irq_lock()、irq_unlock()。

  • 注册中断：IRQ_CONNECT()。

  • 在可能的情况下设置优先级：irq_priority_set()。

  • 启用/禁用中断：irq_enable()、irq_disable()。

备注

IRQ_CONNECT 是一个宏，它利用汇编器和/或链接器脚本技巧在构建时连接中断，从而节省启动时间和代码段大小。

向量表应为每个可能发生的中断和异常包含一个处理程序。处理程序可以简单到只是一个自旋循环。不过我们强烈建议处理程序至少打印一些调试信息。当遇到属于故障的异常（例如除零或非法内存访问），或遇到非预期的中断（伪中断，spurious interrupt）时，这些信息有助于找出问题所在。示例请参阅 arch/arm/core/cortex_m/fault.c 中的 ARM 实现。

线程上下文切换

多线程是内核存在的根本目的。Zephyr 支持两种线程：可抢占线程和协作式线程。决定下一个调度哪个线程的规则由内核处理。但上下文切换本身的方法要由架构移植来实现。

Zephyr 为上下文切换提供了两种互斥的接口。首选接口是 arch_switch，在启用 CONFIG_USE_SWITCH 时选用。另一种接口是 arch_swap，在禁用 CONFIG_USE_SWITCH 时选用。移植到新架构时，只需实现其中之一；但对于 SMP 平台，必须实现 arch_switch。

上下文切换可能在以下几种情况下发生：

  • 线程执行阻塞操作时，例如获取当前不可用的信号量。

  • 可抢占线程通过释放某个对象，解除了阻塞在该对象上的更高优先级线程的阻塞时。

  • 中断解除了一个比当前执行线程优先级更高的线程的阻塞，且当前执行线程是可抢占线程时。

  • 线程运行结束时。

  • 线程引发致命异常并被从运行线程中移除时。例如，访问了非法内存。

因此，上下文切换必须能够处理所有这些情况。

上下文切换有两种类型：协作式（cooperative）和抢占式（preemptive）。

  • 当一个线程主动把控制权交给另一个线程时，就会发生 协作式 上下文切换。这有两种情况：

    • 线程显式让出（yield）时。

    • 线程尝试获取一个当前不可用的对象，并愿意等待该对象变为可用时。

  • 当 ISR 或线程执行的某个操作调度了一个比当前运行线程优先级更高的线程，且当前运行线程是可抢占线程时，就会发生 抢占式 上下文切换。此类操作的一个例子是释放更高优先级线程正在等待的对象。

备注

当正在运行的是协作式线程时，控制权永远不会被夺走。

协作式上下文切换总是由线程调用内核内部例程 z_swap（或其变体之一）来完成。该例程再相应地调用 arch_switch 或 arch_swap。调用它们时，不会再检查是否要进行上下文切换，上下文切换必定发生。

备注

在 32 位 x86 上，arch_swap 足够通用、架构也足够灵活，因此可以在退出中断时调用它来触发上下文切换。但这不应被视为惯例，因为 ARM Cortex-M 和 ARCv2 移植都没有这样做。

由于 z_swap 是协作式的，ABI 规定的调用者保存寄存器已经在栈上了。无需将它们保存到 k_thread 结构中。

上下文切换也可以以抢占方式执行。这发生在退出 ISR 时，位于内核的中断退出桩中：

  • x86 上调用处理程序之后的 _interrupt_enter。

  • ARM 上的 z_arm_exc_exit 和 z_arm_int_exit。

  • ARCv2 上的 _firq_exit 和 _rirq_exit。

决定是否执行上下文切换的逻辑很简单，并且只在退出非嵌套中断时执行：

启用 CONFIG_USE_SWITCH 时……

  • 中断退出代码应调用 z_get_next_switch_handle()，并返回到由所返回的 switch 句柄标识的线程上下文

未启用 CONFIG_USE_SWITCH 时……

  • 中断退出代码应从就绪队列中取出缓存的线程，并且：

    • 如果缓存的线程不是当前线程，则执行上下文切换。

    • 否则不执行。

这很简单，但至关重要：如果实现不正确，内核将无法按预期工作，并会出现各种离奇的崩溃，主要原因是栈损坏。

线程创建和终止

要启动一个新线程，必须构造一个栈帧，使上下文切换能够像弹出一个已被切换出去的线程的栈帧那样弹出它。这应在一个特定于架构的内部例程 _new_thread 中实现。

线程入口点也不能被直接调用，即不应将其设置为新线程的 PC。而是必须用 _thread_entry 包装。这意味着栈帧中的 PC 应设置为 _thread_entry，线程入口点则作为第一个参数传给 _thread_entry。具体细节取决于 ABI。

是否需要特定于架构的线程终止实现取决于具体架构。存在一个通用实现，但它未必适用于某个特定架构。

已遇到过的一个需要特定于架构的线程终止实现的原因是：线程因正常退出而中止，与因异常而中止，处理方式可能不同。ARM Cortex-M 就是如此：如果线程触发了致命异常，CPU 必须退出处理程序模式；而如果线程从其入口函数正常退出，则不需要。

这意味着需要实现特定于架构的 k_thread_abort() 版本，并根据架构需要设置 Kconfig 选项 CONFIG_ARCH_HAS_THREAD_ABORT（例如参见 arch/arm/core/cortex_m/Kconfig）。

线程本地存储

要在新架构上启用线程本地存储：

  1. 实现 arch_tls_stack_setup()，在栈中设置 TLS 存储区。存储区需要如何组织，请参阅工具链文档。可以使用以下辅助函数：

    • 函数 z_tls_data_size() 返回线程本地变量所需的大小（不包括工具链和架构所需的任何额外数据）。

    • 函数 z_tls_copy() 为线程本地变量准备 TLS 存储区。它只复制变量本身，不处理特定于架构和/或工具链的数据。

  2. 在上下文切换中，取出新线程 struct k_thread 中的 tls 字段，放入合适的寄存器（或其他某个变量）中，以便访问 TLS 存储区。应使用哪些寄存器，请参阅工具链和架构文档。

  3. 在 Kconfig 中，向与新架构相关的 Kconfig 添加 select ARCH_HAS_THREAD_LOCAL_STORAGE。

  4. 运行 tests/kernel/threads/tls，确保新代码能够正常工作。

设备驱动

内核运行所需的硬件设备很少。理论上，唯一必需的设备是中断控制器，因为内核可以在没有系统时钟的情况下运行。但实际上，要运行健全性检查测试套件中的大部分（甚至全部）测试，还需要系统时钟。由于这两者通常与架构紧密相关，它们属于架构移植的一部分。

中断控制器

不同架构的中断控制器和中断概念可能存在很大差异。

例如，x86 有 IDT 的概念以及不同的中断控制器。中断在 IDT 中的位置决定了它的优先级。

另一方面，ARM Cortex-M 将 NVIC 作为架构定义的一部分。不需要在 NVIC 向量表之外再设一张类似 IDT 的表。IRQ 在表中的位置与其优先级无关：优先级可以按条目编程设置。

ARCv2 的中断单元也是架构定义的一部分，与 NVIC 有些类似。不过，ARC 将异常号与中断号定义为一一对应（即异常 1 就是 IRQ1，设备 IRQ 从 16 开始），而 ARM 中 IRQ0 等同于异常 16（奇怪的是，异常 1 可以视为 IRQ-15）。

所有这些差异意味着，在中断控制器方面，不同架构之间几乎无法共享任何内容。

系统时钟

x86 的架构定义中包含 APIC 定时器和 HPET。ARM Cortex-M 有 SYSTICK 异常。ARCv2 则有 timer0/1 设备。

内核超时在系统时钟定时器驱动的中断处理程序上下文中处理。

串口控制台

还有一种设备几乎是架构移植的必备设备，因为它对调试非常有用。那就是一个简单的、轮询方式的、只输出的串口驱动，用于发送控制台（printk、printf）输出。

它并非必需，也可以改用 RAM 控制台（CONFIG_RAM_CONSOLE），将所有输出发送到一个可由调试器读取的环形缓冲区中。

工具库

内核依赖于若干函数，在现代处理器上，这些函数可以只用很少的指令或以无锁方式实现。因此，它们应作为架构移植的一部分来实现。

  • 原子操作。

    • 如果给定架构存在相应指令，则通过 Kconfig 选项 CONFIG_ATOMIC_OPERATIONS_ARCH 配置该实现。

    • 如果给定架构不存在相应指令，则有一个通用版本，它在非原子操作两侧包裹 irq_lock() 或 irq_unlock()。该版本通过 Kconfig 选项 CONFIG_ATOMIC_OPERATIONS_C 配置。

  • 查找最低置位位和查找最高置位位。

    • 如果给定架构不存在相应指令，总是可以将这些函数实现为通用 C 函数。

可以使用编译器内建函数来实现它们，但要注意确保其使用了所需的编译器屏障。

CPU 空闲/电源管理

内核通过两个函数提供 CPU 电源管理支持：arch_cpu_idle() 和 arch_cpu_atomic_idle()。

arch_cpu_idle() 可以简单到在中断解锁的情况下调用该架构的省电指令，例如 x86 上的 hlt、ARM 上的 wfi 或 wfe、ARC 上的 sleep。该函数可以在一个循环中调用，所在上下文不在乎进入睡眠之前是否会被中断打断。正确使用该函数的场景基本上有两种：

  • 在单线程系统中，在唯一的线程里使用，且该线程在初始化之后不再执行实际工作，即在应用程序运行期间一直处于什么也不做的循环中。

  • 在空闲线程中。

另一方面，arch_cpu_atomic_idle() 必须能够以原子方式重新启用中断并执行省电指令。因此，它可以用在实际的应用程序代码中，同样是在单线程系统中。

通常，让 CPU 空闲应交由空闲线程处理，但在一些非常特殊的场景下，应用程序也可以使用这些 API。

给定架构必须同时提供这两个函数。不过，如果愿意，其实现可以只是以下步骤：

  1. 解锁中断

  2. NOP

不过，强烈建议提供真正的实现。

故障管理

发生未处理的 CPU 异常时，架构代码必须调用 z_fatal_error()。该函数会转储与架构无关的信息，并通过调用 k_sys_fatal_error() 来决定下一步的处理策略。可以覆盖该函数以实现应用程序特定的策略，例如锁定中断并永远自旋（默认实现），甚至关闭系统电源（如果支持）。

工具链和链接

必须在构建系统中添加工具链支持。

需要在 include/zephyr/toolchain/gcc.h 中添加一些特定于架构的定义。可参考该文件中针对当前已支持架构的现有内容。

每种架构还需要自己的链接器脚本，即使大部分段可以从其他架构的链接器脚本中派生而来。有些段可能是新架构特有的，例如 ARM 上的 SCB 段和 x86 上的 IDT 段。

内存管理和内存映射

如果目标平台启用了分页，并要求驱动对其 I/O 区域进行内存映射，则需要启用 CONFIG_MMU，并实现以下 API：

  • arch_mem_map()

  • arch_mem_unmap()

  • arch_page_phys_get()

栈对象

内存保护硬件的存在会影响栈对象的创建方式。所有架构移植都必须指定栈指针所需的对齐方式，这由 CPU 和 ABI 的要求共同决定。它在架构头文件中通过 ARCH_STACK_PTR_ALIGN 定义，通常是 4、8 或 16 字节这样的较小值。

线程栈有两种类型：

  • “内核”栈：使用 K_KERNEL_STACK_DEFINE() 及相关 API 定义，可以承载运行在监管者模式下的内核线程，也可用作中断/异常处理的栈。它们的对齐要求宽松得多，占用的保留数据也更少。不会为特权提升栈预留内存。

  • “线程”栈：通常占用更多内存，但能够承载运行在用户模式下的线程，也能满足内核栈的所有用例。

如果未启用 CONFIG_USERSPACE，“线程”栈和“内核”栈是等价的。

可以在架构层定义额外的宏，用于指定栈对象基址的对齐方式、栈对象内部不用作线程栈缓冲区的保留数据，以及如何向上取整栈大小以支持用户模式线程。如果没有这些定义，则采用以下默认值：

  • ARCH_KERNEL_STACK_RESERVED：默认无保留空间

  • ARCH_THREAD_STACK_RESERVED：默认无保留空间

  • ARCH_KERNEL_STACK_OBJ_ALIGN：默认按 ARCH_STACK_PTR_ALIGN 对齐

  • ARCH_THREAD_STACK_OBJ_ALIGN：默认按 ARCH_STACK_PTR_ALIGN 对齐

  • ARCH_THREAD_STACK_SIZE_ALIGN：默认向上取整到 ARCH_STACK_PTR_ALIGN

所有栈创建宏都基于这些宏定义。

所有栈对象都具有如下布局，根据配置不同，某些区域的大小可能为零。它始终由两个主要部分组成：开头的保留内存，以及其后的栈缓冲区本身。某些区域的边界只能在运行时、在其关联线程对象的上下文中确定。其他区域则完全可以在构建时计算出来。

某些架构可能需要在运行时从栈缓冲区中划出保留内存，而不是在构建时无条件地预留，或者需要补充现有的保留区域（ARM FPU 就是如此）。这类划出的区域总是记录在 thread.stack_info.start 中。由 thread.stack_info.start 和 thread.stack_info.size 指定的区域总是可以被用户模式线程完全访问。thread.stack_info.delta 表示一个偏移量，可用于从栈对象的最末端计算初始栈指针，其中已考虑了 TLS 存储和 ASLR 随机偏移。

+---------------------+ <- thread.stack_obj
| Reserved Memory     | } K_(THREAD|KERNEL)_STACK_RESERVED
+---------------------+
| Carved-out memory   |
|.....................| <- thread.stack_info.start
| Unused stack buffer |
|                     |
|.....................| <- thread's current stack pointer
| Used stack buffer   |
|                     |
|.....................| <- Initial stack pointer. Computable
| ASLR Random offset  |      with thread.stack_info.delta
+---------------------| <- thread.userspace_local_data
| Thread-local data   |
+---------------------+ <- thread.stack_info.start + thread.stack_info.size

目前，Zephyr 不支持向上增长的栈。

无内存保护

如果未使用内存保护，则默认值就足够了。

基于硬件的栈溢出检测

此选项利用硬件特性，在监管者模式下的线程发生栈溢出时产生致命错误。这对调试很有用，但出于以下几个原因，发生这种情况后无法可靠地对系统状态作出任何断言：

  • 发生溢出时，内核可能正处于临界区内，从而使重要的全局数据结构处于损坏状态。

  • 对于使用保护内存区域实现栈保护的系统，在硬件检测到这种情况之前，有可能越过保护区域并破坏相邻的数据结构。

要启用 CONFIG_HW_STACK_PROTECTION 特性，系统必须提供某种基于硬件的栈溢出保护，并启用 CONFIG_ARCH_HAS_STACK_PROTECTION 选项。

支持两种形式的基于硬件的栈溢出检测：为此专门设计的 CPU 特性，或紧挨在栈缓冲区之前的特殊只读保护区域。

CONFIG_HW_STACK_PROTECTION 只能捕获监管者线程的栈溢出。捕获用户线程的栈溢出并不需要它；CONFIG_USERSPACE 与之相互独立。

此特性只检测监管者模式下的栈溢出，包括处理系统调用时的栈溢出。它不能保证内核未被破坏。监管者模式下的任何栈溢出都应被视为致命错误，无法对整个系统的完整性作出任何断言。

用户模式下的栈溢出（从内核的角度看）是可恢复的，不需要特殊配置；CONFIG_HW_STACK_PROTECTION 只适用于捕获 CPU 处于监管者模式时的溢出。

基于 CPU 的栈溢出检测

如果通过特殊的 CPU 寄存器（例如 ARM 的 SPLIM）检测监管者模式下的栈溢出，则默认值就足够了。

基于保护区域的栈溢出检测

通过紧挨在栈缓冲区之前、写入时会产生异常的特殊内存保护区域来检测监管者模式下的栈溢出。保留内存将用作该保护区域。

ARCH_KERNEL_STACK_RESERVED 应定义为内存保护区域的最小大小。在大多数 ARM CPU 上为 32 字节。还应将 ARCH_KERNEL_STACK_OBJ_ALIGN 设置为该区域所需的对齐方式。

基于 MMU 的系统不应为保护区域保留 RAM，而应在每个栈映射到地址空间时，直接在其下方留出一个不存在的虚拟页。栈对象仍需按页粒度正确对齐并确定大小。

+-----------------------------+ <- thread.stack_obj
| Guard reserved memory       | } K_KERNEL_STACK_RESERVED
+-----------------------------+
| Guard carve-out             |
|.............................| <- thread.stack_info.start
| Stack buffer                |
.                             .

为内核栈划出保护区域的情况并不常见，应尽可能避免。通常在以下两种情况下才需要：

  • 同一个栈可能被改作承载用户线程，此时不需要保护区域，也不应无条件地预留它。当特权提升栈不在栈对象内部时就是这种情况。

  • 所需的保护区域大小可变，取决于上下文。例如，某些 ARM CPU 在异常期间采用惰性浮点压栈，可能会在不写入任何内容的情况下将栈指针减去一个很大的值，从而完全越过最小尺寸的保护区域并破坏相邻内存。与其无条件地预留更大的保护区域，不如在线程使用浮点时再划出额外的内存。

启用用户模式

启用用户模式会带来两项新要求：

  • 必须分配一个大小固定、由 CONFIG_PRIVILEGED_STACK_SIZE 指定、用户线程无法访问的独立特权模式栈。内核在处理系统调用时将其用作栈。如果实现了栈保护，则必须能够在其前面放置一个栈保护区域，必要时还要支持划出区域。

  • 内存保护硬件必须能够设置一个恰好覆盖线程栈缓冲区的区域，该区域记录在 thread.stack_info 中。这意味着 ARCH_THREAD_STACK_SIZE_ADJUST() 需要将请求的栈大小向上取整，使某个区域能够覆盖它；同时 ARCH_THREAD_STACK_OBJ_ALIGN() 也要按照内存保护硬件的粒度来指定。

如果内存保护硬件要求所有内存区域的大小都是 2 的幂并按自身大小对齐，情况会更加复杂。这在较旧的 MPU 上很常见，由 CONFIG_MPU_REQUIRES_POWER_OF_TWO_ALIGNMENT 表示。

thread.stack_info 始终记录栈对象中用户可访问的部分，使用其中存储的范围设置一个允许用户访问的内存保护区域，必须总是正确的。

非 2 的幂内存区域要求

在没有 2 的幂区域要求的系统上，由 K_THREAD_STACK_RESERVED 定义的线程栈保留内存区可以用来容纳特权模式栈。其布局可能如下：

+------------------------------+ <- thread.stack_obj
| Other platform data          |
+------------------------------+
| Guard region (if enabled)    |
+------------------------------+
| Guard carve-out (if needed)  |
|..............................|
| Privilege elevation stack    |
+------------------------------| <- thread.stack_obj +
| Stack buffer                 |      K_THREAD_STACK_RESERVED =
.                              .      thread.stack_info.start

创建线程时，保护区域以及任何划出的区域（如果需要）将被配置为只读区域。

  • 如果线程是监管者线程，特权提升区域只是额外的栈内存。溢出最终会撞上保护区域。

  • 如果线程运行在用户模式下，将配置一个内存保护区域，允许用户线程访问栈缓冲区，但不能访问其前后的任何内容。用户模式下的溢出会撞上用户线程无权访问的特权提升栈。处理系统调用时的溢出会撞上保护区域。

在 MMU 系统上不应有物理保护区域；特权模式栈将映射到内核内存中，栈缓冲区映射到内存的用户部分，二者下方都有不存在的虚拟保护页，用于捕获运行时的栈溢出。

其他平台数据也可以存放在保护区域之前，但如果这些数据可以存放在 thread.arch 中的某处，则强烈不建议这样做。

需要定义 ARCH_THREAD_STACK_RESERVED，以表示包含平台数据、特权提升栈和保护区域的保留区域的大小。其大小必须合适，以便能在其后紧接着放置一个授予用户模式访问栈缓冲区权限的 MPU 区域。

2 的幂内存区域要求

线程栈对象的大小和对齐必须是同一个 2 的幂，且不含任何保留内存，以便在内存中高效排列。因此，线程栈中的任何保护区域都必须完全从栈缓冲区中划出，特权提升栈也必须在其他地方分配。

ARCH_THREAD_STACK_SIZE_ADJUST() 和 ARCH_THREAD_STACK_OBJ_ALIGN() 都应定义为 Z_POW2_CEIL()。K_THREAD_STACK_RESERVED 必须为 0。

对于特权栈，必须启用 CONFIG_GEN_PRIV_STACKS。对于系统中的每个线程栈，都会生成一个对应的、用于处理系统调用的固定大小内核栈。运行时可以使用 z_priv_stack_find() 根据线程栈地址快速查找特权栈的地址。这些栈的布局与其他仅供内核使用的栈相同。

+-----------------------------+ <- z_priv_stack_find(thread.stack_obj)
| Reserved memory             | } K_KERNEL_STACK_RESERVED
+-----------------------------+
| Guard carve-out (if needed) |
|.............................|
| Privilege elevation stack   |
|                             |
+-----------------------------+ <- z_priv_stack_find(thread.stack_obj) +
                                     K_KERNEL_STACK_RESERVED +
                                     CONFIG_PRIVILEGED_STACK_SIZE

+-----------------------------+ <- thread.stack_obj
| MPU guard carve-out         |
| (supervisor mode only)      |
|.............................| <- thread.stack_info.start
| Stack buffer                |
.                             .

线程栈对象中划出的保护区域只在线程运行于监管者模式时使用。如果线程降级到用户模式，就不再有保护区域，整个对象都用作栈缓冲区，关联的用户模式线程拥有完全访问权限，thread.stack_info 也会相应更新。

用户模式线程

要支持用户模式线程，需要实现若干内核到架构的 API，并且系统必须启用 CONFIG_ARCH_HAS_USERSPACE 选项。更多详细信息请参阅以下各函数的文档：

  • arch_buffer_validate()：测试当前线程是否对特定内存区域具有访问权限

  • arch_user_mode_enter()：不可逆地将监管者线程降级为用户模式权限。必须清除栈。

  • arch_syscall_oops()：在无法验证系统调用参数时产生内核 oops，并使该 oops 看起来是在用户线程中调用系统调用的位置产生的

  • arch_syscall_invoke0() 到 arch_syscall_invoke6()：以相应数量的参数调用系统调用，所有参数都必须在特权提升期间通过寄存器传递。

  • arch_is_user_context()：如果 CPU 当前运行在用户模式下，则返回非零值

  • arch_mem_domain_max_partitions_get()：表示一个内存域的最大区域数。MMU 系统没有数量限制，MPU 系统则对此有约束。

某些架构在调用内存域 API 时，可能需要更新软件内存管理结构，或修改另一个 CPU 上的硬件寄存器。若是如此，架构必须 select CONFIG_ARCH_MEM_DOMAIN_SYNCHRONOUS_API，并且必须实现一些额外的 API。这在 MMU 系统上很常见，在 MPU 系统上则不常见：

  • arch_mem_domain_thread_add()

  • arch_mem_domain_thread_remove()

  • arch_mem_domain_partition_add()

  • arch_mem_domain_partition_remove()

详情请参阅这些 API 的 Doxygen 文档。

除了实现这些 API 之外，还有其他一些工作：

  • _new_thread() 需要以用户模式创建带有 K_USER 的线程

  • 上下文切换时，应通过对内存管理硬件进行相应的配置修改，将被换出线程的栈内存标记为用户模式不可访问。被换入线程的栈内存则应相应地标记为可访问。这样可以确保线程无法干扰其他线程的栈。

  • 上下文切换时，系统需要在换入线程和换出线程的内存域之间切换。

  • 线程栈区域必须包含一个内核栈区域。该区域在任何时候都应对用户线程不可访问。进行系统调用时会使用此栈。它对所有线程应为固定大小，并且必须足够大，以便处理任何系统调用。

  • 需要建立一个软件中断或某种特权提升机制。这与 _arch_syscall_invoke 宏的实现方式密切相关。进行系统调用时，需要在 _k_syscall_table 中查找相应的处理函数。错误的系统调用 ID 应跳转到 K_SYSCALL_BAD 处理程序。系统调用完成后，必须注意不要将任何寄存器状态泄漏回用户模式。

GDB Stub

要在新架构上启用用于远程调试的 GDB stub：

  1. 在相应的架构包含目录下新建 gdbstub.h 头文件（include/zephyr/arch/<arch>/gdbstub.h）。

    • 新建一个结构体 struct gdb_ctx 作为 GDB 上下文。

      • 必须定义一个名为 exception、类型为 unsigned int 的成员，用于存储 GDB 异常原因。进入 z_gdb_main_loop() 之前需要设置该值。

      • 架构可以根据 GDB stub 正常工作的需要定义任意数量的成员。

      • 需要将指向该结构体的指针传给 z_gdb_main_loop()，该指针会在那里再传给其他 GDB stub 函数。

  2. 进入和退出 GDB stub 主循环的函数。

    • 如果架构依赖中断来处理断点，则需要实现中断服务例程（ISR），作为 GDB stub 主循环的入口点。

    • 这些函数需要保存和恢复上下文，使代码可以像没有遇到断点一样继续执行。

    • 这些函数需要在保存执行上下文后调用 z_gdb_main_loop()，进入 GDB stub 主循环以接收来自 GDB 的命令。

    • 调用 z_gdb_main_loop() 之前，必须设置 gdb_ctx.exception 以指明异常原因。

  3. 实现支持 GDB stub 功能所需的函数：

    • arch_gdb_init()

      • 此函数需要初始化支持 GDB stub 功能所需的部分，例如设置 GDB 上下文和连接调试中断。

      • 此函数必须通过特定于架构的方法（例如触发调试中断）停止代码执行。这样 GDB 就可以在启动期间连接。

    • arch_gdb_continue()

      • 当 GDB 发送 c 或 continue 命令以继续执行代码时，调用此函数。

    • arch_gdb_step()

      • 当 GDB 发送 si 或 stepi 命令，要求执行一条机器指令后再返回 GDB 提示符时，调用此函数。

    • 硬件寄存器读/写函数：

      • 由于 GDB stub 运行在目标上，对硬件寄存器的操作需要先进行缓存，以免影响 GDB stub 的执行。可以把它想象成上下文切换，执行上下文切换到了 GDB stub。因此需要保存上下文切换前正在运行线程的寄存器值。对寄存器值的操作只能在这份缓存副本上进行。切换回之前运行的线程之前，再把更新后的值写入硬件寄存器。

      • arch_gdb_reg_readall()

        • 此函数收集将出现在 g/G 数据包中、要发回 GDB 的所有硬件寄存器值。G 数据包的格式与架构相关。具体要求请查阅 GDB。

        • 注意，对于大多数架构，必须返回一个有效的 G 数据包并发送给 GDB。如果向 GDB 发送了长度不正确的数据包，GDB 将中止调试会话。

      • arch_gdb_reg_writeall()

        • 此函数接收 GDB 发送的 G 数据包，并用其中的值填充硬件寄存器。

      • arch_gdb_reg_readone()

        • 此函数读取一个硬件寄存器的值，并将结果发送给 GDB。

      • arch_gdb_reg_writeone()

        • 此函数写入从 GDB 接收到的一个硬件寄存器的值。

    • 断点：

      • arch_gdb_add_breakpoint() 和 arch_gdb_remove_breakpoint()

      • GDB 可能会选择使用软件断点，即修改断点位置的内存，将其中的指令替换为软件断点指令或陷阱指令。执行到断点后，GDB 会再恢复原来的内存内容。GDB 默认支持这种方式，通常无需在架构代码中处理软件断点（断点类型为 0）。

      • 如果代码位于运行时无法修改的 ROM 或 Flash 中，则需要硬件断点（类型 1）。如何启用硬件断点，请查阅该架构的数据手册。

      • 如果架构不支持硬件断点，则无需在架构代码中实现这些函数。GDB 将改用软件断点。

  4. 对于某些内存区域不可访问的架构，需要定义一个名为 gdb_mem_region_array、类型为 gdb_mem_region 的数组，用于指定可访问的区域。对于数组中的每一项：

    • gdb_mem_region.start 指定内存区域的起始地址。

    • gdb_mem_region.end 指定内存区域的结束地址。

    • gdb_mem_region.attributes 指定内存区域的权限。

      • GDB_MEM_REGION_RO：区域只读。

      • GDB_MEM_REGION_RW：区域可读写。

    • gdb_mem_region.alignment 指定内存区域的读/写对齐要求。如果没有对齐要求，可以逐字节读写，则使用 0。
