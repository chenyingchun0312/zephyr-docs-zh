SoC 移植指南

本页介绍如何在 Zephyr 中添加对新 SoC 的支持，无论是在上游 Zephyr 项目中，还是在你自己的本地仓库中。

SoC 相关定义

本文假定你已熟悉 Zephyr 中的开发板概念。有关硬件支持层级以及 Zephyr 文档中所用术语的概要介绍，请参阅 硬件支持层级。

对于 SoC 移植，最重要的术语有：

  • SoC：开发板 CPU 所属的具体片上系统。

  • SoC 系列（series）：一组密切相关的 SoC。

  • SoC 家族（family）：一组更宽泛的、具有相似特性的 SoC。

  • CPU 集群：由一个或多个 CPU 核心组成的集群。

  • CPU 核心：某个架构的一个具体 CPU 实例。

  • 架构：指令集架构。

架构

见 架构移植指南。

创建 SoC 目录

每个 SoC 必须有唯一的名称。请使用 SoC 厂商给出的正式名称，并检查该名称是否已被使用。某些情况下，可能已经有人贡献了同名的 SoC。如果 SoC 名称已被使用，那么你或许应该改进现有的 SoC，而不是新建一个。可以使用 list_hardware 脚本获取 Zephyr 中所有已知 SoC 的列表，例如在 Zephyr 根目录下运行 ./scripts/list_hardware.py --soc-root=. --socs，即可列出已被使用的名称。

首先创建目录 zephyr/soc/<VENDOR>/soc1，其中 <VENDOR> 是你的厂商子目录。

备注

如果要将 SoC 贡献给 Zephyr，则必须使用 <VENDOR> 子目录；但如果 SoC 放在本地仓库中，则 <your-repo>/soc 下可以使用任意目录结构。<VENDOR> 子目录必须与 dts/bindings/vendor-prefixes.txt 列表中定义的某个厂商一致。如果该 SoC 厂商在列表中没有前缀，则必须新建一个。

备注

SoC 目录名不必与 SoC 名称一致，甚至可以在一个目录中定义多个 SoC。在 Zephyr 中，SoC 通常组织在公共 SoC 家族或 SoC 系列目录树下的子文件夹中。

SoC 目录结构应如下所示：

soc/<VENDOR>/<soc-name>
├── soc.yml
├── soc.h
├── CMakeLists.txt
├── Kconfig
├── Kconfig.soc
└── Kconfig.defconfig

将 <soc-name> 替换为你的 SoC 名称。

必需的文件有：

  1. soc.yml：描述 SoC 高层元数据的 YAML 文件，例如：

    • SoC 名称：SoC 的名称

    • CPU 集群：如果 SoC 包含一个或多个集群，则列出这些 CPU 集群

    • SoC 系列：该 SoC 所属的 SoC 系列

    • SoC 家族：该系列所属的 SoC 家族

  2. soc.h：可用于描述 SoC 或提供 SoC 配置宏的头文件。Zephyr 中的驱动、子系统、开发板及其他源代码经常会包含 soc.h。

  3. Kconfig.soc：SoC 的基础配置，以 config SOC_<soc-name> 的形式定义 Kconfig SoC 符号，并将 SoC 名称提供给 Kconfig 的 SOC 设置。如果 soc.yml 描述了 SoC 家族和系列，则它们也必须在此文件中定义。不得 select SoC 目录树之外的 Kconfig 设置。要选择通用的 Zephyr Kconfig 设置，必须使用 Kconfig 文件。

  4. CMakeLists.txt：由 Zephyr 构建系统加载的 CMake 文件。此 CMake 文件可以定义以该 SoC 为构建目标时要使用的额外包含路径和/或源文件。此外还必须定义要使用的基础链接器脚本。

可选的文件有：

  • Kconfig、Kconfig.defconfig：配置系统（Kconfig） 格式的软件配置。它们用于选择架构和可用的外设。

编写 SoC YAML

SoC YAML 文件从高层描述 SoC 家族、SoC 系列和 SoC。

详细配置（例如硬件描述和配置）在设备树和 Kconfig 中完成。

仅包含一个 SoC 的简单 SoC YAML 文件骨架如下：

socs:
  - name: <soc1>

SoC 文件夹中可以存放多个 SoC。例如，如果它们属于同一家族或系列，建议将这些 SoC 放在一个公共目录树中。公共文件夹中的多个 SoC 和 SoC 系列可以在 soc.yml 文件中这样描述：

family:
  - name: <family-name>
    series:
      - name: <series-1-name>
        socs:
          - name: <soc1>
            cpuclusters:
              - name: <coreA>
              - name: <coreB>
                ...
          - name: <soc2>
      - name: <series-2-name>
        ...

编写 SoC 设备树

SoC 设备树包含文件位于 <zephyr-repo>/dts 文件夹下对应的 <ARCH>/<VENDOR> 中。

SoC 的 dts/<ARCH>/<VENDOR>/<soc>.dtsi 以设备树源（DTS）格式描述 SoC 硬件，所有使用该 SoC 的开发板都必须包含它。

如果存在更高层的 <arch>.dtsi 文件，那么一个不错的起点是在你的 <soc>.dtsi 中包含该文件。

一般来说，<soc>.dtsi 应如下所示：

#include <arch>/<arch>.dtsi

/ {
        chosen {
                /* common chosen settings for your SoC */
        };

        cpus {
                #address-cells = <m>;
                #size-cells = <n>;

                cpu@0 {
                device_type = "cpu";
                compatible = "<compatibles>";
                /* ... your CPU definitions ... */
        };

        soc {
                /* Your SoC definitions and peripherals */
                /* such as ram, clock, buses, peripherals. */
        };
};

提示

为了让文件系统结构更清晰，可以将多个 <VENDOR>/<soc>.dtsi 文件组织在子目录中。例如按 SoC 系列组织，如 <VENDOR>/<SERIES>/<soc>.dtsi。

多个 CPU 集群

设备树反映的是硬件。一个 CPU 集群可用的内存空间和外设可能与另一个 CPU 集群大不相同，因此每个 CPU 集群通常都有自己的 .dtsi 文件。

CPU 集群的 .dtsi 文件应遵循 <soc>_<cluster>.dtsi 命名规则。<soc>_<cluster>.dtsi 文件的内容与不含 CPU 集群的 SoC .dtsi 类似。

编写 Kconfig 文件

Zephyr 使用 Kconfig 语言配置软件特性。在为你的 SoC 编译 Zephyr 应用程序之前，SoC 需要提供一些 Kconfig 设置。

设置 Kconfig 配置值的方法详见 设置 Kconfig 配置值。

SoC 目录中有一个必需的 Kconfig 文件，以及两个可选文件：

soc/<vendor>/<your soc>
├── Kconfig.soc
├── Kconfig
└── Kconfig.defconfig
Kconfig.soc

一个共享的 Kconfig 文件，可以同时被 Zephyr Kconfig 树和 sysbuild Kconfig 树引入（source）。

此文件在 Kconfig 树中选择 SoC 家族和系列，以及其他可能与 SoC 相关的 Kconfig 设置，某些情况下还包括 SOC_PART_NUMBER。此文件不得 select 可复用 Kconfig SoC 树之外的任何内容。

Kconfig.soc 可能如下所示：

config SOC_FAMILY_<SOC_FAMILY_NAME>
        bool

config SOC_SERIES_<SOC_SERIES_NAME>
        bool
        select SOC_FAMILY_<SOC_FAMILY_NAME>

config SOC_<SOC_NAME>
        bool
        select SOC_SERIES_<SOC_SERIES_NAME>

config SOC_FAMILY
        default "<soc_family_name>" if SOC_FAMILY_<SOC_FAMILY_NAME>

config SOC_SERIES
        default "<soc_series_name>" if SOC_SERIES_<SOC_SERIES_NAME>

config SOC
        default "<soc_name>" if SOC_<SOC_NAME>

注意，SOC_NAME 是 SoC 名称的纯大写形式，SOC_SERIES_NAME 是 SoC 系列名称的纯大写形式，SOC_FAMILY_NAME 是 SoC 家族名称的纯大写形式。如果这些字段没有出现在 soc.yml 文件中，那么它们也不应出现在 Kconfig.soc 文件中。

Kconfig 的 SOC、SOC_SERIES 和 SOC_FAMILY 设置在全局范围内定义为字符串，因此 Kconfig.soc 文件只应定义默认的字符串值，而不应定义类型。注意，这些字符串值必须与 soc.yml 文件中使用的值一致。

备注

构建系统支持 soc_name、soc_series_name 和 soc_family_mame 的任意大小写形式，但如果提交开发板以纳入 Zephyr 本身，它们必须是 Kconfig 名称的纯小写形式

Kconfig

由 soc/Kconfig 包含。

此文件可以添加当前 SoC 特有的 Kconfig 设置。

Kconfig 通常会使用 HAS_<support> 形式的设置来表明支持某种硬件。

config SOC_<SOC_NAME>
        select ARM
        select CPU_HAS_FPU

如果设置名称与 Zephyr 中已有的某个 Kconfig 设置相同，并且只修改该设置的默认值，则应改用 Kconfig.defconfig。

Kconfig.defconfig

Kconfig 选项的 SoC 特定默认值。

并非所有 SoC 都有 Kconfig.defconfig 文件。

整个文件应放在一对 if SOC_<SOC_NAME> / endif 或 if SOC_SERIES_<SERIES_NAME> / endif 之间，如下所示：

if SOC_<SOC_NAME>

config NUM_IRQS
        default 32

endif # SOC_<SOC_NAME>

多个 CPU 集群

CPU 集群必须在 Kconfig.soc 文件中提供额外的 Kconfig 设置。其形式通常为 SOC_<SOC_NAME>_<CLUSTER>，因此对于具有 clusterA 和 clusterB 两个集群的 soc1，内容如下：

定义了 CPU 集群的 SoC

config SOC_SOC1_CLUSTERA
        bool
        select SOC_SOC1

config SOC_SOC1_CLUSTERB
        bool
        select SOC_SOC1
