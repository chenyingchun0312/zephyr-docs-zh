概述

控制器局域网（Controller Area Network）是一种两线制串行总线，由 Bosch CAN 规范、Bosch CAN FD（灵活数据速率）规范以及 ISO 11898-1:2003 标准定义。CAN 最为人熟知的是在汽车领域的应用，但它也用于家庭和工业自动化以及其他产品。

警告

只有当总线处于空闲（隐性）状态且持续至少 11 个隐性位时，CAN 控制器才能完成初始化。因此必须确保 CAN RX 为高电平，哪怕只是短时间。回环模式下同样需要满足这一点。

ISO 11898-1:2003 定义的位时序如下：

一个位被分为四个段。

  • Sync_Seg：各节点在 Sync_Seg 的边沿进行同步。其长度固定为一个时间量子。

  • Prop_Seg：总线的信号传播延迟以及收发器和节点的其他延迟。

  • Phase_Seg1 和 Phase_Seg2：定义采样点。位在 Phase_Seg1 结束时被采样。

位速率根据时间量子的时长和上述各值计算。一个位的长度等于 Sync_Seg、Prop_Seg、Phase_Seg1 与 Phase_Seg2 之和乘以单个时间量子的时长。位速率是单个位长度的倒数。

位在采样点处被采样。采样点位于 Phase_Seg1 和 PhaseSeg2 之间，因此是需要用户选择的参数。CiA 建议将采样点设置在位的 87.5% 处。

再同步跳转宽度（SJW）定义了采样点可以移动的时间量子数。需要再同步时，采样点会被移动。

时序参数（SJW、位速率和采样点，或者位速率、Prop_Seg、Phase_Seg1 和 Phase_Seg2）最初由设备树设置，并可在运行时通过时序 API 修改。

CAN 使用所谓的标识符来标识帧，而不是用地址来标识节点。标识符可以是 11 位宽（标准帧或基本帧），扩展帧则为 29 位。Zephyr CAN API 同时支持标准标识符和扩展标识符。CAN 帧以一个显性的帧起始（Start Of Frame）位开始，之后是标识符。这一阶段称为仲裁阶段。仲裁阶段允许发生写冲突，冲突通过显性位覆盖隐性位的方式解决。各节点监视总线，发现自己的发送被覆盖时便中止发送。这样一来，数值较小的标识符实际上就比数值较大的标识符拥有更高的优先级。

过滤器用于将特定节点关心的标识符列入允许列表。不匹配任何过滤器的标识符会被忽略。过滤器既可以精确匹配，也可以只匹配标识符的指定部分，这种方法称为掩码。例如，对于标准标识符，11 位全部置位的掩码要求完全匹配；对于扩展标识符则是 29 位全部置位。匹配标识符时，掩码中为零的位会被忽略。大多数 CAN 控制器在硬件中只实现了有限数量的过滤器。为了节省内存，Kconfig 中也限制了过滤器的数量。

传输过程中可能出现错误。节点检测到错误帧时，会用错误帧部分覆盖当前帧。根据控制器的状态，错误帧可以是被动错误帧或主动错误帧。控制器处于主动错误状态时，会发送六个连续的显性位，这违反了位填充规则，所有节点都能检测到。发送方随后可以重新发送该帧。

已初始化的节点可能处于以下状态之一：

  • 主动错误（Error-active）

  • 被动错误（Error-passive）

  • 总线关闭（Bus-off）

初始化后，节点处于主动错误状态。在此状态下，节点可以发送主动错误帧、ACK 和过载帧。每个节点都有接收错误计数器和发送错误计数器。如果接收错误计数器或发送错误计数器超过 127，节点进入被动错误状态。在此状态下，节点不再允许发送主动错误帧。如果发送错误计数器继续增加到 255，节点进入总线关闭状态。在此状态下，节点不允许向总线发送任何显性位。处于总线关闭状态的节点在接收到 128 次 11 个连续隐性位后可以恢复。

关于 CAN 总线的更多信息，请参阅 维基百科 CAN 条目。

Zephyr 支持以下 CAN 功能：

  • 标准标识符和扩展标识符

  • 带掩码的过滤器

  • 回环模式和静默模式

  • 远程请求

发送

以下代码片段演示如何发送数据。

这个基本示例发送一个标准标识符为 0x123、带八字节数据的 CAN 帧。像本例这样把 NULL 作为回调传入时，发送函数会阻塞，直到该帧发送完成并被至少一个其他节点应答，或发生错误。超时只作用于获取邮箱的过程。一旦分配了发送邮箱，发送便无法取消。

struct can_frame frame = {
        .flags = 0,
        .id = 0x123,
        .dlc = 8,
        .data = {1,2,3,4,5,6,7,8}
};
const struct device *const can_dev = DEVICE_DT_GET(DT_CHOSEN(zephyr_canbus));
int ret;

ret = can_send(can_dev, &frame, K_MSEC(100), NULL, NULL);
if (ret != 0) {
        LOG_ERR("Sending failed [%d]", ret);
}

此示例演示如何发送扩展标识符为 0x1234567、带两字节数据的帧。消息发送完成或发生错误时，会调用所提供的回调。向超时参数传入 K_FOREVER 会使函数阻塞，直到为该帧分配了发送邮箱或发生错误。它不会像上面的示例那样阻塞到消息发送完成。

void tx_callback(const struct device *dev, int error, void *user_data)
{
        char *sender = (char *)user_data;

        if (error != 0) {
                LOG_ERR("Sending failed [%d]\nSender: %s\n", error, sender);
        }
}

int send_function(const struct device *can_dev)
{
        struct can_frame frame = {
                .flags = CAN_FRAME_IDE,
                .id = 0x1234567,
                .dlc = 2
        };

        frame.data[0] = 1;
        frame.data[1] = 2;

        return can_send(can_dev, &frame, K_FOREVER, tx_callback, "Sender 1");
}

接收

只有与过滤器匹配的帧才会被接收。以下代码片段演示如何通过添加过滤器来接收帧。

下面是供 can_add_rx_filter() 使用的接收回调示例。用户数据参数在添加过滤器时传入。

void rx_callback_function(const struct device *dev, struct can_frame *frame, void *user_data)
{
        ... do something with the frame ...
}

以下代码片段演示如何添加带回调函数的过滤器。这是接收消息最高效、但也最需谨慎的方式。回调函数在中断上下文中调用，因此应尽可能短小，并且不能阻塞。不允许在用户空间上下文中添加回调函数。

本例中的过滤器配置为精确匹配标识符 0x123。

const struct can_filter my_filter = {
        .flags = 0U,
        .id = 0x123,
        .mask = CAN_STD_ID_MASK
};
int filter_id;
const struct device *const can_dev = DEVICE_DT_GET(DT_CHOSEN(zephyr_canbus));

filter_id = can_add_rx_filter(can_dev, rx_callback_function, callback_arg, &my_filter);
if (filter_id < 0) {
  LOG_ERR("Unable to add rx filter [%d]", filter_id);
}

下面是 can_add_rx_filter_msgq() 的示例。使用此函数可以同步接收帧。该函数可以在用户空间上下文中调用。消息队列的大小应与预期积压的帧数相当。

本例中的过滤器配置为精确匹配扩展标识符 0x1234567。

const struct can_filter my_filter = {
        .flags = CAN_FILTER_IDE,
        .id = 0x1234567,
        .mask = CAN_EXT_ID_MASK
};
CAN_MSGQ_DEFINE(my_can_msgq, 2);
struct can_frame rx_frame;
int filter_id;
const struct device *const can_dev = DEVICE_DT_GET(DT_CHOSEN(zephyr_canbus));

filter_id = can_add_rx_filter_msgq(can_dev, &my_can_msgq, &my_filter);
if (filter_id < 0) {
  LOG_ERR("Unable to add rx msgq [%d]", filter_id);
  return;
}

while (true) {
  k_msgq_get(&my_can_msgq, &rx_frame, K_FOREVER);
  ... do something with the frame ...
}

can_remove_rx_filter() 移除指定的过滤器。

can_remove_rx_filter(can_dev, filter_id);

设置位速率

位速率和采样点最初在运行时设置。要在应用程序中修改它们，可以使用 can_set_timing() API。can_calc_timing() 函数可以根据位速率和以千分比表示的采样点计算时序。以下示例将位速率设置为 250k 波特，采样点为 87.5%。

struct can_timing timing;
const struct device *const can_dev = DEVICE_DT_GET(DT_CHOSEN(zephyr_canbus));
int ret;

ret = can_calc_timing(can_dev, &timing, 250000, 875);
if (ret > 0) {
  LOG_INF("Sample-Point error: %d", ret);
}

if (ret < 0) {
  LOG_ERR("Failed to calc a valid timing");
  return;
}

ret = can_stop(can_dev);
if (ret != 0) {
  LOG_ERR("Failed to stop CAN controller");
}

ret = can_set_timing(can_dev, &timing);
if (ret != 0) {
  LOG_ERR("Failed to set timing");
}

ret = can_start(can_dev);
if (ret != 0) {
  LOG_ERR("Failed to start CAN controller");
}

对于支持 CAN FD 的控制器，也有类似的 API 用于计算和设置数据阶段的时序。参见 can_set_timing_data() 和 can_calc_timing_data()。

SocketCAN

Zephyr 还支持 SocketCAN，即 Zephyr CAN API 的 BSD 套接字实现。SocketCAN 让控制器局域网也能使用人们熟知的 BSD 套接字 API，十分方便。它与 Linux SocketCAN 实现兼容，许多其他高层 CAN 项目都构建在后者之上。注意，帧会被路由到网络协议栈，而不是直接传递，这会带来一些计算和内存开销。
