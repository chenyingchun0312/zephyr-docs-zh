改进型 Inter-Integrated Circuit（I3C）总线

I3C（Improved Inter-Integrated Circuit，改进型内部集成电路）是一种双信号线共享外设接口总线。总线上的设备可以担任两种角色：发起事务并控制时钟的“控制器”（controller），或响应事务命令的“目标”（target）。

目前该 API 基于 I3C Specification 1.1.1 版。

I3C 控制器 API

当 I3C 控制器控制总线（尤其是起始条件、停止条件和时钟）时，使用 Zephyr 的 I3C 控制器 API。这是最常见的模式，用于与传感器等 I3C 目标设备交互。

由于 I3C 的特性，总线上有些设备上电时可能没有地址，因此 I3C 控制器需要额外执行动态地址分配。为此，控制器需要维护单独的结构来跟踪设备状态。这可以在构建时完成，例如为 I3C 和 I2C 设备分别创建设备描述符数组：

static struct i3c_device_desc i3c_device_array[] = I3C_DEVICE_ARRAY_DT_INST(inst);
static struct i3c_i2c_device_desc i2c_device_array[] = I3C_I2C_DEVICE_ARRAY_DT_INST(inst);

宏 I3C_DEVICE_ARRAY_DT_INST 和 I3C_I2C_DEVICE_ARRAY_DT_INST 是辅助宏，用于创建与 I3C 控制器下的设备树节点相对应的设备描述符数组。

下面是在设备驱动初始化函数中初始化 I3C 控制器和 I3C 总线的通用步骤：

  1. 初始化 I3C 控制器设备驱动实例的数据结构。可以使用 DEVICE_DT_INST_DEFINE 等常用的设备定义宏，并将初始化函数作为参数传给该宏。

    • i3c_addr_slots 和 i3c_dev_list 是用于辅助地址分配和设备列表管理的结构体。如果使用它们，需要调用 i3c_addr_slots_init() 初始化该结构体。这两个结构体还可以配合各种辅助函数使用。

    • 如果控制器驱动需要，初始化设备描述符。

  2. 初始化硬件，包括但不限于：

    • 设置引脚复用和方向。

    • 为控制器设置时钟。

    • 为硬件上电。

    • 配置硬件（例如 SCL 时钟频率）。

  3. 执行总线初始化。通用辅助函数 i3c_bus_init() 会执行以下步骤。如果控制器在总线初始化期间不需要任何特殊处理，可以使用该函数。

    1. 执行 RSTDAA，复位已连接设备的动态地址。如果已连接的设备已被分配了地址（例如在上电时），记录用的数据结构中并没有这些地址的记录。因此最好先复位，再为它们分配新地址。

    2. 执行 DISEC，禁止来自设备的所有事件。

    3. 如有需要，执行 SETDASA，使用设备的静态地址为其分配动态地址。

      • 并非所有已连接设备都支持用 SETAASA 将静态地址分配为动态地址。

      • 需要单独获取 BCR 和 DCR，以填充 I3C 目标设备描述符结构体中的相应字段。

    4. 如果仍有设备没有地址，执行 ENTDAA 开始动态地址分配。

      • 如果有设备在等待地址，它会回传其预置 ID（Provisioned ID）、BCR 和 DCR。将收到的预置 ID 与已注册的 I3C 设备列表进行匹配。

        • 如果匹配成功，为其分配地址（若尚未执行 SETDASA，则使用所声明的静态地址，否则使用一个空闲地址）。

          • 同时设置设备描述符结构体中的 BCR 和 DCR 字段。

        • 如果没有匹配，根据策略可以为其分配一个空闲地址，也可以由设备驱动停止分配过程并报错。

          • 注意，I3C API 需要设备描述符才能工作。没有设备描述符的设备无法通过该 API 访问。

      • 如果没有需要 DAA 的已连接设备，可以跳过此步骤。

    5. 以下步骤是可选的，但强烈建议执行：

      • 执行 GETMRL 和 GETMWL，获取最大读/写长度。

      • 执行 GETMXDS，获取最大读/写速度和最大读周转时间。

      • 辅助函数 i3c_bus_init() 会获取 BCR、DCR、MRL 和 MWL 等基本设备信息。

    6. 执行 ENEC，重新使能来自设备的事件。

      • 辅助函数 i3c_bus_init() 只会重新使能热加入（hot-join）事件。IBI 事件只应在使能某个设备的 IBI 时才使能。

带内中断（IBI）

如果目标设备可以产生带内中断（IBI，In-Band Interrupt），需要让控制器知道这一点。

  • i3c_ibi_enable() 用于使能目标设备的 IBI。

    • 有些控制器硬件带有 IBI 槽位，需要对其进行编程，控制器才能识别来自特定目标设备的 IBI。

      • 如果硬件带有 IBI 槽位，i3c_ibi_enable() 需要对这些 IBI 槽位进行编程。

      • 注意，控制器上的 IBI 槽位通常有限，因此该操作可能失败。

    • 驱动中的实现还应发送 ENEC 命令，使能该目标设备的中断。

  • i3c_ibi_disable() 用于禁止目标设备的 IBI。

    • 如果控制器硬件使用 IBI 槽位，此操作会从槽位中移除该目标设备的描述。

    • 驱动中的实现还应发送 DISEC 命令，禁止该目标设备的中断。

设备树

下面是在设备树中定义 I3C 控制器的示例：

i3c0: i3c@10000 {
        compatible = "vendor,i3c";

        #address-cells = <0x3>;
        #size-cells = <0x0>;

        reg = <0x10000 0x1000>;
        interrupts = <0x1F 0x0>;

        pinctrl-0 = <&pinmux-i3c>;
        pinctrl-names = "default";

        i2c-scl-hz = <400000>;

        i3c-scl-hz = <12000000>;

        status = "okay";

        i3c-dev0: i3c-dev0@420000ABCD12345678 {
                compatible = "vendor,i3c-dev";

                reg = <0x42 0xABCD 0x12345678>;

                status = "okay";
        };

        i2c-dev0: i2c-dev0@380000000000000050 {
                compatible = "vendor-i2c-dev";

                reg = <0x38 0x0 0x50>;

                status = "okay";
        };
};

I3C 设备

对于 I3C 设备，reg 属性包含 3 个元素：

  • 第一个元素是设备的静态地址。

    • 如果不使用静态地址，可以为零。此时地址将在 DAA（动态地址分配，Dynamic Address Assignment）期间分配。

    • 如果非零且未设置 assigned-address 属性，则在发出 SETDASA（根据静态地址设置动态地址，Set Dynamic Address from Static Address）后，该值即为设备地址。

  • 第二个元素是预置 ID（PID）的高 16 位，其中包含左移 1 位的制造商 ID，对应 48 位预置 ID 的第 33-47 位（从零开始计数）。

    • 必须为非零值。第二个元素为零会把该节点标记为 I2C 设备（如下文所述），辅助宏会为其创建传统 I2C 描述符，而不是 I3C 描述符。即使设备通过 SETDASA 寻址、PID 在其他方面并未使用，也要指定 PID。

  • 第三个元素包含预置 ID 的低 32 位，由器件 ID（左移 16 位，即 PID 的第 16-31 位）和实例 ID（左移 12 位，即 PID 的第 12-15 位）组合而成。

注意，单元地址（@ 之后的部分）必须与 reg 属性完全一致：每个元素视为 32 位整数，组合成一个 96 位整数。这是正确生成设备树宏所必需的。

I2C 设备

对于设备驱动支持在 I3C 总线上工作的 I2C 设备，其设备节点可以描述为 I3C 控制器的子节点。如果设备驱动只能与 I2C 控制器配合工作，请按下文所述将节点定义在 I2C 虚拟控制器之下。否则，reg 属性与 I3C 设备类似，包含 3 个元素：

  • 第一个元素是设备的静态地址。由于 I2C 设备不支持动态地址分配，该地址必须有效。

  • 第二个元素始终为零。

    • 各种辅助宏据此判断设备树条目是否对应 I2C 设备。

  • 第三个元素是 LVR（传统虚拟寄存器，Legacy Virtual Register）：

    • bit[31:8] 未使用。

    • bit[7:5] 是 I2C 设备索引：

      • 索引 0

        • I3C 设备带有 50 ns 尖峰滤波器，不受 SCL 上高频信号的影响。

      • 索引 1

        • I2C 设备没有 50 ns 尖峰滤波器，但可以在 SCL 高频下工作。

      • 索引 2

        • I3C 设备没有 50 ns 尖峰滤波器，且无法在 SCL 高频下工作。

    • bit[4] 是 I2C 模式指示位：

      • 0 表示 FM+ 模式。

      • 1 表示 FM 模式。

与 I3C 设备类似，单元地址必须与 reg 属性完全一致：每个元素视为 32 位整数，组合成一个 96 位整数。

I3C 设备的设备驱动

I3C 控制器 API 的所有传输函数都需要使用设备描述符 i3c_device_desc。该结构体包含 I3C 设备的运行时信息，例如其动态地址、BCR、DCR、MRL 和 MWL。因此，I3C 设备的驱动应使用 i3c_device_find() 从控制器获取指向该设备描述符的指针。该函数接受一个 i3c_device_id 类型的 ID 参数用于匹配。返回的指针随后可用于对控制器的后续 API 调用。

I3C 总线上的 I2C 设备

由于 I3C 向后兼容 I2C，只要控制器设备驱动实现了 I2C API，I3C 控制器 API 无需修改即可处理 I2C API 调用。其优点是现有 I2C 设备可以直接使用，无需修改其设备驱动。不过，由于 I3C 控制器 API 基于设备描述符工作，每次调用 I2C API 都需要根据 I2C 设备地址查找对应的设备描述符，这会给 I2C API 调用增加一些处理开销。

另一方面，也可以扩展设备驱动，通过 I3C 控制器 API 使用原生的 I2C 设备支持。在设备初始化期间，需要调用 i3c_i2c_device_find() 获取指向设备描述符的指针。该指针可用于后续 API 调用。

注意，无论使用上述哪种方法，I2C 设备的设备树节点都必须按照 I3C 标准声明：

I2C 虚拟控制器设备驱动提供了一种在 I3C 总线上连接 I2C 设备的方式，相关设备驱动可以原样使用，无需修改。这需要在设备树中添加一个中间节点：

i3c0: i3c@10000 {
        <... I3C controller related properties ...>
        <... Nodes of I3C devices, if any ...>

        i2c-dev0: i2c-dev0@420000000000000050 {
                compatible = "vendor-i2c-dev";

                reg = <0x42 0x0 0x50>;

                status = "okay";
        };
};
