贡献指南

作为一个开源项目，我们欢迎并鼓励社区直接向项目提交补丁。在我们协作的开源环境中，提交修改的标准和方法有助于减少活跃的开发社区可能带来的混乱。

本文档说明如何参与项目讨论、报告 bug 和提出改进请求，以及如何向项目提交补丁，使你的补丁能快速被代码库接受。

前提条件

作为贡献者，你需要熟悉 Zephyr 项目，了解如何配置、安装和使用它（参见 Zephyr Project website 中的说明），以及如何按照 Zephyr 入门指南 中的介绍搭建开发环境。

你应该熟悉 Git 和 CMake 等常用开发工具，以及 GitHub 等平台。

如果还没有，你需要在 https://github.com 上创建一个（免费的）GitHub 账号，并在开发系统上安装 Git 工具。

备注

Zephyr 开发工作流程支持全部 3 种主流操作系统（Linux、macOS 和 Windows），但以下各节中用到的部分工具只能在 Linux 和 macOS 上使用。在 Windows 上，你无需自己运行这些工具，而是依靠基于 Github Actions 的持续集成（CI）服务，当你提交 PR（拉取请求）时，它会在 GitHub 上自动运行。你可以在 PR 对话列表末尾附近的工作流程详情链接中查看任何失败结果。更多信息请参阅 Continuous Integration

许可证

许可证对开源项目非常重要。它有助于确保软件能够继续按照作者所期望的条款提供。

Zephyr 使用 Apache 2.0 license（见项目 GitHub repo 中的 LICENSE 文件），在开放贡献与允许你随意使用软件之间取得平衡。Apache 2.0 许可证是一种宽松的开源许可证，允许你自由地使用、修改、分发和销售包含以 Apache 2.0 许可证授权的软件的自有产品。（更多相关信息，请参阅 Why choose Apache 2.0 licensing 和 Top 10 Apache License Questions Answered 等文章。）

许可证告诉你作为开发者拥有哪些由版权持有人授予的权利。贡献者必须充分理解并同意这些许可权利。有时版权持有人并不是贡献者本人，例如贡献者代表公司开展工作时。

使用其他许可证的组件

Zephyr 项目中有一些导入或复用的组件使用其他许可证，如 Zephyr 项目组件的许可 中所述。

从使用 Apache 2.0 以外许可证的其他项目向 Zephyr OS 导入代码，需要结合具体情况充分理解，并经 Zephyr 理事会批准。

通过仔细审查潜在的贡献，并对所贡献的代码强制执行 开发者原创证明（DCO），我们可以确保 Zephyr 社区使用 Zephyr 项目开发产品，而无需担心专利或版权问题。

关于导入组件的贡献和评审流程的更多信息，请参阅 贡献外部组件。

版权和许可证声明

Zephyr 遵循 SPDX/REUSE 风格的文件头。在每个文件的顶部添加机器可读的版权声明和许可证标识符，以便工具能够检测到它们（例如使用 REUSE tool 的 west spdx）。

Zephyr 项目遵循 Linux 基金会关于版权声明的 Community Best Practice，因此我们建议使用以下版权声明：

SPDX-FileCopyrightText: Copyright The Zephyr Project Contributors

同时加上许可证标识符：

SPDX-License-Identifier: Apache-2.0

实用指导：

  • 使用该文件自身的注释语法，将这两行放在文件的最顶部。

  • 如果你编写了大量原创内容，可以 为你自己或你所在的组织再添加一行。

开发者原创证明（DCO）

为了尽最大诚意确保满足许可证标准，Zephyr 项目要求遵循开发者原创证明（Developer Certificate of Origin，DCO）流程。

DCO 是附在每位开发者所做的每项贡献上的一份声明。在贡献的提交信息中（本文档后面会更详细地介绍），开发者只需添加一条 Signed-off-by 声明，即表示同意 DCO。

开发者提交补丁，即承诺该贡献者有权根据许可证提交该补丁。DCO 协议如下所示，也可在 https://developercertificate.org/ 查看。

Developer's Certificate of Origin 1.1

By making a contribution to this project, I certify that:

(a) The contribution was created in whole or in part by me and I
    have the right to submit it under the open source license
    indicated in the file; or

(b) The contribution is based upon previous work that, to the
    best of my knowledge, is covered under an appropriate open
    source license and I have the right under that license to
    submit that work with modifications, whether created in whole
    or in part by me, under the same open source license (unless
    I am permitted to submit under a different license), as
    Indicated in the file; or

(c) The contribution was provided directly to me by some other
    person who certified (a), (b) or (c) and I have not modified
    it.

(d) I understand and agree that this project and the contribution
    are public and that a record of the contribution (including
    all personal information I submit with it, including my
    sign-off) is maintained indefinitely and may be redistributed
    consistent with this project or the open source license(s)
    involved.

DCO 签署（Sign-Off）

DCO 中的“签署”是指每个提交日志信息中的 "Signed-off-by:" 行。Signed-off-by: 行必须采用以下格式:

Signed-off-by: Your Name <your.email@example.com>

对于你的提交，请替换：

  • 将 Your Name 替换为你的法定姓名（不允许使用化名、黑客代号或团体名称）

  • 将 your.email@example.com 替换为你创作该提交时实际使用的电子邮件地址。不允许使用 you-id+your-username@users.noreply.github.com 之类的伪造或匿名电子邮件。该电子邮件必须与你创作该提交时所用的邮件地址一致（如果不一致，CI 将会失败）。

可以使用 git commit -s 自动在提交正文中添加 Signed-off-by: 行。可以参考 zephyr git 历史中的其他提交作为示例。关于在 Git 中配置用户名和电子邮件的说明，请参阅 Git 设置。

其他要求：

  • 如果你要修改他人创建的现有提交，必须添加你自己的 Signed-off-by: 行，且不得删除已有的那一行。

AI 编程助手

本节为在向 Zephyr 项目做贡献时使用 AI 工具和助手的贡献者提供指导。

许可证与法律要求

所有贡献都必须遵守项目的许可证要求，并与 Zephyr 的许可证（例如 Apache-2.0，详情请参阅 许可证）兼容。

Signed-off-by 与开发者原创证明

AI 代理 不得 添加 Signed-off-by 标签。只有人类才能在法律上作出 开发者原创证明（DCO） 证明。提交补丁的人负责：

  • 评审所有 AI 生成的代码。

  • 确保符合许可证要求。

  • 添加自己的 Signed-off-by 标签以作出 DCO 证明。

  • 对该贡献承担全部责任。

使用情况披露与署名

当使用 AI 工具帮助编写贡献时，恰当的署名有助于跟踪 AI 在开发过程中不断变化的作用。贡献中应包含以下格式的 Assisted-by: 标签：

Assisted-by: [Agent Name]:[Model Version] [Tool1] [Tool2]

其中：

  • [Agent Name] 是 AI 工具或框架的名称。

  • [Model Version] 是所使用的具体模型版本。

  • [Tool1] [Tool2] 是可选的、所使用的专门分析工具。

不应列出基本的开发工具（git、gcc、make、编辑器）。

示例：

Assisted-by: Claude:claude-opus-4.6 coccinelle

源代码树结构

要克隆 Zephyr 项目主仓库，请按照 获取 Zephyr 并安装 Python 依赖项 中的说明操作。

本节介绍主仓库的源代码树。除了 Zephyr 内核本身之外，你还会找到技术文档、示例代码、受支持开发板的配置以及一系列子系统测试的源文件。开发者都可以对这些内容做出贡献和改进。

了解 Zephyr 源代码树有助于找到与特定 Zephyr 功能相关的代码。

代码树的顶层有几个重要文件：

CMakeLists.txt

CMake 构建系统的顶层文件，包含构建 Zephyr 所需的大量逻辑。

Kconfig

顶层 Kconfig 文件，它引用了同样位于顶层目录中的 Kconfig.zephyr 文件。

详细的 Kconfig 文档请参阅 手册中的 Kconfig 章节。

west.yml

West（Zephyr 的元工具） 清单（manifest），列出了由 west 命令行工具管理的外部仓库。

Zephyr 源代码树还包含以下顶层目录，每个目录下可能还有一层或多层子目录，此处不作介绍。

arch

特定于架构的内核及片上系统（SoC）代码。每种受支持的架构（例如 x86 和 ARM）都有自己的子目录，其中又包含以下方面的子目录：

  • 特定于架构的内核源文件

  • 特定于架构的、用于私有 API 的内核头文件

soc

与 SoC 相关的代码和配置文件。

boards

与开发板相关的代码和配置文件。

doc

Zephyr 技术文档的源文件，以及用于生成 https://docs.zephyrproject.org 网站内容的工具。

drivers

设备驱动代码。

dts

用于描述无法自动发现的、开发板特定硬件细节的 设备树 源文件。

include

所有公共 API 的头文件，lib 下定义的 API 除外。

kernel

与架构无关的内核代码。

lib

库代码，包括最小 C 标准库。

misc

不属于其他任何顶层目录的杂项代码。

samples

演示 Zephyr 功能用法的示例应用程序。

scripts

用于构建和测试 Zephyr 应用程序的各种程序和其他文件。

cmake

构建 Zephyr 所需的其他构建脚本。

subsys

Zephyr 的各个子系统，包括：

  • USB 设备协议栈代码

  • 网络代码，包括 Bluetooth 协议栈和各种网络协议栈

  • 文件系统代码

  • Bluetooth 主机（host）和控制器（controller）

tests

针对 Zephyr 功能的测试代码和基准测试。

share

其他与架构无关的数据。目前其中包含 Zephyr 的 CMake 包。

PR（拉取请求）和 issue

在开始编写补丁之前，请先在我们的 Zephyr Project Issues 系统中查看你想解决的问题是否已有人报告。在 Zephyr devel mailing list（或 Zephyr Discord Server）上进行讨论，听听其他人对你提出的问题（以及所建议的解决方案）有何看法。你可能会发现其他人也遇到过你发现的问题，或者对修改或新增功能有类似的想法。向 Zephyr devel mailing list 发送消息，向开发社区介绍并讨论你的想法。

在提交自己的 issue 之前，先搜索已有的或相关的 issue，始终是个好习惯。当你提交 issue（bug 或功能请求）后，分类（triage）团队会审查并评论你提交的内容，通常在几个工作日内完成。

你可以在 GitHub 上找到所有 open pull requests，并在 Github issues 中找到处于打开状态的 Zephyr Project Issues。

Git 设置

我们需要知道你是谁，以及如何联系你。要将这些信息添加到你的 Git 安装中，请将 Git 配置变量 user.name 设为你的全名，将 user.email 设为你的电子邮件地址。

例如，如果你的名字是 Zephyr Developer，电子邮件地址是 z.developer@example.com：

git config --global user.name "Zephyr Developer"
git config --global user.email "z.developer@example.com"

备注

user.name 必须是你的全名（至少包括名和姓），而不是化名或黑客代号。Git 配置中使用的电子邮件地址必须与你签署提交时使用的电子邮件地址一致。如果不一致，CI 系统会判定你的 PR 失败。

如果你打算使用 Github.com 网页界面编辑提交，请确保你的 github 个人资料中的 email address 和 name 也与 git 配置中使用的（user.name 和 user.email）一致。

PR 指南

打开新的 PR 时，请遵循以下指南，以确保符合 Zephyr 标准并便于评审。

如有疑问，建议浏览 Zephyr 仓库中已有的 PR。使用搜索过滤器和标签，找到与你所提议的修改类似的 PR。

备注

GitHub 默认的代码界面使用 4 个字符宽的制表符。但 Zephyr 遵循 Linux kernel coding style，使用 8 个字符宽的制表符。

为确保你看到的代码与其他开发者一致，请前往 user preferences on GitHub，将制表符宽度改为 8 个空格。

提交信息指南

修改以 Git 提交的形式提交。每个提交都有一条描述该修改的 提交信息。可接受的提交信息形如：

[area]: [summary of change]

[Commit message body (must be non-empty)]

Signed-off-by: [Your Full Name] <[your.email@address]>

你需要修改上面方括号中的文字（[like this]），使其与你的提交相符。

下面是一条良好的提交信息示例。

drivers: sensor: abcd1234: fix bus I/O error handling

The abcd1234 sensor driver is failing to check the flags field in
the response packet from the device which signals that an error
occurred. This can lead to reading invalid data from the response
buffer. Fix it by checking the flag and adding an error path.

Signed-off-by: Zephyr Developer <z.developer@example.com>

[area]: [summary of change]

这一行称为提交的 标题。标题必须：

  • 只有一行

  • 长度少于 72 个字符

  • 后面紧跟一个完全空白的行

[area]

[area] 前缀通常标识所修改代码的领域。如果修改影响多个领域，也可以标识修改的更大范围上下文。

下面是一些示例：

  • doc: ... 用于文档修改

  • drivers: foo: 用于 foo 驱动的修改

  • Bluetooth: Shell: 用于 Bluetooth shell 的修改

  • net: ethernet: 用于与以太网相关的网络修改

  • dts: 用于涉及整个代码树的设备树修改

  • style: 用于代码风格修改

如果不确定该用什么，可以尝试运行 git log FILE（其中 FILE 是你正在修改的文件），参考以前修改过同一文件的提交。

[summary of change]

[summary of change] 部分应简要描述你所做的工作。下面是一些示例：

  • doc: update wiki references to new site

  • drivers: sensor: sensor_shell: fix channel name collision

提交信息正文

警告

不允许提交信息正文为空。即使是很小的修改，也请写上描述性的提交信息正文。否则你的 PR 将无法通过 CI 检查。

提交信息的这一部分应说明你的修改做了什么，以及为什么需要它。请写得具体些。内容为 "Fixes stuff" 的正文会被拒绝。请务必视情况包含以下内容：

  • 修改做了 什么，

  • 为什么 选择这种方法，

  • 做了 哪些 假设，以及

  • 如何 确认它能正常工作——例如运行了哪些测试。

提交信息中的每一行通常应不超过 75 个字符。较长的行请用换行符折行。包含长 URL、电子邮件地址等的行属于例外。

已被接受的提交信息示例可以参考 Zephyr GitHub 的 变更日志。

小技巧

你应该已经完成了 Git 设置。使用 git commit -s 创建提交，即可利用这些信息自动添加 Signed-off-by: 行。

出于开源许可的原因，你的提交必须包含如下形式的 Signed-off-by: 行：

Signed-off-by: [Your Full Name] <[your.email@address]>

例如，如果你的全名是 Zephyr Developer，电子邮件地址是 z.developer@example.com：

Signed-off-by: Zephyr Developer <z.developer@example.com>

这表示你已亲自确认你的修改符合 开发者原创证明（DCO）。因此，你必须使用法定姓名。不允许使用化名或“黑客别名”。

你使用的姓名和电子邮件地址必须与 Git 提交的 Author: 字段中的姓名和电子邮件一致。

关于贡献者和评审者行为期望的更完整讨论，请参阅 贡献者行为期望。

添加链接

如果你的修改解决了某个特定的 GitHub issue，请在 PR 描述中使用以下格式加入对它的引用：

Fixes zephyrproject-rtos/zephyr#[issue number]

仅对于向 Zephyr 项目提交的 PR，也可以使用简写形式，例如：

Fixes #[issue number]

将 [issue number] 替换为相关的 GitHub issue 编号。例如：

Fixes zephyrproject-rtos/zephyr#1234

使用这种语法可以确保在 PR 合并时自动关闭该 issue。请始终写明完整的仓库路径（zephyrproject-rtos/zephyr）以避免歧义，在跨多个仓库工作时尤其如此。

提交信息中也可以使用相同的格式。

要链接到其他外部资源（例如相关的 issue、数据手册或技术参考手册），请使用 Link: 标签：

Link: https://github.com/zephyrproject-rtos/zephyr/issues/<issue number>

持续集成（CI）

Zephyr 项目运行着一个持续集成（CI）系统，它在每个 PR（拉取请求）上运行，以验证 PR 的以下几个方面：

  • Git 提交格式

  • 编码风格

  • 针对多种架构和开发板的 Twister 构建

  • 构建文档以验证所有文档修改

CI 运行在 Github Actions 上，使用的工具与 CI Tests 一节中所述的相同。在 PR 可以合并之前，CI 结果必须为绿色，显示 "All checks have passed"。CI 会在创建 PR 时运行，之后每次通过提交修改 PR 时都会再次运行。

CI 运行的当前状态始终显示在 GitHub PR 页面底部、评审状态的下方。根据运行成功或失败，你会看到：

  • "All checks have passed"（所有检查均已通过）

  • "All checks have failed"（所有检查均未通过）

如果失败，可以点击失败信息下方的 "Details" 链接，跳转到 Github Actions 查看结果。点击该链接后，你会进入 Github actions 的结果摘要页面，其中有一个表格列出了所有不同的构建。要查看是哪个构建或测试失败了，请点击包含失败（即非绿色）构建的那一行。

在本地运行 CI 测试

check_compliance.py

scripts/ci/check_compliance.py 脚本是评估代码是否符合 Zephyr 既定指南和最佳实践的有用工具。该脚本封装了一组执行各种检查的工具，包括静态检查工具（linter）和格式化工具。

鼓励开发者在打开新的 PR 之前，先在本地运行该脚本验证自己的修改：

./scripts/ci/check_compliance.py -c <commit range>

这些检查并行运行，每个 CPU 使用一个工作进程。传入 -p N 可将工作进程数量限制为 N，传入 -p 1 则按顺序运行各项检查。

./scripts/ci/check_compliance.py -p 1 -c <commit range>

备注

在 Windows 上，如果 .pl 扩展名尚未与任何应用程序关联，那么第一次在未指定解释器的情况下运行 .pl 文件时，Windows 会询问用哪个应用程序打开 Perl 文件。请将默认应用设为 Strawberry Perl。默认情况下，其可执行文件安装在 C:\Strawberry\perl\bin\perl.exe。

KeepSorted 检查

KeepSorted 检查确保指定的代码、配置或文档块保持有序。

要使用 KeepSorted 检查，请将已排序的内容包在专门的、包含开始和结束标记的行之间，这些行通常使用注释：

// zephyr-keep-sorted-start
option_a
option_b
option_c
// zephyr-keep-sorted-stop
KeepSorted 标记选项

每个块的排序行为可以通过多种方式定制。为此，可以在开始标记所在的同一行上添加以下一个或多个参数：

re(regex_pattern)

启用正则表达式模式，此时只检查与指定正则表达式匹配的行是否有序，其他行会被忽略。

检查 yaml 文件中属性是否有序的示例：

# zephyr-keep-sorted-start re(^\s+\- name:)
projects:
  - name: application
    revision: main
  - name: library1
    revision: feature-branch
  - name: library2
    revision: main
# zephyr-keep-sorted-stop
strip(characters)

在进行排序比较之前，先从各行中去掉指定的字符。当各行带有在排序时应被忽略的可选前缀或后缀时，这个选项很有用。

去掉 yaml 字典键两侧引号的示例：

# zephyr-keep-sorted-start strip(":)
ACPI:
  status: odd fixes
"West project: acpica":
  status: odd fixes
# zephyr-keep-sorted-stop
nofold

禁用行折叠。默认情况下，主行之后的缩进行会与主行拼接（折叠）在一起进行排序比较。nofold 选项会禁用此行为，并忽略缩进行。

ignorecase

使用 Python 的 str.casefold 启用不区分大小写的排序。这样可以在已排序的块中混用大写和小写条目，而不会违反排序顺序。如果省略，则默认使用 Python 的字符串排序。

同一个标记行上可以组合多个选项：

.. zephyr-keep-sorted-start re(^\* \w) ignorecase
* Shell
  Some important message about the shell.

* STM32
  Updates for this vendor.
.. zephyr-keep-sorted-stop

twister

备注

twister 仅在 Linux 上得到完整支持；在 Windows 和 MacOS 上，并非所有目标设备都支持执行测试。

如果你认为自己的修改可能会导致某些测试失败，可以将 PR 作为草稿提交，让项目 CI 自动为你运行 测试运行器（Twister）。

如果某个测试失败，可以从 CI 运行日志中查看如何在本地重新运行它，例如：

west twister -p native_sim -s tests/drivers/build_all/sensor/drivers.sensor.generic_test

静态代码分析

Coverity Scan 是一项为开源项目提供静态代码分析的免费服务。它基于 Coverity 的商业产品，能够分析 C、C++ 和 Java 代码。

Coverity 的静态代码分析不会运行代码，而是使用抽象解释来获取代码控制流和数据流的信息。它能够跟踪程序可能经过的所有代码路径。例如，分析器知道 malloc() 返回的内存之后必须用 free() 释放。它会跟踪所有分支和函数调用，查看所有可能的组合是否都释放了内存。分析器能够检测各种问题，例如资源泄漏（内存、文件描述符）、NULL 解引用、释放后使用、未检查的返回值、死代码、缓冲区溢出、整数溢出、未初始化的变量等等。

结果可在 Coverity Scan 网站上查看。要访问这些结果，你需要自己创建一个账号。在 Zephyr 项目页面上，可以选择 "Add me to project" 申请加入项目。新成员必须经过管理员批准。

Zephyr 代码库每两周进行一次静态分析。对于静态分析工具检测到的任何问题，都会自动创建 GitHub issue。这些 issue 的初始优先级与工具所定义的优先级相同（或等同）。

为确保责任明确并高效解决问题，这些 issue 会分配给负责受影响代码的相应维护者。

一个由在静态分析、代码质量和软件安全方面具有专业知识的成员组成的专门团队负责确保静态分析流程的有效性，并核实所发现的问题得到妥善分类并及时解决。

工作流程

如果分析 Coverity 报告后得出结论认为这是误报，请将分类（classification）设为 "False positive" 或 "Intentional"，将操作（action）设为 "Ignore"，将负责人（owner）设为你自己的账号，并添加一条评论说明为何认为该问题是误报或有意为之。

在 zephyr 项目中相关的 Github issue 里更新详细信息，并且只有在扫描服务网站上完成上述步骤之后才关闭它。任何未修复、也未在扫描服务中忽略该条目就被关闭的 issue，如果问题仍然存在于代码中，将会被自动重新打开。

贡献工作流程

我们鼓励的一个通用做法是进行小而可控的修改。这种做法可以简化评审，使合并和变基更容易，并保持修改历史清晰整洁。

向 Zephyr 项目做贡献时，还需要尽可能多地提供有关修改的信息，更新相应的文档，并在提交之前充分测试你的修改。

Zephyr 开发者使用的通用 GitHub 工作流程结合了命令行 Git 命令和通过浏览器与 GitHub 的交互。和 Git 本身一样，完成一项任务有多种方式。这里介绍一种典型的工作流程：

  1. Create a Fork of Zephyr：在 GitHub 上将 Zephyr fork 到你的个人账号。（在 GitHub 上 Zephyr 项目仓库页面的右上角点击 fork 按钮。）

  2. 在你的开发计算机上，进入 获取代码 时创建的 zephyr 文件夹:

    cd zephyrproject/zephyr

    将指向 上游仓库 的默认远程仓库从 origin 重命名为 upstream:

    git remote rename origin upstream

    让 Git 知道你刚刚创建的 fork，并将其命名为 origin:

    git remote add origin https://github.com/<your github id>/zephyr

    然后验证远程仓库:

    git remote -v

    输出应类似于:

    origin   https://github.com/<your github id>/zephyr (fetch)
origin   https://github.com/<your github id>/zephyr (push)
upstream https://github.com/zephyrproject-rtos/zephyr (fetch)
upstream https://github.com/zephyrproject-rtos/zephyr (push)

  3. 为你的工作创建一个（基于 main 的）主题分支（如果你在解决某个 issue，建议在分支名中包含该 issue 编号）:

    git switch main
git switch -c fix_comment_typo

    Zephyr 的某些子系统在独立于 main 的分支上进行开发工作，因此你可能需要在检出时指明这一点:

    git switch -c fix_out_of_date_patch origin/net

  4. 进行修改，在本地测试，再修改，再测试，再次测试……（另请参阅前面关于 twister 的章节）。

  5. 一切就绪后，通过添加修改过的文件开始 PR 流程:

    git add [file(s) that changed, add -p if you want to be more specific]

    可以使用以下命令查看尚未暂存的文件:

    git status

  6. 确认待提交的修改与预期一致:

    git diff --cached

  7. 将修改提交到本地仓库:

    git commit -s

    -s 选项会自动在提交信息中添加你的 Signed-off-by:。这一行表示你同意 开发者原创证明（DCO），没有它，你的提交会被拒绝。关于编写提交信息的具体指南，请参阅 提交信息指南 一节。

  8. 将包含修改的主题分支推送到你个人 GitHub 账号下的 fork:

    git push origin fix_comment_typo

  9. 在 Web 浏览器中进入你 fork 的仓库，针对你刚刚处理、想要发起 PR 的分支，点击 Compare & pull request 按钮。

  10. 检查 PR 中的修改，并确认你是向 main 分支发起 PR。你的提交信息中的标题和内容也应显示出来。

  11. 机器人会（根据仓库中的 MAINTAINERS 文件）指派一名或多名建议的评审者。如果你是项目成员，此时也可以选择其他评审者。

  12. 点击提交按钮，你的 PR 即被发送并等待评审。有评审评论时会发送电子邮件，你也可以在 https://github.com/zephyrproject-rtos/zephyr/pulls 查看你的 PR。

  13. 在等待 PR 被接受和合并期间，你可以创建另一个分支来处理另一个 issue。（请务必基于 main 而不是上一个分支创建新分支。）:

    git switch main
git switch -c fix_another_issue

    然后使用上述相同的流程在这个新的主题分支上工作。

  14. 如果评审者确实要求修改你的补丁，你可以交互式地变基提交来解决评审中提出的问题。在你的开发仓库中:

    git rebase -i <offending-commit-id>^

    在交互式变基编辑器中，将 pick 替换为 edit 以选择特定的提交（如果你的 PR 中有多个提交），或者删除该行以完全删除某个提交。然后编辑文件，解决评审中提出的问题。

    和之前一样，检查并测试你的修改。准备就绪后，继续提交补丁:

    git add [file(s)]
git rebase --continue

    如有需要，更新提交说明，然后继续:

    git push --force origin fix_comment_typo

    通过强制推送更新，你原来的 PR 会随你的修改一起更新，因此无需重新提交 PR。

  15. 推送所要求的修改之后，在 PR 页面上检查是否存在合并冲突。如果存在，请对本地分支进行变基:

    git fetch --all
git rebase --ignore-whitespace upstream/main

    --ignore-whitespace 选项可以防止（由变基调用的）git apply 修改任何空白字符。解决冲突后再次推送:

    git push --force origin fix_comment_typo

    备注

    虽然修订提交并强制推送是 GitHub 之外常见的评审模式，也是 Zephyr 推荐的模式，但它并不是 GitHub 主要支持的模式。强制推送可能导致意外行为，例如除最后一个之外的 "View Changes" 按钮都无法使用，GitHub 会提示找不到较早的提交。你也并不总是能将最近评审过的版本与最新提交的版本进行比较。重写历史时，GitHub 只保证可以访问最新版本。

  16. 如果 CI 运行失败，你需要修改代码来解决问题，并按上述方法通过变基修订你的提交。关于 CI 系统的更多信息，请参阅 Continuous Integration。

贡献技巧

以下是一些能改进并加快 PR 评审过程的技巧。如果你遵循这些技巧，你的 PR 很可能会得到所需的关注，并能尽早准备好合并：

  1. 推送后续修改时，使用 git-rebase 的 --keep-base 选项

  2. 在 PR 页面上检查该修改是否仍可在没有合并冲突的情况下合并

  3. 确保 PR 的标题说明了修复或添加了什么

  4. 确保你的 PR 有正文，并在其中更详细地说明所提交的内容

  5. 确保在 PR 正文中引用你所修复的 issue

  6. 提交之后立即关注早期的 CI 结果，发现问题后及时修复

  7. 1-2 小时后重新查看 PR，了解所有 CI 检查的状态，确保全部为绿色

  8. 如果收到修改要求并提交了相应的修改，请务必在 GitHub 界面上点击 "Re-request review" 按钮，通知那些要求修改的人

标明贡献来源

向代码树中添加新文件时，务必在文件中详细说明其来源、注明归属，并说明预期用途。如果该文件是 Zephyr 的原创文件，提交信息中应包含以下内容（如果没有 Origin 标签，则默认视为 "Original"）:

Origin: Original

如果该文件是 从外部项目导入的，提交信息中应包含有关原始项目的详细信息、该项目的位置、该文件来源提交的 SHA-id 以及预期用途。

例如，一份在本地维护的导入副本:

Origin: Contiki OS
License: BSD 3-Clause
URL: https://www.contiki-os.org/
commit: 853207acfdc6549b10eb3e44504b1a75ae1ad63a
Purpose: Introduction of networking stack.

例如，模块仓库中一份在外部维护的导入副本:

Origin: Tiny Crypt
License: BSD 3-Clause
URL: https://github.com/01org/tinycrypt
commit: 08ded7f21529c39e5133688ffb93a9d0c94e5c6e
Purpose: Introduction of TinyCrypt

涉及整个代码树的修改

本节介绍属于涉及整个代码树的修改（treewide change）的贡献，以及适用于它们的一些附加要求。由于此类修改影响很大，制定这些要求是为了让它们得到更多的评审，并让用户更容易注意到。

定义与决策

涉及整个代码树的修改 是指对 Zephyr API、编码实践或其他开发要求的任何修改，这些修改要么意味着需要在整个 zephyr 源代码仓库中进行相应修改，要么可以合理预期会要求大量基于 Zephyr 的外部源代码进行相应修改。

这个定义必然是非正式的，因为判断某个修改是否涉及整个代码树可能带有主观性，并可能取决于其他上下文。

在判断所提议的修改是否涉及整个代码树时，项目维护者应做出良好的判断，并优先考虑 Zephyr 开发者的体验。长期的分歧可以由 Zephyr 项目的技术指导委员会（TSC）解决，但请避免过早升级到 TSC。

对涉及整个代码树的修改的要求

  • zephyr 仓库必须为任何属于涉及整个代码树的修改的 issue 或 PR 添加 'treewide' GitHub 标签

  • 在与该修改相关的任何 PR 可以合并之前，提议涉及整个代码树修改的人必须创建一个 RFC issue，描述该修改及其理由和影响等

  • 在与该修改相关的任何 PR 可以合并之前，项目的 架构工作组（WG） 必须将该 issue 列入议程，并讨论项目是接受还是拒绝该修改（如果工作组未能达成共识，则升级到 TSC）

  • 架构工作组必须为每项涉及整个代码树的修改指定合并相关 PR 的程序，包括影响特定子系统的 PR 所需的批准，或额外的评审时间要求

  • 如果 RFC 被架构工作组接受，那么在与该修改相关的任何 PR 可以合并之前，提议涉及整个代码树修改的人必须就该 RFC 发送电子邮件到 devel@lists.zephyrproject.org

示例

过去一些涉及整个代码树的修改示例：

  • 弃用第 1 版 日志 API，改用第 2 版（参见提交 262cc55609）

  • 移除对旧版 设备树绑定 语法的支持（6bf761fc0a）

注意，为广泛使用的 API 添加新版本、同时保留对旧版本的支持，不属于涉及整个代码树的修改。但弃用和移除此类 API 则属于涉及整个代码树的修改。

专用驱动要求

独立器件的驱动应尽可能使用 Zephyr 总线 API（SPI、I2C……），以便该器件可以与任何厂商的、实现了兼容总线的任何 SoC 配合使用。

如果由于某个 SoC 系列中存在专用加速器，在技术上无法使用 Zephyr API 达到完整性能，可以通过为该 SoC 系列提供专用路径来扩展对外部器件的支持。但是，驱动仍必须为所有其他 SoC 提供常规路径（通过 Zephyr API）。每个例外都必须经过架构工作组批准，以便进行验证，并可能从中学习和改进。
