提案与 RFC

许多修改，包括 bug 修复和文档改进，都可以通过常规的 GitHub PR（拉取请求）工作流来实现和评审。

但也有许多修改属于“重大”修改，需要经过设计流程，并在项目相关方之间达成共识。

“RFC”（request for comments，征求意见稿）流程旨在为新功能进入项目提供一条一致且受控的途径。

如果贡献者和项目相关方打算对 Zephyr 或其文档做出“重大”修改，应考虑使用此流程。以下是一些能从 RFC 中受益的例子：

  • 会新增 API 接口范围、并且引入时需要功能开关的新功能。

  • 修改现有的稳定 API。

  • 移除已作为 Zephyr 的一部分发布的功能。

  • 引入新的惯用用法或约定，即使它们不涉及对 Zephyr 本身代码的修改。

RFC 流程是一个很好的机会，可以在贡献者的提案成为 Zephyr 的一部分之前，让更多人审视它。很多时候，即使是看似“显而易见”的提案，在更多感兴趣的人有机会发表意见之后，也能得到显著改进。

RFC 流程还有助于在功能设计过程中促进对该功能的讨论，在设计尚未完全实现、仍容易修改的时候，将重要的约束纳入设计。

对于重大功能，请先创建一个 issue 并概述你的提案，以便进行讨论。这也有助于我们更好地协调工作、避免重复劳动，并帮助你完善修改，使其能被项目顺利接受。提供以下信息可以提高你的 issue 被迅速处理的可能性：

  • 提案概述

  • 动机或使用场景

  • 设计细节

  • 备选方案

  • 测试策略

有些修改或贡献不需要 RFC，但修改的理由和细节应包含在 PR 中：

  • 对现有的成熟子系统所做的小幅增强和修改。

  • 改写措辞、重新组织或重构

  • 添加或移除警告

  • 向现有子系统添加新的开发板、SoC 或驱动

  • ...

该流程本身就是创建一个带有 RFC 标签 的 GitHub issue，并在其中详尽地记录提案。鼓励使用 RFC form，以确保提案遵循项目参与者已经熟悉的模板。

与 PR 一样，如果存在分歧或发表的意见不足以继续推进，RFC 可能需要在某次 Zephyr meetings 中进行讨论才能向前推进。请务必为其添加适当的标签，或将其加入相应的 GitHub 项目，以便在下次会议中对其进行审议。
