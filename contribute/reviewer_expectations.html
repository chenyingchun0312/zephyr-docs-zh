评审者行为期望

  • 在 PR 上发表评论时要尊重他人。更多详情请参阅 Zephyr Code of Conduct。

  • Zephyr 项目认识到评审者和维护者的精力有限。作为评审者，请按以下顺序安排评审请求的优先级：

    1. 与 Zephyr Release Plan 中的事项相关的 PR，或在稳定期（RC1 之后）以下一个版本为目标的 PR。

    2. 评审者已要求进行阻塞性修改的 PR。

    3. 作为领域维护者被分配给该评审者的 PR。

    4. 其他所有 PR。

  • 评审者应通过反馈以及与 PR 作者的互动，努力推动 PR 达到可合并状态。

  • 尽量一次性对整个 PR 给出反馈。这样贡献者就有机会在下一次更新 PR 时处理所有评论。

  • 允许进行部分评审，但评审者必须添加评论，说明自己评审了 PR 的哪一部分。有用的部分评审示例包括：

    • 特定领域的评审（例如设备树）。

    • 影响 PR 可读性的代码风格修改。

    • 当所要求的修改会连带影响后续提交时，分别评审各个提交。

  • 避免通过要求新功能来扩大 PR 的范围，尤其是当该 PR 关联有相应的 RFC 时。评审者应将建议以评论形式添加到该 RFC 中。这也有助于促进更多协作，因为在最小实现合并之后，多个贡献者更容易共同开发某个功能。

  • 使用 "Request Changes" 选项时，在评论中将琐碎的、非功能性的要求标记为 "Non-blocking"（非阻塞）。当只剩下非阻塞的修改时，评审者应批准 PR。是否处理所有非阻塞评论由 PR 作者自行决定。PR 作者应以某种方式回应每条评审评论，哪怕只是一个表情符号。

  • 对于评审者不认同、但项目中并未成文规定的风格修改，可以作为非阻塞意见指出，但不能构成要求修改的理由。评审者可以选择修正代码树中可能存在的不一致之处，将新的指南或规则写入文档，然后在评审中强制执行。

  • 每当要求进行与风格相关的修改时，评审者应能指出项目文档中相应的指南、规则或理由。这不适用于某些类型的修改要求，特别是那些针对所提交修改本身的要求（例如使用某种特定的数据结构或选择何种锁原语）。

  • 使用 "Request Changes" 选项时，评审者应 清楚地 说明要求做哪些修改。所要求的修改应在该 PR 的范围之内，并遵循项目的贡献指南和风格指南。此外，评审者必须能够指出 PR 中引发修改要求的确切问题。

  • 评审者不应针对 CI 会自动发现的问题要求修改，因为这会导致即使 CI 失败已被解决，PR 仍处于阻塞状态，并可能不必要地推迟合并。

  • 评审者不得因为技术上或结构上的分歧而关闭 PR。如果所要求的修改无法在评审过程中解决，应通过 PR 技术问题升级处理 途径寻求可能的解决方案，其中可能包括关闭该 PR。

  • 使用 AI 工具辅助评审代码或起草回复时：

    • 评审者有责任跟进自己所用 AI 工具（例如 GitHub Copilot）生成的评论。

    • 评审者绝不能将未经核实的 LLM 原始输出直接粘贴为 PR 评论。

    • 总之：所有 AI 生成的反馈都必须经过人类评审者的审查、核实并结合上下文，由该评审者对评论或评审的准确性和语气承担全部责任。
