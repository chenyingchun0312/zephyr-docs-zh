文档编写指南

备注

关于如何构建文档，请参阅 文档生成。

Zephyr 项目的内容使用 reStructuredText [2] 标记语言（文件扩展名为 .rst）及 Sphinx 扩展编写，并由 Sphinx 处理，生成格式化的独立网站。开发者既可以直接查看 .rst 标记文件的原始内容，也可以（在安装 Sphinx 后）在本地 构建文档，生成 HTML 或 PDF 格式的文档，然后用网页浏览器查看 HTML 内容。Zephyr documentation [4] 网站提供的也是同样的 .rst 内容。

关于 reStructuredText [2] 和 Sphinx extensions [1] 的详细信息，可以在各自的网站上查阅。

本文档是一份速查参考，列出了编写你正在阅读的这份文档时常用的 reST 和 Sphinx 指令（directive）与角色（role）。

关于如何编写良好的 C API 文档，请参阅 Doxygen 风格指南。

内容结构

制表符、空格与缩进

在 reST 文件中缩进是有意义的，建议使用空格缩进。多余的缩进也可能（无意中）改变内容的渲染方式。对于列表和指令，应将内容文本缩进到与上一行第一个非空白字符对齐。例如:

* List item that spans multiple lines of text
  showing where to indent the continuation line.

1. And for numbered list items, the continuation
   line should align with the text of the line above.

.. code-block::

   The text within a directive block should align with the
   first character of the directive name.

其他要求请参阅 Zephyr 编码风格指南。

标题

虽然 reST 允许同时使用上划线和与之匹配的下划线来表示标题，但我们只使用下划线来标示标题。

  • 文档标题（h1）使用 # 作为下划线字符

  • 第一级节标题（h2）使用 *

  • 第二级节标题（h3）使用 =

  • 第三级节标题（h4）使用 -

标题下划线的长度必须与标题文字相同。

例如:

This is a title heading
#######################

some content goes here

First section heading
*********************

列表

对于项目符号列表，在段落开头放置星号（*）或连字符（-），续行缩进两个空格。

列表（或子列表）的第一项之前必须有一个空行，并且应与前一段落处于相同的缩进级别（其本身不缩进）。

对于编号列表，例如以 1. 或 a. 开头，之后使用 # 符号自动编号。续行缩进三个空格:

* This is a bulleted list.
* It has two items, the second
  item and has more than one line of reST text.  Additional lines
  are indented to the first character of the
  text of the bullet list.

1. This is a new numbered list. If the wasn't a blank line before it,
   it would be a continuation of the previous list (or paragraph).
#. It has two items too.

a. This is a numbered list using alphabetic list headings
#. It has three items (and uses autonumbering for the rest of the list)
#. Here's the third item

#. This is an autonumbered list (default is to use numbers starting
   with 1).

   #. This is a second-level list under the first item (also
      autonumbered).  Notice the indenting.
   #. And a second item in the nested list.
#. And a second item back in the containing list.  No blank line
   needed, but it wouldn't hurt for readability.

定义列表（由术语及其定义组成）便于为一个词或短语附上解释。例如以下 reST 内容:

The Makefile has targets that include:

html
   Build the HTML output for the project

clean
   Remove all generated output, restoring the folders to a
   clean state.

将渲染为：

Makefile 包含以下目标：

html

为项目构建 HTML 输出

clean

删除所有生成的输出，将文件夹恢复到干净状态。

多列列表

如果有一个很长的项目符号列表，而每一项都很短，可以使用特殊的 .. rst-class:: rst-columns 指令，指定将列表项渲染为多列。该指令作用于下一个非注释元素（例如段落），或作用于缩进在该指令之下的内容。例如以下无序列表:

.. rst-class:: rst-columns

* A list of
* short items
* that should be
* displayed
* horizontally
* so it doesn't
* use up so much
* space on
* the page

将渲染为：

  • 一个由

  • 简短条目

  • 组成、应当

  • 以水平

  • 方式显示

  • 的列表，这样

  • 它就不会

  • 占用太多

  • 页面空间

最多显示三列，列数会根据显示窗口的可用宽度而变化，必要时在窄屏（手机）上减少为一列。我们已弃用 hlist 指令，因为它在较小的屏幕上表现不正常。

表格

创建表格有几种方式，各有其限制或特点。网格表格 在定义合并行和合并列方面功能最强，但难以维护:

+------------------------+------------+----------+----------+
| Header row, column 1   | Header 2   | Header 3 | Header 4 |
| (header rows optional) |            |          |          |
+========================+============+==========+==========+
| body row 1, column 1   | column 2   | column 3 | column 4 |
+------------------------+------------+----------+----------+
| body row 2             | ...        | ...      | you can  |
+------------------------+------------+----------+ easily   +
| body row 3 with a two column span   | ...      | span     |
+------------------------+------------+----------+ rows     +
| body row 4             | ...        | ...      | too      |
+------------------------+------------+----------+----------+

此示例将渲染为：

表头行，第 1 列（表头行可选）

表头 2

表头 3

表头 4

表体第 1 行，第 1 列

第 2 列

第 3 列

第 4 列

表体第 2 行

...

...

也可以轻松地跨行

表体第 3 行，跨两列

...

表体第 4 行

...

...

列表表格 维护起来容易得多，但不支持跨行或跨列:

.. list-table:: Table title
   :widths: 15 20 40
   :header-rows: 1

   * - Heading 1
     - Heading 2
     - Heading 3
   * - body row 1, column 1
     - body row 1, column 2
     - body row 1, column 3
   * - body row 2, column 1
     - body row 2, column 2
     - body row 2, column 3

此示例将渲染为：

表格标题

标题 1

标题 2

标题 3

表体第 1 行，第 1 列

表体第 1 行，第 2 列

表体第 1 行，第 3 列

表体第 2 行，第 1 列

表体第 2 行，第 2 列

表体第 2 行，第 3 列

:widths: 参数用于定义相对列宽，默认各列等宽。如果有一个三列表格，希望第一列的宽度是另外两个等宽列的一半，可以指定 :widths: 1 2 2。如果希望浏览器根据列内容自动设置列宽，可以使用 :widths: auto。

选项卡内容

如 入门指南 中所示，可以通过选项卡界面向读者提供可替换的内容。读者点击某个选项卡时，就会显示该选项卡的内容，例如:

.. tabs::

   .. tab:: Apples

      Apples are green, or sometimes red.

   .. tab:: Pears

      Pears are green.

   .. tab:: Oranges

      Oranges are orange.

将显示为：

苹果是绿色的，有时是红色的。

梨是绿色的。

橙子是橙色的。

选项卡还可以分组，这样在一处切换当前选项卡时，整个页面中所有同名的选项卡都会随之切换。例如：

Linux 第 1 行

macOS 第 1 行

Windows 第 1 行

Linux 第 2 行

macOS 第 2 行

Windows 第 2 行

在后一种情况下，我们使用的是 .. group-tab:: 而不是简单的 .. tab::。其底层使用的是 Zephyr 环境中已包含的 sphinx-tabs 扩展。在选项卡中，除标题以外，几乎可以放置任何内容（代码块、有序和无序列表、图片、段落等）。关于 sphinx-tabs 的更多信息，请参阅上面的链接。

文本格式

reStructuredText 支持多种文本格式选项。本节为 Zephyr 文档中最常用的一些文本格式选项提供速查参考。完整列表请参阅 reStructuredText Quick Reference [5]、reStructuredText Interpreted Text Roles [6] 以及 additional roles provided by Sphinx [7]。

内容突出显示

一些常用的 reST 行内标记示例：

  • 一个星号：*text* 表示强调（斜体），

  • 两个星号：**text** 表示着重强调（粗体），以及

  • 两个反引号：``text`` 用于 inline code 示例。

如果正文中出现的星号或反引号可能与行内标记定界符混淆，可以在其前面加一个反斜杠（\）来消除歧义。

文件名与命令

Sphinx 对 reST 进行了扩展，支持额外的行内标记元素（称为“角色”），用于为文本标注特殊含义，并实现带样式的输出格式。（完整列表请参阅 Sphinx Inline Markup [3] 文档。）

虽然可以使用双引号将文本渲染为“代码”，但建议使用以下角色来标记文件名、命令名以及其他“特殊”文本。

  • file 用于文件名，例如 :file:`CMakeLists.txt` 会渲染为 CMakeLists.txt

    备注

    如果要表示“可变”的文件路径，可以用花括号把路径中的可变部分括起来，例如 :file:`{boardname}_defconfig` 会渲染为 boardname_defconfig。

  • command 用于命令名，例如 :command:`make` 会渲染为 make

  • envvar 用于环境变量，例如 :envvar:`ZEPHYR_BASE` 会渲染为 ZEPHYR_BASE

要创建指向 GitHub 上 Zephyr 组织中托管文件的引用，请参阅下文的 交叉引用 Zephyr 树中的文件 一节。

用户交互

在记录用户交互（例如组合键或图形界面操作）时，请使用以下角色以合适的方式突出显示这些命令：

  • kbd 用于键盘输入，例如 :kbd:`Ctrl-C` 会渲染为 Ctrl-C

  • menuselection 用于菜单选择，例如 :menuselection:`File --> Open` 会渲染为 File ‣ Open

  • guilabel 用于界面标签，例如 :guilabel:`Cancel` 会渲染为 Cancel

数学公式

可以使用 math 角色或 math 指令插入数学公式。如果公式较复杂，指令提供了更大的灵活性。

数学公式的输入语言是 LaTeX 标记。示例:

The answer to life, the universe, and everything is :math:`30 + 2^2 + \sqrt{64} = 42`.

这将渲染为：

生命、宇宙以及一切的终极答案是 \(30 + 2^2 + \sqrt{64} = 42\)。

非 ASCII 字符

优先使用纯 ASCII 字符，除非为了正确性或遵循排版惯例而需要特定符号（例如 µ 这样的单位，或 ™ 这样的常见标记）。

避免纯粹出于美观目的添加非 ASCII 字符。

文件 doc/substitutions.txt 包含一些用于特殊格式需求（例如强制换行）的基本 HTML 替换定义，但 Unicode 字符可以而且应该直接用在文档源文件中。

代码块与命令示例

使用 reST 的 code-block 指令可以创建带高亮的等宽文本块，通常用于展示格式化的代码或控制台命令及输出。它还支持智能语法高亮（使用 Pygments 软件包），也可以直接指定高亮语言。例如:

.. code-block:: c

   struct k_object {
      char *name;
      uint8_t perms[CONFIG_MAX_THREAD_BYTES];
      uint8_t type;
      uint8_t flags;
      uint32_t data;
   } __packed;

注意 code-block 指令与代码块正文第一行之间有一个空行，并且正文内容缩进三个空格（与指令名称的第一个非空白字符对齐）。

这将渲染为：

struct k_object {
   char *name;
   uint8_t perms[CONFIG_MAX_THREAD_BYTES];
   uint8_t type;
   uint8_t flags;
   uint32_t data;
} __packed;

当然也支持其他语言（参见 languages supported by Pygments [8]），特别建议在适当的时候使用以下语言：

  • c 用于 C 代码

  • cpp 用于 C++ 代码

  • python 用于 Python 代码

  • console 用于控制台输出，即交互式 shell 会话，其中命令以提示符为前缀（例如 Linux 上的 $，或 Zephyr shell 的 uart:~$），并且同时显示输出。命令会被高亮，输出则不会。此外，使用“复制”按钮复制代码块时，只会自动复制命令，而不包括提示符和命令的输出。

  • shell 或 bash 用于 shell 命令。这两种语言的高亮效果相同，但可以用 bash 表示命令是 bash 特有的，用 shell 表示通用的 shell 命令。

    备注

    如果代码块中包含提示符，不要使用 bash 或 shell，而应使用 console。

    反过来，如果代码块中不包含提示符，也不是在展示包含命令及其输出的交互式会话，就不要使用 console。

    何时使用 bash/shell，何时使用 console

    使用场景

    code-block 代码片段

    预期输出

    一条或多条命令，无输出

    		 
    .. code-block:: shell

   echo "Hello World!"

    echo "Hello World!"

    包含命令及其输出的交互式 shell 会话

    		 
    .. code-block:: console

   $ echo "Hello World!"
   Hello World!

    $ echo "Hello World!"
Hello World!

    包含命令及其输出的交互式 Zephyr shell 会话

    		 
    .. code-block:: console

   uart:~$ version
   Zephyr version 3.5.99
   uart:~$ kernel uptime
   Uptime: 20970 ms

    uart:~$ version
Zephyr version 3.5.99
uart:~$ kernel uptime
Uptime: 20970 ms

  • bat 用于 Windows 批处理文件

  • cfg 用于包含“KEY=value”条目的配置文件（例如 Kconfig 的 .conf 文件）

  • cmake 用于 CMake

  • devicetree 用于设备树

  • kconfig 用于 Kconfig

  • yaml 用于 YAML

  • rst 用于 reStructuredText

未指定语言时，语言被设为 none，代码块不会被高亮。也可以显式使用 none 达到同样的效果，例如:

.. code-block:: none

   This would be a block of text styled with a background
   and box, but with no syntax highlighting.

将显示为：

This would be a block of text styled with a background
and box, but with no syntax highlighting.

编写代码块还有一种简写方式：在引导段落末尾加上双冒号（::），并将其后的代码块内容缩进三个空格。输出时只会显示一个冒号。这种代码块没有高亮（即 none）。不过，可以使用 highlight 指令自定义文档中使用的默认语言（例如，可以参考本文档开头的做法）。

链接与交叉引用

交叉引用内部内容

传统的 reST 链接只能在当前文件内使用，写法如下:

Refer to the `internal-linking`_ page

渲染效果如下，

请参阅 internal-linking 页面

注意末尾的下划线表示这是一个出站链接。在此示例中，标签紧挨着加在标题之前，因此显示的文字就是标题文字本身。可以按如下方式书写，改变链接显示的文字:

Refer to the `show this text instead <internal-linking_>`_ page

渲染效果如下，

请参阅 show this text instead 页面

交叉引用外部内容

借助 Sphinx，我们可以为 Zephyr 项目文档中任何带标签的文本创建链接引用。

文档中的目标位置通过标签指令定义:

.. _my label name:

Heading
=======

注意开头的下划线表示这是一个入站链接。紧跟在该标签之后的内容必须是一个标题，它是 Zephyr 文档中任何位置的 :ref:`my label name` 引用的目标。引用此标签时会显示标题文字。也可以改变该链接显示的文字，例如:

:ref:`some other text <my label name>`

为了便于站内跨页面链接，每个文件都应在标题前设置一个引用标签，以便其他文件引用。这些引用标签在整个网站中必须唯一，因此应避免使用“samples”这类通用名称。例如，本文档 .rst 文件的开头是:

.. _doc_guidelines:

Documentation Guidelines for the Zephyr Project
###############################################

其他 .rst 文档可以用 :ref:`doc_guidelines` 标签链接到本文档，显示为 文档编写指南。这种内部交叉引用可以跨多个文件使用，链接文字取自文档源文件，因此标题改变时，链接文字也会随之更新。

也可以定义指向任意 URL 的链接，然后在文档中引用它。例如，在文档中有如下标签定义:

.. _Zephyr Wikipedia Page:
   https://en.wikipedia.org/wiki/Zephyr_(operating_system)

就可以这样引用它:

Read the `Zephyr Wikipedia Page`_ for more information about the
project.

小技巧

当文档包含大量外部链接时，可以将它们集中列在文档末尾的“参考资料”一节中。这可以通过 target-notes 指令实现。示例:

References
==========

.. target-notes::

.. _external_link1: https://example.com
.. _external_link2: https://example.org

交叉引用 C 文档

:c:member:
:c:data:
:c:var:
:c:func:
:c:macro:
:c:struct:
:c:union:
:c:enum:
:c:enumerator:
:c:type:

可以使用以下角色交叉引用 C 函数、宏、类型等的 Doxygen 文档。

在 HTML 输出中，它们会渲染为指向对应条目 Doxygen 文档的链接。例如:

Check out :c:func:`gpio_pin_configure` for more information.

将渲染为：

更多信息请参阅 gpio_pin_configure()。

与内置的 ref 角色类似，可以提供自定义的链接文字。

交叉引用 CMake 文档

可以使用以下角色交叉引用 Zephyr 的 CMake 模块、命令和变量的文档。

:cmake:module:

此角色用于引用 CMake 模块。例如:

See :cmake:module:`extensions` for more information.

将渲染为：

更多信息请参阅 extensions。

:cmake:command:

此角色用于引用 CMake 命令。例如:

See :cmake:command:`yaml_load` for more information.

将渲染为：

更多信息请参阅 yaml_load()。

由 CMake 自身文档描述的命令通过其完全限定名称引用，并以显式链接目标的形式给出:

See :cmake:command:`target_sources <command:target_sources>` for more information.

将渲染为：

更多信息请参阅 target_sources。

:cmake:variable:

此角色用于引用 CMake 变量。例如:

See :cmake:variable:`CMAKE_C_COMPILER` for more information.

将渲染为：

视觉元素

图片

使用 image 指令在文档中插入图片:

.. image:: ../../../../images/doc-gen-flow.png
   :align: center
   :alt: alt text for the image

如果要添加图片说明，请使用:

.. figure:: ../../../../images/doc-gen-flow.png
   :alt: image description

   Caption for the figure

指定的文件名是相对于文档源文件的路径，建议将图片放在文档源文件所在位置的 images 文件夹中。

支持网页浏览器通常可处理的图片格式：WebP、PNG、GIF、JPEG 和 SVG。

图片尺寸应保持在必要的大小，一般宽度至少 500 px 但不超过 1000 px，文件大小不超过 100 KB，除非为了清晰起见确实需要特别大的图片。

根据内容推荐的图片格式

  • 截图：WebP 或 PNG。

  • 图表：简单的图表可以考虑使用 Graphviz（参见下文的 专门章节。如果使用外部工具，首选 SVG。

  • 照片（例如开发板照片）：使用 WebP，最长边不超过 600 px。只要拍摄对象能与背景分离（开发板照片通常如此），就应以透明背景保存图片，使其能与文档的浅色和深色主题都融为一体。

    可以使用 cwebp [9] 或 ImageMagick [10] 将现有图片转换为合适尺寸的 WebP。例如:

    # Using cwebp (resize width to 600 px, height auto, ~80% quality).
# For a portrait image, use "-resize 0 600" to cap the height instead.
cwebp -resize 600 0 board_name.png -o board_name.webp

# Using ImageMagick
magick board_name.png -resize 600x600 -quality 80 board_name.webp

    如果源图片已经带有透明背景（例如带 alpha 通道的 PNG），这两个工具都会在生成的 WebP 中保留透明度。-resize 600 0 / 600x600 参数只会缩小图片，并保持其宽高比。

要在文档中插入 Graphviz 图表，请使用 graphviz 指令。例如:

   digraph G {

      A -> B;
      B -> C;

Mermaid

Mermaid [13] 是一款使用简单文本语法创建图表和可视化内容的工具，特别适合创建流程图、时序图、类图和状态转换图。

要在文档中插入 Mermaid 图表，请使用 mermaid 指令。例如:

.. mermaid::
   :caption: State transition diagram for a GPIO debounce
   :alt: GPIO debounce state diagram showing transitions between inactive and active states
         through maybe_active and maybe_inactive intermediate states before each state becomes
         stable.

   ---
   config:
     state:
       useMaxWidth: false
   ---
   stateDiagram-v2

       State inactive {
           [*] --> stable_inactive
           stable_inactive --> maybe_active : edge to active
           maybe_active --> stable_inactive : edge to inactive
       }

       State active {
           [*] --> stable_active
           stable_active --> maybe_inactive : edge to inactive
           maybe_inactive --> stable_active : edge to active
       }

       [*] --> inactive

       maybe_active --> active : After(x ms)
       maybe_inactive --> inactive : After(x ms)

将渲染为：

图表会横跨页面宽度绘制，其高度由宽高比决定，因此高度大于宽度的图表最终会比实际需要的大得多。像上例那样关闭 useMaxWidth，可以让图表保持 Mermaid 为其计算出的尺寸；在窄屏上它仍会缩小以适应屏幕。该设置属于图表类型，此处为 state，在其他场合可能是 flowchart、sequence 或其他类型。

关于所支持的图表、语法和示例，请参阅 Mermaid documentation [14]。在创建或更新图表时，可以使用 Mermaid live editor [15] 快速迭代。

自定义 Sphinx 角色与指令

Zephyr 文档使用自定义的 Sphinx 角色和指令来提供附加功能，使编写和维护风格一致的文档更加容易。

应用程序构建命令

.. zephyr-app-commands::

为管理（构建、烧录等）应用程序所需的 shell 命令生成格式一致的文档

例如，要生成为 qemu_x86 构建 samples/hello_world 的命令，可使用:

.. zephyr-app-commands::
   :zephyr-app: samples/hello_world
   :board: qemu_x86
   :goals: build

这将渲染为：

# From the root of the zephyr repository
west build -b qemu_x86 samples/hello_world

选项

:tool: (string)

要使用的工具。当前有效的选项为 cmake、west 和 all，默认为 west。

:app: (string)

要构建的应用程序的路径。

:zephyr-app: (string)

要构建的应用程序的路径，该应用程序位于上游 zephyr 仓库中。与 :app: 互斥。

:cd-into: (no value)

如果设置，构建说明将在 :app: 文件夹内部给出，而不是在其外部。

:generator: (string)

要生成的构建系统。

当前有效的选项为 ninja 和 make，默认为 ninja。此选项不区分大小写。

:host-os:

说明所针对的主机操作系统。

有效的选项为 unix、win 和 all，默认为 all。

:board: (string)

如果设置，构建命令将以指定的开发板为目标。

:shield: (string)

如果设置，构建命令将以指定的扩展板（shield）为目标。

可以用逗号分隔的列表指定多个扩展板。

:conf:

如果设置，构建命令将使用指定的配置文件。

如果指定了多个配置文件，请用双引号将以空格分隔的文件列表括起来，例如 "a.conf b.conf"。

:gen-args: (string)

如果设置，表示传给 CMake 调用的附加参数。

:build-args: (string)

如果设置，表示传给构建调用的附加参数。

:west-args: (string)

如果设置，表示传给 west 调用的附加参数（对 :tool: cmake 无效）。

:flash-args: (string)

如果设置，表示传给烧录调用的附加参数。

:debug-args: (string)

如果设置，表示传给调试调用的附加参数。

:debugserver-args: (string)

如果设置，表示传给 debugserver 调用的附加参数。

:attach-args: (string)

如果设置，表示传给 attach 调用的附加参数。

:snippets: (string)

如果设置，表示应用程序在编译时应使用所列出的代码片段（snippet）。

可以用逗号分隔的列表指定多个代码片段。

:build-dir: (string)

如果设置，应用程序构建目录将在标准构建目录后 追加 这个以 Unix 风格分隔的相对路径。这主要用于在同一页面中区分同一应用程序的多次构建。

:build-dir-fmt: (string)

如果设置，则假定 west config build.dir-fmt` 已被设为此路径。

与 :build-dir: 互斥，并依赖于 :tool: west。

:goals: (string)

以空白分隔的列表，表示要对应用程序执行的操作（可以是 build、flash、debug、debugserver、run 中的任意项）。

完成这些任务的命令将按正确的顺序生成。

:maybe-skip-config: (no value)

如果设置，表示读者可能已经创建并进入了构建目录，并会调整文字，说明无需再次执行此操作。

:compact: (no value)

如果设置，生成的输出是单个代码块，不带额外的注释行。

无障碍指南

无障碍是文档的一个重要方面，它确保所有用户（包括残障用户）都能访问和理解内容。

编写和维护 Zephyr 项目文档时，请遵循以下指南，为所有人改善无障碍性。

图片与插图

所有图片和插图都必须包含恰当的替代文本（alt text），以便向依赖屏幕阅读器或无法查看图片的用户传达视觉内容的含义。

  • 使用 image 指令插入图片时，请使用 :alt: 属性。示例：

    .. image:: ../../../../contribute/documentation/image/doc-gen-flow.png
   :alt: Documentation generation process overview

  • 如果图片中包含文字，请确保替代文本逐字包含这些文字。

  • 使用允许添加说明文字的 figure 指令时，:alt: 文本仍然很重要。替代文本应描述图片本身，而说明文字则提供额外的背景或解读。示例：

    .. figure:: ../../../../images/arch-diagram.png
   :alt: High-level overview of Zephyr OS architecture showing layers and components.

   High-level overview of Zephyr OS architecture.

  • 对于能用文字清楚说明的信息，避免把图片作为传达该信息的唯一方式。

编写替代文本的最佳实践

  • 准确且等效：呈现与图片相同的核心信息。

  • 简洁：简明地传达图片的核心信息。

  • 避免冗余：不要使用“……的图像”或“……的图片”之类的说法，因为屏幕阅读器通常会告知该元素是图片。

  • 描述而不解读：只描述图片上可见的内容。

  • 复杂图片：对于图表、示意图或其他复杂的视觉内容，在替代文本中提供摘要。如果完整理解需要更多细节，可以考虑在周围文字中或作为插图说明的一部分提供更详细的描述。使用 Graphviz 等基于文本的图表工具也有助于改善无障碍性。

标题与结构

使用 标题 合理地组织文档结构。这样，使用辅助技术的用户就能理解文档的组织方式并高效地浏览。

表格

表格只应用于表格数据，并且必须能被屏幕阅读器访问。

  • 始终为行和列定义表头。

  • 尽可能使用 list-table 指令，以获得更好的响应式效果和无障碍性。

  • 如果表格的上下文不是一目了然，请为表格添加标题。示例：

    .. list-table:: GPIO Pin Configuration Options
   :widths: 15 30
   :header-rows: 1

   * - Field
     - Description
   * - GPIO_INPUT
     - Configures pin as input
   * - GPIO_OUTPUT
     - Configures pin as output
