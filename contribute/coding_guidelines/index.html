编码规范

主要规则

编码规范规则基于 MISRA-C 2012，是 MISRA-C 的一个 子集。下表列出了该子集，包括规则摘要、其 MISRA-C 严重级别，以及其他标准中的等效规则，供参考。

下表中的严重级别和其他参考信息仅供参考。所列规则对 Zephyr 均为必需规则，所有新代码都应遵守下列规则。

备注

对于现有的 Zephyr 维护者和协作者，如果无法通过雇主获得 MISRA-C 2012 文本，项目可以提供数量有限的副本。如需 MISRA-C 2012 副本，请发送电子邮件至 safety@lists.zephyrproject.org，详细说明无法通过其他途径获得的原因，以及获得副本后预期作出的贡献。安全委员会将审核所有申请。

附加规则

规则 A.1：条件编译

严重级别

必需（Required）

描述

不要在头文件中对函数声明进行条件编译。不要在头文件中对结构体声明进行条件编译。为避免在相应功能未启用时浪费内存，可以在结构体定义中有条件地排除某些字段。

理由

根据编译时选项从头文件中排除声明，可能导致无法生成这些声明的文档。缺少这些声明还会使代码路径需要随所选选项变化时，无法使用 if (IS_ENABLED(CONFIG_FOO)) {} 来替代预处理器条件。

规则 A.2：包容性语言

严重级别

必需（Required）

描述

不要新引入下列冒犯性术语。此规则适用于（但不限于）源代码、注释、文档和分支名称。替代术语可能因领域或子系统而异，但应尽可能遵循更新后的行业标准。

为维护现有实现，或为由 Zephyr 项目之外的机构管理的行业标准规范添加新实现时，允许例外。

建议在更新的行业标准规范发布或管理机构公开宣布新术语后尽快修改现有用法；如果没有适用的规范，则建议立即修改。

规则 A.3：宏名称冲突

严重级别

必需（Required）

描述

对于 MIN、MAX、ARRAY_SIZE 等名称常用的宏，不得为了避免与其他实现发生名称冲突而对其进行修改或保护。具体来说，不得给它们加前缀以放入 Zephyr 专用的命名空间，不得使用 #undef 重新定义，也不得使用 #ifndef 有条件地将其排除在编译之外。如果与来自某个 模块 的现有定义发生冲突，则需要修改该模块自身的代码（最好在上游修改，或者在 Zephyr 自己的分叉中修改）。

此规则普遍适用于整个 Zephyr 项目，与宏的引入时间或其在代码树中的当前名称无关。如果某个宏名称在其他几个知名开源项目中被普遍使用，那么 Zephyr 中的实现也应使用该名称。虽然“普遍使用”的含义带有主观、无法度量的成分，但最终目标是为用户提供他们熟悉的宏。

最后，此规则同样适用于模块之间的名称冲突：在这种情况下，两个模块在被纳入之前，都应修改为使用该冲突宏名称的模块专用版本。

理由

Zephyr 是一个 RTOS，它以模块的形式附带额外的功能和依赖项。这些模块通常是独立的项目，其使用的宏名称可能与其他模块或 Zephyr 本身冲突。由于在本文档的语境中，Zephyr 被视为中心或主项目，它应当实现这些宏的无命名空间版本。鉴于 Zephyr 为每个模块都使用了对应上游的分叉，总是可以修补每个模块中的宏实现以避免冲突。

严重级别

必需（Required）

描述

某些 C 标准库（例如 Newlib 和 Picolibc）包含额外的函数和宏，它们由扩展 ISO C 标准的标准和事实标准（例如 POSIX、Linux）定义。

ISO/IEC 9899:2011 标准并不要求 C 编译器工具链支持这些非标准函数，因此使用这些函数可能会与自带 C 标准库的第三方工具链产生兼容性问题。
