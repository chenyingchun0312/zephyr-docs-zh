贡献者行为期望

Zephyr 项目鼓励 贡献者 以较小的 PR（拉取请求）形式提交修改。较小的 PR 有以下好处：

  • 评审更快、更彻底。对评审者来说，抽出几分钟多次评审较小的修改，比分配大段时间评审一个大型 PR 更容易。

  • 如果评审者或维护者否决了修改的方向，浪费的工作更少。

  • 更容易变基和合并。较小的 PR 与代码树中其他修改发生冲突的可能性更小。

  • 如果 PR 破坏了功能，更容易回退。

备注

本页不适用于草稿 PR。草稿 PR 可以是任意大小、包含任意数量的提交，也可以是若干较小 PR 的任意组合，用于测试和预览。草稿 PR 不要求评审，并且从一开始就作为草稿创建的 PR 默认不会通知任何人。

如何界定较小的 PR

  • 较小的 PR 应只包含一个自成一体的逻辑修改。

  • 添加大型新功能或 API 时，PR 应只处理该功能的一部分。在这种情况下，请创建一个 RFC 提案，向评审者描述该功能的其余部分。

  • 在以下情况下，PR 应包含测试或示例：

    • 添加新特性或新功能。

    • 修改某项功能，特别是更改 API 行为约定时。

    • 修复与硬件无关的 bug。测试应在 bug 未修复时失败，在应用修复后通过。

  • PR 必须更新因功能性代码修改而受影响的所有文档。

  • 如果引入了新的 API，PR 必须包含该 API 的使用示例。这样可以为评审者提供上下文，并避免提交包含未使用 API 的 PR。

单个 PR 中的多个提交

我们还鼓励贡献者将 PR 拆分为多个提交。请记住，PR 中的每个提交仍然必须能够干净地构建，并通过所有 CI 测试。

例如，在为某个 API 引入扩展时，贡献者可以将 PR 拆分为针对以下具体修改的多个提交：

  1. 引入新的 API，包括共享的设备树绑定

  2. 更新驱动实现 X，包括驱动专用的设备树绑定

  3. 更新驱动实现 Y

  4. 为新 API 添加测试

  5. 添加一个使用该 API 的示例

  6. 更新文档

大型修改

对 Zephyr 项目的大型修改必须提交一个 RFC 提案，描述修改的完整范围和后续工作。RFC 提案为评审者提供必要的上下文，同时允许较小的、增量式的 PR 得到评审并合并到项目中。RFC 还应定义最小可行实现。

需要 RFC 提案的修改包括：

  • 提交新功能。

  • 提交新 API。

  • 涉及整个代码树的修改。

  • 其他能从 RFC 提案流程中受益的大型修改。

对于过大或过于复杂的 PR，维护者可以酌情要求贡献者创建 RFC。

PR 要求

重要

不符合下述质量期望的 PR 不太可能得到评审者的参与，评审者也可能在不提供详细反馈的情况下对这类 PR 要求修改。

贡献者应在请求评审之前自行检查自己的修改，并确保满足所有要求。

  • PR 中的每个提交都必须提供遵循 提交信息指南 的提交信息。

  • 不允许有 fixup 提交或合并提交，更多信息请参阅 贡献工作流程。

  • PR 描述必须包含修改摘要及其理由。

  • PR 中的所有文件都必须符合 许可证要求。

  • 代码必须遵循 Zephyr 的 编码风格指南 和 编码规范。

  • PR 必须通过所有 CI 检查，如 PR 合并标准 中所述。贡献者可以将 PR 标记为草稿，并明确请求评审者提供早期反馈，即使 CI 检查未通过也可以。

  • PR 中的提交应代表清晰、合乎逻辑的修改单元，便于评审，并保持可二分查找性（bisectability）。以下指南对这一原则做了展开说明：

    1. 独立、合乎逻辑的修改单元

      每个提交都应对应一个自成一体、有意义的修改。例如，添加功能、修复 bug 或重构现有代码应分别作为单独的提交。避免在同一个提交中混合不同类型的修改（例如功能实现和无关的重构）。

    2. 保持可二分查找性

      PR 中的每个提交都必须能成功构建并通过所有相关测试。这样才能有效地使用 git bisect 找出引入 bug 或问题的具体提交。

    3. 压缩中间或非最终的开发历史

      在开发过程中，提交可能包含中间修改（例如部分实现、临时文件或调试代码）。在提交 PR 之前，应将这些提交压缩（squash）或重写。移除非最终的产物，例如：

      • 临时重命名、之后又再次重命名的文件。

      • 在后续提交中被重写或大幅修改的代码。

    4. 提交前确保历史干净

      在提交 PR 之前，使用交互式变基（git rebase -i）清理提交历史。这有助于：

      • 将零碎、不完整的提交压缩为一个内聚的提交。

      • 确保每个提交都保持可二分查找。

      • 在提高清晰度的同时，保持正确的作者归属。

    5. 重命名和代码重写

      如果在开发过程中的后续提交里重命名或重写了文件或代码，请压缩或重写之前的提交，以反映最终结构。这样可以确保：

      • 历史保持干净，易于理解。

      • 通过消除多余的重命名或部分重写，保持可二分查找性。

    6. 作者归属

      在清理提交历史时，确保作者归属保持准确。

    7. 可读、易评审的历史

      最终的提交历史应便于未来的维护者理解。合乎逻辑的修改单元应组织成若干提交，清晰连贯地讲述所完成的工作。

  • 添加重要的新功能时，应将针对该新功能的测试添加到自动化测试套件中。所有 API 函数都应有测试用例，并且应有针对 API 行为约定的测试。由维护者和评审者酌情判断所提供的测试是否充分。以下示例展示了如何有效测试 API 的最佳实践。

    • Kernel timer tests（内核定时器测试）为 kernel timer（内核定时器）提供了约 85% 的测试覆盖率（按代码行数计算）。

    • 片外外设的模拟器是测试驱动 API 的有效方式。fuel gauge tests（电量计测试）使用 smart battery emulator（智能电池模拟器），为 fuel gauge API（电量计 API）和 smart battery driver（智能电池驱动）提供了测试覆盖。

    • Zephyr 项目的代码覆盖率报告可在 Codecov 上查看。

  • 对 API 的不兼容修改还必须更新下一个版本的发布说明，详细描述该修改。标记为实验性的 API 不受此要求约束。

  • 对 API 的修改必须按照 API 版本规则递增 API 版本号。

  • 必须添加和/或更新文档，以反映 PR 所引入的代码修改。文档修改必须使用现有页面中的恰当术语，并且必须使用美式英语撰写。如果在文档中包含图片，必须遵循 图片 中的规则。更多信息请参阅 文档编写指南。

  • 在发布工程团队成员将 PR 合并到 zephyr 代码树之前，PR 还必须满足所有 PR 合并标准。

维护者可以要求贡献者将一个 PR 拆分为若干较小的 PR，也可以要求其创建一个 RFC 提案。

有助于评审者的工作流程建议

  • 在 PR 中说明你测试了什么以及如何测试：用了哪些开发板或模拟器、哪些 twister 场景或示例，以及哪些没有测试（例如你没有的硬件）。评审者无法区分“在硬件上测试过”和“能编译通过”，所以要说明是哪一种。对于 bug 修复，说明是如何复现该 bug 的，并说明新增的测试在没有修复时会失败。

  • 将后续修改作为对其所属提交的修订（amend）推送（参见 贡献工作流程），而不是作为额外的 "fix review comments" 提交。

  • 明确说明 PR 之间的依赖关系。如果某个 PR 包含另一个尚未合并的 PR 中的提交，请在描述的开头注明（例如 "Depends on #N; the first two commits belong to #N, review them there"），以免评审者重复评审同一段代码或在错误的 PR 中发表评论。在可能的情况下，在所依赖的 PR 合并之前，将这类依赖性 PR 保持为草稿，或者将两项修改放在同一个 PR 中。

  • 评审进行期间，不要将 PR 变基到 main 上，除非存在合并冲突，或者 CI 需要某个只在 main 上才有的修改。GitHub 没有实现 git range-diff，因此变基之后，评审者无法再看到自上一轮以来改动了什么，只能重新阅读整个 PR，并且已有的批准也会被撤销。PR 获得批准之后再变基则没有问题。如果变基不可避免，请将其作为不含其他修改的单独更新推送，并添加评论加以说明。

  • 回复每一条评审评论，要么说明你所做的修改，要么说明为何没有修改。除非你完全按照评审者的建议进行了修改，否则不要自行将评论标记为已解决并隐藏；这应留给提出该评论的评审者处理。Zephyr 项目不要求在合并前解决所有评论。保留一些已完成的讨论处于打开状态，有时有助于了解全局情况。

  • 在 "Files changed" 视图中使用绿色的 "Start Review" 和 "Add Review" 按钮回复评论。这样可以回复多条评论并批量发布回复，从而减少发送给评审者的电子邮件数量。

  • 推送处理评审评论的修改之后，点击每位要求修改的评审者旁边的 "Re-request review"，使该 PR 重新出现在他们的评审队列中。如果这次推送还包含了任何评审评论都未要求的修改，例如变基或无关的修复，请在 PR 评论中加以说明。

让 PR 得到评审

Zephyr 社区由形形色色的个人组成，他们的投入程度和优先事项各不相同。因此，评审者和维护者可能无法立即处理某个 PR。

  • 如果 PR 1 周没有动静，请在 PR 中添加评论，提醒（ping）该 PR 的负责人（Assignee）或评审者。

  • 如果 PR 2 周没有动静，请在 Discord 的 #pr-help 频道发布一条消息，附上该 PR 的链接。

PR 技术问题升级处理

当贡献者反对评审者提出的修改要求时，Zephyr 定义了以下升级处理流程来解决技术分歧。

在升级处理技术分歧之前，请按以下步骤操作：

  • 在 PR 中由负责人、维护者和评审者之间协商解决。

    • 如适用，由负责人担任协调人。

  • 如果没有进展，负责人（维护者）有权驳回评审者过时、无关或不相干的修改要求，但须给评审者至少 1 个工作日的时间来回应、重新考虑其最初的修改要求，或启动升级处理流程。

    负责人有责任在 PR 中记录驳回任何评审的理由，并应通知评审者其评审已被驳回。

    为了给评审者留出回应和升级处理的时间，负责人应阻止该 PR 被合并，方法是不批准该 PR 或设置 DNM 标签。

参与评审过程的任何一方（负责人、评审者或修改的原作者）都可以按以下步骤触发升级处理：

  • 在 PR 上添加 Architecture Review 标签，升级到 Architecture Working Group。除了处理此类升级的每周例会之外，如有请求，Architecture Working Group 还应协助对升级事项进行线下评审，尤其是当任何一方无法参加会议时。

  • 如果所有解决和升级途径都失败了，负责人可以在 PR 上添加 TSC 标签，升级到 TSC，并在 TSC 中获得有约束力的决议。

  • 负责人应确保升级事项得到解决，并将结果记录在 GitHub 上相关的 PR 或 issue 中。
