二进制 blob

对于一个支持多种架构和众多不同 IC 系列的操作系统来说，某些功能如果没有以二进制形式分发的可执行代码的帮助，可能就无法使用。二进制 blob（简称 blob）是包含二进制格式的专有机器码或数据的文件，例如没有以 OSI 批准的许可证发布相应源代码的文件。

Zephyr 支持通过其内置机制下载和使用第三方二进制 blob，但有一些重要的注意事项，将在以下各节中介绍。需要特别指出的是，本节中的所有信息仅适用于 上游（原版）Zephyr。

在 Zephyr 的分叉（fork）或第三方发行版中，对二进制 blob 的支持没有任何限制（也许许可证兼容性除外）。实际上，Zephyr 的构建系统支持与 blob 相关的任意使用场景，包括链接库、将镜像烧录到目标设备等。因此，如果用户无法满足本页所述的要求，可以自由地创建使用二进制 blob 的、基于 Zephyr 的下游软件。

软件许可证

大多数二进制 blob 以专有许可证分发，这些许可证的性质和条件差别很大。由厂商在 blob 提交过程中指定许可证。blob 厂商可以要求用户在获取和安装 blob 时进行点击确认或执行其他类似 EULA 的流程。

托管

blob 必须托管在互联网上，并由第三方基础设施管理。两个可能的例子是由各硬件厂商管理的 Git 仓库和 Web 服务器。

Zephyr 项目不会在其 Git 仓库或任何其他地方托管二进制 blob。

获取 blob

blob 通过 west blobs 命令从官方第三方来源获取。

blob 本身必须在由各自厂商维护的独立 Zephyr 模块仓库 中所包含的 module.yml 文件里指定。这意味着，要在上游 Zephyr 发行版中加入对某个二进制 blob 的引用，必须先有一个模块仓库，或者在提交过程中创建一个。

每个可获取的 blob 都必须在相应的 module.yml 文件中单独标识。blob 的规格说明必须包含：

  • 对 blob 本身的概要描述

  • 版本信息

  • 对厂商所提供文档的引用

  • blob 的 类型，必须是允许的类型之一

  • blob 的校验和，west blobs 会在下载后对其进行检查。这是为了保证可复现性，并在 blob 变化时能够使用 Git 和 west 对问题进行二分查找（bisect）

  • 适用于该 blob 的许可证文本或对该文本的引用，采用 SPDX 格式

关于这些字段更正式的定义，请参阅 相应章节。

west blobs 命令可用于列出可用 blob 的元数据，以及从用户选定的模块中获取 blob。

west blobs 命令只获取和存储二进制 blob 本身。任何配套代码，包括 blob 的接口头文件，都必须位于相应的模块仓库中。

污染（tainting）

包含二进制 blob 会污染 Zephyr 构建。污染的定义源自 Linux 内核；在 Zephyr 中，被污染的镜像是指其中包含二进制 blob 的镜像。

污染状态将通过以下方式告知用户：

  • 一个或多个 Kconfig 选项 TAINT_BLOBS_* 会被设为 y

  • Zephyr 构建系统会在配置阶段发出警告。可以通过 Kconfig 禁用该警告

  • west spdx 生成的 SBOM 会列出链接到镜像中的 blob（参见 预构建库）

  • 内核默认的致命错误处理程序也会明确打印内核的污染状态

  • 启动横幅会打印内核的污染状态

允许的类型

Zephyr 接受以下二进制 blob 类型：

  • 预编译库：以预编译二进制形式分发的硬件支持库，通常用于 SoC 外设。例如无线外设的支持库

  • 固件镜像：包含协处理器或从 CPU 可执行代码的镜像。它可以是完整的，也可以是部分的（通常是增量或补丁数据），一般由主 CPU 复制到 RAM 或 Flash 存储器中。例如运行 Bluetooth LE 控制器的内核所用的固件

  • 其他二进制数据文件。例如预训练的神经网络模型数据

不接受通过专有库提供的与硬件无关的功能。例如，以静态归档形式分发的专有且与硬件无关的 TCP/IP 协议栈会被拒绝。

注意，blob 属于可接受的类型并不意味着项目会无条件接受它；任何 blob 都可能因其他原因而在逐案审查中被拒绝（参见下文针对库的要求）。如有分歧，由 TSC 裁定某个 blob 是否属于上述类型之一。

针对预编译库的要求

本节包含专门针对预编译库 blob 的其他要求。

任何希望提交预编译库的人都必须声明该库满足这些要求。如果之后发现某个 blob 不满足这些要求，项目可以将其从上游发行版中移除。

接口头文件

预编译库必须附带一个或多个定义该库接口的头文件，这些头文件须以 OSI 批准的非 copyleft 许可证分发。

允许的依赖

本节定义了库 blob 要求构建系统提供的外部符号的相关要求。

  • blob 不得直接依赖 Zephyr API。换句话说，必须能够在完全没有 Zephyr 源代码的情况下构建该二进制文件。这是出于松耦合和可维护性的需要，因为 Zephyr API 可能会发生变化，而并非所有项目维护者都能修改这类 blob

  • 如果预编译库中的代码需要 Zephyr（或一般意义上的 RTOS）提供的功能，可以随库一起提供一个操作系统抽象层（也称移植层）的实现。该操作系统抽象层的实现必须是源代码形式，以 OSI 批准的许可证发布，并使用 Doxygen 编写文档。

工具链要求

预编译库 blob 必须采用与 Zephyr 项目支持的工具链兼容、并且能够由其链接的数据格式。这是出于可维护性和可用性的需要。不过，使用这类库可能需要特殊的编译器和/或链接器标志。例如，移植层可能需要特殊标志，静态归档可能需要使用特定的链接器标志。

有限的范围

允许任意库 blob 存在降低上游 Zephyr 软件发行版开源程度的风险。举个极端的例子，如果某个目标平台的 zephyr 内核时钟驱动只是包装一个库 blob 的移植层，那么仅使用开源软件将无法启动该目标平台。

为降低这一风险，上游库 blob 的范围受到限制。项目维护者定义了一个开源测试套件，上游目标平台必须仅使用主线发行版及其模块中包含的开源软件就能通过该测试套件。该开源测试套件目前包括：

  • samples/philosophers

  • tests/kernel

该测试套件的范围可能会随时间扩大。其目标是为一个最小功能集指定测试，任何获得上游 Zephyr 支持的目标平台都必须通过开源软件支持该功能集。

如果某个硬件目标平台无法通过该测试套件，项目可由发布团队酌情决定移除对它的支持。

支持与维护

Zephyr 项目不负责所贡献二进制 blob 的维护和支持。因此，由 Zephyr 项目发布团队酌情逐案决定：

  • 在 zephyr 仓库问题跟踪器上报告的、需要使用 blob 才能复现的 GitHub issue，可能不会被视为 bug

  • 此类 issue 可能会以超出 Zephyr 项目范围为由被关闭

这并不意味着需要 blob 才能复现的 issue 会不经调查就被关闭。例如，该 issue 可能暴露了 Zephyr 中某条代码路径的 bug，而这条路径在没有 blob 的情况下很难或无法触发。项目维护者可以接受并尝试解决此类 issue。

然而，需要保留一定的灵活性，因为项目维护者可能无法判断某个 issue 是由 Zephyr 的 bug 还是 blob 本身引起的，也可能因缺少硬件等原因而无法复现该 bug。

blob 必须有指定的维护者，他们必须及时响应用户的问题报告，并提供 blob 更新来解决问题。如果维护者缺乏响应或支持，Zephyr 项目发布团队可酌情随时从 zephyr/west.yml 中移除引用这些 blob 的模块修订版本。这是为了让项目能够控制代码腐化（bit-rot）、安全问题等。

提议集成二进制 blob 的提交者必须承诺在可预见的未来维护该 blob 的集成。

关于持续集成，项目的 CI 基础设施 不会 获取二进制 blob。该基础设施会构建测试和示例并可选择执行它们，以防止回归和问题进入代码库。这既包括在新建 GitHub PR（拉取请求）时运行的 CI，也包括 CI 基础设施的任何其他定期执行。

提交和评审流程

要在项目中加入对二进制 blob 的引用，应通过标准的 PR（拉取请求）工作流提交，不需要技术指导委员会（TSC）批准。维护者和评审者负责确保所有与 blob 相关的提交符合 二进制 blob 中定义的成文标准。

首次集成二进制 blob 的 PR 应包含有关这些 blob 及其所提供功能的详细信息。该 PR 应提供以下信息以便于评审：

  • 二进制 blob 的来源。

  • blob 的类型（预编译库、固件镜像）。

  • 将引用这些 blob 的 Zephyr 模块。

  • 简要描述这些 blob 的作用。

  • 这些 blob 依赖哪些其他组件（如果有的话）？

  • 这些 blob 所使用的分发许可证。

如果首次集成的 PR 获得了相应的批准，即可集成这些二进制 blob。对于任何技术分歧，适用标准的 PR 升级处理流程。

之后对二进制 blob 的更新遵循 模块更新流程。
