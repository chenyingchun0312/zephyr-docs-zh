示例的定义与标准

定义

示例是一个简洁的 Zephyr 应用程序，用于以易于理解的方式概览一个或多个功能、子系统或模块，包括内核服务、驱动、协议等。示例的范围应当有限，只应专注于演示所展示的子系统或模块中重要或核心的方面。

提交新功能时建议附带示例，但这不是强制要求。

示例标准

1. 示例不得用于测试功能或验证平台

  • 示例的主要目的是为用户提供参考。

  • 示例不得使用 Zephyr 的测试框架。

    • 不得使用 CONFIG_ZTEST

    • 示例中不得使用 zassert。

  • 如果示例能够提供可验证的输出，则应将输出与预期值进行比较，以便对示例本身进行一定程度的测试。更多详细信息请参阅 测试运行器（Twister）。

  • 虽然能成功运行示例确实可以验证功能按预期工作，但这不能替代提交到 tests/ 文件夹中、具有完整覆盖率的专门且全面的测试。在示例中，唯一测试的是可构建性，在某些情况下还会测试示例是否按预期运行，也就是说，测试的是示例本身，而不是示例所基于的子系统。

2. Twister 应能构建每一个示例。

  • 每个示例都必须有一个 YAML 文件。参考：测试运行器（Twister）。

    For example:

    tests:
  sample.kernel.cond_var:
    integration_platforms:
      - native_sim
    tags:
      - kernel
      - condition_variables
    harness: console
    harness_config:
      type: one_line
      regex:
        - ".*Waited and joined with 3 threads"

  • 不要将测试标记为仅构建（build only）。示例应能在文档列出的平台上构建 并 运行。使用 harness 选项跳过执行。只有当 harness 设置为 ztest 或 console 时，Twister 才会尝试烧录并执行构建出的二进制文件。

  • 示例的默认配置必须放在 prj.conf 文件中，并且应能在所有受支持的平台上正常工作。不要依赖 YAML 文件中的 extra_args 或 extra_configs 选项来构建示例。

  • 测试应验证示例的默认配置，以及示例 README 文件中记录的所有可选功能。示例绝不应用于测试其所属子系统或模块的功能。

  • 与示例及其运行相关的、有文档说明的配置选项，可以使用 YAML 文件中的 extra_args 或 extra_configs 选项进行验证。prj.conf 文件中应包含基础配置选项。

  • 在适用的情况下，可以利用 harness_config 的 regex 选项验证示例输出。

  • 使用 platform_allow 将测试限制在示例实际验证过的平台上。这些平台应在示例的 README 文件中列出。

  • 存在时间或资源限制时，使用 integration_platforms 限制范围。理想情况下，通过 PR 向 Zephyr 源码树提交变更时，一个平台就足以验证该示例。

  • 使示例尽可能通用。除非针对特定硬件，否则避免让示例依赖特定平台。

3. 示例应充分覆盖某个子系统、功能或模块。

DO's:

  • 覆盖该功能最常见、最重要的用例。

  • 保持代码简单易读。示例：samples/philosophers。

DONT's:

  • 示例不得测试负面或边界情况下的行为。

  • 示例不得是单元测试。

4. 示例必须有文档。

  • 示例文件夹中必须有一个 README.rst 文件，例如 samples/subsys/foo/README.rst，清楚地说明示例的用途、硬件要求以及（如适用）预期的示例输出。

  • 确保从 samples/index.rst 开始的示例层级结构中可以访问到该 README.rst 文件。

README Template:

  • 概述（如适用）。

  • 软件/硬件要求

  • 构建与运行说明

  • 示例输出（如适用）。

作为入门参考，samples/kernel/condition_variables/condvar 这个示例是一个很好的范例。
