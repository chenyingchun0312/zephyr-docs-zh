zperf 确定性回环吞吐量测试（qemu_x86 + icount）

概述

本文介绍一种自包含的方式，将 zperf 示例用作 网络吞吐量回归检查。该方式与硬件无关，最重要的是，它与运行模拟器的主机速度无关。

测量完全在 qemu_x86 客户机内部运行：

  • 所有流量都经过客户机内部的回环接口，因此测量路径上没有外部（实时）网络后端。

  • QEMU 以 icount 模式 运行，因此客户机的时间概念由已执行的指令数推导得出，而不是来自主机的挂钟时间。

  • 该示例自行驱动（没有交互式 shell）：它在回环接口上启动一个 UDP 接收端和一个 TCP 接收端，向 127.0.0.1 上传数据，并打印结果。

吞吐量等于 bytes / elapsed_time，因此只有当 elapsed_time 是确定的且与主机无关时，该指标才可用于回归检测。在 icount 模式下，虚拟 CPU 每执行一条指令，虚拟时间就前进 2^shift ns，因此报告的吞吐量成为 每字节指令数 的确定性函数：多次运行之间、不同机器之间结果相同，并且对真实的代码回归敏感（每字节指令数增加会使该数值降低）。所有流量都保持在回环接口上，意味着不存在会破坏 icount 确定性的外部实时后端。

备注

Mbps 的绝对值是一个 虚拟时间代理指标（代表每字节指令数），而不是真实的线路速率。只能比较在相同 icount shift、数据包大小和节拍频率下采集的数值。

工作原理

运行器位于 src/main.c 中，由 CONFIG_ZPERF_LOOPBACK_SELFTEST 控制。启用后，示例会：

  1. 自行启用网络（自动初始化被禁用，以免传输与网络启用过程产生竞争）。

  2. 对于每个 IP 协议族，运行一系列传输，每次传输依次启动对应的接收端、运行阻塞式上传、停止接收端，并为每次传输打印一行 ZPERF-RESULT <marker>_mbps=<value>：

    标记

    传输

    udp4 / udp6

    基准 UDP，接近 MTU 的负载（单个未分片的数据报）。

    udp4_frag / udp6_frag

    使用超大负载的 UDP，在发送端强制进行 IP 分片，在接收端进行重组。仅在启用了对应的 CONFIG_NET_IPV4_FRAGMENT / CONFIG_NET_IPV6_FRAGMENT 时运行。

    tcp4 / tcp6

    基准 TCP（启用 Nagle）。

    tcp4_nodelay / tcp6_nodelay

    使用 TCP_NODELAY（禁用 Nagle）的 TCP，用于覆盖另一条发送路径。

  3. 打印最终的 ZPERF-DONE 标记。

两个 IP 协议族都会被测试，因此任一代码路径中的回归都能被发现。IPv4 传输使用 127.0.0.1，IPv6 传输使用 ::1；回环驱动会将这两个地址都分配给回环接口。对于每个协议族，接收端都绑定到该回环地址（而不仅仅是接口的默认地址），以便客户端能够连接。当 CONFIG_NET_IPV6 被禁用时，会跳过 IPv6 测试（IPv4 同理）。

每次上传都使用非默认的套接字优先级（NET_PRIORITY_VI）发送。结合配置了多个流量类别（见下文），流量会经由 net_tc.c 中各流量类别专用的线程，而不是在调用者上下文中处理，因此每次运行都会测试这条调度路径。

整个过程由 overlay-loopback-icount.conf 配置，它叠加在现有的 overlay-loopback.conf 之上。

配置参数

Kconfig 选项

含义

CONFIG_ZPERF_LOOPBACK_SELFTEST

启用自驱动的回环运行器。

CONFIG_ZPERF_LOOPBACK_SELFTEST_DURATION_MS

每次（UDP 和 TCP）上传运行的持续时间。

CONFIG_ZPERF_LOOPBACK_SELFTEST_PACKET_SIZE

负载大小（字节）。默认值是 1280 字节 MTU 下的 IPv6 TCP MSS，因此每次写入都是一个完整大小的分段（见下文）。

CONFIG_ZPERF_LOOPBACK_SELFTEST_FRAG_PACKET_SIZE

额外的分片 UDP 运行所用的负载大小（字节）。必须超过 MTU（使数据报被分片），且小于 CONFIG_NET_ZPERF_MAX_PACKET_SIZE。

CONFIG_ZPERF_LOOPBACK_SELFTEST_RATE_KBPS

目标速率；0 表示以（虚拟）CPU 允许的最快速度发送。

CONFIG_ZPERF_LOOPBACK_SELFTEST_PORT

接收端和客户端共同使用的服务器端口。

实现说明 / 注意事项

overlay-loopback-icount.conf 中包含了一些不太直观的设置：

  • 栈大小。 回环驱动在发送方上下文中同步投递每个数据包，因此整个接收路径（以及阻塞式客户端上传）都嵌套在调用者的栈上。主线程和网络线程的栈都已加大；否则客户机在启动时会发生栈溢出并出错。

  • 节拍频率。 节拍频率提高到 10 kHz。在默认的 100 Hz 下，USECS_PER_TICK >= 1000 会编译进 UDP 上传器的时钟补偿路径，该路径会除以每个数据包的持续时间。在不限速率时该持续时间为零，因此高于 1 kHz 的节拍既避免了除零错误，又能提供细粒度的发送节奏控制。

  • 接近 MTU 的数据包大小以及 MSS 注意事项。 覆盖文件将回环 MTU（CONFIG_NET_LOOPBACK_MTU）提高到 1280，并将 zperf 自身的数据包上限（CONFIG_NET_ZPERF_MAX_PACKET_SIZE）提高到负载之上，因此默认 1220 字节的负载会产生接近 MTU 的帧。大帧使每字节的工作（校验和、遍历缓冲区/分片）超过每次调用的固定开销而占主导地位，而这正是吞吐量回归检查应当敏感的部分。要在不同协议族之间进行 公平 的 TCP 比较，1220 这个确切值很重要：zperf TCP 上传器每次 send() 发送整个负载，由 TCP 按 MSS 进行分段。在 1280 字节 MTU 下，IPv4 MSS 为 1280 - 40 = 1240，而 IPv6 MSS 只有 1280 - 60 = 1220（IPv6 报头大 20 字节）。例如 1232 的负载在 IPv4 下可放入一个分段，但超过了 IPv6 MSS，因此每次 IPv6 写入都会被拆分为一个完整的 1220 字节分段加一个 12 字节的小分段，IPv6 的分段/ACK 数量几乎翻倍，IPv6 TCP 吞吐量几乎减半。使用 1220 可使两种协议族的每次写入都保持为单个完整大小的分段。基准 UDP 负载在两种协议族下也都小于 MTU，因此这些数据报不会被 IP 分片。由于 net_buf 数据大小（1100）小于 MTU，每个帧仍会跨越两个缓冲区分片，这是有意为之，用于测试分片链的遍历。

  • IP 分片覆盖。 启用了 CONFIG_NET_IPV4_FRAGMENT 和 CONFIG_NET_IPV6_FRAGMENT，运行器为每个协议族额外增加一次 UDP 运行，其负载（CONFIG_ZPERF_LOOPBACK_SELFTEST_FRAG_PACKET_SIZE，默认为 2000）超过 MTU。这会驱动发送端 ipv4.c / ipv6.c 中的分片路径以及接收端的重组路径（即 *_frag 标记）。CONFIG_NET_ZPERF_MAX_PACKET_SIZE 被提高到该负载之上。

  • 流量类别与优先级。 覆盖文件配置了多个 TX/RX 流量类别（CONFIG_NET_TC_TX_COUNT / CONFIG_NET_TC_RX_COUNT = 2），并启用了 CONFIG_NET_CONTEXT_PRIORITY（以及 CONFIG_NET_ALLOW_ANY_PRIORITY）。每次上传都设置非默认的 SO_PRIORITY，因此流量通过各流量类别专用的线程分派，而不是在调用者上下文中处理。这会测试 net_tc.c 调度路径，但会增加上下文切换，因此与单流量类别配置相比，绝对数值会降低。

  • 不限速率时的计算。 在不限速率（rate = 0）模式下，运行器会选取一个足够高的速率，使每个数据包的节奏延迟向下取整为零。该合成速率以 64 位计算，以避免中间结果溢出，因此支持任何现实的数据包大小（最大约 500 kB）。

  • 不使用 SLIP/TAP。 QEMU 的 SLIP 主机网络后端已被禁用；运行时不需要主机端的 slip.sock。

  • 日志缓冲区大小。 结果行使用 printk() 打印，日志子系统会通过其延迟后端转发这些内容。在默认的 1024 字节缓冲区下，qemu_x86_64 运行会在最初的 IPv4 传输期间使缓冲区溢出，随后 CONFIG_LOG_MODE_OVERFLOW 会丢弃三条最旧的消息，从而悄无声息地吞掉 udp4_frag 结果行，导致该指标根本不会出现在报告中。覆盖文件将 CONFIG_LOG_BUFFER_SIZE 提高到 4096。测量本身不受影响；使用更大缓冲区时，32 位的数值逐位相同。

用法

构建并运行一次

west build -p -b qemu_x86 -d ../build/zperf_loop samples/net/zperf -- \
    -DEXTRA_CONF_FILE="overlay-loopback.conf;overlay-loopback-icount.conf"
west build -t run -d ../build/zperf_loop

预期输出（在给定构建上，数值是确定的，并且在多次运行中完全重复；具体数值取决于工具链、数据包大小、icount shift 和节拍频率，因此仅作示例）:

ZPERF-RESULT udp4_mbps=13.099
ZPERF-RESULT udp4_frag_mbps=20.249
ZPERF-RESULT tcp4_mbps=5.970
ZPERF-RESULT tcp4_nodelay_mbps=5.876
ZPERF-RESULT udp6_mbps=13.310
ZPERF-RESULT udp6_frag_mbps=20.059
ZPERF-RESULT tcp6_mbps=5.979
ZPERF-RESULT tcp6_nodelay_mbps=5.910
ZPERF-DONE

IPv4 和 IPv6 的 TCP 数值接近，因为默认负载就是 IPv6 TCP MSS；参见 Implementation notes / gotchas 中的 MSS 注意事项。*_frag（分片）UDP 运行报告的数值比基准 UDP 运行 更高，因为即使计入分片的工作量，更大的数据报也能把每个数据报的固定开销分摊到更多负载上。

通过 twister 运行

tests.yaml 中的场景 sample.net.zperf.loopback_icount 使用 console harness，并将吞吐量数值记录到 twister JSON 报告中：

./scripts/twister -p qemu_x86 -s sample.net.zperf.loopback_icount \
    --outdir ../build/zperf_run

该场景可在 qemu_x86（32 位）和 qemu_x86_64（64 位）上运行；后者提供一个 64 位数据点（例如 64 位校验和快速路径）。两者可以在一次运行中同时测量：

./scripts/twister -T samples/net/zperf -s sample.net.zperf.loopback_icount \
    -p qemu_x86 -p qemu_x86_64 --outdir ../build/zperf_run

使用 -T samples/net/zperf 限制扫描范围，可以避免为单个场景遍历整个源码树。

两个平台报告的绝对数值不同，彼此之间不可比较，因此 scripts/zperf_regression.py 以 twister 平台名称（qemu_x86/atom、qemu_x86_64/atom）作为每个指标的键，并分别报告。使用 --platform 可将报告限制为其中一个平台，参数可以是完整的 board/soc 名称，也可以只写开发板名称。

基准与回归门限

辅助脚本 scripts/zperf_regression.py 读取 twister 运行的记录数据。在参考提交上采集一次基准：

./scripts/twister -p qemu_x86 -s sample.net.zperf.loopback_icount \
    --outdir ../build/zperf_base
samples/net/zperf/scripts/zperf_regression.py --base-dir .. \
    --twister-json ../build/zperf_base/twister.json \
    --save baseline.json

在之后的提交上重新运行，并以允许的最大降幅（百分比）作为门限：

./scripts/twister -p qemu_x86 -s sample.net.zperf.loopback_icount \
    --outdir ../build/zperf_cur
samples/net/zperf/scripts/zperf_regression.py --base-dir .. \
    --twister-json ../build/zperf_cur/twister.json \
    --baseline baseline.json --tolerance 5

如果任何记录的指标降幅超过容差，脚本会以非零状态退出，因此适合作为 CI 回归检查。

也可以直接比较两次运行，无需中间的基准文件：

samples/net/zperf/scripts/zperf_regression.py --base-dir .. \
    --twister-json ../build/zperf_cur/twister.json \
    --baseline-twister-json ../build/zperf_base/twister.json

其余选项影响的是报告的形式，而不是测量本身：

选项

含义

--threshold PCT

报告的噪声下限，默认为 1%。变化小于此值的指标会被描述为不变，而不是改进或回归。对于给定的二进制文件，icount 结果完全可重复，但两个源码树会构建出两个不同的二进制文件，仅代码布局的差异就可能使数值变化，即使执行的工作没有任何改变。实际上这种漂移很小：在比较相隔 157 个提交、且其间只改动了 TCP 的两个源码树时，所有 UDP 指标在 qemu_x86 上逐位相同，在 qemu_x86_64 上的差异也在 0.02% 以内。

--markdown PATH

以 markdown 表格形式输出比较结果，每个平台一节，用于 GitHub Actions 作业摘要或 PR 评论。所有指标均未变化的平台会折叠到一个 <details> 块中，其摘要行会注明这一点；有指标变化的平台则保持展开。

--annotate

每个平台输出一条 ::notice:: 工作流命令，汇总发生变化的指标。

--exit-zero

始终以成功状态退出。适用于比较仅供参考、不得导致构建失败的情况。缺失或无法构建的基准也以同样方式报告，即视为无法进行比较。

备注

为了在脚本由自动化流程驱动时保证安全，它读写的每个文件都必须解析到 --base-dir（默认：当前目录）之下的位置；逃逸出该目录的路径（通过 .. 或绝对路径）会被拒绝。示例中传入 --base-dir ..，是因为它们从同级的 ../build 目录树读取 twister 报告，同时将输出写入仓库。

持续集成

.github/workflows/net-perf.yml 会在每个涉及 subsys/net/、include/zephyr/net/、lib/net_buf/、回环驱动或本示例的 PR 上运行此场景。它在同一个运行器上、在两个平台上分别测量该 PR 及其目标分支，并将比较结果写入作业摘要。

以下两个细节保证了比较结果的意义：

  • 工作流在 PR 变基到目标分支之后运行，因此差异只反映该系列提交本身的影响，不会混入目标分支上无关的变化。

  • 测量目标分支时使用 PR 中的 samples/net/zperf/ 副本，因此两侧的运行器、覆盖文件和负载大小完全相同，只有被测代码不同。因此，修改该示例的 PR 不会通过改变测量对象而使数值发生变化。

配套的工作流 .github/workflows/net-perf-comment.yml 会将相同的报告作为评论发布到 PR 上，使数值在评审变更的地方可见。它是一个独立的工作流，因为测量由 pull_request 事件触发，该事件的令牌对于派生仓库是只读的，无法发表评论；配套工作流在 workflow_run 上运行，从构件（artifact）中读取报告和 PR 编号，并且从不检出 PR 代码。每个 PR 只有一条评论，每次推送时原地重写；所有指标均未变化的平台会被折叠，使不变的结果只占一行。

该检查 仅供参考。它以 --exit-zero 运行，每个测量步骤都设置为 continue-on-error，并且不属于必需检查：异常或出人意料的数值只是提供给评审者的信息，绝不会阻止合并。无法产生的结果（例如目标分支构建失败）会被报告为无法进行比较，作业仍然通过。

只测量回环路径，因此报告中数值不变并不代表变更对性能没有影响；驱动、L2 和卸载相关的工作根本不会在这里体现。

可视化结果

传入 --plot 可将指标的条形图写入一个自包含的 SVG 文件（无需额外的 Python 依赖）。不带基准时绘制当前值；与 --baseline 结合使用时，绘制基准与当前值分组对比的条形图：

samples/net/zperf/scripts/zperf_regression.py --base-dir .. \
    --twister-json ../build/zperf_cur/twister.json \
    --baseline baseline.json --plot throughput.svg

当报告中包含多个平台时，平台名称会附加到每个文件名后，因此上例会写出 throughput-qemu_x86_atom.svg 和 throughput-qemu_x86_64_atom.svg。
