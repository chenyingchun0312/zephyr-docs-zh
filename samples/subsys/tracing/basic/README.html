Tracing

Browse source code on GitHub

概述

本示例演示 跟踪 子系统。它驱动内核中具有代表性的一组功能，因此无论构建时选择何种跟踪格式和后端，都会产生丰富且连续的跟踪事件流，供主机捕获和可视化：

  • 两个线程（一个静态，一个动态）以乒乓方式互相发送“Hello World”问候，并通过一对信号量进行同步。只要示例在运行，就会不断产生线程切换、休眠以及信号量释放/获取事件。

  • 启动时，一个一次性工作负载会驱动一个互斥量、系统工作队列和一个内核定时器，使这些对象的生命周期事件也出现在跟踪中。

  • 示例中多处使用 sys_trace_named_event() 发出自定义的、由应用程序定义的事件（一个短名称加两个 32 位参数）。具名事件是在应用程序代码中为跟踪添加标注的主要方式。

可选的 GPIO 场景（samples/subsys/tracing/basic/src/gpio_main.c）还会调用 GPIO API，从而触发 GPIO 跟踪钩子。

格式与后端

跟踪沿两个相互独立的维度进行配置：格式 描述事件的编码方式，后端 描述编码后的字节如何离开设备。

默认的 samples/subsys/tracing/basic/prj.conf 是一个完整、可用的基线配置：它启用了使用 CTF 格式和 RAM 后端的跟踪，不需要任何传输方式或设备树设置，因此可以在任何开发板上构建和运行。不加任何额外选项构建示例就已经会产生跟踪。

要通过某种传输方式输出跟踪流，或使用其他格式，请通过 EXTRA_CONF_FILE 在基线之上叠加某个 prj_*.conf 覆盖配置。每个覆盖配置只包含与基线不同的选项，因此可以与基线（以及开发板配置）组合使用而不会重复：

默认（RAM）配置的用法

不加任何额外选项，为任意开发板构建基线配置：

west build -b qemu_x86 samples/subsys/tracing/basic

CTF 流缓冲在 RAM 中的 ram_tracing 数组里。让应用程序运行一段时间，然后在调试器中暂停目标，并将缓冲区转储到文件中。例如，在 GDB 中：

dump binary memory channel0_0 &ram_tracing &ram_tracing+sizeof(ram_tracing)

缓冲区大小由 CONFIG_RAM_TRACING_BUFFER_SIZE 控制。转储的文件是一个 CTF 流，请按照 Decoding a CTF trace 中的说明进行解码。

UART 跟踪后端的用法

使用以下命令构建 UART 跟踪镜像：

west build -b mps2/an521 samples/subsys/tracing/basic -- -DEXTRA_CONF_FILE=prj_uart.conf

或者，构建二进制 CTF 流：

west build -b mps2/an521 samples/subsys/tracing/basic -- -DEXTRA_CONF_FILE=prj_uart_ctf.conf

备注

可能需要在设备树的 chosen 节点下设置 zephyr,tracing-uart 属性。示例请参阅 samples/subsys/tracing/basic/boards/mps2_an521_cpu0.overlay。

应用程序运行一段时间后，检查跟踪输出文件（跟踪 UART 上收到的字节）。对于 CTF 流，请按照 Decoding a CTF trace 中的说明进行解码。

USB 跟踪后端的用法

使用以下命令构建 USB 跟踪镜像：

west build -b reel_board samples/subsys/tracing/basic -- -DEXTRA_CONF_FILE=prj_usb_ctf.conf

当串口控制台出现如下稳定输出后：

thread_a: Hello World from reel_board!
thread_b: Hello World from reel_board!
thread_a: Hello World from reel_board!
thread_b: Hello World from reel_board!

将开发板的 USB 端口连接到主机设备，并在主机上运行 scripts/tracing/trace_capture_usb.py 脚本：

sudo python3 trace_capture_usb.py -v 0x2FE3 -p 0x0001 -o channel0_0

USB 设备的 VID 和 PID 是可配置的，只需相应地调整即可。捕获的 channel0_0 文件是一个 CTF 流，请按照 Decoding a CTF trace 中的说明进行解码。

POSIX 跟踪后端的用法

使用以下命令构建 POSIX 跟踪镜像：

west build -b native_sim samples/subsys/tracing/basic -- -DEXTRA_CONF_FILE=prj_native_ctf.conf

运行生成的可执行文件，它会将 CTF 流写入当前工作目录中名为 channel0_0 的文件：

./build/zephyr/zephyr.exe

几秒钟后按 Ctrl-C 停止运行，并按照 Decoding a CTF trace 中的说明解码 channel0_0。

USER 跟踪后端的用法

“user”格式完全不使用后端，而是由内核调用应用程序直接实现的弱符号 sys_trace_*_user 回调。本示例实现的线程、ISR、休眠和 GPIO 钩子请参阅 samples/subsys/tracing/basic/src/tracing_user.c。使用以下命令构建 USER 跟踪镜像：

west build -b qemu_x86 samples/subsys/tracing/basic -- -DEXTRA_CONF_FILE=prj_user.conf

事件发生时，这些回调会直接打印到控制台，例如：

sys_trace_thread_switched_in_user: 0x...
sys_trace_k_thread_sleep_enter_user: thread=0x... timeout=... ticks

SEGGER SystemView RTT 的用法

使用 SystemView RTT 跟踪代码片段（rtt-tracing） 构建 SystemView 跟踪镜像：

west build -b frdm_k64f -S rtt-tracing samples/subsys/tracing/basic

在目标运行期间，在 SEGGER SystemView 主机应用程序中打开跟踪。

Percepio Tracealyzer 的用法

构建 Percepio 跟踪镜像（要求工作区中存在 percepio 模块）：

west build -b frdm_k64f samples/subsys/tracing/basic -- -DEXTRA_CONF_FILE=prj_percepio.conf

在 Percepio Tracealyzer 中打开生成的记录。

GPIO 跟踪的用法

使用以下命令构建 GPIO 跟踪镜像（带 GPIO 钩子的 user 格式）：

west build -b native_sim samples/subsys/tracing/basic -- -DEXTRA_CONF_FILE=prj_gpio.conf -DEXTRA_DTC_OVERLAY_FILE=gpio.overlay

调用 GPIO API 时，GPIO 回调会打印到控制台。

解码 CTF 跟踪

CTF 后端（UART、USB、POSIX 和 RAM）输出遵循 subsys/tracing/ctf/tsdl/metadata 中元数据的二进制流。要查看它，请将捕获的流放在该元数据文件旁边，并使用支持 CTF 的工具打开，例如 babeltrace2：

mkdir ctf
cp channel0_0 ctf/
cp $ZEPHYR_BASE/subsys/tracing/ctf/tsdl/metadata ctf/
babeltrace2 ctf/

同一个 ctf 目录也可以在 Trace Compass 中打开，以图形化时间线查看。

在终端中查看 CTF 跟踪

如果想快速查看而不安装任何外部工具，可以使用 scripts/tracing/trace_viewer.py 在控制台上以图形方式呈现跟踪，风格类似 SEGGER SystemView 或 Trace Compass。它自行解码打包的 CTF 记录（从同一个 subsys/tracing/ctf/tsdl/metadata 读取字段布局），因此除 Python 3 外没有其他依赖。

使用默认的 semihosting 后端时，运行会在构建目录中生成 tracing.bin：

west build -p -b mps2/an385 samples/subsys/tracing/basic -t run
$ZEPHYR_BASE/scripts/tracing/trace_viewer.py build/tracing.bin

交互视图将屏幕的大部分用于甘特图式的时间线，每个线程一条泳道（另加空闲和 ISR 泳道）。每条泳道按线程随时间变化的 状态 着色，而不是按线程身份着色，因此调度情况一目了然：运行（█，绿色）、就绪/被抢占并等待 CPU（▓，黄色）、阻塞在内核对象上（▒，红色）、因超时而休眠（░，青色）以及挂起（—）。从就绪到运行的转换就是上下文切换；而某个线程处于阻塞状态、同时一个较低优先级的线程在运行，就是典型的优先级反转形态。当某条泳道处于阻塞状态时，信息栏会针对播放头处选中的泳道指出阻塞 原因，例如 blocked on sem 0x2000012c 或 blocked on mutex 0x...。

泳道下方的指标面板汇总可见窗口内的情况：CPU 繁忙度仪表、上下文切换速率和事件速率，以及每个线程的堆叠利用率条，显示各线程在运行、就绪、阻塞和休眠之间的时间分配。该面板会随平移和缩放而更新（按 m 切换显示）。

可移动的播放头用于选择跟踪中的某个时间点，图表下方有一个紧凑的信息栏（图例、正在运行的线程，以及所选泳道的状态和原因）。导航按键：方向键（移动播放头 / 选择泳道）、,/.（平移）、+/-（缩放）、a（适配整个跟踪）、m（切换指标面板）和 i（切换信息栏）。

按 space 回放跟踪：播放头按实际时间前进，图表随之滚动；[ 和 ] 调整回放速度。按 v 切换到原始 CTF 日志视图，这是一个可滚动的表格，列出所有已解码的事件，并高亮显示最靠近播放头的事件。按 q 退出。

要在应用程序仍在运行时观察跟踪逐步生成，请添加 -f / --follow。查看器会随着文件增长增量解码，并使图表始终停留在最新事件处；任何平移或缩放都会解除这种跟随。随时按 End（或 f）即可跳转到最新状态，并与新到达的事件重新同步，甘特图视图和日志视图都适用。这与 semihosting 后端天然契合，应用程序在 QEMU 下运行时，该后端会写入 tracing.bin:

west build -t run &
$ZEPHYR_BASE/scripts/tracing/trace_viewer.py -f build/tracing.bin

（查看器会等待文件和第一批事件出现，因此可以在运行之前或之后启动它。）

传入 --text 可生成静态、非交互式的 ASCII 时间线，便于通过管道传递或重定向；传入 --metadata <path> 可指定特定的元数据文件。
