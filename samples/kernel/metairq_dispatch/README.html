Meta-IRQ Thread Priority

Browse source code on GitHub

概述

本示例实现一个以 Meta-IRQ 优先级运行的线程，在硬件 ISR 结束时同步地执行“下半部”（bottom half）式处理。它实现了一个模拟“设备”，该设备产生的消息需要分发到多个异步队列，这些队列分别供给以不同优先级运行的工作线程。分发由一个 Meta-IRQ 线程处理，该线程通过队列从设备 ISR（实际上只是一个定时器中断）获取数据。

每条消息都需要在工作线程中进行随机（且不可忽略）量的处理。这构成了一个“突发负载”环境：偶尔的负载尖峰需要抢占正在运行的线程，并推迟较低优先级线程的调度。每条消息附带一个时间戳，可以在以下几个点计算每条消息的延迟：

  • 从 ISR 中创建消息到 Meta-IRQ 线程收到并分发消息之间的周期数。

  • 从 ISR 到工作线程收到消息之间的时间。

  • 在工作线程中处理消息实际花费的时间，用于与所需处理时间比较。这提供了一种测量线程未被调度时抢占开销的方法。

结果中需要注意的几点：

  • 平均而言，较高优先级（编号较小）的线程延迟更低、处理延时更小，符合预期。

  • 协作式调度线程的处理延时表现明显优于可抢占线程，因为它们只能被 Meta-IRQ 线程抢占。

  • 由于排队和突发负载，任何优先级的工作线程都会经历一些与负载相关的延时，因为 CPU 偶尔会出现工作量超过可用时间的情况。

  • 但无论系统负载或线程配置如何，Meta-IRQ 线程总是在 ISR 之后立即运行。它在所有情况下都表现出可靠、恒定的延迟，因为它可以抢占所有其他线程，包括通常无法被抢占的协作式线程。

要求

本示例应能在任何支持中断抢占正在运行的线程、具有可用定时器驱动和日志输出的 Zephyr 平台上良好运行。出于精度考虑，在定时器节拍率较高（理想情况下 10 kHz 以上）的系统上，它会产生更好（也更多）的数据。

注意，由于本测试本质上测量的是线程抢占行为，未经修改无法在 native_sim 平台上运行。在该仿真环境中，线程不会被抢占，只会在特定的检测点（例如 k_busy_wait() 中）主动释放 CPU。

构建与运行

本应用程序可以按如下方式在 frdm_k64f 上构建并运行：

west build -b frdm_k64f samples/kernel/metairq_dispatch
west flash

要为其他开发板构建，请将上面的 "frdm_k64f" 改为该开发板的名称。
