详细描述

IEEE 802.15.4 驱动接口 API。

注解
出于向后兼容，此结构体被称为 "radio" API。更好的名称应是 "IEEE 802.15.4 驱动 API"，因为典型的驱动不仅实现 L1/无线（PHY）特性，在厂商特定的驱动硬件或固件提供卸载机会时也会实现 L2（MAC）特性。

虽然 L1 级驱动特性完全由驱动实现，且为支持某些应用需求可能是必需的，但 L2 特性在默认情况下宜为可选，仅在驱动维护者认为有必要为性能优化或精确时序时才需实现。对于所有 L2/MAC 特性，尤其当多数现有树内驱动未在厂商硬件/固件中实现这些特性时，宜在与驱动无关的 L2 层提供回退实现（"Soft MAC"）。然而，若驱动提供卸载机会，则 L2 实现应将性能关键或资源密集的任务委托给驱动。

所有驱动都应支持两种外部可观测的接口工作状态："UP" 和 "DOWN"。驱动还可以额外支持 "TESTING" 接口状态（参见 continuous_carrier()）。

适用以下规则：

  • 当接口能够发送和接收报文时视为 "UP"，否则视为 "DOWN"（参见 RFC 2863, section-3.1.14、net_if_oper_state 中相应 ifOperStatus 值的精确定义，以及下面 continuous_carrier() 的例外）。在 "UP" 状态下因活动的接收窗口配置而暂时禁用接收机的设备仍被视为 "UP"。
  • 上层将假定：在调用 start() 返回零或 -EALREADY 后，驱动所管理的接口为 "UP"；在调用 stop() 返回零或 -EALREADY 后，接口为 "DOWN"。
  • 驱动应阻塞 start()/stop() 调用，直到接口完全转换到新状态（例如接收机已可工作、正在进行的发送已结束等）。若无需 CPU 参与即可等待新状态，驱动宜让出调用线程（即 "睡眠"）。
  • 驱动负责保证状态变化的原子性。应实现适当的同步手段（加锁、原子标志等）。
  • 当接口处于 "DOWN" 时，驱动应置于尽可能低的功耗状态。驱动可以在达到最低功耗状态之前就从 stop() 返回，即异步管理功耗。当接口处于 "UP" 时，驱动宜在可能时自行异步地转入更低功耗状态。若驱动声称支持定时 RX/TX 能力且上层配置了 RX 时隙，则驱动应立即（异步地）转入尽可能低的功耗状态，直到 RX 时隙开始或某个已调度的报文需要发送。
  • 驱动不得自行改变接口的 "UP"/"DOWN" 状态。初始时接口应处于 "DOWN" 状态。
  • 实现可选 continuous_carrier() 操作的驱动，若该操作返回零，则被视为处于 RFC 2863 的 "testing" ifOperStatus 状态。该状态在调用 start() 或 stop() 之前一直有效。若 continuous_carrier() 返回非零值，则上层采用之前的状态。
  • 若调用 start()/stop() 返回零或 -EALREADY 之外的任何值，上层将认为接口处于 RFC 2863 所定义的 "lowerLayerDown" 状态。
  • 目前不支持 RFC 2863 的 "dormant"、"unknown" 和 "notPresent" ifOperStatus 状态。"lowerLevelUp" 状态。
  • ed_scan()、cca() 和 tx() 操作应仅在 "UP" 状态下受支持，在其他任何状态下返回 -ENETDOWN。更多细节参见下面的函数级 API 文档。
注解
对于支持定时 RX/TX 的设备，"UP" 状态并不等同于 "接收机已启用"。若在调用 start() 之前配置了接收窗口（即 RX 时隙，参见 UP 状态时不会启用接收机。在接口处于 "UP" 时配置接收窗口会立即使接收机被禁用，直到配置的接收时间到来。

注解
此函数不得返回任何可由 MAC（L2）层配置的值。它专用于来自驱动实现、且无法由 L2 直接或间接推导的非布尔（即标量或结构化）属性。布尔属性应实现为 ieee802154_hw_caps。

-ENOENT驱动不提供所请求的属性。值结构体未用属性数据更新。该值属性的内容未定义。

◆ tx

int(*) ieee802154_radio_api::tx(const struct device *dev, enum ieee802154_tx_mode mode, struct net_pkt *pkt, struct net_buf *frag)

将报文分片作为单个帧发送

视驱动支持的卸载特性级别而定，该帧可能未完全加密/认证，也可能不含 FCS。L2 实现有责任根据驱动所声明的卸载能力准备帧，并决定 CCA、CSMA/CA、ACK 或重传过程需要在驱动外部（"soft MAC"）还是内部（"hard MAC"）执行。

所有源自 L2 的帧都应预先分配并预填充所有必需的 IE，以便驱动完全无需解析和操作 IE。若驱动不具备 IEEE802154_HW_RX_TX_ACK 能力，这也包括 ACK 报文。对于具备 IEEE802154_HW_RX_TX_ACK 能力的驱动，另请参见 IEEE802154_CONFIG_ENH_ACK_HEADER_IE。

对于 L2 在未知 TX 时间时无法准备的 IE（例如 CSL IE、会合时间 IE、时间校正 IE 等），应在任一定时 TX 模式下发送，并在 IE 中预填充适当的时序信息，使得驱动完全无需解析和操作 IE，除非帧由驱动自己生成。

若支持并使用任一定时 TX 模式（参见 ieee802154_hw_caps 和 ieee802154_tx_mode），则驱动应负责自行在精确的编程时刻调度并发送报文，无需上层进一步交互。调用 tx() 将阻塞，直到报文成功发送（可能包括信道获取和报文确认）或发生终止性发送错误。驱动应睡眠，并将功耗保持在尽可能低的水平，直到调度的发送时间到来或处于其他空闲等待时间。

警告
驱动不得取得给定网络报文和帧（分片）缓冲区的所有权。驱动所需的任何数据（包括实际帧内容）必须同步读取，并在需要稍后使用时在内部复制（例如协议配置所需的 IE 内容、帧计数器状态、序列号等）。函数返回后，上层可立即复用或释放报文和缓冲区。
注解
实现可以 **睡眠**，通常不是 **isr-ok**，尤其当支持定时 TX、CSMA/CA、重传、自动 ACK 或其他意味着相当长空闲等待时间的卸载特性时。除非接口处于 "UP"，否则应返回 -ENETDOWN。
发送发生在通过调用 set_channel() 所设置的信道上。然而，若设置了 CONFIG_IEEE802154_SELECTIVE_TXCHANNEL 且驱动具备 IEEE802154_HW_SELECTIVE_TXCHANNEL 能力，则以 mode 为 IEEE802154_TX_MODE_TXTIME 或 IEEE802154_TX_MODE_TXTIME_CCA 请求的发送，应使用 net_pkt_ieee802154_txchannel() 返回的信道来发送报文，并（若帧要求）在该信道上接收 ACK。操作完成后，驱动应返回先前由 set_channel() 调用设置的信道。上层有责任通过调用 net_pkt_set_ieee802154_txchannel() 为报文设置所需的信道。此特性允许 IEEE 802.15.4-2020 第 6.12.2.7 章 "多信道上的 CSL" 所述的 CSL 发送。此特性允许在发送前尽可能晚地切换信道，而不会中断若单独调用 set_channel() 可能发生的接收。
参数
dev指向 IEEE 802.15.4 驱动设备的指针
mode发送模式，其中一些需要特定的卸载能力。
pkt指向要发送的网络报文的指针。
frag指向包含单个分片（含要发送的帧数据）的网络缓冲区的指针
返回值
0帧已成功发送或已调度。若驱动支持 ACK 卸载且帧请求了确认（AR 位置位），则表示该报文已被对端成功确认。
-EINVAL无效报文（例如缺少预期的 IE，或加密/认证状态与预期不符）。
-EBUSY由于介质忙，无法发送该帧（仅限 CSMA/CA 或 CCA 卸载特性）。
-ENOMSG该帧未被 ACK 报文确认（仅限 TX ACK 卸载特性），或收到的 ACK 报文无效。
-ENOBUFS由于缺少内部资源，无法调度该帧（仅限定时 TX 卸载特性）。
