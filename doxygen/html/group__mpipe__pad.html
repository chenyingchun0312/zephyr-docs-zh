详细描述

两个元素相接的点。

pad 是元素的输入或输出连接器。它有方向——source pad（MPIPE_PAD_SRC）发出数据，sink pad（MPIPE_PAD_SINK）接收数据——mpipe_pad_link 将各一个连接起来。该链接通过双方的 peer 指针记录在两侧，这对指针是每个缓冲区、事件和查询经过的路径。

pad 还按值持有一个 mpipe_structure，即它最终确定的能力。在协商运行之前，它不作任何约束，并且 mpipe_pad_set_caps with NULL puts it back that way, which is what the PAUSED to READY transition does.

Buffers, events and queries

有三种流量跨越链接，每种都有自己的钩子：

  • 一个 缓冲区 到达 sink pad 的 process_fn。处理函数拥有传给它的缓冲区，即使失败也必须释放它；无论如何，调用方都不会再碰它。
  • 一个 事件 通告某事，并使用以下函数发送 mpipe_pad_send_event - a format to apply, or the end of the stream. The default handler forwards it across the element to the peers on the other side.
  • 一个 查询 询问某事，并使用 mpipe_pad_query 发送。答案写入询问方拥有的存储，因此查询不分配任何内存。

事件和查询都由 派发 承载；决定派发是询问还是通告的是传给它的函数，而不是派发本身的任何内容。

Enumerating capabilities

支持多种格式的元素不会把它们描述为持有列表的单个能力——没有列表类型，因为没有分配。它会针对每个索引调用一次 enum_caps_fn，一次产生一个能力，协商则遍历这些索引。参见 mpipe_pad_enum_caps for the three-way return that drives the walk.

Presence

pad 记录一个存在性，描述它应在何时存在——元素构建后即 MPIPE_PAD_ALWAYS、随流出现和消失的 MPIPE_PAD_SOMETIMES、仅在请求后才有的 MPIPE_PAD_REQUEST。目前只实现了 MPIPE_PAD_ALWAYS：该字段会被存储，但没有任何逻辑依据它动作，因此请把另外两种视为保留。

向 pad 发送查询

使用 pad 的查询函数向该 pad 发送查询。

caps 查询会向其携带的存储作答，因此不携带任何存储的查询会在 pad 的查询函数被调用之前被拒绝。这正是查询函数可以不检查就直接解引用 mpipe_dispatch::caps 的原因。

参数
pad指向要发送查询的 Pad 的指针，不得为 NULL
query指向要发送的 派发 的指针，不得为 NULL。caps 查询必须携带用于作答的能力存储。
返回值
0Success.
-EINVALcaps 查询未携带用于作答的能力存储
-ENOTSUP该 pad 没有查询函数
-ENODATAcaps 查询被以空能力作答
返回
pad 的查询函数返回的任何负 errno

◆ mpipe_pad_send_event_default()

int mpipe_pad_send_event_default ( struct mpipe_pad * pad,
struct mpipe_dispatch * event )

#include <zephyr/mpipe/mpipe_pad.h>

pad 的默认事件处理函数

将 pad 上收到的事件转发到同一元素中所有对侧 pad 的对端。若 pad 是 sink pad，事件会转发到每个 source pad 的对端；若 pad 是 source pad，则转发到每个 sink pad 的对端。

若元素只有 source pad 或只有 sink pad，则没有对侧 pad 可发送事件，因此该函数返回 -ENOTSUP。

参数
pad指向收到该事件的 Pad 的指针
event指向要发送的 派发 的指针
返回值
0事件至少到达了一个对端。
-ENOTSUP没有对侧 pad 拥有对端，或所有对端都拒绝了该事件。对端自身的错误会被记录而不会传播。
