◆ can_send()

int can_send ( const struct device * dev,
const struct can_frame * frame,
k_timeout_t timeout,
can_tx_callback_t callback,
void * user_data )

#include <zephyr/drivers/can.h>

将 CAN 帧排队以便在 CAN 总线上发送

将 CAN 帧排队以便在 CAN 总线上发送，并可指定超时和完成回调函数。

排队的 CAN 帧按其优先级顺序发送：

  • CAN-ID 越小，优先级越高。
  • 在 CAN-ID 相同时，数据帧的优先级高于远程传输请求（RTR）帧。
  • 在基 ID（扩展标识符的高 11 位）相同时，使用标准（11 位）标识符的帧优先级高于使用扩展（29 位）标识符的帧。
  • 优先级相同的排队帧的发送顺序取决于硬件。
注解
若发送跨越多个 CAN 帧且 CAN-ID 相同的分段消息，在需要 FIFO 顺序时，发送方必须确保一次只排队一帧。

默认情况下，在总线仲裁丢失或缺失确认时，CAN 控制器会自动重试发送。某些 CAN 控制器支持通过 CAN_MODE_ONE_SHOT 禁用自动重传。

dev指向该驱动实例设备结构的指针。
frame要发送的 CAN 帧。
timeout等待空闲 TX 邮箱的超时时间，或 K_FOREVER。
callback可选回调，在帧已发送或发生发送错误时调用。若为 NULL，则该函数会阻塞直到帧发送完成。若从用户模式调用，该回调必须为 NULL。
user_data传递给回调函数的用户数据。
返回值
0成功时。
-EINVAL向函数传入了无效参数。
-ENOTSUP向函数传入了不支持的参数。
-ENETDOWNCAN 控制器处于停止状态。
-ENETUNREACHCAN 控制器处于总线关闭状态。
-EBUSYCAN 总线仲裁丢失（仅当禁用自动重传时适用）。
-EIO发生通用发送错误（例如禁用自动重传时缺失 ACK）。
-EAGAINon timeout.

uint32_t bitrate )

#include <zephyr/drivers/can.h>

设置 CAN 控制器的比特率

CAN in Automation（CiA）301 v4.2.0 建议所有比特率使用 87.5% 的采样点位置。然而，某些 CAN 控制器在较高比特率下难以满足该要求。

该函数默认对超过 800 kbit/s 的比特率使用 75.0% 的采样点，对超过 500 kbit/s 的比特率使用 80.0，其他所有比特率使用 87.5。这与 Linux 内核使用的采样点位置一致。

参见

参数

返回值
0成功时。

-EINVAL请求的比特率超出范围。
-ENOTSUPCAN 控制器/收发器组合不支持请求的比特率。
