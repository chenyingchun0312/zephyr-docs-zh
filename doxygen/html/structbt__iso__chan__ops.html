ISO 信道操作结构。

注解
这些回调在线程上下文中调用，绝不会在 ISR 中调用。回调是由协议栈内部上下文调用，还是由触发它的 API 调用同步调用，以及来自哪个上下文，不属于 API 的一部分，且可能随版本变化。参见 Callback execution contexts for the hazards of blocking in a callback and their mitigations.

◆ disconnected

void(*) bt_iso_chan_ops::disconnected(struct bt_iso_chan *chan, uint8_t reason)

信道已断开回调

若提供此回调，则信道断开时都会调用它，包括连接被拒绝或设置安全失败时。

若信道已建立（即已对该信道调用 bt_iso_chan_ops.connected），则信道对象仍然有效，不得将信道内存清零或释放。为避免出现问题，建议使用 k_work_submit 或类似机制，以免在回调中覆盖任何数据。

由于上述原因，仍可以对 chan 使用 bt_iso_chan_get_info()。

若 chan 是单播（CIS）信道，则当关联的 ACL 连接也断开时，此回调总会在 bt_conn_cb::disconnected 之前被调用。

参数
chan已断开的信道
reason断开原因，取值见 BT_HCI_ERR_*。

◆ send_failed

void(*) bt_iso_chan_ops::send_failed(struct bt_iso_chan *chan, int err)

信道发送失败回调

若对 bt_iso_chan_send() 的调用成功，但 chan disconnected before the controller marked the SDU as completed. None, part or all of the SDU may have been given to the controller by then.

参数
chan发送操作失败的信道。
err发送失败的原因。

◆ sent

void(*) bt_iso_chan_ops::sent(struct bt_iso_chan *chan)

信道发送回调

当控制器将该 SDU 标记为完成时调用此回调。控制器何时执行此操作取决于具体实现，可能在 SDU 排队待发送之后，也可能在其发送到空口上或被刷新之后。

参数
chan已发送数据的信道。
