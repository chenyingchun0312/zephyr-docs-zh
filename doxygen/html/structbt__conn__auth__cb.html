◆ app_passkey

uint32_t(*) bt_conn_auth_cb::app_passkey(struct bt_conn *conn)

允许应用程序为配对提供通行码。

若实现此回调，应用程序可为配对提供通行码。通行码的有效范围为 0 - 999999。应用程序应返回用于配对的通行码，或返回 BT_PASSKEY_RAND 以生成随机通行码。此回调仅对核心规范第 3 卷第 H 部分定义的通行码输入方法调用。配对中由哪台设备显示通行码取决于设备的 IO 能力；详见 Bluetooth 核心规范 6.0 版第 3 卷第 H 部分表 2.8。就该表而言，当此回调为非 NULL 时，设备获得“显示”能力。这与回调返回的是指定密钥还是 BT_PASSKEY_RAND 无关。

注解
使用此回调时，由应用程序负责使用随机且唯一的密钥。
参数
conn当前正在进行配对的连接。
返回
用于配对的通行码，或由主机生成随机通行码的 BT_PASSKEY_RAND。

◆ cancel

void(*) bt_conn_auth_cb::cancel(struct bt_conn *conn)

取消正在进行的用户请求。

将调用此回调通知应用程序取消任何先前的用户请求（通行码显示、输入或确认）。

此回调可设为 NULL，但只要提供了 passkey_display、passkey_entry、passkey_confirm 或 pairing_confirm 回调，就必须始终提供它。

参数
conn当前正在进行配对的连接。

void(*) bt_conn_auth_cb::oob_data_request(struct bt_conn *conn, struct bt_conn_oob_info *info)

请求用户提供带外（OOB）数据。

调用时用户应提供 OOB 数据。所需数据由信息结构体指明。

对于 LE Secure Connections OOB 配对，用户应根据可用情况提供本地 OOB 数据、远端 OOB 数据或两者。其值应使用 bt_le_oob_set_sc_data() API 提交给协议栈。

为支持 OOB 配对，此回调必须设为非 NULL。

参数
conn当前正在进行配对的连接。
infoOOB 配对信息。

◆ pairing_accept

enum bt_security_err(*) bt_conn_auth_cb::pairing_accept(struct bt_conn *conn, const struct bt_conn_pairing_feat *const feat)

询问是否继续处理传入的配对。

收到任何配对的请求/响应时都会调用此回调，由应用程序决定是否允许继续配对。

从对端收到的配对信息会传入以辅助决策。

由于此回调是同步的，应用程序应立即返回响应值，否则可能影响配对时序。因此，不应将这一信息传达给用户以采取行动。

其余回调不受此影响，但请注意其他回调可能在配对期间被调用。例如，若注册了 pairing_confirm，则对 Just-Works 配对两者都会被调用。

此回调可以不注册，此时配对将继续进行，如同未设置该 Kconfig 标志一样。

对于 BR/EDR 安全简单配对（SSP），收到 BT_HCI_EVT_IO_CAPA_REQ HCI 事件时会调用此回调。此处 feat 为 NULL。

参数
conn发起配对的连接。
feat配对请求/响应信息。在 BR/EDR SSP 中为 NULL。

◆ pairing_confirm

void(*) bt_conn_auth_cb::pairing_confirm(struct bt_conn *conn)

请求确认传入的配对。

当传入的配对请求不适用其他任何用户回调时，将调用此回调以进行确认。

若用户决定接受配对，应调用 bt_conn_auth_pairing_confirm() API。若用户决定拒绝配对，应调用 bt_conn_auth_cancel() API。

此回调可设为 NULL，表示本地设备不具备确认配对请求的能力。若设为非 NULL，则还必须提供取消回调，因为这是应用程序得知应停止请求用户确认配对请求的唯一途径。

参数
conn当前正在进行配对的连接。

◆ passkey_confirm

void(*) bt_conn_auth_cb::passkey_confirm(struct bt_conn *conn, unsigned int passkey)

请求用户确认通行码。

调用时用户应确认对端设备上显示的通行码与此相同。通行码范围为 0 - 999999，应零填充至始终为六位数字（例如 37 会显示为 000037）。

用户确认通行码一致后，应调用 bt_conn_auth_passkey_confirm() API。若用户认为通行码不一致，则应调用 bt_conn_auth_cancel() API。

此回调可设为 NULL，表示本地设备不具备确认通行码的能力。若设为非 NULL，则还必须提供取消回调，因为这是应用程序得知应停止请求用户确认通行码的唯一途径。

参数
conn当前正在进行配对的连接。
passkey待确认的通行码。

◆ passkey_display

void(*) bt_conn_auth_cb::passkey_display(struct bt_conn *conn, unsigned int passkey)

向用户显示通行码。

调用时应用程序应向用户显示给定的通行码，预期用户随后会在对端设备上输入该通行码。通行码范围为 0 - 999999，应以零填充，始终显示六位数字。例如值 37 应显示为 000037。

此回调可设为 NULL，表示本地设备不具备显示通行码的能力。若设为非 NULL，则还必须提供取消回调，因为这是应用程序得知应停止显示通行码的唯一途径。

参数
conn当前正在进行配对的连接。
passkey要向用户显示的通行码。

◆ passkey_display_keypress

void(*) bt_conn_auth_cb::passkey_display_keypress(struct bt_conn *conn, enum bt_conn_auth_keypress type)

在配对过程中接收通行码按键通知

这允许远端设备借助本地设备向用户反馈其在远端输入通行码的进度。当远端设备本身没有适合显示进度的显示屏时，这很有用。

此回调的处理程序应跟踪已输入的位数，并向用户显示类似密码输入框的反馈。

此回调仅在本地侧进行通行码显示时才相关。

会验证事件类型在该枚举范围内，未做其他净化处理。远端可能以任意顺序发送任意类型的大量事件。

参数
conn相关的连接。
type事件类型。已验证在该枚举范围内。

◆ passkey_entry

void(*) bt_conn_auth_cb::passkey_entry(struct bt_conn *conn)

请求用户输入通行码。

调用时用户应输入通行码。通行码范围必须为 0 - 999999，并应视为已零填充，因为对端设备通常就是这样显示的（例如 37 会显示为 000037）。

用户输入通行码后，应使用 bt_conn_auth_passkey_entry() API 将其值提交给协议栈。

此回调可设为 NULL，表示本地设备不具备输入通行码的能力。若设为非 NULL，则还必须提供取消回调，因为这是应用程序得知应停止请求用户输入通行码的唯一途径。

参数
conn当前正在进行配对的连接。

◆ pincode_entry

void(*) bt_conn_auth_cb::pincode_entry(struct bt_conn *conn, bool highsec)

请求用户输入通行码。

对于正在进行配对的 BR/EDR（Bluetooth Classic）连接，将调用此回调。调用后用户应输入长度为 1 到 16 位的 PIN 码。若 highsec 参数为 true，则 PIN 码必须为 16 位。

输入后，应使用 bt_conn_auth_pincode_entry() API 将 PIN 码提交给协议栈。

此回调可设为 NULL，但那样将无法通过 BR/EDR 进行配对。若提供此回调，则还必须提供取消回调。

参数
conn当前正在进行配对的连接。
highsec若需要 16 位 PIN 则为 true。
