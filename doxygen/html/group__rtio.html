rtio_iodev_sqe 状态字的位

状态字独立于不可变的 rtio_sqe 携带条目的身份和生命周期。每次条目归还到池时都会递增代数，因此针对此前占用者捕获的任何句柄都不再匹配。

#include <zephyr/rtio/sqe.h>

永不指向仍在进行的提交的句柄值

用 rtio_iodev_sqe_from_handle() 解析此值始终得到 NULL，因此可以安全地用作“无提交”的哨兵值，也可以传给 rtio_sqe_cancel()（在那里它是已满足的空操作）。其块索引对任何池都是越界的。

◆ rtio_sqe_cancel()

int rtio_sqe_cancel ( struct rtio * r,
rtio_sqe_handle_t handle )

#include <zephyr/rtio/rtio.h>

尝试取消某个 SQE

如果可能（当前未在执行），则取消某个 SQE 并产生结果为 -ECANCELED 的失败。

该提交由此前从 r 捕获的不透明 rtio_sqe_handle_t 标识（例如通过 rtio_sqe_copy_in_get_handles()）。如果该提交已经完成且其池槽位已被回收，则句柄不再能解析，取消操作成为已满足的空操作：未完成的请求已经不存在了。身份检查（边界 + 已分配 + 代数）和取消标记作为一次原子比较并设置（compare-and-set）作用于条目的状态字，因此若提交并发完成（释放时递增了代数）则句柄会失配并空操作，要么在条目仍可证明属于调用方时命中；过期或垃圾句柄无法标记该槽位中无关的占用者。

只标记 handle 所指定的那一个提交。取消是尽力而为的，要取消一个链或事务，调用方需保留 rtio_sqe_copy_in_get_handles() 产生的每个句柄并逐一取消；链中其余部分无法从单个句柄抵达。在某个成员被分派之前标记它确实能阻止其执行，因为执行器在将其交给 iodev 的途中会检查每个成员的状态；但如果某个成员的前驱在其被标记之前或标记期间完成，它可能已经在运行，并将运行到完成。

参数
[in]r产生 handle 的 RTIO 上下文
[in]handle要取消的 SQE 的句柄
返回
如果该 SQE 已被标记为取消（或已完成）则为 0
<0 出错

详情参见 rtio_sqe_prep_await。参见 rtio_sqe_prep_await_executor 以了解不阻塞任何 rtio_iodev 的对应版本。

准备一个不产生 CQE 的回调操作提交

与 rtio_sqe_prep_callback 类似，但在 SQE 上设置了 RTIO_SQE_NO_RESPONSE 标志，以阻止完成时产生 CQE。

当回调是某个序列中的最后一个操作、其职责是清理之前所有 CQE 时，这很有用。如果没有 RTIO_SQE_NO_RESPONSE，完成本身会产生一个无法在回调中消费的 CQE。
