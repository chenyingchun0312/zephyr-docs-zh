详细描述

元素向应用程序报告的内容。

消息的传递方向与派发相反。派发跨越两个元素之间的 pad 链接；消息则完全离开图，沿 bin 的通道向上到达驱动管道的一方，用以说明流已结束或发生了故障。

它是一个小型值类型，被复制进出通道，因此发布它并不转移所有权。它携带故障发生的位置——发出它的元素——以及发生了什么，由一个类型表示，并在失败时附带说明哪个阶段出错的域和说明原因的错误码。这两者合起来旨在回答管道不运行时最关键的两个问题：哪个元素，以及处于哪个阶段。

消息刻意设计为机器可读。它不携带面向人的字符串；描述故障的句子应留在发现它的位置写入日志，而应用程序则对域和错误码做分支判断。

消息在包含其来源的 bin 的总线上发布，该总线通道可用 mpipe_element_get_bus_chan 获得。任何 zbus 观察者都可以监视它：监听者在发布线程中内联运行，既不得阻塞也不得改变管道状态；消息订阅者（ CONFIG_ZBUS_MSG_SUBSCRIBER）在自己的线程中用 zbus_sub_wait_msg() 读取，不会丢失任何消息。请在 bin 消失之前分离观察者。

消息类型是单个位，因此消费者可以通过将它们按位或成一个掩码来选择多种类型。MPIPE_MESSAGE_UNKNOWN 为零，不匹配任何类型：它是未初始化的消息，而不是可选择的类型。

◆ mpipe_error_domain

enum mpipe_error_domain

#include <zephyr/mpipe/mpipe_message.h>

故障发生的域：元素当时正在做什么。

管道会在少量彼此不同的位置失败，知道是哪一个往往就意味着知道原因。此枚举为这些位置命名，使报告能说明元素当时在做什么，而不仅是有东西出错了。

结合 mpipe_message::code 中的 errno，这一对就是应用程序据以分支判断的依据：

if (msg.domain == MPIPE_ERROR_RESOURCE && msg.code == -ENOENT) {
// the input file does not exist
}

◆ mpipe_message_post()

int mpipe_message_post ( const struct mpipe_message * message)

#include <zephyr/mpipe/mpipe_message.h>

将消息发布到包含其来源的 bin 的总线。

通过 mpipe_element_get_bus_chan 从消息的来源定位总线，并在那里发布。总线按值复制消息，因此栈上存储即可。这是唯一的发布方式：消息来自某个元素，而正是来源决定了消息属于哪条总线。

调用方声明并初始化消息。指定初始化器中省略的字段为零，而零是每个字段的中性值：MPIPE_ERROR_FAILED 域，无错误码。

当故障对流是致命的时候发布错误，这才是应用程序需要获知的。调用方可以通过返回 errno 报告的故障仍然只是 errno；错误消息并不适用于每一次失败的调用。

在 ISR 之外，该调用会等待总线，因此不得从同一总线的监听者中发起。

struct mpipe_message msg = {
.origin = &sink->element,
.type = MPIPE_MESSAGE_EOS,
};
(void)mpipe_message_post(&msg);
