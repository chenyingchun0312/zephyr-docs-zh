Bluetooth HCI lockstep 命令辅助函数

自从
4.5
版本
0.1.0

用于一次发送一条 HCI 命令并等待其响应的辅助函数，面向通过自有传输与控制器交换 HCI 命令的 HCI 驱动（通常用于厂商特定的控制器初始化），无需 Bluetooth Host 的命令机制，且无论构建中是否存在 Host。

该辅助函数依赖 HCI 流量保持同步：当某条命令尚未完成时不会发送其他命令，因此收到的下一个命令响应就是该命令的响应。这一点在控制器初始化期间、HCI 传输移交给其用户之前成立，从而无需操作码关联状态机。命令流控仍然有效：只有当控制器允许时才发送命令，控制器最初允许，并通过每个命令响应的 Num_HCI_Command_Packets 字段允许，包括控制器为自行允许命令而发送的、带 NOP 操作码的 HCI_Command_Complete 事件。

驱动提供其传输的发送函数，并把从控制器收到的数据包送入 bt_hci_lockstep_feed()，该函数消费所等待的响应，并把其他每个数据包留给驱动处理。命令通过 hci_pkt.h 中的辅助函数构造，本头文件会包含该文件。

该辅助函数只初始化一次，并在传输的一次次打开之间保留其对控制器命令许可的认知。若驱动用 HCI 命令之外的方式复位控制器，例如在打开时通过复位线复位，则应在该复位之后、发送第一条命令之前调用 bt_hci_lockstep_reset()。

只要使能了 CONFIG_BT，该辅助函数就包含在构建中。

注解
这不是应用程序 API：预期的使用者是 HCI 驱动。需要在 Host 运行时同时发送 HCI 命令的应用程序应使用 hci.h 中更高层的 bt_hci_cmd_alloc()、bt_hci_cmd_send() 和 bt_hci_cmd_send_sync() API，它们与 Host 的命令流控协同工作。

uint16_t opcode,
struct net_buf_simple * cmd,
struct net_buf_simple * rsp )

#include <zephyr/drivers/bluetooth/hci_lockstep.h>

发送一条 HCI 命令并等待其响应。

用 bt_hci_pkt_push_cmd_hdr() 把 cmd 中的命令参数封装成完整的 HCI 命令包，等待控制器允许一条命令，用传输发送函数发送该包，并等待控制器的 HCI_Command_Complete 或 HCI_Command_Status 响应通过 bt_hci_lockstep_feed() 到达。该调用最多等待 bt_hci_lockstep::timeout in total, for the controller to allow a command and then to respond to it.

响应存储在 rsp 中，该缓冲区会先被清空：先是状态，随后是 HCI_Command_Complete 的返回参数，也就是 hci_types.h 中 bt_hci_rp_* 结构的布局。超出 rsp 容量的字节会被丢弃，因此请按预期的返回参数确定其大小。HCI_Command_Status 响应不携带返回参数，因此 rsp 只保存其状态，这仅表示控制器已接受该命令，完成情况稍后通过该命令自己的事件上报。

必须从线程上下文调用，且一次只允许一个调用：驱动会串行化其调用方。返回 -EINVAL 和 -EMSGSIZE 时 cmd 保持不变；其他任何返回值下它都保存着完整的命令包，因此在重用之前要用 bt_hci_pkt_reset_cmd()。每次失败都会连同操作码一起记录日志，因此调用方无需再次记录。响应已经到达后才上报的传输发送失败只记录日志：命令已到达控制器，其响应仍然有效。

-EAGAIN 表示控制器无响应，应据此处理而不是重试：要么它在超时内没有允许任何命令，要么它没有响应该命令，之后它不允许再发送命令，而迟到的响应无法与后续同操作码命令的响应区分开。

参数
lslockstep 辅助函数。
opcodeHCI 命令操作码。
cmd保存命令参数的缓冲区，用 BT_HCI_PKT_CMD_DEFINE() 或 bt_hci_pkt_reset_cmd() 设置；对于无参数的命令则为 NULL。
rsp用于返回参数的缓冲区，为 NULL 时丢弃它们。
返回值
0命令成功完成。
-EIO控制器返回了错误状态，该状态被记录并存入 rsp。
-EAGAIN控制器在 bt_hci_lockstep::timeout 内没有允许任何命令，或没有响应。
-EINVALcmd 的头部空间不足以容纳包前缀。
-EMSGSIZEcmd 中的参数字节数超过一条 HCI 命令所能携带的数量。
返回
传输发送失败时返回的负 errno 值，即发送函数的返回值；命令未被提交。

bool bt_hci_lockstep_feed ( struct bt_hci_lockstep * ls,
const uint8_t * pkt,
size_t len )
isr-ok

#include <zephyr/drivers/bluetooth/hci_lockstep.h>

把收到的 HCI 数据包送入 lockstep 辅助函数。

在使用该辅助函数期间，驱动应对从控制器收到的每个数据包调用它。当该数据包是 bt_hci_lockstep_cmd_send_sync() 所等待命令的响应时，辅助函数会消费它并唤醒等待者；其他数据包则留给驱动照常处理。该数据包不会被修改。

送入的每个命令响应，无论是否被消费，都会更新控制器允许的命令数，而这正是 bt_hci_lockstep_cmd_send_sync() 所等待的；带 NOP 操作码的 HCI_Command_Complete 事件仅为此而存在。

可从任何上下文调用，包括 ISR。调用由驱动的单一接收路径串行化，并按数据包收到的顺序进行。

参数
lslockstep 辅助函数。
pkt收到的数据包，以其包指示符开头。
lenpkt 的长度，单位为字节。
返回值
true该数据包是所等待的响应，已被消费。
false该数据包不是所等待的响应。

◆ bt_hci_lockstep_reset()

void bt_hci_lockstep_reset ( struct bt_hci_lockstep * ls)
isr-ok

#include <zephyr/drivers/bluetooth/hci_lockstep.h>

恢复 lockstep 辅助函数的初始状态。

恢复初始的一条命令许可，用于通过 HCI 命令之外的方式复位的控制器，使该辅助函数不再等待复位后的控制器不会通告的许可。传输发送函数和 bt_hci_lockstep::timeout 保持原样。

可从任何上下文调用，包括 ISR，且可以与 bt_hci_lockstep_feed() 同时调用，因此由无法停止的回调送入数据包的驱动也可以使用它。正在等待控制器允许其命令的 bt_hci_lockstep_cmd_send_sync() 调用会继续并发送该命令，正如恢复路径复位一个已停止响应的控制器时那样。

尚未完成的命令（发送方已获得许可但尚未收到响应）是另一回事：无法知道它是在复位之前还是之后到达控制器的，因此预期驱动此时不会复位其控制器。如果确实复位了，该命令会被放弃。它的响应不再被消费，其发送方会失败：若命令未能提交则返回传输的错误，否则在超时耗尽后返回 -EAGAIN（不会更早），这样仍然到达的响应就不会被误认为后续同操作码命令的响应。

控制器在复位之前发送的数据包不应在之后送入：该辅助函数无法把它们与后续操作的响应区分开，因此针对同一操作码的过期响应会被当作新响应，而过期的、不允许任何命令的命令响应会撤销已恢复的许可。

参数
lslockstep 辅助函数。
