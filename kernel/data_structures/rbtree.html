平衡红黑树

当有序容器在运行时可能变得很大时，由于搜索链表的算法开销，链表就不再适用。针对这类情况，Zephyr 提供了一种平衡树实现，对于大小为 N 的树，其搜索和删除操作的运行时间上限为 O(log2(N))。它采用了多种学术资料中描述的传统红黑树实现。

rbtree 的 rbtree 跟踪结构体可以在用户可访问内存中的任意位置初始化。首次使用前，它应全部为零。不需要也不要求调用特定的初始化 API。

与位置显式确定的链表不同，rbtree 中节点的顺序必须由用户以谓词函数的形式提供。在尝试任何树操作之前，应将一个 rb_lessthan_t() 类型的函数赋给 rbtree 结构体的 lessthan_fn 字段。顾名思义，当按照树所需的顺序第一个节点参数“小于”第二个节点参数时，该函数应返回布尔值 True。注意，不允许出现“相等”的情况，树中的节点必须具有唯一确定的顺序，算法才能正确工作。

与 slist 和 dlist 容器一样，rbtree 中的节点表示为一个 rbnode 结构体，它位于用户管理的内存中，通常嵌入在树所跟踪的数据结构内。与链表代码不同，rbnode 中的数据是完全不透明的。用户无法像操作链表那样提取二叉树的拓扑结构并“手动”遍历树。

可以使用 rb_insert() 将节点插入树中，并使用 rb_remove() 将其删除。rb_get_min() 和 rb_get_max() 用于访问树中的“第一个”和“最后一个”节点（按比较函数定义的顺序而言）。还有一个谓词 rb_contains()，如果给定的节点指针是树中的元素，则返回布尔值 True。如上所述，这些例程都保证时间复杂度不超过树大小的对数级。

rbtree 提供了两种枚举所有元素的机制。第一种是 rb_walk()，这是一种简单的回调实现：调用者指定一个 C 函数指针和一个要传给它的无类型参数，树代码会按顺序为每个节点调用该函数。它的优点是实现非常简单，代价是用户使用的 API 稍显繁琐（与 ISO C 的 bsearch() 例程类似）。不过它是递归实现的，因此在禁止使用递归这类无界栈技术的环境中并不总是可用。

另外还提供了 RB_FOR_EACH 迭代器。与链表的类似 API 一样，它使用嵌套代码块而不是回调，以更自然的方式进行遍历。它也是非递归的，不过默认情况下需要在栈上占用对数级大小的空间（但在需要时，可以将其配置为改用固定/最大大小的缓冲区，以避免动态分配）。与链表一样，它也有一个 RB_FOR_EACH_CONTAINER 变体，使用指向外层结构体字段的指针而不是原始节点指针进行枚举。

树的内部实现

如前所述，Zephyr 的 rbtree 实现是学术资料中广泛描述的传统红黑树。算法的底层细节与现有惯例一致，不在本文档讨论范围之内。这里的讨论仅限于 Zephyr 实现中值得注意或特有的细节。

该树保证的核心不变式是：从树根到任意叶子的路径长度，不超过到其他任意叶子路径长度的两倍。实现方法是为每个节点关联一位“颜色”（红色或黑色），并强制执行一条规则：红色子节点不能是另一个红色子节点的子节点（即到根的任意路径上黑色节点的数量必须相同，且“额外”的红色节点数量不能超过该数量）。这条规则通过一组旋转规则来保证，这些规则用于在修改后“修复”树。

从概念上讲，这些旋转是在一个将某个节点与另一个节点“交换”位置的原语之上实现的。典型的实现只需交换节点内部的 “data” 指针即可实现这一点，但由于 Zephyr 的 rbnode 是侵入式的，这种方法行不通。Zephyr 必须包含更复杂一些的代码来处理边界情况（例如，被交换的某个节点可能是根节点，或者两个节点可能已经是父子关系）。

Zephyr rbtree 的 rbnode 结构体只包含两个指针，分别表示二叉树中节点的 “left” 和 “right” 子节点。然而，在修改后为重新平衡而遍历树时，通常还需要能够从某个节点“向上”迭代。业界的红黑树实现很常见的做法是为此存储第三个 “parent” 指针。Zephyr 避免了这一需求：在向下遍历树时，它会在本地构建一个节点指针“栈”，并在修改时相应地更新。因此，Zephyr rbtree 的运行时存储开销不会超过 dlist。

这种平衡树数据结构每个节点只需两个指针的数据，并且完全不需要内存分配 API，这些特性在业界相当罕见，在某种程度上是 Zephyr 所独有的。
