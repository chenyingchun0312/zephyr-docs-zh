概述

威胁模型

Zephyr 认为用户模式线程是不可信的，因此将其与其他用户模式线程以及内核相互隔离。有缺陷或恶意的用户模式线程无法泄露或修改其他线程或内核的私有数据/资源，也无法干扰或控制其他用户模式线程或内核。

Zephyr 用户模式特性的使用场景示例：

  • 内核可以防范许多无意的编程错误，否则这些错误可能会悄无声息或以严重的方式破坏系统。

  • 内核可以把解释器、网络协议和文件系统等复杂的数据解析器放入沙箱，使恶意的第三方代码或数据无法危及内核或其他线程。

  • 内核可以支持多个逻辑“应用程序”的概念，每个应用程序拥有自己的一组线程和私有数据结构，并且彼此隔离，即使其中一个崩溃或被攻破也不会影响其他应用程序。

设计目标

对于运行在非特权 CPU 状态（下文称为“用户模式”）的线程，我们旨在防范以下情况：

  • 我们阻止访问未经明确授权的内存，也阻止以与内存策略不相符的方式访问内存，例如试图写入只读区域。

    • 对线程栈缓冲区的访问将由一项策略控制，该策略部分取决于底层的内存保护硬件。

      • 默认情况下，用户线程对其自身的栈缓冲区拥有读写权限。

      • 默认情况下，用户线程永远无权访问不属于同一内存域的用户线程栈。

      • 默认情况下，用户线程永远无权访问由管理态（supervisor）线程拥有的线程栈，也无权访问用于处理系统调用特权提升、中断或 CPU 异常的线程栈。

      • 取决于硬件，用户线程可能对同一内存域中其他用户线程的栈拥有读写权限。

        • 在 MPU 系统上，线程只能访问其自身的栈缓冲区。

        • 在 MMU 系统上，线程可以访问同一内存域中的任何用户线程栈。可移植的代码不应依赖这一点。

    • 默认情况下，程序代码段和只读数据在整个内核范围内对所有线程以只读方式开放。该策略可以调整。

    • 默认情况下，除上述内容外，用户线程不会被授予对任何内存的访问权限。

  • 我们阻止使用未经明确授权的设备驱动或内核对象，授权粒度为单个对象或单个驱动实例。

  • 我们会校验带有错误参数的内核或驱动 API 调用，否则这些调用可能导致崩溃或破坏内核私有的数据结构。这包括：

    • 使用了错误的内核对象类型。

    • 使用了超出合理范围或没有意义的参数值。

    • 根据 API 的语义，传入了调用线程没有足够读或写权限的内存缓冲区。

    • 使用了未处于正确初始化状态的内核对象。

  • 我们确保能够检测并安全处理用户模式下的栈溢出。

  • 我们阻止通过系统调用调用内核配置中未包含的函数。

  • 我们阻止禁用或篡改由内核定义、由硬件强制执行的内存保护。

  • 我们阻止从用户模式重新进入管理态模式，除非通过内核定义的系统调用和中断处理函数。

  • 我们阻止用户模式线程引入新的可执行代码，内核系统调用所支持的范围除外。

我们明确不防范以下攻击：

  • 内核本身以及所有在管理态模式下执行的线程都被假定为可信的。

  • 工具链以及构建系统使用的所有辅助程序都被假定为可信的。

  • 内核构建被假定为可信的。构建时有大量逻辑用于创建有效内核对象表、定义系统调用以及配置中断。此过程中处理的 .elf 二进制文件都被假定为可信代码。

  • 对于在内核模式下进行的内存域配置中的错误，如果它把内核私有数据结构暴露给用户线程，我们无法防范。内核对象所在的 RAM 应始终配置为仅管理态可访问。

  • 可以在顶层声明用户模式线程，并为其分配对内核对象的权限。一般来说，参与内核构建并生成 zephyr.elf 的所有 C 文件和头文件都被假定为可信的。

  • 我们不防范通过让线程得不到 CPU 时间而造成的拒绝服务攻击。Zephyr 没有线程优先级老化机制，某个优先级的用户线程可以使所有更低优先级的线程饿死；如果未启用时间片轮转，同优先级的其他线程也会被饿死。

  • 可同时活动的线程数量有构建时定义的上限，超过上限后创建新的用户线程将会失败。

  • 运行在管理态模式下的线程发生栈溢出时可能会被捕获，但无法保证系统的完整性。

高层策略细节

总体而言，我们通过以下机制实现这些线程级内存保护目标：

  • 任何用户线程只能访问内存的一个子集：通常是其栈、程序代码段、只读数据，以及它所属的 内存域 中配置的所有分区。对其他任何 RAM 的访问都必须通过系统调用代表该线程完成，或者由管理态线程使用内存域 API 明确授权。新创建的线程会继承父线程的内存域配置。线程之间可以通过共同属于同一内存域进行通信，也可以通过信号量和管道等内核对象通信。

  • 用户线程不能直接访问属于内核对象的内存。虽然通过指向内核对象的指针来引用它们，但对内核对象的实际操作是通过系统调用接口完成的。设备驱动和线程栈也被视为内核对象。这确保了内核对象中对内核私有的任何数据都无法被篡改。

  • 默认情况下，用户线程除了自己的线程对象外，无权访问任何内核对象或驱动。这种访问权限必须由另一个线程授予，该线程要么处于管理态模式，要么同时拥有接收方线程对象和被授权内核对象的权限。创建新线程时可以选择自动继承父线程被授予的所有内核对象的权限，但父线程本身除外。

  • 出于性能和占用空间的考虑，Zephyr 通常对内核对象或设备驱动 API 很少甚至不做参数错误检查。从用户模式通过系统调用进行的访问会多经过一层处理函数，这些函数应严格校验访问权限和对象类型，通过边界检查或其他手段检查其他参数的有效性，并验证对所涉及的任何内存缓冲区具有正确的读写权限。

  • 线程栈的定义方式保证超出指定的栈空间时会产生硬件故障。具体实现方式因架构而异。

限制

所有内核对象、线程栈和设备驱动实例，如果要在用户模式下使用，都必须在构建时定义。需要动态使用内核对象的场景，必须通过预先定义的可用对象池来实现。

如果在内核启动后加载额外的应用程序二进制数据来执行，会有一些限制：

  • 加载的目标代码无法定义能被内核识别的内核对象。这类代码需要改用从对象池请求内核对象的 API。

  • 同样，由于加载的目标代码不属于内核构建过程，无论其运行在何种模式下，这类代码都无法安装中断处理函数、实例化设备驱动或定义系统调用。

  • 并非来自可信来源的加载目标代码，在进入执行时 CPU 应始终已处于用户模式。
