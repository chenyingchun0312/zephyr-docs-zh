工作队列线程

工作队列（workqueue）是一种内核对象，它使用一个专用线程以先进先出的方式处理工作项。每个工作项通过调用该工作项指定的函数来处理。工作队列通常由 ISR 或高优先级线程使用，将非紧急的处理工作转交给较低优先级的线程，从而不影响时间敏感的处理。

可以定义任意数量的工作队列（仅受可用 RAM 限制）。每个工作队列通过其内存地址引用。

工作队列具有以下关键属性：

  • 一个 队列，存放已添加但尚未处理的工作项。

  • 一个 线程，负责处理队列中的工作项。该线程的优先级可配置，可根据需要设为协作式或抢占式。

无论工作队列线程的优先级如何，它在处理每个已提交的工作项之间都会让出（yield）CPU，以防止协作式工作队列使其他线程得不到运行。

工作队列必须先初始化才能使用。初始化会将其队列置为空，并创建工作队列的线程。该线程永久运行，但在没有可处理的工作项时会休眠。

工作项生命周期

可以定义任意数量的 工作项。每个工作项通过其内存地址引用。

每个工作项都被指定一个 处理函数，即工作队列线程处理该工作项时执行的函数。该函数接受一个参数，即工作项本身的地址。工作项还会维护有关其状态的信息。

工作项必须先初始化才能使用。初始化会记录工作项的处理函数，并将其标记为未挂起。

ISR 或线程可以将工作项提交到工作队列，使其处于 已排队 状态（K_WORK_QUEUED）。提交工作项会将它追加到工作队列的队列中。工作队列线程处理完队列中排在前面的所有工作项后，会从队列中取出下一个工作项并调用其处理函数。根据工作队列线程的调度优先级以及队列中其他工作项所需的工作量，已排队的工作项可能很快得到处理，也可能在队列中停留较长时间。

可延迟工作项可以被 调度 到工作队列（K_WORK_DELAYED），参见 Delayable Work。

工作项在工作队列上运行时处于 运行中 状态（K_WORK_RUNNING）；如果它在某个线程请求取消之前已开始运行，还可能处于 正在取消 状态（K_WORK_CANCELING）。

一个工作项可以同时处于多种状态，例如它可以：

  • 正在某个队列上运行；

  • 被标记为正在取消（因为某个线程使用了 k_work_cancel_sync() 等待该工作项完成）；

  • 已排队，等待在同一队列上再次运行；

  • 已调度，等待提交到某个（可能不同的）队列

以上状态同时存在。处于以上任一状态的工作项都属于 挂起（k_work_is_pending()）或 忙碌（k_work_busy_get()）状态。

处理函数可以使用线程可用的任何内核 API。但是，可能阻塞的操作（例如获取信号量）必须谨慎使用，因为在处理函数执行完毕之前，工作队列无法处理其队列中的后续工作项。

如果不需要，可以忽略传给处理函数的那个参数。如果处理函数需要关于所执行工作的额外信息，可以将工作项嵌入到一个更大的数据结构中。处理函数随后可以利用该参数值，通过 CONTAINER_OF 计算外层数据结构的地址，从而获取所需的额外信息。

工作项通常只初始化一次，之后每当需要执行工作时就提交到特定的工作队列。如果 ISR 或线程试图提交一个已排队的工作项，该工作项不受影响：它保持在工作队列中的当前位置，工作只执行一次。

处理函数可以将作为参数传入的工作项重新提交到工作队列，因为此时该工作项已不在队列中。这样处理函数就可以分阶段执行工作，而不会过度延迟工作队列中其他工作项的处理。

重要

在工作队列线程处理完挂起的工作项之前，不得 修改该工作项。这意味着工作项处于忙碌状态时不得重新初始化。此外，在处理函数执行完毕之前，不得修改其执行工作所需的任何额外信息。

可延迟工作

ISR 或线程可能需要调度一个工作项，使其在指定时间段之后而不是立即得到处理。这可以通过 调度 一个 可延迟工作项，让它在将来某个时间提交到工作队列来实现。

可延迟工作项包含一个标准工作项，并增加了记录该工作项应在何时、提交到何处的字段。

可延迟工作项的初始化及调度到工作队列的方式与标准工作项类似，只是使用不同的内核 API。发出调度请求时，内核会启动一个超时机制，在指定延迟结束后触发。超时发生后，内核将工作项提交到指定的工作队列，工作项在其中保持排队状态，直到以标准方式得到处理。

注意，可延迟工作所用的工作处理函数接收到的仍是指向底层不可延迟工作结构的指针，而该结构无法从 k_work_delayable 公开访问。要访问包含该可延迟工作对象的对象，请使用以下惯用写法：

static void work_handler(struct k_work *work)
{
        struct k_work_delayable *dwork = k_work_delayable_from_work(work);
        struct work_context *ctx = CONTAINER_OF(dwork, struct work_context,
                                                timed_work);
        ...

触发式工作

k_work_poll_submit() 接口会调度一个响应 轮询事件（参见 轮询 API）的触发式工作项，当被监视的资源变为可用、轮询信号被触发或发生超时时，它会调用用户定义的函数。与 k_poll() 不同，触发式工作不需要专门的线程来等待或主动轮询轮询事件。

触发式工作项是一个标准工作项，额外具有以下属性：

  • 一个指针，指向会触发向工作队列提交工作项的轮询事件数组

  • 包含轮询事件的数组的大小。

触发式工作项的初始化及提交到工作队列的方式与标准工作项类似，只是使用专门的内核 API。发出提交请求后，内核开始观察轮询事件所指定的内核对象。一旦至少有一个被观察的内核对象改变状态，工作项就会被提交到指定的工作队列，并在其中保持排队状态，直到以标准方式得到处理。

重要

在触发式工作项的整个生命周期内（从提交到工作项执行或被取消），触发式工作项及其引用的轮询事件数组都必须保持有效，且不能修改。

只要触发式工作项仍在等待轮询事件，提交它的 ISR 或线程就可以 取消 它。此时内核停止等待所关联的轮询事件，指定的工作也不会执行。否则无法取消。

系统工作队列

内核定义了一个称为 系统工作队列 的工作队列，任何需要工作队列支持的应用程序或内核代码都可以使用它。系统工作队列是可选的，只有在应用程序使用它时才存在。

重要

只有在无法向系统工作队列提交新工作项时，才应定义额外的工作队列，因为每个新工作队列都会带来很大的内存开销。如果新工作项无法与现有系统工作队列的工作项共存而不产生不可接受的影响，就有理由使用新的工作队列；例如，新工作项会执行阻塞操作，使系统工作队列的其他处理延迟到不可接受的程度。

另请注意：系统工作队列默认使用最低的协作式优先级。这意味着处理完系统工作队列中的工作优先于 所有可抢占线程。将系统工作队列的优先级配置为可抢占是有风险的，因为子系统和驱动可能隐式依赖于工作项在协作式上下文中执行。因此，对于低优先级任务，使用一个优先级更低的独立工作队列可能更合适。

如何使用工作队列

定义和控制工作队列

工作队列使用 k_work_q 类型的变量定义。初始化工作队列的步骤是：定义其线程使用的栈区域，初始化 k_work_q（将其内存清零或调用 k_work_queue_init()），然后调用 k_work_queue_start()。栈区域必须使用 K_THREAD_STACK_DEFINE 定义，以确保它在内存中被正确设置。

以下代码定义并初始化一个工作队列：

#define MY_STACK_SIZE 512
#define MY_PRIORITY 5

K_THREAD_STACK_DEFINE(my_stack_area, MY_STACK_SIZE);

struct k_work_q my_work_q;

k_work_queue_init(&my_work_q);

k_work_queue_start(&my_work_q, my_stack_area,
                   K_THREAD_STACK_SIZEOF(my_stack_area), MY_PRIORITY,
                   NULL);

此外，可以通过可选的最后一个参数控制队列标识以及与线程重新调度相关的某些行为；详见 k_work_queue_start()。

可以使用以下 API 与工作队列交互：

  • k_work_queue_drain() 可用于阻塞调用者，直到工作队列中没有剩余工作项。队列排空期间，从工作队列线程重新提交的工作项会被接受，但来自其他任何线程或 ISR 的工作项都会被拒绝。可以将禁止提交更多工作的限制延续到排空操作完成之后，使阻塞的线程能在队列被“堵住”期间执行其他工作。注意，排空队列不影响可延迟工作项的调度或处理，但如果队列被堵住而截止时间到期，该工作项将提交失败且不会给出任何提示。

  • k_work_queue_unplug() 解除之前的排空操作对向该队列提交工作所施加的阻止。

提交工作项

工作项使用 k_work 类型的变量定义。它必须通过调用 k_work_init() 初始化，除非它是用 K_WORK_DEFINE 定义的，此时初始化在编译时完成。

已初始化的工作项可以通过调用 k_work_submit() 提交到系统工作队列，或通过调用 k_work_submit_to_queue() 提交到指定的工作队列。

以下代码演示 ISR 如何将错误消息的打印工作转交给系统工作队列。注意，如果 ISR 在工作项仍处于排队状态时试图重新提交它，该工作项保持不变，相应的错误消息也不会被打印。

struct device_info {
    struct k_work work;
    char name[16]
} my_device;

void my_isr(void *arg)
{
    ...
    if (error detected) {
        k_work_submit(&my_device.work);
    }
    ...
}

void print_error(struct k_work *item)
{
    struct device_info *the_device =
        CONTAINER_OF(item, struct device_info, work);
    printk("Got error on device %s\n", the_device->name);
}

/* initialize name info for a device */
strcpy(my_device.name, "FOO_dev");

/* initialize work item for printing device's error messages */
k_work_init(&my_device.work, print_error);

/* install my_isr() as interrupt handler for the device (not shown) */
...

可以使用以下 API 检查工作项的状态或与其同步：

  • k_work_busy_get() 返回表示工作项状态的标志快照。值为零表示该工作未被调度、未被提交、未在执行，也没有以其他方式仍被工作队列基础设施引用。

  • k_work_is_pending() 是一个辅助函数，当且仅当工作已被调度、已排队或正在运行时返回 true。

  • 线程可以调用 k_work_flush() 阻塞，直到工作项完成。如果工作未处于挂起状态，它会立即返回。

  • k_work_cancel() 尝试阻止工作项执行，不一定能成功。可以在 ISR 中安全调用。

  • 线程可以调用 k_work_cancel_sync() 阻塞，直到工作完成；如果取消成功或无需取消（工作未提交或未运行），它会立即返回。可以在（ISR 中）调用 k_work_cancel() 之后使用它，确认由 ISR 发起的取消已经完成。

调度可延迟工作项

可延迟工作项使用 k_work_delayable 类型的变量定义。它必须通过调用 k_work_init_delayable() 初始化。

延迟工作有两种常见用例，区别在于发生新事件时是否应延长截止时间。一个例子是收集异步到达的数据，例如来自键盘所连 UART 的字符。有两个 API 可在延迟之后提交工作：

  • k_work_schedule()（或 k_work_schedule_for_queue()）将工作调度为在特定时间或延迟之后执行。在延迟结束前再次使用该 API 调度同一工作项，不会改变该工作项被提交到其队列的时间。如果策略是从收到 第一个 未处理数据起，持续收集数据直到指定延迟结束，请使用该 API；

  • k_work_reschedule()（或 k_work_reschedule_for_queue()）无条件地设置工作的截止时间，替换之前任何未完成的延迟，并在必要时更改目标队列。如果策略是从收到 最后一个 未处理数据起，持续收集数据直到指定延迟结束，请使用该 API。

如果工作项未被调度，这两个 API 的行为相同。如果将 K_NO_WAIT 指定为延迟，其行为就如同工作项被立即直接提交到目标队列，而不等待最小超时（除非使用的是 k_work_schedule() 且之前的延迟尚未结束）。

两者都有可以控制提交所用队列的变体。

辅助函数 k_work_delayable_from_work() 可用于从传给工作处理函数的 k_work 指针，获取指向包含它的 k_work_delayable 的指针。

还可以使用以下 API 检查工作项的状态或与其同步：

  • k_work_delayable_busy_get() 是 k_work_busy_get() 针对可延迟工作的对应函数。

  • k_work_delayable_is_pending() 是 k_work_is_pending() 针对可延迟工作的对应函数。

  • k_work_flush_delayable() 是 k_work_flush() 针对可延迟工作的对应函数。

  • k_work_cancel_delayable() 是 k_work_cancel() 针对可延迟工作的对应函数；k_work_cancel_delayable_sync() 也与此类似。

与工作项同步

虽然在任何上下文中都可以使用 k_work_busy_get() 和 k_work_delayable_busy_get() 确定普通工作项和可延迟工作项的状态，但有些用例需要在工作项提交之后与其同步。可以在线程上下文中调用 k_work_flush()、k_work_cancel_sync() 和 k_work_cancel_delayable_sync()，等待达到所请求的状态。

调用这些 API 时必须提供一个 k_work_sync 对象，该对象没有供应用程序查看的成员，但需要用它来提供同步对象。如果代码需要在启用 CONFIG_KERNEL_COHERENCE 的架构上工作，不应在栈上分配这些对象。

工作队列最佳实践

避免竞态条件

有时工作项要处理的数据天然是线程安全的，例如由某个线程放入 k_queue、再在工作线程中处理的数据。更常见的情况是需要外部同步来避免数据竞争：即工作线程可能检查或操作正被另一个线程或中断访问的共享状态。这种状态可能是表示需要执行工作的标志，也可能是由 ISR 或线程填充、由工作处理函数读取的共享对象。

对于简单的标志，使用 原子服务 可能就足够了。其他情况下，可以使用自旋锁（k_spinlock）或感知线程的锁（k_sem、k_mutex 等）来确保不发生数据竞争。

如果所选的锁机制可能 sleep，那么让工作线程睡眠会使工作队列中的其他工作项得不到运行，而这些工作项可能需要继续执行才能让锁被释放。工作处理函数应尝试以不等待的方式获取锁。例如：

static void work_handler(struct work *work)
{
        struct work_context *parent = CONTAINER_OF(work, struct work_context,
                                                   work_item);

        if (k_mutex_lock(&parent->lock, K_NO_WAIT) != 0) {
                /* NB: Submit will fail if the work item is being cancelled. */
                (void)k_work_submit(work);
                return;
        }

        /* do stuff under lock */
        k_mutex_unlock(&parent->lock);
        /* do stuff without lock */
}

注意，如果持有锁的线程优先级低于工作队列，重新提交可能会使本应释放锁的线程得不到运行，导致应用程序失败。在需要上述惯用写法的场合，最好使用可延迟工作项，并以非零延迟（重新）调度工作，让持有锁的线程能够继续执行。

注意，如果工作项已被取消，从工作处理函数中提交可能会失败。这通常是可以接受的，因为处理函数结束后取消就会完成。如果不可接受，上述代码必须采取其他措施，通知应用程序该工作无法执行。

单独看，工作项本身是自锁的，因此仅仅为了提交或调度它们，无需持有外部锁。即使你使用受此类锁保护的外部状态来阻止进一步的重新提交，只要能确定该工作项最终会获取它的锁并检查该状态以决定是否需要做什么，重新提交就是安全的。如果可延迟工作项因无法获取锁而在其处理函数中被重新调度，则需要其他自锁状态（例如应用程序/驱动在发起取消时设置的原子标志）来检测取消，避免已取消的工作项在截止时间到达后再次被提交。

检查返回值

所有工作 API 函数都会返回底层操作的状态，很多情况下必须验证是否得到了预期结果。

  • 如果工作正在被取消，或者队列不接受新工作项，提交工作项（k_work_submit_to_queue()）可能会失败。此时该工作不会执行，这可能导致依靠工作处理函数驱动的子系统失去响应。

  • 异步取消（k_work_cancel() 或 k_work_cancel_delayable()）可能在工作项仍由处理函数运行时就已完成。此时继续操作与工作处理函数共享的状态会导致数据竞争，进而引发故障。

Zephyr 代码中曾经出现过许多竞态条件，原因就是没有检查操作的结果。

有时可能有充分理由认为，表示操作未按预期完成的返回值并不构成问题。这种情况下，代码应清楚地说明这一点：(1) 将返回值强制转换为 void，表明有意忽略该结果；(2) 说明在意外情况下会发生什么。例如：

/* If this fails, the work handler will check pub->active and
 * exit without transmitting.
 */
(void)k_work_cancel_delayable(&pub->timer);

但在这种情况下，后续代码仍必须避免数据竞争，因为它无法保证工作线程没有在访问与工作相关的状态。

不要过早优化

工作队列 API 在设计上可以安全地从多个线程和中断中调用。试图从外部检查工作项的状态并根据结果做决定，很可能会引入新的问题。

因此，有新工作到来时，直接提交即可。不要试图通过 k_work_is_pending() 或 k_work_busy_get() 检查状态快照来判断工作项是否已提交，或者检查 k_work_delayable_remaining_get() 是否返回非零延迟，以此进行“优化”。这些检查并不可靠：“忙碌”指示在检查结果返回时可能已经过时；如果工作从多个上下文提交，或者（对可延迟工作而言）截止时间已到但工作仍处于已排队或运行中状态，“不忙碌”指示也可能是错的。

一个通用的最佳实践是，始终在共享状态中维护某个条件，供处理函数检查以确认是否有工作要做。这样就可以把工作处理函数当作标准的清理路径：不必在提交工作项的地方处理取消和清理，而是可能把所有事情都放在工作处理函数中完成。

可以安全使用 k_work_is_pending() 的少见情况是：如果你 确定 在检查期间不会有其他代码提交该工作（通常是因为你持有一个锁，阻止了对提交所用状态的访问），就可以用它进行检查，以避免调用 k_work_flush() 或 k_work_cancel_sync()。

建议用法

使用系统工作队列将复杂的中断相关处理从 ISR 推迟到一个共享线程中执行。这样既能及时完成中断相关处理，又不影响系统响应后续中断的能力，也不需要应用程序另外定义和管理一个线程来执行这些处理。
