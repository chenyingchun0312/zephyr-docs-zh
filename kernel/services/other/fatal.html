致命错误

源代码中触发的软件错误

Zephyr 提供了多种引发致命错误的方法，包括构建时检查、条件编译的断言，以及主动调用的 panic 或 oops。

运行时断言（ZASSERT() 和旧的 __ASSERT()）失败会引发致命错误。有关断言 API 及其失败行为的配置方式，请参阅 断言。

内核 Oops

内核 oops 是通过 k_oops() 触发的软件致命错误，应用于表示应用程序逻辑中出现了不可恢复的情况。

生成的致命错误原因码为 K_ERR_KERNEL_OOPS。

内核 Panic

内核 panic 是通过 k_panic() 触发的软件致命错误，应用于表示 Zephyr 内核处于不可恢复的状态。如果内核遇到 panic，k_sys_fatal_error_handler() 的实现不应返回，因为整个系统需要复位。

运行在用户模式下的线程不允许调用 k_panic()，这样做会改为产生内核 oops。否则，生成的致命错误原因码为 K_ERR_KERNEL_PANIC。

异常

伪中断

如果 CPU 在某条中断线上收到硬件中断，而该中断线尚未通过 IRQ_CONNECT() 或 irq_connect_dynamic() 安装处理程序，内核将产生原因码为 K_ERR_SPURIOUS_IRQ() 的致命错误。

栈溢出

如果线程压入其执行栈的数据超出了栈缓冲区的容量，内核可能能够检测到这种情况，并产生原因码为 K_ERR_STACK_CHK_FAIL 的致命错误。

如果线程运行在用户模式下，栈溢出总能被捕获，因为线程根本没有权限写入栈缓冲区之外的相邻内存地址。由于这是由内存保护硬件强制执行的，因此不存在破坏线程原本无权写入的内存数据的风险。

如果线程运行在特权（supervisor）模式下，或者未启用 CONFIG_USERSPACE，那么栈溢出能否被捕获取决于配置。部分架构支持 CONFIG_HW_STACK_PROTECTION，它可以捕获特权模式下的栈溢出，包括代表用户线程处理系统调用时发生的溢出。这通常通过专用的 CPU 特性，或紧邻栈缓冲区放置的只读 MMU/MPU 保护区域来实现。以这种方式捕获的栈溢出能够检测到溢出，但不能保证没有数据被破坏，应当将其视为影响整个系统健康状态的非常严重的情况。

如果平台缺乏内存管理硬件支持，可以使用 CONFIG_STACK_SENTINEL。这是一种纯软件的栈溢出检测功能，它会定期检查栈缓冲区末尾的哨兵值是否被破坏。它不需要硬件支持，但无法防止数据被破坏。由于检查通常在中断退出时进行，溢出可能在栈实际溢出之后相当长的时间才被检测到。

最后，Zephyr 通过 CONFIG_STACK_CANARIES 支持 GCC 编译器的栈金丝雀（stack canary）。启用后，编译器会将启动时随机生成的金丝雀值插入函数栈帧中，并在函数退出时检查金丝雀是否被覆盖。如果检查失败，编译器会调用 __stack_chk_fail()，其 Zephyr 实现会引发栈溢出致命错误。这种情况下的错误并不表示整个栈缓冲区都已溢出，而是表示当前函数的栈帧已被破坏。更多细节请参阅编译器文档。

默认情况下，所有线程共享一个在启动时生成的金丝雀值。启用 CONFIG_STACK_CANARIES_TLS 后，金丝雀改为存放在 线程本地存储 中，使每个线程拥有自己的值，从而使金丝雀的位置和值更难预测，代价是每个线程需要额外的设置工作。

作为一项补充性的加固措施，CONFIG_STACK_POINTER_RANDOM 会在创建线程时为其初始栈指针加上一个随机偏移。这是一种有限形式的地址空间布局随机化，使任意栈帧的位置都不确定，从而阻碍某些类型的安全攻击，代价是每个线程的栈区域最多会消耗所配置的字节数。

其他异常

任何其他类型的未处理 CPU 异常都会产生错误码 K_ERR_CPU_EXCEPTION。

致命错误处理

遇到致命错误时采取何种策略，由 k_sys_fatal_error_handler() 函数的实现决定。该函数有一个弱链接的默认实现，它调用 LOG_PANIC() 输出所有挂起的日志消息，然后通过 k_fatal_halt() 无条件地停止系统。

应用程序可以通过覆盖 k_sys_fatal_error_handler() 的实现来自行实现错误处理策略。如果该实现返回，出错的线程将被中止，系统其余部分继续运行。更多细节和约束请参阅该函数的文档。
