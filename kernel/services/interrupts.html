中断

中断服务例程（interrupt service routine，ISR）是为响应硬件或软件中断而异步执行的函数。ISR 通常会抢占当前线程的执行，从而以极低的延迟做出响应。只有在所有 ISR 工作完成之后，线程才会恢复执行。

概念

可以定义任意数量的 ISR（仅受可用 RAM 限制），但要受底层硬件施加的约束。

ISR 具有以下关键属性：

  • 触发该 ISR 的 中断请求（IRQ）信号。

  • 与该 IRQ 关联的 优先级。

  • 被调用以处理该中断的 中断服务例程。

  • 传给该函数的 参数值。

IDT 或向量表用于将给定的中断源与给定的 ISR 关联。在任何时刻，一个特定 IRQ 只能关联一个 ISR。

多个 ISR 可以使用同一个函数来处理中断，这样单个函数就可以为产生多种中断的设备提供服务，或为多个（通常是同类型的）设备提供服务。传给 ISR 函数的参数值使该函数能够确定是哪个中断被触发。

内核为所有未使用的 IDT 表项提供一个默认 ISR。如果有意外中断被触发，该 ISR 会产生致命系统错误。

内核支持 中断嵌套。这意味着如果有更高优先级的中断被触发，正在执行的 ISR 可以被抢占。更高优先级的 ISR 处理完成后，较低优先级的 ISR 恢复执行。

ISR 在内核的 中断上下文 中执行。该上下文有自己专用的栈区域（在某些架构上是多个栈区域）。如果启用了中断嵌套支持，中断上下文栈的大小必须足以支持多个 ISR 并发执行。

重要

许多内核 API 只能由线程使用，而不能由 ISR 使用。对于可能同时被线程和 ISR 调用的例程，内核提供了 k_is_in_isr() API，让例程可以根据自己是作为线程的一部分还是作为 ISR 的一部分执行来调整其行为。

多级中断处理

通过使用一个或多个嵌套中断控制器，硬件平台可以支持比原生更多的中断线。多个硬件中断源被合并到一条线上，然后路由到父控制器。

如果支持嵌套中断控制器，应启用 CONFIG_MULTI_LEVEL_INTERRUPTS，并根据硬件架构配置 CONFIG_2ND_LEVEL_INTERRUPTS 和 CONFIG_3RD_LEVEL_INTERRUPTS。

系统会分配一个唯一的 32 位中断号，其中嵌入了用于选择和调用正确中断服务例程（ISR）的信息。每一级中断在这个 32 位数中占一个字节，因此该架构最多支持四级中断，如下图所示并解释：

└───┴───┴─│─┴───┴───┴───┴───┴───┴───┴─│─┴───┴───┘
          └─────────────────┐         └─────────────────────┐
      5                     v                               v
┌───┬───┬───┬───┬───┬───┬───┐   ┌───┬───┬───┬───┬───┬───┬───┐
│   │ ╷ │   │ C │   │   │   │   │   │   │   │   │ B │   │   │   (LEVEL 2)

图中显示了三级中断。

  • 每个单元格代表一条中断线，从 0（最右侧）开始编号。

  • 第 1 级有 12 条中断线，其中两条（2 和 9）连接到嵌套控制器，线 4 上连接一个设备“A”。

  • 其中一个第 2 级控制器的中断线 5 连接到一个第 3 级嵌套控制器，线 3 上连接一个设备“C”。

  • 第 3 级控制器的线 2 上连接一个设备“D”。

下面说明如何为每个硬件中断生成唯一的中断号。以上图中的 A、B、C、D 四个中断为例：

A -> 0x00000004
B -> 0x00000302
C -> 0x00000409
D -> 0x00030609

备注

第 2 级及以上各级的位值偏移 1，因为 0 表示该级不存在中断号。在本例中，第 3 级控制器的线 2 上连接设备 D，该控制器连接到第 2 级控制器的线 5，而第 2 级控制器又连接到第 1 级控制器的线 9（2 -> 5 -> 9）。由于第 2 级及以上各级存在编码偏移，设备 D 的中断号为 0x00030609。

阻止中断

在某些情况下，当前线程在执行时间敏感的操作或临界区操作时，可能需要阻止 ISR 执行。

线程可以使用 IRQ 锁 暂时阻止系统中所有的 IRQ 处理。该锁在已经生效时仍可再次加锁，因此例程可以使用它，而无需知道它是否已经生效。线程必须按加锁的次数相同地解锁，内核才能在该线程运行期间再次处理中断。

重要

线程持有 IRQ 锁时不允许 睡眠；只能调用 isr-ok 函数。

另外，线程也可以暂时 禁用 某个指定的 IRQ，使其关联的 ISR 在该 IRQ 被触发时不执行。之后必须 启用 该 IRQ，才能让 ISR 执行。

重要

禁用一个 IRQ 会阻止关联的 ISR 抢占系统中的 所有 线程，而不仅仅是禁用该 IRQ 的线程。

零延迟中断

使用 IRQ 锁阻止中断可能会增加观测到的中断延迟。然而，对于某些低延迟用例，较高的中断延迟可能是不可接受的。

为满足这类用例，内核允许具有严格延迟要求的中断以不会被中断锁阻塞的优先级执行。这类中断被定义为 零延迟中断。支持零延迟中断需要启用 CONFIG_ZERO_LATENCY_IRQS。由于普通 ISR 会与内核交互，任何配置为零延迟的中断还必须声明为 直接 ISR（并且其中不得使用 ISR_DIRECT_PM）。此外，必须将标志 IRQ_ZERO_LATENCY 传给 IRQ_DIRECT_CONNECT 宏，才能将特定中断配置为零延迟。在某些架构上，可以将零延迟中断的 ISR 同时声明为直接 ISR 和动态 ISR，参见 定义“直接”ISR。

零延迟中断预期用于直接管理硬件事件，完全不与内核代码交互。它们应把所有内核 API 视为未定义行为（即在零延迟中断上下文中使用这些 API 的应用程序需自行直接验证行为是否正确）。零延迟中断不得修改从普通 Zephyr 上下文调用的内核 API 所检查的任何数据，也不得产生需要同步处理的异常（例如内核 panic）。

当系统电源管理在 PM 恢复过程中保持中断锁定时，零延迟中断不受锁定恢复顺序的约束，可能在 PM 挂起/恢复逻辑期间、在 PM 恢复的状态记录以及 SoC/设备硬件恢复完成之前就被分发。这类 ISR 必须能在 PM 唤醒过程中安全运行；否则，在系统状态不允许该 ISR 执行时，必须屏蔽或禁用该中断源。关于如何在可能产生零延迟中断的设备路径处于活动状态时将不安全的状态排除在策略选择之外，可参考 设备电源策略约束。

重要

零延迟中断是否受支持取决于具体架构。该功能目前在 ARM Cortex-M 架构变体中实现。

小技巧

为减轻 Flash 访问延迟，可以考虑将 ISR 及所有相关符号重定位到 RAM 中。

转移 ISR 工作

ISR 应当快速执行，以确保系统运行可预测。如果需要进行耗时的处理，ISR 应将部分或全部处理工作转移给线程，从而恢复内核响应其他中断的能力。

内核支持多种将中断相关处理转移给线程的机制。

  • ISR 可以使用 FIFO、LIFO 或信号量等内核对象，通知辅助线程进行中断相关处理。

  • ISR 可以让系统工作队列线程执行一个工作项。（参见 工作队列线程。）

ISR 将工作转移给线程时，通常在 ISR 完成后只发生一次切换到该线程的上下文切换，使中断相关处理几乎可以立即继续进行。但是，根据处理转移工作的线程的优先级，当前正在执行的协作式线程或其他更高优先级的线程可能会在处理转移工作的线程被调度之前执行。

共享中断线

在某些硬件平台上，同一条中断线可能被不同的 IP 使用。例如，中断 17 可能被 DMA 控制器用来表示数据传输已完成，也可能被 DAI 控制器用来表示传输 FIFO 已达到其水位线。为了使其正常工作，要么需要采用某种特殊逻辑，要么需要寻找变通方案（例如使用 shared_irq 中断控制器），而这些做法的可扩展性都不太好。

为解决这个问题，可以使用共享中断，通过 CONFIG_SHARED_INTERRUPTS 启用。每当试图（使用 IRQ_CONNECT 或 irq_connect_dynamic()）在同一条中断线上注册第二个 ISR/参数对时，该中断线就会变为共享，也就是说每次该中断被触发时，这两个 ISR/参数对（之前注册的和刚注册的）都会被调用。在共享中断上下文中使用某条中断线的实体称为客户端。一个中断允许的最大客户端数量由 CONFIG_SHARED_IRQ_MAX_NUM_CLIENTS 控制。

中断共享对用户是透明的。因此，用户可以像平常一样使用 IRQ_CONNECT 和 irq_connect_dynamic() 注册中断，中断共享在后台自动处理。

同时启用共享中断支持和动态中断支持后，用户可以使用 irq_disconnect_dynamic() 动态断开 ISR。ISR 断开后，当它所注册的中断线被触发时，该 ISR 将不再被调用。

请注意，启用 CONFIG_SHARED_INTERRUPTS 会使二进制文件的大小明显增加。请谨慎使用。

实现

定义普通 ISR

ISR 在运行时通过调用 IRQ_CONNECT 定义。之后必须调用 irq_enable() 来启用它。

备注

不带前缀的中断控制 API（例如 irq_enable() 和 irq_lock()）是旧式写法。新代码应使用它们带命名空间的等价函数 k_irq_enable()、k_irq_lock() 等。不带前缀的名称仍然完全受支持。

重要

IRQ_CONNECT() 不是 C 函数，它在后台使用了一些内联汇编技巧。它的所有参数都必须在构建时已知。具有多个实例的驱动可能需要定义每个实例各自的配置函数，以便为每个实例配置中断。

以下代码定义并启用一个 ISR。

#define MY_DEV_IRQ  24       /* device uses IRQ 24 */
#define MY_DEV_PRIO  2       /* device uses interrupt priority 2 */
/* argument passed to my_isr(), in this case a pointer to the device */
#define MY_ISR_ARG  DEVICE_GET(my_device)
#define MY_IRQ_FLAGS 0       /* IRQ flags */

void my_isr(void *arg)
{
   ... /* ISR code */
}

void my_isr_installer(void)
{
   ...
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_PRIO, my_isr, MY_ISR_ARG, MY_IRQ_FLAGS);
   irq_enable(MY_DEV_IRQ);
   ...
}

由于 IRQ_CONNECT 宏要求其所有参数在构建时已知，这在某些情况下可能无法接受。也可以使用 irq_connect_dynamic() 在运行时安装中断，其用法与 IRQ_CONNECT 完全相同：

void my_isr_installer(void)
{
   ...
   irq_connect_dynamic(MY_DEV_IRQ, MY_DEV_PRIO, my_isr, MY_ISR_ARG,
                       MY_IRQ_FLAGS);
   irq_enable(MY_DEV_IRQ);
   ...
}

动态中断需要启用 CONFIG_DYNAMIC_INTERRUPTS 选项。目前不支持删除或重新配置动态中断。

定义“直接”ISR

普通 Zephyr 中断会带来一些开销，对某些低延迟用例来说可能无法接受。具体来说：

  • 需要获取 ISR 的参数并将其传给 ISR

  • 如果启用了电源管理且系统处于空闲状态，在执行 ISR 之前，所有硬件都会从低功耗状态恢复，这可能非常耗时

  • 虽然有些架构会由硬件完成这一步，但其他架构需要在代码中切换到中断栈

  • 中断处理完成后，操作系统还要执行一些逻辑，可能需要做出调度决策

  • 零延迟中断 必须始终声明为直接 ISR，因为普通 ISR 会与内核交互

Zephyr 支持所谓的“直接”中断，这类中断通过 IRQ_DIRECT_CONNECT 安装，其处理函数使用 ISR_DIRECT_DECLARE 声明。直接中断有一些特殊的实现要求，功能也有所缩减；详见 IRQ_DIRECT_CONNECT 和 ISR_DIRECT_DECLARE 的定义。

直接中断只在选择了 CONFIG_ARCH_HAS_DIRECT_INTERRUPTS 的架构上可用。在其他任何架构上使用 IRQ_DIRECT_CONNECT 或 ISR_DIRECT_DECLARE 都会导致构建失败。

以下代码演示一个直接 ISR：

#define MY_DEV_IRQ  24       /* device uses IRQ 24 */
#define MY_DEV_PRIO  2       /* device uses interrupt priority 2 */
#define MY_IRQ_FLAGS 0       /* IRQ flags */

ISR_DIRECT_DECLARE(my_isr)
{
   do_stuff();
   /* PM done after servicing interrupt for best latency. This cannot be
   used for zero-latency IRQs because it accesses kernel data. */
   ISR_DIRECT_PM();
   /* Ask the kernel to check if scheduling decision should be made. If the
   ISR is for a zero-latency IRQ then the return value must always be 0. */
   return 1;
}

void my_isr_installer(void)
{
   ...
   IRQ_DIRECT_CONNECT(MY_DEV_IRQ, MY_DEV_PRIO, my_isr, MY_IRQ_FLAGS);
   irq_enable(MY_DEV_IRQ);
   ...
}

是否支持安装动态直接中断取决于具体架构。该功能目前在 Arm Cortex-M 架构变体中通过宏 ARM_IRQ_DIRECT_DYNAMIC_CONNECT 实现，可用它声明一个既是直接又是动态的中断。

在 RAM 中执行 ISR

为实现超低延迟，可以将 ISR 和向量表重定位到 RAM 中，以消除 Flash 访问延迟。启用 CONFIG_SRAM_VECTOR_TABLE 和 CONFIG_SRAM_SW_ISR_TABLE 选项即可将向量表放到 RAM 中。然后，可以使用 Zephyr 的 代码和数据重定位 功能，将 ISR 代码及所有相关符号也重定位到 RAM 中。

共享一条中断线

以下代码使用同一个中断号定义两个 ISR。

#define MY_DEV_IRQ 24               /* device uses INTID 24 */
#define MY_DEV_IRQ_PRIO 2           /* device uses interrupt priority 2 */
/*  this argument may be anything */
#define MY_FST_ISR_ARG INT_TO_POINTER(1)
/*  this argument may be anything */
#define MY_SND_ISR_ARG INT_TO_POINTER(2)
#define MY_IRQ_FLAGS 0              /* IRQ flags */

void my_first_isr(void *arg)
{
   ... /* some magic happens here */
}

void my_second_isr(void *arg)
{
   ... /* even more magic happens here */
}

void my_isr_installer(void)
{
   ...
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_first_isr, MY_FST_ISR_ARG, MY_IRQ_FLAGS);
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_second_isr, MY_SND_ISR_ARG, MY_IRQ_FLAGS);
   ...
}

Defining a regular ISR 中所述关于 IRQ_CONNECT 的限制同样适用于此处。如果禁用了 CONFIG_SHARED_INTERRUPTS，上述代码会产生构建错误。否则，每次中断 24 被触发时，上述代码中的两个 ISR 都会被调用。

如果 CONFIG_SHARED_IRQ_MAX_NUM_CLIENTS 被设置为小于 2（当前客户端数量）的值，会产生构建错误。

如果启用了动态中断，irq_connect_dynamic() 允许在运行时共享中断。超过所配置的最大允许客户端数量会导致断言失败。

动态断开 ISR

以下代码使用同一个中断号定义两个 ISR，其中第二个 ISR 在运行时被断开。

#define MY_DEV_IRQ 24               /* device uses INTID 24 */
#define MY_DEV_IRQ_PRIO 2           /* device uses interrupt priority 2 */
/*  this argument may be anything */
#define MY_FST_ISR_ARG INT_TO_POINTER(1)
/*  this argument may be anything */
#define MY_SND_ISR_ARG INT_TO_POINTER(2)
#define MY_IRQ_FLAGS 0              /* IRQ flags */

void my_first_isr(void *arg)
{
   ... /* some magic happens here */
}

void my_second_isr(void *arg)
{
   ... /* even more magic happens here */
}

void my_isr_installer(void)
{
   ...
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_first_isr, MY_FST_ISR_ARG, MY_IRQ_FLAGS);
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_second_isr, MY_SND_ISR_ARG, MY_IRQ_FLAGS);
   ...
}

void my_isr_uninstaller(void)
{
   ...
   irq_disconnect_dynamic(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_first_isr, MY_FST_ISR_ARG, MY_IRQ_FLAGS);
   ...
}

调用 irq_disconnect_dynamic() 会使中断 24 变为非共享，即系统的行为就像第一次 IRQ_CONNECT 调用从未发生过一样。只有启用了 CONFIG_DYNAMIC_INTERRUPTS 时才允许这样做，否则会产生链接错误。

实现细节

中断表在构建时使用一些专门的构建工具建立。此处介绍的细节适用于除 x86 之外的所有架构，x86 的情况见下文 x86 Details 一节。

调用 IRQ_CONNECT 会声明一个 struct _isr_list 实例，该实例被放在一个特殊的 .intList 段中。该段只在预编译阶段存在于编译后的代码中。它供 Zephyr 脚本生成中断表使用，并会从最终构建结果中移除。该脚本实现了不同的解析器，用于处理 .intList 段中的数据并生成所需的输出。

默认解析器生成 C 数组，其中填充的参数和中断处理函数以地址形式表示，这些地址直接取自 .intList 段的条目。它适用于所有架构和编译器（上面提到的例外除外）。该解析器的局限在于，数组生成后要求代码不再被重定位。此阶段的任何重定位都可能导致中断数组中的条目不再指向预期的函数。这意味着该解析器虽然兼容性更好，却使我们无法使用链接时优化（Link Time Optimization）。

本地 ISR 声明解析器采用另一种方法，在二进制层面构建相同的数组。数组的所有条目都在本地声明和定义，即直接在使用 IRQ_CONNECT 的文件中完成。这些条目被放在一个具有唯一合成名称的段中。随后该段的名称被放入 .intList 段，用于生成一段链接脚本片段，将条目放到正确的地址上。该解析器目前仅限于受支持的架构和工具链，但作为回报，它为链接器保留了对象关系的信息，从而可以启用链接时优化。

使用 C 数组的实现

这是默认配置，适用于 Zephyr 支持的所有架构。

每次调用 IRQ_CONNECT 都会声明一个 struct _isr_list 实例，该实例被放在一个特殊的 .intList 段中：

struct _isr_list {
    /** IRQ line number */
    int32_t irq;
    /** Flags for this IRQ, see ISR_FLAG_* definitions */
    int32_t flags;
    /** ISR to call */
    void *func;
    /** Parameter for non-direct IRQs */
    void *param;
};

Zephyr 分两个阶段构建；构建的第一阶段生成 ${ZEPHYR_PREBUILT_EXECUTABLE}.elf，其中包含 .intList 段中的所有条目，前面有一个头部：

struct {
    void *spurious_irq_handler;
    void *sw_irq_handler;
    uint32_t num_isrs;
    uint32_t num_vectors;
    struct _isr_list isrs[];  <- of size num_isrs
};

随后，gen_isr_tables.py 脚本使用 ${ZEPHYR_PREBUILT_EXECUTABLE}.elf 中由头部和 struct _isr_list 实例组成的这些数据，生成一个定义了向量表和软件 ISR 表的 C 文件，该文件再被编译并链接到最终的应用程序中。

这些表中并不编码中断的优先级。IRQ_CONNECT 还有一个运行时部分，负责将中断所需的优先级写入中断控制器。有些架构不支持中断优先级的概念，这时优先级参数会被忽略。

向量表

启用 CONFIG_GEN_IRQ_VECTOR_TABLE 时会生成向量表。该数据结构由 CPU 直接使用，它只是一个函数指针数组，其中第 n 个元素对应 IRQ 线 n 的 IRQ 处理函数，这些函数指针为：

  1. 对于使用 IRQ_DIRECT_CONNECT 声明的“直接”中断，此处放置其处理函数。

  2. 对于使用 IRQ_CONNECT 声明的普通中断，此处放置通用软件 IRQ 处理函数的地址。这段代码执行通用的内核中断状态记录，并从软件 ISR 表中查找 ISR 及其参数。

  3. 对于完全未配置的中断线，此处放置伪中断（spurious IRQ）处理函数的地址。一旦遇到伪中断，该处理函数会引发致命系统错误。

有些架构的所有中断共用一个入口点，不支持向量表，这时应禁用 CONFIG_GEN_IRQ_VECTOR_TABLE 选项。

有些架构可能会保留开头的若干向量用于系统异常，并在其他地方的表中声明它们，这时需要设置 CONFIG_GEN_IRQ_START_VECTOR，以便正确偏移表中的索引。

软件 ISR 表

这是一个 struct _isr_table_entry 数组：

struct _isr_table_entry {
    void *arg;
    void (*isr)(void *);
};

通用软件 IRQ 处理函数用它查找 ISR 及其参数并执行该 ISR。当前活动的 IRQ 线从中断控制器寄存器中查得，并用作该表的索引。

共享软件 ISR 表

这是一个 struct z_shared_isr_table_entry 数组：

struct z_shared_isr_table_entry {
    struct _isr_table_entry clients[CONFIG_SHARED_IRQ_MAX_NUM_CLIENTS];
    size_t client_num;
};

该表记录每条中断线上已注册的客户端。每当某条中断线变为共享时，z_shared_isr() 会替换 _sw_isr_table 中当前注册的 ISR。这个特殊的 ISR 会遍历已注册客户端的列表并调用各个 ISR。

使用链接脚本的实现

这种通过准备和解析 .isrList 段来实现中断向量数组的方式称为本地 ISR 声明。之所以这样命名，是因为构成中断向量的数组条目都在调用 IRQ_CONNECT 宏的位置本地创建。然后使用自动生成的链接脚本将其放到内存中的正确位置。

该选项需要通过选择 CONFIG_ISR_TABLES_LOCAL_DECLARATION 来启用。如果所用的架构和工具链支持该配置，则会设置 CONFIG_ISR_TABLES_LOCAL_DECLARATION_SUPPORTED。关于当前受支持的配置，请参阅该选项的详细说明。

每次调用 IRQ_CONNECT 或 IRQ_DIRECT_CONNECT 都会声明一个 struct _isr_list_sname 实例，该实例被放在一个特殊的 .intList 段中：

struct _isr_list_sname {
    /** IRQ line number */
    int32_t irq;
    /** Flags for this IRQ, see ISR_FLAG_* definitions */
    int32_t flags;
    /** The section name */
    const char sname[];
};

注意，段名称放在柔性数组成员中。这意味着已初始化结构体的大小会随结构名称的长度而变化。整个条目由脚本在应用程序构建期间使用，包含正确放置中断所需的全部信息。

除 _isr_list_sname 之外，IRQ_CONNECT 宏还会生成一个将成为中断数组一部分的条目：

struct _isr_table_entry {
    const void *arg;
    void (*isr)(const void *);
};

该数组被放在一个段中，段名称保存在 _isr_list_sname 结构体中。

IRQ_DIRECT_CONNECT 宏生成的值取决于架构。它可以是一个指向中断处理函数的变量：

static uintptr_t <unique name> = ((uintptr_t)func);

也可以是一个实际的裸函数（naked function），实现跳转到中断处理函数：

static void <unique name>(void)
{
    __asm(ARCH_IRQ_VECTOR_JUMP_CODE(func));
}

与 IRQ_CONNECT 类似，所创建的变量或函数被放在一个段中，段名称保存在 _isr_list_sname 中。

脚本生成的文件

中断表生成脚本会创建 3 个文件：isr_tables.c、isr_tables_swi.ld 和 isr_tables_vt.ld。

isr_tables.c 包含中断、直接中断和共享中断（如果启用）的所有结构体。该文件只实现应用程序未实现的那些结构体，并在未在此处实现的中断位置留下注释，说明在哪里可以找到它。

然后使用两个链接文件。isr_tables_vt.ld 文件被包含在所选架构要求放置中断向量的位置。isr_tables_swi.ld 文件描述软件中断表元素的放置位置。之所以需要单独的文件，是因为根据当前配置，它可能被放在可写段或不可写段中。

x86 细节

x86 架构有一种特殊的向量表，称为中断描述符表（IDT），它必须按照 x86 处理器文档的规定以特定方式布局。它本质上仍是一个向量表，arch/x86/gen_idt.py 工具使用 .intList 段来创建它。但是，在基于 APIC 的系统上，向量表中的索引并不对应 IRQ 线。前 32 个向量保留给 CPU 异常，其余所有向量（直到索引 255）按每 16 个一组对应优先级。在这种方案中，优先级为 0 的中断放在向量 32-47 中，优先级 1 放在 48-63 中，依此类推。arch/x86/gen_idt.py 工具构建 IDT 时，每配置一个中断，都会在所请求优先级对应的范围内查找一个空闲向量，并在那里设置处理函数。

在 x86 上，当 CPU 执行某个中断或异常向量时，没有万无一失的办法确定是哪个向量被触发，因此不使用按 IRQ 线索引的软件 ISR 表。取而代之的是，IRQ_CONNECT 调用会创建一个小型汇编函数，以 ISR 和参数作为实参调用 _interrupt_enter() 中的通用中断代码。放入 IDT 的正是这个汇编中断桩函数的地址。对于使用 IRQ_DIRECT_CONNECT 声明的中断，无参数的 ISR 直接放入 IDT。

在向量表中的位置对应中断优先级的系统上，中断控制器需要在运行时知道哪个向量与某条 IRQ 线关联。为此，arch/x86/gen_idt.py 还会创建一个 _irq_to_interrupt_vector 数组，将 IRQ 线映射到它在 IDT 中所配置的向量。IRQ_CONNECT 在运行时使用该数组，在中断控制器中设置 IRQ 与向量之间的关联。

对于动态中断，构建过程必须生成一些 4 字节的动态中断桩函数，每个使用中的动态中断对应一个。桩函数的数量由 CONFIG_X86_DYNAMIC_IRQ_STUBS 选项控制。每个桩函数会压入一个唯一标识符，然后用它从一个表中取出相应的处理函数和参数，该表在连接动态中断时填充。

超出默认支持的中断数量

在多级配置中生成中断时，确定给定中断号属于哪一级时默认使用每级 8 位的掩码。当 CPU 的单个聚合器支持超过 255 个中断时，这可能成为问题。这种情况下，可能需要覆盖这些默认值，为每一级使用自定义的位数。无论每一级使用多少位，所有级别所用位数的总和必须小于或等于 32 位，以便放入一个 32 位整数中。要修改每一级的位数，可通过设置 CONFIG_1ST_LEVEL_INTERRUPT_BITS（第一级）、CONFIG_2ND_LEVEL_INTERRUPT_BITS（第二级）和 CONFIG_3RD_LEVEL_INTERRUPT_BITS（第三级）覆盖 Kconfig.multilevel 中的默认值 8。这些掩码控制生成中断值、检查中断级别以及将中断转换到其他级别时所用位掩码的长度和移位量。相关的控制逻辑位于 irq_multilevel.h 中。

建议用法

使用普通 ISR 或直接 ISR 执行需要非常快速响应、并且能够在不阻塞的情况下迅速完成的中断处理。

备注

耗时或涉及阻塞的中断处理应交给线程完成。关于应用程序中可以使用的各种技术，参见 Offloading ISR Work。
