系统定时器驱动

本页介绍内核的节拍记账与产生这些节拍的硬件驱动之间的接口。内核一侧的记账以及应用程序所能看到的一切，在 内核计时 中介绍。

定时器驱动

节拍级别的内核计时由定时器驱动驱动，其 API 相对简单。

  • 驱动应能通过 sys_clock_announce() 调用向内核“通告”新的节拍，该调用传入自上次通告调用（或系统启动）以来经过的整数节拍数。这些调用可以在任何时刻发生，但驱动应尽量确保（在中断延迟影响允许的范围内）它们发生在节拍边界附近（即不在某个节拍的“中途”），最重要的是，它们在长时间内要保持正确，并且相对于其他计数器和真实世界时间的偏差尽可能小。

  • 驱动应向内核提供 sys_clock_set_timeout() 调用，内核借此指明在必须收到一次通告调用以触发已注册的超时之前，最多可以经过多少个节拍。在该时刻之前通告新的节拍是合法的（但节拍数必须正确），而在该时刻之后才通告则会导致错过事件。注意，这里传入的超时值是相对于当前时间的差值，但这并不能免除驱动长期以稳定速率提供节拍的要求。该函数的简单实现容易出现错误，即不足一个节拍的部分被错误地“重置”，从而导致时钟偏差。

  • 驱动应提供 sys_clock_elapsed() 调用，用于给出自上次调用 sys_clock_announce() 以来（相对于真实世界时钟）已经过的节拍数的当前值；内核需要用它来检测新到达的超时是否已到期。

  • 驱动可以选择提供 sys_clock_no_timeout() 调用。当没有挂起的超时（即超时队列为空），并且启用了 CONFIG_SYSTEM_CLOCK_SLOPPY_IDLE 时，内核会调用它来代替 sys_clock_set_timeout()。

    此时不会有节拍通告到来，系统也不关心精确的运行时间记录，因此驱动可以采取一些措施来节省资源。在下一次调用 sys_clock_set_timeout() 时恢复正常运行；与 sys_clock_disable() 不同，这并不是一次拆除操作。

    定时器的 计数器 不得停止。sys_clock_cycle_get_32() 和 sys_clock_cycle_get_64() 必须继续递增计数，就像该调用从未发生过一样。

    备注

    在超时队列为空时 CPU 仍会继续运行，例如因为就绪队列中仍有线程，或者因为有中断触发。这些线程和 ISR 可能会调用 k_cycle_get_32() 或 k_busy_wait()。这限制了实现可以采取的措施：屏蔽定时器中断是安全的，而关闭定时器时钟很可能不安全。具体哪些操作是安全的，取决于硬件。

    该钩子是可选的。如果没有提供，内核会以它所能表达的最长等待时间，即 UINT32_MAX 个节拍，调用 sys_clock_set_timeout()。这在数值上与此处原来使用的 K_TICKS_FOREVER 相同，后者是长期以来表示“无截止时间”的信号，因此尚未改造的驱动仍能正常工作。

  • 驱动可以选择提供 sys_clock_idle_enter() 调用。当 CPU 即将进入低功耗空闲状态时，电源管理路径会调用它来代替 sys_clock_set_timeout()。它接收距离下一次预期唤醒的节拍数；如果没有预期的唤醒，并且允许运行时间记账产生漂移，则接收 SYS_CLOCK_IDLE_FOREVER。

    需要将计时交给低功耗唤醒定时器，或者需要以其他方式为睡眠重新配置自身的驱动，在这里完成这些工作。收到 SYS_CLOCK_IDLE_FOREVER 时，驱动还可以停止其时基，这是 sys_clock_no_timeout() 所不允许的；之所以可以这样做，是因为 CPU 正在进入空闲，并且在退出空闲时一定会调用 sys_clock_idle_exit()。只有调用该函数的 CPU 会进入空闲，因此如果驱动的时基由多个 CPU 共享，驱动必须确保只有最后一个进入空闲的 CPU 才停止时钟。

    该钩子是可选的。如果没有提供，内核会调用 sys_clock_set_timeout()，并将其已弃用的 idle 参数设为 true，因此仍依据该参数进行低功耗处理的驱动可以继续正常工作。

最后这三个入口点划分了系统可能处于的四种状态：

无挂起事件

有挂起事件

运行

sys_clock_no_timeout()

sys_clock_set_timeout(ticks)

空闲

sys_clock_idle_enter(SYS_CLOCK_IDLE_FOREVER)

sys_clock_idle_enter(ticks)

如果未启用 CONFIG_SYSTEM_CLOCK_SLOPPY_IDLE，左列的情况永远不会出现：内核会始终设置一个人为的截止时间，使运行时间保持精确，驱动只会遇到右列的情况。

定时器驱动加锁

内核通过 sys_clock_lock() 和 sys_clock_unlock() 提供统一的定时器锁。该锁既保护内核内部的节拍记账（curr_tick 和超时队列），也保护驱动中必须与之保持一致的私有状态（例如硬件周期计数器的基准值）。

维护内部状态的定时器驱动应在其 ISR 开始时获取该锁，更新硬件状态，然后将锁的键值传给 sys_clock_announce_locked()，由后者负责释放。这样可以确保驱动的周期计数器基准值和内核的 curr_tick 总是在同一把锁下更新，从而消除使用两把独立的锁时可能出现的竞争条件。这类竞争条件可能出现在 SMP 系统上，也可能（较少见地）出现在需要一致实时参考值的更高优先级 ISR 的单处理器系统上。

内核调用驱动提供的回调 sys_clock_set_timeout() 和 sys_clock_elapsed() 时，总是已经持有该锁。

为了保持向后兼容，sys_clock_announce() 仍然可用，它会在内部获取该锁。新驱动和迁移后的驱动应优先使用 sys_clock_lock() / sys_clock_announce_locked() 模式。

注意，按照这套 API 自然实现的结果是一个“无节拍”（tickless）内核：它只为已注册的事件接收和处理定时器中断，依靠可编程的硬件计数器产生不规则的中断。但传统的“有节拍”或“简单”计数器驱动也可以很容易地实现：

  • 驱动可以按与操作系统节拍频率相对应的固定速率接收中断，每次都以参数 1 调用 sys_clock_announce()。

  • 驱动可以忽略对 sys_clock_set_timeout() 的调用，因为无论超时状态如何，每个节拍都会被通告。

  • 驱动可以在每次调用 sys_clock_elapsed() 时都返回零，因为能检测到的已经过节拍数不会超过一个（否则就会收到中断）。

SMP 细节

一般来说，上述定时器 API 在多处理器环境中运行时没有变化。内核会在内部对所有访问进行适当的同步，并确保所有临界区都尽可能小。但有几点需要详细说明：

  • Zephyr 不关心由哪个 CPU 处理定时器中断。让所有定时器中断都在单个处理器上处理并不违规（尽管在某些情况下可能并不理想）。现有的 SMP 架构实现的都是对称的定时器驱动。

  • sys_clock_announce() 调用应在驱动层面实现全局同步。内核不做任何按 CPU 的跟踪，并期望当两个定时器中断几乎同时触发时，只有其中一个向计时子系统提供当前节拍数。如果没有经过任何节拍，另一个可以合法地提供为零的节拍数。它不应因时间片轮转的需要而“跳过”通告调用（参见 内核计时 中关于时间片的说明）。

  • 有些 SMP 硬件使用单个全局定时器设备，另一些则使用每个 CPU 独立的计数器。这里的复杂性（例如确保 CPU 之间的计数器同步）应由驱动而非内核处理。

  • 通过 sys_clock_set_timeout() 传回给驱动的下一个超时值，对每个 CPU 都是相同的。因此默认情况下，每个 CPU 都会为每个事件同时收到定时器中断，尽管按定义只有其中一个应该以非零的节拍数参数调用 sys_clock_announce()。对于时间敏感的应用程序，这可能是正确的默认行为（因为它能尽量降低出错的 ISR 或中断锁延迟超时的可能性），但在某些情况下可能带来性能问题。按照当前的设计，任何此类优化都由定时器驱动负责。

通用无节拍核心

上面描述的工作，包括周期到节拍的换算、通告基准值、按节拍对齐的截止时间计算，以及计数器回绕和范围处理，在每个无节拍驱动中几乎都相同，而各驱动手写的不同实现一再成为定时器缺陷的来源。drivers/timer/system_timer_generic.h 统一实现了这部分逻辑。

它是一个实现头文件，而不是声明头文件：包含它就会 定义 sys_clock_set_timeout()、sys_clock_elapsed() 以及 sys_clock_cycle_get_32() / sys_clock_cycle_get_64()。任意数量的驱动都可以基于它构建；每个驱动在提供下文所述的宏和原语之后包含它一次。一次构建只编译一个系统定时器驱动，因此这些定义只会出现一次。驱动只需处理周期，节拍域由核心负责。

无论计数器宽度如何，核心都会生成两个周期读取函数，包括 64 位版本：通告基准值是 64 位的，而没有调用者时链接器会丢弃该读取函数。

驱动是否同时选择 CONFIG_TIMER_HAS_64BIT_CYCLE_COUNTER，仍由驱动自行决定。该选项表示 64 位读取开销很小，或者至少不比 32 位读取更大，因此优先使用较窄的读取函数没有好处。使用 TIMER_CORE_COUNTER_NONATOMIC 时，两个读取函数都经过时钟锁，这一前提成立；如果计数器可原子读取但宽度小于 64 位，则只有 64 位读取函数会获取锁，32 位读取函数仍然是无锁读取。

驱动必须提供两个原语：读取硬件周期计数器的 timer_driver_cycle_get()，以及一个设置定时的函数，根据后端不同为 timer_driver_set_compare() 或 timer_driver_set_reload()。驱动的 ISR 先确认硬件中断，然后调用 timer_core_announce()；驱动的初始化函数先连接 IRQ，然后调用 timer_core_init()；在 SMP 系统上，驱动的 smp_timer_init() 调用 timer_core_smp_prime()。

后端选择

以下宏中必须恰好定义一个，用于说明硬件的类型：

TIMER_CORE_BACKEND_COMPARE_ORDERED

绝对比较器，有序匹配：一旦计数器达到或超过设定值，中断就会触发，因此已经过去的截止时间会立即触发。可用范围为计数器宽度的一半。

TIMER_CORE_BACKEND_COMPARE_EXACT

绝对比较器，相等匹配：如果写入的值已被计数器越过，就要等整整一个计数器周期才会匹配。核心通过一个校验循环写入比较器，因此驱动无需自行设定最小延迟下限。

TIMER_CORE_BACKEND_RELOAD

相对延迟：递减计数器和比较匹配后复位的周期定时器。这类硬件被假定为自动重装载，因此在有节拍的内核中，它会从初始化时设定的值开始自由运行。

可选宏

仅当下面给出的默认值不适用时才需要定义各个宏：

TIMER_CORE_CYCLES_PER_SEC

计数器频率，单位为 Hz。默认为内核系统时钟频率。当计数器经过预分频或以自身固定的频率运行时，需要设置它。核心据此推导出 TIMER_CORE_CYC_PER_TICK，驱动可以读取该值用于自身的硬件设置（通常是初始化时设定的单节拍周期），但绝不能自行定义它。

TIMER_CORE_CYCLES_PER_SEC_RUNTIME

上述频率是一个变量而不是构建时常量，因为它是从时钟控制器读取的，或者在初始化时计算得出。此时核心会预先计算一次每个节拍的周期数，而不是依赖编译器对除法的常量折叠。在调用 timer_core_init() 之前，该变量必须已经是最终值。

TIMER_CORE_COUNTER_WIDTH

timer_driver_cycle_get() 返回的计数值的宽度，单位为位，最大为 64。默认为本机寄存器宽度。其他宽度的计数器必须自行声明其宽度：否则，32 位 CPU 上真正的 64 位计数器会继承 32 位掩码，丢失超过 2^32 个周期的跨度。核心会把每个差值按此宽度进行掩码处理，因此较窄的计数器可以直接读取原始值，驱动无需在软件中扩展计数宽度。

TIMER_CORE_COUNTER_NONMONOTONIC

计数器读数可能暂时落后于已经观察到的值，例如 QEMU SMP 下的全局定时器就是如此。核心会把回退的读数视为没有经过时间，而不是一次巨大的跳变。

TIMER_CORE_COUNTER_NONATOMIC

timer_driver_cycle_get() 不是一次原子读取，而是根据 ISR 也会访问的状态合成的值。此时核心会在时钟锁的保护下读取它。

TIMER_CORE_HAVE_CYCLE_GET_32、TIMER_CORE_HAVE_CYCLE_GET_64

表示驱动自行定义相应的入口点，核心不再定义。适用于需要进行缩放的计数器。包含头文件之后可以使用 timer_core_cycle_get()，它给出计数器自身计数域中的全宽度计数值，驱动可以据此进行缩放。

设置了 TIMER_CORE_CYCLES_PER_SEC 的驱动必须定义 32 位版本，因为以自身频率运行的计数器的原始值无法被内核直接使用。此时核心也不会生成 64 位读取函数，因为它同样位于驱动刚刚声明为不同的计数域中。如果需要 64 位读取函数，也要一并提供。

TIMER_CORE_ALARM_MAX_CYCLES

设置定时的原语所能表达的最大值，仅此而已。默认为 TIMER_CORE_COUNTER_WIDTH 的完整跨度，因为定时器和计数器通常是同一个硬件。如果设置定时的范围由其他因素决定，例如比计数器更窄的比较或重装载寄存器，或者是一个独立的设备，则需要设置它。

它描述的是硬件容量，因此不包含任何安全余量。核心会根据 TIMER_CORE_COUNTER_WIDTH 推导出自己的余量：设置的定时距离上一次通告不超过计数器跨度的一半（使用 TIMER_CORE_COUNTER_NONMONOTONIC 时为四分之一），这样即使通告延迟，得到的差值仍能通过掩码正确解析。两者中先达到的限制生效。

TIMER_CORE_ALARM_MIN_CYCLES

重装载值下限，单位为周期，仅适用于 TIMER_CORE_BACKEND_RELOAD。默认为 1。

TIMER_CORE_ALARM_LEAD_CYCLES

比较值必须领先计数器的周期数，以确保能捕获匹配，仅适用于 TIMER_CORE_BACKEND_COMPARE_EXACT。默认为 1，即在计数器仍小于比较器时写入的比较器会触发。如果硬件需要先把写入操作同步到计数器的时钟域，并且会错过设置得比这更近的匹配，则需要增大该值。

新的无节拍驱动应基于此头文件构建，而不是重新实现节拍记账。该头文件完整记录了每个宏和原语。
