内核计时

Zephyr 提供了一套健壮且可扩展的计时框架，能够基于任意精度的硬件计时源报告和跟踪定时事件。

时间单位

内核使用多种时间单位跟踪时间，各自用于不同的目的。

实际时间值通常以毫秒或微秒为单位指定，是向应用程序代码呈现时间的默认方式。它们的优点是普遍可移植、易于理解，但可能无法与底层硬件的精度完全匹配。

内核通过 k_cycle_get_32() 和 k_cycle_get_64() API 提供“周期”（cycle）计数。其设计意图是：该计数器代表操作系统能够向用户提供的最快的周期计数器（例如 CPU 周期计数器），并且读取操作非常快。对时间非常敏感的应用程序代码可以用轮询的方式使用它，以获得最高的精度。该计数器的频率可以通过 sys_clock_hw_cycles_per_sec() 获取。在大多数平台上，这是一个运行时常量，其值为 CONFIG_SYS_CLOCK_HW_CYCLES_PER_SEC，并在系统整个生命周期内保持不变。在系统定时器频率不固定的平台上，sys_clock_hw_cycles_per_sec() 返回运行时的值，应用程序代码不得假定频率是单一且不变的。

运行时系统定时器频率

有些平台需要在运行时获取系统定时器频率，原因可能是定时器驱动从硬件中探测时钟频率，也可能是定时器时钟频率在启动后会发生变化。

能够在运行时更改当前系统定时器频率的平台必须启用 CONFIG_SYSTEM_CLOCK_HW_CYCLES_PER_SEC_RUNTIME_UPDATE，并且：

  • 在应用时钟变更后调用 z_sys_clock_hw_cycles_per_sec_update()。

  • 如果系统定时器驱动缓存了派生常量（例如每个节拍的周期数），或者需要在时钟变化时重新配置硬件，则需要在定时器驱动中提供 z_sys_clock_hw_cycles_per_sec_update() 的覆盖实现。

z_sys_clock_hw_cycles_per_sec_update() 的默认实现只更新所存储的频率值。

备注

CONFIG_SYSTEM_CLOCK_HW_CYCLES_PER_SEC_RUNTIME_UPDATE 将系统定时器频率作为单个 全局 值进行跟踪。它与按 CPU 调频的配置不兼容，因为在这类配置中，不同 CPU 可能观察到不同的系统定时器频率。

启用该选项后，sys_clock_hw_cycles_per_sec() 和时间单位换算都会遵循当前的运行时值。

为了进行异步计时，内核定义了“节拍”（tick）的概念。“节拍”是内核进行所有内部运行时间和超时记账时使用的内部计数单位。中断应尽可能在节拍边界上产生，内核不跟踪不足一个节拍的部分。节拍频率可以通过 CONFIG_SYS_CLOCK_TICKS_PER_SEC 配置。在大多数硬件平台上（即支持设置任意中断超时的平台），默认值预计在 10 kHz 左右，而软件仿真平台和旧式驱动则使用更传统的 100 Hz。

换算

Zephyr 提供了一个列举全面、可控制舍入方式的换算库，覆盖所有时间单位。"ms"（毫秒）、"us"（微秒）、"tick"（节拍）或 "cyc"（周期）中的任何单位都可以换算为其他任何单位。舍入方式可控，每种换算都提供 "floor"（向下舍入到最接近的输出单位）、"ceil"（向上舍入）和 "near"（舍入到最接近值）三种形式。此外，输出精度可以指定为 32 位或 64 位。

例如：k_ms_to_ticks_ceil32() 会把以毫秒为单位的输入值换算为向上取整的节拍数，并返回截断为 32 位精度的结果；k_cyc_to_us_floor64() 会以完整的 64 位精度把测得的周期计数换算为经过的微秒数。换算例程的完整列表请参阅参考文档。

在大多数平台上，各计数器频率互为整数倍，且输出可以容纳在单个字中，这些换算会展开为 2 到 4 个操作的序列，只在确实需要并且被请求时才使用完整精度。

运行时间

内核代表应用程序跟踪系统运行时间（uptime）计数。随时可以通过 k_uptime_get() 获取该值，它返回自系统启动以来的运行时间，单位为毫秒。大多数可移植的应用程序代码应使用这个函数。

不过，内核内部是以 64 位整数节拍计数进行跟踪的。有精确计时需求的应用程序（并且愿意自行换算为可移植的实际时间单位）可以通过 k_uptime_ticks() 访问该计数。

k_uptime_delta() 可用于获取某个参考时间与当前时间之间经过的时间。参考时间会被更新为当前运行时间，以便方便地计算下一次经过的时间。

超时

Zephyr 内核提供了许多带有“超时”参数的 API。从概念上讲，它表示某个事件将发生的时间。例如：

  • 诸如 k_sem_take() 或 k_queue_get() 之类的内核阻塞操作可以指定一个超时，超时到期时若仍无数据可用，例程将返回错误码。

  • 内核 k_timer 对象必须为其持续时间和周期指定延迟。

  • 内核 k_work_delayable API 提供了一个超时参数，指明工作队列项何时被添加到系统队列中。

所有这些值都使用 k_timeout_t 值指定。这是一个不透明的结构体类型，必须使用一系列内核超时宏之一进行初始化。最常用的 K_MSEC 定义相对于当前时间的若干毫秒之后的时间。

对于相对超时，“当前时间”的含义取决于上下文：

  • 在超时回调中调度相对超时时（例如在传给 k_timer_init() 的到期函数中，或在传给 k_work_init_delayable() 的工作处理函数中），“当前时间”是当前正在触发的超时最初被调度的确切时间，即使“实际时间”已经向前推进。这是为了确保在另一个定时器回调中调度的定时器，始终以相对于正在触发的定时器的精确偏移来计算。这样就可以按固定间隔触发，而不会随时间累积系统性的时钟漂移。

  • 在应用程序上下文中调度超时时，“当前时间”是指内核收到超时值时 k_uptime_ticks() 所返回的值。

其他超时初始化方式遵循上述单位约定：K_NSEC()、K_USEC、K_TICKS 和 K_CYC() 分别指定在给定的纳秒数、微秒数、节拍数和周期数之后到期的超时值。

k_timeout_t 值的精度可配置，默认为 32 位。以非节拍单位表示的较大运行时间计数会遇到复杂的回绕语义，因此长时间运行且对时间敏感的应用程序应配置为使用 64 位超时类型。

最后，还可以将超时指定为自系统启动以来的绝对时间。使用 K_TIMEOUT_ABS_MS 初始化的超时会在系统运行时间达到指定值后到期。该 API 同样有纳秒、微秒、周期和节拍版本。

计时的内部实现

超时队列

使用上述 API 指定的所有 Zephyr k_timeout_t 事件都在一个全局事件队列中管理。事件发生时要执行的操作由请求该事件的子系统以回调函数指针的形式提供，同时提供一个 _timeout 跟踪结构体，该结构体通常嵌入在子系统定义的数据结构中（例如 wait_q 结构体，或 k_tid_t 线程结构体）。

注意，通过 k_timeout_t 传入的各种单位，在插入队列时都只换算一次为节拍。内核内部不存在多次换算的步骤，因此无论有多少事件、超时有多长，精度都能保证在节拍级别。

保存该队列的数据结构在构建时通过 CONFIG_TIMEOUT_BACKEND 选项组选择。各后端之间只共享前端（通告路径、SMP 重入处理，以及相对超时与绝对超时的规则）；队列本身由各后端提供，因此集成者可以根据工作负载选择合适的数据结构，而无需修改公共代码。

默认后端 CONFIG_TIMEOUT_BACKEND_DLIST 将事件存放在按到期时间排序的双向链表中，每个事件保存相对于其前一个事件的节拍差值。插入操作相对于挂起超时的数量为 O(N)：对于典型系统中挂起的少量超时来说开销很小，但当大量超时同时存在时，扩展性很差。另外四种后端目前都处于实验阶段，它们以额外的内存或行为差异为代价，换取大规模场景下更快的插入速度：

  • CONFIG_TIMEOUT_BACKEND_MINHEAP 将事件保存在以绝对到期时间为键的二叉最小堆中，使插入和删除的复杂度为 O(log N)。它要求使用 64 位节拍（CONFIG_TIMEOUT_64BIT）和固定容量的堆（CONFIG_TIMEOUT_HEAP_MAX_ENTRIES，溢出会导致致命错误），并且不保证在同一节拍到期的超时的触发顺序。

  • CONFIG_TIMEOUT_BACKEND_WHEEL 是一个分层时间轮，对近期的超时提供 O(1) 的插入和删除，超出范围的超时则放入一个有序溢出链表。它的单事件占用和静态占用都是最大的，不保证同一节拍的触发顺序，并且由于其下一个超时的估计值受时间轮周期限制，会周期性地唤醒处于无节拍空闲状态的 CPU（其他后端没有这一功耗开销）。

  • CONFIG_TIMEOUT_BACKEND_BUCKET 是一个单级分桶差值链表，是时间轮的简化版本。它在一个可调的近期窗口（CONFIG_TIMEOUT_BUCKET_LISTS）内提供 O(1) 插入，超出窗口时退回到有序溢出链表。它同样要求使用 64 位节拍，但与时间轮不同，它保证同一节拍的触发顺序，并且不会增加空闲唤醒开销。

  • CONFIG_TIMEOUT_BACKEND_SKIPLIST 是以绝对到期时间为键的 Pugh 跳表。插入和删除的期望复杂度为 O(log N)，没有容量限制，同一节拍的触发顺序为 FIFO。它要求使用 64 位节拍。每个事件存储 CONFIG_TIMEOUT_SKIPLIST_MAX_LEVEL 个前向指针，因此单事件占用的 RAM 高于差值链表或最小堆。

非默认后端面向同时持有大量超时的系统，尤其是超时集中在近期的系统。对大多数应用程序而言，差值链表仍是合适的默认选择。

定时器驱动

节拍级别的内核计时由定时器驱动驱动。该接口及其运行时所处的加锁环境在 系统定时器驱动 中介绍。

时间片

计时子系统的另一项辅助工作，是向调度器提供节拍计数器，以实现线程的时间片轮转。线程的时间片不能用超时值表示，因为它反映的不是全局的到期时间，而是一个按 CPU 计算的值，在 SMP 环境中需要在每个 CPU 上独立跟踪。

由于可能没有其他硬件可用于驱动时间片轮转，Zephyr 复用了现有的定时器驱动。这意味着，当当前调度的是启用时间片的线程时，传给 sys_clock_set_timeout() 的值可能会被限制为小于当前下一个超时的值。

保留毫秒 API 的子系统

一般来说，这类代码的移植方式与应用程序代码相同。来自用户的毫秒值可以按子系统希望的任何方式处理，然后在交给内核时使用 K_MSEC() 转换为内核超时。

当然，这样做的代价是无法使用新特性，例如更高精度的超时构造器或绝对超时。但对于许多需求简单的子系统来说，这可能是可以接受的。

一个复杂之处是 K_FOREVER。过去可能能够在其毫秒 API 中接受该值的子系统现在不能再这样做了，因为它已不再是整数类型。这类代码需要使用另一个整数值的标记来表示“永久”。当然，K_NO_WAIT 也存在同样的类型安全问题，但由于它（一直以来）只是数值零，因此有一条自然的移植途径。

使用 k_timeout_t 的子系统

理想情况下，接受“超时”参数以指定等待时间的代码应尽可能使用内核原生的抽象。但 k_timeout_t 是不透明的，应用程序需要先对其进行转换才能检查其值。

有些转换很简单。需要检测 K_FOREVER 的代码，只需使用 K_TIMEOUT_EQ() 宏比较不透明结构体是否相等，并进行特殊处理即可。

更复杂的情况是：子系统需要接受一个超时并循环等待其结束，同时执行一些可能需要对底层内核代码进行多次阻塞操作的处理。例如，考虑以下设计：

void my_wait_for_event(struct my_subsys *obj, int32_t timeout_in_ms)
{
    while (true) {
        uint32_t start = k_uptime_get_32();

        if (is_event_complete(obj)) {
            return;
        }

        /* Wait for notification of state change */
        k_sem_take(obj->sem, timeout_in_ms);

        /* Subtract elapsed time */
        timeout_in_ms -= (k_uptime_get_32() - start);
    }
}

这段代码需要检查超时值，而这已不再可行。针对这类情况，新 API 提供了内部例程 sys_timepoint_calc() 和 sys_timepoint_timeout()，用于在任意超时与时间点值之间相互转换，时间点值基于超时到期时的运行时间节拍。因此，这样的循环可以写成：

void my_wait_for_event(struct my_subsys *obj, k_timeout_t timeout)
{
    /* Compute the end time from the timeout */
    k_timepoint_t end = sys_timepoint_calc(timeout);

    do {
        if (is_event_complete(obj)) {
            return;
        }

        /* Update timeout with remaining time */
        timeout = sys_timepoint_timeout(end);

        /* Wait for notification of state change */
        k_sem_take(obj->sem, timeout);
    } while (!K_TIMEOUT_EQ(timeout, K_NO_WAIT));
}

注意，sys_timepoint_calc() 接受特殊值 K_FOREVER 和 K_NO_WAIT，并且对绝对超时和普通超时的处理方式完全相同。反过来，如果创建时间点时使用的是 K_FOREVER 或 K_NO_WAIT，sys_timepoint_timeout() 可能会返回这两个值；如果时间点已经过去，也会返回后者。对于简单的情况，也可以使用 sys_timepoint_expired()。

但使用这些例程的子系统仍需小心。注意，相对超时需要相对于“当前时间”来解释，而这个时间显然是调用 sys_timepoint_calc() 的时间。但用户期望的是他们把超时传给你的那个时间。因此必须注意只调用该函数一次，并尽可能与用户代码中创建超时的时刻同步。它不应作用于“已存储”的超时值，也绝不应在循环中反复调用。
