功能安全需求

简介

安全委员会按照项目功能安全工作的 路线 3s 方法，牵头收集反映实现 实际 状态的需求。其目标 不是 创建新需求来要求为项目增加功能。

需求收集在一个单独的仓库中：需求仓库

需求仓库内容的当前渲染版本可在 Zephyr 项目需求 查看。

Zephyr 项目中需求管理的目标

在开发以及记录已实现或预期的功能时，有效的需求管理至关重要，它确保 Zephyr RTOS 能够实现其预期用途，在其约束条件下可靠运行，并能方便地与硬件平台集成，以及集成到嵌入式软件栈和软件应用层中。

需求管理提供了一种结构化的方法，用于在系统的整个生命周期中捕获、组织和追溯利益相关方的需要和期望。项目文档 中提供的文档已经着重介绍了实现细节，从内核功能到 API 配置选项以及具体模块的行为。虽然这对开发者来说必不可少，但仅依赖底层文档可能导致理解碎片化、可追溯性有限，并且难以扩展或认证使用 Zephyr RTOS 的最终系统。

为了加深这种理解，并为产品负责人、软件架构师、质量管理、功能安全管理和评估人员等不编写代码的角色提供价值，Zephyr 项目需要有描述整体功能、结构和实现约束的更高层次需求。

以下是需求仓库的准则，以及向仓库添加需求时对合适的需求结构和语法的期望。

注意：这些是在需求仓库中创建需求的准则，需求仓库不像发布给 Zephyr 用户的文档那样使用 .rst 编写。要了解更多关于编写文档的准则，请参阅 文档编写指南

范围

需求的初始范围涵盖内核（KERNEL）功能。也欢迎提交非内核功能的需求，但目前不是重点。

管理 Zephyr 需求：结构、工具和语法

仓库中的需求层级

安全工作组评估了一种用需求来补充现有底层描述的合适方法。为此，在现有文档结构之上建立了两级需求结构：最高层的系统需求，用于定义 Zephyr RTOS 作为一个整体的总体能力；以及软件需求，用于将系统需求的期望分解为 RTOS 中各个组件的详细规格。

系统需求

系统需求描述 Zephyr RTOS（此处即“系统”）的行为。它们从高层角度描述 Zephyr RTOS 的功能和约束条件，而不深入功能本身的细节。

系统需求的目的是概览 Zephyr RTOS 当前已实现的特性。

这些需求从功能、性能和接口的角度阐明 RTOS 必须实现的目标，例如确定性的任务调度、中断处理延迟、内存占用限制以及对行业标准的遵从。系统需求是设计决策和确认标准的基础。

要编写这些需求，编写者最好已经对 Zephyr RTOS 项目和/或 RTOS 特有的需求和约束条件有所了解。

软件需求

在系统需求层之下，软件需求将系统级需求细化到更细的粒度。这些组件级需求将系统级的期望分解为 RTOS 中各个组件的详细规格，包括调度器、内存管理器和进程间通信机制等模块。

软件需求描述每个组件的行为、接口和约束条件，确保它们共同实现系统级目标。这些需求定义了该功能应能执行的具体动作以及该功能的行为，使每项需求都能通过测试、分析和/或检查来验证。

这一层级的需求在定义上仍然必须与实现无关。实现层面的定义应放在文档中；如果文档中尚未包含，则需要作为本次需求编写工作的另一项任务补充进去。

需求管理工具链

需求仓库：

需求仓库 体现了 Zephyr 对需求管理的结构化方法，目前侧重于在其目标功能安全认证范围内编写需求，但并不局限于这一范围。

使用该仓库时，请遵循创建分支和提交 PR 的常规 GitHub 工作流程。该仓库的 PR 目前由安全工作组成员审查，至少需要获得以下角色之一的批准才能合并：Zephyr 安全经理（Safety Manager）、Zephyr 安全主席（Safety Chair）或 Zephyr 安全架构师（Safety Architect）。

需求工具：

我们使用 StrictDoc 工具来编写、关联 Zephyr 项目的需求，并渲染出可浏览的 .html 版本

StrictDoc 是一款轻量级的开源工具，用于编写、浏览和导出结构化需求。它支持层级化需求、可追溯性以及便于审查的 HTML 导出。

需求使用 StrictDoc 自己的标记语法编写。

对于喜欢以所见即所得（WYSIWYG）方式编辑的用户，也可以使用 StrictDoc 的本地服务器编辑 StrictDoc 导出的 .html 文件。

要配置你的工具链，请跳转到 需求管理入门 一节。

需求的验证：

新增和修改的需求（即提交到需求仓库的 PR 中的内容）需要通过审查进行验证。审查意见可以在 PR 审查期间直接记录在评论中。需求审查既要考虑技术上的正确性，也要考虑需求必须按照特定标准编写这一形式上的要求。

关于检查清单和形式要求的更多细节，请参阅 功能安全需求检查清单。在 Zephyr 项目的测试中，必须评估实现是否符合需求中描述的功能。

需求语法元素术语表

所有需求都必须使用规定的语法：

在 StrictDoc 中记录的需求的结构

属性

描述

UID

用于识别需求的唯一 ID，由 StrictDoc 自动分配。

STATUS

描述需求的状态：Draft（草稿）、Approved（已批准）、Retired（已废弃）

TYPE

Functional（功能性）、Non-functional（非功能性）

COMPONENT

应实现该需求的组件

REFERENCE

对父需求和/或子需求的引用

TITLE

需求的描述性标题。请使用简短精炼的需求标题。

STATEMENT

需求的描述

USER_STORY

描述该需求的用户故事（可选，仅当它能为需求陈述提供额外价值时才添加）

需求 UID（唯一标识符）的处理

用于管理需求的工具 StrictDoc 负责处理与每项需求关联的唯一标识符（UID）。管理 UID 时，请按以下步骤操作：

  1. 不要为新需求添加需求 UID 和 UID 字段

  2. 完成新需求的编写后，执行：strictDoc manage auto-uid .

  3. 如有需要，使用新分配的 UID 在需求之间建立关联

完成上述操作后，需求即已就绪，可以创建 PR。PR 中的 CI 会检查需求 UID 是否有效以及是否存在重复。如果 PR 中存在重复，需要通过变基（rebase）并重新执行上述步骤来解决。

一致性

所有需求在语言和用词方面都应保持一致。（参见：Syntax）

还建议查看 需求仓库 中已有的需求，以及该仓库 PR 中正在进行的讨论，以便体会在这一背景下怎样做是合理的。

需求仓库的 PR

  • 遵守 Zephyr 项目的 贡献指南。

    • 前提是这些准则适用于需求仓库。

  • 避免创建同时包含琐碎变更和非琐碎变更的大型提交。

  • 避免在同一个提交中既移动又修改需求。

良好需求的特征

  • 无歧义

  • 可验证（例如，功能性需求可测试）

  • 清晰（简洁、简短、简单、精确）

  • 正确

  • 易于理解

  • 可行（现实、可能实现）

  • 独立

  • 原子性

  • 必要

  • 与实现无关（抽象）

需求集合的特征

  • 完整

  • 一致

  • 无冗余

语法

  • 建议使用公认的需求语法。

    • EARS 是一个很好的参考，尤其适合不熟悉需求编写的人。

    • 只要满足上述需求特征，也接受其他格式。
