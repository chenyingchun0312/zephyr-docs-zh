概述

USB 设备协议栈是位于 USB 设备控制器驱动与 USB 设备类驱动或用户应用程序之间、与硬件无关的接口。它移植自 LPCUSB 设备协议栈，并随着时间推移不断修改和扩展。它提供以下功能：

  • 使用设备控制器驱动提供的 USB 设备控制器驱动 API（已弃用） 与 USB 设备控制器交互。

  • 响应标准设备请求并返回标准描述符，本质上是处理“第 9 章”的内容，具体而言是通用串行总线规范 2.0 版表 9-3 中的标准设备请求。

  • 提供供 USB 设备类或用户应用程序使用的编程接口。相关 API 在 include/zephyr/usb/usb_device.h 中描述

备注

USB 设备支持 API（已弃用） 中列出的所有 API 以及依赖它们的函数均已弃用，并将在 v4.5.0 中移除。请改用新的 USB 设备支持，其 API 见 USB 设备支持 API。

支持的 USB 类

Audio

Audio 类目前有一个实验性实现。它遵循规范 1.00 版（bcdADC 0x0100），且仅支持同步（synchronous）同步类型。请参阅示例 Legacy USB Audio microphone & headphones 和 Legacy USB Audio headset。

Bluetooth HCI USB 传输层

Bluetooth HCI USB 传输层的实现使用 HCI RAW 通道 向主机暴露 HCI 接口。它与 Bluetooth 规范中的描述不完全一致，只包含一个具有以下端点配置的接口：

  • 通过控制端点传输 HCI 命令（仅主机到设备方向）

  • 通过中断 IN 端点传输 HCI 事件

  • 通过一个批量 IN 端点和一个批量 OUT 端点传输 ACL 数据

由于 Bluetooth 不支持语音通道，用于语音通道的第二个接口尚未实现。在 Linux 下，如果 HCI USB 传输层是配置中唯一的接口，这并不是大问题，btusb 驱动不会尝试占用第二个（同步传输）接口。但如果 HCI USB 用在复合配置中且是第一个接口，Linux 的 btusb 驱动会同时占用第一个和下一个接口，导致其他复合功能无法工作。因此，HCI USB 不应在复合配置中使用。新 USB 支持中的实现已修复了此问题。

请参阅示例 HCI USB。

CDC ACM

CDC ACM 类在 Zephyr 中被用作多个子系统的后端。然而，对于缺乏经验的用户来说，配置它可能并不容易。下面介绍不同的使用场景和一些常见陷阱。

面向 CDC ACM 用户的接口是 通用异步收发器（UART） 驱动 API。但它在行为上与真实的 UART 控制器有两个重要区别：

  • 只有在 USB 设备协议栈初始化并启动之后才能传输数据，在此之前的所有数据都会被丢弃

  • 即使设备已连接到主机，主机端仍需要有一个应用程序来请求数据

  • CDC ACM 的 poll out 实现遵循该 API，仅当启用了 hw-flow-control 属性且在非 ISR 上下文中调用时，才会在 TX 环形缓冲区已满时阻塞。

CDC ACM UART 的设备树 compatible 属性为 zephyr,cdc-acm-uart。当启用 USB 设备支持且设备树源文件中存在兼容节点时，会自动选中 CDC ACM 支持。如有需要，可以通过 CONFIG_USB_CDC_ACM 显式禁用 CDC ACM 支持。大约可以定义和使用四个 CDC ACM UART 实例，具体受控制器支持的最大端点数量限制。

CDC ACM UART 节点应是 USB 设备控制器节点的子节点。由于各厂商对控制器节点的命名各不相同，而我们的示例和应用程序应尽可能通用，默认 USB 设备控制器通常被分配 zephyr_udc0 节点标签。CDC ACM UART 通常在设备树覆盖文件中描述，如下所示：

&zephyr_udc0 {
        cdc_acm_uart0: cdc_acm_uart0 {
                compatible = "zephyr,cdc-acm-uart";
                label = "CDC_ACM_0";
        };
};

示例 USB CDC ACM UART sample 也有类似的覆盖文件。由于其中没有特殊属性，用设备树描述 CDC ACM UART 似乎有些多余。使用设备树的目的在于，让应用程序可以方便地在真实 UART 控制器和 CDC ACM UART 之间互换。

通过 CDC ACM UART 使用控制台

利用上面的 CDC ACM UART 节点以及 chosen 节点的 zephyr,console 属性，可以指定将 CDC ACM UART 用于控制台。示例 Console over USB CDC ACM 使用了类似的覆盖文件。

/ {
        chosen {
                zephyr,console = &cdc_acm_uart0;
        };
};

&zephyr_udc0 {
        cdc_acm_uart0: cdc_acm_uart0 {
                compatible = "zephyr,cdc-acm-uart";
                label = "CDC_ACM_0";
        };
};

建议应用程序在使用控制台之前等待 DTR 信号：

const struct device *const dev = DEVICE_DT_GET(DT_CHOSEN(zephyr_console));
uint32_t dtr = 0;

if (usb_enable(NULL)) {
        return;
}

while (!dtr) {
        uart_line_ctrl_get(dev, UART_LINE_CTRL_DTR, &dtr);
        k_sleep(K_MSEC(100));
}

printk("nuqneH\n");

将 CDC ACM UART 用作后端

与控制台示例类似，可以通过设置 chosen 节点 属性，将 CDC ACM UART 配置为其他子系统的后端。

以下列出几个 Zephyr 专用的 chosen 属性，可用于为子系统或应用程序选择 CDC ACM UART 作为后端：

  • zephyr,bt-c2h-uart 用于 Bluetooth，示例参见 HCI UART

  • zephyr,ot-uart 用于 OpenThread，示例参见 OpenThread co-processor

  • zephyr,shell-uart 被 Shell 用作串行后端，示例参见 samples/subsys/shell/shell_module

  • zephyr,uart-mcumgr 由示例 SMP server 使用

缓解 POSIX tty 默认 ECHO 问题

Linux 等 POSIX 系统默认在 tty 设备上启用 ECHO。如果不需要回显，主机端应用程序可以在 tty 设备上调用 open()，然后调用 ioctl()（最好通过 tcsetattr()）来禁用回显。遗憾的是，open() 和 ioctl() 之间存在固有的竞争窗口：此期间 ECHO 处于启用状态，收到的任何字符（即使主机应用程序没有调用 read()）都会被回显。当 CDC ACM 端口另一端没有任何真实 UART 时，这个问题尤其明显，因为不存在由波特率带来的额外延迟。

为缓解该问题，Zephyr 的 CDC ACM 实现在设备被配置后，会在 IN 端点上预备一个 ZLP（零长度包）。当主机读取该 ZLP 时（这几乎是主机应用程序已打开 tty 设备的最佳指示），Zephyr 会在发送真正的有效载荷之前强制延迟 CONFIG_CDC_ACM_TX_DELAY_MS 毫秒。这应能为第一个（且仅第一个）打开 tty 设备的应用程序留出足够时间，在不需要回显时禁用 ECHO。如果完全不需要 CDC ACM 设备回显，最好设置 udev 规则，在设备连接后立即禁用 ECHO。

当 CDC ACM 实例用于 Zephyr Shell 时，ECHO 尤其不受欢迎，因为回送给 Shell 的颜色控制字符会被解释为（无效）命令，用户最终会看到乱码。虽然 minicom 默认会禁用 ECHO，但在带复位退出时，它会将 termios 设置恢复为进入时的状态。因此，如果 minicom 是第一个打开 tty 设备的应用程序，带复位退出会重新启用 ECHO，从而给下一个应用程序造成问题（这无法在 Zephyr 端缓解）。为避免该问题，建议退出 minicom 时不复位，或在启动 minicom 之前禁用 ECHO。

DFU

USB DFU 类的实现与 设备固件升级 和 MCUBoot API 紧密耦合。这意味着目标平台必须支持 Flash 镜像 API。

请参阅示例 Legacy USB DFU (Device Firmware Upgrade)。

USB 人机接口设备（HID）支持

HID 支持滥用了 设备驱动模型，仅仅是为了让应用程序能够使用 device_get_binding()。注意，并不存在真正意义上的 HID 设备 API，接口改由 hid_ops 提供。默认实例名为 HID_n，其中 n 可以是 {0, 1, 2, ...}，取决于 CONFIG_USB_HID_DEVICE_COUNT。

每个 HID 实例都需要一个 HID 报告描述符。必须使用 usb_hid_register_device() 注册与核心交互的接口以及报告描述符。

由于 USB HID 规范不只被 USB 子系统使用，USB HID API 参考分为两部分：人机接口设备（HID） 和 USB HID 类 API（已弃用）。应使用 人机接口设备（HID） 中的 HID 辅助宏来编写 HID 报告描述符。宏名称与 USB HID 规范中使用的名称一致。

对于 HID 类接口，每个实例都需要一个 IN 中断端点，OUT 中断端点则是可选的。因此，hid_ops 的最低实现要求是提供 int_in_ready 回调。

#define REPORT_ID               1
static bool configured;
static const struct device *hdev;

static void int_in_ready_cb(const struct device *dev)
{
        static uint8_t report[2] = {REPORT_ID, 0};

        if (hid_int_ep_write(hdev, report, sizeof(report), NULL)) {
                LOG_ERR("Failed to submit report");
        } else {
                report[1]++;
        }
}

static void status_cb(enum usb_dc_status_code status, const uint8_t *param)
{
        if (status == USB_DC_RESET) {
                configured = false;
        }

        if (status == USB_DC_CONFIGURED && !configured) {
                int_in_ready_cb(hdev);
                configured = true;
        }
}

static const uint8_t hid_report_desc[] = {
        HID_USAGE_PAGE(HID_USAGE_GEN_DESKTOP),
        HID_USAGE(HID_USAGE_GEN_DESKTOP_UNDEFINED),
        HID_COLLECTION(HID_COLLECTION_APPLICATION),
        HID_LOGICAL_MIN8(0x00),
        HID_LOGICAL_MAX16(0xFF, 0x00),
        HID_REPORT_ID(REPORT_ID),
        HID_REPORT_SIZE(8),
        HID_REPORT_COUNT(1),
        HID_USAGE(HID_USAGE_GEN_DESKTOP_UNDEFINED),
        HID_INPUT(0x02),
        HID_END_COLLECTION,
};

static const struct hid_ops my_ops = {
        .int_in_ready = int_in_ready_cb,
};

int main(void)
{
        int ret;

        hdev = device_get_binding("HID_0");
        if (hdev == NULL) {
                return -ENODEV;
        }

        usb_hid_register_device(hdev, hid_report_desc, sizeof(hid_report_desc),
                                &my_ops);

        ret = usb_hid_init(hdev);
        if (ret) {
                return ret;
        }

        return usb_enable(status_cb);
}

如果应用程序希望通过 OUT 中断端点接收输出报告，必须启用 CONFIG_ENABLE_HID_INT_OUT_EP 并提供 int_out_ready 回调。其缺点是 CONFIG_ENABLE_HID_INT_OUT_EP 或 CONFIG_HID_INTERRUPT_EP_MPS 等 Kconfig 选项会作用于所有实例。新 USB 支持中的 HID 类实现将修复这一设计问题。

请参阅示例 USB HID mouse。

大容量存储类（Mass Storage Class）

MSC 遵循仅批量传输（Bulk-Only Transport）规范，并使用 磁盘访问 访问 RAM 磁盘、基于 Flash 分区仿真的块设备或 SD 卡，并将其暴露给主机。同一时间只能导出一个磁盘实例。

实现所使用的磁盘由 CONFIG_MASS_STORAGE_DISK_NAME 设置，它应与应用程序要暴露给主机的磁盘访问驱动所用的名称相同。Flash、RAM 和 SDMMC/MMC 磁盘驱动使用节点属性 disk-name 设置磁盘名称。

对于基于 Flash 分区仿真的块设备，所使用的 Flash 分区和 Flash 磁盘必须在设备树中描述。如果开发板层面已经描述了存储分区，应用程序的设备树覆盖文件还必须先删除 storage_partition 节点。CONFIG_MASS_STORAGE_DISK_NAME 应与 disk-name 属性相同。

/delete-node/ &storage_partition;

&mx25r64 {
        partitions {
                compatible = "fixed-partitions";
                #address-cells = <1>;
                #size-cells = <1>;

                storage_partition: partition@0 {
                        label = "storage";
                        reg = <0x00000000 0x00020000>;
                };
        };
};

/ {
        msc_disk0 {
                compatible = "zephyr,flash-disk";
                partition = <&storage_partition>;
                disk-name = "NAND";
                cache-size = <4096>;
        };
};

disk-property "NAND" 可能令人困惑，但这只是某些文件系统识别磁盘的方式。因此，如果应用程序还要访问所暴露磁盘上的文件系统，应使用默认名称，请参阅示例 USB Mass Storage。

网络

有三种工作方式类似的实现，它们在远端（USB 主机）与 Zephyr 网络支持之间提供虚拟以太网连接。

  • CDC ECM 类，通过 CONFIG_USB_DEVICE_NETWORK_ECM 启用

  • CDC EEM 类，通过 CONFIG_USB_DEVICE_NETWORK_EEM 启用

  • RNDIS 支持，通过 CONFIG_USB_DEVICE_NETWORK_RNDIS 启用

请参阅示例 Legacy USB device netusb sample。

使用 RNDIS 支持的应用程序应启用 CONFIG_USB_DEVICE_OS_DESC，以便在运行 Microsoft Windows 操作系统的主机上获得更好的用户体验。

二进制设备对象存储（BOS）支持

可以通过 Kconfig 选项 CONFIG_USB_DEVICE_BOS 启用 BOS 处理。该选项还会将设备描述符的 bcdUSB 改为 0210。应用程序应使用 usb_bos_register_cap() 注册能力描述符（Capability Descriptor）等描述符。已注册的描述符会被添加到根 BOS 描述符中，并由协议栈处理。

请参阅示例 Legacy WebUSB。

接口号和端点地址分配

在 USB 术语中，function（功能）是向主机提供某种能力的设备，例如实现键盘的 HID 类设备。一个功能包含一组 interfaces（接口），且至少需要一个接口。接口可以包含设备 endpoints（端点）；例如，实现 HID 类设备至少需要一个输入端点，而实现 USB DFU 类则不需要任何端点。组合了多个功能的 USB 设备是多功能 USB 设备，例如 HID 类设备与 CDC ACM 设备的组合。

借助 Zephyr RTOS 的 USB 支持，可以将内置的 USB 类/功能或用户自定义实现进行各种组合，限制在于可用的设备端点数量。每个设备端点都可以被唯一寻址。端点地址由端点方向和端点号（一个四位的值）组合而成。端点号 0 用于默认控制方式，以初始化和配置 USB 设备。按照规范，另外最多还有 15 IN 和 15 OUT 个设备端点可供功能使用。实际数量取决于所用的设备控制器。并非所有控制器都支持最大端点数量和所有端点类型。例如，某个设备控制器可能支持一个 IN 和一个 OUT 同步端点，但只能使用端点号 8，因此端点地址为 0x88 和 0x08。此外，有的控制器可以在同一端点号上同时使用 IN/OUT 端点（例如中断 IN 端点 0x81 和批量 OUT 端点 0x01），而另一些控制器每个端点号只能处理一个端点。接口数量、接口关联、端点类型和地址等信息通过接口描述符、接口专用描述符和端点描述符提供给主机。

特定功能的主机驱动使用接口描述符和端点描述符来获取端点地址、类型和其他属性。这使得功能主机驱动可以是通用的，例如可以构建由一个或多个 CDC ACM 以及一个或多个 CDC ECM 类实现组成的多功能设备，而无需专用驱动。

Zephyr RTOS 中内置 USB 类/功能实现的接口描述符和端点描述符，通常按升序分配了默认的接口号和端点地址。初始化期间，默认接口号可能会根据给定配置中的接口数量重新分配。端点地址则会根据控制器能力（因为并非每个控制器都能支持某些端点组合）以及给定配置中的接口数量重新分配。这也意味着 Zephyr RTOS 中设备端的类/功能必须在运行时检查接口描述符和端点描述符的实际值。该机制还使我们能够提供通用示例和通用多功能示例，它们只受控制器所提供资源（例如端点数量和端点 FIFO 大小）的限制。

某些特定功能的主机驱动（例如 Linux 内核中的驱动）可能不读取接口描述符和端点描述符来检查接口号或端点地址，而是使用硬编码的值。因此，这类主机驱动无法以通用方式使用，也就是说，无法在不同的设备控制器上、或在与其他功能组合的不同设备配置下使用。这也可能是因为该驱动是为特定硬件设计的，并不打算用于该硬件的克隆品。反之，如果驱动本质上是通用的、应当适用于不同的硬件变体，那么它就不得使用硬编码的接口号和端点地址。Zephyr RTOS 中无法禁用端点重新分配，这可能使你无法实现硬件克隆固件。如有可能，应修正主机驱动的实现，使其使用接口描述符和端点描述符中的值。

在 native_sim 中通过 USBIP 测试

可以使用通过 USBIP 实现的虚拟 USB 控制器来测试 USB 设备协议栈。按照常规构建流程，为 native_sim 配置构建 USB 示例。

使用以下命令运行构建好的示例：

west build -t run

在终端窗口中运行以下命令列出 USB 设备：

$ usbip list -r localhost
Exportable USB devices
======================
 - 127.0.0.1
        1-1: unknown vendor : unknown product (2fe3:0100)
           : /sys/devices/pci0000:00/0000:00:01.2/usb1/1-1
           : (Defined at Interface level) (00/00/00)
           :  0 - Vendor Specific Class / unknown subclass / unknown protocol (ff/00/00)

在终端窗口中运行以下命令挂接 USB 设备：

$ sudo usbip attach -r localhost -b 1-1

USB 设备应已连接到你的 Linux 主机，可以使用以下命令进行验证：

$ sudo usbip port
Imported USB devices
====================
Port 00: <Port in Use> at Full Speed(12Mbps)

USB 厂商标识符和产品标识符

Zephyr 项目的 USB 厂商 ID（Vendor ID）为 0x2FE3。厂商将 Zephyr USB 设备支持集成到自己的产品中时，不得使用该 USB 厂商 ID。

每个 USB sample 都有自己唯一的产品 ID（Product ID）。USB 维护者（如果已指定）或 Zephyr 技术指导委员会（Technical Steering Committee）可以根据理由充分且有文档记录的申请，分配其他 USB 产品 ID。
