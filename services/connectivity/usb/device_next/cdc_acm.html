USB 设备 CDC ACM

USB 设备协议栈提供的 CDC ACM 功能只实现了抽象控制模型（Abstract Control Model）串口仿真。顾名思义，它的唯一用途是仿真串行线路。大多数现代操作系统都应开箱即用地支持它。

CDC ACM 功能在主机端和设备端都表现为一个串行接口，而面向用户或应用程序的接口是 通用异步收发器（UART） 驱动 API。这样，已经使用 UART API 的应用程序无需修改负责数据通信的代码，即可使用 CDC ACM 功能提供的串行接口，只需额外进行配置并初始化 USB 设备协议栈。

CDC ACM UART 配置

与真实的 UART 控制器一样，虚拟 CDC ACM UART 也在设备树中描述。CDC ACM UART 的设备树 compatible 属性为 zephyr,cdc-acm-uart。

当启用 USB 设备支持且设备树源文件中存在兼容节点时，会自动选中 CDC ACM 支持。如有需要，可以通过 CONFIG_USBD_CDC_ACM_CLASS 显式禁用 CDC ACM 支持。可创建的 CDC ACM 实例数量取决于 USB 设备控制器支持的端点数量。每个 CDC ACM 实例需要三个端点：两个批量端点（一个 IN、一个 OUT）和一个 MaxPacketSize 为 16 的中断 IN 端点。CDC ACM 节点可以使用 label 属性在主机端区分不同的接口。下面是设备树覆盖文件的示例。

&zephyr_udc0 {
        cdc_acm_uart0: cdc_acm_uart0 {
                compatible = "zephyr,cdc-acm-uart";
                label = "CDC_ACM_0";
        };
};

应用程序在使用 CDC ACM UART 之前，可能需要等待 DTR 信号。关于如何实现该功能，请参阅 USB CDC ACM UART sample。

备注

要与主机通信，除了 UART 配置之外，应用程序还必须启用 USB 设备协议栈，相关内容请参阅 如何配置和启用 USB 设备支持，并仔细阅读下一章。对于从旧版协议栈迁移的用户和应用程序，这是唯一需要调整的部分。

将 CDC ACM UART 用作串行后端

使用上面的示例和 zephyr,console chosen 节点属性，可以将 CDC ACM UART 配置为控制台设备。

/ {
        chosen {
                zephyr,console = &cdc_acm_uart0;
        };
};

&zephyr_udc0 {
        cdc_acm_uart0: cdc_acm_uart0 {
                compatible = "zephyr,cdc-acm-uart";
                label = "CDC_ACM_0";
        };
};

与上例中将控制台配置为使用 CDC ACM UART 的方式相同，可以使用 zephyr,shell-uart chosen 节点属性将 Shell 配置为使用 CDC ACM UART 作为串行后端。请参阅示例 Custom Shell module 和 chosen 节点文档。

由于用作串行后端的场景非常常见，且 CDC ACM UART 在运行时无需任何配置，协议栈提供了一个辅助功能，用于执行 如何配置和启用 USB 设备支持 中描述的步骤。该辅助功能通过 CONFIG_CDC_ACM_SERIAL_INITIALIZE_AT_BOOT 启用，会以单个 CDC ACM 实例初始化 USB 设备协议栈。示例 Console over USB CDC ACM 演示了其用法。

像 nRF52840 Dongle 这类没有调试适配器、但带有 USB 设备控制器，并希望将 CDC ACM UART 用作日志和 Shell 默认串行后端的开发板，也应使用 CONFIG_CDC_ACM_SERIAL_INITIALIZE_AT_BOOT。由于该配置对任何开发板都相同，代码树中提供了通用的 devicetree file 和 Kconfig file，必须在开发板的设备树和 Kconfig.defconfig 文件中包含它们。

在应用程序中使用 CDC ACM UART

CDC ACM 实现了一个虚拟 UART 控制器，提供中断驱动 UART API 和轮询 UART API，暂不支持 ASYNC API。如果应用程序要通过 CDC ACM UART 通信，推荐使用中断驱动 UART API。理解 API 文档至关重要，此外下面还给出一些说明。

中断驱动 UART API

CDC ACM UART 的实现在内部使用两个环形缓冲区，它们承担 中断驱动 API 中 TX/RX FIFO（TX/RX 缓冲区）的功能。

如 中断驱动 API 所述，函数 uart_irq_update()、uart_irq_is_pending()、uart_irq_rx_ready()、uart_irq_tx_ready()、uart_fifo_read() 和 uart_fifo_fill() 应在中断处理函数中调用，参见 uart_irq_callback_user_data_set()。为防止未定义行为，这些函数的实现会检查自身的调用上下文，如果不是在中断处理函数中调用则返回失败。

此外，如 UART API 所述，uart_irq_is_pending()、uart_irq_rx_ready() 和 uart_irq_tx_ready() 只能在 uart_irq_update() 之后调用。

简化来说，应用程序的中断处理函数大致如下：

static void interrupt_handler(const struct device *dev, void *user_data)
{
        while (true) {
                uart_irq_update(dev);

                if (uart_irq_is_pending(dev) <= 0) {
                        break;
                }

                if (uart_irq_rx_ready(dev)) {
                        int len;
                        int n;

                        /* ... */
                        n = uart_fifo_read(dev, buffer, len);
                        /* ... */
                }

                if (uart_irq_tx_ready(dev)) {
                        int len;
                        int n;

                        /* ... */
                        n = uart_fifo_fill(dev, buffer, len);
                  /* ... */
                }
        }
}

所有这些函数都不直接依赖于 USB 设备的状态。填充 TX FIFO 并不意味着数据正在发送到主机；成功读取 RX FIFO 也不意味着设备仍与主机连接。如果 TX FIFO 中有空间且 TX 中断已启用，uart_irq_tx_ready() 就会成功。如果 RX FIFO 中有数据且 RX 中断已启用，uart_irq_rx_ready() 就会成功。函数 uart_irq_tx_complete() 尚未实现。

轮询 UART API

CDC ACM 的 poll out 实现遵循 轮询 API，仅当启用了 hw-flow-control 属性且在非 ISR 上下文中调用时，才会在 TX FIFO 已满时阻塞。
