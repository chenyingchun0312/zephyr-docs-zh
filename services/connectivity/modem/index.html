调制解调器模块

该服务提供与调制解调器通信所需的模块。

调制解调器是独立的设备，实现了执行射频（Radio-Frequency，RF）通信所需的硬件和软件，包括 GNSS、蜂窝、WiFi 等。

各调制解调器模块通过数据输入/数据输出管道动态互连，因而可以独立测试，并且非常灵活，确保了稳定性和可扩展性。

调制解调器管道

该模块用于以线程安全的方式，对通过多种机制（如 UART 和 CMUX DLCI 通道）进行的数据输入/数据输出通信进行抽象。

调制解调器后端内部会包含一个 modem_pipe 结构体实例，以及抽象其底层机制所需的各种缓冲区和其他结构体。

调制解调器后端在初始化时会返回指向其内部 modem_pipe 结构体的指针，之后通过调制解调器管道 API 使用该指针与后端交互。

modem_pipe

Related code samples

  • AT Command Client在控制台与调制解调器之间建立双向 UART 桥接，用于 AT 命令通信。

调制解调器 PPP

该模块定义一个 L2 PPP 网络接口（见 L2 层管理），并将其绑定到调制解调器后端。L2 PPP 接口负责发送和接收网络数据包。这些网络数据包在通过调制解调器后端传输之前，必须封装成 PPP 帧。该模块负责完成这一封装。

modem_ppp

调制解调器 CMUX

该模块是遵循 3GPP 27.010 规范的 CMUX 实现。CMUX 是一种多路复用协议，支持多个双向数据流，这些数据流称为 DLCI 通道。该模块连接到单个调制解调器后端，并对外提供多个调制解调器后端，每个后端代表一个 DLCI 通道。

该协议定义了简单的成帧方式，用于将每个 DLC 拆分成小的数据块。

Zephyr 实现了基本帧类型，其 MTU 大小可在构建时配置。

对于支持 CMUX 省电命令（Power Saving Command，PSC）的调制解调器，该模块还利用该命令实现了省电功能。更多详细信息，请参阅下文的 CMUX 省电 一节。

modem_cmux

调制解调器管道链接（pipelink）

该模块用于在全局范围内共享调制解调器管道，目的是将设备驱动中调制解调器管道的创建和设置与这些管道的使用者解耦。有关如何在设备驱动与应用程序之间使用调制解调器管道链接的示例，请参阅 drivers/modem/modem_at_shell.c 和 drivers/modem/modem_cellular.c。

modem_pipelink

调制解调器 chat

该模块实现了与调制解调器之间基于脚本的 AT 命令通信。AT 命令被组织成脚本，每个脚本是一系列命令-响应交互。该模块通过调制解调器管道发送命令字符串，然后等待与某个预期模式相匹配的响应。找到匹配项后，会调用一个可选的回调，并传入解析得到的参数。

脚本在构建时使用 MODEM_CHAT_SCRIPT_DEFINE 和 MODEM_CHAT_SCRIPT_CMDS_DEFINE 宏定义。每个脚本条目将一个请求字符串与一个或多个 modem_chat_match 模式配对。匹配模式支持通过指定分隔符（例如 ","）来解析参数，从而可以方便地从 +CSQ: 20,99 这类响应中提取字段。

除了脚本化的交互之外，该模块还会持续监视数据流中的非请求响应，即调制解调器在没有先收到命令的情况下发送的消息（例如 +CEREG: 网络注册状态更新）。这些响应由一组单独的匹配模式处理，这些模式在初始化 chat 实例时注册。

chat 模块可以连接到任意调制解调器管道，因此既可以通过原始 UART 后端通信，也可以通过 CMUX DLCI 通道通信，两者可以互换。

modem_chat

蜂窝调制解调器

通用蜂窝调制解调器驱动 drivers/modem/modem_cellular.c 将上述所有模块组合在一起，实现了一个完整的、与硬件无关的蜂窝数据连接。它提供一个标准的 Zephyr 网络接口，使应用程序无需任何调制解调器专用代码即可使用 BSD 套接字 API。

架构概览

该驱动将各调制解调器模块组装成分层的管道架构：

  1. UART 后端：一个 modem_backend_uart 实例提供最底层的调制解调器管道。它将物理 UART 外设抽象为调制解调器管道 API，执行线程安全的、中断驱动的传输。

  2. CMUX：modem_cmux 实例连接到 UART 管道，并按照 3GPP 27.010 规范将其复用为两个 DLCI 通道。

  3. DLCI 通道 1（数据）：该管道在初始化期间承载 AT 命令流量，在连接建立后则承载 PPP 成帧的 IP 数据。

  4. DLCI 通道 2（命令）：在数据连接处于活动状态时，该管道专用于 AT 命令流量，使驱动能够在不中断数据流的情况下查询信号质量、注册状态和其他参数。

  5. 调制解调器 chat：一个 modem_chat 实例执行 AT 命令脚本。在 CMUX 启动之前，它直接连接到 UART 管道；之后它会先切换到 DLCI 1 执行初始化脚本，再切换到 DLCI 2 进行周期性监视。

  6. 调制解调器 PPP：一个 modem_ppp 实例将 Zephyr IP 数据包封装为 PPP 帧，并通过 DLCI 1 发送。在接收方向上，它会去除 PPP 帧封装，并将数据包交给网络协议栈。

同时使用两个 DLCI 通道是关键所在：调制解调器可以在 DLCI 1 上全速传输 IP 数据，而驱动可以继续在后台通过 DLCI 2 交换 AT 命令。

连接生命周期

该驱动围绕一个内部状态机构建，该状态机依次经历以下阶段：

上电和硬件复位

驱动会对调制解调器的复位和电源 GPIO（如果在设备树中定义了）施加脉冲，并等待调制解调器开始响应。

初始 AT 配置

调制解调器 chat 模块直接连接到 UART 管道，并运行该调制解调器专用的 init_chat_script。该脚本通常会关闭回显，查询 IMEI、型号和固件版本，并配置非请求响应的上报。此阶段的所有通信都是通过 UART 进行的普通 AT 通信，CMUX 尚未启用。

启动 CMUX

初始化脚本执行成功后，驱动会发送 AT+CMUX 命令，将调制解调器切换到多路复用模式。CMUX 模块连接到 UART 管道，并打开 DLCI 1 和 DLCI 2。从此时起，所有通信都在 CMUX 帧内进行。

APN 配置和拨号

驱动将调制解调器 chat 连接到 DLCI 1，先运行一个动态构建的 APN 脚本（AT+CGDCONT），再运行拨号脚本（ATD*99# 或等效命令）。成功后，调制解调器在 DLCI 1 上进入数据模式。

数据连接

调制解调器 PPP 模块连接到 DLCI 1 管道，调制解调器 chat 则切换到 DLCI 2。一旦 +CEREG（或 +CREG / +CGREG）非请求响应表明调制解调器已在网络上注册，驱动就会调用 net_if_carrier_on()。

此时，Zephyr 网络协议栈会在 DLCI 1 上协商建立 PPP 会话，应用程序即可正常使用套接字。与此同时，DLCI 2 上的周期性 chat 脚本会监视信号质量和注册状态。

关机

驱动会运行关机脚本，并对断电 GPIO 施加脉冲，使调制解调器正常断电。状态机随后返回空闲状态。

添加对新调制解调器的支持

通用蜂窝驱动使用通过设备树 compatible 绑定及相关 chat 脚本提供的、针对每种调制解调器的配置。添加新的调制解调器需要以下三项内容：

  1. 一个包含通用蜂窝调制解调器基础绑定的设备树绑定。

  2. chat 脚本，定义用于初始化、拨号、周期性监视以及（可选的）关机的 AT 命令序列。

  3. 一个将 chat 脚本与硬件配置关联起来的设备实例化宏。

驱动会自动处理所有管道连接、CMUX 管理、PPP 成帧和状态机逻辑。

已支持的调制解调器

drivers/modem/modem_cellular.c 已支持以下调制解调器：

  • Fibocom LE250

  • Quectel BG95, BG96

  • Quectel EG25-G, EG800Q

  • SIMCom SIM7080, A76xx

  • u-blox SARA-R4, SARA-R5, LARA-R6

  • Sierra Wireless HL7800

  • Telit ME910G1, ME310G1, LE910C1 Thread-x, LEx10Q1

  • Nordic Semiconductor nRF91 SLM

  • Sequans GM02S

每种已支持的调制解调器都使用同一组宏（MODEM_CHAT_SCRIPT_CMDS_DEFINE、MODEM_CHAT_SCRIPT_DEFINE、MODEM_CELLULAR_DEFINE_INSTANCE 等）定义。有关初始化、拨号、周期性和关机 chat 脚本的完整示例，请参阅 drivers/modem/modem_cellular.c。所有调制解调器共享的通用基础设备树属性记录在 dts/bindings/modem/zephyr,cellular-modem-device.yaml 中。

树外调制解调器

驱动的宏和数据结构通过 include/zephyr/drivers/modem/modem_cellular.h 导出，因此可以在 Zephyr 源码树之外（例如在应用程序源码中）定义一个全新的调制解调器，而无需修改任何上游文件。这对于针对特定用例微调 AT 命令序列，或者在提交到上游之前开发对新调制解调器的支持非常有用。

首先创建一个包含通用基础绑定的设备树绑定，然后使用 modem_cellular.h 中的宏编写驱动源文件。只需要以下三个文件。

设备树绑定：app/dts/bindings/my,modem.yaml：

compatible: "my,modem"

include: zephyr,cellular-modem-device.yaml

设备树覆盖文件（overlay）：app.overlay（部分）：

&uart30 {
    modem: modem {
        compatible = "my,modem";
        status = "okay";
        mdm-power-gpios = <&gpio1 13 GPIO_ACTIVE_HIGH>;
    };
};

驱动源文件：app/src/my_modem.c：

#include <zephyr/drivers/modem/modem_cellular.h>
#include <zephyr/device.h>

MODEM_CELLULAR_COMMON_CHAT_MATCHES();
MODEM_CHAT_MATCHES_DEFINE(my_modem_unsol,
    MODEM_CELLULAR_COMMON_UNSOL_MATCHES);

/* Init script — configure the modem, enable unsolicited LTE
 * registration notifications, then switch to CMUX.
 */
MODEM_CHAT_SCRIPT_CMDS_DEFINE(init_chat_script_cmds,
    MODEM_CHAT_SCRIPT_CMD_RESP("ATE0",              ok_match),
    MODEM_CHAT_SCRIPT_CMD_RESP("AT+CEREG=1",        ok_match),
    MODEM_CHAT_SCRIPT_CMD_RESP("AT+CMUX=0,0,5,127", ok_match));

MODEM_CHAT_SCRIPT_DEFINE(init_chat_script, init_chat_script_cmds,
    abort_matches, modem_cellular_chat_callback_handler, 1);

/* Dial script — enable the radio and open data mode */
MODEM_CHAT_SCRIPT_CMDS_DEFINE(dial_chat_script_cmds,
    MODEM_CHAT_SCRIPT_CMD_RESP("AT+CFUN=1", ok_match),
    MODEM_CHAT_SCRIPT_CMD_RESP("ATD*99#",   connect_match));

MODEM_CHAT_SCRIPT_DEFINE(dial_chat_script, dial_chat_script_cmds,
    dial_abort_matches, modem_cellular_chat_callback_handler, 60);

static const struct modem_cellular_vendor_config my_modem_vendor = {
    .scripts = {
        .init = &init_chat_script,
        .dial = &dial_chat_script,
    },
    .unsol_matches = {
        .matches = my_modem_unsol,
        .size = ARRAY_SIZE(my_modem_unsol),
    },
    .chat_delimiter = "\r",
    .chat_filter = "\n",
    .power_pulse_duration_ms = 1000,
    .reset_pulse_duration_ms = 100,
    .startup_time_ms = 5000,
    .shutdown_time_ms = 5000,
};

/* Macro for defining a DT instance */
#define MY_MODEM_DEVICE(inst)                                                   \
    MODEM_DT_INST_PPP_DEFINE(inst,                                              \
        MODEM_CELLULAR_INST_NAME(ppp, inst), NULL, 1500, 64);                   \
                                                                                \
    static struct modem_cellular_data                                           \
        MODEM_CELLULAR_INST_NAME(data, inst);                                   \
                                                                                \
    MODEM_CELLULAR_DEFINE_AND_INIT_USER_PIPES(inst,                             \
        (user_pipe_0, 3), (user_pipe_1, 4))                                     \
                                                                                \
    MODEM_CELLULAR_DEFINE_INSTANCE(inst, &my_modem_vendor, NULL)

#define DT_DRV_COMPAT my_modem
DT_INST_FOREACH_STATUS_OKAY(MY_MODEM_DEVICE)
#undef DT_DRV_COMPAT

上面的示例虽然很精简，但足以在通用蜂窝调制解调器上建立 PPP 连接。更完整的示例请参阅 drivers/modem/modem_cellular.c。

开发板专用初始化脚本

初始化、网络和拨号脚本的作用域是厂商级的（以设备树 compatible 为键），因此对于使用同一调制解调器的不同开发板之间存在差异的配置（例如射频调谐器的频段路由），原本需要复制并修改厂商驱动。作为替代，开发板可以使用 MODEM_CELLULAR_BOARD_INIT_DEFINE 注册自己的 chat 脚本。该脚本在 CMUX 建立之后、APN 和网络配置之前，通过 AT 控制通道运行。未注册脚本的开发板不会增加任何 ROM 或 RAM 占用。

驱动会用推进连接流程的回调覆盖该脚本的完成回调，因此脚本上设置的任何回调都会被忽略。

MODEM_CHAT_MATCH_DEFINE(board_init_ok_match, "OK", "", NULL);
MODEM_CHAT_SCRIPT_CMDS_DEFINE(board_init_cmds,
    MODEM_CHAT_SCRIPT_CMD_RESP("AT+QCFG=\"rf/tuner_cfg\",0,\"12,28\"", board_init_ok_match));
MODEM_CHAT_SCRIPT_NO_ABORT_DEFINE(board_init, board_init_cmds, NULL, 10);

MODEM_CELLULAR_BOARD_INIT_DEFINE(DT_NODELABEL(modem), &board_init);

CMUX 省电

3GPP TS 27.010 为 CMUX 规定了一种省电机制，当调制解调器支持该机制时，可以在 Zephyr 中使用。

规范的以下章节描述了该省电机制：

  • 5.2.5 Inter-frame Fill（帧间填充）

  • 5.4.6.3.2 Power Saving Control (PSC) message（省电控制（PSC）消息）

  • 5.4.7 Power Control and Wake-up Mechanisms（电源控制和唤醒机制）

该省电机制允许对 CMUX 模块所使用的 UART 设备进行运行时电源管理。当任何 DLCI 通道上都没有数据需要发送或接收时，CMUX 模块会在一段可配置的超时之后进入空闲状态。在空闲状态下，CMUX 模块会向调制解调器发送一条省电控制消息，请求其进入低功耗状态。随后 CMUX 模块可以关闭管道设备；如果启用了运行时电源管理，UART 设备就可以断电。

当任何 DLCI 通道上有数据需要发送或接收时，CMUX 模块会退出空闲状态，并通过持续发送标志字符来唤醒调制解调器，直到收到调制解调器发回的标志字符为止。

有些调制解调器通过 CMUX 之外的硬件信号线来控制休眠和唤醒，而不是通过带内协议。对于这类调制解调器，可以使用 cmux-no-powersave-handshake 属性在进入和退出两个阶段都跳过握手。进入时，CMUX 跳过 PSC 帧交换，直接转入省电状态。退出时，CMUX 跳过标志字符交换，在管道重新打开后直接转入已连接状态。下一个发出的帧会自行重新同步成帧。

有些调制解调器只有在 DTR（Data Terminal Ready，数据终端就绪）信号无效时才允许 UART 断电。在这种情况下，可以将支持 DTR 的 UART 设备与 CMUX 模块配合使用，根据 UART 的电源状态控制 DTR 信号。

要在 UART 断电时因收到数据而唤醒，需要调制解调器支持用 RING 信号唤醒主机。RING 信号由调制解调器驱动处理，驱动在检测到 RING 信号时打开管道设备，使 CMUX 模块能够唤醒调制解调器并处理收到的数据。

subsys/modem/modem_cmux.c 模块使用以下状态机实现省电机制。

在已连接状态下，modem_cmux_process_received_byte() 需要按照规范 5.2.5 Inter-frame Fill 中的描述回复重复的标志字符。空闲定时器保持运行，并在每次发送或接收帧时清零。定时器到期将启动向省电模式的转换。

在 POWERSAVE 状态下，所有 DLC 管道保持打开，但通往 UART 的管道被阻塞或关闭，因此所有数据都缓存在 CMUX 环形缓冲区中，等待唤醒。在此状态下，同样会回复重复的标志字符，以便远端按照 5.4.7 中的描述继续执行唤醒过程。如果管道已关闭，并且启用了运行时电源管理，UART 设备就可以断电。

当空闲定时器在 CONNECTED 状态下到期时，CMUX 状态机会阻塞所有 DLC 管道，并向远端发送 PSC 命令，以启动向 POWERSAVE 状态的转换。PSC 命令得到回复后，CMUX 转入 POWERSAVE 模式。

在 CONNECTED 状态下，远端也可以发送 PSC 命令来启动向省电模式的转换。CMUX 会阻塞所有 DLC 管道并发送 PSC 响应。TX 缓冲区清空后，CMUX 进入 POWERSAVE 状态。

在 POWERSAVE 状态下，当任一 DLC 管道尝试发送数据时，CMUX 会缓存该数据并转入 WAKEUP 状态，按照 5.4.7 的规定，通过发送连续的标志字符流来启动唤醒过程。远端回复标志字符，表示已准备好接收数据。CMUX 随后停止发送标志字符，返回 CONNECTED 状态，恢复正常运行。

CMUX 省电机制可以通过以下设备树属性进行配置：

cmux-enable-runtime-power-save:
  type: boolean
  description: Enable runtime power saving using CMUX PSC commands.
               This requires modem to support CMUX and PSC commands while keeping the data
               connection active.
cmux-close-pipe-on-power-save:
  type: boolean
  description: Close the modem pipe when entering power save mode.
              When runtime power management is enabled, this closes the UART.
              This requires modem to support waking up the UART using RING signal.
cmux-idle-timeout-ms:
  type: int
  description: Time in milliseconds after which CMUX will enter power save mode.
  default: 10000

带省电功能的 CMUX 设备树设置示例：

&uart1 {
  status = "okay";
  zephyr,pm-device-runtime-auto;

  uart_dtr: uart-dtr {
    compatible = "zephyr,uart-dtr";
