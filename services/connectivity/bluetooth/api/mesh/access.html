访问层

访问层（access layer）是应用程序与 Bluetooth Mesh 网络之间的接口。访问层提供了将节点行为划分为元素和模型的机制，这些元素和模型由应用程序实现。

Mesh 模型

Mesh 节点的功能由模型表示。一个模型实现节点所支持的一种行为，例如充当灯、传感器或温控器。Mesh 模型被分组到 元素 中。每个元素都被分配了自己的单播地址，并且每种类型的模型在一个元素中最多只能有一个。按照惯例，每个元素代表 Mesh 节点行为的一个方面。例如，一个包含一个传感器、两盏灯和一个电源插座的节点，会将这些功能分布到四个元素上，每个元素实例化所支持行为中某一方面所需的全部模型。

节点的元素和模型结构在节点组成数据（composition data）中指定，组成数据在初始化期间传给 bt_mesh_init()。Bluetooth SIG 定义了一组基础模型（参见 Mesh 模型），并在 Bluetooth Mesh 模型规范 中定义了一组用于实现常见行为的模型。所有不是由 Bluetooth SIG 定义的模型都是厂商模型，并且必须与一个公司 ID（Company ID）关联。

Mesh 模型有若干参数，可以通过 Mesh 协议栈的初始化或通过 配置服务器 进行配置：

操作码列表

操作码列表包含模型可以接收的所有消息操作码，以及可接受的最小负载长度和用于处理这些消息的回调。模型可以支持任意数量的操作码，但在每个元素中，每个操作码只能由一个模型列出。

完整的操作码列表必须在组成数据中传给模型结构体，并且不能在运行时更改。操作码列表的结尾由特殊条目 BT_MESH_MODEL_OP_END 确定。除非列表为空，否则该条目必须始终存在于操作码列表中。列表为空时，应使用 BT_MESH_MODEL_NO_OPS 代替正式的操作码列表定义。

AppKey 列表

AppKey 列表包含模型可以用来接收消息的所有应用密钥。只有使用 AppKey 列表中的应用密钥加密的消息才会被传给该模型。

每个模型最多可容纳的应用密钥数量由 CONFIG_BT_MESH_MODEL_KEY_COUNT 配置选项设置。AppKey 列表的内容由 配置服务器 管理。

订阅列表

模型会处理所有发往其所在元素单播地址的消息（前提是所用的应用密钥在 AppKey 列表中）。此外，模型还会处理发往其订阅列表中任意组地址或虚拟地址的数据包。这使节点能够用一条消息寻址整个 Mesh 网络中的多个节点。

每个模型的订阅列表最多可容纳的地址数量由 CONFIG_BT_MESH_MODEL_GROUP_COUNT 配置选项设置。订阅列表的内容由 配置服务器 管理。

模型发布

模型可以通过两种方式发送消息：

  • 在 bt_mesh_msg_ctx 中指定一组消息参数，然后调用 bt_mesh_model_send()。

  • 设置一个 bt_mesh_model_pub 结构体，然后调用 bt_mesh_model_publish()。

使用 bt_mesh_model_publish() 发布消息时，模型将使用由 配置服务器 配置的发布参数。这是发送主动（非请求触发）模型消息的推荐方式，因为它将选择消息参数的责任交给了网络管理员，而网络管理员通常比单个节点更了解 Mesh 网络。

为了支持使用发布参数进行发布，模型必须分配一个用于发布的数据包缓冲区，并将其传给 bt_mesh_model_pub.msg。配置服务器还可以为发布消息设置周期性发布。为支持这一点，模型必须填写 bt_mesh_model_pub.update 回调。bt_mesh_model_pub.update 回调会在消息发布之前被调用，使模型可以修改负载以反映其当前状态。

将 bt_mesh_model_pub.retr_update 设置为 1，模型就可以让 bt_mesh_model_pub.update 回调在每次重传时都被触发。例如，使用延迟（Delay）参数的模型可以利用这一点，在每次重传时调整该参数。bt_mesh_model_pub_is_retransmission() 函数可用于区分首次发布和重传。BT_MESH_PUB_MSG_TOTAL 和 BT_MESH_PUB_MSG_NUM 宏可用于返回一个发布间隔内的总发送次数和当前重传序号。

扩展模型

Bluetooth Mesh 规范允许 Mesh 模型相互扩展。当一个模型扩展另一个模型时，它会继承该模型的功能；利用扩展，可以由简单模型构建出复杂模型，复用现有模型的功能，从而避免定义新的操作码。模型可以扩展任意数量、来自任意元素的模型。当一个模型扩展同一元素中的另一个模型时，这两个模型将共享订阅列表。Mesh 协议栈的实现方式是将两个模型的订阅列表合并为一个，二者可拥有的订阅数量也合并计算。模型可以扩展本身又扩展了其他模型的模型，从而形成一棵“扩展树”。扩展树中的所有模型在其跨越的每个元素中共享同一个订阅列表。

模型扩展通过在初始化期间调用 bt_mesh_model_extend() 完成。一个模型只能被另一个模型扩展，并且扩展关系不能形成循环。注意，节点状态的绑定以及模型之间的其他关系必须由模型实现自行定义。

模型扩展机制会在访问层数据包处理中增加一些开销，并且必须通过 CONFIG_BT_MESH_MODEL_EXTENSIONS 显式启用才会生效。

模型数据存储

Mesh 模型的每个实例可能都有需要持久化存储的关联数据。访问 API 提供了一种存储这些数据的机制，它利用了内部的模型实例编码方案。模型可以调用 bt_mesh_model_data_store()，为每个实例存储一个用户自定义的数据条目。为了在设备下次重启时能够读出这些数据，必须填写模型的 bt_mesh_model_cb.settings_set 回调。当在持久化存储中找到模型专属数据时，就会调用该回调。模型可以调用作为参数传入该回调的 read_cb 来获取数据。详情请参阅 设置（Settings） 模块文档。

如果模型数据变化频繁，每次变化都进行存储可能会加剧 Flash 磨损。为减少磨损，模型可以调用 bt_mesh_model_data_store_schedule() 推迟数据的存储。协议栈会调度一个工作项，其延迟由 CONFIG_BT_MESH_STORE_TIMEOUT 选项定义。工作项运行时，协议栈会为每个请求存储数据的模型调用 bt_mesh_model_cb.pending_store 回调。然后，模型可以调用 bt_mesh_model_data_store() 来存储数据。

如果启用了 CONFIG_BT_MESH_SETTINGS_WORKQ，bt_mesh_model_cb.pending_store 回调将在一个专用线程中被调用。这样，在存储模型数据期间，协议栈仍可以处理其他收发消息。当需要存储大量数据时，建议使用该选项和 bt_mesh_model_data_store_schedule() 函数。

组成数据

组成数据（Composition Data）提供 Mesh 设备的相关信息。设备的组成数据包含设备上的元素、设备支持的模型以及其他功能的信息。组成数据被分成不同的页，每一页包含设备某一方面的功能信息。要访问这些信息，用户可以使用 配置服务器 模型，或者在支持的情况下使用 大型组成数据服务器 模型。

组成数据页 0

组成数据页 0 提供设备的基本信息，对所有 Mesh 设备都是必需的。它包含元素和模型的组成、支持的功能以及制造商信息。

组成数据页 1

组成数据页 1 提供模型之间关系的信息，对所有 Mesh 设备都是必需的。一个模型可以扩展一个或多个模型，和/或与一个或多个模型相对应。模型可以通过调用 bt_mesh_model_extend() 扩展另一个模型，或通过调用 bt_mesh_model_correspond() 与另一个模型相对应。CONFIG_BT_MESH_MODEL_EXTENSION_LIST_SIZE 指定设备的组成数据中可以存储多少个模型关系，该数值应当与 bt_mesh_model_extend() 和 bt_mesh_model_correspond() 的调用次数相符。

组成数据页 2

组成数据页 2 提供所支持的 Mesh 配置文件（profile）的信息。Mesh 配置文件规范定义了希望支持某个 Bluetooth SIG 定义的配置文件的设备所需满足的产品要求。当前支持的配置文件可以在 Bluetooth SIG 分配号码（Assigned Numbers） 的第 3.12 节中找到。只有声称支持一个或多个 Mesh 配置文件的设备才必须提供组成数据页 2。

组成数据页 128、129 和 130

组成数据页 128、129 和 130 分别镜像组成数据页 0、1 和 2。当组成数据将在固件更新后发生变化时，它们用于表示所镜像页面的新内容。详情请参阅 组成数据和模型元数据。

可延迟消息

可延迟消息功能通过 Kconfig 选项 CONFIG_BT_MESH_ACCESS_DELAYABLE_MSG 启用。这是一项可选功能，它针对模型为响应所收到消息而发送的消息（也称为响应消息）实现了规范中的建议。

响应消息应当按以下随机延迟发送：

  • 如果收到的消息发往单播地址，延迟 20 到 50 毫秒

  • 如果收到的消息发往组地址或虚拟地址，延迟 20 到 500 毫秒

如果设置了 bt_mesh_msg_ctx.rnd_delay 标志，就会触发可延迟消息功能。在等待随机延迟到期期间，可延迟消息功能会将消息保存在本地内存中。

如果随机延迟到期时传输层没有足够的内存来发送消息，该消息会再推迟 10 毫秒。如果传输层由于其他任何原因无法发送消息，可延迟消息功能会以传输层错误码触发 bt_mesh_send_cb.start 回调。

如果可延迟消息功能找不到足够的空闲内存来保存传入的消息，它会提前发送那些延迟即将到期的消息以释放内存。

当 Mesh 协议栈被挂起或重置时，尚未发送的消息会被移除，并以错误码触发 bt_mesh_send_cb.start 回调。

备注

当一个模型连续发送多条消息时，消息的发送顺序可能与它们被传给访问层的顺序不同。这是因为某些消息的延迟可能比其他消息更长。

当同一模型发出的一组消息需要按特定顺序发送时，请将 bt_mesh_msg_ctx.rnd_delay 设置为 false 以禁用随机化。

可延迟发布

可延迟发布功能在以下情况下实现了规范中关于消息发布延迟的建议：

  • Bluetooth Mesh 协议栈启动时，或由 bt_mesh_model_publish() 函数触发发布时，延迟 20 到 500 毫秒

  • 对于周期性发布的消息，延迟 20 到 50 毫秒

此功能是可选的，通过 CONFIG_BT_MESH_DELAYABLE_PUBLICATION Kconfig 选项启用。启用后，每个模型可以通过将 bt_mesh_model_pub.delayable 位域分别设置为 1 或 0 来启用或禁用可延迟发布。该位域可以随时更改。
