概述

受限应用协议（CoAP）是一种专用的 Web 传输协议，适用于受限节点和受限网络（例如低功耗、有损网络）。它为支持 CoAP 特性的 RESTful Web 服务提供了便捷的 API。关于该协议本身的更多信息，请参见 RFC 7252。

Zephyr 提供了一个同时支持客户端和服务器角色的 CoAP 库。可以通过 Kconfig 选项 CONFIG_COAP 启用该库，并可根据用户需要进行配置。Zephyr CoAP 库使用普通缓冲区实现。API 的使用者自行创建用于通信的套接字，并把缓冲区传给该库进行解析或其他处理。该库本身不会为用户创建任何套接字。

在 CoAP 之上，Zephyr 还支持 LwM2M（“Lightweight Machine 2 Machine”，轻量级机器对机器）协议，这是一种简单、低成本的远程管理与服务启用机制。更多信息请参见 轻量级 M2M（LwM2M）。

支持的 RFC：

  • RFC 7252 - The Constrained Application Protocol (CoAP)

  • RFC 6690 - Constrained RESTful Environments (CoRE) Link Format

  • RFC 7959 - Block-Wise Transfers in the Constrained Application Protocol (CoAP)

  • RFC 7641 - Observing Resources in the Constrained Application Protocol (CoAP)

  • RFC 8613 - Object Security for Constrained RESTful Environments (OSCORE)

备注

并非支持这些 RFC 的全部内容。所支持的特性取决于 Zephyr 的需求。

Zephyr CoAP 库还支持 RFC 8613 中规定的受限 RESTful 环境对象安全（OSCORE）。更多信息请参见 OSCORE 支持（RFC 8613）。

使用示例

CoAP 服务器

备注

Zephyr 提供了 CoAP 服务器 子系统，下面的内容用于创建自定义的服务器实现。

要创建 CoAP 服务器，需要为服务器定义资源。.well-known/core 资源应添加在所有其他需要包含在 .well-known/core 资源响应中的资源之前。

static struct coap_resource resources[] = {
    { .get = well_known_core_get,
      .path = COAP_WELL_KNOWN_CORE_PATH,
    },
    { .get  = sample_get,
      .post = sample_post,
      .del  = sample_del,
      .put  = sample_put,
      .path = sample_path
    },
    { },
};

应用程序从套接字读取数据，并把缓冲区传给 CoAP 库以解析消息。如果 CoAP 消息格式正确，该库会结合缓冲区和上面定义的资源，调用正确的回调函数来处理来自客户端的 CoAP 请求。根据 CoAP 请求作出应答或执行相应操作是回调函数的职责。

coap_packet_parse(&request, data, data_len, options, opt_num);
...
coap_handle_request(&request, resources, options, opt_num,
                    client_addr, client_addr_len);

如果启用了 CONFIG_COAP_URI_WILDCARD，服务器可以使用类似 MQTT 的通配符方式匹配多个资源：

  • 加号表示路径中的单级通配符；

  • 井号表示路径中的多级通配符。

static const char * const led_set[] = { "led","+","set", NULL };
static const char * const btn_get[] = { "button","#", NULL };
static const char * const no_wc[] = { "test","+1", NULL };

它接受 /led/0/set、led/1234/set、led/any/set、/button/door/1、/test/+1，但对 /led/1、/test/21、/test/1 返回 -ENOENT。

该选项默认启用；如果资源路径类似 '/some_resource/+/#'，请禁用该选项，以避免出现意外行为。

CoAP 客户端

备注

Zephyr 提供了 CoAP 客户端 子系统，下面的内容用于创建自定义的客户端实现。

如果 CoAP 客户端知道 CoAP 服务器中的资源，客户端就可以开始准备 CoAP 请求并等待响应。如果客户端不知道 CoAP 服务器中的资源，可以通过 .well-known/core CoAP 消息请求资源。

/* Initialize the CoAP message */
char *path = "test";
struct coap_packet request;
uint8_t data[100];
uint8_t payload[20];

coap_packet_init(&request, data, sizeof(data),
                 1, COAP_TYPE_CON, 8, coap_next_token(),
                 COAP_METHOD_GET, coap_next_id());

/* Append options */
coap_packet_append_option(&request, COAP_OPTION_URI_PATH,
                          path, strlen(path));

/* Append Payload marker if you are going to add payload */
coap_packet_append_payload_marker(&request);

/* Append payload */
coap_packet_append_payload(&request, (uint8_t *)payload,
                           sizeof(payload) - 1);

/* send over sockets */

测试

测试 Zephyr CoAP 库的方法有多种。

libcoap

libcoap 为资源受限（例如计算能力、射频范围、内存、带宽或网络数据包大小受限）的设备实现了一种轻量级应用协议。源代码见 libcoap。libcoap 提供了一个脚本（examples/etsi_coaptest.sh），用于测试 Zephyr 中的 coap-server 功能。

更多细节请参见 net-tools 项目

可以按照 使用 QEMU 联网 中的说明，在 QEMU 上构建并运行 CoAP service 示例。

在主机上使用以下命令运行 libcoap 实现的 ETSI 测试用例：

sudo ./libcoap/examples/etsi_coaptest.sh -i tap0 2001:db8::1

TTCN3

Eclipse 提供了基于 TTCN3 的测试，可以针对 CoAP 实现运行。

安装 eclipse-titan，并为 titan 工具设置符号链接

sudo apt-get install eclipse-titan

cd /usr/share/titan

sudo ln -s /usr/bin bin
sudo ln /usr/bin/titanver bin
sudo ln -s /usr/bin/mctr_cli bin
sudo ln -s /usr/include/titan include
sudo ln -s /usr/lib/titan lib

export TTCN3_DIR=/usr/share/titan

git clone https://gitlab.eclipse.org/eclipse/titan/titan.misc.git

cd titan.misc

按照以下说明设置 CoAP 测试套件：

  • https://gitlab.eclipse.org/eclipse/titan/titan.misc

  • https://gitlab.eclipse.org/eclipse/titan/titan.misc/-/tree/master/CoAP_Conf

构建完成后，可以按照 使用 QEMU 联网 中的说明，在 QEMU 上构建并运行 CoAP service 示例。

根据实际环境，修改 coap.cfg 文件中客户端（测试套件）和服务器（Zephyr coap-server 示例）的地址。

使用以下命令执行测试用例。

ttcn3_start coaptests coap.cfg

ttcn3 测试的输出示例如下。

Verdict statistics: 0 none (0.00 %), 10 pass (100.00 %), 0 inconc (0.00 %), 0 fail (0.00 %), 0 error (0.00 %).
Test execution summary: 10 test cases were executed. Overall verdict: pass
