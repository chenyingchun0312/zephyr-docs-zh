zperf：网络流量生成器

  • 示例用法

  • iperf3

  • 会话管理

概述

zperf 是一个 shell 工具，可以在 Zephyr 中生成网络流量。该工具可用于评估网络带宽。

zperf 与 iPerf 2.0.10 及更新版本兼容。如需兼容更早的版本，请启用 CONFIG_NET_ZPERF_LEGACY_HEADER_COMPAT。另外，zperf 也可以使用 iperf3 协议，参见 iperf3。一次构建只能使用两者之一。

任何应用程序都可以启用 zperf，Zephyr 中也提供了一个专门的示例。详细信息请参见 zperf 示例应用程序。

示例用法

如果 Zephyr 作为客户端，则 iPerf 必须以服务器模式运行。例如，进行 UDP 测试时必须使用以下命令行：

$ iperf -s -l 1K -u -V -B 2001:db8::2

进行 TCP 测试时，命令行如下：

$ iperf -s -l 1K -V -B 2001:db8::2

在 Zephyr 控制台中，可以按如下方式执行 zperf：

zperf udp upload 2001:db8::2 5001 10 1K 1M

UDP 速率为 0 时会以尽可能快的速度发送，与 iperf -b 0 相同。

对于 TCP，zperf 命令如下：

zperf tcp upload 2001:db8::2 5001 10 1K 1M

如果在配置文件中指定了 Zephyr 和主机的 IP 地址，可以按如下方式启动 zperf：

zperf udp upload2 v6 10 1K 1M

如果要测试 TCP，则如下：

zperf tcp upload2 v6 10 1K 1M

如果 Zephyr 作为服务器，对于 UDP，按如下方式设置下载模式：

zperf udp download 5001

对于 TCP，则如下：

zperf tcp download 5001

在主机端，如果测试 UDP，必须使用以下命令行运行 iPerf：

$ iperf -l 1K -u -V -c 2001:db8::1 -p 5001

如果测试 TCP，则使用：

$ iperf -l 1K -V -c 2001:db8::1 -p 5001

如果 Zephyr 无法有序地接收所有数据包，可以使用 -b 选项限制 iPerf 的输出。

iperf3

启用 CONFIG_NET_ZPERF_IPERF3 后，zperf 与 iperf3 而不是 iPerf 2 互通。该支持处于实验阶段。zperf API 和 shell 命令保持不变，默认端口变为 iperf3 的默认端口 5201。

当 Zephyr 作为服务器时，启用要接受的协议：

zperf tcp download
zperf udp download

iperf3 客户端为每次测试选择 TCP 或 UDP，两者使用同一个端口，并且无论哪种情况都有一个 TCP 控制连接。因此这两条命令共享监听端口：每条命令启用各自的协议，请求未启用协议的测试会被拒绝。在主机上：

$ iperf3 -c 2001:db8::1
$ iperf3 -c 2001:db8::1 -u -b 10M

当 Zephyr 作为客户端时，在主机上运行 iperf3 -s，并在 Zephyr 控制台中执行：

zperf tcp upload 2001:db8::2 5201 10 1K
zperf udp upload 2001:db8::2 5201 10 1K 10M

一次测试在单个流上运行。反向（-R）、双向（--bidir）和并行（-P）测试，以及省略测试开头（-O）都会被拒绝，并给出 iperf3 在服务器未实现某选项时打印的消息。同一时间只运行一个测试，第二个客户端会被告知服务器忙。多播和 CONFIG_ZPERF_SESSION_PER_THREAD 是 iPerf 2 的功能。

与 iPerf 2 比较时需要注意以下几点：

  • iperf3 服务器会一直统计 TCP 数据，直到客户端在控制连接上结束测试，而结束消息可能先于最后一部分数据到达，因此服务器报告的数据量可能略少于客户端发送的数据量。iPerf 2 服务器则统计到连接关闭为止。

  • 对于 UDP，在服务器收到的最后一个数据报之后丢失的数据报，在 zperf 上传报告中会计为丢失，这与 iPerf 2 相同。iperf3 本身则不计入这些数据报。

  • iperf3 不报告乱序情况，因此上传报告中不会有乱序数据包。

  • 服务器只读取每个 UDP 数据报的报头，依靠 ZSOCK_MSG_TRUNC 获知其完整长度。如果套接字卸载驱动忽略该标志，服务器统计的字节数就会偏少。

  • 每次测试在两端各占用一个控制连接和一个数据流，并且每次测试结束后，已关闭的连接还会在 TIME_WAIT 状态停留一段时间。请像示例的 overlay-iperf3.conf 那样，在 CONFIG_NET_MAX_CONTEXTS 和 CONFIG_NET_MAX_CONN 中为它们留出余量。

会话管理

如果设置了 CONFIG_ZPERF_SESSION_PER_THREAD 选项，用户在启动上传时提供 -a 选项，即可同时进行多个上传会话。每个会话都有自己的工作队列来运行测试。测试结束后也可以查看会话的测试结果。可以使用 -w 选项启动会话，此时工作线程会等待开始信号，使所有线程能够同时启动。这可以避免由于 zperf shell 的优先级低于已启动的会话线程而无法运行的情况。如果只有一个上传会话，则不太需要 -w。

以下 zperf shell 命令可用于会话管理：

自定义数据上传

通过 zperf_upload_params.data_loader 设置自定义数据源，zperf 可以对数据上传进行更高级的性能分析。这样可以生成自定义的数据包内容，而不是发送只由 z 字符组成的固定数据包。一个示例用例是测定从外部 Flash 存储芯片上传数据的最大吞吐量。

原始 TX 模式

zperf 支持原始数据包发送模式，用于测试自定义 L2 帧或厂商特定的协议。该模式绕过 UDP/TCP，直接使用数据包套接字发送原始数据包。

要启用原始 TX 模式，请设置以下 Kconfig 选项：

CONFIG_NET_SOCKETS_PACKET=y
CONFIG_NET_ZPERF_RAW_TX=y

最大报头大小可通过 CONFIG_NET_ZPERF_RAW_TX_MAX_HDR_SIZE 配置（默认：64 字节）。

使用原始 TX 模式之前，必须在网络接口上启用 TX 注入模式：

uart:~$ net iface txinjection 1 on

原始 TX 上传命令的语法为：

zperf raw upload [-a] <if_index> <header_hex> [<duration_sec>] [<packet_size>] [<rate_kbps>]

其中：

  • -a：可选的异步模式标志

  • if_index：网络接口索引（例如 1）

  • header_hex：用户提供的报头，以十六进制字符串表示（厂商元数据 + 帧头）

  • duration_sec：测试持续时间，单位为秒（默认：1）

  • packet_size：包含报头在内的数据包总大小（默认：256）

  • rate_kbps：目标速率，单位为 Kbps，支持 K/M 后缀（默认：10）。0 表示以尽可能快的速度发送。

发送带厂商元数据的原始 802.11 帧的示例：

uart:~$ zperf raw upload 1 12345678000400030000000088000000ffffffffffa06960e35215a06960e3521500000000aaaa030000000800 10 1024 50M

该十六进制报头字符串包含：

  • 厂商元数据（本例中为前 12 个字节）

  • 带 LLC/SNAP 的 802.11 QoS 数据帧头

负载（用 z 字符填充）会自动追加，使数据包达到指定的大小。
