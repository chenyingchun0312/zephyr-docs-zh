概述

Zephyr CoAP 库支持 RFC 8613 中规定的受限 RESTful 环境对象安全（OSCORE）。OSCORE 使用 COSE（CBOR 对象签名与加密）为 CoAP 消息提供端到端保护。

OSCORE 在应用层保护 CoAP 消息，提供：

  1. 机密性：消息负载和敏感选项被加密

  2. 完整性：消息通过 MAC 进行认证

  3. 重放保护：序列号可防止重放攻击

  4. 对代理友好：外层选项保持可见，便于路由

与 DTLS 不同，OSCORE 提供的端到端安全在代理于不同传输协议（UDP、TCP、HTTP）之间转换时依然有效。

其他 OSCORE 配置选项：

  • CONFIG_COAP_OSCORE_MAX_CONTEXTS：OSCORE 安全上下文的最大数量

  • CONFIG_COAP_OSCORE_EXCHANGE_CACHE_SIZE：每个服务要跟踪的 OSCORE 交换数量

  • CONFIG_COAP_OSCORE_EXCHANGE_LIFETIME_MS：所跟踪的 OSCORE 交换的生命周期，这些交换用于保护

    延迟（分离）响应

  • CONFIG_COAP_OSCORE_CONTEXT_REUSE：启用 OSCORE 对跨重启复用上下文的支持

  • CONFIG_COAP_OSCORE_MASTER_SECRET_MAX_LEN：OSCORE 主密钥（Master Secret）的最大长度，单位为字节

  • CONFIG_COAP_OSCORE_MASTER_SALT_MAX_LEN：OSCORE 主盐值（Master Salt）的最大长度，单位为字节

配置

通过 CONFIG_COAP_OSCORE 启用 OSCORE 支持。该选项依赖于 uoscore-uedhoc 模块和 PSA Crypto 支持：

CONFIG_COAP_OSCORE=y
CONFIG_UOSCORE=y
CONFIG_PSA_CRYPTO=y

uoscore 模块会自动选中所需的 PSA 加密算法（AES-CCM、HKDF-SHA256 等）。

服务器用法

要在 CoAP 服务上启用 OSCORE，请使用 COAP_SERVICE_DEFINE_OSCORE（DTLS 则使用 COAPS_SERVICE_DEFINE_OSCORE）定义服务。该宏会静态分配每个服务的 OSCORE 交换缓存。安全上下文通过 Zephyr OSCORE API 单独创建，并添加到一个共享池中；应用程序不会直接包含底层的 uoscore-uedhoc 头文件。收到的请求会根据其接收方 ID（Recipient ID）和 ID 上下文（ID Context）匹配到正确的上下文，因此单个服务可以服务多个客户端，每个客户端都有自己的上下文：

#include <zephyr/net/coap_oscore.h>
#include <zephyr/net/coap_service.h>

static struct coap_oscore_context *my_oscore_ctx;

static uint16_t my_service_port = 5683;

/* Final argument "true" requires OSCORE for all requests. */
COAP_SERVICE_DEFINE_OSCORE(my_service, NULL, &my_service_port,
                           COAP_SERVICE_AUTOSTART, true);

int my_service_oscore_init(void)
{
    /* coap_oscore_context_add() copies the key material, so these
     * buffers need not outlive the call and can live on the stack.
     */
    const uint8_t master_secret[16] = { /* ... */ };
    const uint8_t master_salt[8] = { /* ... */ };
    const uint8_t sender_id[] = { /* ... */ };
    const uint8_t recipient_id[] = { /* ... */ };

    struct coap_oscore_init_params params = {
        .master_secret = master_secret,
        .master_secret_len = sizeof(master_secret),
        .sender_id = sender_id,
        .sender_id_len = sizeof(sender_id),
        .recipient_id = recipient_id,
        .recipient_id_len = sizeof(recipient_id),
        .master_salt = master_salt,
        .master_salt_len = sizeof(master_salt),
        .aead_alg = COAP_OSCORE_AEAD_AES_CCM_16_64_128,
        .hkdf = COAP_OSCORE_HKDF_SHA_256,
        .fresh_master_secret_salt = true,
    };

    /* Add the context to the shared pool once its key material is
     * available. Call once per client identity (Recipient ID).
     */
    return coap_oscore_context_add(&params, &my_oscore_ctx);
}

可同时分配的上下文数量由 CONFIG_COAP_OSCORE_MAX_CONTEXTS 控制。使用 coap_oscore_context_remove() 释放上下文。上下文采用引用计数：只要仍有正在处理的请求、活动的交换或观察者引用某个上下文，coap_oscore_context_remove() 就会返回 -EAGAIN，并保留该上下文。等这些引用释放后再重试移除。

当服务启用了 OSCORE（使用 OSCORE 宏创建，并且至少有一个上下文被添加到池中）时：

  1. 传入请求：服务器会自动验证并解密受 OSCORE 保护的请求（RFC 8613 第 8.2 节）。资源处理函数收到的是已解密的 CoAP 消息，内层选项可见。

  2. 发出的响应：服务器会自动对源自 OSCORE 交换的响应和通知进行 OSCORE 保护（RFC 8613 第 8.3 节）。某条发出的消息是否必须受保护按如下方式决定：

    • 同步响应在处理请求期间产生，会与

      每个服务的交换缓存进行匹配，找到匹配条目时即受保护。这些条目会在 CONFIG_COAP_OSCORE_EXCHANGE_LIFETIME_MS 之后过期。在混合服务（同时有 OSCORE 和非 OSCORE 客户端）上，如果在交换缓存条目过期后发送同步响应，将得到明文响应。

    • 观察通知根据观察者所存储的 OSCORE

      状态进行保护，该状态在整个观察期间一直存在。

    • 延迟（分离）响应在请求处理函数

      返回之后产生，会与每个服务的交换缓存进行匹配，找到匹配条目时即受保护。这些条目会在 CONFIG_COAP_OSCORE_EXCHANGE_LIFETIME_MS 之后过期。在混合服务（同时有 OSCORE 和非 OSCORE 客户端）上，如果在交换缓存条目过期后发送延迟响应，将得到明文响应。

  3. 错误处理：OSCORE 验证错误以简单的 CoAP 响应发送，

    不经过 OSCORE 处理（RFC 8613 第 8.2 节）：- COSE 解码失败 → 4.02 Bad Option - 未找到安全上下文 → 4.01 Unauthorized - 解密失败 → 4.00 Bad Request

  4. 强制 OSCORE：如果定义服务时把 _oscore_required 参数

    设为 true，未受保护的请求会以 4.01 Unauthorized 被拒绝。

  5. 失败即关闭行为：如果对响应的 OSCORE 保护失败，服务器不会回退到发送明文响应。在强制 OSCORE 的服务上，无法匹配到任何 OSCORE 状态的发出响应也会被丢弃，而不是以明文发送。观察通知永远不会降级。在混合服务上，任何交换缓存条目已过期的响应（同步或延迟）都无法再匹配，会以未受保护的形式发送。实际上这影响的是延迟（分离）响应，因为同步响应匹配的是在处理请求时刚刚创建的条目（参见第 2 项和 CONFIG_COAP_OSCORE_EXCHANGE_LIFETIME_MS）。

已知限制

  1. 混合服务交换过期后的明文：在混合服务（同时服务 OSCORE 和非 OSCORE 客户端的服务）上，交换缓存条目已过期的响应无法再匹配到其 OSCORE 状态，会以明文发送。这同时影响同步响应和延迟（分离）响应（参见 CONFIG_COAP_OSCORE_EXCHANGE_LIFETIME_MS）。对于任何承载敏感数据的服务，请将其定义为强制 OSCORE（把 _oscore_required 参数设为 true，例如通过 COAP_SERVICE_DEFINE_OSCORE），而不是运行混合服务。强制 OSCORE 的服务会拒绝未受保护的请求，并丢弃无法保护的响应，因此永远不会降级为明文。

安全上下文派生

OSCORE 安全上下文由一小组参数派生而来（RFC 8613 第 3 节）：

必需参数：

  • 主密钥（Master Secret）：共享密钥（对于 AES-CCM-16-64-128，通常为 16 字节）

  • 发送方 ID（Sender ID）：发送方的唯一标识符

  • 接收方 ID（Recipient ID）：接收方的唯一标识符

可选参数：

  • 主盐值（Master Salt）：额外的熵（推荐使用，通常为 8 字节）

  • ID 上下文（ID Context）：额外的上下文标识符

  • AEAD 算法：默认为 AES-CCM-16-64-128

  • KDF：默认为 HKDF-SHA-256

这些参数通常通过以下方式建立：

  1. 预共享密钥：在设备配置下发时设置

  2. EDHOC：基于 COSE 的临时 Diffie-Hellman（参见 uoscore-uedhoc 模块）

安全注意事项

  1. 序列号溢出：对于 AES-CCM-16-64-128，发送方序列号（SSN）不得超过 2^23-1。uoscore 库会强制执行这一限制。

  2. 主密钥保护：主密钥必须安全存储（例如存放在安全存储中，或通过 EDHOC 派生）。

  3. 跨重启持久化：如果重启后复用同一个主密钥（即主密钥不会重新派生，例如通过 EDHOC 派生），则必须把发送方序列号持久化到非易失性存储器中，以防止 nonce 重用，否则会破坏机密性和完整性。接收方的重放窗口不需要持久化：它保存在内存中，重启后会按照 RFC 8613 附录 B.1.2 中的描述，使用 Echo 选项重新同步。

不支持 OSCORE 时的处理

当未启用 OSCORE 支持（未设置 CONFIG_COAP_OSCORE）时，Zephyr CoAP 协议栈按照 RFC 7252 第 5.4.1 节，对 OSCORE 选项采用失败即关闭的行为：

服务器行为（当 CONFIG_COAP_OSCORE=n 时）：

  • 带 OSCORE 选项的 CON 请求：返回 4.02（Bad Option） 响应

  • 带 OSCORE 选项的 NON 请求：静默拒绝（丢弃）该消息

  • 带 OSCORE 选项的 响应：对 CON 发送 RST，静默丢弃 NON/ACK
