概述

网络数据包是网络协议栈处理的主要数据。这类数据通过 net_pkt 结构体表示，该结构体提供了保存数据包、写入和读取数据包的手段，并包含核心层保存重要信息所需的元数据。本文档中将此类对象称为 net_pkt。

该数据结构及其相关的全部 API 定义在 include/zephyr/net/net_pkt.h 中。

架构说明

协议栈中有两条网络数据包流：用于发送路径的 TX 和用于接收路径的 RX。在这两条路径中，每个 net_pkt 都是从头到尾写入和读取的，更确切地说，是从报头到负载。

并发与线程安全

net_pkt 结构体及其相关 API 不是线程安全的。网络协议栈依赖严格的 独占所有权 模型。网络数据包被创建或接收后，在任一时刻都只归一个线程或执行上下文所有。

并发主要通过以下几种模式进行管理：

  • 通过 FIFO 转移所有权： net_pkt 最常见的生命周期是在相互隔离的执行上下文之间传递（例如从 RX 驱动线程传到 IP 协议栈）。数据包一旦入队，发送方就放弃其引用并失去访问权。

  • 浅克隆（``net_pkt_shallow_clone``）： 如果某个数据包必须由一层保留（例如 TCP 为可能的重传而保留），同时又要由另一层处理，则使用 net_pkt_shallow_clone() 创建一个新的包装对象，指向相同的底层只读数据（数据缓冲区本身采用线程安全的引用计数）。

  • 粗粒度协议锁： 当数据包被有意保存在内存队列中时，由更高层的子系统锁（例如连接互斥量）加以保护。

struct net_pkt 中的 atomic_ref 字段用于内存生命周期管理（防止释放后使用的情况），并不是用于并发修改的锁。

内存管理

分配

所有 net_pkt 对象都来自一个预定义的 struct net_pkt 池。此类池通过以下方式定义

NET_PKT_SLAB_DEFINE(name, count)

不过请注意，很少需要直接使用它，因为核心层已经提供了两个池，一个用于 TX 路径，一个用于 RX 路径。

可以通过以下方式分配一个原始 net_pkt：

pkt = net_pkt_alloc(timeout);

然而，原始 net_pkt 本质上在没有缓冲区的情况下毫无用处，还需要各种元数据信息才有意义。它至少需要知道将通过哪个网络接口发送，或是从哪个网络接口接收的。由于这是一个非常常见的操作，因此提供了一个辅助函数：

pkt = net_pkt_alloc_on_iface(iface, timeout);

还有一个更完整的分配函数，可以一次性分配 net_pkt 及其缓冲区：

pkt = net_pkt_alloc_with_buffer(iface, size, family, proto, timeout);

缓冲区的分配方式见下文。

缓冲区分配

net_pkt 对象不定义自己的缓冲区，而是使用一个现有对象：net_buf。（更多信息请参见 网络缓冲区。）不过，它在很大程度上隐藏了这种缓冲区的使用，因为 net_pkt 为缓冲区分配（以及后文将看到的缓冲区操作）引入了网络感知能力。

要分配缓冲区，net_pkt 至少需要设置好网络接口。在分配缓冲区时即使数据包的地址族未知，这也能工作。此时可以这样做：

net_pkt_alloc_buffer(pkt, size, proto, timeout);

如果协议未知，proto 可以为 0（不存在 IPPROTO_UNSPEC）。

如前所述，可以通过 net_pkt_alloc_with_buffer() 一次性分配 net_pkt 及其缓冲区。实际上这是使用最广泛的分配函数。

缓冲区分配会根据数据包的网络接口、地址族和协议来判断能否分配所请求的大小。具体来说，分配器会通过网络接口得知 MTU，再根据地址族和协议确定报头空间（如果只指定了这两项）。如果总大小能容纳在 MTU 之内，则分配的空间为请求的大小，可能再加上报头空间。如果 MTU 空间不足，请求的大小会被缩减，使可能的报头空间与新的大小一起能容纳在 MTU 之内。

例如，在 MTU 为 1500 字节的以太网网络接口上：

pkt = net_pkt_alloc_with_buffer(iface, 800, NET_AF_INET4, IPPROTO_UDP, K_FOREVER);

将为新的 net_pkt 成功分配 800 + 20 + 8 字节的缓冲区，其中：

pkt = net_pkt_alloc_with_buffer(iface, 1600, NET_AF_INET4, IPPROTO_UDP, K_FOREVER);

将成功分配 1500 字节，其中 20 + 8 字节（IPv4 + UDP 报头）不会用于负载。

在接收端，当地址族和协议未知时：

pkt = net_pkt_rx_alloc_with_buffer(iface, 800, AF_UNSPEC, 0, K_FOREVER);

将分配 800 字节，且没有额外的报头空间。但如果是：

pkt = net_pkt_rx_alloc_with_buffer(iface, 1600, AF_UNSPEC, 0, K_FOREVER);

将分配 1514 字节，即 MTU 加上以太网报头空间。

可以调用 net_pkt_alloc_buffer() 增加分配的缓冲区空间，因为它会考虑已有的缓冲区。如果 net_pkt 的地址族有效，它还会考虑报头空间以及 proto 参数。在这种情况下，新分配的缓冲区空间会追加到已有空间之后，而不是插入到前面。不过请注意，这种用例相当有限。通常，从一开始就应该知道需要请求多大的空间。

释放

每个 net_pkt 都有引用计数。分配时引用计数设为 1。可以使用 net_pkt_ref() 增加引用计数，使用 net_pkt_unref() 减少引用计数。当计数降为零时，缓冲区也会被解除引用，net_pkt 会自动放回空闲的 net_pkt_slabs 中

如果在 net_pkt 释放之后仍需要其缓冲区，则需要在最后一次调用 net_pkt_unref 之前，对整条 net_buf 链再增加一次引用。更多信息请参见 网络缓冲区。

操作

访问 net_pkt 缓冲区有两种方式，下面几节将分别说明：基本读/写访问和数据访问，推荐使用后者。

读写访问

如前所述，虽然 net_pkt 使用 net_buf 作为其缓冲区，但它提供了自己的 API 来访问缓冲区。实际上，一个网络数据包可能分散在一条 net_buf 对象链上，此时 net_buf 提供的函数就力不从心了。因此，net_pkt 提供了一组函数，隐藏了潜在的非连续访问所带来的全部复杂性。

数据在缓冲区中的移动通过每个 net_pkt 内部维护的游标进行。所有读/写操作都会影响该游标。另请注意，读写函数对其长度参数要求严格：如果无法读/写指定的长度，操作就会失败。长度并不被视为上限，而是必须读取或写入的确切数据量。

由于存在 TX 和 RX 两条路径，因此有两种访问模式：写入（write）和覆写（overwrite）。这听起来可能有点不寻常，但实际上很简单，而且提供了灵活性。

在写入模式下，写入缓冲区的任何内容都会影响缓冲区中实际数据的长度。不要把缓冲区长度与缓冲区大小混淆，后者是任何模式都无法超过的上限。而在覆写模式下，写入的内容必须落在有效数据上，并且不会影响缓冲区长度。默认情况下，新分配的 net_pkt 处于写入模式，其游标指向缓冲区的起始位置。

下面逐步介绍这些函数，以及它们在不同模式下的行为。

刚分配好 500 字节缓冲区时，net_pkt 的长度为 0，即其缓冲区中没有有效数据。可以这样验证：

len = net_pkt_get_len(pkt);

现在写入 8 个字节：

net_pkt_write(pkt, data, 8);

缓冲区长度现在为 8 字节。还有多种辅助函数，用于写入一个字节或大端序的 uint16_t、uint32_t。

net_pkt_write_u8(pkt, &foo);
net_pkt_write_be16(pkt, &ba);
net_pkt_write_be32(pkt, &bar);

从逻辑上讲，net_pkt 的长度现在为 15。但如果此时尝试读取，将会失败，因为 net_pkt 中当前游标位置之后没有可读的内容。在写入模式下，可以通过重置 net_pkt 的游标来读取已经写入的内容。例如：

net_pkt_cursor_init(pkt);
net_pkt_read(pkt, data, 15);

这会将 pkt 的游标重置到缓冲区的起始位置，然后就可以读取实际存在的 15 个字节。之后游标又会指向缓冲区的末尾。

要将一大片区域设置为同一个字节，可以使用提供的 memset 函数：

net_pkt_memset(pkt, 0, 5);

现在 net_pkt 的长度为 20 字节。

可以通过 net_pkt_set_overwrite() 函数切换模式，并且可以随时来回切换。net_pkt 会被设为覆写模式，并重置其游标：

net_pkt_set_overwrite(pkt, true);
net_pkt_cursor_init(pkt);

现在可以使用同样的操作函数，但它们仅限于缓冲区中已有的数据，即 20 字节。

如果需要知道 net_pkt 中还有多少可用空间，可以调用：

net_pkt_available_buffer(pkt);

或者，如果需要考虑报头空间，可以调用：

net_pkt_available_payload_buffer(pkt, proto);

如果要将游标放到某个已知位置，请使用 net_pkt_skip() 函数。例如，要跳过 IP 报头，可以使用：

net_pkt_cursor_init(pkt);
net_pkt_skip(pkt, net_pkt_ip_header_len(pkt));

数据访问

虽然前面介绍的 API 相当简单，但它总是需要在 net_pkt 缓冲区与外部之间来回复制数据。在很多场合，以连续方式访问缓冲区中存储的信息更为合适，对于内嵌报头的网络数据包尤其如此。

这些报头在大多数情况下都是一组已知的固定字节。因此，用一个结构体表示某种类型的报头会更加自然。此外，如果已知报头所占的空间位于缓冲区的连续区域中，那么将缓冲区中的实际位置直接强制转换为报头类型会高效得多。无论是读取还是写入这类报头的字段，直接访问都能节省内存。

net_pkt 为此提供了一套专用 API，构建在前面介绍的 API 之上。它可以透明地处理连续访问和非连续访问。

有两个宏用于定义数据访问描述符：当无法确定数据是否位于连续区域时使用 NET_PKT_DATA_ACCESS_DEFINE，当能保证数据位于连续区域时使用 NET_PKT_DATA_ACCESS_CONTIGUOUS_DEFINE。

以 IP 和 UDP 为例。IPv4 和 IPv6 报头总是位于数据包的开头，并且足够小，可以放入 128 字节的 net_buf 中（这只是举例，也可以选择 64 字节）。

NET_PKT_DATA_ACCESS_CONTIGUOUS_DEFINE(ipv4_access, struct net_ipv4_hdr);
struct net_ipv4_hdr *ipv4_hdr;

ipv4_hdr = (struct net_ipv4_hdr *)net_pkt_get_data(pkt, &ipv4_access);

对于 struct net_ipv4_hdr 也是如此。而 UDP 报头在 IPv6 等情况下很可能不在连续区域中，因此：

NET_PKT_DATA_ACCESS_DEFINE(udp_access, struct net_udp_hdr);
struct net_udp_hdr *udp_hdr;

udp_hdr = (struct net_udp_hdr *)net_pkt_get_data(pkt, &udp_access);

此时，net_pkt 的游标指向所请求数据的开头。在 RX 路径上，这些报头只会被读取而不会被修改，因此要继续处理，游标需要前进越过这些数据。有一个专门的函数用于此目的：

net_pkt_acknowledge_data(pkt, &ipv4_access);

然而，在 TX 路径上，报头字段已被修改。在这种情况下：

net_pkt_set_data(pkt, &ipv4_access);

如果数据位于连续区域，它会相应地前移游标；否则，它会写入数据并更新游标。注意，net_pkt_set_data() 也可以用于 RX 路径，但使用 net_pkt_acknowledge_data() 会稍快一些，因为它完全不关心数据是否连续，只是直接通过 net_pkt_skip() 前移游标。
