概述

QUIC 是一种在 RFC 9000 中标准化的通用多路复用传输协议。它运行在 UDP 之上，提供有序、可靠的字节流传输，并集成了 TLS 1.3 安全性（RFC 9001）、流多路复用和连接迁移。Zephyr 的 QUIC 实现位于 CONFIG_QUIC 下。

与嵌入式应用相关的主要特性：

  • 流多路复用：双向流和单向流共享同一个 UDP 套接字，避免了传输层的队头阻塞。

  • 集成 TLS 1.3：握手内置于连接建立过程中，不需要单独的 TLS 层。

  • 流量控制：基于额度的按流和按连接流量控制，防止快速发送方压垮资源受限的接收方。

  • 丢包恢复：探测超时（PTO）机制可在不依赖 ICMP 或 TCP 式 ACK 时钟的情况下重传数据。

  • 路径 MTU 发现：数据报分组层 PMTU 发现（DPLPMTUD，RFC 9000 第 14.3 节）在握手之后探测路径，并且只有在探测包得到确认后才增大发送大小。

  • 套接字集成：使用 zsock_send、zsock_recv、zsock_recvmsg、zsock_sendmsg、zsock_close 等标准 Zephyr 套接字调用进行数据传输。

  • 双栈：同时支持 IPv4 和 IPv6 连接。

备注

QUIC 支持目前在 Zephyr 中处于 实验阶段。使用 CONFIG_QUIC=y 启用它，并请注意 API 和 Kconfig 选项可能在不同版本之间发生变化。

架构与概念

要有效使用该库，了解 连接 与 流 之间的关系会很有帮助。

  • QUIC 连接套接字：表示通往对端的“隧道”。它负责 TLS 握手、拥塞控制和连接终止。通常不会直接通过该套接字发送应用数据，而是用它来创建流。

  • QUIC 流套接字：表示连接内部的一条轻量级数据通道。实际的应用数据（send 或 recv）就在这里流动。

应用程序工作流程

以下各节概述如何使用该库编写通用的客户端和服务器应用程序。

客户端应用程序

客户端发起到远程服务器的连接，打开一个流，发送请求，并读取响应。

第 1 步：设置地址

struct net_sockaddr_in remote_addr = {
    .sin_family = NET_AF_INET,
    .sin_port = net_htons(4422),
};

zsock_inet_pton(NET_AF_INET, "192.0.2.1", &remote_addr.sin_addr);

第 2 步：打开 QUIC 连接

int conn_sock = quic_connection_open((struct net_sockaddr *)&remote_addr, NULL);
if (conn_sock < 0) {
    /* Handle error */
}

/* The TLS handshake occurs automatically upon the first stream creation. */

第 3 步：打开流

/* Create a bidirectional stream initiated by the client */
int stream_sock = quic_stream_open(conn_sock,
                                   QUIC_STREAM_CLIENT,
                                   QUIC_STREAM_BIDIRECTIONAL,
                                   0);

第 4 步：传输数据

在 流套接字 而不是连接套接字上使用标准套接字调用。

zsock_send(stream_sock, "Hello Server", 12, 0);

char buffer[64];
zsock_recv(stream_sock, buffer, sizeof(buffer), 0);

第 5 步：清理

quic_stream_close(stream_sock);
quic_connection_close(conn_sock);

服务器应用程序

服务器绑定到本地端口，等待传入连接，接受流并处理数据。

第 1 步：绑定连接套接字

struct net_sockaddr_in local_addr = {
   .sin_family = NET_AF_INET,
   .sin_port = net_htons(4422),
   .sin_addr.s_addr = NET_INADDR_ANY,
};

/* Create the listening context */
int conn_sock = quic_connection_open(NULL, (struct net_sockaddr *)&local_addr);

第 2 步：接受传入的流

quic_connection_open() 返回的套接字充当“父”套接字。在 连接套接字 上使用 zsock_accept()，可以获取对端发起的新流的文件描述符。

struct net_sockaddr_in peer_addr;
net_socklen_t addrlen = sizeof(peer_addr);

/* Block until a client opens a stream */
int stream_sock = zsock_accept(conn_sock, (struct net_sockaddr *)&peer_addr, &addrlen);

if (stream_sock >= 0) {
    /* Handle the new stream (read/write data) */
    char buf[128];
    int len = zsock_recv(stream_sock, buf, sizeof(buf), 0);

    /* Echo back */
    zsock_send(stream_sock, buf, len, 0);

    /* Close the stream when done, also zsock_close() can be used */
    quic_stream_close(stream_sock);
}

TLS 与安全配置

QUIC 传输使用 Mbed TLS 和 PSA API 进行加密操作。安全凭据（证书、密钥）通过 Zephyr 的 TLS 凭据 子系统管理。

管理证书

在打开连接之前，必须使用 tls_credential_add() 注册证书。

  1. CA 证书：客户端验证服务器时需要。

  2. 服务器证书和私钥：服务器需要。

示例：加载凭据

#include <zephyr/net/tls_credentials.h>

/* Tag ID to reference credentials later */
#define MY_SEC_TAG 1

static const char server_cert[] = ...; /* PEM or DER data */
static const char priv_key[] = ...;    /* PEM or DER data */

void setup_credentials(void) {
    tls_credential_add(MY_SEC_TAG, TLS_CREDENTIAL_PUBLIC_CERTIFICATE,
                       server_cert, sizeof(server_cert));
    tls_credential_add(MY_SEC_TAG, TLS_CREDENTIAL_PRIVATE_KEY,
                       priv_key, sizeof(priv_key));
}

将凭据应用于 QUIC

在 连接套接字 创建之后，立即使用 zsock_setsockopt() 将凭据应用到 QUIC 套接字上。必须在创建流之前设置凭据。

对端证书验证遵循与 Zephyr TLS 套接字相同的默认策略：客户端默认要求对端验证成功，而服务器默认不验证客户端证书，除非显式启用了 ZSOCK_TLS_PEER_VERIFY。因此，未加载 CA 证书的客户端默认会握手失败；有意跳过服务器认证的应用程序必须通过 ZSOCK_TLS_PEER_VERIFY = MBEDTLS_SSL_VERIFY_NONE 显式选择退出。

sec_tag_t sec_tag_list[] = { MY_SEC_TAG };

zsock_setsockopt(conn_sock, ZSOCK_SOL_TLS, ZSOCK_TLS_SEC_TAG_LIST,
                 sec_tag_list, sizeof(sec_tag_list));

将 ALPN 应用于 QUIC

在 QUIC 中，应用层协议协商（ALPN）是必需的。ALPN 用于协商运行在两个 QUIC 端点之上的应用协议。在 连接套接字 创建之后，立即使用 zsock_setsockopt() 将 ALPN 列表应用到 QUIC 套接字上。必须在创建流之前设置 ALPN 列表。注意，列表项必须是常量，不能是变量。

const char * const alpn_list[] = {
    "echo-quic",
    NULL
};

ret = zsock_setsockopt(quic_sock, ZSOCK_SOL_TLS, ZSOCK_TLS_ALPN_LIST,
                            alpn_list, sizeof(alpn_list));
if (ret < 0) {
    LOG_ERR("Failed to set ALPN (%d)", -errno);
}

会话恢复与 0-RTT

完成一次完整握手后，服务器可以签发 TLS 1.3 NewSessionTicket。客户端可以保存由此得到的会话状态，并在之后的连接中出示它，从而无需完整握手即可 恢复 会话；在服务器允许的情况下，还可以在握手完成之前，在第一轮发送中就发送 0-RTT 早期数据。

0-RTT 支持通过 CONFIG_QUIC_0RTT 编译进来（默认禁用）。1-RTT 的会话恢复无需该选项即可工作；启用该选项会增加早期数据的提供/接受/重放处理。

警告

0-RTT 早期数据可能被网络攻击者 重放 （RFC 9001 第 9.2 节）。只能通过 0-RTT 发送幂等/可安全重放的操作的数据，并要做好对端拒绝它的准备（此时必须在握手完成后重试发送这些数据）。协议栈会使签发的票据只能使用一次，并应用一个票据时效的新鲜度窗口，但这种防重放状态只保存在内存中，且仅针对单个实例（重启后不会保留，也不会在多个服务器实例之间共享）。

客户端：导出并复用会话状态

握手完成后，从连接套接字读取可恢复的状态并保存。在新连接上，在打开第一个流之前导入该状态。当 0-RTT 就绪时，第一个流的数据会作为早期数据发送。

struct quic_session_state state;
net_socklen_t optlen = sizeof(state);

/* After the first connection's handshake completes: */
zsock_getsockopt(conn_sock, ZSOCK_SOL_QUIC, ZSOCK_QUIC_SO_SESSION_STATE,
                 &state, &optlen);

/* On a later connection, before the first stream is opened: */
zsock_setsockopt(new_conn_sock, ZSOCK_SOL_QUIC, ZSOCK_QUIC_SO_SESSION_STATE,
                 &state, sizeof(state));

由于 struct quic_session_state 包含恢复密钥，应将其视为敏感数据并安全存储。其布局通过 QUIC_SESSION_STATE_VERSION 进行版本管理。

服务器：签发票据并允许 0-RTT

在握手之前，在监听套接字（或服务器端连接套接字）上设置以下选项：

  • ZSOCK_QUIC_SO_SESSION_TICKET_ENABLE （指向 int 的指针）-- 非零值使服务器在握手后发送 NewSessionTicket，从而启用 1-RTT 会话恢复。

  • ZSOCK_QUIC_SO_MAX_EARLY_DATA_SIZE （指向 uint32_t 的指针）-- 任何非零值都会在新签发的票据上启用 0-RTT（并且需要 CONFIG_QUIC_0RTT，否则 setsockopt() 会以 ENOTSUP 失败）。按照 RFC 9001 第 4.6.1 节，票据中始终通告固定的哨兵值 0xffffffff；客户端实际可发送的早期数据量受连接的流量控制（传输参数）限制，因此该选项只是一个启用开关，而不是字节预算。

int enable = 1;
uint32_t early_data = 1; /* non-zero enables 0-RTT for issued tickets */

zsock_setsockopt(quic_sock, ZSOCK_SOL_QUIC, ZSOCK_QUIC_SO_SESSION_TICKET_ENABLE,
                 &enable, sizeof(enable));
zsock_setsockopt(quic_sock, ZSOCK_SOL_QUIC, ZSOCK_QUIC_SO_MAX_EARLY_DATA_SIZE,
                 &early_data, sizeof(early_data));

每个流的早期数据状态

在服务器上，可以在 流 套接字上使用 ZSOCK_QUIC_SO_STREAM_EARLY_DATA （指向 int 的指针）查询某个流是否携带了已被接受的 0-RTT 数据。这样协议层就可以实施重放保护（例如，HTTP/3 对非幂等的早期请求回复 425 Too Early）。

PSA 密钥槽

每个端点的数据包保护密钥都存放在 PSA 密钥槽中，密钥槽的数量在构建时由 CONFIG_MBEDTLS_PSA_KEY_SLOT_COUNT 确定。该选项的默认值不足以支持多于一个连接，而 QUIC 不会自动调整它。当没有空闲密钥槽时，新连接的握手会失败，日志中会给出相应提示。

确定数量时可参考以下数据：

  • 一个已建立的连接在每个端点上大约占用 5 个密钥槽。

  • 正在进行的握手在每个端点上短时间内最多需要约 14 个密钥槽。其中大多数会在握手过程中释放：开始使用 Handshake 数据包时释放 Initial 密钥，握手确认后释放 Handshake 密钥。

  • 一个监听套接字大约占用 2 个密钥槽。

  • 密钥更新时，每个端点会短暂地额外需要最多 3 个密钥槽。

端点是连接的一端。仅作为客户端或仅作为服务器的设备，每个连接有一个端点；当连接的两端运行在同一设备上时（例如环回测试），每个连接计算两次。应用程序其他部分使用的密钥槽需另外计算。

路径 MTU 发现（DPLPMTUD）

Zephyr 的 QUIC 协议栈按照 RFC 9000 第 14.3 节的描述执行 数据报分组层路径 MTU 发现 （DPLPMTUD）。RFC 8899 的搜索状态位于通用的 数据报 PLPMTUD API 子系统中；QUIC 负责提供探测数据包（PING 加填充）、禁止分片的 UDP 发送，并通过其恢复机制提供 ACK/丢失确认。

其目标是找到能够在不发生 IP 层分片的情况下穿越路径的最大 UDP 负载大小，然后将该大小用于应用数据包。

行为

TLS 握手完成后，协议栈可能会发送包含一个 PING 帧和填充的 探测数据报。探测包的大小用于检验更大的路径 MTU，并且在底层 UDP 套接字上启用 禁止分片 后发送（参见 IPv4 和 IPv6 套接字选项 中的 ZSOCK_IP_DONTFRAG / ZSOCK_IPV6_DONTFRAG）。这些都在内部处理，应用程序无需配置 QUIC 使用的 UDP 套接字。

协议栈跟踪三个相关的限值：

  • 对端 ``max_udp_payload_size`` 传输参数 - 远程端点在握手期间通告的上限。

  • 本地上限 - 由接口或套接字 MTU 减去 IP 和 UDP 报头开销得出。

  • 已验证的发送大小 - 经 ACK 确认的最大探测包大小。它决定了发出的 QUIC 数据包最大可以有多大。

发送大小从 QUIC 要求的 1200 字节最小 UDP 负载 开始。当已验证的大小低于本地上限和对端上限时，协议栈会通过二分查找寻找更大的可用大小。探测包被 ACK 后会提高已验证的限值；探测包多次丢失则会缩小搜索范围。流帧的大小会控制在当前已验证的限值之内，因此一旦探测成功，高 MTU 路径上的吞吐量就会自动提升。

与丢包恢复的交互

DPLPMTUD 探测包会引发 ACK，并与流数据共用同一套丢包恢复机制。发生探测超时（PTO）时，优先重传在途的流帧；只有在没有需要重传的流数据时（即本来会发送单纯 PING 探测包的情况下），才会发送 DPLPMTUD 探测包。

目前没有面向应用程序的 QUIC API 用于启用、禁用或调整 DPLPMTUD。只要可能存在更大的路径 MTU，握手完成后就会自动开始探测。实现自有 UDP 协议的传输层可以复用 数据报 PLPMTUD API 中记录的同一套通用 API。

配置选项

以下所有选项都位于 if QUIC 块内，只有启用 CONFIG_QUIC 时才可见。

2-3

4

QUIC 传输参数（流量控制）

这些值在握手期间通告给远程对端（参见 RFC 9000 第 18.2 节）。它们决定了 对端在收到窗口更新之前允许发送 多少数据。每个值都应与相应的本地接收缓冲区大小一致；通告的窗口大于接收缓冲区会导致缓冲区溢出，而通告的窗口小于缓冲区则不能充分利用可用内存。

CONFIG_QUIC_STREAM_RX_WINDOW_UPDATE_THRESHOLD

25

流接收缓冲区被消耗到多大百分比时发送 MAX_STREAM_DATA 帧以补充对端的窗口。较低的值（例如 15%）会更频繁地发送更新，从而以额外的控制帧为代价提升高延迟链路上的吞吐量。

缓冲区大小与 RAM 分配

以下选项直接控制 QUIC 子系统在初始化时分配多少 RAM。它们之间如何相互影响的详细分析，请参见 Memory Model。

选项

默认值

说明

CONFIG_QUIC_ENDPOINT_PENDING_DATA_LEN

1500

每个端点的接收暂存缓冲区大小，单位为字节。应等于网络 MTU。结合 CONFIG_QUIC_PKT_COUNT，端点 RX 暂存总量 = endpoints x pkt_count x this value。

CONFIG_QUIC_TX_BUFFER_SIZE

1500

每个端点的输出数据包组装缓冲区。至少应为网络 MTU（为符合 IPv6 要求，最小为 1280，最大为 1500）。在确认更大的路径 MTU 之前，DPLPMTUD 可能会将 已验证的 UDP 负载限制在该值以下；参见 路径 MTU 发现（DPLPMTUD）。

CONFIG_QUIC_CRYPTO_RX_BUFFER_SIZE

4096

每个端点共享的 CRYPTO 帧重组缓冲区，在 TLS 握手期间使用。由于 QUIC 依次经过各个加密级别（Initial -> Handshake -> Application），所有级别复用同一个缓冲区。要与浏览器互通，4096 字节是最小值：Chrome 和 Firefox 可能会把一个 ClientHello 拆分成 10 个或更多 CRYPTO 帧分片，总计可达约 4 KiB。对于使用小证书的嵌入式设备之间的部署，可减为 2048。范围：1024-8192。

CONFIG_QUIC_CRYPTO_OOO_SLOTS

8

每个端点的乱序 CRYPTO 帧元数据槽数量。每个槽（约 8 字节）记录一个乱序分片的偏移量和长度，直到其前面的空缺被填补。与浏览器互通需要 8 个槽；仅嵌入式部署时可减为 4。范围：4-16。

CONFIG_QUIC_STREAM_TX_BUFFER_SIZE

8192

每个流用于保存已发送但未确认数据的缓冲区。QUIC 发送方无法越过未确认窗口继续前进，因此在高延迟链路上，这是限制吞吐量的主要参数。其大小至少应为带宽时延积：throughput_bytes_per_ms x rtt_ms。

CONFIG_QUIC_STREAM_RX_BUFFER_SIZE

QUIC_STREAM_TX_BUFFER_SIZE

每个流的接收缓冲区。默认为 TX 缓冲区大小，这对于对称的请求/响应模式是最优的。对于非对称的工作负载（例如仅下载的流），可以单独减小。

CONFIG_QUIC_STREAM_OOO_SLOTS

4

每个流的乱序 STREAM 帧槽数量。每个槽最多保存 CONFIG_QUIC_STREAM_OOO_SEG_SIZE 字节。在无丢包的本地网络上设为 2；在乱序严重的 WAN 链路上增加到 8 或更多。

CONFIG_QUIC_STREAM_OOO_SEG_SIZE

1280

单个缓存的乱序分段的最大大小。将其设为 MTU 可以避免传入帧被分片。当乱序交付不常见时，可减为 512 字节。

CONFIG_QUIC_SENT_PKT_HISTORY_SIZE

64

最近发送数据包记录的环形缓冲区深度。每个条目约 24 字节。必须足够大，以同时覆盖所有在途数据包：至少为 ceil(STREAM_TX_BUFFER_SIZE / TX_BUFFER_SIZE) x 2。在有丢包或高延迟的 WAN 链路上增加到 128-256。

CONFIG_QUIC_TLS_TRANSCRIPT_BUF_LEN

4096

每个连接用于累积 TLS 1.3 握手记录（transcript）的缓冲区，该记录用于 Finished MAC 计算和 HKDF 密钥派生。4096 字节可以覆盖使用 RSA-2048 和 EC P-256 证书的典型 TLS 1.3 握手。对于更长的证书链或 RSA-4096，增加到 6144-8192。占用的 RAM 总量等于该值乘以 CONFIG_QUIC_MAX_CONTEXTS。

超时选项

选项

默认值

说明

CONFIG_QUIC_MAX_IDLE_TIMEOUT

30000

无活动多少毫秒后静默关闭连接。两个端点都会通告各自的值，取两者中较小者生效。设为 0 可完全禁用空闲超时。推荐值：5000 ms（环回）、10000 ms（LAN）、30000 ms（WAN）。

CONFIG_QUIC_CONNECT_TIMEOUT

3000

等待握手完成的毫秒数，超过此时间 connect() 调用将失败。为应对握手期间的丢包，该值至少应为预期 RTT 的 10 倍。

CONFIG_QUIC_MAX_PTO_TIMEOUT_MS

10000

PTO 指数退避的上限，单位为毫秒。每发生一次连续的探测超时，PTO 定时器就加倍：PTO_n = PTO_base x 2^n。该上限可以防止重传延迟过长。不应超过 CONFIG_QUIC_MAX_IDLE_TIMEOUT。

选项

默认值

说明

CONFIG_QUIC_SERVICE_THREAD_PRIO

NUM_PREEMPT_PRIORITIES

QUIC 服务分派器的线程优先级。>= 0 的值为抢占式（0 为最高）；< 0 的值为协作式。

CONFIG_QUIC_SERVICE_STACK_SIZE

CONFIG_QUIC_PKT_COUNT

内存模型

下表显示了各个 RAM 区域如何随配置参数变化。除非另有说明，所有大小的单位均为字节。

内存区域

计算公式

端点 RX 暂存区

QUIC_MAX_ENDPOINTS x QUIC_PKT_COUNT x QUIC_ENDPOINT_PENDING_DATA_LEN

端点 TX 缓冲区

QUIC_MAX_ENDPOINTS x QUIC_TX_BUFFER_SIZE

加密 RX 缓冲区

QUIC_MAX_ENDPOINTS x QUIC_CRYPTO_RX_BUFFER_SIZE

加密乱序槽

QUIC_MAX_ENDPOINTS x QUIC_CRYPTO_OOO_SLOTS x 8

流 TX 缓冲区

(QUIC_MAX_CONTEXTS x (QUIC_MAX_STREAMS_BIDI + QUIC_MAX_STREAMS_UNI)) x QUIC_STREAM_TX_BUFFER_SIZE

流 RX 缓冲区

(QUIC_MAX_CONTEXTS x (QUIC_MAX_STREAMS_BIDI + QUIC_MAX_STREAMS_UNI)) x QUIC_STREAM_RX_BUFFER_SIZE

流乱序缓冲区

total_streams x QUIC_STREAM_OOO_SLOTS x QUIC_STREAM_OOO_SEG_SIZE

已发送数据包历史

QUIC_MAX_CONTEXTS x QUIC_SENT_PKT_HISTORY_SIZE x 24

TLS 握手记录缓冲区

QUIC_MAX_CONTEXTS x QUIC_TLS_TRANSCRIPT_BUF_LEN

TLS 上下文（Mbed TLS）

约 8192 x QUIC_MAX_CONTEXTS （估算值；取决于密码套件）

连接状态

约 512 x QUIC_MAX_CONTEXTS

流状态

约 128 x total_streams

QUIC RAM 总量估算 （1 个连接、3 个双向流、1500 字节流缓冲区、LAN 客户端默认值时的粗略最小值）：

Endpoint RX staging :  2 x 1 x 1500 = 3 000 B
Endpoint TX         :  2 x 1500      = 3 000 B
Crypto RX buffers   :  2 x 2048      = 4 096 B  (embedded client, LAN)
Crypto OOO slots    :  2 x 4 x 8     =   256 B
Stream TX           :  3 x 1500      = 4 500 B
Stream RX           :  3 x 1500      = 4 500 B
OOO buffers         :  3 x 2 x 512   = 3 072 B
Sent-pkt history    :  1 x 16 x 24   =   384 B
TLS transcript      :  1 x 4096      = 4 096 B
TLS context         :  1 x 8192      = 8 192 B
State overhead      :  512 + 3x128   =   896 B
---------------------------------------------
Approximate total                   ~ 35 992 B (~35 KiB)

在流数量较少时，主要开销是每个连接的 Mbed TLS 上下文。流数量较多时，流的 TX/RX 缓冲区则成为主要开销。

Kconfig 优化器

要选出既节省内存又能维持目标吞吐量的缓冲区大小，需要在多个相互依赖的参数之间取得平衡。为此，Zephyr 提供了一个 Python 优化器脚本：

scripts/net/quic-kconfig-optimizer.py

该脚本接受部署场景的描述（连接数、MTU、网络类型、预期 RTT 和 RAM 预算），并输出一整套推荐的 CONFIG_ 值，同时给出 RAM 占用的估算明细和一段可直接粘贴的 prj.conf 片段。

前提条件

该脚本需要 Python 3.8 或更高版本，除标准库外不需要其他依赖。

python3 --version   # must be 3.8+

用法：交互模式

不带参数运行该脚本，即可进入引导式交互模式。每个提示都会在方括号中显示默认值；按 Enter 接受默认值。

最小 IoT 传感器（客户端、仅 IPv4、RAM 预算紧张）

一个传感器向云端点打开一个 QUIC 连接，使用单个双向流上报遥测数据，可供 QUIC 使用的 RAM 为 48 KiB：

python3 scripts/net/quic-kconfig-optimizer.py \
    --contexts 1 --streams-bidi 1 --streams-uni 0 \
    --mtu 1280 --ram-budget 49152 \
    --role client --ip-version ipv4 \
    --rtt-ms 80 --loss-rate 0.5 \
    --app-message-size 256 \
    --ooo-expected no --network-type wan

脚本会将流缓冲区设为 1500 B（最小值，因为 2 x 256 = 512 < 1500），将乱序槽设为 2，并将已发送数据包历史保持在 16 个条目，这些取值都是为了在尽量减少 RAM 的同时，仍能应对 WAN 链路上预期 0.5% 的丢包。

双栈服务器（IPv4 + IPv6，多个客户端）

一个边缘网关通过 IPv4 和 IPv6 接受最多四个并发的客户端连接，可供 QUIC 使用的 RAM 为 256 KiB：

python3 scripts/net/quic-kconfig-optimizer.py \
    --contexts 4 --streams-bidi 3 --streams-uni 1 \
    --mtu 1500 --ram-budget 262144 \
    --role server --ip-version both \
    --rtt-ms 5 --loss-rate 0.0 \
    --app-message-size 8192 \
    --ooo-expected no --network-type lan

脚本会推荐三个端点（两个用于监听套接字，每个客户端地址族一个），并将流缓冲区设为 16 KiB（以容纳 2 条 8192 B 的消息）。在 4 个上下文、每个上下文 4 个流的情况下，这部分将占据 RAM 预算的大头。

有丢包的高吞吐量 WAN 链路

一个通过蜂窝 WAN 连接、存在明显丢包的数据汇聚设备，需要为固件更新负载维持持续的吞吐量：

python3 scripts/net/quic-kconfig-optimizer.py \
    --contexts 1 --streams-bidi 2 --streams-uni 0 \
    --mtu 1400 --ram-budget 0 \
    --role client --ip-version ipv4 \
    --rtt-ms 150 --loss-rate 3.0 \
    --app-message-size 32768 \
    --ooo-expected yes --network-type wan

此时脚本会将流缓冲区加倍（丢包率 >= 2%），并选择 15% 的窗口更新阈值（高延迟 WAN），以保持对端的发送窗口打开，最大限度地利用管道。它还会将乱序槽设为 8、分段大小设为 1280 字节，以应对蜂窝网络的乱序。

调优指南

先使用优化器的默认值，然后进行测量。 脚本的启发式规则比较保守。在决定增大缓冲区之前，请使用 Zephyr 网络统计（CONFIG_NET_STATISTICS）观察实际的流窗口停滞和乱序事件。

流缓冲区是 RAM 开销的最大来源。 在多连接设备上，contexts x streams x 2 x stream_buf 占主导。将流缓冲区大小减半可按比例节省内存。只有在分析表明发送方持续停滞时，才应将其增大到超过带宽时延积（BDP）。

连接级窗口不能成为瓶颈。 CONFIG_QUIC_INITIAL_MAX_DATA 必须大于或等于最大的单流窗口；否则，即使各个流的窗口都是打开的，连接级上限也会限制吞吐量。

CRYPTO 缓冲区随端点数而非连接数增长。 CONFIG_QUIC_CRYPTO_RX_BUFFER_SIZE 和 CONFIG_QUIC_CRYPTO_OOO_SLOTS 每个端点分配一次，因此其 RAM 开销为 QUIC_MAX_ENDPOINTS x buffer_size。要与浏览器互通，需要使用 4096 字节的默认值（Chrome 和 Firefox 会将 ClientHello 拆分为许多小的 CRYPTO 帧）；在对端同样是 Zephyr 设备的纯嵌入式部署中，可减为 2048。

IPv4 映射的 IPv6。 当同时需要 IPv4 和 IPv6 时，启用 CONFIG_QUIC_ENDPOINT_USE_IPV4_MAPPING_TO_IPV6 可以让一个 UDP 套接字同时服务两个地址族，从而将 CONFIG_QUIC_MAX_ENDPOINTS 减一，并节省相关的缓冲区 RAM。

禁用未使用的流方向。 如果应用程序只使用客户端发起的流，请将 CONFIG_QUIC_MAX_STREAMS_UNI 设为 0。优化器会自动考虑这一点。

乱序内存是按流分配的。 QUIC_STREAM_OOO_SLOTS x QUIC_STREAM_OOO_SEG_SIZE x total_streams 可能相当可观。在可靠的 LAN 上，将 CONFIG_QUIC_STREAM_OOO_SLOTS 设为 2、将 CONFIG_QUIC_STREAM_OOO_SEG_SIZE 设为 512 是安全的，每个连接可节省数 KiB。
