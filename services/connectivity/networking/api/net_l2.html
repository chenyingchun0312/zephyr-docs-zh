概述

L2 协议栈的设计目的是对上层网络协议栈隐藏整个网络链路层部分及相关的设备驱动。这是通过 include/zephyr/net/net_if.h 中声明的 net_if 实现的。

除了 net_if 对象以及 L2 层在 include/zephyr/net/net_l2.h 中以 net_l2 形式提供的通用 API 之外，上层不了解任何实现细节。

只有 L2 层可以与关联到 net_if 对象的设备驱动通信。L2 层规定了设备驱动所提供的 API，这些 API 针对该设备，并为二者协同工作而优化。

目前已有用于 以太网、IEEE 802.15.4 Soft-MAC、CANBUS、OpenThread、Wi-Fi 的 L2 层，以及一个可用作编写新 L2 层模板的 dummy 层示例。

L2 层 API

要创建一个 L2 层或某个特定 L2 层的驱动，需要了解 L3 层如何与之交互，以及 L2 层应有的行为。更多细节另请参见 网络协议栈架构。通用 L2 API 包含以下函数：

  • recv()：所有设备驱动在收到数据包并将其放入 net_pkt 后，都会通过 net_recv_data() 把该缓冲区推送给网络协议栈。此时网络协议栈并不知道如何处理它，而是把缓冲区交给 L2 协议栈的 recv() 函数处理。L2 协议栈对数据包执行所需的处理，例如解析链路层头部，或处理仅属于链路层的数据包。如果数据包有错误，recv() 函数返回 NET_DROP；如果数据包已被 L2 完全消耗，返回 NET_OK；如果网络协议栈接下来应处理该数据包，返回 NET_CONTINUE。

  • send()：与接收函数类似，网络协议栈会调用该函数来实际发送网络数据包。所有相关的链路层内容都由该函数生成并添加。send() 函数返回已发送的字节数；如果发送网络数据包失败，则返回负的错误码。

  • enable()：该函数用于启用/禁用网络接口上的流量。出错时返回 <0，无错误时返回 >=0。

  • get_flags()：该函数返回 L2 驱动的能力，例如 L2 是否支持组播或混杂模式。

网络设备驱动

网络设备驱动完全以 Zephyr 设备驱动模型为基础。请参阅 设备驱动模型。

不过存在两点区别：

  • driver_api 指针必须指向一个有效的 net_if_api 指针。

  • 网络设备驱动必须使用 NET_DEVICE_INIT_INSTANCE()，以太网设备则使用 ETH_NET_DEVICE_INIT()。这些宏会调用 DEVICE_DEFINE() 宏，并实例化一个与所创建的设备驱动实例相关联的唯一 net_if。

网络设备驱动的实现取决于它所属的 L2 协议栈：以太网、IEEE 802.15.4 等。下一节将描述设备驱动在接收或发送网络数据包时应有的行为。其余部分与硬件相关，此处不再详述。

以太网设备驱动

接收时，由设备驱动负责向网络数据包中填充所需数量的数据缓冲区。网络数据包本身是一个 net_pkt，应通过 net_pkt_rx_alloc_with_buffer() 分配。之后所有数据缓冲区都会由 net_pkt_write() 自动分配和填充。

接收完所有网络数据后，设备驱动需要调用 net_recv_data()。如果该调用失败，则由设备驱动负责通过 net_pkt_unref() 释放对该缓冲区的引用。

发送时，设备驱动的发送函数会被调用，由设备驱动负责连同所有缓冲区一次性发送整个网络数据包。

每个以太网设备驱动最终都需要像下面这样调用 ETH_NET_DEVICE_INIT()：

ETH_NET_DEVICE_INIT(..., CONFIG_ETH_INIT_PRIORITY,
                    &the_valid_net_if_api_instance, 1500);

IEEE 802.15.4 设备驱动

IEEE 802.15.4 L2 的设备驱动与以太网的基本相同。上面所述的内容，尤其是关于 recv() 的部分，在这里同样适用。不过存在两点特定区别：

  • 它需要一个专用的设备驱动 API：ieee802154_radio_api，它重载了 net_if_api。这是因为 802.15.4 L2 对设备驱动的需求不止 send() 和 recv() 函数。该专用 API 声明于 include/zephyr/net/ieee802154_radio.h。每个 IEEE 802.15.4 设备驱动都必须提供一个指向已正确填充的此类 API 结构体的有效指针。

  • 发送数据包与以太网略有不同。大多数 IEEE 802.15.4 PHY 只支持相对较小的帧，总共 127 字节，包括帧头、负载和帧校验和。要通过无线电发送的缓冲区往往无法满足这一帧大小限制，例如包含 IPv6 数据包的缓冲区经常需要被拆分为多个分片，并且 IPv6 数据包头部和分片需要先使用 6LoWPAN 等协议压缩，然后才能交给无线电驱动。此外，IEEE 802.15.4 标准还定义了介质访问（例如 CSMA/CA）、帧重传、加密以及其他预处理过程（例如添加信息元素），各个无线电驱动不应需要关心这些。因此，ieee802154_radio_api 要求一个 tx 函数指针，它不同于 net_if_api 的 send 函数指针。Zephyr 原生的 IEEE 802.15.4 L2 实现提供了一个通用的 ieee802154_send() 作为替代，用作 net_if 的 send 函数。ieee802154_send() 的实现负责 IEEE 802.15.4 标准的数据包准备过程：把数据包拆分为可能经过压缩、加密及其他预处理的分片缓冲区，通过 ieee802154_radio_api 的 tx 函数一次发送一个缓冲区，并且只有在整个传输成功或失败之后才释放对网络数据包的引用。

IEEE 802.15.4 无线电设备驱动与 L2 之间的交互是双向的：

  • L2 -> L1：诸如 ieee802154_send() 的方法以及若干 IEEE 802.15.4 网络管理调用会调用到驱动中，例如通过无线电链路发送数据包，或在运行时重新配置驱动。这些传入调用全部由 ieee802154_radio_api 中的方法处理。

  • L1 -> L2：在一些情况下，驱动需要发起对 L2/MAC 层的调用。在这些情况下，Zephyr 的 IEEE 802.15.4 L1 -> L2 适配 API 采用“控制反转”模式，避免在相互独立的驱动实现中重复复杂逻辑；每当需要反向传递信息或硬件与 L2 紧密协作时，该模式都能确保与具体实现无关的松耦合，以及 MAC（L2）与 PHY（L1）之间清晰的关注点分离。例如在驱动初始化期间，驱动会调用 ieee802154_init()，把接口的 MAC 地址以及其他硬件相关配置传给 L2。类似地，驱动可以向 L2 指示需要与硬件紧密集成的性能或时序关键的无线电事件（例如 ieee802154_handle_ack()）。从 L1 到 L2 的调用不是作为 ieee802154_radio_api 中的方法实现的，而是独立函数，并在 include/zephyr/net/ieee802154_radio.h 中按此声明和记录。API 文档会明确说明哪些函数必须由所有 L2 协议栈实现，作为 L1 -> L2“控制反转”适配 API 的一部分。

注意：include/zephyr/net/ieee802154_radio.h 中未被明确记录为回调的独立函数被视为 PHY（L1）层内的辅助函数，其实现独立于任何特定的 L2 协议栈，例如 ieee802154_is_ar_flag_set()。

与所有网络接口一样，IEEE 802.15.4 设备驱动实现最终都必须调用 NET_DEVICE_INIT_INSTANCE()：

NET_DEVICE_INIT_INSTANCE(...,
                         the_device_init_prio,
                         &the_valid_ieee802154_radio_api_instance,
                         IEEE802154_L2,
                         NET_L2_GET_CTX_TYPE(IEEE802154_L2), 125);
