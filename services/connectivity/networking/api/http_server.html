概述

Zephyr 提供了一个 HTTP 服务器库，可以注册 HTTP 服务以及与这些服务关联的 HTTP 资源。服务器为每个已注册的服务创建一个监听套接字，并处理传入的客户端连接。可以通过普通 TCP 套接字（HTTP）或 TLS 套接字（HTTPS）进行通信。支持 HTTP/1.1（RFC 2616）、HTTP/2（RFC 9113）和 HTTP/3（RFC 9114）协议版本。

服务器的运行通常对应用程序透明，它在后台线程中运行。应用程序可以通过相应的 API 函数控制服务器的活动。

某些资源类型（例如动态资源）提供针对资源的应用程序回调，使服务器能够与应用程序交互（例如提供资源内容或处理请求负载）。

目前支持以下资源类型：

  • 静态资源：内容在编译时定义，运行时不能修改（HTTP_RESOURCE_TYPE_STATIC）。

  • 静态文件系统资源：文件系统的挂载路径以及提供该文件系统的 URL 在构建时固定，但文件系统中的内容可以动态改变。这意味着 HTTP 服务器之外的其他代码可以创建、修改或删除这些文件（HTTP_RESOURCE_TYPE_STATIC_FS）。

  • 动态资源：内容在运行时由相应的应用程序回调提供（HTTP_RESOURCE_TYPE_DYNAMIC）。

  • Websocket 资源：允许与服务器建立 Websocket 连接（HTTP_RESOURCE_TYPE_WEBSOCKET）。

Zephyr 提供了一个示例，演示 HTTP(s) 服务器的运行以及各种资源类型的用法。更多信息请参见 HTTP Server。

服务器设置

要在应用程序中启用 HTTP 服务器功能，需要满足几个前提条件。

首先，必须在应用程序配置文件中通过 Kconfig 选项 CONFIG_HTTP_SERVER 启用 HTTP 服务器：

prj.conf
CONFIG_HTTP_SERVER=y

所有 HTTP 服务和 HTTP 资源都放在专用的链接器段中。服务的链接器段已在本地预定义，但应用程序负责为与各服务关联的资源定义链接器段。资源的链接器段名称应以 http_resource_desc_ 为前缀，后接服务名称。

资源的链接器段应在链接器文件中定义。例如，对于名为 my_service 的服务，链接器段应按如下方式定义：

sections-rom.ld
#include <zephyr/linker/iterable_sections.h>

ITERABLE_SECTION_ROM(http_resource_desc_my_service, Z_LINK_ITERABLE_SUBALIGN)

最后，必须使用 CMake 把链接器文件和链接器段添加到应用程序中：

CMakeLists.txt
zephyr_linker_sources(SECTIONS sections-rom.ld)
zephyr_linker_section(NAME http_resource_desc_my_service
                      KVMA RAM_REGION GROUP RODATA_REGION)

备注

需要为系统中注册的每个 HTTP 服务定义一个单独的链接器段。

使用示例

服务

应用程序需要使用 HTTP_SERVICE_DEFINE 宏定义一个（或多个）HTTP 服务，其名称与链接器段所用的名称相同：

#include <zephyr/net/http/service.h>

static uint16_t http_service_port = 80;

HTTP_SERVICE_DEFINE(my_service, "0.0.0.0", &http_service_port, 1, 10, NULL, NULL, NULL);

也可以使用 HTTPS_SERVICE_DEFINE 定义 HTTPS 服务：

#include <zephyr/net/http/service.h>
#include <zephyr/net/tls_credentials.h>

#define HTTP_SERVER_CERTIFICATE_TAG 1

static uint16_t https_service_port = 443;
static const sec_tag_t sec_tag_list[] = {
    HTTP_SERVER_CERTIFICATE_TAG,
};

HTTPS_SERVICE_DEFINE(my_service, "0.0.0.0", &https_service_port, 1, 10,
                     NULL, NULL, NULL, sec_tag_list, sizeof(sec_tag_list));

按服务配置

HTTP 服务支持单独的服务配置，目前只包括通过 http_service_config 结构体创建套接字。这使应用程序可以定制套接字的创建行为，例如设置特定的套接字选项或使用自定义套接字类型。

要使用自定义套接字创建：

static int my_socket_create(const struct http_service_desc *svc, int af, int proto)
{
    int fd;

    /* Create socket with custom parameters */
    fd = zsock_socket(af, SOCK_STREAM, proto);
    if (fd < 0) {
        return fd;
    }

    /* Set custom socket options */
    /* Add any other custom socket configuration */

    return fd;
}

static const struct http_service_config my_service_config = {
    .socket_create = my_socket_create,
};

static uint16_t http_service_port = 80;

HTTP_SERVICE_DEFINE(my_service, "0.0.0.0", &http_service_port, 1, 10,
                    NULL, NULL, &my_service_config);

自定义套接字创建函数接收以下参数：- svc：指向服务描述符的指针 - af：地址族（NET_AF_INET 或 NET_AF_INET6）- proto：协议（NET_IPPROTO_TCP，HTTPS 则为 NET_IPPROTO_TLS_1_2）

该函数成功时应返回套接字文件描述符，失败时应返回负的错误码。

如果不需要自定义配置，只需为 config 参数传入 NULL：

HTTP_SERVICE_DEFINE(my_service, "0.0.0.0", &http_service_port, 1, 10,
                    NULL, NULL, NULL);

回退资源

定义 HTTP/HTTPS 服务时，可以使用 _res_fallback 参数指定一个回退资源，当没有其他资源与 URL 匹配时就使用该资源。例如，可以用它为所有未知路径提供首页（适用于在前端处理路由的单页应用），或提供自定义的 404 响应。

static int default_handler(struct http_client_ctx *client, enum http_transaction_status status,
                   const struct http_request_ctx *request_ctx,
                   struct http_response_ctx *response_ctx, void *user_data)
{
    static const char response_404[] = "Oops, page not found!";

    if (status == HTTP_SERVER_REQUEST_DATA_FINAL) {
        response_ctx->status = 404;
        response_ctx->body = response_404;
        response_ctx->body_len = sizeof(response_404) - 1;
        response_ctx->final_chunk = true;
    }

    return 0;
}

static struct http_resource_detail_dynamic default_detail = {
    .common = {
        .type = HTTP_RESOURCE_TYPE_DYNAMIC,
        .bitmask_of_supported_http_methods = BIT(HTTP_GET),
    },
    .cb = default_handler,
    .user_data = NULL,
};

/* Register a fallback resource to handle any unknown path */
HTTP_SERVICE_DEFINE(my_service, "0.0.0.0", &http_service_port, 1, 10, NULL, &default_detail, NULL);

备注

HTTPS 服务依赖于在系统中注册的 TLS 凭据。关于如何在系统中配置 TLS 凭据，请参见 TLS 凭据子系统。

定义 HTTP(s) 服务后，就可以使用 HTTP_RESOURCE_DEFINE 宏为其注册资源。

应用程序可以通过启用 CONFIG_HTTP_SERVER_RESOURCE_WILDCARD 选项来启用资源通配符支持。设置该选项后，只用一个资源处理函数就可以匹配多个传入的 HTTP 请求。URL 路径中的模式使用 POSIX API 函数 fnmatch() 进行匹配。

示例：

HTTP_RESOURCE_DEFINE(my_resource, my_service, "/foo*", &resource_detail);

这会匹配所有以字符串 foo 开头的 URL。模式匹配语法的说明请参见 POSIX.2 第 2.13 章。

静态资源

静态资源的内容在构建时定义，且不可更改。下面的示例展示了如何在应用程序中把经过 gzip 压缩的网页定义为静态资源：

static const uint8_t index_html_gz[] = {
    #include "index.html.gz.inc"
};

struct http_resource_detail_static index_html_gz_resource_detail = {
    .common = {
        .type = HTTP_RESOURCE_TYPE_STATIC,
        .bitmask_of_supported_http_methods = BIT(HTTP_GET),
        .content_encoding = "gzip",
    },
    .static_data = index_html_gz,
    .static_data_len = sizeof(index_html_gz),
};

HTTP_RESOURCE_DEFINE(index_html_gz_resource, my_service, "/",
                     &index_html_gz_resource_detail);

资源内容及其内容编码由应用程序决定。对于上面的示例，可以在应用程序的 CMakeLists.txt 文件中添加以下代码，在构建期间生成经过 gzip 压缩的网页：

CMakeLists.txt
set(gen_dir ${ZEPHYR_BINARY_DIR}/include/generated/)
set(source_file_index src/index.html)
generate_inc_file_for_target(app ${source_file_index} ${gen_dir}/index.html.gz.inc --gzip)

其中 src/index.html 是要压缩的网页的位置。

静态文件系统资源

静态文件系统资源的内容在构建时定义，且不可更改。注意，只支持 GET 操作，用户无法向文件系统上传文件。下面的示例展示了如何在应用程序中把路径定义为静态资源：

struct http_resource_detail_static_fs static_fs_resource_detail = {
    .common = {
        .type                              = HTTP_RESOURCE_TYPE_STATIC_FS,
        .bitmask_of_supported_http_methods = BIT(HTTP_GET),
    },
    .fs_path = "/lfs1/www",
};

HTTP_RESOURCE_DEFINE(static_fs_resource, my_service, "*", &static_fs_resource_detail);

位于 /lfs1/www 中的所有文件都可供客户端访问。如果文件经过 gzip 压缩，文件名必须加上 .gz 后缀（例如 index.html.gz），这样当客户端请求 index.html 时，服务器会发送 index.html.gz，并在 HTTP 头部中添加 gzip 内容编码。

内容类型根据文件扩展名确定。服务器支持 .html、.js、.css、.jpg、.png 和 .svg。可以使用 HTTP_SERVER_CONTENT_TYPE 宏提供更多内容类型。所有其他文件都以 text/html 内容类型提供。

HTTP_SERVER_CONTENT_TYPE(json, "application/json")

从静态文件系统提供文件时，可以使用 Kconfig 选项 CONFIG_HTTP_SERVER_STATIC_FS_RESPONSE_SIZE 配置响应分块大小。它决定了向客户端传输文件内容时每个分块的大小。

动态资源

对于动态资源，需要注册一个资源回调，用于在服务器与应用程序之间交换数据。

下面的示例代码展示了如何使用一个简单的资源处理函数注册动态资源，该处理函数会把收到的数据回显给客户端：

static int dyn_handler(struct http_client_ctx *client, enum http_transaction_status status,
                       const struct http_request_ctx *request_ctx,
                       struct http_response_ctx *response_ctx, void *user_data)
{
#define MAX_TEMP_PRINT_LEN 32
    static char print_str[MAX_TEMP_PRINT_LEN];
    enum http_method method = client->method;
    static size_t processed;

    __ASSERT_NO_MSG(request_ctx->data != NULL);

    if (status == HTTP_SERVER_TRANSACTION_ABORTED ||
        status == HTTP_SERVER_TRANSACTION_COMPLETE) {
        if (status == HTTP_SERVER_TRANSACTION_ABORTED) {
            LOG_DBG("Transaction aborted after %zd bytes.", processed);
        }
        processed = 0;
        return 0;
    }

    processed += request_ctx->data_len;

    snprintf(print_str, sizeof(print_str), "%s received (%zd bytes)",
             http_method_str(method), request_ctx->data_len);
    LOG_HEXDUMP_DBG(request_ctx->data, request_ctx->data_len, print_str);

    if (status == HTTP_SERVER_REQUEST_DATA_FINAL) {
        LOG_DBG("All data received (%zd bytes).", processed);
        processed = 0;
    }

    /* Echo data back to client */
    response_ctx->body = request_ctx->data;
    response_ctx->body_len = request_ctx->data_len;
    response_ctx->final_chunk = (status == HTTP_SERVER_REQUEST_DATA_FINAL);

    return 0;
}

struct http_resource_detail_dynamic dyn_resource_detail = {
    .common = {
        .type = HTTP_RESOURCE_TYPE_DYNAMIC,
        .bitmask_of_supported_http_methods =
            BIT(HTTP_GET) | BIT(HTTP_POST),
    },
    .cb = dyn_handler,
    .user_data = NULL,
};

HTTP_RESOURCE_DEFINE(dyn_resource, my_service, "/dynamic",
                     &dyn_resource_detail);

对于单个请求，资源回调可能会被调用多次，因此应用程序应能够跟踪数据接收的进度。

status 字段告知应用程序服务器向应用程序传递请求负载的进度。只要状态报告为 HTTP_SERVER_REQUEST_DATA_MORE，应用程序就应预期在后续的回调调用中还会收到更多数据。当所有请求负载都已传给应用程序后，服务器报告 HTTP_SERVER_REQUEST_DATA_FINAL 状态。如果在请求处理期间发生通信错误（例如客户端在完整负载接收完之前关闭了连接），服务器报告 HTTP_SERVER_TRANSACTION_ABORTED。当响应已完整发送给客户端时，服务器报告 HTTP_SERVER_TRANSACTION_COMPLETE 状态。这两个事件中的任何一个都表示请求处理已结束，应用程序应重置为该资源记录的所有进度，并等待新请求到来。服务器保证同一时间只有一个客户端可以访问该资源。

request_ctx 参数用于向应用程序传递请求数据：

  • data 和 data_len 字段向应用程序传递请求数据。

  • 如果启用了 CONFIG_HTTP_SERVER_CAPTURE_HEADERS，headers、header_count 和 headers_status 字段会向应用程序传递请求头部。这些字段只在请求的第一次回调中填充；详情请参见 访问请求头部。

应用程序使用 response_ctx 字段向 HTTP 服务器传递响应数据：

  • status 字段允许应用程序发送 HTTP 响应码。如果未填充，响应码默认为 200。

  • 应用程序可以使用 headers 和 header_count 字段发送任意 HTTP 头部。如果未填充，默认只发送 Transfer-Encoding 和 Content-Type。如有需要，回调可以覆盖 Content-Type。

  • body 和 body_len 字段用于发送正文数据。

  • final_chunk 字段用于表示应用程序已没有更多响应数据要发送。

头部和/或响应码只能在第一个被填充的 response_ctx 中发送，之后的回调中只允许发送后续的正文数据。

服务器会持续调用资源回调，直到它把所有请求数据都提供给应用程序，并且应用程序报告没有更多数据要放入应答中。

Websocket 资源

Websocket 资源会注册一个应用程序回调，在发生 Websocket 连接升级时调用。回调会收到与底层 TCP/TLS 连接对应的套接字描述符。一旦被调用，应用程序就完全接管该套接字，即负责在用完后将其释放。

static int ws_socket;
static uint8_t ws_recv_buffer[1024];

int ws_setup(int sock, struct http_request_ctx *request_ctx, void *user_data)
{
    ws_socket = sock;
    return 0;
}

struct http_resource_detail_websocket ws_resource_detail = {
    .common = {
        .type = HTTP_RESOURCE_TYPE_WEBSOCKET,
        /* We need HTTP/1.1 Get method for upgrading */
        .bitmask_of_supported_http_methods = BIT(HTTP_GET),
    },
    .cb = ws_setup,
    .data_buffer = ws_recv_buffer,
    .data_buffer_len = sizeof(ws_recv_buffer),
    .user_data = NULL, /* Fill this for any user specific data */
};

HTTP_RESOURCE_DEFINE(ws_resource, my_service, "/", &ws_resource_detail);

上面这个最简示例展示了如何使用一个简单的回调注册 Websocket 资源，该回调只用于保存所提供的套接字描述符。对 Websocket 连接的进一步处理由应用程序决定，超出了本指南的范围。基于 Websocket 的回显服务实现示例请参见 HTTP Server。

访问请求头部

应用程序可以登记它关注的特定 HTTP 请求头部。这些头部随后会针对每个传入请求进行存储，并可在动态资源回调中访问。

重要

捕获的请求头部 只在 给定请求的 第一次回调中 传递给应用程序。在同一请求的后续回调中，request_ctx 的 headers、header_count 和 headers_status 字段会被清除（headers_status 变为 HTTP_HEADER_STATUS_NONE）。应用程序必须在第一次回调期间把所需的头部值复制出来，而不是稍后再读取。

注意，第一次回调可能也可能不会同时携带请求正文数据（这取决于 HTTP 方法和传输分帧）。不要以是否存在正文数据作为处理头部的条件：始终检查 headers_status，并在其不为 HTTP_HEADER_STATUS_NONE 时保存头部。

必须先通过 Kconfig 选项 CONFIG_HTTP_SERVER_CAPTURE_HEADERS 启用此功能。

然后，应用程序就可以登记要捕获的头部，并在动态资源回调中读取其值。推荐的模式是在第一次回调中把关注的头部复制出来，等收到完整的请求正文后再进行处理：

HTTP_SERVER_REGISTER_HEADER_CAPTURE(capture_user_agent, "User-Agent");

static char user_agent[64];

static int dyn_handler(struct http_client_ctx *client, enum http_transaction_status status,
                       const struct http_request_ctx *request_ctx,
                       struct http_response_ctx *response_ctx, void *user_data)
{
    /* Request headers are only present in the first callback, so copy out
     * any values needed later before they are gone.
     */
    if (request_ctx->headers_status != HTTP_HEADER_STATUS_NONE) {
        for (size_t i = 0; i < request_ctx->header_count; i++) {
            const struct http_header *hdr = &request_ctx->headers[i];

            LOG_INF("Captured header: '%s: %s'", hdr->name, hdr->value);

            if (strcasecmp(hdr->name, "User-Agent") == 0) {
                strncpy(user_agent, hdr->value, sizeof(user_agent) - 1);
            }
        }
    }

    /* Process request body data (may be empty in the first callback). */

    if (status == HTTP_SERVER_REQUEST_DATA_FINAL) {
        /* Full request received: act on the body together with the header
         * values stashed above (e.g. user_agent).
         */
    }

    return 0;
}
