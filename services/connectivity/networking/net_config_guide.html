本文介绍如何根据系统中的可用资源设置各种网络配置选项。

网络缓冲区配置选项

网络缓冲区配置选项控制可以同时发送或接收多少数据。

CONFIG_NET_PKT_RX_COUNT

可以同时接收的网络数据包的最大数量。

CONFIG_NET_PKT_TX_COUNT

可以同时等待发送的网络数据包的最大数量。

CONFIG_NET_BUF_RX_COUNT

为接收数据分配的网络缓冲区数量。每个 net_buf 包含一个小的头部和一个固定长度或可变长度的数据缓冲区。设置 CONFIG_NET_BUF_FIXED_DATA_SIZE 时使用 CONFIG_NET_BUF_DATA_SIZE，这是默认设置。缓冲区的默认大小为 128 字节。

CONFIG_NET_BUF_VARIABLE_DATA_SIZE 是一项实验性设置。在该设置下，每个 net_buf 的数据部分从内存池中分配，大小可以等于从网络接收到的数据量。从网络接收数据时，数据被放入 net_buf 的数据部分。根据设备资源和预期的网络使用情况，用户可以通过设置 CONFIG_NET_BUF_DATA_SIZE 调整固定缓冲区的大小；如果使用可变大小缓冲区，则可以通过设置 CONFIG_NET_PKT_BUF_RX_DATA_POOL_SIZE 和 CONFIG_NET_PKT_BUF_TX_DATA_POOL_SIZE 调整数据池的大小。

使用固定大小的数据缓冲区时，可以根据接收的网络数据类型选择数据部分的大小，以调整网络缓冲区的内存占用。如果将数据大小设置为 256，但只接收 32 字节长的数据包，那么每个数据包都会“浪费” 224 字节，因为剩余空间无法利用。数据大小也不应设置得过小，因为每个 net_buf 都有一定的开销。因此，默认网络缓冲区大小设置为 128 字节。

可变大小数据缓冲区功能被标记为实验性，因为它没有像固定大小缓冲区那样经过充分测试。使用可变大小数据缓冲区时，会按网络数据所需的最小数据量进行分配，以期提高内存利用率。额外的代价是从内存池动态分配缓冲区所需的时间。

例如，以太网的最大传输单元（MTU）大小为 1500 字节。如果希望接收两个完整的帧，则 net_pkt RX 数量应设置为 2，net_buf RX 数量应设置为 (1500 / 128) * 2，即 24。如果使用 TCP，这些值需要更大，因为数据包在交给应用程序之前可能会在内部排队。

CONFIG_NET_BUF_TX_COUNT

为发送数据分配的网络缓冲区数量。该设置与接收缓冲区数量类似，只是用于发送。

连接选项

CONFIG_NET_MAX_CONN

该选项指定支持多少个网络连接端点。例如，每个 TCP 连接需要一个连接端点。同样，每个监听中的 UDP 连接也需要一个连接端点。DHCP 和 DNS 等各种系统服务也需要连接端点才能工作。可以在运行时使用网络 shell 命令 net conn 查看网络连接信息。

CONFIG_NET_MAX_CONTEXTS

要分配的网络上下文数量。每个网络上下文描述一个网络五元组，用于监听或发送网络流量。系统中的每个 BSD 套接字使用一个网络上下文。

套接字选项

CONFIG_ZVFS_POLL_MAX

支持的 poll() 条目的最大数量。需要根据系统中轮询的 BSD 套接字数量选择合适的值。

CONFIG_ZVFS_OPEN_MAX

打开的文件描述符的最大数量，包括文件、套接字、特殊设备等。需要根据系统中创建的 BSD 套接字数量选择合适的值。

CONFIG_ZVFS_EVENTFD_MAX

ZVFS eventfd 的最大数量。多个网络子系统（例如 HTTP 服务器、CoAP 服务器、LwM2M 引擎、PTP、SSH 和套接字服务）会分配一个 eventfd 来唤醒其轮询循环。每个这样的子系统都通过一个 CONFIG_ZVFS_EVENTFD_ADD_SIZE_* 选项声明其需求，实际的 eventfd 数量取该选项与所有这些需求之和中的较大值。只有当应用程序自己创建了额外的 eventfd 时，才需要显式设置该选项。

CONFIG_NET_SOCKETPAIR_BUFFER_SIZE

该选项供 socketpair() 函数使用。它设置内部中间缓冲区的大小（以字节为单位），从而限制两个 socketpair 端点之间可以传递的消息的大小。

TLS 选项

CONFIG_NET_SOCKETS_TLS_MAX_CONTEXTS

TLS/DTLS 上下文的最大数量。每个 TLS/DTLS 连接需要一个上下文。

CONFIG_NET_SOCKETS_TLS_MAX_CREDENTIALS

该变量设置单个套接字可使用的 TLS/DTLS 凭据的最大数量。

CONFIG_NET_SOCKETS_TLS_MAX_CIPHERSUITES

每个套接字的 TLS/DTLS 密码套件的最大数量。如果通过套接字选项显式设置，该变量设置单个套接字可使用的 TLS/DTLS 密码套件的最大数量。默认情况下，系统中所有可用的密码套件都可供套接字使用。

CONFIG_NET_SOCKETS_TLS_MAX_APP_PROTOCOLS

支持的应用层协议的最大数量。该变量设置可通过套接字选项显式设置的、基于 TLS/DTLS 的应用层协议的最大数量。默认情况下不设置任何应用层协议。

CONFIG_NET_SOCKETS_TLS_MAX_CLIENT_SESSION_COUNT

该变量指定存储的 TLS/DTLS 会话的最大数量，这些会话用于 TLS/DTLS 会话恢复。

CONFIG_TLS_MAX_CREDENTIALS_NUMBER

可注册的 TLS 凭据的最大数量。请确保该值足够大，以便所有证书都能加载到存储中。

IPv4/6 选项

CONFIG_NET_IF_MAX_IPV4_COUNT

系统中 IPv4 网络接口的最大数量。该值表示系统中有多少个网络接口会启用 IPv4。例如，如果有两个网络接口，但只有其中一个可以使用 IPv4 地址，则该值可以设置为 1。如果两个网络接口都可以使用 IPv4，则应设置为 2。

CONFIG_NET_IF_MAX_IPV6_COUNT

系统中 IPv6 网络接口的最大数量。该设置与 IPv4 数量选项类似，只是用于 IPv6。

TCP 选项

CONFIG_NET_TCP_TIME_WAIT_DELAY

在 TCP TIME_WAIT 状态下等待的时间（以毫秒为单位）。为避免一个（低概率）问题，即来自上一个连接的延迟数据包被递交给复用相同本地/远程端口的下一个连接，RFC 793（TCP）建议将已关闭的旧连接在特殊的 TIME_WAIT 状态下保持 2*MSL（最大报文段生存时间，Maximum Segment Lifetime）。该 RFC 建议 MSL 取 2 分钟，但同时指出

这是一个工程上的选择，如果经验表明有必要，可以更改。

对于资源有限的系统，过大的 MSL 可能导致资源很快耗尽（并引发相关的 DoS 攻击）。同时，现代 TCP 协议栈通过使用随机、不重复的端口号和初始序列号，已在很大程度上缓解了数据包误递的问题。因此，Zephyr 默认使用低得多的值 1500ms。值为 0 时完全禁用 TIME_WAIT 状态。

CONFIG_NET_TCP_RETRY_COUNT

TCP 报文段重传的最大次数。可以用以下公式计算报文段在等待重传期间被缓冲的时间（以毫秒为单位）：

\[\sum_{n=0}^{\mathtt{NET\_TCP\_RETRY\_COUNT}} \bigg(1 \ll n\bigg)\times \mathtt{NET\_TCP\_INIT\_RETRANSMISSION\_TIMEOUT}\]

使用默认值 9 时，IP 协议栈最多会尝试重传 1 分 42 秒。这尽可能接近 RFC 1122 推荐的最小值（1 分 40 秒）。重传次数只占 5 位，因此可接受的值在 0-31 范围内。不过强烈建议不要低于 9。

如果发生重传超时，会以 -ETIMEDOUT 错误码调用接收回调，并解除对该上下文的引用。

CONFIG_NET_TCP_MAX_SEND_WINDOW_SIZE

使用的最大发送窗口大小。该值影响 TCP 选择最大发送窗口大小的方式。默认值 0 表示由 TCP 协议栈根据系统中配置的网络缓冲区数量选择该值。注意，如果系统中有多个活动的 TCP 连接，可能需要对该值进行微调（调低），否则多个 TCP 连接很容易因排队的 TX 数据耗尽 net_buf 池。

CONFIG_NET_TCP_MAX_RECV_WINDOW_SIZE

使用的最大接收窗口大小。该值定义 TCP 接收窗口的最大大小。增大该值可以提高连接吞吐量，但要高效运行，系统中需要有更多可用的接收缓冲区。默认值 0 表示由 TCP 协议栈根据系统中配置的网络缓冲区数量选择该值。

CONFIG_NET_TCP_RECV_QUEUE_TIMEOUT

接收数据排队的时长（以毫秒为单位）。如果收到乱序的 TCP 数据，会将其排队。该值表示在无法将数据交给应用程序的情况下，数据在被丢弃前保留多久。如果设置为 0，则不启用接收排队。该值以毫秒为单位。

注意，当前版本只按顺序排队数据，即队列中不能有空洞。例如，如果收到 SEQ 5、4、3、6，且正在等待 SEQ 2，则报文段 3、4、5、6 中的数据会（按此顺序）排队，并在收到 SEQ 2 时交给应用程序。但如果收到 SEQ 5、4、3、7，则 SEQ 7 会被丢弃，因为缺少 6 号，列表将不连续。

流量类别选项

接收或发送网络数据时，可以配置多个流量类别（队列）。每个流量类别队列都实现为一个具有不同优先级的线程。这意味着可以将较高优先级的网络数据包放入较高优先级的网络队列，以更快或更慢地发送或接收。由于线程调度延迟，实际上发送数据包最快的方式是直接发送，而不使用专门的流量类别线程。因此，如果未启用用户空间，CONFIG_NET_TC_TX_COUNT 选项默认设置为 0。如果启用了用户空间，TX 流量类别数量最少为 1，原因是用户空间应用程序没有足够的权限直接递交消息。

在接收侧，建议至少有一个接收流量类别队列。原因是网络设备驱动接收数据包时通常运行在 IRQ 上下文中，此时不应尝试将网络数据包直接递交给上层，而应将数据包放入流量类别队列。如果网络设备驱动在获取数据包时不运行在 IRQ 上下文中，则 RX 流量类别选项 CONFIG_NET_TC_RX_COUNT 可以设置为 0。

栈大小选项

启用网络的系统中有若干网络专用线程。其中一些线程可能取决于用于启用或禁用某项功能的配置选项。每个线程的栈大小都经过优化，以支持正常的网络操作。

网络管理 API 默认使用一个专用线程。如果启用了 CONFIG_NET_MGMT 和 CONFIG_NET_MGMT_EVENT 选项，该线程负责将网络管理事件递交给系统中设置的事件监听器。启用这些选项后，用户可以注册一个回调函数，net_mgmt 线程会针对每个网络管理事件调用该函数。默认情况下，net_mgmt 事件线程的栈相当小。其设计思路是回调函数只做最少的工作，以便新事件能尽快递交给监听器而不会丢失。net_mgmt 事件线程的栈大小由 CONFIG_NET_MGMT_EVENT_QUEUE_SIZE 选项控制。建议不要在回调函数中执行任何阻塞操作。

可以在内核 shell 中使用 kernel threads 命令监视网络线程的栈使用情况。
