使用 TTCN-3 进行协议一致性测试

  • 整体结构

  • 测试套件

  • 已知的覆盖缺口

    • DNS-SD 传统单播查询

    • MQTT 5.0、数据包标识符和重发

    • 重叠的 DNS 查询

  • 持续集成

  • 其他 TTCN-3 测试套件

Zephyr 的网络协议从两个方向进行测试。tests/net 下的测试用 C 编写，与实现构建在同一个镜像中，从内部检验实现。用 TTCN-3 编写的一致性测试套件则从外部进行测试：它们通过真实的网络接口使用协议通信，并将 Zephyr 发送的内容与标准的要求进行比对。

两者能发现不同的问题。针对实现编写的测试往往会把实现的现有行为固化下来。针对标准编写的测试套件并不了解实现的行为，这正是其意义所在。

TTCN-3 是由 ETSI 标准化的一种测试编写语言。这里的测试套件使用开源 TTCN-3 编译器 Eclipse Titan 编译，存放在 net-tools 仓库的 ttcn3 目录下，与其他用于网络测试的主机侧工具放在一起。

  • 运行一致性测试套件
  • 一致性测试的组成方式

整体结构

一致性测试中 Zephyr 侧只是被测系统：一个普通的应用程序，经过配置启用了被测协议。测试的任何内容都不会编译进该应用程序，也没有控制通道，测试套件完全通过网络驱动它。

这些应用程序以及针对它们运行测试套件的测试框架（harness）位于 tests/net/conformance 下。Twister 构建并启动应用程序，一个小型 pytest 测试框架使用 Titan 构建测试套件并运行它，然后将 Titan 的判定结果转换为测试结果。

当缺少 Titan、第三方 TTCN-3 模块或网络接口时，每个测试都会自行跳过，因此在未为其做好准备的运行中，这些测试套件不会造成影响。运行所需的条件参见 运行一致性测试套件，各部分如何组合参见 一致性测试的组成方式。

已知的覆盖缺口

如果某个测试套件断言的行为与标准不符，会在做出该断言的地方加以说明，从而将偏差记录下来，而不是悄无声息地固化下来。下面列出的是另一类缺口：尚无任何测试套件覆盖的部分。

DNS-SD 传统单播查询

mDNS 响应器的主机名部分按照 RFC 6762 第 6.7 节的要求应答传统单播查询，而服务发现部分则没有做到：它自行构建消息，在属于同一实例的记录上设置缓存刷新位，使用本应用于组播应答的生存时间，而且既不回显标识符，也不回显问题。修复这一问题需要重写名称压缩偏移量，而这些偏移量全都是根据固定的报头大小计算的。

dnssd 测试套件在 f_check_legacy_shape 中记录这一行为，而不是断言标准行为，以免某个测试在有人处理之前一直失败。其中每项检查都说明了需要随之修改的内容。

MQTT 5.0、数据包标识符和重发

mqtt 测试套件覆盖 MQTT 3.1.1。Zephyr 还实现了 MQTT 5.0（CONFIG_MQTT_VERSION_5_0），但 Titan 项目没有发布对应的协议模块，因此要覆盖它，就得先编写消息类型，然后才能编写测试。

数据包标识符和重发也未覆盖。Zephyr 的客户端把这两者都交给应用程序处理：mqtt_publish() 发送调用方给定的标识符和重复标志，因此针对其中任何一项的测试，测的都是被测系统自己的计数器，而不是客户端。

重叠的 DNS 查询

解析器在向没有未完成查询的服务器发送查询之前会更换源端口；在默认一次只发一个查询的情况下，这意味着每次查询都会更换。但在同一服务器上重叠的查询仍然共用一个端口，因此 dns 测试套件中的检查无法发现这种情况下的回归。参见 RFC 5452 第 9.2 节。

持续集成

这些测试套件不在常规的 Twister 运行中：它们需要安装 Titan、一个面向设备的网络接口以及测试套件的检出副本，而普通构建都不具备这些条件。它们运行也较慢，并且不能同时运行。

这些测试套件改为每晚从 .github/workflows/net_conformance.yml 运行。该工作流也可以在 Actions 选项卡中手动启动，并且会在修改了测试、运行测试的脚本或工作流本身的 PR 上运行。该作业运行在 GitHub 托管的虚拟机上而不是容器中，因为创建 tap 接口需要 CAP_NET_ADMIN，而项目自有运行器上的容器不具备该权限。它会安装打包好的 Titan，然后运行 scripts/net/run-conformance-tests.sh。该脚本会启用两个接口，并以 sudo 运行整个目录，确保不跳过任何测试套件。它设置了 NET_CONFORMANCE_REQUIRED，因此无法运行的测试套件会失败而不是跳过：什么都没测的运行不能看起来像通过了一样。Twister 报告和测试框架日志会作为构件（artifact）保存。

其他 TTCN-3 测试套件

Eclipse Titan 项目为大量协议发布了协议模块和测试端口，它们是 gitlab.eclipse.org/eclipse/titan 下的独立仓库。这里的测试套件基于这些模块构建，而不是自行定义消息格式。

那里也有一些完整的测试套件。titan.misc 包含一个 CoAP 一致性测试套件，可以针对 CoAP service 示例运行，参见 CoAP。

Intel 曾为 TCP 重写编写过一个较早的 TCP TTCN-3 测试套件，tcp 测试套件的覆盖范围参考了它，但没有使用其中任何代码。该套件通过 JSON 控制通道驱动 Zephyr，并断言协议栈的内部状态名称，而该控制通道所需的选项已被移除，参见 4.5 迁移指南。
