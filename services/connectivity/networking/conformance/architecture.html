一致性测试的组成方式

整个系统由分布在两个仓库中的四个活动部件组成，它们只在线路上交汇：一个 Zephyr 应用程序、一个 Twister 和 pytest 测试框架、一个包装 Eclipse Titan 的 shell 脚本，以及 TTCN-3 测试套件本身。

各个组成部分

Twister

构建被测系统并启动它，然后针对它运行 pytest 测试框架。它提供测试标识符、平台限制以及整个过程 900 秒的时间预算。

pytest 测试框架

tests/net/conformance/ttcn3_runner.py，所有测试共用。它判断测试套件能否运行，获取接口锁，构建测试套件，运行它并读取判定结果。

被测系统

一个启用了被测协议的普通 Zephyr 应用程序。测试的任何内容都不会编译进其中。

build.sh 和 Eclipse Titan

主机侧构建。Titan 将 TTCN-3 编译为 C++ 并生成 makefile；build.sh 负责整理源文件，使 Titan 能够完成这些工作。

TTCN-3 测试套件可执行文件

测试本身，从外部驱动协议。

Tap 接口

两部分唯一共享的东西。Zephyr 镜像中没有控制通道、没有共享内存，也没有测试钩子。

Zephyr 侧

被测系统

每个应用程序都特意保持普通：启用协议，执行测试套件需要观察的、维持流量所需的操作，并打印一行有辨识度的就绪信息。这一行是应用程序与测试框架之间唯一的约定，测试框架据此在测试套件开始发送之前得知协议栈已就绪。

一个测试套件目录包含：

tests/net/conformance/<suite>/
    CMakeLists.txt
    prj.conf
    README.rst
    tests.yaml
    src/main.c
    pytest/pytest.ini
    pytest/conftest.py
    pytest/test_<suite>_conformance.py

Twister 集成

每个 tests.yaml 都共用同一段配置：

common:
  harness: pytest
  slow: true
  timeout: 900
  platform_allow:
    - native_sim
  integration_platforms:
    - native_sim

harness: pytest 将运行交给测试框架，而不是从控制台输出中读取 ztest 摘要。slow: true 使这些测试套件不进入常规的 Twister 运行，因为完整运行一遍需要几十分钟。900 秒超时必须同时涵盖构建和运行测试套件。native_sim 是唯一的平台，因为正是 tap 驱动将被测系统接入一条真实的链路。

测试本身只有三行：请求锁，等待就绪行，运行测试套件。

def test_mdns_conformance(network_lock, dut, suite_binary):
    dut.readlines_until(regex='mDNS responder ready', timeout=30.0)
    run_suite(suite_binary, SUITE)

network_lock 参数特意放在第一位，原因见下文。conftest.py 在每个测试目录中都相同，只做一件事：将共享的运行器加入 sys.path，并重新导出锁 fixture。

测试框架

以下所有内容都位于 tests/net/conformance/ttcn3_runner.py 中。

占用接口

Twister 在各自独立的 pytest 进程中运行每个测试，因此测试之间的互斥必须跨进程生效。测试框架在一个会话作用域的 fixture 中对锁文件获取排他的 flock。

顺序与锁同样重要。该 fixture 在 dut fixture 之前 被请求，因此当另一个一致性测试占用接口时，被测系统根本不会启动。两个应用程序同时在 192.0.2.1 上应答，会让两个测试套件都无所适从。

锁文件名中包含有效用户 ID。特权测试套件以 root 身份运行，而 root 无法打开其他用户遗留在设置了粘滞位的临时目录中的锁文件。由于一次运行要么全部以特权运行，要么全部不以特权运行，按用户加锁仍然能排除所有可能发生冲突的情况。这也是不能同时启动特权运行和非特权运行的原因。

测试套件特性

测试套件的三项特性从 suites/<name>/build.conf 中读取：

MODE=parallel

测试用例会创建并行测试组件，因此测试套件通过 Titan 的主控制器运行，而不是作为单个可执行文件运行，并且必须安装 expect。

PRIVILEGED=yes

测试套件会绑定特权端口或打开数据包套接字，因此必须以 root 身份运行。

L2=yes

测试套件在 IP 层以下工作，因此需要 zethL2 而不是 zeth。

build.sh 也会把同一个文件作为 shell 片段引入（source），因此它以 shell 赋值语句的形式编写；测试框架只在其中匹配子字符串。

构建和运行测试套件

构建通过 build.sh <suite> 完成，时间预算为 1800 秒，产物为 suites/<suite>/build/<suite>。

运行时必须兼容 Titan 的两种不同安装方式。发行版软件包将其库放在 TTCN3_DIR/lib/titan 中，源码构建则放在 TTCN3_DIR/lib 中；测试框架选用实际存在的那个目录并将其添加到 LD_LIBRARY_PATH 开头，同时将 TTCN3_DIR/bin 添加到 PATH 开头。并行测试套件使用 ttcn3_start 启动，其他测试套件直接启动。

测试套件在一个新的会话中启动，这样超时的测试套件可以连同它启动的所有进程一起被终止。如果遗留一个仍在运行的主控制器，它会在下一个测试中继续占用接口。

将判定结果转换为测试结果

两个正则表达式匹配 Titan 在运行结束时打印的行，并断言三件事：确实打印了判定结果，至少运行了一个测试用例，以及总体判定为 pass。没有产生任何输出的测试套件，或者因所有用例都被过滤掉而什么都没运行的测试套件，都会失败，而不是悄悄通过。判定结果的含义参见 解读结果。

主机侧

以下所有内容都位于 net-tools 仓库的 ttcn3 目录下。

目录布局

ttcn3/
    common/            shared TTCN-3 modules and the ethernet test port
    modules/           third party modules, cloned, not in git
    modules.txt        which modules, at which commit
    fetch-modules.sh   clone or check out the pinned commits
    build.sh           build one suite
    suites/<name>/     the suite, its sources.txt and its .cfg

测试套件的构建方式

build.sh 会清空测试套件的构建目录并以扁平方式重建，将所需的每个源文件以符号链接的形式并排放在同一个目录中。

采用扁平结构并非为了整洁，而是一种变通方法。Titan 生成的 makefile 使用 sed 以目标词干为模式构建依赖规则，一旦某个源文件通过包含斜杠的路径引用，该规则就会失效。因此每个源文件都必须能够仅凭文件名访问。

链接顺序为：测试套件自己的源文件，然后是 common，然后是 common/sources.txt 中列出的模块源文件，最后是测试套件自己的 sources.txt 中列出的源文件。随后 ttcn3_makefilegen 生成 makefile（单一模式的测试套件带 -s，并行测试套件不带），再由 make 构建。

共享的 TTCN-3 层

Zephyr_SUT 包含所有测试套件共用的模块参数。测试套件从不在自身中写入地址或超时，而是从这里获取，这样只需编辑一个配置文件就能将运行转移到另一条链路上。

Zephyr_Transport 提供 Zephyr_Tester 组件，它带有一个 IPL4asp 端口以及用于监听、打开、发送、带保护定时器接收和断言没有任何数据到达的辅助函数。基于套接字的测试套件会扩展该组件，而不是自行打开套接字。

ARP_Types 是手工编写的，放在 common 中而不是 arp 测试套件中，因为任何在 IP 层以下工作的测试套件，都必须在一条没有其他设备会应答的链路上自己应答地址解析。Titan 项目没有发布 ARP 模块。

以太网测试端口

Titan 发布了一个原始链路层测试端口 LANL2asp，但这里没有使用它。它使用 libpcap 捕获，并以零读取超时打开句柄，在 Linux 上这意味着“一直等到捕获块被填满”。在测试链路这样安静的链路上，帧永远到达不了测试，而且没有参数可以改变这一行为。

common/Ethernet_PT.cc 改为读取数据包套接字，每个帧一到达就向上交付。它接受三个测试端口参数：必需的 interface；source_address，默认为接口自身的地址；以及 ethertype，设置后只向上交付该类型的帧。

第三方模块

测试套件基于 Titan 项目发布的协议模块和测试端口构建，而不是自行定义消息格式。共使用了十一个仓库，每个仓库都在 modules.txt 中固定到某个提交，并由 fetch-modules.sh 按需克隆。这些仓库不会被纳入本仓库（vendor），克隆的副本也被 git 忽略，因此今天能通过的测试套件明天仍然能构建。更改固定的提交只需修改一行并重新运行。

上游模块采用 EPL-2.0 许可证，而这里编写的所有内容均采用 Apache-2.0。两者都是 OSI 认可的许可证，这正是 Zephyr 对那些永远不会成为 Zephyr 镜像一部分的工具的要求，参见 贡献外部组件。

测试网络

zeth 是一个两端都有地址的普通 tap 接口，使用它的测试套件只是链路上的另一台主机。zethL2 完全没有地址，并且主机被配置为不在其上应答，这样应答地址解析的只有 Zephyr。如何创建这些接口参见 设置网络接口。

警告

zethL2 这个名称写在三个必须保持一致的地方，而没有任何机制检查它们是否一致：

  • tests/net/conformance/ttcn3_runner.py 中的 L2_INTERFACE，它决定测试运行之前必须存在哪个接口

  • 每个使用 zethL2 的测试的 boards/native_sim.overlay 中的 host-interface，它决定被测系统出现在哪个接口上

  • 每个使用 zethL2 的测试套件配置文件中的 system.pt.interface，它决定测试套件在哪里监听

不一致时的表现是测试套件收不到任何帧并超时，而不是报错。

添加测试套件

一个测试套件由两部分组成，分别位于两个仓库中；在动手之前需要先做一个决定。

选择形式

套接字还是原始帧。 能够通过 UDP 或 TCP 表达测试意图的测试套件会扩展 Zephyr_Tester，使用 IPL4asp 端口，在 zeth 上运行，并且不需要特权。必须亲自查看或发送帧的测试套件使用 Ethernet_Port，在 zethL2 上运行，必须以 root 身份运行，并且必须自己应答地址解析，因为该链路上没有其他设备会应答。请优先使用套接字；原始帧方式需要额外一个接口，还要输入密码。

单一模式还是并行模式。 除非测试用例会创建并行测试组件，否则使用单一模式。并行模式需要 Titan 的主控制器并依赖 expect，还会使测试套件更难手动运行。

主机侧

创建 suites/<name>，其中包含 TTCN-3 源文件、列出测试套件所需模块源文件的 sources.txt，以及包含模块参数和待执行测试用例列表的 <name>.cfg。只运行第三方模块中测试用例的测试套件不需要自己的源文件，coap 就是一个完整的例子。

从 Zephyr_SUT 获取地址和超时。将任何新的上游模块添加到 modules.txt 中并固定提交。如果测试套件是并行的、需要特权或在 IP 层以下工作，请添加 build.conf。

Zephyr 侧

按上面所示的布局在 tests/net/conformance 下创建应用程序。src/main.c 启用协议，产生测试套件需要观察的流量，并打印一行有辨识度的就绪信息。tests.yaml 复制公共配置段，并将测试命名为 net.conformance.<name>。

三个 pytest 文件中，pytest.ini 和 conftest.py 原样复制；test_<name>_conformance.py 只有测试套件名称和所等待的就绪行不同。

记录不符合标准之处

如果测试套件断言的行为与标准不符，请在做出该断言的地方加以说明，从而将偏差记录下来，而不是悄无声息地固化下来。完全没有测试套件覆盖的部分应写入 已知的覆盖缺口；新增测试套件时也正好可以在 测试套件 中添加一行。

试运行

先按 手动运行测试套件 所述手动运行这两部分，等测试套件通过后再通过 Twister 运行。首次构建会较慢；另外请记住，缺少前提条件时测试会被跳过而不是失败，因此一个看似瞬间通过的测试套件很可能根本没有运行。
