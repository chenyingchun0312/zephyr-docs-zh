连接实现

概述

连接实现是特定于某种技术的模块，使特定的 Zephyr 接口能够支持 连接控制。它们负责将通用的 连接控制 API 调用转换为特定于硬件的操作，还负责实现标准化的 持久性和超时 行为。

关于编写符合规范的连接实现的详情，参见 实现指南。

架构

借助 实现 API，可以在构建时使用 CONN_MGR_CONN_DEFINE 定义 连接实现。

这会创建 conn_mgr_conn_impl 结构体的一个静态实例，其中保存对传入的 conn_mgr_conn_api 结构体（应填充实现回调）的引用。

定义之后，可以按名称引用实现，并使用 CONN_MGR_BIND_CONN 将其绑定到任何未绑定的接口。注意不要意外地将两个连接实现绑定到同一个接口。

接口绑定后，就可以在该接口上调用 连接控制 API 函数，这些调用会被转换为 conn_mgr_conn_api 中相应的实现函数。

绑定接口不会直接修改其 iface struct。

而是会创建一个 conn_mgr_conn_binding 实例，并将其追加到内部的 可迭代段 中。

该绑定结构体包含对所绑定接口的引用、该接口所绑定的连接实现，以及一个指向每接口 上下文指针 的指针。

通过遍历该可迭代段，可以查出给定接口绑定了哪个连接实现（如果有的话）。连接控制 API 中的大多数函数都使用这一查找过程。因此，由于查找开销相对较高，应尽量少调用这些函数。

同一个连接实现可以绑定到多个接口。详情参见 不要为实现创建多个实例。

上下文指针

由于同一个连接实现可能由多个 Zephyr 接口共享，每个绑定都会实例化一个该绑定独有的上下文容器（其 类型可配置）。每个绑定在实例化时都带有对该容器的引用，实现可以借此访问每个接口的状态信息。

另请参见 不要在未加锁的情况下访问绑定 和 不要为实现创建多个实例。

定义实现

可以按如下方式定义连接实现：

/* Create the API implementation functions */
int my_connect_impl(struct conn_mgr_conn_binding *const binding) {
        /* Cause your underlying technology to associate */
}
int my_disconnect_impl(struct conn_mgr_conn_binding *const binding) {
        /* Cause your underlying technology to disassociate */
}
void my_init_impl(struct conn_mgr_conn_binding *const binding) {
        /* Perform any required initialization for your underlying technology */
}

/* Declare the API struct */
static struct conn_mgr_conn_api my_impl_api = {
        .connect = my_connect_impl,
        .disconnect = my_disconnect_impl,
        .init = my_init_impl,
        /* ... so on */
};

/* Define the implementation (named MY_CONNECTIVITY_IMPL) */
CONN_MGR_CONN_DEFINE(MY_CONNECTIVITY_IMPL, &my_impl_api);

备注

除非同时 声明上下文指针类型，否则这样做无法工作。

公开声明实现

定义之后，可以按如下方式（在头文件中）声明连接实现，使其可供其他编译单元使用：

my_connectivity_header.h
CONN_MGR_CONN_DECLARE_PUBLIC(MY_CONNECTIVITY_IMPL);

任何需要引用该实现的编译单元都必须包含含有此声明的头文件。

声明上下文类型

要使 CONN_MGR_CONN_DEFINE 正常工作，必须声明相应的上下文指针类型。这是因为所有连接绑定都包含一个其关联上下文指针类型的 上下文指针。

如果使用 CONN_MGR_CONN_DECLARE_PUBLIC，请将该类型与声明一起声明：

my_connectivity_impl.h
#define MY_CONNECTIVITY_IMPL_CTX_TYPE struct my_context_type *
CONN_MGR_CONN_DECLARE_PUBLIC(MY_CONNECTIVITY_IMPL);

然后，确保在调用 CONN_MGR_CONN_DEFINE 之前包含该头文件：

my_connectivity_impl.c
#include "my_connectivity_impl.h"

CONN_MGR_CONN_DEFINE(MY_CONNECTIVITY_IMPL, &my_impl_api);

否则，只需在调用 CONN_MGR_CONN_DEFINE 之前紧接着声明上下文指针类型即可：

#define MY_CONNECTIVITY_IMPL_CTX_TYPE struct my_context_type *
CONN_MGR_CONN_DEFINE(MY_CONNECTIVITY_IMPL, &my_impl_api);

备注

命名很重要。上下文指针类型声明必须使用与实现声明相同的名称，并在末尾加上 _CTX_TYPE。

在上一个示例中，上下文类型命名为 MY_CONNECTIVITY_IMPL_CTX_TYPE，因为连接实现的名称是 MY_CONNECTIVITY_IMPL。

如果连接实现不需要上下文指针，只需将该类型声明为 void：

#define MY_CONNECTIVITY_IMPL_CTX_TYPE void *

将接口绑定到实现

在接口的设备定义之后的任何位置调用 CONN_MGR_BIND_CONN，即可将已定义的连接实现绑定到该接口：

/* Define an iface */
NET_DEVICE_INIT(my_iface,
        /* ... the specifics here don't matter ... */
);

/* Now bind MY_CONNECTIVITY_IMPL to that iface --
 * the name used should match with the above
 */
CONN_MGR_BIND_CONN(my_iface, MY_CONNECTIVITY_IMPL);

连接实现指南

连接管理器并不集中实现所有功能，而是依靠每个连接实现分别实现许多行为和功能。

这种做法使连接管理器保持精简，并允许每个连接实现为自己选择最合适的方式来实现这些行为。但它依赖于一种信任，即所有连接实现都会如实地实现委派给它们的功能。

为保持所有连接实现之间的一致性，编写自己的实现时请遵循以下指南：

完整实现超时和持久性

所有连接实现都必须完整支持 超时和持久性，使用户无论底层技术的固有行为如何，都能禁用或启用这些功能。换言之，无论底层技术行为如何，你的实现都必须让最终用户看到的行为与 超时和持久性 一节的规定完全一致。

关于实现超时和持久性的详细技术讨论，参见 实现超时和持久性。

遵循 API 规范

你实现的每个 implementation API function 都应按照相应连接控制 API 函数所述的方式运行。

例如，你对 conn_mgr_conn_api.connect 的实现应符合 conn_mgr_if_connect() 所述的行为。

允许预先配置连接

连接实现应为应用程序提供在调用 conn_mgr_if_connect() 之前预先配置所有必要连接参数（例如网络 SSID，或在适用时的 PSK）的方法。不应要求在 conn_mgr_if_connect() 调用中或调用之后才提供这些信息，不过 如果未提供这些信息，实现应等待这些信息。

等待有效的连接配置

如果由于应用程序预先配置了无效的连接参数，或根本没有配置连接参数而导致网络关联失败，应将其视为网络故障。

换言之，即使尚未配置有效的连接参数，连接实现也不应放弃连接尝试。

相反，连接实现应异步等待有效的连接参数被配置，可以无限期等待，也可以等到配置的 连接超时 到期。

例外情况是：网络接口被配置为非持久，且连接实现定义了 conn_mgr_conn_api.has_connection_config 的实现。

这种情况下，为降低功耗并避免不必要的状态转换，如果 conn_mgr_conn_api.has_connection_config 返回 false，conn_mgr_if_connect() 会提前退出，而不启用接口。此时会发出 NET_EVENT_CONN_IF_NO_CONFIGURATION 事件，通知订阅者配置有误。

实现接口状态上报

所有连接实现都必须使所绑定接口的状态保持最新。

具体而言：

  • 在 binding init 期间将接口设置为 dormant、carrier-down 或两者兼有。

    • 关于接口 carrier 和 dormant 状态的详情，参见 网络接口状态管理。

  • 更新 dormant 和 carrier 状态，使接口在关联完成且连接就绪时（并且仅在此时）处于非 dormant 和 carrier-up 状态。

  • 一旦检测到服务中断，立即将接口设置为 dormant 或 carrier-down。

    • 对于服务经常间歇性中断的网络技术，可以在此之前加一个较短的超时（与连接超时分开）。

  • 如果该技术也负责 IP 地址分配，请确保这些 IP 地址已 分配给接口。

备注

接口状态更新不一定需要由连接实现直接执行。

例如：

  • 如果接口使用 DHCP，则无需分配 IP 地址。

  • 如果底层的 L2 实现 已经更新接口的 dormant 状态，连接实现就无需再更新。

不要将接口状态用作实现状态

其他线程可能在不遵守绑定互斥量的情况下访问 Zephyr 接口。因此，在连接实现回调执行期间，Zephyr 接口状态可能发生不可预测的变化。

因此，不要基于接口状态来决定实现的行为。

应使接口状态保持最新以反映网络可用性，但不要出于任何目的读取接口状态。

如果需要跟踪 dormant 状态或 IP 地址分配，请使用存储在 上下文指针 中的独立状态变量。

保持不干扰

连接实现不应阻止应用程序直接与相关的特定技术 API 交互。

换言之，应用程序应当能够直接使用底层技术，而不会破坏你的连接实现。

如果确实必须存在例外，应将其限定在特定的 API 调用上，并加以文档说明。

备注

虽然连接实现不能因此出错，但如果应用程序试图直接控制关联状态，实现出现可能意料之外的行为是可以接受的。

例如，如果应用程序直接指示底层技术解除关联，连接实现将其解读为意外的连接丢失并立即尝试重新关联，这是可以接受的。

保持非阻塞

所有连接实现回调都应是非阻塞的。

例如，调用 conn_mgr_conn_api.connect 应发起连接过程并立即返回。

一个例外是 conn_mgr_conn_api.init，其实现允许阻塞。

不过请注意，在该回调中阻塞会延迟系统初始化，因此仍应考虑将耗时任务交给后台线程执行。

使 API 立即就绪

连接实现必须在 conn_mgr_conn_api.init 之后立即准备好接收 API 调用。

例如，即使紧接在 conn_mgr_conn_api.init 之后调用 conn_mgr_conn_api.connect，也必须最终引发一次关联尝试。

如果在调用 conn_mgr_conn_api.init 时底层技术无法立即准备好接收连接命令，则必须以非阻塞方式将对 conn_mgr_conn_api.connect 的调用排队，并在就绪后再执行。

不要在上下文指针之外存储状态信息

连接管理器为每个绑定提供一个上下文指针。

连接实现应将所有状态信息存储在该上下文指针中。

唯一的例外是只打算绑定到单个接口的连接实现，这类实现可以改用静态声明的状态。

另请参见 不要为实现创建多个实例。

只通过绑定结构体访问接口

不要使用静态声明的接口，也不要从外部获取对接口的引用。

例如，不要假定所绑定的接口就是默认接口而使用 net_if_get_default()。

而应始终使用相关 binding struct 提供的 iface pointer。另请参见 不要在未加锁的情况下访问绑定。

使实现在编译时可选

连接实现应提供一个 Kconfig 选项，用于启用或禁用该实现，而不影响所绑定接口的可用性。

换言之，应当可以配置这样的构建：包含连接管理器以及原本会绑定到该实现的接口，但不包含该实现本身及其绑定。

不要为实现创建多个实例

不要为要绑定的每个接口分别声明一个连接实现。

而应将一个全局连接实现绑定到所有接口，并使用上下文指针存储与各个接口相关的状态。

另请参见 不要在未加锁的情况下访问绑定 和 只通过绑定结构体访问接口。

不要在未加锁的情况下访问绑定

绑定可能被多个线程随机访问和修改，因此在未先 locking it 的情况下修改或读取绑定，可能导致不可预测的行为。

这适用于绑定的所有下级内容，包括 上下文容器 中的任何内容。

访问完毕后，务必 unlock 该绑定。

备注

如果相关资源本身是线程安全的，则可能是此规则的例外。

不过，利用这一例外时要小心。仍然可能产生竞争条件，例如同时访问多个线程安全的资源时。

因此，建议无论所访问的资源本身是否线程安全，都始终对绑定加锁。

不要禁用内置功能

不要试图阻止使用内置功能（例如 超时和持久性 或 自动化行为）。

所有连接实现都必须完全支持这些功能。实现不得试图强制某些功能始终启用或始终禁用。

触发连接控制事件

连接控制的 网络管理 事件不会由连接管理器自动触发。

连接实现必须自行触发这些事件。

发生连接 超时 时，触发 NET_EVENT_CONN_CMD_IF_TIMEOUT。详情参见 超时。

发生致命（不可恢复的）连接错误时，触发 NET_EVENT_CONN_IF_FATAL_ERROR。详情参见 致命错误。

关于触发网络管理事件的详情，参见 网络管理。

实现超时和持久性

首先，关于超时和持久性预期行为的高层描述，参见 超时和持久性。

无论底层连接技术的行为如何，连接实现都必须完全符合该描述。

有时这意味着需要在连接实现中编写额外的逻辑来模拟某些行为。以下各节讨论各种常见的边界情况和细微差别，以及如何处理它们。

本身具有持久性的技术

如果底层技术在连接丢失或失败后会自动尝试重新连接或重试连接，那么当这些尝试与超时或持久性设置冲突时，连接实现必须手动取消这些尝试。

例如：

  • 如果底层技术在失去连接后会自动尝试重新连接，而该接口禁用了持久性，连接实现应立即取消这次重新连接尝试。

  • 如果某个接口的底层技术没有内置超时，而该接口上的连接尝试超时了，连接实现必须手动取消连接尝试来模拟超时。

会放弃连接尝试的技术

如果底层技术没有重试连接尝试的机制，或者会在用户配置的超时到期之前放弃尝试，或者在连接丢失后不会重新连接，连接实现必须手动重新请求连接，以抵消这些偏差。

  • 如果底层技术不具有持久性，则在启用持久性时必须手动触发重新连接尝试。

  • 如果底层技术不支持超时，则在启用超时时必须手动取消连接尝试。

  • 如果底层技术强制使用超时，而该超时比连接管理器的超时短，则必须手动触发新的连接尝试。

带关联重试的技术

许多底层技术通常无法一次尝试就完成关联。

这些底层技术可能需要连续进行多次背靠背的关联尝试，通常每次之间有短暂的延迟。

这种情况下，连接实现应将这一系列背靠背的关联子尝试视为一次统一的连接尝试。

例如，某次子尝试失败后，即使禁用了持久性，也不应阻止后续的子尝试，因为它们都算作同一次整体连接尝试。另请参见 连接尝试期间的持久性。

一系列子尝试失败到什么程度时应视为整个连接尝试失败，由各个实现自行决定。

如果连接尝试越过了这一阈值，但配置的超时尚未到期，或者没有设置超时，则应继续进行子尝试。

连接尝试期间的持久性

在连接尝试期间，持久性不应影响实现行为的任何方面。持久性只应影响连接丢失后是否自动触发连接尝试。

是否应执行连接重试应完全由配置的超时决定。
