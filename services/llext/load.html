加载扩展

扩展构建完成并得到 ELF 文件后，就可以使用 LLEXT API 将其加载到 Zephyr 应用程序中。该 API 提供了将扩展加载到内存、访问其符号以及调用其函数的方法。

加载扩展

可以使用 llext_loader 的任何实现来加载扩展，该结构体包含一组函数指针，提供读取 ELF 数据所需的功能。加载器还提供 llext_load() 函数所需的少量上下文（内存）。目前已经提供了以下几种加载器：

  • llext_buf_loader 是基于缓冲区的实现，该缓冲区位于可寻址内存中并包含 ELF。使用这类加载器时，最好借助 LLEXT_TEMPORARY_BUF_LOADER、LLEXT_PERSISTENT_BUF_LOADER 或 LLEXT_WRITABLE_BUF_LOADER 宏之一，告知 LLEXT 内存缓冲区的相应类型。

  • llext_fs_loader 是从文件系统中的文件读取数据的实现。使用 LLEXT_FS_LOADER 宏创建加载器时，必须提供文件路径。

  • llext_semihost_loader 是通过半主机（semihosting）从主机文件系统中的文件读取数据的实现。使用 LLEXT_SEMIHOST_LOADER 宏创建加载器时，必须提供文件路径。

调用 llext_load() 函数并传入扩展名称和已配置的加载器，即可加载扩展。调用成功完成后，扩展即已加载到内存中，可以使用。

备注

启用 用户模式 时，扩展不会被包含在任何用户内存域中。要允许从用户模式访问，必须调用 llext_add_domain() 函数。

初始化和清理扩展

扩展可以定义若干初始化函数，这些函数必须在加载之后、使用扩展中的任何函数之前调用；这在 C++ 等提供对象构造函数概念的语言中很常见。同样，清理函数也必须在卸载扩展之前调用。

LLEXT 支持通过 llext_bringup() 函数调用 ELF 文件 .preinit_array 和 .init_array 节中列出的函数，并通过 llext_teardown() 函数调用 .fini_array 节中列出的函数。这些 API 与 用户模式 兼容，因此既可以在内核上下文中调用，也可以在用户上下文中调用。

重要

这些函数运行的代码完全由 ELF 文件的内容决定。如果 ELF 文件来源不可信，这可能带来安全隐患。

如果扩展需要专用线程，可以使用 llext_bootstrap() 函数来尽量减少样板代码。该函数的签名与 k_thread_create() API 兼容，它会先调用 llext_bringup()，然后在同一上下文中调用用户指定的函数，最后在返回前调用 llext_teardown()。

访问代码和数据

要与新加载的扩展交互，宿主应用程序必须使用 llext_find_sym() 函数获取导出符号的地址。然后可以将返回的 void * 转换为适当的类型并使用。

llext_call_fn() 提供了一个用于调用无参数函数的封装。

需要直接访问新加载扩展中各区域的高级用户，可以参考 llext_get_section_info() 以及其他 LLEXT 检查 API。

使用后的清理

扩展不再需要时，必须调用 llext_unload() 函数释放其使用的内存。该调用完成后，之前获取的所有指向扩展中符号的指针都将失效。

故障排除

该功能仍在积极开发中，因此可能会出现一些问题。由于链接确实会修改二进制代码，一旦出错，结果难以预料。一些常见问题可能包括：

  • llext_find_sym() 的结果指向无效地址；

  • 扩展中定义的常量和变量没有预期的值；

  • 调用扩展中定义的函数导致硬故障（hard fault），或者从该函数返回后主应用程序的内存被破坏。

如果出现上述任何情况，以下提示可能有助于理解问题：

  • 确保将 CONFIG_LLEXT_LOG_LEVEL 设置为 DEBUG，然后获取 llext_load() 调用过程的日志。

  • 如果可能，禁用内存保护（MMU/MPU），观察行为是否有所不同。

  • 尝试将扩展简化为能够重现问题的最少代码。

  • 使用调试器检查内存和寄存器，尝试弄清楚发生了什么。更多详情请参阅 调试扩展。

如果问题仍然存在，请在 GitHub 仓库中提交 issue，并附上上述所有信息。
