配置

LLEXT 子系统提供以下 Kconfig 选项。

哈佛架构

CONFIG_HARVARD

架构使用分离的指令存储器和数据存储器。

CONFIG_HARVARD 不是由 LLEXT 子系统定义的 Kconfig 选项，而必须由开发板或 SoC 定义并选中，以表明 LLEXT 应在构建时加入哈佛架构支持。开发板或 SoC 还必须实现 arch_is_instr_mem()。

堆大小

LLEXT 子系统需要分配一个堆，用于存放与扩展相关的数据。分配静态堆时，由以下选项控制该分配。

CONFIG_LLEXT_HEAP_SIZE

LLEXT 堆的大小，以 KB 为单位。

对于使用哈佛架构的开发板，LLEXT 堆分为两个：一个位于指令存储器中，另一个位于数据存储器中。由以下选项控制这两项分配。

CONFIG_LLEXT_INSTR_HEAP_SIZE

指令存储器中 LLEXT 堆的大小，以 KB 为单位。

CONFIG_LLEXT_DATA_HEAP_SIZE

数据存储器中 LLEXT 堆的大小，以 KB 为单位。

另外，应用程序也可以使用以下选项配置动态堆。

CONFIG_LLEXT_HEAP_DYNAMIC

某些应用程序需要将扩展加载到启动时尚不存在、无法静态分配的存储器中。此选项使应用程序负责分配 LLEXT 堆，不再静态分配 LLEXT 堆。

应用程序必须调用 llext_heap_init() 来指定用作 LLEXT 堆的缓冲区，否则无法加载 LLEXT 模块。当应用程序不再需要 LLEXT 功能时，应调用 llext_heap_uninit()，将该缓冲区的控制权交还给应用程序。

备注

启用 用户模式 时，堆必须足够大，以便能按架构要求的对齐方式分配扩展的各个节。

备注

在哈佛架构上，应用程序必须调用 llext_heap_init_harvard()。

LLEXT 堆的底层数据结构默认是 k_heap，但对于非元数据（即扩展区域），可以通过在 CONFIG_LLEXT_HEAP_MANAGEMENT 中选择 CONFIG_LLEXT_HEAP_MEMBLK，将其改为 sys_mem_blocks_t。

CONFIG_LLEXT_HEAP_MANAGEMENT

选择在 LLEXT 堆内存中存放扩展区域所使用的内存管理 API。此选择不影响 LLEXT 元数据，元数据始终由 k_heap 管理。

CONFIG_LLEXT_HEAP_MEMBLK

使用 sys_mem_blocks_t API 管理存放扩展区域的 LLEXT 堆内存。每个区域至少分配一个块。必须谨慎选择块大小，以确保扩展区域正确对齐。

备注

CONFIG_LLEXT_HEAP_MEMBLK 不支持 CONFIG_LLEXT_HEAP_DYNAMIC。

堆将被分为两个，每个子堆的大小由以下选项控制。

CONFIG_LLEXT_EXT_HEAP_SIZE

可用于 LLEXT 扩展节的堆大小，以 KB 为单位。必须是 CONFIG_LLEXT_HEAP_MEMBLK_BLOCK_SIZE 的倍数。如果选中了 CONFIG_HARVARD，则由 CONFIG_LLEXT_INSTR_HEAP_SIZE 和 CONFIG_LLEXT_DATA_HEAP_SIZE 代替。

CONFIG_LLEXT_METADATA_HEAP_SIZE

可用于 LLEXT 元数据的堆大小，以 KB 为单位。

另一个选项控制块大小。

CONFIG_LLEXT_HEAP_MEMBLK_BLOCK_SIZE

LLEXT sys_mem_blocks_t 堆的块大小，以字节为单位。如果启用了 MMU 或 MPU，则必须等于 LLEXT_PAGE_SIZE 或其倍数。块大小还必须等于任一扩展区域所需的最大对齐值或其倍数。如果选中了 CONFIG_MPU_REQUIRES_POWER_OF_TWO_ALIGNMENT 且区域较大，可能需要大得不合理的块大小才能满足对齐要求。

堆的放置

LLEXT 堆有自定义的节。非哈佛架构的堆节（.llext_heap；如果选中了 CONFIG_LLEXT_HEAP_MEMBLK，则为 .llext_metadata_heap 和 .llext_ext_heap）与 .noinit 节一起放置在文件 include/zephyr/linker/common-noinit.ld 中。如果你的链接脚本都没有包含此文件，就需要手动放置非哈佛架构的 LLEXT 堆节。一种做法是在链接脚本中的 .noinit 节之后包含 snippets-noinit.ld。

/* Located in generated directory. This file is populated by the
 * zephyr_linker_sources() CMake function.
 */
#include <snippets-noinit.ld>

在开发板、SoC 或架构的 CMakeFiles.txt 中将该文件添加为链接器源文件。

zephyr_linker_sources(NOINIT snippets-noinit.ld)

然后在 CMakeFiles.txt 所在的同一目录中创建一个名为 noinit.ld 的文件。

#if defined(CONFIG_LLEXT) && !defined(CONFIG_LLEXT_CUSTOM_HEAP_PLACEMENT)
*(.llext_heap)
*(.llext_ext_heap)
*(.llext_metadata_heap)
#endif /* CONFIG_LLEXT && !CONFIG_LLEXT_CUSTOM_HEAP_PLACEMENT */

对于 ARC，哈佛架构的指令堆节和数据堆节（.llext_instr_heap 和 .llext_data_heap）在架构层面分别放置在指令存储器和数据存储器中。如果使用的是采用哈佛架构的非 ARC 开发板，则需要手动放置 .llext_instr_heap 和 .llext_data_heap。

警告

如果 .llext_instr_heap 所在的指令存储器在加载和链接扩展时不可写，LLEXT 将无法加载扩展。

也可以通过提供自定义链接脚本来指定放置位置。

CONFIG_CUSTOM_LINKER_SCRIPT

用于替代开发板所定义链接脚本的链接脚本路径。

该链接脚本必须基于 Zephyr 提供的某个版本，因为内核可能要求特定的布局或特定的区域。

当应用程序需要在链接脚本中添加节，同时又不想修改 Zephyr 提供的脚本时，这很有用。

使用自定义链接脚本时，可能需要覆盖默认的放置方式。例如，你可能希望在链接脚本中包含 include/zephyr/linker/common-noinit.ld，但把堆节放在其他位置。为此，请选中以下选项。

CONFIG_LLEXT_CUSTOM_HEAP_PLACEMENT

在链接脚本中移除 LLEXT 堆节的默认放置，让用户自行放置堆。

字粒度访问指令存储器堆

字粒度访问指令存储器是一种可按字节寻址、但只能通过字大小且对齐的加载和存储操作访问的指令存储器。LLEXT 子系统目前仅在 Xtensa 架构上支持将指令堆放置在字粒度访问指令存储器中。将来会根据需求增加对非 Xtensa 架构的支持。

要在指令堆位于字粒度访问指令存储器中的情况下使用 LLEXT，你的 Xtensa SoC 或开发板除了 CONFIG_HARVARD 之外，还必须选中以下选项。

CONFIG_ARCH_HAS_WORD_GRANULAR_ACCESS_INSTR_MEM

此选项启用对可按字节寻址、字粒度访问的指令存储器的访问支持。

如果堆使用默认的底层数据结构 k_heap，请启用以下选项。

CONFIG_SYS_HEAP_BIG_ONLY

选中此项可仅针对大堆优化代码。这样可以适应任意大小的堆，但对于小堆，内存使用效率会有所降低。

如果未选中此选项，指令堆初始化期间将对指令存储器执行非对齐和窄宽度访问。

接下来，按照上文堆放置的说明，将 LLEXT 指令堆放置在该指令存储器中。确保你的 SoC 或开发板除了 arch_is_instr_mem() 之外，还实现了 arch_memcpy_to_instr() 和 arch_memcpy_from_instr()。字粒度访问库中的 memcpy_to_word_granular() 和 memcpy_from_word_granular() 函数可能会有帮助。

可以将 ELF 缓冲区放在 RAM 中。加载时，LLEXT 子系统会强制将代码（text）区域放到指令堆上（即使 ELF 缓冲区可写），使其可执行，并在加载和链接期间访问代码区域时遵守字粒度访问的约束。

警告

当指令堆位于字粒度访问指令存储器中时，只能使用缓冲区加载器（llext_buf_loader）加载 ELF。

注意，扩展本身负责确保之后对指令存储器的任何访问也遵守这些约束。

如果仍然遇到加载/存储异常，可以通过以下选项启用 Xtensa 的无符号加载/存储异常处理程序。

CONFIG_XTENSA_EMULATE_UNSUPPORTED_UNSIGNED_LOAD_STORE

当无符号加载/存储指令触发不受支持的加载/存储异常时，异常处理程序会使用受支持的字大小且对齐的加载/存储操作自行完成该操作。目前不支持 VLIW。

如选项说明中所述，要使用此选项，还必须禁用 VLIW，因为启用 VLIW 会导致编译器生成有符号的加载/存储指令。

CONFIG_COMPILER_CODEGEN_VLIW_DISABLED

明确指示编译器绝不生成 VLIW 指令。

ELF 目标文件类型

LLEXT 子系统支持加载不同类型的扩展；可以通过在以下 Kconfig 选项中选择一项来设置类型：

CONFIG_LLEXT_TYPE_ELF_OBJECT

构建可重定位文件，并将其作为 LLEXT 子系统所期望的二进制目标文件类型。只需调用一次编译器即可生成目标文件。

CONFIG_LLEXT_TYPE_ELF_RELOCATABLE

构建可重定位（部分链接）文件，并将其作为 LLEXT 子系统所期望的二进制目标文件类型。这些目标文件由链接器将多个目标文件合并为一个而生成。

CONFIG_LLEXT_TYPE_ELF_SHAREDLIB

构建共享库，并将其作为 LLEXT 子系统所期望的二进制目标文件类型。使用标准链接过程从多个目标文件生成共享库。

备注

目前在 ARM 架构上不支持此选项。

尽量减少分配

默认情况下，LLEXT 子系统的加载机制使用定位/读取（seek/read）抽象，并将所有数据复制到分配的内存中；这样做是为了允许从任何存储介质加载扩展。但有时数据已经位于 RAM 中的缓冲区里，没有必要复制。以下选项允许 LLEXT 子系统在这种情况下优化内存占用。

CONFIG_LLEXT_STORAGE_WRITABLE

允许通过直接引用 ELF 缓冲区中的节数据来加载扩展。要使其生效，需要使用支持 peek 功能的 ELF 加载器，例如 llext_buf_loader。

警告

应用程序必须确保用于加载扩展的缓冲区在扩展卸载之前始终保持已分配状态。

备注

这会在链接阶段直接修改缓冲区的内容。扩展卸载后，必须重新加载缓冲区，才能在 llext_load() 调用中再次使用。

符号组

所有 LLEXT 符号都属于某个组，每个组是否包含在导出符号表中由相应的 Kconfig 符号控制。使用 EXPORT_GROUP_SYMBOL 和 EXPORT_GROUP_SYMBOL_NAMED 宏可以将符号作为某个组的一部分导出。例如，以下代码将符号 memcpy 作为 LIBC 组的一部分导出：

EXPORT_GROUP_SYMBOL(LIBC, memcpy);

组名可以任意取，但必须全部大写。对于 C 代码中使用的每个组，都必须有一个如下形式的对应 Kconfig 符号：

config LLEXT_EXPORT_SYMBOL_GROUP_{GROUP_NAME}
   bool "Export all symbols from the {GROUP_NAME} group"

符号（使用 EXPORT_SYMBOL 或 EXPORT_SYMBOL_NAMED 声明的符号）的默认组是 UNASSIGNED 组。根据上述规则，该组是否包含由 CONFIG_LLEXT_EXPORT_SYMBOL_GROUP_UNASSIGNED 控制。

使用 SLID 进行符号查找

加载扩展时，LLEXT 子系统必须找到扩展所引用的、位于主应用程序中的所有符号的地址。为此，主二进制文件包含一个 LLEXT 专用的符号表，主应用程序导出给扩展的每个符号在其中都有一个从符号名到地址的映射条目。LLEXT 链接器在加载扩展时就可以在该表中进行搜索。由于需要进行字符串比较，这一过程相当慢，而且随着导出符号数量的增加，该表占用的空间可能会变得相当可观。

CONFIG_LLEXT_EXPORT_BUILTINS_BY_SLID

对 Zephyr 二进制文件和所有正在构建的扩展执行一个额外的处理步骤，将符号表中的每个字符串转换为一个指针大小的哈希值，称为符号链接标识符（Symbol Link Identifier，SLID），并将其存储在二进制文件中。

这样可以使用基于整数的比较代替基于字符串的比较，从而加快符号查找过程。基于 SLID 的链接的另一个好处是不再需要在二进制文件中存储符号名称，从而大大减小符号表的大小。

备注

此选项目前与 LLEXT EDK 不兼容。

备注

不支持在主二进制文件和扩展中为此选项使用不同的值。例如，如果主应用程序使用 CONFIG_LLEXT_EXPORT_BUILTINS_BY_SLID=y 构建，则禁止加载使用 CONFIG_LLEXT_EXPORT_BUILTINS_BY_SLID=n 编译的扩展。
