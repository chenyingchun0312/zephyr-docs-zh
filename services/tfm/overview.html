Trusted Firmware-M 概述

Trusted Firmware-M（TF-M） 是平台安全架构（PSA）物联网安全框架 的参考实现。它定义并实现了一套架构和一组软件组件，旨在解决物联网产品中的一些主要安全问题。

Zephyr RTOS 自 Zephyr 2.0.0（配合 TF-M 1.0）起就已通过 PSA 认证，目前集成的是 TF-M 2.1.0。

TF-M 提供什么？

通过一组安全服务以及其设计本身，TF-M 提供：

  • 安全资源与非安全资源的隔离

  • 适合嵌入式的密码学功能

  • 设备机密（密钥等）的管理

  • 固件验证（及加密）

  • 受保护的片外数据存储与读取

  • 设备身份证明（设备证明）

  • 审计日志

构建系统集成

在受支持的平台上使用 TF-M 时，TF-M 会作为标准 Zephyr 构建过程的一部分在后台自动构建和链接。该构建过程对 TF-M 的使用方式做了一些假设，这也决定了 Zephyr 应用程序镜像能做什么、不能做什么：

  • 安全处理环境（安全启动和 TF-M）首先启动

  • Zephyr 的资源分配取决于安全镜像中所做的选择。

架构概述

一般来说，TF-M 应用程序由以下三部分组成，从左到右按可信程度由高到低排列，代码也按相同顺序执行（安全启动 > 安全镜像 > ns 镜像）。

安全引导加载程序是可选的，但默认启用，而安全启动是提供安全解决方案的重要组成部分：

+-------------------------------------+           +--------------+
| Secure Processing Environment (SPE) |           |     NSPE     |
| +----------++---------------------+ |           | +----------+ |
| |          ||                     | |           | |          | |
| | bl2.bin  ||  tfm_s_signed.bin   | |           | |zephyr.bin| |
| |          ||                     | | <- PSA -> | |          | |
| |  Secure  || Trusted Firmware-M  | |    APIs   | |  Zephyr  | |
| |   Boot   ||   (Secure Image)    | |           | |(NS Image)| |
| |          ||                     | |           | |          | |
| +----------++---------------------+ |           | +----------+ |
+-------------------------------------+           +--------------+

（Zephyr）非安全处理环境（NSPE）与（TF-M）安全处理环境镜像之间的通信基于一组 PSA API，通常使用一种 IPC 机制，该机制包含在 TF-M 构建中，并在 Zephyr 中实现（参见 modules/trusted-firmware-m/interface）。

信任根（RoT）架构

TF-M 基于 信任根（Root of Trust，RoT） 架构。这种架构允许建立从最可信、较可信到最不可信的信任层级，为构建或访问可信服务和资源提供了坚实的基础。

这种方法的好处是，可信度较低的组件无法访问或破坏系统中更关键的部分，可信度较低的环境中出现的错误也不会损坏可信度更高的隔离资源。

TF-M 定义了以下 RoT 层级，按可信度从高到低排列：

  • PSA 信任根（PRoT），包括：

    • PSA 不可变信任根：安全启动

    • PSA 可更新信任根：最可信的安全服务

  • 应用程序信任根（ARoT）：隔离的安全服务

PSA 不可变信任根 是系统中最可信的代码，后续的各级信任根都以它为锚点。在 TF-M 中，它就是安全启动镜像，负责验证安全镜像和非安全镜像有效、未被篡改且来源可靠。借助内置的公共签名密钥，安全引导加载程序还会在固件更新过程中验证新镜像。顾名思义，这个镜像是 不可变 的。

PSA 可更新信任根 实现 TF-M 中最可信的安全服务和组件，例如安全分区管理器（Secure Partition Manager，SPM），以及 PSA Crypto、内部可信存储（Internal Trusted Storage，ITS）等共享安全服务。PSA 可更新信任根中的服务可以访问同一信任根中的其他资源。

应用程序信任根 是安全处理环境中权限较低的区域。根据构建 TF-M 时所选的隔离级别，它对 PRoT 的访问受限，在最高隔离级别下甚至对其他 ARoT 服务的访问也受限。ARoT 中有一些标准服务，例如受保护存储（Protected Storage，PS）。一般而言，自己实现的自定义安全服务应放在 ARoT 中，除非有充分理由将其放在 PRoT 中。

这些划分与 不可信代码 不同，后者运行在非安全环境中，在系统中权限最低。在这里就是 Zephyr 应用程序镜像。

隔离级别

目前 TF-M 定义了三个不同的 隔离级别，各区域之间的边界依次愈加严格。所用的隔离级别取决于安全需求以及可用的系统资源。

  • 隔离级别 1 是最低的隔离级别，唯一的主要边界在安全处理环境与非安全处理环境之间，在 Armv8-M 处理器上通常借助 Arm TrustZone 实现。此级别不区分 PSA 可更新信任根（PRoT）和应用程序信任根（ARoT），两者以相同的特权级别执行。此隔离级别生成的组合应用程序镜像最小。

  • 隔离级别 2 在级别 1 的基础上区分了 PSA 可更新信任根和应用程序信任根：ARoT 服务对 PRoT 服务的访问受限，只能通过 PRoT 服务公开的 API 与其通信。不过，各 ARoT 服务彼此之间并未严格隔离。

  • 隔离级别 3 是最高的隔离级别，在级别 2 的基础上将各 ARoT 服务相互隔离，使每个 ARoT 基本上都与其他服务分隔开来。这提供了最高级别的隔离，但代价是额外的开销以及服务之间的代码重复。

可以通过 CONFIG_TFM_ISOLATION_LEVEL 查看当前的隔离级别。

安全启动

TF-M 中默认的安全引导加载程序基于 MCUBoot，在 TF-M 中称为 BL2 （即第二阶段引导加载程序，可能运行在安全 MCU 上基于硬件的引导加载程序等之后）。

TF-M 中的所有镜像都经过哈希和签名，MCUBoot 会在固件更新过程中验证哈希和签名。

TF-M 中所用 MCUBoot 的一些关键特性：

  • 公共签名密钥内置于引导加载程序中

  • S 镜像和 NS 镜像可以使用不同的密钥签名

  • 固件镜像可以选择加密

  • 由客户端软件负责将新镜像写入次槽（secondary slot）

  • 默认使用由两个大小相同的内存区域组成的静态 Flash 布局

  • 可选的安全计数器，用于防回滚保护

处理（可选的）加密镜像时：

  • 只有载荷被加密（头部和 TLV 为明文）

  • 哈希和签名作用于未加密的数据

  • 使用 AES-CTR-128 或 AES-CTR-256 进行加密

  • 每次加密都会随机生成加密密钥（通过 imgtool）

  • AES-CTR 密钥包含在镜像中，可使用以下方式加密：

    • RSA-OAEP

    • AES-KW （128 位或 256 位，取决于 AES-CTR 密钥长度）

    • ECIES-P256

    • ECIES-X25519

在 Zephyr 中控制安全启动的关键配置属性有：

  • CONFIG_TFM_BL2 开关引导加载程序（默认值为 y）。

  • CONFIG_TFM_KEY_FILE_S 覆盖安全镜像的签名密钥。

  • CONFIG_TFM_KEY_FILE_NS 覆盖非安全镜像的签名密钥。

安全处理环境

安全引导加载程序执行完毕后，基于 TF-M 的安全镜像开始在 安全处理环境 中执行。设备在这里完成初始配置，所有安全服务也在这里初始化。

注意，设备的初始状态由安全固件控制，这意味着非安全 Zephyr 应用程序启动时，外设可能并不处于硬件默认的复位状态。如有疑问，请查阅 TF-M 中的开发板支持包，它们位于 TF-M 模块的 platform/ext/target/ 文件夹中（在默认的 Zephyr west 工作区中，该模块位于 modules/tee/tf-m/trusted-firmware-m/）。

安全服务

截至 TF-M 1.8.0，一般可以使用以下安全服务（但厂商支持情况可能有所不同）：

  • 密码学（Crypto）

  • 固件更新（FWU）

  • 初始证明（Initial Attestation）

  • 平台（Platform）

  • 安全存储，包括两部分：

    • 内部可信存储（ITS）

    • 受保护存储（PS）

此外还有一个模板，可用于创建自己的自定义服务。

有关这些服务及其公开 API 的完整细节，请参阅 TF-M 文档。

密钥管理与派生

密钥和机密的管理是任何安全设备的关键部分。需要确保密钥材料只对需要它的区域可用，而对其他任何部分都不可用，并且以难以篡改或被恶意访问的方式安全存储。

TF-M 中的 内部可信存储 服务被 PSA Crypto 服务（其自身基于 mbedtls）用来存储密钥，并确保私钥只能被安全处理环境访问。使用密钥材料的密码学运算（例如对载荷签名或解密敏感数据）全部通过密钥句柄进行。密钥材料在任何时候都不应暴露给 NS 环境。

一个例外是，可以将私钥以单向操作的方式预配到安全处理环境中，例如在工厂预配过程中；但即便如此也应尽量避免，而应（通过 PSA Crypto 服务）请求 SPE 自行生成新的私钥，并在预配期间请求对应的公钥并在工厂中记录下来。这样可以确保私钥材料永远不会暴露，甚至在预配阶段也不会被知晓。

TF-M 还大量使用 硬件唯一密钥（Hardware Unique Key，HUK），每个 TF-M 设备都必须提供该密钥。例如，受保护存储 服务使用这个设备唯一的密钥来加密存储在外部存储器中的信息。这样可以确保即使 Flash 被拆下放到新设备上，其内容也无法被解密，因为每个设备首次加密存储内容时使用的都是自己独有的 HUK。

HUK 还为开发者带来了另一个好处：可以用它派生新的密钥，而 派生密钥 无需存储，因为启动时可以使用额外的盐值/种子值（取决于所用的密钥派生算法）从 HUK 重新生成。这消除了存储问题，也消除了一个常见的攻击途径。在安全设备中，HUK 本身通常受到严密保护，用户无法直接访问。

TFM_CRYPTO_ALG_HUK_DERIVATION 标识使用软件实现时默认的密钥派生算法。当前的默认算法是使用 SHA-256 哈希的 HKDF （RFC 5869）。在某些平台上可能还有其他硬件实现。

非安全处理环境

Zephyr 用作 NSPE，所用开发板需受 TF-M 支持，并已启用 CONFIG_BUILD_WITH_TFM 标志。

一般来说，只需选择某块有效开发板的 */ns 开发板目标（例如 mps2/an521/cpu0/ns），它就会将 Zephyr 应用程序配置为在 NSPE 中运行，正确构建并与 TF-M 安全镜像链接，对安全镜像和非安全镜像签名，并将三个二进制文件合并为一个 tfm_merged.hex 文件。在此配置下，west flash 命令默认烧录 tfm_merged.hex。

目前，Zephyr 不能配置为用作安全处理环境。
