SMP 传输规范

本文档说明实现服务器端和客户端 SMP 传输所需的信息。

低功耗蓝牙（LE）

MCUmgr 客户端在实现 SMP 客户端时，需要使用以下蓝牙特征（Characteristic）：

  • 服务 UUID：8D53DC1D-1DB7-4CD3-868B-8A527460AA84

  • 特征 UUID：DA2E7828-FBCE-4E01-AE9E-261174997C48

所有 SMP 通信都使用同一个 GATT 特征。SMP 请求通过 GATT Write Without Response 命令发送。SMP 响应以 GATT Notification 的形式发送

如果 SMP 请求或响应太大，无法放入单个 GATT 命令，发送方会将其分片到多个数据包中。请求或响应分片时不会引入额外的帧格式，载荷只是被拆分到多个数据包中。由于 GATT 保证数据包按顺序交付，第一个分片中的 SMP 头部已包含重组所需的足够信息。

UART/串口和控制台

Zephyr 的 MCUmgr 子系统所采用的 SMP 协议规范使用基本的数据成帧，以便对 UART 通道进行复用。复用要求每个帧以两字节标记开头，并以换行符结尾。目前 MCUmgr 将帧大小限制为 127 字节，尽管协议本身并没有真正需要这一限制的约束。该限制包括前缀和换行符，因此允许的载荷大小实际上是 124 字节。

虽然 Zephyr 中没有这样的传输，但可以在完全不成帧、使用硬件串口控制或采用其他成帧方式的 UART 传输上实现 MCUmgr 客户端/服务器。

帧分片

基于串口的 SMP 协议被分片为最多 127 字节的帧；每个帧由两字节起始标记、帧体和结尾的换行符组成。

帧共有四种类型：initial、partial、partial-final 和 initial-final；各类型帧的起始标记和/或帧体内容不同。

帧格式

initial 帧之后可以跟随一串可选的 partial 帧，最后必须跟随一个 partial-final 帧。帧体始终采用 Base64 编码，因此此处表示为 MTU - 3 的帧体大小实际上能够承载 N = (MTU - 3) / 4 * 3 字节的原始数据。

initial 帧的帧体前面有两字节的数据包总长度，采用大端编码，其值等于原始帧体大小加上 CRC16 的大小两字节；这意味着 initial 帧中实际允许的帧体大小为 N - 2。

如果帧体大小小于 N - 4，则可以在单个帧中承载整个帧体及其前面的长度和后面的 CRC，这种帧称为 initial-final；initial-final 帧的说明见下文。

原始 UART/串口（不经过控制台）

Zephyr 为 UART 提供了另一种传输方式，它不像基于控制台的 SMP 传输那样使用 Base64，因此代码更小、传输更快。但由于所有通信都使用原始二进制 SMP 协议，它不能用于在同一 UART 上有 shell 或日志输出的设备，也不能用于连接到显示 ASCII 数据的终端的设备。

要使用该协议，请使用 CONFIG_MCUMGR_TRANSPORT_RAW_UART，它要求以原始模式启用 MCUmgr UART 控制台驱动。

超时

由于使用该传输时不成帧，UART 上可能会收到无效数据，导致系统一直等待（例如等待一个永远不会到达的超长数据包）。为防止这种情况，提供了一个超时机制：如果未在特定时间内收到完整的数据包，就清空整个接收缓冲区。建议在 UART 端口上启用此选项；对于 USB CDC 这类“虚拟”UART，数据在传递前可以得到验证，因此不需要此选项。可以通过 CONFIG_MCUMGR_TRANSPORT_RAW_UART_INPUT_TIMEOUT 启用该选项，并通过 CONFIG_MCUMGR_TRANSPORT_RAW_UART_INPUT_TIMEOUT_TIME_MS 设置超时时间。
