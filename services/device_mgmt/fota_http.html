基于 HTTP 的固件空中升级

概述

FOTA HTTP 库从 HTTP 服务器下载固件镜像，并将其直接写入当前未运行的 MCUboot 槽位。随后，应用程序可以请求交换、确认新镜像或擦除该槽位。与 hawkBit 或 UpdateHub 不同，它不涉及任何设备管理协议：任何能够提供文件的 Web 服务器都可以充当更新源，因此非常适合简单的部署场景和台架测试。

镜像在到达时即通过 Flash 镜像 流式写入 Flash，因此其大小不受 RAM 限制。槽位在写入过程中逐步擦除，并且在第一个字节写入之前就会清除该槽位的 MCUboot 尾部（trailer），因此先前镜像的残留数据永远不会被误认为待处理的交换。

下载完成后，库会从 Flash 中读回 MCUboot 头部，如果数据不是镜像，则以 -ENOEXEC 失败。它不验证签名：MCUboot 会在镜像启动之前进行验证，并由这项检查决定镜像能否运行。启用 CONFIG_FOTA_HTTP_SHA256_CHECK 后，可以与调用者提供的摘要进行可选的 SHA-256 比较，以便在重启之前发现传输损坏。被该比较或下文所述的降级检查拒绝的镜像会从槽位中擦除。如果下载中途失败，fota_http_apply() 会拒绝使用该槽位，直到再次成功下载到该槽位为止；而部分数据会保留在原处，以便续传。

更新周期

典型的流程如下：

  1. fota_http_download() 或 fota_http_download_async() 将镜像获取到次槽位中。fota_http_download_params 的可选成员 sha256、resume 以及与 TLS 相关的成员，只有在启用相应 Kconfig 选项时才存在。

  2. fota_http_apply() 将镜像标记为测试启动或永久启用。

  3. 设备重启，MCUboot 将镜像交换到位。

  4. 在测试启动时，应用程序自行验证后调用 fota_http_confirm()。如果没有这一调用，下次重启时 MCUboot 会回退到先前的镜像。

回退步骤要求 MCUboot 处于支持回退的模式，例如 swap-using-move 或 swap-using-offset。在仅覆盖（overwrite-only）模式下，交换一旦发生，先前的镜像就不复存在，确认也不起作用，因此请检查开发板的 sysbuild 配置选择了哪种模式。

测试镜像运行期间，次槽位中保存的是 MCUboot 要回退到的镜像，因此在调用 fota_http_confirm() 之前，fota_http_download() 会以 -EPERM 拒绝下载。

线程与栈

fota_http_download() 在整个传输期间阻塞调用线程，并需要足够的栈来运行 HTTP 客户端，使用 https 时还需支持 TLS 握手。启用 CONFIG_FOTA_HTTP_ASYNC 后，fota_http_download_async() 会在库拥有的线程上执行同样的传输，该线程的栈大小由 CONFIG_FOTA_HTTP_THREAD_STACK_SIZE 决定，并通过完成回调报告结果。shell 命令选用异步版本，因此与 shell 的栈大小无关。只调用 fota_http_download() 的应用程序可以保持该选项禁用，从而无需为该线程栈付出开销。

同一时刻只能运行一个下载。fota_http_cancel() 会在下一个分片到达或请求超时时中止正在进行的传输。

重定向与续传

对于状态码为 301、302、303、307 或 308 的响应，最多跟随 CONFIG_FOTA_HTTP_MAX_REDIRECTS 次重定向。绝对形式和仅含路径形式的 Location 头部都可以接受。

启用 CONFIG_FOTA_HTTP_RESUME 后，在传输进行期间以及传输失败时，下载偏移量会保存在设置中。之后设置了 resume 参数的下载会通过 HTTP Range 请求从该偏移量继续。只有当 URL 和镜像索引与中断的下载一致时才会复用该偏移量；如果服务器发送过 ETag 或 Last-Modified 头部，请求会同时携带 If-Range，因此服务器上已更改的文件会从头重新获取。如果服务器忽略 Range 头部并返回完整文件，传输会从零重新开始；收到 416 Range Not Satisfiable 应答（文件变得比已保存的偏移量更短时服务器会发送该应答）时也是如此。如果校验值（validator）过长而无法存储，也会丢弃已保存的进度，以便下一次下载从头开始，而不是针对可能已更改的文件续传。镜像下载完成后，该偏移量即被清除。

多镜像

在包含多个可更新镜像的布局中，image_index 参数用于选择下载到哪个次槽位。fota_http_apply() 和 fota_http_confirm() 都接受同样的索引，因此在携带另一设备固件的布局中，只会确认本设备已验证的镜像。当多个镜像必须一起运行时，应在重启之前下载并应用所有这些镜像：MCUboot 会验证整组镜像并一次性完成交换；之后还要逐一确认每个镜像，因为未确认的镜像会被单独回退。fota_http_confirm_pending() 只报告镜像 0，因此更新多个镜像的应用程序需要自行跟踪其余镜像。CONFIG_FOTA_HTTP_REJECT_DOWNGRADE 的降级检查也只涵盖镜像 0。

使用 direct-XIP 引导加载程序时，镜像运行所在的槽位在链接时就已确定，因此设备必须获取为空闲槽位构建的镜像变体。fota_http_get_download_slot() 会报告该槽位。这只适用于单镜像布局：对于第一个之后的所有镜像，库总是上传到槽位对中编号为奇数的槽位，这对交换模式和覆盖模式是正确的，但对 direct-XIP 不正确。

降级保护

CONFIG_FOTA_HTTP_REJECT_DOWNGRADE 会将下载的头部中的版本与正在运行的镜像进行比较，如果版本更旧，则使下载失败，并擦除被拒绝的镜像，以免被误应用。这是为应用程序提供的便捷检查。强制执行的策略应由引导加载程序负责，请参阅 MCUboot 的降级防护和硬件回滚保护选项。

TLS

启用 CONFIG_FOTA_HTTP_TLS 后即可接受 https URL。服务器的 CA 证书会在 CONFIG_FOTA_HTTP_TLS_SEC_TAG 或下载参数中传入的标签下查找，可以通过 fota_http_tls_add_ca() 或直接通过 tls_credential_add() 注册。对于双向 TLS，请使用 fota_http_tls_add_client_cert() 注册客户端证书和密钥。

默认要求验证对端，在生产环境中应保持 CONFIG_FOTA_HTTP_TLS_PEER_VERIFY 的默认值。URL 中的主机名会与证书进行比对验证。如果 URL 中使用的是 IP 地址且证书中没有匹配的条目，请在 tls_hostname 参数中传入预期的名称。

只有在启用 CONFIG_MBEDTLS_HAVE_TIME_DATE 时才会强制检查证书的有效期，这要求设备在首次下载之前具有正确的挂钟时间。可以通过 CONFIG_FOTA_HTTP_TLS_VERSION_1_3 选择 TLS 1.3。

Shell 命令

启用 CONFIG_FOTA_HTTP_SHELL 后，fota 命令可以在控制台中使用该库：

fota download <url> [resume] [image=<n>]   download an image
fota cancel                                abort the download in progress
fota apply [permanent] [image=<n>]         boot the downloaded image on the next reset
fota confirm [image]                       confirm the running image
fota status                                show images and confirmation state
fota erase [image]                         erase the secondary slot

完整的操作演示请参阅 Firmware Over-the-Air over HTTP 示例。
