核心转储

核心转储（core dump）模块可以转储 CPU 寄存器和内存内容，供离线调试使用。遇到致命错误时会调用该模块，它根据启用的后端打印或存储数据。

配置

使用以下选项配置该模块。

  • DEBUG_COREDUMP：启用该模块。

以下是启用核心转储输出后端的选项：

  • DEBUG_COREDUMP_BACKEND_LOGGING：使用日志模块输出核心转储。

  • DEBUG_COREDUMP_BACKEND_LOGGING_UDP：与日志后端相同，但可选择以原始 UDP 方式传输；对端为 DEBUG_COREDUMP_LOGGING_UDP_HOST，这是一个由 net_ipaddr_parse() 解析的字符串（IPv4 或 IPv6，可选 :port，省略时默认 UDP 端口为 17777）。使用 scripts/coredump/coredump_udp_receiver.py 为 scripts/coredump/coredump_gdbserver.py 生成二进制文件。

  • DEBUG_COREDUMP_BACKEND_FLASH_PARTITION：使用 Flash 分区输出核心转储。

  • DEBUG_COREDUMP_BACKEND_NULL：在无法启用其他后端时使用的后备核心转储后端。所有输出都发送到 null。

以下是关于内存转储的选项：

  • DEBUG_COREDUMP_MEMORY_DUMP_MIN：只转储发生异常的线程的栈、其线程结构体，以及支持在调试器中遍历栈所需的其他最少量数据。仅在需要转储绝对最少数据时使用。

  • DEBUG_COREDUMP_MEMORY_DUMP_THREADS：转储所有线程的线程结构体和栈，以及调试线程所需的全部数据。

  • DEBUG_COREDUMP_MEMORY_DUMP_LINKER_RAM：转储 _image_ram_start[] 与 _image_ram_end[] 之间的内存区域。其中至少包括 data、noinit 和 BSS 段。这是默认选项。

可以通过一个或多个 核心转储设备 在转储中加入更多内存（即使选择了“DEBUG_COREDUMP_MEMORY_DUMP_MIN”配置）

用法

启用核心转储模块后，发生致命错误时，会根据启用的后端打印或存储 CPU 寄存器和内存内容。这些核心转储数据可以输入一个定制的 GDB 服务器，作为 GDB（及其他兼容 GDB 的调试器）的远程目标。在调试器中可以检查 CPU 寄存器、内存内容和栈。

通常包括以下步骤：

  1. 根据启用的后端，从设备获取核心转储日志。例如，如果使用日志模块后端，则从日志模块后端获取日志输出。

  2. 将核心转储日志转换为 GDB 服务器可以解析的二进制格式。例如，可以使用 scripts/coredump/coredump_serial_log_parser.py 将串口控制台日志转换为二进制文件。如果启用了 UDP 核心转储后端（DEBUG_COREDUMP_BACKEND_LOGGING_UDP），则在收集端主机上运行 scripts/coredump/coredump_udp_receiver.py，把 UDP 数据报重新组装成 相同 的原始二进制格式。

  3. 使用脚本 scripts/coredump/coredump_gdbserver.py 启动定制的 GDB 服务器，以核心转储二进制日志文件和 Zephyr ELF 文件作为参数。也可以在 GDB 内部启动 GDB 服务器，见下文。

  4. 启动与目标架构对应的调试器。

备注

使用 ZEPHYR_TOOLCHAIN_VARIANT=zephyr 的 Intel ADSP CAVS 15-25 平台开发者应使用 SDK 中 xtensa-intel_apl_adsp 工具链里的调试器。

  1. 启用 DEBUG_COREDUMP_BACKEND_FLASH_PARTITION 时，核心转储数据存储在 Flash 分区中。该 Flash 分区必须在设备树中定义：

    &flash0 {
   partitions {
      coredump_partition: partition@255000 {
         label = "coredump-partition";
         reg = <0x255000 DT_SIZE_K(4)>;
      };
   };
};

  1. 运行核心转储串口日志转换器：

    ./scripts/coredump/coredump_serial_log_parser.py coredump.log coredump.bin

  2. 启动定制的 GDB 服务器：

    ./scripts/coredump/coredump_gdbserver.py build/zephyr/zephyr.elf coredump.bin

  3. 启动 GDB：

    <path to SDK>/x86_64-zephyr-elf/bin/x86_64-zephyr-elf-gdb build/zephyr/zephyr.elf

  4. 在 GDB 中，通过端口 1234 连接到 GDB 服务器：

    (gdb) target remote localhost:1234

在 GDB 内部启动 GDB 服务器

可以使用 target remote | 在 GDB 内部启动定制的 GDB 服务器，而不必在单独的 shell 中启动。

  1. 启动 GDB：

    <path to SDK>/x86_64-zephyr-elf/bin/x86_64-zephyr-elf-gdb build/zephyr/zephyr.elf

  2. 在 GDB 中，使用 --pipe 选项启动 GDB 服务器：

    (gdb) target remote | ./scripts/coredump/coredump_gdbserver.py --pipe build/zephyr/zephyr.elf coredump.bin

添加新目标

架构相关块与目标相关，新目标需要新的转储例程和解析器。要添加新目标，需要完成以下工作：

  1. 在 include/zephyr/debug/coredump.h 的 enum coredump_tgt_code 中添加新的目标代码。

  2. 实现 arch_coredump_tgt_code_get()，只需返回新引入的目标代码。

  3. 实现 arch_coredump_info_dump()，构造目标架构块并调用 coredump_buffer_output() 将该块输出到核心转储后端。

  4. 在 scripts/coredump/gdbstubs/ 下的核心转储 GDB stub 脚本中添加解析器

    1. 继承 gdbstubs.gdbstub.GdbStub 类。

    2. 在 __init__ 中，将与异常原因对应的 GDB 信号存入 self.gdb_signal。

    3. 从 self.logfile.get_arch_data() 解析架构相关块。其格式需要与第 3 步中（arch_coredump_info_dump() 内）实现的格式一致。

    4. 实现抽象方法 handle_register_group_read_packet，按 GDB 期望的方式返回寄存器组。关于新目标 GDB 期望什么，请参阅 GDB 的代码和文档。

    5. 可选地实现 handle_register_single_read_packet，用于 g 数据包未涵盖的寄存器。

  5. 扩展 scripts/coredump/gdbstubs/__init__.py 中的 get_gdbstub()，使其返回新实现的 GDB stub。
