资源管理

在很多情况下，需要在运行时协调多个客户端对资源的使用，例如电源轨、时钟、其他外设以及二值（开/关）设备电源管理。在多线程系统中正确管理一个设备的多个使用者相当复杂，尤其是在状态转换可能是异步的情况下，因此最好有一套共享的实现。

Zephyr 为几种协调策略提供了管理器。这些管理器嵌入在使用它们实现特定功能的服务中。

  • 开关管理器（On-Off Manager）

开关管理器（On-Off Manager）

开关管理器支持任意数量的客户端使用一个具有二值状态的服务。典型的应用包括电源轨、时钟以及二值设备电源管理。

该管理器具有以下特性：

  • 稳定状态有关闭（off）、开启（on）和错误（error）。服务总是从关闭状态开始。服务也可能正处于向某一状态转换的过程中。

  • 核心操作是请求（request，添加一个依赖）和释放（release，移除一个依赖）。辅助操作包括复位（reset，清除错误状态）和取消（cancel，从进行中的转换里收回客户端数据）。服务根据发起这些操作的函数调用来管理状态。

  • 收到第一个客户端请求时，服务从关闭转换为开启。

  • 收到最后一个客户端释放时，服务从开启转换为关闭。

  • 每个服务配置都提供实现以下转换的函数：从关闭到开启、从开启到关闭，以及（可选的）从错误状态到关闭。转换必须既能在线程上下文中调用，也能在中断上下文中调用。

  • 请求和复位操作是异步的，使用 异步通知。两种操作都可以取消，但取消不会影响正在进行的转换。

  • 在向关闭状态转换的过程中，可以将开启请求排队：服务成功关闭后，会立即再次开启（在上下文允许的情况下），并在启动完成时通知等待中的客户端。

请求采用引用计数，但不跟踪具体请求。这意味着客户端需要自行记录其请求是否被接受，并且只有在之前已成功完成请求后才能发起释放。不正确地使用该 API 可能导致某个活动客户端被拒之门外，而管理器并不记录哪些具体客户端的请求已被批准。

执行转换时发生的失败会被记录下来，并在管理器复位之前阻止后续的请求或释放。发现错误时，会通知（并取消）挂起的请求。

转换操作的完成通知通过 异步通知 提供。

如果客户端和其他组件希望跟踪服务的所有状态变化，包括服务开始关闭或进入错误状态的时刻，可以使用 onoff_monitor_register() 注册一个监视器，从而获知状态转换。状态变化的通知会在发出与新状态相关的完成通知之前提供。

备注

一个通用 API 可能由多个驱动实现，而常见情况是异步的。开关客户端结构体可能适合作为这种通用 API 的解决方案。如果驱动能够保证转换是同步且与上下文无关的，则可以使用 onoff_sync_service 及其配套 API，而非 onoff_manager，功能上只有少量缩减（主要是不支持监视器 API）。
