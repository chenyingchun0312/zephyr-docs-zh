使用动态分配缓冲区的 ICMsg 后端

通过该后端传输的数据位于共享内存上动态分配的缓冲区中。分配操作是线程安全的，可以在任何上下文中进行。该后端支持：

  • 多个端点。

  • 无拷贝发送。

  • 持有 RX 缓冲区。

  • 从中断上下文发送。

  • 两级端点优先级。

  • 统计信息，以及可选的带利用率报告的 shell 命令

  • 最多支持 32 个块。

  • 数据缓存支持。

  • 内存占用小（约 2 kB 代码）。

概述

每个方向都保留一个共享内存区域，每个区域分为两部分。一部分构成一个固定大小缓冲区的池，分配器用池中相邻的缓冲区构建可变大小的缓冲区。另一部分用于控制路径，由（每个方向的）两个消息队列组成：一个是生产者队列，由发送方写入、接收方读取；另一个是消费者队列，由接收方写入、发送方读取。生产者队列中包含下一条消息（在池中）的位置信息，消费者队列中包含已消费消息（在池中）的位置信息。

数据发送过程如下：

  • 发送方从池中分配一个或多个块。如果没有足够的连续块，线程上下文会按参数中提供的超时进行等待，超时也可以是 K_FOREVER 和 K_NO_WAIT。

  • 向分配的块中填充数据。第一个块的开头是一个 32 位的消息头，包含长度、端点 ID 和本块索引。对于零拷贝的情况，由调用者完成填充；否则会自动复制。在此期间，只要有足够的空闲块，其他线程就不会受到任何阻塞，可以分配块、发送数据和接收数据。

  • 将消息起始所在的块索引写入生产者队列，并在块索引上附加端点的优先级信息。CONFIG_IPC_SERVICE_BACKEND_ICBMSG_MAX_ACTIVE_COUNT 定义了队列中的槽位数。随后向接收方发送邮箱（mailbox）通知。

  • 接收方读取生产者队列，优先处理高优先级的消息。它可以按需持有数据，时间不限。同样，只要有足够的空闲块，其他线程就不会被阻塞。

  • 不再需要数据时，接收方将块索引写入消费者队列。

  • 发送方通过读取消费者队列并释放缓冲区来执行垃圾回收。垃圾回收在发送任何消息之后或者没有可用缓冲区时执行。

配置

该后端通过 Kconfig 和设备树进行配置。

有以下 Kconfig 选项：

CONFIG_IPC_SERVICE_BACKEND_ICBMSG_NUM_EP：已注册端点的最大数量。

CONFIG_IPC_SERVICE_BACKEND_ICBMSG_MAX_ACTIVE_COUNT：队列中的槽位数。

CONFIG_IPC_SERVICE_BACKEND_ICBMSG_DEINIT：支持注销和关闭。

CONFIG_IPC_SERVICE_BACKEND_ICBMSG_SHELL：支持 shell 命令。

配置后端时，请执行以下操作：

  • 如果至少有一个核在共享内存上使用数据缓存，请设置 dcache-alignment 值。该值必须取通信双方的无效化（invalidation）大小或回写（write-back）大小中的最大值。如果通信双方都没有在共享内存上使用数据缓存，可以跳过此项。

  • 定义两个存储区域，并将它们分配给实例的 tx-region 和 rx-region。确保用于数据交换的存储区域是唯一的（不与任何其他区域重叠），并且两个域（或 CPU）都可以访问。

  • 使用 tx-blocks 和 rx-blocks 定义每个区域中可分配块的数量。

  • 定义 MBOX 设备，用于发送信号，通知另一个域（或 CPU）数据已写入。确保另一个域（或 CPU）能够接收该信号。

小心

务必为 dcache-alignment 设置正确的值。错误的值起初可能不会表现出任何迹象，从而给人一切正常的错觉，但不稳定的行为迟早会出现。

如果使用了 dcache-alignment，则应谨慎选择块数配置，以免内存使用效率低下。这是因为块和控制数据都按缓存对齐，如果块数不是缓存对齐的倍数，最后一个块就无法得到高效利用。例如，假设 dcache-alignment 为 32，一个方向使用 1024 字节的共享内存。控制数据占用 64 字节，剩下 960 字节用于缓冲区。使用 16 个块时，每块为 32 字节（由于缓存对齐）；使用 15 个块时，每块为 64 字节（由于缓存对齐），内存利用率要好得多。

请参阅以下其中一个实例的配置示例：

reserved-memory {
   tx: memory@20070000 {
      reg = <0x20070000 0x0800>;
   };

   rx: memory@20078000 {
      reg = <0x20078000 0x0800>;
   };
};

ipc {
   ipc0: ipc0 {
      compatible = "zephyr,ipc-icbmsg";
      dcache-alignment = <32>;
      tx-region = <&tx>;
      rx-region = <&rx>;
      tx-blocks = <16>;
      rx-blocks = <16>;
      mboxes = <&mbox 0>, <&mbox 1>;
      mbox-names = "tx", "rx";
      status = "okay";
   };
};

必须为通信的另一方（域或 CPU）提供类似的配置。交换 MBOX 通道、存储区域（tx-region 和 rx-region）以及块数（tx-blocks 和 rx-blocks）。

限制

  • 要求通信双方的字节序相同。

  • 不支持检测远端的意外复位。

示例

  • IPC service: Multi-endpoint

详细协议规范

ICBMsg 协议使用动态分配的共享内存块来传输消息。

共享内存的组织

ICBMsg 使用两个共享内存区域：rx-region 用于接收消息，tx-region 用于发送消息。这两个区域不需要彼此相邻，不需要按特定顺序放置，大小也不必相同。这两个区域在两个核上是互换的。

每个共享内存区域分为以下两部分：

  • 控制区：由生产者队列和消费者队列占用的区域。

  • 块区：包含承载消息内容的可分配块的区域。该区域被划分为大小相同、按缓存边界对齐的块。

各个区的位置经过计算，既满足缓存边界要求，又能最优地利用区域。计算采用以下算法：

输入：

  • region_begin、region_end：区域的边界。

  • local_blocks：本区域中的块数。

  • remote_blocks：对端区域中的块数。

  • alignment：存储器缓存对齐。

算法：

  1. 将区域边界按缓存对齐：

    • region_begin_aligned = ROUND_UP(region_begin, alignment)

    • region_end_aligned = ROUND_DOWN(region_end, alignment)

    • region_size_aligned = region_end_aligned - region_begin_aligned

  2. 计算控制区所需的最小大小：

    • 每个队列占用 IPC_SERVICE_BACKEND_ICBMSG_MAX_ACTIVE_COUNT 字节，外加 8 字节的队列头。

    • 通常每个方向的控制数据不超过 64 字节。

  3. 计算块区的可用大小。注意，由于块对齐，实际大小可能更小：

    blocks_area_available_size = region_size_aligned - control_area

  4. 计算单个块的大小：

    block_size = ROUND_DOWN(blocks_area_available_size / local_blocks, alignment)

  5. 计算块区的实际大小：

    blocks_area_size = block_size * local_blocks

  6. 计算块区的起始地址：

    blocks_area_begin = region_end_aligned - blocks_area_size

结果：

  • region_begin_aligned：ICMsg 区的起始位置。

  • blocks_area_begin：ICMsg 区的结束位置，也是块区的起始位置。

  • block_size：单个块的大小。

  • region_end_aligned：块区的结束位置。


消息传输

ICBMsg 使用以下两种类型的消息：

  • 控制消息：绑定或解除绑定之类的消息。

  • 数据消息：承载实际用户数据的消息。

它们的用途不同，但生命周期和流程相同，具体步骤如下：

  1. 发送方要发送一条包含 K 字节的消息。

  2. 发送方从自己 tx-region 的块区中预留能够容纳至少 K + 4 字节的块。额外的 + 4 字节为消息头预留。这些块必须是连续的（一个接一个）。发送方负责管理块的分配。如果没有可用的块，线程上下文可能会阻塞，中断上下文则会返回错误。

  3. 发送方填写消息头。

  4. 发送方用自己的数据填充块的其余部分。未使用的空间会被忽略。

  5. 发送方将消息写入生产者队列，并发送邮箱信号。

  6. 接收方在邮箱中断上下文中执行邮箱回调，并读取生产者队列。

  7. 接收方读取块索引，并在自己的 rx-region 中定位该消息。

  8. 接收方读取端点和消息长度，然后处理该消息。

  9. 接收方将消息的块索引写入消费者队列，从而消费该消息。此时不发送邮箱信号。

  10. 发送方在每次发送之后或发送失败时检查消费者队列。从消费者队列中读取消息，并将其释放回池中。


绑定实例

打开后端实例时，它会发送一条包含 64 位魔数的绑定消息。随后启用邮箱回调，实例开始等待绑定消息。收到绑定消息后，该实例即与远端实例绑定，可以注册端点。

绑定端点

端点绑定消息包含端点名称的 SHA 以及端点 ID，端点 ID 是存放端点数据的本地数组中的索引。

有两种可能的情况：

  • 远端实例在端点注册之前就已发送了该端点的绑定消息。

  • 端点在收到远端实例的绑定消息之前就已注册。

收到绑定消息时，将其中的 SHA 与端点数据数组中存储的 SHA 进行比较。如果找到匹配项，说明本地实例已经注册了该端点，此时将端点 ID 存入端点数据并调用绑定回调。如果找不到匹配项，则查找一个空槽位，将端点 ID 和 SHA 存入该槽位。

注册端点时，计算端点名称的 SHA，并与端点数据数组中存储的 SHA 进行比较。如果找到匹配项，说明已经收到该端点的远端绑定消息，此时向远端实例发送绑定消息并调用绑定回调。如果找不到匹配项，则查找一个空槽位，将端点 ID 和 SHA 存入该槽位，并向远端实例发送绑定消息，但端点此时尚未绑定。

此后，数据消息使用远端端点 ID 来标识端点。

解除端点绑定

注销端点时，会发送解除绑定控制消息，并将该端点从端点数据数组中移除。收到解除绑定消息时，将对应端点槽位标记为空，并调用解除绑定回调。
