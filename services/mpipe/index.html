概述

多媒体流水线子系统（mpipe）用一组称为元素（element）的独立处理组件构建媒体流。应用程序声明所需的元素，将它们链接成一个图，并通过状态机驱动该图。mpipe 负责在相邻元素之间协商数据格式、确定缓冲区配置，并在元素之间传递缓冲区。

mpipe 提供的是组件以及组件之间的组合规则，而不是现成的解决方案。只需把元素绑定到不同的设备，同一个图就能在另一块开发板上运行；出现新的需求时，通常只需增加一个元素，而不必重写。

元素本身位于按媒体领域分组的插件（plugin）中。插件可以独立添加，拥有自己的目录、Kconfig 和头文件，而无需改动框架。

mpipe 不进行任何动态分配。元素和流水线都是应用程序拥有的对象，缓冲区来自在流水线启动时确定大小的池，能力（capability）则是按值传递的固定大小结构体。协商在调用 mpipe_element_set_state() 的线程上运行，因此该线程需要足以支持协商的栈大小。

mpipe 是可选的，也并不总是合适的工具。只驱动单个设备的应用程序直接使用该设备的 API 会更好。当多个设备需要就格式达成一致并相互传递缓冲区时，mpipe 才能发挥作用。

构建流水线

应用程序包含 <zephyr/mpipe/mpipe.h> 以使用流水线 API；每实例化一种元素，还要包含该元素自己的头文件。

元素是应用程序拥有的普通对象，mpipe 不分配任何元素。每种元素类型都有自己的初始化函数，接收该类型的对象和一个 id：

/* Concrete element types come from plugins; each has its own header. */
static struct mpipe pipe;
static struct my_src source;
static struct my_sink sink;

ret = mpipe_pipeline_init(&pipe, PIPE_ID);
ret = my_src_init(&source, SRC_ID);
ret = my_sink_init(&sink, SINK_ID);

id 只需在流水线内唯一。元素通过属性进行配置，这样调用者无需知道元素的具体类型即可完成设置：

ret = mpipe_object_set_properties((struct mpipe_object *)&source,
                                  MY_SRC_PROP_PATH, "/SD:/in.bin",
                                  MPIPE_PROP_LIST_END);

然后以任意顺序将它们添加到流水线中，并按流的顺序链接起来：

ret = mpipe_bin_add((struct mpipe_bin *)&pipe,
                    (struct mpipe_element *)&source,
                    (struct mpipe_element *)&sink, NULL);

ret = mpipe_element_link((struct mpipe_element *)&source,
                         (struct mpipe_element *)&sink, NULL);

这些强制类型转换是明确定义的，因为每个元素都将其基类嵌入为第一个成员。如果两个元素的能力不可能有交集，链接操作就会拒绝它们，因此不可能成立的图会在构建时失败，而不是在启动时才失败。

将流水线设置为 MPIPE_STATE_PLAYING 并不是直接跳到该状态。流水线及其子元素会按顺序依次经历各个状态，从 READY 到 PAUSED 再到 PLAYING，格式协商和池的启动正是在这一过程中完成的。

随后，应用程序监听流水线的消息通道，以便了解运行如何结束并对故障作出处理。错误消息会指明引发错误的元素及其所处的阶段，因此应用程序可以报告“能力协商在元素 3 处失败”，而不仅仅是“运行已停止”。将图恢复到 MPIPE_STATE_READY 即可将其拆除：

/* Needs CONFIG_ZBUS_MSG_SUBSCRIBER=y */
ZBUS_MSG_SUBSCRIBER_DEFINE(main_sub);

struct zbus_channel *bus = mpipe_element_get_bus_chan((struct mpipe_element *)&pipe);

ret = zbus_chan_add_obs(bus, &main_sub, K_FOREVER);

if (mpipe_element_set_state((struct mpipe_element *)&pipe, MPIPE_STATE_PLAYING) != 0) {
        /* the element that refused is still in its previous state */
}

const struct zbus_channel *chan;
struct mpipe_message msg;

do {
        ret = zbus_sub_wait_msg(&main_sub, &chan, &msg, K_FOREVER);
} while ((msg.type & (MPIPE_MESSAGE_ERROR | MPIPE_MESSAGE_EOS)) == 0);

(void)mpipe_element_set_state((struct mpipe_element *)&pipe, MPIPE_STATE_READY);

元素、pad 与链接

每个 mpipe 元素 都通过将 mpipe_object 嵌入为第一个成员来派生自它。mpipe_element 增加了状态机和 pad。每种元素基类（源、接收器、变换、解析器和 bin）各自增加该类元素所需的内容，例如 pad 以及协商过程调用的钩子；具体元素则嵌入一个基类并添加自己的字段。只承载数据的类型（能力、消息、分派）是这一层次结构之外的普通结构体：

  • mpipe_src 产生缓冲区，只有源 pad。由于它位于图的头部，它还负责驱动协商。

  • mpipe_sink 消费缓冲区，只有接收 pad。

  • mpipe_transform 各有一个源 pad 和一个接收 pad，将输入转换为输出。

  • mpipe_parser 将无格式的字节流切分成完整的帧，这与把一种格式转换为另一种格式是不同的工作。

  • mpipe_bin 容纳其他元素，并按状态转换所要求的顺序将状态变化转发给它们。

  • mpipe 是顶层 bin：它拥有流线程和消息通道。

mpipe_pad 是两个元素的连接点。它带有方向（源或接收）、所链接的对端以及在其上协商得到的能力。它还带有框架分派调用的回调：process_fn 接收缓冲区，query_fn 应答查询，event_fn 处理事件。链接两个元素就是将一个源 pad 链接到一个接收 pad，流的每一跳都是这样的一对。

状态机

元素处于三种状态之一，并且每次只能在相邻状态之间移动一步：

READY 表示已构造并链接，但不持有格式和缓冲区。主要工作发生在从 READY 到 PAUSED 的转换中：源驱动整个图的能力协商，缓冲池查询确定由谁提供缓冲区以及提供多少，然后启动各个池。

转换的方向决定了 bin 处理其子元素的顺序：

  • 向上转换时，子元素从接收器向源依次转换，这样在向下游元素推送任何数据之前，它已经准备就绪。

  • 向下转换时，子元素从源向接收器依次转换，这样就不会有元素继续向已经拆除的元素产生数据。

失败的转换不会被回滚。拒绝转换的元素保持原状态，而已经转换的元素保持其新状态。这是有意为之：由此得到的图能准确显示是哪个元素在哪次转换中拒绝了。

能力协商

能力（capability）描述跨越链接的数据：一种媒体类型加上一组字段，每个字段由一个 mpipe_caps_field 标识符和一个 mpipe_value 组成。它是一个 mpipe_structure，即按值持有的固定大小类型：

struct mpipe_structure s;

mpipe_structure_init_fields(&s, MPIPE_MEDIA_VIDEO,
    MPIPE_CAPS_PIXEL_FORMAT, MPIPE_TYPE_UINT, VIDEO_PIX_FMT_RGB565,
    MPIPE_CAPS_IMAGE_WIDTH, MPIPE_TYPE_UINT_RANGE, 16, 1280, 2,
    MPIPE_CAPS_IMAGE_HEIGHT, MPIPE_TYPE_UINT_RANGE, 16, 720, 2,
    MPIPE_CAPS_END);

字段可以保存单个值，也可以保存写作 [min, max, step] 的范围，因此上面的能力涵盖从 16 到 1280、步长为 2 的所有宽度。当两个能力的媒体类型相同、至少有一个共同的字段标识符，并且每个共同字段的值都有交集时，这两个能力就有交集。结果是两者的并集：共同字段保存求交后的值，只有一方带有的字段则原样传递。正因如此，约束才能沿着一串本身并不关心该约束的元素向下传递。ANY 能力不施加任何约束，与任何能力都有交集；pad 在协商之前带有的就是这种能力。空能力不带任何字段，与任何能力都没有交集。

源在从 READY 到 PAUSED 时分两轮驱动协商：

caps 查询向下游传递，每个元素先根据自己支持的内容收窄查询，再向自己的下游询问，返回的答复则收窄为整条链的共同部分。如果某个元素拒绝，源只是改为提供它支持的下一种格式，而不会使协商失败。

变换元素是值得关注的情况，因为它的两侧可能使用不同的格式：解码器输入一种格式，输出另一种格式。原地工作的元素在缓冲区所在位置直接改写缓冲区，因此通过它的格式不变。在两侧格式不同的情况下，transform_caps 钩子负责将能力从元素的一侧映射到另一侧。查询在两个方向上都要经由该钩子穿过元素：向外传递时用于询问下游对端，返回时再将答复重新表示为输入侧的形式。

答复中可能仍包含范围，因此源会将其固定（fixate），即把每个范围缩减为单个值，并将结果作为 caps 事件向下游通告。每个元素通过其 set_caps 钩子应用自己这一侧的配置，硬件实际上就是在这里完成配置的。

由于一个 pad 只持有一个能力而不是一组能力，对于支持多种格式的元素，框架按索引逐个遍历：先向它请求能力 0，然后是 1，依此类推，直到它报告没有更多能力为止。格式来自设备的元素在应答每个索引时会去询问其驱动。

缓冲池协商

仅有格式并不能说明一个图需要多少缓冲区、缓冲区必须多大、必须如何对齐，以及由谁的池提供。第二轮查询会在格式固定之后、在同一次转换中立即确定这些问题：

查询向下传递到接收器，提议（proposal）则在返回途中逐级写入，因此元素在做出任何决定之前，总是已经拿到了其下游的提议。

变换元素的两侧是分别确定的：decide_buffer_pool 根据下游的提议确定输出池，而 propose_buffer_pool 则用元素在输入侧的需求来应答上游的查询。例外情况是直通（passthrough），此时同一个缓冲区穿过元素，只需确定一个池。

提议要么是一个完整的池，要么只是一份配置。提供池可以让上游元素采用它，从而避免复制；提供配置则只声明需求，而不移交任何东西。无论哪种方式，针对提议者仍然拥有的池的需求，都只能通过 mpipe_buffer_pool_set_config() 传达给该池，由池的所有者进行验证、限制或拒绝。

谁启动池，谁就在从 PAUSED 到 READY 时停止它。正是这种对称性使停止后重新播放的行为与首次运行一致。

缓冲区流转

缓冲区流转是零拷贝的。每个产生数据的元素都拥有一个 mpipe_buffer_pool，它是对其底层存储的一张虚函数表（configure、set_config、start、stop、acquire_buffer、release_buffer）。借助这层间接性，插件可以直接交出其驱动已经拥有的缓冲区，而不是它的副本，因此摄像头采集的帧无需复制就能到达显示屏。在元素之间传递的是引用，而不是像素。

缓冲区是 Zephyr 的 net_buf 分配，并附带一个 mpipe_buffer_meta，其中记录框架需要了解的缓冲区信息：拥有它的池、其中有效数据的长度以及时间戳。

mpipe_push_buffer() 将缓冲区沿下游传递，依次调用每个元素的 process_fn，并跟随其产生的缓冲区继续传递。输出为 NULL 表示缓冲区已被消费，传递随即停止。处理函数拥有传给它的缓冲区，即使处理失败也要释放该缓冲区。

流水线运行时

流水线自己的线程驱动源：它获取一个缓冲区并将其推送到下游，直到源报告数据结束。随后，它向下游发送流结束（end-of-stream）事件，并使自身暂停。如果流水线需要让图的两个部分在不同线程上运行，就在两者之间放置一个队列元素。

  • 从 PLAYING 到 PAUSED 只会暂停源线程。已排队的内容都会保留，因此恢复后可以无损地继续。

  • 从 PAUSED 到 READY 会拆除图：仍在传递中的缓冲区被丢弃，子元素停止各自的池，并等待流线程结束（join）。

消息通过流水线的消息通道发送给应用程序，该通道是一个 zbus 通道，可以通过 mpipe_element_get_bus_chan() 获取。消息包含事件发生的位置（发出消息的元素）以及发生了什么：一个类型；如果是故障，还包括指明失败阶段的域和说明原因的 errno。消息不带面向人的字符串；描述故障的语句应记录在检测到故障之处的日志中，而应用程序根据域和 errno 进行分支处理。

带有多个接收器的流水线会为每个接收器产生一条流结束消息。流水线会对这些消息计数，只转发最后一条，因此应用程序恰好收到一次通知，而且永远不会在某个分支仍在运行时拆除图。

编写元素

元素在框架之外编写，不需要对框架做任何修改。它可以将某个基类嵌入为第一个成员，用自己的 id 调用该基类的初始化函数，并只覆盖自己需要的钩子：

struct my_sink {
        struct mpipe_sink sink;   /* must be first */
        const struct device *dev;
};

int my_sink_init(struct my_sink *self, uint8_t id)
{
        int ret = mpipe_sink_init(&self->sink, id);

        if (ret != 0) {
                return ret;
        }

        self->sink.sink_pad.enum_caps_fn = my_sink_enum_caps;
        self->sink.set_caps = my_sink_set_caps;

        return 0;
}

以下按流水线调用的顺序列出这些钩子：

  • 元素配置：对象上的 set_property 和 get_property，应用程序通过 mpipe_object_set_properties() 和 mpipe_object_get_properties() 调用它们。属性只配置该元素本身，不需要其他任何元素对其达成一致。

  • 元素能力：pad 上的 enum_caps_fn 给出元素支持的内容，每个索引对应一个能力，超出最后一个时报告 -ENOENT。构建时已知的能力用 MPIPE_STRUCTURE_DEFINE 定义一次，然后复制输出；只有运行时才知道的能力则通过查询驱动来构建。set_caps 应用协商确定的格式，硬件就在这里完成配置。变换元素还要实现 transform_caps，将一侧的能力映射到另一侧。

  • 缓冲区配置：下游元素通过 propose_buffer_pool 提出其需求，上游元素在拿到该提议后通过 decide_buffer_pool 做出决定。

  • 状态变化：change_state 执行元素在每次转换时要做的工作。它必须链式调用其基类，由基类完成每个元素都应执行的能力重置和池拆除。

  • 处理函数：接收 pad 上的 process_fn 是元素的核心。它接收一个缓冲区并拥有该缓冲区，然后交回自己产生的缓冲区；如果消费了该缓冲区，则返回 NULL。源没有处理函数：流水线线程从源的池中获取缓冲区。

基础元素

基础插件 CONFIG_MPIPE_BASE 包含不属于任何媒体领域的元素：

  • mpipe_caps_filter 约束其所在链接上协商的格式。

  • mpipe_tee 将每个缓冲区推送到图的每个分支。

  • mpipe_queue 在自己的线程上运行其下游的元素。

  • mpipe_app_src 作为源，注入应用程序推送的内容。

  • mpipe_app_sink 作为接收器，将到达它的内容交给应用程序。

调试

CONFIG_MPIPE_DUMP 通过 mpipe_dump_bin() 将流水线渲染为 Graphviz 图：包括每个元素及其状态和 pad、每个 pad 的对端，以及在其上协商得到的能力。

CONFIG_MPIPE_PLAYER 增加一个播放器，它从工作线程驱动流水线完成播放、暂停、停止和重新播放；启用 shell 时还提供相应的 shell 命令。

配置选项

  • CONFIG_MPIPE 启用该框架。每个插件都有自己的选项，并提供自己的 Kconfig 文件。

  • CONFIG_MPIPE_BASE 构建基础元素，每个元素由各自的选项控制。

  • CONFIG_MPIPE_DUMP 和 CONFIG_MPIPE_PLAYER 构建调试工具。

  • CONFIG_MPIPE_STRUCTURE_MAX_FIELDS 决定单个能力的大小。应按一次求交中可能出现的最大字段并集来设置它，而不是按单个元素设置的字段数。

  • CONFIG_MPIPE_NET_BUF_POOL_COUNT 决定共享 net_buf 池的大小：即所有流水线中同时在传递的缓冲区数量之和。

  • CONFIG_MPIPE_BIN_MAX_CHILDREN 限制单个 bin 中的元素数量，它决定了状态变化期间用于对元素排序的数组的大小。

  • CONFIG_MPIPE_THREADS_NUM、CONFIG_MPIPE_THREAD_STACK_SIZE 和 CONFIG_MPIPE_THREAD_DEFAULT_PRIORITY 配置流水线所使用的线程池。

  • CONFIG_MPIPE_WORKQUEUE 允许元素将有限的工作项卸载到一个共享的优先级工作队列上。

  • CONFIG_MPIPE_RPC 构建客户端元素，这些元素在另一个核上执行其处理。

  • CONFIG_MPIPE_FAKE_SRC 提供一个合成数据源，用于在真实源需要硬件的情况下测试图。
