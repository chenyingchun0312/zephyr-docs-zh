Zephyr 存储器存储（ZMS）

Zephyr 存储器存储（Zephyr Memory Storage）是一种新的键值存储系统，旨在适用于所有类型的非易失性存储技术。它既支持传统的片上 NOR Flash，也支持 RRAM 和 MRAM 等完全不需要单独擦除操作的新技术，也就是说，这类设备上的数据可以随时直接覆盖。

总体行为

ZMS 将存储空间划分为多个扇区（至少 2 个），每个扇区都会被键值对填充，直到写满。

键值对分为两部分：

  • 键部分写入一个称为 "ID-ATE" 的 ATE（Allocation Table Entry，分配表条目）中，ATE 从扇区底部开始存储。

  • 值部分称为“数据”（data），以原始形式从扇区顶部开始存储。

此外，每个扇区的最后几个位置存储头部 ATE，这些 ATE 用于描述扇区的状态（已关闭、已打开）以及 ZMS 的当前版本。

当前扇区写满时，我们首先确认下一个扇区为空，然后对扇区 N+2（N 为当前扇区编号）进行垃圾回收，即将其中有效的 ATE 移到空的 N+1 扇区，再擦除已完成垃圾回收的扇区，然后通过写入一个 garbage_collect_done ATE 和关闭 ATE（头部条目之一）来关闭当前扇区。之后转到下一个扇区，重新开始写入条目。

这一过程不断重复，直到到达分区末尾。然后对第一个扇区进行垃圾回收并擦除其内容，再从第一个扇区重新开始。

扇区中各元素的定义

Empty ATE 在擦除扇区时写入（位于扇区的最后一个位置）。

Close ATE 在关闭扇区时写入（位于扇区的倒数第二个位置）。

GC_done ATE 用于表示下一个扇区已经完成垃圾回收。该 ATE 可以位于扇区中的任意位置。

ID ATE 包含一个 zms_id_t 类型的键，并描述数据的存储位置、大小及其 CRC32。

Data 是与 ID-ATE 关联的实际值。

ZMS 如何工作？

挂载存储系统

挂载存储系统时，首先获取 Flash 参数，检查文件系统属性（sector_size、sector_count 等）是否正确，然后调用 zms_init 函数使存储进入就绪状态。

默认情况下，如果无法挂载分区，zms_mount() 会返回错误。对于面向恢复的用例，可以使用 zms_mount_force()，在首次挂载失败时自动擦除并重新初始化分区。

挂载标志

可以通过 zms_fs.mount_flags 中的可选标志控制 ZMS 的挂载行为。

  • 默认行为（未设置任何可选标志，mount_flags = 0）：如果分区已被擦除且找不到有效的 ZMS 头部，zms_mount() 会通过创建初始 ZMS 头部来格式化分区。

  • ZMS_MOUNT_FLAG_NO_FORMAT：如果分区已被擦除且找不到有效的 ZMS 头部，zms_mount() 不会格式化分区，而是返回 -ENOTSUP。

要挂载文件系统，必须初始化 zms_fs 结构体中的以下元素：

struct zms_fs {
        /** File system offset in flash **/
        off_t offset;

        /** Storage system is split into sectors, each sector size must be multiple of
         * erase-blocks if the device has erase capabilities
         */
        uint32_t sector_size;
        /** Number of sectors in the file system */
        uint32_t sector_count;

        /** Optional mount behavior flags (enum zms_mount_flags) */
        uint32_t mount_flags;

        /** Flash device runtime structure */
        const struct device *flash_device;
};

初始化

由于 ZMS 采用快进式写入机制，它必须找到上次停止时的最后一个扇区以及条目的最后一个指针。它必须查找一个已关闭扇区后跟一个已打开扇区的位置，然后在已打开的扇区中找到（恢复）最后写入的 ATE。之后，它会检查其后的扇区是否为空，如果不为空则将其擦除。

ZMS ID/数据写入

为了避免用相同的 ID 重复写入相同的数据，ZMS 必须在所有扇区中查找是否存在相同的 ID，然后比较其数据。如果数据相同，则不执行写入。如果必须执行写入，则在扇区中写入一个 ATE 和数据（如果操作不是删除）。如果扇区已满（无法容纳当前数据和 ATE），ZMS 必须移到下一个扇区，对新打开扇区之后的扇区进行垃圾回收，然后将其擦除。

ZMS ID/数据读取（带历史记录）

默认情况下，ZMS 会从最新到最旧遍历所有已存储的 ATE，查找具有相同 ID 的最后一份数据。如果找到 ID 匹配的有效 ATE，就取出其数据并返回读取的字节数。如果提供了不为 0 的历史计数，则会取出具有相同 ID 的较旧数据。

ZMS 条目枚举（迭代器 API）

应用程序无需提供预定义的 ID 列表即可枚举已存储的条目。当 ID 由有效载荷数据派生（例如打包后的地址），并且应用程序没有在 Flash 中维护单独的索引时，这一功能非常有用。

这组 API 通常在启动时使用，此时应用程序根据 ZMS 中持久化的 ID/长度元数据重建其内存中的状态。

迭代器 API 包括：

  • zms_iter_init()：初始化迭代器状态。

  • zms_iter_init_with_config()：初始化迭代器状态，并可选地设置 ID 掩码、闭区间 ID 范围和谓词过滤器。

  • zms_iter_next()：每次取出一个有效条目（唯一 ID）。

  • zms_iter_next_all()：取出所有匹配的条目（完整历史记录，包括删除标记）。

在 zms_iter_next() 与 zms_iter_next_all() 之间进行选择

  • zms_iter_next() 返回唯一的有效 (id, len) 对：

    • 跳过扇区/头部条目。

    • 跳过删除标记（len == 0 的条目）。

    • 如果同一 ID 在存储历史中出现多次，只返回最新的有效记录。

    • 为了保证唯一性，ZMS 会检查每个候选 ID 是否存在更新的条目，这可能需要额外的扫描。

  • zms_iter_next_all() 速度更快，它按遇到的顺序返回所有匹配的 (id, len) 对：

    • 返回同一 ID 的历史条目。

    • 返回删除标记（len == 0 的条目）。

    • 不执行唯一性过滤。

    • 应用程序负责按照自己的策略过滤/压缩返回的数据对。

    如果只想枚举与位掩码、特定闭区间 ID 范围、谓词回调或这些过滤器任意组合相匹配的 ID，请使用 zms_iter_init_with_config()。

迭代器返回值

调用 zms_iter_next() 或 zms_iter_next_all() 时返回：

  • 找到条目时返回 1；输出参数包含 ID 和数据长度。

  • 没有更多可枚举的条目时返回 0。

  • 出错时返回负的 errno（例如 -EINVAL、-EIO、-ENXIO）。

迭代器总是报告元数据（ID 和长度）。此外，当调用者提供非 NULL 的 data 缓冲区时，迭代器还会将条目内容直接复制到其中，但仅限于足够小、可以存储在 ATE 内部的条目。对于较大的条目，或者未提供缓冲区时，必须显式读取数据：使用 zms_read() 读取最新值，或使用 zms_read_hist() 读取较旧的版本。

并发与快照行为

调用 zms_iter_init() 时，迭代器会记录一个遍历边界。初始化之后写入的条目不属于本次遍历。

不要在两次迭代步进调用（zms_iter_next() 或 zms_iter_next_all()）之间对同一个 zms_fs 调用 zms_write()（包括删除操作）。如果迭代过程中的写入触发了垃圾回收，迭代器的行为是未定义的。无论是否加锁，这条规则都适用于执行迭代的线程：获取下文所述的锁只能阻止其他线程在遍历期间写入。

阻止并发写入者

zms_fs 将其内部写锁以普通的 struct k_mutex zms_lock 字段形式暴露出来。zms_write() 和 zms_delete() 在写入期间会在内部获取该互斥量。如果应用程序有多个线程共享同一个 zms_fs，可以在整个迭代过程中持有同一个互斥量，以便在遍历边界需要保持有效的期间阻止其他线程写入：

k_mutex_lock(&fs.zms_lock, K_FOREVER);

rc = zms_iter_init(&fs, &iter);
/* ... */

while ((rc = zms_iter_next(&fs, &iter, &id, &len, NULL, 0)) == 1) {
  /* ... */
}

k_mutex_unlock(&fs.zms_lock);

用法示例

struct zms_iter iter;
bool predicate_id_not_2(zms_id_t id)
{
  return id != (zms_id_t)2;
}

struct zms_iter_config iter_config = {
  .mask_id = (zms_id_t)0x03,
  .min_id = (zms_id_t)0x01,
  .max_id = (zms_id_t)0x03,
  .use_mask = true,
  .use_range = true,
  .use_predicate = true,
  .predicate_func = predicate_id_not_2,
};
zms_id_t id;
size_t len;
uint8_t data[ZMS_DATA_IN_ATE_SIZE];
int rc;

/* Block writes from other threads for the duration of the traversal. */
k_mutex_lock(&fs.zms_lock, K_FOREVER);

rc = zms_iter_init_with_config(&fs, &iter, &iter_config);
if (rc) {
  /* handle error */
}

while ((rc = zms_iter_next(&fs, &iter, &id, &len, data, sizeof(data))) == 1) {
  /* id: entry ID matching configured mask/range/predicate, len: current stored size */
  /* data: filled with the entry's content when it is small enough to be
   * stored directly inside the ATE; otherwise left untouched, in which case
   * zms_read() must be used to fetch it.
   */
  printk("id=0x%llx len=%zu\n", (unsigned long long)id, len);
}

k_mutex_unlock(&fs.zms_lock);

if (rc < 0) {
  /* handle iterator error */
}

如果只需要 (id, len) 对，可选参数 data/data_len 可以设为 NULL/0。提供缓冲区时，只会复制 ZMS 直接存储在 ATE 内部的数据；较大的条目仍须通过 zms_read() 获取。

将 zms_iter_config 零初始化，或保持 use_mask、use_range 和 use_predicate 处于禁用状态，即可保留默认行为：接受所有 ID 以及完整的 zms_id_t 范围。

要确定迭代器返回的某个 ID 有多少个版本，可以递增 cnt 调用 zms_read_hist()，直到返回 -ENOENT。

ZMS 空闲空间计算

ZMS 还可以返回分区中剩余的空闲空间。不过，此操作非常耗时，因为它需要遍历分区所有扇区中的全部有效 ATE，并针对每个有效 ATE 查找是否存在更旧的 ATE。由于该函数耗时且可能拖慢调用线程，不建议应用程序频繁使用。

循环计数器

每个扇区都有一个主循环计数器（lead cycle counter），它是一个 uint8_t，用于验证所有其他 ATE。主循环计数器存储在空 ATE（empty ATE）中。ATE 必须与空 ATE 中存储的循环计数器值相同才有效。每当 ATE 从一个扇区移到另一个扇区时，都必须采用目标扇区的循环计数器。擦除扇区时，会递增空 ATE 的循环计数器，并对空 ATE 执行一次写入。该扇区中的所有 ATE 随即失效。

关闭扇区

关闭扇区时，会在扇区末尾添加一个关闭 ATE（close ATE），其循环计数器必须与空 ATE 相同。关闭扇区时，所有尚未使用的剩余空间都会被填充为垃圾数据，以免遗留带有有效循环计数器的旧 ATE。

触发垃圾回收

某些应用程序需要确保存储写入具有明确的最大延迟。调用 ZMS 进行写入时，当前扇区可能几乎已满，以致 ZMS 需要触发 GC 切换到下一个扇区。此操作很耗时，会导致某些应用程序无法满足其实时性约束。ZMS 为此增加了一个 API，供应用程序获取当前扇区剩余的空闲空间。这样，应用程序就可以在当前扇区几乎写满时自行决定何时切换到下一个扇区。这当然会触发对下一个扇区的垃圾回收操作，但能保证应用程序的下一次写入不会触发垃圾回收。

一个条目使用 16 字节来编码其信息。具体结构由 ATE 格式决定，可以为特定应用程序选择 ATE 格式。

用户数据（键值对）的可用空间

ZMS 始终需要一个空扇区才能执行垃圾回收（GC）。因此，假设一个分区中有 4 个扇区，ZMS 只会使用其中 3 个扇区存储键值对，并保留一个空扇区以便执行 GC。这个空扇区会在分区的 4 个扇区之间轮换。

备注

一次可写入扇区的单个数据的最大长度为 64K（在 ZMS 的未来版本中可能会改变）。

小数据值

足够小的值会存储在条目（ATE）本身之中，而不会在扇区顶部写入数据。条目中能容纳的数据量取决于所选的格式。请参阅 ATE 结构 一节。

ZMS 的条目大小为 16 字节，这意味着在这种情况下，分区中可用于存储数据的最大空间按下式计算：

\[\small\frac{(NUM\_SECTORS - 1) \times (SECTOR\_SIZE - (5 \times ATE\_SIZE)) \times (DATA\_SIZE)}{ATE\_SIZE}\]

其中：

NUM_SECTOR：扇区总数

SECTOR_SIZE：扇区大小

ATE_SIZE：16 字节

(5 * ATE_SIZE)：为头部和删除项保留的 ATE

DATA_SIZE：8 字节或 4 字节，取决于 ATE 格式

例如，对于 4 个 1024 字节的扇区，采用默认 ATE 格式时，8 字节长度数据的可用空间为 \(\frac{3 \times 944 \times 8}{16} = 1416 \, \text{ bytes}\)。

大数据值

超过 DATA_SIZE 的值存储在 ATE 之外，位于扇区顶部。在这种情况下，很难估算可用的空闲空间，因为这取决于数据的大小。但可以考虑到：每在扇区顶部添加 N 字节数据，就必须在扇区底部额外添加 16 字节的 ATE，因此每个键值对总共占用 \(N + 16\) 字节。

举个例子：

对于一个包含 4 个 1024 字节扇区的分区，数据大小为 64 字节。只有 3 个扇区可用于写入，每个扇区的容量为 944 字节，因此每个扇区可以存储 11 个键值对（\(\frac{944}{64 + 16}\)）。在这种情况下，该分区总共可存储的数据为 \(11 \times 3 \times 64 = 2112 \text{ bytes}\)。

Advanced mode

磨损均衡

该存储系统针对不需要擦除的设备进行了优化。依赖擦除值的存储系统（例如 NVS）需要用写操作来模拟擦除。这会大大缩短这类设备的预期寿命，并增加写操作的延迟以及设备为空时的初始化时间。ZMS 使用循环计数机制，避免在这类设备上模拟擦除操作。它还保证在每个扇区写入周期内，每个存储位置只被写入一次。

例如，在不需要擦除操作的设备上，使用 NVS 擦除一个 4096 字节的扇区必须执行 256 次 Flash 写入（假设 write-block-size = 16 字节），而使用 ZMS 只需执行 1 次 16 字节的写入。在这种情况下，该操作快 256 倍。

垃圾回收操作在将数据块从一个扇区移到另一个扇区时会执行写操作，因此也会缩短存储单元的预期寿命。为了不让垃圾回收器影响设备的预期寿命，建议合理确定分区的大小。分区大小应为可能写入存储的数据最大大小（包括头部）的两倍。

参见 用户数据的可用空间。

设备寿命计算

存储设备，无论是传统的 Flash 还是 RRAM/MRAM 等新技术，其预期寿命都是有限的，由存储单元可被擦除/写入的次数决定。Flash 设备按其工作方式每次擦除一页（否则存储单元无法被覆盖），而对于不需要擦除操作的存储设备，存储单元可以直接被覆盖。

这里用一个典型场景来计算设备的预期寿命：假设我们使用同一个 ID 存储一个 4 字节变量，但其内容每分钟变化一次。分区有 4 个扇区，每个扇区 1024 字节。每次写入该变量需要 16 字节的存储空间。由于每个扇区有 944 字节可用于 ATE，而 ZMS 是快进式存储系统，因此我们将在 \(\frac{(944 \times 4)}{16} = 236 \text{ minutes}\) 之后重写第一个扇区的第一个位置。

除了正常写入之外，垃圾回收器还会将仍然有效的数据从旧扇区移到新扇区。由于本例使用的是同一个 ID，且分区足够大，垃圾回收器不会移动任何数据。对于可写入 20 000 次的存储设备，该存储大约可以使用 4 720 000 分钟（约 9 年）。

要得出更通用的公式，首先必须计算我们典型的数据集在 ZMS 中实际占用的有效大小。对于 小数据 的 ID/数据对，effective_size 为 16 字节；对于 大数据，effective_size 为 16 + sizeof(data) 字节。假设 total_effective_size 是写入存储的数据的总大小，并且分区大小设置得当（有效大小的两倍），以避免垃圾回收器频繁移动数据块。

设备的预期寿命（以分钟为单位）按下式计算：

\[\small\frac{(SECTOR\_EFFECTIVE\_SIZE \times SECTOR\_NUMBER \times MAX\_NUM\_WRITES)}{(TOTAL\_EFFECTIVE\_SIZE \times WR\_MIN)}\]

其中：

SECTOR_EFFECTIVE_SIZE：扇区大小减去头部大小（80 字节）

SECTOR_NUMBER：扇区数量

MAX_NUM_WRITES：存储设备以写入次数表示的预期寿命

TOTAL_EFFECTIVE_SIZE：写入的数据集的总有效大小

WR_MIN：每分钟写入该数据集的次数

Advanced mode

特性

与 NVS 等现有存储系统相比，ZMS 引入了许多新特性，并将从初始版本继续演进，加入更多满足新技术需求（例如低延迟和更大的存储空间）的特性。

现有特性

版本 1

  • 支持不需要擦除操作的存储设备（只需一次写操作即可使扇区失效）

  • 支持较大的分区和扇区大小（64 位地址空间）

  • 支持 32 位 ID 和 64 位 ID

  • 小数据值存储在 ATE 本身之中

  • 内置数据 CRC32（包含在 ATE 中）

  • ZMS 版本管理（用于应对未来的演进）

  • 支持较大的 write-block-size（仅用于需要它的平台）

  • 支持多种 ATE 格式，以满足不同应用程序的需求

  • 支持通过 zms_mount_force() 进行强制挂载恢复（挂载失败时自动擦除并重新初始化分区）

  • 支持查找缓存以加速重复的 ID 查找，并可选地按实例配置缓存，以便为每个分区定制缓存大小

  • 支持通过 zms_iter_init() 和 zms_iter_next() 枚举有效条目，无需预先声明 ID 列表

未来特性

  • 增加挂载多个使用不同 ATE 格式的文件系统的能力（目前同一应用程序中的所有文件系统必须使用相同的格式）

  • 对于周期性写入 ID/值对且数据量不超过分区大小一半（总是存在具有相同 ID 的旧条目）的应用场景，增加跳过垃圾回收器的能力。

  • 将 ID 划分为命名空间，并由应用程序按需分配 ID，以处理不同子系统或示例所用 ID 之间的冲突。

  • 增加根据循环计数值获取设备磨损程度的能力

  • 增加一个恢复函数，在出现问题时能够恢复存储分区

  • 增加一个库/应用程序，支持从 NVS 条目迁移到 ZMS 条目

ZMS 与 Zephyr 中的其他存储系统

本节在 Zephyr 存储系统（不是完整的文件系统，而是较简单的非层次化存储系统）的大背景下介绍 ZMS。目前 Zephyr 至少还包含另外两个在范围和功能上大致可比的系统：NVS 和 FCB。应用程序应使用哪一个取决于你的需求和所用的硬件，本节提供的信息可帮助你做出选择。

  • 如果使用的是 RRAM 或 MRAM 这类不需要擦除操作的设备，ZMS 无疑是最适合的存储子系统，因为它的设计避免了在这类设备上用大块写入来模拟擦除操作，而是代之以单次写入调用。

  • 对于 write_block_size 较大和/或需要与传统 Flash 页大小（等于 erase_block_size）不同的扇区大小的设备，ZMS 同样是最佳选择，因为可以定制这些参数并在 ZMS 中加入对这些设备的支持。

  • 对于采用传统 Flash 技术的设备，推荐使用 NVS，因为它的资源占用较小（ATE 和头部 ATE 都更小）。与 ZMS 相比，NVS 擦除 Flash 的速度也很快，并且不需要额外的写操作。对于这类设备，由于 NVS 的 ATE 更小，其读写速度也会比 ZMS 更快。

  • 如果应用程序需要超过 64K 个 ID 用于存储，推荐使用 ZMS，因为它的 ID 字段最多可达 64 位。

  • 如果应用程序以 FIFO（先进先出）模式工作，那么 FCB 是这种用例的最佳存储方案。

更一般地，要在 NVS 和 ZMS 之间做出正确选择，首先应检查所有限制因素，确保应用程序可以使用其中一个或另一个子系统；如果两种方案都可行，则应根据本节所述的设备预期寿命计算结果做出最佳选择：磨损均衡。

提高性能的建议

扇区大小和数量

  • 应合理设置存储分区的总大小，以便使用 ZMS 获得最佳性能。有关 ZMS 中实际可用空闲空间的所有信息都可以在文档中找到，参见 用户数据的可用空间。建议选择的存储分区大小为将要写入存储的键值对大小的两倍。

  • 扇区大小的设置应保证一个扇区能够容纳将要存储的最大数据。增大扇区会减慢垃圾回收操作，但会降低其发生频率。相反，减小扇区会加快垃圾回收操作，但也会使其发生得更频繁。

  • 对于 设置 等子系统，所有路径-值对都会拆分为两个 ZMS 条目（ATE）。计算所需存储空间时，应把这两个条目所需的头部考虑在内。

  • 使用 小数据值 可以提高性能，因为这些数据写在条目之内。例如，对于 设置 子系统，选择长度小于或等于 8 字节的路径名可以加快读写。

缓存大小

  • 直接使用 ZMS API 时，建议缓存大小至少等于将要写入存储的不同条目的数量。

  • 每增加一个缓存条目，RAM 使用量就会增加 8 字节。应谨慎选择缓存大小。

  • 如果通过 设置 使用 ZMS，必须考虑到每个设置条目会被拆分为两个 ZMS 条目。建议缓存大小至少为设置条目数量的两倍。

手动按实例配置缓存

启用 CONFIG_ZMS_LOOKUP_CACHE_MANUAL 时，每个 zms_fs 实例都可以提供自己的查找缓存缓冲区，而不使用全局的 CONFIG_ZMS_LOOKUP_CACHE_SIZE 设置。

在 zms_mount() 之前调用 zms_set_lookup_cache()，为该实例分配缓存缓冲区。如果未分配缓冲区，该 zms_fs 实例的查找缓存将保持禁用。

static struct zms_fs zms_a;
static struct zms_fs zms_b;
static uint64_t zms_a_cache[512];
static uint64_t zms_b_cache[32];

zms_set_lookup_cache(&zms_a, zms_a_cache, ARRAY_SIZE(zms_a_cache));
zms_set_lookup_cache(&zms_b, zms_b_cache, ARRAY_SIZE(zms_b_cache));

ID 大小

  • 对大多数应用程序来说，64 位 ID 空间预计都会超出实际需要。除非确有特殊需要，否则建议坚持使用 32 位 ID。即使在 64 位系统上，64 位 ID 预计也会对代码大小和性能产生轻微影响，因为 ID 在存储中的字节位置没有按 8 字节边界对齐。
