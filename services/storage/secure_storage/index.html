安全存储

安全存储子系统提供了 Platform Security Architecture (PSA) Secure Storage API 中所定义函数的实现。
可以在尚未提供该 API 实现的 开发板目标 上启用它。

概述

安全存储子系统使 PSA Secure Storage API 可在所有支持非易失性存储器的开发板目标上使用。因此，它为那些尚无该 API 实现的开发板目标提供了实现，从而确保该 API 的功能可用。例如，启用了 Trusted Firmware-M (TF-M) 的开发板目标（以 /ns 结尾）无法启用该子系统，因为 TF-M 已经提供了该 API 的实现。

除了提供 API 的功能支持之外，根据设备特定的安全特性和配置，该子系统还可能对通过 PSA Secure Storage API 存储的静态数据（data at rest）提供保护。
但请记住，在可能的情况下最好使用 TF-M 这样的安全处理环境，因为它具备隔离保证，能够提供更高的安全性。

限制

安全存储子系统对 PSA Secure Storage API 的实现：

  • 并不追求完全符合规范。

    其首要目标是在所有开发板目标上提供该 API 的功能支持。
    下文列出了该实现偏离规范的几个重要方面。

  • 不保证其存储的数据在所有情况下都能在静态时保持安全。

    这取决于设备特定的安全特性和配置。

  • 截至撰写本文时，尚未提供受保护存储（PS）API 的实现。

    PS API 会直接调用内部可信存储（ITS）API（除非提供了 PS API 的 自定义实现）。

下面列出了该实现有意偏离规范的一些方面及其原因。此列表并不详尽。

  • UID 类型默认只有 30 位。（与 2.5 UIDs 不符。）

    这项优化是为了更方便地将 UID 直接用作存储条目 ID（例如，在启用 CONFIG_SECURE_STORAGE_ITS_STORE_IMPLEMENTATION_ZMS 时用于 ZMS）。
    Zephyr 为该 API 的不同使用者定义了各自的数值范围，从而保证不会发生冲突。更多信息请参阅 include/zephyr/psa 中的头文件。
    如果需要完整的 64 位 UID 范围，可以通过 CONFIG_SECURE_STORAGE_64_BIT_UID 启用。但要注意，即使启用了该选项，ZMS 实现仍会为调用者 ID 保留第 30 位和第 31 位。

  • ITS 中存储的数据默认经过加密和认证。（与 3.2. Internal Trusted Storage requirements 中的 1. 不符。）

    规范认为 ITS 底层的存储 implicitly confidential and protected from replay（隐式保密且可防止重放）（2.4. The Internal Trusted Storage API），因为 most embedded microprocessors (MCU) have on-chip flash storage that can be made inaccessible except to software running on the MCU（大多数嵌入式微处理器（MCU）都具有片上 Flash 存储，可以将其设置为仅允许 MCU 上运行的软件访问）（2.2. Technical Background）。
    并非所有 MCU 都是如此。因此，该实现为存储的数据提供了额外的保护。

    不过，这并不能保证所存储的数据在所有情况下都能在静态时保持安全，因为这取决于设备特定的安全特性和配置。它需要一个随机熵源，尤其需要一个安全的加密密钥提供者（CONFIG_SECURE_STORAGE_ITS_TRANSFORM_AEAD_KEY_PROVIDER）。

    此外，ITS 中存储的数据无法防御重放攻击，因为这需要受硬件保护的存储。

  • 通过 PSA Secure Storage API 存储的数据无法防止软件或调试手段直接读写。（与 3.2. Internal Trusted Storage requirements 中的 2. 和 10. 不符。）

    数据仅在静态时受到保护。要在运行时也提供保护，需要特定的硬件机制支持。

  • PSA_STORAGE_FLAG_WRITE_ONCE 标志只能防止条目通过 API 被修改，而不能防止存储介质本身被修改。

    要维持该标志，首先需要知道某个条目曾经被创建过，而这一状态必须在存储介质被重写后依然保留。与重放保护一样，这需要受硬件保护的存储。
    因此，能够写入存储介质的攻击者可以覆盖或删除只写一次（write-once）的条目：要么篡改该条目，之后子系统会将其视为已损坏并允许替换；要么直接擦除它，之后它看起来就像从未存在过。对条目进行加密和认证都无法防止这两种情况。

  • psa_its_get*() 函数可能返回 PSA_ERROR_INVALID_SIGNATURE 和 PSA_ERROR_DATA_CORRUPT。

    规范没有为 ITS API 定义这些错误码，因为它假定其底层存储受硬件保护，从中读回的数据总是完好的。由于这里并非如此，该实现会传递这些错误码，以便调用者区分被篡改的条目和内部故障。

配置

要配置 Zephyr 提供的 PSA Secure Storage API 实现，请查看可用的 Kconfig options。它们定义在 subsys/secure_storage/ 下的各个 Kconfig 文件中。

定制

如果现有实现提供的功能不能满足需要，也可以在不同层次上用自定义实现替换 Zephyr 的实现。

整个 API

如果你已经有完整的 ITS 或 PS API 实现并希望使用它，可以启用以下 Kconfig 选项并实现相关函数：

  • CONFIG_SECURE_STORAGE_ITS_IMPLEMENTATION_CUSTOM，用于 ITS API。

  • CONFIG_SECURE_STORAGE_PS_IMPLEMENTATION_CUSTOM，用于 PS API。

ITS API

Zephyr 的 ITS API 实现（CONFIG_SECURE_STORAGE_ITS_IMPLEMENTATION_ZEPHYR）使用 ITS 转换（transform）模块和存储（store）模块，这两个模块可以分别配置和定制。请查看 ITS transform and store Kconfig options，了解不同的配置方式。

特别建议使用或实现一个安全的 encryption key provider。
