使用 ARM Coresight STM 进行多域日志记录

Arm CoreSight SoC-400 是一套全面的组件库，用于在系统中构建调试和跟踪功能。STM（System Trace Macrocell，系统跟踪宏单元）是集成在 CoreSight 系统中的一种跟踪源，主要用于对嵌入软件中的插桩进行高带宽跟踪。这种插桩由对 STMESP（STM Extended Stimulus Port，STM 扩展激励端口）外设寄存器的内存映射写操作组成。多个内核可以共享并直接访问 STM，彼此无需感知对方。每个内核有 65536 个激励端口（寄存器组完全相同），可以独立访问，因此不同上下文需要记录数据时无需加锁。

STM 扩展激励端口（STMESP）

本地域（每个内核）可以访问自己的一组 STMESP 外设。每组外设都有用于写入数据（可带或不带时间戳、可带或不带标记）和写入标志的寄存器。每次写 STMESP 寄存器，用户数据都会被编码为 MIPI System Trace Protocol v2（STPv2）格式。硬件在必要时向数据流中加入 Major 和 Channel 操作码，从而对来自不同 STMESP 寄存器组和不同内核的数据进行复用。时间戳（来自所有内核共用的时间源）和同步操作码由 STM 自动加入。

STM 生成的数据流可以送往不同的接收端（sink）。例如，可以直接发送到 TPIU（Trace Port Interface Unit，跟踪端口接口单元），或保存到称为 ETR（Embedded Trace Router，嵌入式跟踪路由器）的 RAM 环形缓冲区中。TPIU 是一个 5 引脚接口（4 个数据引脚和时钟），需要外部工具（例如 J-Trace PRO）来捕获数据。使用 ETR 时，由系统中的某一个内核负责处理这些数据，例如通过 UART 将其转储到主机。

ARM Coresight 嵌入式跟踪路由器（ETR）

ETR 是一个保存跟踪数据的 RAM 环形缓冲区。由于其中可能包含来自不同源的数据，需要使用额外的封装协议对这些数据进行复用，所用的是 Coresight Trace Formatter。数据被编码为 16 字节的帧，每帧最多容纳 15 字节数据。RAM 环形缓冲区的大小限制为 4k，因此存在数据溢出的风险。发生溢出时数据会丢失，但由于 STPv2 数据流中有同步操作码，可以恢复同步。

ETR 中的数据在设备上处理。数据可以原样转发到主机（例如通过 UART），由主机工具解码；也可以在片上解码，以人类可读的格式输出。

Nordic Semiconductor NRF54H20 的实现没有使用 ETR 外设来获取缓冲区占用情况，而是使用自己的封装：Trace Buffer Monitor（TBM，跟踪缓冲区监视器）。

STMESP 日志前端

这里实现了 自定义前端 API。该自定义前端假定所有必需的操作都在日志宏调用的上下文中执行，并假定由前端提供时间戳。前端利用了存在多组 STMESP 寄存器这一点，使用多组寄存器来避免锁定上下文。通过原子递增的通道计数器选取一组唯一的 STMESP，整条消息都写入该 STMESP。前端只使用有限的一组寄存器池，把大多数通道留作其他用途。

早期日志

在 STM 或 ETR/TPIU 设置好之前无法使用 STMESP。为了支持早期日志，在基础设施就绪之前，数据会写入一个专用的 RAM 缓冲区。当收到 STM 基础设施就绪的通知（log_frontend_stmesp_etr_ready()）后，RAM 缓冲区的内容会写入 STMESP。早期日志仅适用于拥有并配置 Coresight 基础设施的内核（例如在 NRF54H20 上是 Secure 内核）。

跟踪点

某些情况下日志记录仍然太慢（尽管它已经非常快）。针对这类情况，新增了专门的 trace point API。它极快，因为只需对一个 STMESP 寄存器进行一次写操作。该 API 有 2 个函数：

  • log_frontend_stmesp_tp() ——接受单个参数：索引。索引范围为 0 到 65280。

  • log_frontend_stmesp_tp_d32() ——接受两个参数：索引和用户数据。索引范围为 0 到 65280。用户数据是一个 32 位字。

在 NRF54H20 上记录一个跟踪点只需不到 100 ns，大约比最快的日志消息快 7 倍。

使用 STM 记录日志

STM 日志有 2 种工作模式：

  • 基于字典——一种辅助模式，使用基于字典的日志。在这种模式下，日志字符串可以从二进制文件中移除，因为只有解码时才需要它们，而解码由主机工具完成。这种模式占用内存更少，速度更快（快 2-3 倍）。写入的数据更少，因此 ETR 缓冲区发生数据溢出的可能性也更小。

  • 独立——数据在片上解码并打印人类可读的字符串。这种模式需要更多的设备资源和处理能力。

下图展示了使用 ARM Coresight STM 的多域日志记录。

每个内核（本地域）都使用日志前端，将日志数据写入 STMESP 寄存器。

如果使用 TPIU 作为输出，则不再需要其他软件组件。STPv2 数据流由 STM 组合并通过 TPIU 发送。

如果使用 ETR RAM 缓冲区，则由拥有缓冲区的内核（proxy）负责处理这些数据。如果使用基于字典的日志，proxy 只需通过 UART 原样发送数据。如果使用独立日志，proxy 会使用 ARM Coresight 跟踪解格式化器 和 MIPI STP 解码器 对数据进行解码并对消息解复用。消息由日志 消息格式化 格式化为人类可读的字符串。

基于字典的日志

辅助式多核日志使用基于字典的日志向 STM 发送不含冗余字符串的消息，它基于 Zephyr 日志 API 提供的 基于字典的日志 功能。日志消息中不包含格式字符串，而是记录字符串所在的地址（消息 ID），从而减小日志子系统的体积。如果数据写入 ETR 缓冲区，proxy 内核负责转储这些数据。装有解码工具的主机 PC 使用构建过程中生成的 JSON 数据库，把这些地址翻译回人类可读的文本。

使用日志时，这种方法有以下优点：

  • 它减小了二进制文件的体积，因为日志消息中使用的字符串并不存储在二进制文件中。日志基础设施也非常精简：在本地域上只有前端，甚至不需要字符串格式化函数。

  • 它减少了需要发送到应用核并由应用核处理的数据量，因为字符串格式化工作被转移到了主机端。

  • 日志记录速度快。在 NRF54H20 上记录一条简单消息（最多 2 个参数）只需不到 1 us。

proxy 内核使用 Nordic 专有的外设（TBM）获取 ETR 缓冲区的占用情况，并通过 UART 发送数据。Nordic 专用的 ETR 缓冲区驱动位于 drivers/debug/debug_nrf_etr.c。

配置

对于 Nordic SoC，应使用专用的代码片段（snippet）（Nordic 基于字典的 STM 日志代码片段（nordic-log-stm-dict））来启用日志。每个内核都应使用该代码片段构建。只要有任何内核要使用它，应用核也必须启用它，因为应用核充当 proxy（处理 ETR 缓冲区）。所有内核必须使用相同的日志配置。

读取日志

要读取基于字典的 STM 日志输出，请执行以下操作：

  1. 设置日志捕获。

    使用 nrfutil trace stm 命令开始从设备捕获日志，并为每个域 ID 指定数据库配置，以及串口、波特率和输出文件名:

    nrfutil trace stm --database-config 34:build/zephyr/log_dictionary.json,35:build_rad/zephyr/log_dictionary.json --input-serialport /dev/ttyACM1 --baudrate 115200 --output-ascii out.txt

  2. 捕获并解码日志。

    nrfutil 会从指定的 UART 端口捕获日志数据，并使用提供的字典数据库将日志解码为人类可读的格式。解码后的日志保存在指定的输出文件中（上例中为 out.txt 文件）。

  3. 打开输出文件，查看解码后的日志消息。

    该文件包含时间戳以及人类可读格式的日志消息。

如果日志捕获找不到同步点，请重新运行捕获过程。

备注

重新运行该过程时，可能会出现解码伪影或时间戳不正确的情况。

其他注意事项

使用 STM 日志时，请注意以下几点：

  • 使用经过优化的日志宏（最多带 2 个字长的数值参数，例如 LOG_INF("%d %c", (int)x, (char)y)），以减小日志的体积并提高日志速度。

  • 对于内存受限的应用程序（例如运行在 PPR 内核上时），请在项目配置中将 CONFIG_PRINTK 和 CONFIG_BOOT_BANNER 这两个 Kconfig 选项都设为 n，以禁用 printk() 函数。

  • 使用多个域（例如无线电核和应用核）时，请确保每个数据库都以正确的域 ID 作为前缀。

  • 由于存储 STM 日志的 RAM 缓冲区大小有限，部分日志消息可能会被丢弃。
