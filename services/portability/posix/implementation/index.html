实现细节

在许多方面，Zephyr 像任何 POSIX 操作系统一样提供支持：API 绑定以 C 语言提供，配置后，POSIX 头文件位于标准包含路径中。

与其他通用 POSIX 操作系统不同

  • Zephyr 不是“POSIX 操作系统”。Zephyr 内核并不是围绕 POSIX 标准设计的，POSIX 支持是一项可选功能

  • Zephyr 应用程序不单独链接，也不作为子进程执行

  • Zephyr、库和应用程序代码一起编译和链接，在单一（可能是虚拟的）地址空间中运行，类似于单进程应用程序

  • Zephyr 不提供 POSIX shell、编译器和实用工具，也不能自托管（self-hosting）。

备注

与 Linux 内核或 FreeBSD 不同，Zephyr 并不为每种支持的架构维护一张静态的系统调用号表，而是在构建时动态生成系统调用。更多信息请参阅 系统调用。

设计

作为一个库，Zephyr 的 POSIX API 实现力求成为应用程序、中间件与 Zephyr 内核之间的一层薄抽象层。

一些总体设计考虑：

  • POSIX 接口及其实现应属于 Zephyr 的 POSIX 库，而不应放在其他地方，除非 POSIX API 实现和其他某项功能都需要它。实现应保留在 POSIX 实现中的一个例子是 getopt()。实现应属于独立库的例子有多线程和网络。

  • 当 POSIX API 和另一个 Zephyr 子系统都依赖某项功能时，该功能应实现为一个独立的 Zephyr 库，供 POSIX API 和另一个库或子系统共同使用。这样可以降低代码中出现依赖循环的可能性。在可行的情况下，这条规则也应扩展到宏。在下面的例子中，libposix 依赖 libzfoo 来实现 Zephyr 中的某项功能“foo”。如果 libzfoo 也依赖 libposix，就会形成依赖循环。可以通过一个共同依赖 libcommon 来消除该循环。

  • POSIX API 调用应以普通可调用的 C 函数形式提供；如果实现中需要使用 Zephyr 系统调用，该系统调用的声明和实现应隐藏在 POSIX API 之后。
