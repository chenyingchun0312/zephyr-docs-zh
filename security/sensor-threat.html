传感器设备威胁模型

本文档描述了一种物联网传感器设备的威胁模型。明确阐述威胁模型有助于指导开发工作，也可以用来帮助确定这些工作的优先级。

该设备包含某种类型的传感器（例如温度传感器，或管道中的压力传感器），传感器将数据发送到运行微控制器的 SoC。该微控制器连接到云服务，并将传感器数据转发给该服务。云服务也可以向设备发送配置数据以及软件更新镜像。总体框图如图 1 所示：

在该传感器设备中，传感器通过 SPI 总线与 SoC 相连，SoC 具有一个网络接口，用于与云服务通信。这些接口的具体细节可能以意想不到的方式影响威胁模型，因此需要考虑各种变体（例如，使用通过某种总线连接的独立网络接口 SoC）。

该模型还重点关注通过 MQTT-over-TLS 协议进行的通信，因为该协议似乎应用广泛 [1]。

资产

威胁模型需要考虑的一个方面是设备运行所涉及的资产。以下列表列举了该模型中包含的资产：

  1. 引导加载程序。这是存放在设备内 Flash 中的一个小型代码/数据镜像，是最先运行的代码。为了建立信任根，该镜像必须是不可修改的。该模型假定 SoC 提供了一种保护 Flash 某个区域、使其以后不能再被写入的机制，并且在生产早期将该镜像编程写入设备后就会启用这种保护 [th-imboot]。

  2. 应用程序固件镜像。该资产由微控制器运行的其余固件组成。之所以要区分出来，是因为随着信息安全漏洞被发现，这部分镜像需要定期更新。对该镜像更新的要求如下：

    1. 该镜像只能被替换为经过授权的镜像 [th-authrepl]。

    2. 当有经过授权的替换镜像可用时，应及时进行更新 [th-timely-update]。

    3. 镜像更新应是原子的，即在运行镜像时，Flash 中要么完整地包含更新镜像，要么完整地包含旧镜像 [th-atomic-update]。

  3. 根证书列表。为了认证云服务（服务器），物联网设备必须拥有一份允许为服务器证书签名的根证书列表。对于基于云提供商的服务，该列表通常由服务提供商提供。由于根证书可能过期，也可能被吊销，因此该列表需要定期更新 [th-root-certs]、[th-root-check]。

  4. 客户端机密。为了向服务认证客户端，客户端必须拥有某种机密。这通常是一个私钥，一般是 RSA 密钥或 EC 私钥。与服务器建立通信时，设备会将该机密用于 TLS 建立过程，或用于对通信中使用的消息进行签名。

    该机密通常由服务提供商或在其他地方运行的软件生成，并且必须被安全地安装到设备上。策略可能要求定期更换该机密，这就需要一种更新客户端机密的方法。通常，服务会允许同时存在两到三个有效密钥，以便在仍使用旧密钥的同时进行更新。

    这些机密必须受到保护以防被读取，并且只应让尽可能少的代码访问它们。[th-secret-storage]

  5. 当前日期/时间。TLS 证书验证需要知道当前的日期和时间，以确定当前时间是否在证书的有效期内。此外，基于令牌的客户端认证通常要求客户端对一条包含令牌有效时间窗口的消息进行签名。证书验证要求设备的日期和时间误差在一天左右以内。令牌生成通常要求时间误差在 5-10 分钟以内。

    可以通过查询外部时间服务器来近似获得安全的时间。安全 NTP 可能超出了物联网设备的能力范围。时间不正确的主要风险是拒绝服务（设备拒绝有效的证书）以及生成时间无效的令牌。攻击者有可能诱使设备生成在未来才有效的令牌，但攻击者还必须伪造服务器的证书才能截获这些令牌。[th-time]

  6. 传感器数据。从传感器接收并交付给服务的数据，在交付时不得被修改或篡改。

  7. 设备配置。设备需要保存各种配置数据，例如要连接的服务的主机名、时间服务器的地址、向服务发送传感器数据的频率和参数，以及其他数据。随着配置的变化，这些配置数据需要定期更新。只应允许经过授权的各方进行更新。[th-conf]

  8. 日志。为了协助分析信息安全问题，设备应记录与信息安全相关的事件的信息。物联网设备的存储空间通常有限，因此需要仔细选择要记录的日志。也可以将这些日志事件发送到云服务，存储在资源更充足的环境中。应记录的事件类型包括：

    1. 固件镜像更新。系统应记录新镜像的下载，以及镜像何时更新成功。

    2. 客户端机密更改。应记录客户端机密的更改和新增。

    3. 设备配置的更改。

    [th-logs]

通信

除了资产之外，威胁模型还考虑系统各实体之间传递数据或资产的位置。

  1. Flash 内容。Flash 器件包含若干区域。Flash 的内容可以由 SoC 的 CPU 以编程方式修改。

    1. 引导加载程序。如“资产”一节所述，引导加载程序是 Flash 器件中的一个小区域，包含最先运行的代码。该区域应在设备生命周期的早期写入，然后将 Flash 器件配置为永久禁止修改该区域。该配置还应防止通过外部接口（例如 JTAG 或 SWD 调试器）进行修改。

      引导加载程序负责验证应用程序镜像的签名，并在需要更新时用更新镜像更新应用程序镜像。

      引导加载程序在安装更新镜像之前应验证其签名。

      引导加载程序应只接受版本号比当前镜像更新的更新镜像。

    2. 应用程序镜像。应用程序镜像包含设备正常运行期间执行的代码。在运行该镜像之前，引导加载程序应验证镜像的数字签名，以避免运行被篡改过的镜像。Flash/系统应配置为：引导加载程序运行完成后，CPU 将无法写入应用程序镜像。

    3. 更新镜像。这是 Flash 中用于存放新版本应用程序镜像的区域。该镜像将在正常运行期间由应用程序下载并存储。完成后，应用程序可以触发重启，再由引导加载程序安装新镜像。

    4. 机密存储区。Flash 中的一个区域将用于存储客户端机密。该区域由应用程序镜像中的一部分代码读写。应对应用程序进行配置，使不需要访问该区域的代码既不能读取也不能写入该区域，同时要考虑到在大部分应用程序代码中可能发现的漏洞利用。机密内容一旦泄露，攻击者就能冒充该设备。

      初始机密应在一个与设备正常运行相分离的预配（provisioning）过程中写入设备。之后的更新可以根据通过与服务之间的安全信道接收到的指令来进行。

    5. 配置存储区。应有一个用于存储其他配置信息的区域。在资源受限的设备上，允许将其与机密存储区存放在同一区域中，但这会增加能访问机密存储区的代码，因此也就增加了必须仔细审查的代码。

    6. 日志存储区。设备可以有一个用于写入日志事件的 Flash 区域。

  2. 传感器/执行器接口。在本设计中，传感器或执行器通过某种总线（例如 SPI）与 SoC 通信。硬件设计应使攻击者难以截获该总线上的通信。所需的技术取决于传感器数据的敏感性和用途，可以从将传感器安装在与 MCU 相同的 PCB 上，到用环氧树脂灌封整个设备。

  3. 与云服务的通信。设备与云服务之间的通信将通过公共互联网进行。因此，应假定攻击者可以任意截获该信道，例如返回伪造的 DNS 结果，或尝试对与云服务的通信发起中间人攻击。

    设备与云服务之间的所有通信都应使用 TLS [th-all-tls]。TLS 协议栈应配置为只使用普遍认为安全的密码套件 [2]，并具备前向保密性。通信应通过以下方式加以保护：

    1. 密码套件选择。设备应只允许使用公认安全的密码套件进行通信 [th-tls-ciphers]。

    2. 服务器证书验证。应验证服务器出示的证书 [th-root-check]。

      1. 命名。证书应注明云服务服务器所提供的主机和服务。RFC 6125 描述了这方面的最佳实践。只要服务能够使用符合要求的证书，设备可以对证书提出比该 RFC 所述更严格的要求。

      2. 路径验证。设备应验证证书链具有一条从设备内所含的根证书到服务所出示证书的有效签名路径。RFC 4158 对此做了总体描述。只要所用的服务器证书符合限制，设备可以要求使用更受限的路径。

      3. 有效期。应根据设备所能获得的最准确的当前时间，检查所有出示证书的有效期。

    3. 客户端认证。客户端应使用只有该特定设备知道的机密向服务认证自身。有几种可选方式，所用的技术通常由所使用的特定服务提供商规定 [th-tls-client-auth]。

      1. TLS 客户端证书。TLS 协议允许客户端出示证书，并证明自己知道该证书所对应的机密。这些证书通常保存在服务提供商处。这些证书可以是自签名的，也可以由 CA 签名。由于服务提供商维护着一份有效证书列表（将证书映射到设备身份），由 CA 为这些证书签名并不会增加额外的信息安全，但可能有助于管理这些证书。

      2. 基于令牌的认证。客户端也可以使用 MQTT CONNECT 报文的 password 字段来认证自身。但是，机密本身不得在该报文中传输，而应使用基于令牌的协议，例如 RFC 7519 的 JSON Web Token（JWT）。这些令牌的有效期通常很短（例如 1 小时），以防止被截获后被重复使用。在设备验证服务器身份之前，不得发送令牌。

    4. 随机数/熵源。加密通信需要生成安全的伪随机数。设备应使用现代的、公认的密码学随机位生成器来生成这些随机数。设备应使用在 SoC 内以硬件实现的非确定性随机位生成器（真 RBG），或使用由 SoC 内熵源提供种子的确定性随机位生成器（伪 RBG）。有关经过批准的 RBG 的信息，请参见 NIST SP 800-90A；有关测试设备熵源的信息，请参见 NIST SP 800-90B [th-entropy]。

  4. 与时间服务的通信。理想情况下，设备应包含维护安全时间的硬件。但是，目前使用的大多数 SoC 都不支持这一点，因此需要查询外部时间服务。RFC 4330 及其引用的 RFC 描述了简单网络时间协议（SNTP），可用于从网络时间服务器查询当前时间。

  5. 设备生命周期。物联网设备的生命周期从生产一直延续到设备的销毁和处置。该生命周期中影响信息安全的环节包括初始预配、正常运行、重新预配和销毁。

    1. 初始预配。在初始预配阶段，需要编程写入引导加载程序、初始应用程序镜像、设备机密和初始配置数据 [th-initial-provision]。此外，还应启用引导加载程序的 Flash 保护。在这些信息中，只有设备机密需要每台设备各不相同。该机密应被安全地保管，并在编程写入设备后，在设备以外的所有位置将其销毁 [th-initial-secret]。

    2. 正常运行。正常运行包括本文档其余部分所描述的行为。

    3. 重新预配。有时需要对设备重新预配，例如将其用于其他应用。一种方法是保留相同的设备机密，替换配置数据以及与该设备关联的云服务数据。也可以编程写入新的设备机密，但这样做时必须以安全的方式进行，并在新机密编程写入设备后在外部将其销毁 [th-reprovision]。

    4. 销毁。为了防止设备机密被用来冒充设备，在设备退役时，应使该设备的机密失效 [th-destruction]。可行的方法包括：

      1. 从硬件上销毁设备。

      2. 安全地擦除包含机密的 Flash 区域 [3]。

      3. 从服务中移除设备身份和证书。

其他注意事项

除上述内容外，联网设备通常还需要一种配置方法，使其能够连接到所处的网络环境。实现方法有很多种，重要的是这些配置方法不能绕过上述信息安全要求。

威胁

[th-imboot]

必须使用不可修改的引导加载程序启动。

[th-authrepl]

应用程序镜像只能被替换为经过授权的镜像。

[th-timely-update]

应用程序更新应及时进行。

[th-atomic-update]

应用程序更新应是原子的。

[th-root-certs]

TLS 必须有一份受信任的根证书列表。

[th-root-check] (1,2)

TLS 必须验证来自服务器的根证书是有效的。

[th-secret-storage]

必须有一种安全存储客户端机密的机制。只应让尽可能少的代码访问这些机密。

[th-time]

系统必须对当前日期/时间有较为准确的认知。

[th-conf]

系统必须接收并保存配置数据。

[th-logs]

系统必须记录与信息安全相关的事件，并将其存储在本地或发送到服务。

[th-all-tls]

与云服务的所有通信都应使用 TLS。

[th-tls-ciphers]

TLS 应配置为只允许公认的密码套件（并具备前向保密性）。

[th-tls-client-auth]

设备应使用所述方法之一向云提供商认证自身。

[th-entropy]

TLS 层应使用现代的、公认的密码学随机位生成器，并由 SoC 内的熵源提供种子。

[th-initial-provision]

设备应在部署前载入每台设备各自独有的机密。

[th-initial-secret]

初始机密应被安全地保管，并在设备完成预配后立即在所有外部位置将其销毁。

[th-reprovision]

重新预配设备应以安全的方式进行。

[th-destruction]

设备退役时，应使设备机密失效。

注释

[1]

参见 https://www.slideshare.net/kartben/iot-developer-survey-2018。截至撰写本文时，三大云物联网服务提供商 AWS IoT、Google Cloud IoT 和 Microsoft Azure IoT 都提供 MQTT over TLS。一些反馈表明，有人在各种网络上遇到了 UDP 协议和路由方面的困难。

[2]

随着新的漏洞利用被发现，被视为安全的标准可能会改变。https://www.ssllabs.com/ 等组织提供了关于目前应如何配置 TLS 才能确保安全的信息。

[3]

请注意，仅仅擦除该 Flash 区域可能是不够的。
