安全编码

传统上，基于微控制器的系统并不太重视信息安全。人们通常认为这些系统是孤立的，与外界隔绝，而且仅仅因为难以接触到它们，所以不太容易受到攻击。物联网改变了这一点。如今，运行在小型微控制器上的代码往往能够访问互联网，或者至少能够访问其他设备（这些设备本身也可能存在漏洞）。由于这类设备的部署数量通常很大，不受控制的访问可能造成毁灭性的后果 [1]。

本文档描述了在 Zephyr 项目中确保信息安全得到落实的要求和流程。所有提交的代码都应遵守这些原则。

本文档的大部分内容来自 [CIIBPB]。

简介与范围

本文档从信息安全的角度介绍 Zephyr Project 的指南。其中的许多理念取自其他开源项目。

我们首先概述与 Zephyr 相关的安全设计。接下来是 Secure development knowledge 一节，给出参与本项目的开发者需要具备的基本要求。该节提供了对其他信息安全文档的引用，而如何编写安全软件的完整细节超出了本文档的范围。该节还描述了至少一名主要开发者应具备的漏洞知识。这些知识是后文所述审查流程所必需的。

随后描述了将更改纳入 Zephyr 代码库所使用的审查流程，接着说明项目如何处理信息安全敏感问题。

最后，本文档说明了如何修改本文档本身。

安全编码

要将 Zephyr 这样的开放软件系统设计得安全，就需要遵守一套明确的设计标准。[SALT75] 定义了以下被广泛接受的保护机制原则，以帮助防止违反信息安全的行为并限制其影响：

  • 开放设计（Open design）这一设计准则体现了这样一条格言：在任何被广泛使用的系统上，保护机制都无法保密。因此，不应依赖保密的、定制的信息安全措施，而应使用公认的密码算法和成熟的密码库。

  • 机制经济性（Economy of mechanism）规定，系统的底层设计应尽可能简单、精小。在 Zephyr 项目中，这可以通过模块化代码 [PAUL09] 和抽象的 API 等方式来实现。

  • 完全仲裁（Complete mediation）要求对每个对象和进程的每次访问都必须先经过认证。应尽可能避免使用存储访问条件的机制。

  • 失效安全默认值（Fail-safe defaults）规定，访问默认是受限的，只有在系统保护方案所定义的特定条件下（例如认证成功之后）才被允许。此外，服务的默认设置应以提供最高信息安全的方式来选择。这对应于“默认安全”（Secure by Default）范式 [MS12]。

  • 权限分离（Separation of privilege）原则是指，必须满足两个或更多条件才能授予访问权限。在 Zephyr 项目中，这可以包括拆分密钥 [PAUL09]。

  • 最小权限（Least privilege）描述了这样一种访问模型：每个用户、程序和线程都只应拥有执行其任务所需的、系统中尽可能小的权限子集。这种正向信息安全模型旨在最大限度地减小系统的攻击面。

  • 最少公共机制（Least common mechanism）规定，如果并非绝对必要，多个用户或进程共用的机制不应共享。[SALT75] 中给出的例子是：某个函数应实现为由每个用户各自执行的共享库，而不是实现为由所有用户共享的特权（supervisor）过程。

  • 心理可接受性（Psychological acceptability）要求信息安全特性易于开发者使用，以确保这些特性得到使用并被正确应用。

除了这些通用原则之外，以下几点专门针对安全 RTOS 的开发：

  • 互补安全/纵深防御（Complementary Security/Defense in Depth）：不要依赖单一的威胁缓解手段。在互补安全方法中，部分威胁缓解由底层平台完成。如果平台不提供此类机制，或这些机制不可信，则应采用纵深防御 [MS12] 范式。

  • 较少使用的服务默认关闭：为了减少系统暴露于潜在攻击的程度，仅很少使用的特性或服务不应默认启用（[MS12] 中给出的阈值为 80%）。在 Zephyr 项目中，这可以通过配置管理来实现。每项功能和每个模块都应表示为一个配置选项，并且需要显式启用。这样，特定用例不需要的所有特性、协议和驱动都可以被禁用。如果启用了底层选项和 API 但应用程序并未使用，应通知用户。

  • 变更管理：为了保证对系统所做更改的可追溯性，每项更改都应遵循规定的流程，包括变更请求、影响分析、批准、实施和验证阶段。每个阶段都应提供相应的文档。所有提交都应关联到问题跟踪系统中的缺陷报告或变更请求。没有有效关联的提交应被拒绝。

安全开发知识

安全设计者

Zephyr 项目必须至少有一名懂得如何设计安全软件的主要开发者。

这要求理解以下设计原则，其中包括 [SALT75] 中的 8 条原则：

  • 机制经济性（使设计在可行范围内尽可能简单、精小，例如通过大刀阔斧的简化）

  • 失效安全默认值（访问决策应默认拒绝，项目的安装应默认安全）

  • 完全仲裁（每一次可能受限的访问都必须检查权限，并且不可绕过）

  • 开放设计（信息安全机制不应依赖于攻击者不了解其设计，而应依赖于更容易保护和更改的信息，例如密钥和密码）

  • 权限分离（理想情况下，对重要对象的访问应取决于不止一个条件，这样攻破一个保护系统也无法获得完全访问权限。例如，多因素认证（如同时要求密码和硬件令牌）比单因素认证更强）

  • 最小权限（进程应以所需的最小权限运行）

  • 最少公共机制（设计应尽量减少由多个用户共用、并被所有用户依赖的机制，例如临时文件目录）

  • 心理可接受性（人机界面必须设计得易于使用，按照“最小意外”原则进行设计会有所帮助）

  • 有限的攻击面（攻击者可能尝试从中输入或提取数据的各个不同位置的集合）

  • 使用允许列表进行输入验证（输入通常应在被接受之前检查其是否有效；这种验证应使用允许列表（只接受已知的有效值），而不是阻止列表（试图列出已知的无效值））。

漏洞知识

项目中的“主要开发者”是指熟悉项目代码库、能够熟练地修改代码，并被项目中大多数其他参与者认可的任何人。主要开发者通常在过去一年中做出过一定数量的贡献（通过代码、文档或解答问题）。如果开发者发起了该项目（且离开项目未超过三年）、可以选择通过私有漏洞报告渠道（如果有的话）接收信息、可以代表项目接受提交，或者负责发布项目软件的正式版本，通常就会被视为主要开发者。如果只有一名开发者，那么此人就是主要开发者。

至少一名主要开发者 必须 了解在这类软件中会导致漏洞的常见错误类型，并且对每种错误至少掌握一种应对或缓解方法。

示例（取决于软件类型）包括 SQL 注入、操作系统命令注入、经典缓冲区溢出、跨站脚本、缺少认证和缺少授权。常用的列表请参见 CWE/SANS top 25 或 OWASP Top 10。

非营利组织 OpenSecurityTraining2 为 C/C++ 开发者提供了一门免费课程 OST2_1001。该课程讲授如何预防、检测和缓解线性栈/堆缓冲区溢出、非线性越界写入、整数溢出以及其他整数问题。后续课程 OST2_1002 涵盖未初始化数据访问、竞争条件、释放后使用（use-after-free）、类型混淆以及信息泄露漏洞。

Zephyr 信息安全小组委员会

应设立一个“Zephyr 信息安全小组委员会”（Zephyr Security Subcommittee），负责执行本指南、监督审查并改进这些指南。

该团队将依据 Zephyr 项目章程设立。

代码审查

Zephyr 项目应使用一个代码审查系统，所有更改都必须经过该系统。每项更改都应至少由一名不是该更改作者的主要开发者审查。该开发者应（根据其对信息安全的一般理解）判断此更改是否影响系统的信息安全；如果有影响，则应请具备漏洞知识的开发者或安全设计者也审查该代码。上述任何人都有权阻止该更改合并到主线代码中，直到信息安全问题得到解决。

问题与缺陷跟踪

Zephyr 项目应有一个问题跟踪系统（例如 GitHub），用于记录和跟踪在系统中发现的缺陷。

由于信息安全问题通常比较敏感，该问题跟踪系统应有一个用于标识信息安全问题的字段。设置该字段后，该问题应只对 Zephyr 信息安全小组委员会可见。此外，还应有一个字段，允许 Zephyr 信息安全小组委员会添加其他可查看指定问题的用户。

这种禁止公开期（embargo），即受限可见性，应只持续固定的时长，默认值由项目决定。但是，由于信息安全方面的考虑往往来自 Zephyr 项目之外，可能需要延长禁止公开期。所需的时间应在问题中明确注明。

Zephyr 信息安全小组委员会应至少每月审查一次问题列表。审查应着重于跟踪修复情况、确定是否需要通知或邀请外部各方参与，以及确定何时解除问题的禁止公开期。禁止公开期 不应 通过自动化手段解除，但审查团队应避免在解除已解决问题的禁止公开期时出现不必要的延迟。

本文档的修改

对本文档的修改应由 Zephyr 信息安全小组委员会审查，并经协商一致批准。
