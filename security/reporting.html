信息安全漏洞报告

简介

Zephyr 项目中的漏洞最好通过在 Zephyr 仓库的 security advisories page 上创建一个 security advisory 草稿来报告。也可以通过电子邮件将报告发送至 vulnerabilities@zephyrproject.org，提交给项目信息安全事件响应团队。信息安全响应团队会在 1 周内确认并分析这些报告。

所有漏洞都通过 GitHub 上 Zephyr 项目的 security advisories page 进行跟踪和管理，原始提交者将被授予访问权限，以查看自己报告的问题。

漏洞报告指南

信息安全研究和漏洞报告是对 Zephyr 项目有价值的贡献。为了让这一过程对每个人都安全且富有成效，所有报告及相关活动都必须遵守 Zephyr 项目的 Code of Conduct。

以下指南说明了在研究和报告 Zephyr 中的信息安全漏洞时应遵循的要求。

报告要求

为了帮助信息安全响应团队高效地对问题进行分诊和解决，报告应当：

  • 描述受影响的组件、版本、开发板或平台，以及复现该问题所需的配置。

  • 提供清晰的分步复现说明，并尽可能提供一个最小化的概念验证（proof-of-concept）。

  • 说明信息安全影响（例如机密性、完整性或可用性的丧失）以及任何已知的缓解措施。

  • 避免包含破坏性载荷，或在报告被意外泄露时可能对用户或系统造成危害的组件。

报告者应本着善意，在任何公开披露之前给项目留出合理的机会来调查和修复问题，并遵循以下各节所述的禁止公开期（embargo）和披露流程。

信息安全问题管理

此缺陷跟踪系统中的问题会按照下图在若干状态之间转换：

digraph { node [style = rounded]; init [shape = point]; New [shape = box]; Triage [shape = box]; { rank = same; rankdir = LR; Assigned [shape = box]; Rejected [shape = box]; } Review [shape = box]; Accepted [shape = box]; Public [shape = box]; init -> New; New -> Triage; Triage -> Rejected [dir = both]; Triage -> Assigned; Assigned -> Review [dir = both]; Review -> Accepted; Review -> Rejected; Accepted -> Public; }

  • New（新建）：此状态表示由报告者直接录入的新报告。如果问题是由响应团队根据电子邮件录入的，则应直接转为 Triage 状态。

  • Triage（分诊）：此问题正在等待响应团队分诊。响应团队会分析问题，确定负责方，将问题分配给相应的人员，并将问题转为 Assigned 状态。分诊的一部分工作是设置问题的优先级。

  • Assigned（已分配）：问题已分配，正在等待被分配者修复。

  • Review（审查）：一旦有针对该问题的 Zephyr PR，就会在问题的评论中添加该 PR 的链接，并将问题转为 Review 状态。

  • Accepted（已接受）：表示针对该问题的修复已合并到 Zephyr 的相应分支中。

  • Public（已公开）：禁止公开期已结束。问题将被设为公开可见，相关的 CVE 会被更新，文档中的漏洞页面也会更新以包含详细信息。

由于信息安全报告的敏感性，创建的信息安全公告（security advisory）会保持私有。这些问题只对特定各方可见：

  • PSIRT 邮件列表的成员

  • 报告者

  • 经 Zephyr 信息安全小组委员会（Security Subcommittee）提议并批准的其他人员。一般情况下包括：

    • 负责修复的代码所有者。

    • 受此漏洞影响的相关版本的 Zephyr 发布负责人。

Zephyr 信息安全小组委员会应在任何出席人数超过三人的会议上审查已报告的漏洞。审查过程中，委员会应确定新问题是否需要设置禁止公开期。

是否设置禁止公开期的判断依据为：1. 问题的严重程度；2. 问题的可利用性。小组委员会认定不需要禁止公开期的问题，将在常规的 Zephyr 项目缺陷跟踪系统中重新记录。

信息安全敏感漏洞应在最长 90 天的禁止公开期之后公开。其目的是给 Zephyr 项目留出 30 天来修复问题，并给使用 Zephyr 构建产品的外部各方留出 60 天来应用和分发这些修复。

对代码的修复应通过 Zephyr 项目 GitHub 上的 PR 进行。开发者应尽量不透露所修复内容的敏感性质，并且不得提及已为该问题分配的 CVE 编号。开发者只需描述修复了什么即可。

信息安全小组委员会将维护禁止公开期内的 CVE 与这些 PR 之间的对应信息（这些信息保存在 GitHub 信息安全公告中），并定期发布信息安全问题状态报告。

每个被认定为信息安全漏洞的问题都应分配一个 CVE 编号。在制作修复的过程中，可能需要分配更多的 CVE 编号，或撤销已分配的编号。

漏洞通知

每个 Zephyr 版本都应包含一份该版本中已修复 CVE 的报告。由于这些漏洞的敏感性，版本中只应包含已修复 CVE 的列表。禁止公开期结束后，应更新漏洞页面，加入这些漏洞的更多详细信息。漏洞页面应注明报告者的贡献，除非报告者明确要求匿名。

Zephyr 项目应维护一个漏洞警报（vulnerability-alerts）邮件列表。该列表最初由每个项目成员各提供一名联系人。其他各方可以通过填写 Vulnerability Registry 中的表单申请加入此列表。项目总监将对这些申请方进行审核，以确定他们确有正当理由在禁止公开期内了解信息安全漏洞。

信息安全小组委员会会定期向此邮件列表发送信息，说明已知的处于禁止公开期的问题及其在项目内的向后移植状态。这些信息旨在让列表成员判断是否需要将这些更改向后移植到他们的内部代码树中。

问题完成分诊后，将向此列表通报：

  • Zephyr 项目信息安全公告链接（GitHub）。

  • 分配的 CVE 编号。

  • 涉及的子系统。

  • 问题的严重程度。

修复该问题的 PR 被接受（合并）后，除上述内容外，还将向此列表通报：

  • CVE 编号与修复它的 PR 之间的对应关系。

  • Zephyr 项目内的向后移植计划。

信息安全漏洞的向后移植

在 Zephyr 中修复的每个信息安全问题都应向后移植到以下版本：

  • 当前的长期稳定（LTS）版本。

  • 最近的两个版本。

修复的开发者应负责所有必要的向后移植，并将其应用到上面列出的各个发布分支，除非该修复不适用（即漏洞是在该版本发布之后引入的）。关于 漏洞修复 的所有建议同样适用于向后移植的 PR（及相关问题）。此外，建议开发者私下告知相应的发布经理，该向后移植 PR 和问题是在处理一个漏洞。

向后移植情况将在信息安全公告中跟踪。

知情必要原则

由于信息安全漏洞的敏感性，重要的是只与有必要知情的各方共享细节和修复。以下各方需要在禁止公开期结束之前了解信息安全漏洞的详细信息：

  • 维护者只能访问其所负责领域内的全部信息。

  • 当前的发布经理，以及受该漏洞影响的历史版本的发布经理（参见上文的向后移植部分）。

  • 项目信息安全事件响应团队（PSIRT）可以完全访问所有信息。PSIRT 由白金会员的代表以及来自其他成员、从事分诊工作的志愿者组成。

  • 根据需要，可以邀请发布经理和维护者参加额外的信息安全会议来讨论漏洞。
