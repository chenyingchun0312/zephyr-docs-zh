TI AM243x LaunchPad

Board Overview

Name:
lp_am243
Vendor:

Texas Instruments

Status:

Not actively maintained

Architecture:

arm

SoC:

am2434

Browse board sources

概述

AM243x Launchpad 是一款基于 AM2434 SoC 的开发板，因此具有两个运行在 800 MHz 的双核 Cortex-R5F 集群，以及一个运行在 400 MHz 的 Cortex-M4F。该开发板还包含一颗 Flash 芯片、用于选择启动模式的 DIP 开关以及 2 个 RJ45 以太网口。

更多信息请参阅 AM243x Launchpad product page [5] 和 AM2434 SoC website [6]。

硬件

AM64x/AM243x 特性

AM64x / AM243x 是一个 SoC 系列，最多支持 2 个 Cortex-A53 内核（仅 AM64x SoC），典型运行频率 1 GHz；最多 4 个 Cortex-R5F 内核，典型运行频率 800 MHz；以及一个 Cortex-M4F 内核，典型运行频率 400 MHz。在 Zephyr 代码中，这两个系列都称为 AM64x，因为它们的区别仅在于是否有 Cortex-A 内核。如果使用 AM243x 系列 SoC，所有与 Cortex-A 内核相关的内容都不适用。由于共用文档文件，有时仍会记录这些内容。

ARM 内核和外设分为 MAIN 域和 MCU 域，其中只有 ARM Cortex-M4F 内核位于 MCU 域内。默认情况下两个域可以相互交互，但也可以将两个域隔离。

以下列表给出了不完全的概览。目前并非所有外设都在 Zephyr 中得到支持：

  • 最多 2 个 ARM Cortex-A53 内核

  • 最多 2 个双核 Cortex-R5F 集群

  • 1 个 Cortex-M4F

  • 2 MiB 内部 SRAM

  • GPIO

  • ADC

  • UART

  • SPI

  • I2C

  • 多个定时器

  • 多个看门狗

  • CAN-FD

  • 以太网

  • USB

  • PCIe

  • 外部（LP）DDR4 RAM 接口

  • DMSC（集中式电源/资源管理）

  • 加密加速

  • 安全启动

AM243x Launchpad

AM243x Launchpad 使用 AM2434 SoC，因此在 MAIN 域中有 2 个运行在 800 MHz 的双核 Cortex-R4F 集群，在 MCU 域中有一个运行在 400 MHz 的 Cortex-M4F。

开发板上实际包含：

  • 512 Mb（即 64 MB）Infineon NOR Flash

  • 用于更改启动模式的 DIP 开关

  • 用于不同复位方式的按键

  • 多个 LED（部分用于电源指示，部分连接到 GPIO 引脚）

  • 两个带 PHY 的物理以太网口

  • 一个 XDS110 调试探针（JTAG 仿真）

Cortex-R5F0_0 内核默认使用连接到 XDS110 调试探针的 UART 外设，因此无需额外的 UART 转 USB 桥即可使用。为避免冲突，Cortex-M4F 内核默认使用 MCU_UART0 外设，可通过开发板上的 J17 排针访问。

启动固件

AM64x/AM243x 启动流程

由于支持安全启动，AM64x/AM243x SoC 系列有自己的启动流程。SoC 上电后，在 R5F0_0 上执行 ROM 中不可修改的引导加载程序（称为 RBL）。随后应执行基于 Texas Instruments MCU+ SDK 的二级引导加载程序（称为 SBL），由它启动最终的 Zephyr 固件。RBL 可以从多种来源获取镜像，例如外部 Flash 或通过 UART 传输。仅在 AM64x 系列 SoC 上还有另一种方式：使用 TI SDK 中预制的镜像充当 SBL，在 Cortex-A 上启动 Linux，然后使用 remoteproc 将 Zephyr 固件加载到另一个内核上。

在本开发板上，可以通过拨码开关选择从哪个位置获取 SBL 镜像。

UART 启动模式

SW4 [1:7]

11100000
QSPI 启动模式

SW4 [1:7]

01000100

烧录

AM2434 SoC 的启动过程要求启动镜像采用特定格式，并且需要等待 AM2434 内部的 DMSC-L 启动并配置存储器防火墙。由于 Zephyr 尚不支持这一过程，因此需要使用 TI MCU+ SDK 中的某个 SBL 引导加载程序示例。

注意

在所有与 MCU+ SDK 相关的章节中，都需要将 $Z_MCUPSDK_BOARD 替换为 am243x-lp（如果不是在文件中，也可以将其设置为环境变量）！

备注

请注意，虽然该开发板使用的是 Quad SPI（QSPI）而不是 Octal SPI（OSPI），但 TI MCU+ SDK 在该开发板的 OSPI 代码中仍会正确使用 QSPI

MCU+ SDK

设置

以下步骤基于编写本文档时的情况，将来可能会变化。这些步骤面向 Linux，并假定已安装一些基础软件（如 python3 和 openssl）。

要构建这些内容，需要安装 TI MCU+ SDK。为此需要按照 mcupsdk-core GitHub 仓库 [4] 中描述的步骤操作，其中包括使用 west 克隆仓库。建议为此使用另一个 Python venv，因为 MCU+ SDK 有自己的 Python 依赖，可能与 Zephyr 的依赖冲突。如果想少克隆几个仓库，可以将 west init 命令中的 all/dev.yml 替换为 am243x/dev.yml。

还需要按照“Downloading And Installing Dependencies”一节操作，但要将命令中所有的 am263x 替换为 am243x。如果不需要 doxygen 和 CCS，可以向安装脚本传入 --skip_doxygen=true 和 --skip_ccs=true。可能会遇到脚本无法执行的错误。要解决此问题，需要用 chmod +x <path> 将其标记为可执行，然后再次运行 download_components.sh。

注意

另请记下 tools 和 mcu_plus_sdk 的安装路径。下文将 tools 安装路径（来自 download_components.sh）称为 $TI_TOOLS，将 MCU+ SDK 路径（运行 west init 时所在的 mcu_plus_sdk 目录）称为 $MCUPSDK。建议将它们设置为环境变量，但仍需在文件中相应地替换它们。

备注

总结来说，设置 MCU+ SDK 时很可能需要运行以下命令或类似版本：

python3 -m venv .venv
source .venv/bin/activate
pip3 install west
west init -m https://github.com/TexasInstruments/mcupsdk-manifests.git --mr mcupsdk_west --mf am243x/dev.yml
west update
./mcupsdk_setup/am243x/download_components.sh --skip_doxygen=true --skip_ccs=true

脚本成功完成后，切换到 $MCUPSDK，编辑 source/drivers/bootloader/bootloader.c 文件，在 Bootloader_runCpu 中无条件地将 entryPoint 设置为 0。由于 Zephyr 目前构建镜像的方式，需要这样做。

现在可以使用以下命令构建内部库：

make gen-buildfiles DEVICE=am243x PROFILE=release
make libs DEVICE=am243x PROFILE=release

如果遇到编译错误，必须自行修复。为此可能需要修改参数类型、从 makefile 中删除缺失的源文件，或从 TI 在线参考资料中下载缺失的头文件。

Building MCU+ SDK SBLs

示例 SBL 实现位于 examples/drivers/boot/<example>/$Z_MCUPSDK_BOARD/r5fss0-0_nortos 目录中。

可以在 $MCUPSDK 目录下执行 make -C examples/drivers/boot/<example>/$Z_MCUPSDK_BOARD/r5fss0-0_nortos/ti-arm-clang/ DEVICE=am243x PROFILE=release 来构建示例。虽然存在 sbl_prebuilt 目录，但目前其中没有内容，只在 SBL 构建过程中才会填充。

根据使用方式，建议按需构建以下 SBL：

sbl_null

通过 Code Composer Studio IDE 直接加载 Zephyr .elf 的引导加载程序。由于使用方便，建议在开发期间从 Flash 启动它。

sbl_uart

通过 UART 启动 RPRC 格式固件文件的引导加载程序。建议在开发期间从 UART 启动它，这样不必反复在 UART 和 OSPI 之间切换启动模式。

sbl_ospi

从 Flash 加载 RPRC 格式固件的引导加载程序。需要持久化时推荐使用。它在 Flash 偏移 0x80000 处查找 RPRC 镜像。

sbl_uart_uniflash

可在 RBL 之后启动的应用程序，通常通过 UART 加载。它通过 UART 接收数据并写入 Flash。

更多 SBL 参见 TI MCU+ SDK 启动流程文档网站 [1]。

Flashing data into external flash with the MCU+ SDK

要将数据烧录到外部 Flash，需要构建 sbl_uart_uniflash 示例，将构建出的 sbl_uart_uniflash.release.hs_fs.tiimage 文件复制到工作目录，并创建一个配置文件，将其中的 $FLASH_OFFSET 和 $FLASH_FILE 替换为要烧录的 Flash 偏移和文件。

备注

$FLASH_OFFSET 应以十六进制地址给出，例如 0x80000

备注

无需重启即可将多个文件烧录到不同位置，只需复制最后一行并调整文件和 Flash 偏移即可。

--flash-writer=sbl_uart_uniflash.release.hs_fs.tiimage
--operation=flash-phy-tuning-data
--file=$FLASH_FILE --operation=flash --flash-offset=$FLASH_OFFSET

然后运行 python3 uart_uniflash.py -p /dev/ttyUSB0 --cfg=<path-to-the-config-file>。根据所连接的设备，可能需要调整 /dev/ttyUSB0。更多文档参见 TI MCU+ SDK 烧录文档网站 [2]。

Creating a SBL bootable RPRC image from a Zephyr ELF

要将 Zephyr ELF 文件转换为可由 sbl_uart 或 sbl_ospi 等 SBL 启动的 RPRC 文件，需要运行多条命令。下面的代码块给出了这些命令，并假定 zephyr.elf 文件位于当前工作目录。可以根据要运行固件的内核修改 BOOTIMAGE_CORE_ID。

export BOOTIMAGE_CORE_ID_r5fss0-0=4
export BOOTIMAGE_CORE_ID_m4=14
# set CORE_ID as per your target core
export BOOTIMAGE_CORE_ID=${BOOTIMAGE_CORE_ID_desired-core}
$TI_TOOLS/sysconfig_1.21.2/nodejs/node $MCUPSDK/tools/boot/out2rprc/elf2rprc.js ./zephyr.elf
$MCUPSDK/tools/boot/xipGen/xipGen.out -i ./zephyr.rprc -o ./zephyr.rprc_out -x ./zephyr.rprc_out_xip --flash-start-addr 0x60000000
$TI_TOOLS/sysconfig_1.21.2/nodejs/node $MCUPSDK/tools/boot/multicoreImageGen/multicoreImageGen.js --devID 55 --out ./zephyr.appimage ./zephyr.rprc_out@${BOOTIMAGE_CORE_ID}
$TI_TOOLS/sysconfig_1.21.2/nodejs/node $MCUPSDK/tools/boot/multicoreImageGen/multicoreImageGen.js --devID 55 --out ./zephyr.appimage_xip ./zephyr.rprc_out_xip@${BOOTIMAGE_CORE_ID}
python3 $MCUPSDK/source/security/security_common/tools/boot/signing/appimage_x509_cert_gen.py --bin ./zephyr.appimage --authtype 1 --key $MCUPSDK/source/security/security_common/tools/boot/signing/app_degenerateKey.pem --output ./zephyr.appimage.hs_fs

生成的文件为当前工作目录中的 zephyr.appimage.hs_fs。它采用 SBL 可识别的 TI RPRC 格式，格式说明见 TI MCU+ SDK 启动工具文档网站 [3]。

完整启动流程示例

下面汇总列出启动所需的步骤。

要通过调试器启动，首先应按照 Building MCU+ SDK SBLs 中的说明构建 sbl_uart_uniflash 和 sbl_null。然后将开发板置于 UART 启动模式，并按照 Flashing data into external flash with the MCU+ SDK 中的说明将 sbl_null.release.hs_fs.tiimage 文件烧录到地址 0x0。

之后即可切换到 OSPI 启动模式，通过 Code Composer Studio 调试器将 Zephyr ELF 文件直接加载到所需的内核上。

要通过 UART 启动镜像，需要按照 Building MCU+ SDK SBLs 中的说明构建 sbl_uart，并将开发板切换到 UART 启动模式。

然后按照 Creating a SBL bootable RPRC image from a Zephyr ELF 中的说明将 Zephyr ELF 文件转换为 RPRC，并运行 python3 $MCUPSDK/tools/boot/uart_bootloader.py -p /dev/ttyUSB0 --bootloader=sbl_uart.release.hs_fs.tiimage --file=zephyr.appimage.hs_fs

要通过 OSPI 启动镜像，需要按照 Building MCU+ SDK SBLs 中的说明构建 sbl_uart_uniflash 和 sbl_ospi。然后将开发板置于 UART 启动模式，并按照 Flashing data into external flash with the MCU+ SDK 中的说明将 sbl_ospi.release.hs_fs.tiimage 文件烧录到 0x0。此操作只需进行一次。

之后每次构建新的 Zephyr 固件，都需要按照 Creating a SBL bootable RPRC image from a Zephyr ELF 中的说明将 Zephyr ELF 转换为 RPRC 文件，并按照 Flashing data into external flash with the MCU+ SDK 中的说明将其烧录到 0x80000。然后即可切换到 OSPI 启动模式并运行。

调试

OpenOCD

本开发板配备 XDS110 JTAG 调试器。要调试二进制文件，请使用 debug 构建目标：

west build -b lp_am243/<soc>/<core> <my_app>
west debug

提示

要使用此功能，需要足够新的 OpenOCD 版本，因此可能需要自行编译 OpenOCD。具体方法请参阅 building OpenOCD from source [7]。
