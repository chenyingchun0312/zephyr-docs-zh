ESP32-DevKitC

Board Overview

Name:
esp32_devkitc
Vendor:

Espressif Systems

Status:

Not actively maintained

Architecture:

xtensa

SoC:

esp32

Browse board sources

概述

ESP32 是一系列低成本、低功耗的片上系统微控制器，集成 Wi-Fi 和双模 Bluetooth。ESP32 系列采用 Tensilica Xtensa LX6 微处理器，有双核和单核两种型号。ESP32 由总部位于上海的中国公司乐鑫科技（Espressif Systems）设计开发，由台积电（TSMC）采用 40nm 工艺制造。更多信息请参阅 ESP32-DevKitC [6]。

硬件

ESP32 特性

  • 双核 Xtensa 微处理器（LX6），主频 160 或 240MHz

  • 520KB of SRAM

  • 802.11b/g/n/e/i

  • Bluetooth v4.2 BR/EDR 和 BLE

  • 其他外设：

    • 12 位 ADC，最多 18 个通道

    • 2 个 8 位 DAC

    • 10 个触摸传感器

    • 4x SPI

    • 2x I2S

    • 2x I2C

    • 3x UART

    • SD/SDIO/MMC 主机

    • 从机（SDIO/SPI）

    • 以太网 MAC

    • CAN 总线 2.0

    • IR (RX/TX)

    • 电机 PWM

    • LED PWM，最多 16 个通道

    • 霍尔效应传感器

    • 温度传感器

  • 加密硬件加速（RNG、ECC、RSA、SHA-2、AES）

  • 5uA 深度睡眠电流

非对称多处理（AMP）

搭载 ESP32 和 ESP32-S3 SoC 的开发板可以运行两个不同的应用程序。得益于双核架构，每个核都可以独立运行定制任务，和/或通过 OpenAMP 框架交换数据。代码参考见 Inter-Processor Communication (IPC) 目录。

备注

** AMP 与串口输出支持 **

在当前的 Zephyr ESP32 实现中，运行在 APPCPU 上的应用程序尚不能使用由 Zephyr 管理的串口驱动（例如 printk()、日志或控制台 UART）。因此，Zephyr 提供的串口输出 API 只能在 PROCPU 上使用。

作为变通方法，运行在 APPCPU 上的应用程序可以使用 ets_printf() 等 ESP32 ROM 函数输出诊断或调试信息。

更多信息请参阅 ESP32 Datasheet [1] 或 ESP32 Technical Reference Manual [2]。

简单引导

开发板可以直接加载单个二进制镜像，无需二级引导加载程序。在不做额外配置的情况下构建应用程序时，这是默认选项。

备注

简单引导不提供任何安全功能，也不支持 OTA 更新。

MCUboot 引导加载程序

用户也可以改用 MCUboot 引导加载程序。这种情况下，必须至少构建（并烧录）一次引导加载程序。

构建应用程序时有两种方式可选：

  1. Sysbuild

  2. 手动构建

备注

用户可以在开发板默认配置文件中添加以下一行来选用 MCUboot 引导加载程序。

CONFIG_BOOTLOADER_MCUBOOT=y

Sysbuild

借助 sysbuild，可以构建并烧录在搭载 ESP32 SoC 的开发板上完成引导所需的全部镜像。

要使用 sysbuild 构建示例应用程序，请使用以下命令：

west build -b <board> --sysbuild samples/hello_world

默认情况下，ESP32 sysbuild 会生成引导加载程序（MCUboot）镜像和应用程序镜像，但也可以配置为生成其他类型的镜像。

sysbuild 创建的构建目录结构与传统 Zephyr 构建不同。输出按域（domain）子目录组织：

build/
├── hello_world
│   └── zephyr
│       ├── zephyr.elf
│       └── zephyr.bin
├── mcuboot
│    └── zephyr
│       ├── zephyr.elf
│       └── zephyr.bin
└── domains.yaml

备注

使用 --sysbuild 选项时，每次进行全新（pristine）构建都会重新构建并重新烧录引导加载程序。

有关系统构建的更多信息，请阅读 Sysbuild（系统构建） 文档。

手动构建

在开发过程中，通常希望尽可能快地完成构建和烧录。为此，可以使用传统构建方式逐个构建镜像。

以下说明同时适用于手动构建和 sysbuild，唯一的区别在于构建目录的结构。

备注

请记住，引导加载程序（MCUboot）至少需要烧录一次。

按常规方式构建并烧录应用程序（详见 构建应用程序 和 运行应用程序）。

# From the root of the zephyr repository
west build -b <board> samples/hello_world

常规的 flash 目标可直接用于该开发板配置。以下以 Hello World 应用程序为例。

# From the root of the zephyr repository
west build -b <board> samples/hello_world
west flash

备注

在提供内置 USB Serial/JTAG 控制器的目标上，执行 west flash 后芯片可能停留在下载模式，在重新上电之前不会启动新镜像。如果出现这种情况，请使用看门狗复位进行烧录，使芯片自行重启：

west flash --reset-type watchdog-reset

更快的烧录

为了加快开发周期，--esp-skip-flashed 会在 Flash 中已有的二进制文件与待烧录的文件一致时跳过写入，一致性通过在设备上进行 MD5 校验来确认：

west flash --esp-skip-flashed

如需更快地重新烧录，--esp-diff 只写入与上次烧录的镜像不同的区域。它与本地缓存的副本进行比较，而不是读取设备，因此仅当自上次 west flash 以来 Flash 未被其他工具、开发板或手动写入修改过时才可使用：

west flash --esp-diff

可以关闭进度输出以使日志更简洁，这在 CI 中很有用：

west flash --esp-no-progress

使用以下命令打开串口监视器：

west espressif monitor

开发板自动复位并启动后，监视器中应显示以下信息：

***** Booting Zephyr OS vx.x.x-xxx-gxxxxxxxxxxxx *****
Hello World! <board>

使用 Espressif QEMU

Espressif 开发板可以在 Espressif 的 QEMU 分支 下运行，用于无需硬件的本地测试。CONFIG_ESPRESSIF_QEMU 会生成一个合并后的 SPI Flash 镜像。启用该选项还会选中隐藏的开发板标记 CONFIG_ESPRESSIF_QEMU_TARGET。只有当开发板选择加入 espressif_qemu 模拟平台时，才提供 west build -t run 目标（下文的 DevKitC 开发板通过共享的 board.cmake 辅助文件实现这一点）。

在参考 DevKitC 开发板上启用 Espressif QEMU 有两种方式：

  1. 在硬件开发板目标上使用 -DCONFIG_ESPRESSIF_QEMU=y 选择加入。这样同一个固件镜像既可以烧录到硬件（不带该选项时），也可以在 QEMU 下运行。所支持 SoC 上的其他开发板也可以设置该 Kconfig（用于导出 Flash 布局），但要使用 -t run，还需要同样的 SUPPORTED_EMU_PLATFORMS espressif_qemu 配置。

  2. 使用下列参考 DevKitC 目标上的 开发板变体（/qemu 限定符）。该变体的 defconfig 设置了 CONFIG_ESPRESSIF_QEMU，因此无需使用 -D。这些变体适用于本地和 CI 中的 west build -t run 工作流。Espressif QEMU 的 Twister simulation: 元数据尚未接入；请将 /qemu 视为开发板标识符加模拟平台，而不是标准 qemu_* Twister 模拟的直接替代品。

QEMU 变体设备树

硬件 DevKitC 目标保留完整的设备树。/qemu 开发板变体包含相同的硬件 *.dts，并为 QEMU 未建模的节点覆盖设置 status = "disabled"（或使用 /delete-node/）：

  • boards/espressif/esp32_devkitc/esp32_devkitc_procpu_qemu.dts

  • boards/espressif/esp32s3_devkitc/esp32s3_devkitc_procpu_qemu.dts

  • boards/espressif/esp32c3_devkitc/esp32c3_devkitc_qemu.dts

  • boards/espressif/esp32c6_devkitc/esp32c6_devkitc_hpcore_qemu.dts

通用覆盖文件禁用 Wi-Fi、蓝牙、I2C、I2S、通用 SPI、ADC 以及未模拟的 PWM 相关模块；移除 GPIO 按键节点；并清除不支持的 chosen 属性。Xtensa 变体还会禁用触摸、脉冲计数器和 MCPWM 节点。ESP32-S3 另外禁用第二个 I2C/SPI/I2S 实例、USB Serial/JTAG 和 OTG、LEDC、SD/MMC、温度传感器以及 LCD/CAM 控制器。ESP32-C3 禁用 USB Serial/JTAG、LEDC 及其温度传感器。ESP32-C6 禁用 IEEE 802.15.4、LP UART、MCPWM、脉冲计数器、TRNG（以及 zephyr,entropy）、AES 和 mbox0；SHA 仍可用。

UART、Flash 分区、定时器组和看门狗节点保持可用，以便进行冒烟测试（例如 samples/hello_world）。ESP32 / S3 / C3 上保留 TRNG 和完整的加密模块；ESP32-C6 只保留 SHA。GPIO 控制器节点和 CONFIG_GPIO=y 必须保持启用，因为 Espressif UART 驱动会选中 GPIO 驱动来进行引脚复用；尝试禁用它们会导致 Kconfig 依赖错误。这只是启动所需的基础设施，并不表示 QEMU 实现了应用层 GPIO 或 GPIO 矩阵。GPIO 按键已从设备树中移除。

自动与手动 QEMU 参数

启用 CONFIG_ESPRESSIF_QEMU 后，west build -t run 目标会自动追加以下参数：

  • 在 ESP32-C3 和 ESP32-C6 上添加 -icount 3

  • ESP32 ECO3 eFuse 镜像（见 Flash size / ESP32 chip revision）

  • -drive file=…/flash_image.bin,if=mtd,format=raw

  • 设置了 CONFIG_ESP_SPIRAM 时添加 -m <size>；大小取自 CONFIG_ESP_SPIRAM_SIZE（默认值来自设备树中开发板 psram0 的 size 属性）

  • 在 ESP32-S3 上设置了 CONFIG_SPIRAM_MODE_OCT 时添加 -global driver=ssi_psram,property=is_octal,value=true

对于可选情况（禁用看门狗、ESP32 上的 SD 卡等），请使用 QEMU_EXTRA_FLAGS 环境变量。

安装 Espressif QEMU

从 https://github.com/espressif/qemu/releases 下载预构建的二进制文件（Xtensa 和 RISC-V 软件包）。

示例（Linux x86_64，发布版本 esp-develop-9.2.2-20260417）:

mkdir -p ~/Downloads ~/opt
cd ~/Downloads
wget https://github.com/espressif/qemu/releases/download/esp-develop-9.2.2-20260417/qemu-xtensa-softmmu-esp_develop_9.2.2_20260417-x86_64-linux-gnu.tar.xz
wget https://github.com/espressif/qemu/releases/download/esp-develop-9.2.2-20260417/qemu-riscv32-softmmu-esp_develop_9.2.2_20260417-x86_64-linux-gnu.tar.xz
tar -xf qemu-xtensa-softmmu-*.tar.xz -C ~/opt --one-top-level=qemu-xtensa-softmmu
tar -xf qemu-riscv32-softmmu-*.tar.xz -C ~/opt --one-top-level=qemu-riscv32-softmmu

将两个 bin 目录都加入 PATH，或者将 ESPRESSIF_QEMU_PATH / QEMU_BIN_PATH 设置为平台格式的路径列表，其中包含目标 SoC 所需的目录。不支持 -machine esp* 的通用发行版 QEMU 无法使用。

在 CMake 配置阶段，会依次（按此顺序）对 ESPRESSIF_QEMU_PATH、QEMU_BIN_PATH 和 PATH 中找到的每个 qemu-system-xtensa / qemu-system-riscv32 执行 -machine help 探测，并使用第一个实现了该 SoC 机器的版本。这样会跳过 Zephyr SDK 在 hosttools 中自带的 QEMU，因为它是不含 Espressif 机器的上游构建版本。所选的二进制文件会打印为:

-- Espressif QEMU: /home/user/opt/qemu-xtensa-softmmu/qemu/bin/qemu-system-xtensa (-machine esp32)

由于查找在配置阶段进行，构建之后再安装 QEMU 或修改 ESPRESSIF_QEMU_PATH 时，需要重新运行 CMake（west build --pristine）。

构建与运行（简单引导）

除非指定了 --sysbuild 或在 west 配置中设置了 build.sysbuild，west build 不会使用 sysbuild，因此普通构建生成的是不含 MCUboot 的简单引导镜像。下文中的 --no-sysbuild 明确表明这一点，同时也会覆盖 west 配置中的 build.sysbuild=true。

选择加入（硬件开发板 + CMake 缓存项）:

west build -b esp32_devkitc/esp32/procpu samples/hello_world \
  --no-sysbuild --pristine \
  -- -DCONFIG_ESPRESSIF_QEMU=y

west build -t run

QEMU 开发板变体（由 defconfig 提供 CONFIG_ESPRESSIF_QEMU）:

west build -b esp32_devkitc/esp32/procpu/qemu samples/hello_world \
  --no-sysbuild --pristine

west build -t run

构建会生成 build/zephyr/flash_image.bin（合并后的 SPI 镜像），并注册 espressif_qemu 模拟平台（run_espressif_qemu / debugserver_espressif_qemu，别名为 west build -t run / debugserver）。在 ESP32 上还会生成 build/zephyr/qemu_efuse_eco3.bin 并将其传给 QEMU。等效的手动调用方式:

qemu-system-xtensa -nographic -machine esp32 \
  -drive file=build/zephyr/qemu_efuse_eco3.bin,if=none,format=raw,id=efuse \
  -global driver=nvram.esp32.efuse,property=drive,value=efuse \
  -drive file=build/zephyr/flash_image.bin,if=mtd,format=raw

ESP32-C3 选择加入示例:

west build -b esp32c3_devkitc/esp32c3 samples/hello_world \
  --no-sysbuild --pristine \
  -- -DCONFIG_ESPRESSIF_QEMU=y
west build -t run

ESP32-C3 变体（无需 -D）:

west build -b esp32c3_devkitc/esp32c3/qemu samples/hello_world \
  --no-sysbuild --pristine
west build -t run
# or:
qemu-system-riscv32 -nographic -icount 3 -machine esp32c3 \
  -drive file=build/zephyr/flash_image.bin,if=mtd,format=raw

MCUboot / sysbuild

使用 sysbuild 时，CONFIG_ESPRESSIF_QEMU 会将 MCUboot（boot_partition）和已签名的应用程序（slot0_partition）合并到同一个 Flash 镜像中:

west build -b esp32_devkitc/esp32/procpu samples/hello_world \
  --sysbuild --pristine \
  -- -DCONFIG_ESPRESSIF_QEMU=y

west build --domain hello_world -t run

这里必须指定 --domain：run 由应用程序镜像定义，而 sysbuild 顶层构建中没有该目标。镜像写入 build/<app>/zephyr/flash_image.bin，而不是 build/zephyr/。

合并时会使用引导加载程序域中的 ../mcuboot/zephyr/zephyr.bin。sysbuild 将每个镜像作为独立的外部工程添加，因此只要两个 ExternalProject 目标都存在，这些 DevKitC 开发板的 sysbuild.cmake 总是让应用程序排在 mcuboot 之后构建（该依赖不以 CONFIG_ESPRESSIF_QEMU 为条件，因为该选项在 sysbuild 的 CMake 上下文中不一定可见）。如果没有这一顺序，两个域会并发构建，合并时可能读到不完整的引导加载程序二进制文件。

启用 CONFIG_BOOTLOADER_MCUBOOT 的非 sysbuild 构建不会在构建树中生成引导加载程序二进制文件（在硬件上 MCUboot 已预先烧录）。对于 QEMU，可以使用 --sysbuild，或者通过 -DESPRESSIF_QEMU_MCUBOOT_BIN=<path to mcuboot zephyr.bin> 传入现有的引导加载程序镜像。该路径必须是绝对路径，因为合并操作在构建目录中执行。

GDB 调试

启动 QEMU，使 CPU 保持复位状态，并在端口 1234 上开启 GDB stub:

west build -t debugserver

在 sysbuild 下，与 run 一样添加 --domain <app>。然后在另一个终端中使用 Zephyr SDK 自带的 GDB 连接:

$ZEPHYR_SDK_INSTALL_DIR/gnu/xtensa-espressif_esp32_zephyr-elf/bin/xtensa-espressif_esp32_zephyr-elf-gdb \
  build/zephyr/zephyr.elf \
  -ex "target remote :1234" \
  -ex "tb main" -ex "c"

对于 RISC-V SoC（ESP32-C3、ESP32-C6），请改用 gnu/riscv64-zephyr-elf/bin/riscv64-zephyr-elf-gdb。如果 PATH 中有 ESP-IDF 环境，也可以使用 ESP-IDF 工具链中的 GDB（xtensa-esp32-elf-gdb、riscv32-esp-elf-gdb）。

高级 QEMU 参数

可以通过 QEMU_EXTRA_FLAGS 环境变量（以空格分隔）注入额外参数，该变量在 CMake 配置阶段读取：请在首次构建前设置，或在修改后重新运行 CMake 使其生效。以下选项 不会 自动追加：

  • 禁用 TG 看门狗： -global driver=timer.esp32.timg,property=wdt_disable,value=true（ESP32-S3、ESP32-C3 和 ESP32-C6 使用 timer.esp32c3.timg 属性名）

  • SD/MMC (ESP32 only): -drive file=sdcard.img,if=sd,format=raw

  • 自定义 eFuse 存储： 配置时使用 -DESPRESSIF_QEMU_EFUSE_HEX_FILE=/path/to/efuse.hex。hex 文件中允许包含空白字符。构建时会将其复制到构建目录，用 Python 解码，并将生成的二进制文件传给该机器的 eFuse 设备。如果不使用此覆盖选项，ESP32 使用内置的 ECO3 镜像，其他 SoC 则不挂载 eFuse 驱动器。源码树永远不会被写入。

    有关 efuse 布局和启动模式（strap mode），请参阅 https://github.com/espressif/esp-toolchain-docs/tree/main/qemu 下各 SoC 的页面。

PSRAM（启用 SPIRAM 时自动配置）

启用 CONFIG_ESP_SPIRAM 时，CMake 会追加 -m <size>，其中 <size> 由 CONFIG_ESP_SPIRAM_SIZE 推导得出（字节数 ÷ 1 MiB，后缀 M）。不支持的大小会导致配置失败（不会传入只得到部分支持的 -m）。由于硬件 WROVER N4R8 设备树默认值为 8M，ESP32 /qemu 变体将 psram0 限制为 4M。

QEMU 文档列出的大小：

  • ESP32： 2M、4M（PSRAM MMU 未完全模拟）

  • ESP32-S3： 2M、4M、8M、16M 或 32M；当 CONFIG_SPIRAM_MODE_OCT=y 时，八线（OPI）模式还会添加 ssi_psram 的 is_octal 全局参数

如有需要，可通过 QEMU_EXTRA_FLAGS 覆盖或补充。

Flash 大小

合并后的镜像会填充到设备树中开发板 zephyr,flash 的大小，使 SPI Flash 头和 QEMU MTD 大小一致。Espressif QEMU 支持 2、4、8 和 16 MB；请使用 Flash 大小为其中之一的开发板或覆盖文件。

ESP32 芯片版本

QEMU 默认的 efuse 报告 ESP32 版本为 0，除非启用 CONFIG_ESP32_USE_UNSUPPORTED_REVISION，否则 Zephyr 会拒绝该版本。启用 CONFIG_ESPRESSIF_QEMU 后，run / debugserver 目标会自动挂载一个 ECO3 eFuse 镜像（设置了 CHIP_VER_REV1 和 CHIP_VER_REV2），使客户机报告芯片版本为 v3.0。

在配置阶段，ECO3 hex 文件会写入构建目录，并用 Python 解码为 build/zephyr/qemu_efuse_eco3.bin。可以在配置时使用 -DESPRESSIF_QEMU_EFUSE_HEX_FILE=... 覆盖（或者在之后的 west build / west build -t run 中传入同样的 -D，这会重新运行 CMake）。仅设置环境变量是不够的：该路径只在 CMake 配置阶段读取。布局与 Emulating ESP32 ECO3 一致。

等效的手动 QEMU 调用方式:

qemu-system-xtensa -nographic -machine esp32 \
  -drive file=build/zephyr/qemu_efuse_eco3.bin,if=none,format=raw,id=efuse \
  -global driver=nvram.esp32.efuse,property=drive,value=efuse \
  -drive file=build/zephyr/flash_image.bin,if=mtd,format=raw

调试

OpenOCD 调试

Espressif 芯片需要使用带有 ESP32 专用补丁的定制版 OpenOCD。请从 OpenOCD for ESP32 [3] 下载最新版本。

详细的 JTAG 设置说明请参阅 JTAG debugging for ESP32 [5]。

Zephyr 线程感知

OpenOCD 支持 Zephyr RTOS 线程感知，使 GDB 能够：

  • 使用 info threads 列出所有线程

  • 显示线程名称、优先级和状态

  • 在不同线程上下文之间切换

  • 显示任意线程的回溯（backtrace）

Requirements:

  • OpenOCD ESP32 v0.12.0-esp32-20251215 [4] 或更高版本

  • 构建时启用 CONFIG_DEBUG_THREAD_INFO=y

Example:

# From the root of the zephyr repository
west build -b <board> samples/hello_world -- -DCONFIG_DEBUG_THREAD_INFO=y -DOPENOCD=<path/to/bin/openocd> -DOPENOCD_DEFAULT_PATH=<path/to/openocd/share/openocd/scripts>
west debug

使用自定义 OpenOCD

Zephyr SDK 自带 OpenOCD，但可能不支持 ESP32。要使用 Espressif OpenOCD，请在构建时指定其路径：

# From the root of the zephyr repository
west build -b <board> samples/hello_world -- -DOPENOCD=/path/to/openocd -DOPENOCD_DEFAULT_PATH=/path/to/openocd/scripts
west debug
