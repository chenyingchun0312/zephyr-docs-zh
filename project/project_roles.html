TSC 项目角色

项目角色

你可以作为 贡献者（Contributor）、协作者（Collaborator） 或 维护者（Maintainer） 参与 Zephyr 项目。

贡献者：为项目贡献代码、文档或其他资产的任何社区成员。

协作者：参与项目一个或多个领域的活跃贡献者。

维护者：负责项目中某个特定领域或子系统的主导协作者。维护者还会在需要时作为其领域的代表参与技术指导委员会（TSC）。

这里的领域是指 Zephyr 项目代码库中特定的子系统、组件或模块。领域的例子包括但不限于网络、文件系统、设备驱动、架构支持以及板级支持包（开发板和 SoC 定义）。

项目中的每个领域至少应有一名维护者，并可以有多名协作者。根据领域的规模和复杂程度，也可以有多名维护者，但维护者人数应保持在切实可行的最低限度，以确保有效的管理和决策。

贡献者

贡献者 是希望在任何层面为项目做出贡献的开发者。

贡献者拥有以下权利和职责：

  • 贡献代码、文档、翻译、美术作品等的权利。

  • 报告缺陷（bug）和提出改进建议的权利。

  • 参与审查他人贡献的权利。

  • 参与功能开发流程的权利。

  • 决定一经做出即应遵守的责任。欢迎提供新的相关信息以重新讨论已有决定。

  • 对自己的贡献所引入的问题和缺陷负责。

  • 尊重社区规则的责任。

  • 在参与讨论和审查贡献时提供建设性意见的责任。

  • 遵守项目行为准则（https://github.com/zephyrproject-rtos/zephyr/blob/main/CODE_OF_CONDUCT.md）的责任

Zephyr 贡献者徽章

当你对 Zephyr 项目的首次贡献被合并后，你就有资格申领 Zephyr 贡献者徽章。这枚数字徽章可以展示在你的网站、博客、社交媒体个人资料等处，让你展示自己对 Zephyr 项目的参与，并帮助提高项目的知名度。

你可以填写 Zephyr Contributor Badge form 来申请贡献者徽章。

协作者

协作者 是同时参与维护 Zephyr 源代码的贡献者。在做出决定时，他们的意见权重更大，这完全基于贤能原则（meritocracy）。

要成为协作者，你需要持续参与项目，包括在一段时间内为项目做出重要贡献，并参与至少一个领域的开发和审查。

要申请成为协作者，请提交一个 PR，将你自己添加到 MAINTAINERS 文件 中某个领域的 collaborators 部分，并通知该领域的维护者。该添加需要获得该领域维护者的批准。

除贡献者的权利和职责外，协作者还拥有以下权利和职责：

  • 与所维护领域的维护者一起，参与制定该领域中短期目标的权利。

  • 参与功能开发流程的责任。

  • 在合理时间内审查相关代码变更的责任。

  • 确保代码质量达到预期水平的责任。

  • 参与社区讨论的责任。

  • 在适当时指导新贡献者的责任

  • 在进行质量验证和发布流程时参与其中的责任。

协作者在 PR 上提出的修改请求应由原提交者处理。如果所请求的修改不符合项目的 期望 和准则，或者出现分歧，则由指派人（assignee）负责推进审查流程并解决分歧。

协作者对 PR 的批准计入合并 PR 所需的最少批准数。合并可能还需满足其他标准。

维护者

维护者 是同时负责了解、指导和预判 Zephyr 源代码某一领域需求的协作者。

个人可以通过长期持续地做出有意义的贡献而成为某个领域的维护者，包括：

  • 为该领域做出重要的技术贡献。

  • 积极参与开发流程，包括代码审查和设计讨论。

  • 熟悉该领域的架构、约束条件和演进历程。

作为原作者向项目引入新的领域或子系统，并展示出公认的专业能力和对该领域的长期投入时，也可以获得维护者身份。

在任何情况下，维护者身份都既体现了技术上的所有权，也体现了对支持该领域的社区的持续参与。

要申请成为维护者，请提交一个 PR，将你自己添加到 MAINTAINERS 文件 中某个领域的 maintainers 部分，并通知该领域的现有维护者。该添加需要获得该领域维护者的批准。

通常只有一名维护者，但视领域而定，也可能由多名维护者共同承担职责。

除贡献者和协作者的权利和职责外，维护者还拥有以下权利和职责：

  • 确定相关子系统或所参与领域整体架构的权利。

  • 与协作者和提交者一起，在相关子系统或所参与领域中做出决定的权利。参见 PR 技术问题升级处理。

  • 向 TSC 传达相关子系统或领域发展方向的责任

  • 确保项目的所有贡献都在合理时间内得到审查的责任。

  • 执行行为准则的责任。作为社区的领导者，维护者应在遵守项目行为准则、为每个人营造友好包容的环境方面起到表率作用。

  • 对其代码领域中的静态分析问题进行分类处理的责任。参见 静态代码分析。

维护者对 PR 的批准计入合并 PR 所需的最少批准数。合并可能还需满足其他标准。

团队与支持性工作

指派人（Assignee）

指派人 是 PR 所修改领域的维护者之一。

指派人会根据所修改的代码自动设置。无法自动设置，或者另一名指派人更合适时，其他维护者或发布工程团队可以设置指派人；在后一种情况下，应在评论中说明更改的理由。

  • 推动 PR 达到可合并状态的责任

  • 驳回过时的、无关的或不符合 期望 的审查意见，并向其他维护者、开发者和贡献者征求审查的权利

  • 在所提出的问题或修改请求得到处理之前阻止 PR 合并的权利

  • 如果自己是代码的原提交者，则有责任重新指派该 PR

  • 征求受影响子系统维护者的批准

  • 推动 PR 技术问题升级处理 流程的责任

静态分析审计团队

静态分析审计团队与发布工程团队紧密合作，确保在一个发布周期内提出的静态分析缺陷得到妥善处理。该团队拥有以下权利和职责：

  • 撤销静态分析工具（例如 Coverity）中任何不符合项目期望的分类处理结果的权利。

  • 将不当分类告知代码所有者的责任。

  • 如果有问题未得到相应代码所有者的妥善处理，向 TSC 发出警示的责任。

加入静态分析审计团队

  • 深度参与项目、并具备一定静态分析专业知识的贡献者。

发布工程团队

由参与多个领域的活跃维护者组成的团队。

  • 发布工程团队的成员应按照既定的节奏和遴选流程担任发布经理角色。

  • 该节奏和遴选流程由发布工程团队制定，并由 TSC 批准。

  • 该团队直接向 TSC 汇报。

发布工程团队拥有以下权利和职责：

  • 按照项目规则将代码变更合并到 zephyr 代码树的权利。

  • 撤销任何破坏代码库的变更的权利

  • 关闭在 <N> 个月内没有任何活动的过时变更的权利

  • 接受并遵循 TSC 指示的责任。

  • 与维护者协调代码合并的责任。

  • 对于已获得相应维护者批准并符合变更合并标准的所有贡献，无论其来源和领域如何，都负有合并的责任。

  • 使 Zephyr 代码库保持可用并通过（CI 意义上的）测试状态的责任

加入发布工程团队

  • 深度参与项目的维护者可以由 TSC 投票成员提名加入发布工程团队。被提名人经现有 TSC 投票成员批准后即可成为团队成员。

  • 为确保发布工程团队正常运作，TSC 应定期审查该团队所遵循的流程、适当的规模以及成员构成（例如，确保团队成员在地理上分布于多个地点和时区）。

发布经理

负责按照项目针对某个特定版本的里程碑和路线图，推动该版本最终完成的 维护者。

  • 发布经理需经 TSC 批准。

发布经理是发布工程团队的成员，除拥有该团队的权利和职责外，还拥有以下权利和职责：

  • 在代码冻结里程碑（M3，参见 项目管理概述）之后管理和协调所有代码合并的权利。

  • 推动和协调该版本的问题分类流程的责任

  • 编写该版本发布说明的责任

  • 及时将版本状态通知项目所有利益相关方（包括整个社区）的责任。

  • 在重大变更和重要里程碑之前，与 QA 和验证人员协调，直接或通过 QA 验证变更的责任。

角色卸任

经 TSC 或 TSC 代表批准担任项目角色的个人，如果不再积极履行与其角色相关的权利和职责，TSC 可以要求其卸任该角色。

不活跃的维护者或协作者卸任时，会从 Zephyr 仓库 MAINTAINERS 文件 的相关部分中删除其 GitHub 用户名。卸任可以由 TSC、TSC 代表或当事人自己发起。维护者也可以发起删除其领域内不活跃的协作者。

维护者可以反对被卸任，并请求 TSC 做出决定。

MAINTAINERS 文件

以下准则适用于 MAINTAINERS 文件的结构、范围和维护。

  • 根据 Zephyr 项目章程，MAINTAINERS 文件应有指定的负责人，负责该文件的准确性、结构和日常维护。这些负责人应由 TSC 任命。

  • 维护职责的划分粒度应保持切实可行、易于管理。

  • TSC 应与现有维护者和贡献者合作，积极发掘并鼓励贡献者站出来担任代码库中无人维护领域的维护者，并协助为这些组件指派维护者。

  • 无人维护的领域应在 MAINTAINERS 文件中明确标注。

  • 对 MAINTAINERS 文件的更新应：

    • 在引入新文件或新目录时，一般作为独立的提交包含在内。

    • 重大变更（包括新增领域和新增维护者）应作为单独的 PR 提交，并需获得 MAINTAINERS 文件维护者的批准。此类活动可能源于将现有的大领域拆分为较小的领域，或者合并较小的领域。

为代码库不同领域指派维护者的准则：

架构、核心组件、子系统、示例和测试：

每个领域都应明确指派一名维护者。

开发板（包括相关示例和测试）和 SoC（包括 DTS 定义）

每个开发板和 SoC 都应通过一个涵盖这些开发板、SoC 及其相关组件和驱动的平台领域，明确指派维护者。

驱动/后端

API 层面的领域应有一名维护者，具体的驱动实现或后端也应通过涵盖该驱动实现的平台领域进行覆盖。驱动实例或后端发生变更时，会指派驱动领域或子系统的维护者。
