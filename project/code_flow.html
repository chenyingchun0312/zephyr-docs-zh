代码流程与分支

简介

zephyr Git 仓库有三种类型的分支：

main

包含最新的开发状态

collab-*

协作分支，用于共同开发新功能，这些功能就绪后会引入 main 分支。创建新的协作分支需要给出理由并获得 TSC 批准。协作分支应基于 main 分支创建，在协作分支中开发的任何变更都应以 main 开发分支为目标。对于已发布的 Zephyr 版本，如果 TSC 批准引入修复和新功能，应通过向后移植（backport）PR（拉取请求）来完成。

vx.y-branch

跟踪基于某个主版本的维护版本的分支

在功能进入主线之前先在协作分支中开发，可以让团队独立地开发某个子系统或功能，提高效率、缩短周转时间，并促进开发者之间的协作、简化沟通。

提交到协作分支的变更可以在分支中逐步演进和完善，然后再提交到主线代码树进行最终集成。

为复杂功能专门设立一个隔离的分支，可以在将新增内容集成到正式项目之前，围绕它们展开深入讨论。

协作分支是临时性的，协作工作完成后应予以删除。申请创建分支时，提案应包含以下内容：

  • 定义将协作分支的变更合并回 main 分支的退出标准。

  • 定义该分支预期生命周期的时间表。建议选定一个 Zephyr 版本来确定时间表。延长该时间表需要 TSC 批准。

角色与职责

协作分支所有者负有以下职责：

  • 使用项目提供的基础设施和工具（GitHub、Git）

  • 对协作分支的所有变更都应以 GitHub PR 的形式提交。

  • 只有在基于 main 分支执行变基（rebase）时，才允许强制推送协作分支。

  • 审查团队成员提交的变更，并在提交变更时请求分支所有者进行审查。

  • 使分支与上游保持同步，并定期更新。

  • 使用以下方法频繁地将变更推送到上游：

    • GitHub PR：例如，当变更尚未在本地分支（单人分支）中经过审查时。

    • 合并请求：当一组变更已在本地分支中完成，并已在协作分支中经过审查和测试时。
