代码文档

API 文档

文档完善的 API 能改善开发者的使用体验，也是衡量一个 API 是否成功的基本要求。Doxygen 是一个通用文档工具，Zephyr 项目用它来编写 API 文档。它可以生成在线文档浏览器（HTML 格式），也可以为其他工具提供输入，用于从带文档注释的源文件生成参考手册。特别是，在生成 Zephyr 项目的在线文档时，Doxygen 的 XML 输出会被用作输入。

对需求的引用

API 文档大多描述的是需求或所宣称功能的实现，因此可以追溯到具体功能。我们将 API 文档作为把实现追溯到已记录功能的主要接口。这是通过 Doxygen 原生的需求追溯命令（@satisfies 和 @verifies）实现的，这些命令引用的是在其他地方的需求目录中维护的需求。

测试文档

为了帮助理解每个测试的作用以及它测试的是哪项功能，我们也使用相同的工具、在相同的上下文中为所有测试代码编写文档，并为在同一环境中维护的所有单元测试和集成测试生成文档。测试文档通过引用其所验证的 API 或功能来编写：创建指回这些 API 的链接，并添加对原始需求的引用。

文档编写准则

测试代码

Zephyr 项目使用多种测试方法，最常见的是 Ztest 框架。测试文档只应针对入口测试函数（通常以 test_ 为前缀）以及由 Ztest 框架直接调用的函数编写。这些测试会出现在测试报告中，使用它们的名称和标识符是识别它们、并从需求追溯到它们的最佳方式。

测试文档不应干扰实际的 API 文档，需要采用一种新的结构以避免混淆。通过使用一致的命名方案并遵循明确定义的结构，我们就能把这些文档归入单独的模块，并在为追溯报告解析测试数据时唯一地识别它们。以下是需要遵循的几条准则：

  • 所有测试代码文档都应归入 all_tests Doxygen 组

  • 所有测试文档都应位于以 tests_ 为前缀的 Doxygen 组之下

记录需求

需求使用 Doxygen 的 @requirement 命令记录，该命令接受一个唯一标识符和一个可选的标题。Doxygen 会把所有需求汇集到一个页面上，并允许在任何地方通过标识符引用它们。请使用专门用于该需求的注释块，通常在需求目录中维护:

/**
* @requirement ZEPH-015 (Give a semaphore)
*
* The kernel shall provide a mechanism to give a semaphore, increasing its
* count up to its configured maximum.
*/

这里使用的标识符（例如 ZEPH-015）与下文 @satisfies 和 @verifies 命令所引用的标识符相同，正是它将实现和测试关联回需求。

Doxygen 的 @verifies 命令表示某个测试验证了某项需求:

/**
* @brief Tests for the Semaphore kernel object
* @defgroup kernel_semaphore_tests Semaphore
* @ingroup all_tests
* @{
*/

...
/**
* @brief A brief description of the tests
* Some details about the test
* more details
*
* @verifies ZEPH-015
*/
void test_sema_thread2thread(void)
{
...
}
...

/**
* @}
*/

为了覆盖某个实现或某段代码如何满足某项需求，我们使用 Doxygen 的 @satisfies 命令:

/**
* @brief Give a semaphore.
*
* This routine gives @a sem, unless the semaphore is already at its maximum
* permitted count.
*
* @note Can be called by ISRs.
*
* @param sem Address of the semaphore.
*
* @satisfies ZEPH-015
*/
__syscall void k_sem_give(struct k_sem *sem);

要生成追溯矩阵，首先需要构建文档，具体来说需要构建 Doxygen 的 XML 输出:

$ make doxygen

解析 Doxygen 生成的 XML 数据，以生成追溯矩阵。
