测试框架

Zephyr 测试框架（Ztest）提供了一个简单的测试框架，供开发期间使用。它提供基本的断言宏和通用的测试结构。

该框架有两种使用方式：作为集成测试的通用框架，或者用于对特定模块进行单元测试。

快速入门：集成测试

samples/subsys/testsuite/integration 中提供了一个可以直接运行的简单基础示例。要为 foo 的 bar 组件编写测试应用程序，应将该示例目录复制到 tests/foo/bar，并在其中根据测试应用程序的用途修改文件。

要构建并执行测试应用程序中定义的所有适用的测试场景，请使用 Twister 工具，例如：

west twister -T tests/foo/bar/

要只选择其中一个测试场景，请使用 --scenario 命令运行 Twister：

west twister --scenario tests/foo/bar/your.test.scenario.name

在上面的命令行中，tests/foo/bar 是测试应用程序的路径，your.test.scenario.name 引用 tests.yaml 文件中定义的一个测试场景，类似于样板测试套件示例中的 sample.testing.ztest。

有关 Twister 如何处理 Ztest 应用程序的更多细节，请参见 Twister 测试项目示意图。

该示例包含以下文件：

CMakeLists.txt
1# SPDX-License-Identifier: Apache-2.0
2
3cmake_minimum_required(VERSION 3.28.0)
4find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
5project(integration)
6
7FILE(GLOB app_sources src/*.c)
8target_sources(app PRIVATE ${app_sources})
tests.yaml
1tests:
2  # section.subsection
3  sample.testing.ztest:
4    build_only: true
5    platform_allow:
6      - native_sim
7    integration_platforms:
8      - native_sim
9    tags: test_framework
prj.conf
1CONFIG_ZTEST=y
src/main.c
 1/*
 2 * Copyright (c) 2016 Intel Corporation
 3 *
 4 * SPDX-License-Identifier: Apache-2.0
 5 */
 6
 7#include <zephyr/ztest.h>
 8
 9
10ZTEST_SUITE(framework_tests, NULL, NULL, NULL, NULL, NULL);
11
12/**
13 * @brief Test Asserts
14 *
15 * This test verifies various assert macros provided by ztest.
16 *
17 */
18ZTEST(framework_tests, test_assert)
19{
20	zassert_true(1, "1 was false");
21	zassert_false(0, "0 was true");
22	zassert_is_null(NULL, "NULL was not NULL");
23	zassert_not_null("foo", "\"foo\" was NULL");
24	zassert_equal(1, 1, "1 was not equal to 1");
25	zassert_equal_ptr(NULL, NULL, "NULL was not equal to NULL");
26}

一个测试应用程序可以由多个测试套件组成，这些测试套件可以测试功能，也可以测试 API。实现测试用例的函数应遵循以下准则：

  • 测试用例函数名应以 test_ 为前缀

  • 测试用例应使用 doxygen 编写文档

  • 测试用例函数名在被测部分或组件中应当唯一

例如：

/**
 * @brief Test Asserts
 *
 * This test case verifies the zassert_true macro.
 */
ZTEST(my_suite, test_assert)
{
        zassert_true(1, "1 was false");
}

列出测试

Zephyr 代码树中的测试（测试应用程序）由许多测试场景组成，这些场景作为某个项目的一部分运行，测试相似的功能，例如某个 API 或某项特性。twister 脚本可以解析所有测试应用程序或其中一部分的测试场景、套件和用例，并生成细粒度的报告，即测试用例是通过还是失败，或者是被阻塞还是被跳过。

Twister 会解析源文件以查找测试用例名称，因此可以列出所有测试用例。例如，要列出所有内核测试用例，可以运行：

west twister --list-tests -T tests/kernel

跳过测试

特殊测试或架构特定的测试无法在所有平台和架构上运行，但我们仍然希望将它们计入并报告为已跳过。由于测试清单和测试列表是从代码中提取的，在测试套件内部添加条件判断并不理想。对于在特定平台或特性下需要跳过的测试，需要使用 ztest_test_skip() 或 Z_TEST_SKIP_IFDEF 显式报告跳过。如果测试运行了，就需要报告通过或失败。例如：

#ifdef CONFIG_TEST1
ZTEST(common, test_test1)
{
     zassert_true(1, "true");
}
#else
ZTEST(common, test_test1)
{
     ztest_test_skip();
}
#endif

ZTEST(common, test_test2)
{
     Z_TEST_SKIP_IFDEF(CONFIG_BUGxxxxx);
     zassert_equal(1, 0, NULL);
}

ZTEST_SUITE(common, NULL, NULL, NULL, NULL, NULL);

快速入门：单元测试

Ztest 可用于单元测试。这意味着在测试单个函数时，无需引入整个 Zephyr OS，而是可以将测试工作集中在相关的特定模块上。由于只需编译该模块，并直接调用被测函数，测试速度会更快。

要设置单元测试，需要在包含单元测试源文件的目录中添加 CMakeLists.txt、tests.yaml 和 prj.conf。该目录生成的二进制文件使用 -DBOARD=unit_testing 构建。调用 twister 时，脚本 zephyr/scripts/pylib/twister/twisterlib/testplan.py 会过滤掉所有未设置 type: unit 的 tests.yaml。使用 BOARD=unit_testing 构建固件时，只会执行单元测试。

备注

单元测试作为 原生 应用程序在主机上运行，因此受到与 POSIX 架构 文档中所述类似的 限制。因此，只支持在 Linux 上运行单元测试。要在 Windows 或 macOS 上运行单元测试，需要使用运行 Linux 客户机的容器或虚拟机，并遵循与 POSIX 架构依赖 相同的说明。

unit_testing 开发板

单元测试针对特殊的 unit_testing 开发板（subsys/testsuite/boards/unit_testing）构建。它既不是真实的硬件，也不是仿真目标，而是一块 arch: unit 的伪开发板，使用主机工具链生成普通的原生可执行文件。通过 -DBOARD=unit_testing 选择它（对于标记为 type: unit 的场景，Twister 会自动这样做）时，只会构建和链接你添加到 testbinary 目标中的源文件以及 Ztest 单元测试 harness。

关键在于，完全不会构建 Zephyr 内核和操作系统。没有启动流程、没有调度器、没有由设备树驱动的设备初始化，也没有驱动模型。被测函数会被编译到测试二进制文件中并被直接调用。被测模块所依赖的任何内核 API 或其他依赖都必须由测试自身提供，通常以桩函数或 mock 的形式提供。

与 native_sim 及其他开发板的区别

unit_testing 开发板很容易与 Native simulator - native_sim 混淆，因为二者都在主机上运行。但它们有本质区别：

  • Native simulator - native_sim 会将 完整的 Zephyr OS（内核、设备树、Kconfig、驱动和子系统）构建为一个主机二进制文件，它的启动和运行方式与真实硬件上的 Zephyr 镜像完全相同，只是针对主机而不是目标 SoC 编译。可以用它在主机上运行完整的应用程序和集成测试。针对这些开发板的测试 不 设置 type: unit。

  • unit_testing 则 不会 构建上述任何内容。它只链接被测代码和 Ztest，其余一切都使用桩函数或 mock 替代，并直接调用被测函数。这使得构建和运行都很快，并能将注意力集中在单个模块上，代价是必须为每个依赖提供桩函数。这些测试必须设置 type: unit（参见 下文）。

简而言之，要在运行中的 Zephyr 系统环境下测试代码，请使用 native_sim；要在不引入内核的情况下测试单独的模块，请使用 unit_testing。

CMakeLists.txt

要声明某个源码目录中的单元测试，需要将相关源文件添加到 CMake unittest 组件提供的 testbinary 目标中。下面是一个最小示例：

cmake_minimum_required(VERSION 3.28.0)

project(app)
find_package(Zephyr COMPONENTS unittest REQUIRED HINTS $ENV{ZEPHYR_BASE})
target_sources(testbinary PRIVATE main.c)

由于不会包含大多数代码所依赖的基本内核数据结构，你必须在测试中提供函数桩。Ztest 提供了一些用于模拟函数的辅助工具，如下所示。

在单元测试中，mock 对象可以模拟复杂真实对象的行为，用于通过验证是否发生了与某个对象的交互（如有需要，还可以断言交互的顺序）来判定测试是失败还是通过。

tests.yaml

必须在 tests.yaml 中将键 "type" 的值设为 "unit"

tests:
   testscenario.testsuite:
      tags: your_tag
      type: unit

prj.conf

对于单元测试，该文件通常只包含

CONFIG_ZTEST=y

如果单元测试需要额外的库（例如 math-lib），需要通过 CMakeLists.txt 或在 tests.yaml 中添加：

tests:
   testscenario.testsuite:
      tags: your_tag
      type: unit
      extra_args:
         - EXTRA_LDFLAGS="-lm"

单元测试的示例位于 tests/unit/ 目录中。

创建测试套件

使用 Ztest 创建测试套件非常简单，只需调用 ZTEST_SUITE。该宏接受以下参数：

  • suite_name - 套件的名称。该名称在单个二进制文件中必须唯一。

  • ztest_suite_predicate_t - 可选的谓词函数，用于选择测试何时运行。谓词会得到一个指针，指向通过 ztest_run_all() 传入的全局状态，并应返回一个布尔值，决定是否运行该套件。

  • ztest_suite_setup_t - 可选的 setup 函数，返回一个测试 fixture。每次运行测试套件时会调用并执行一次。

  • ztest_suite_before_t - 可选的 before 函数，会在该套件中每个测试之前运行。

  • ztest_suite_after_t - 可选的 after 函数，会在该套件中每个测试之后运行。

  • ztest_suite_teardown_t - 可选的 teardown 函数，会在套件中所有测试结束后运行。

下面是一个使用谓词的测试套件示例：

#include <zephyr/ztest.h>
#include "test_state.h"

static bool predicate(const void *global_state)
{
     return ((const struct test_state*)global_state)->x == 5;
}

ZTEST_SUITE(alternating_suite, predicate, NULL, NULL, NULL, NULL);

向套件中添加测试

有 5 个宏可用于向套件中添加测试，分别是：

  • ZTEST (suite_name, test_name) - 可用于向由 suite_name 指定的套件中添加名为 test_name 的测试。

  • ZTEST_P (suite_name, test_name) - 向给定套件中添加一个值参数化测试。测试主体会针对每个注册的参数值各执行一次。在主体内部，调用 ztest_get_current_param() 或使用带类型的辅助宏 ZTEST_GET_PARAM 获取当前值。套件 fixture（data 参数）与参数相互独立，永远不会被覆盖。完整的 API 请参见 Value-parameterized tests。

  • ZTEST_USER (suite_name, test_name) - 行为与 ZTEST 相同，只是在启用 CONFIG_USERSPACE 时，测试会在用户空间线程中运行。

  • ZTEST_F (suite_name, test_name) - 行为与 ZTEST 相同，只是测试函数中已经包含一个名为 fixture、类型为 <suite_name>_fixture 的变量。

  • ZTEST_USER_F (suite_name, test_name) - 将 ZTEST_F 的 fixture 功能与测试的用户空间线程结合起来。

测试 fixture

测试 fixture 可用于简化重复的测试设置操作。很多情况下，同一套件中的测试需要先进行一些初始设置，然后在每个测试之间进行某种形式的重置。这可以通过以下方式使用 fixture 实现：

#include <zephyr/ztest.h>

struct my_suite_fixture {
     size_t max_size;
     size_t size;
     uint8_t buff[1];
};

static void *my_suite_setup(void)
{
     /* Allocate the fixture with 256 byte buffer */
     struct my_suite_fixture *fixture = malloc(sizeof(struct my_suite_fixture) + 255);

     zassume_not_null(fixture, NULL);
     fixture->max_size = 256;

     return fixture;
}

static void my_suite_before(void *f)
{
     struct my_suite_fixture *fixture = (struct my_suite_fixture *)f;
     memset(fixture->buff, 0, fixture->max_size);
     fixture->size = 0;
}

static void my_suite_teardown(void *f)
{
     free(f);
}

ZTEST_SUITE(my_suite, NULL, my_suite_setup, my_suite_before, NULL, my_suite_teardown);

ZTEST_F(my_suite, test_feature_x)
{
     zassert_equal(0, fixture->size);
     zassert_equal(256, fixture->max_size);
}

在用户空间线程中（例如执行 ZTEST_USER 或 ZTEST_USER_F 期间）使用测试 fixture 分配的内存时，需要将该内存声明为用户空间可访问。这是因为 fixture 内存由内核空间拥有并初始化。Ztest 框架提供了 ZTEST_DMEM 和 ZTEST_BMEM 宏，用于这类用户空间/内核空间共享内存。

高级功能

值参数化测试

值参数化测试允许同一个测试主体针对所提供列表中的每个值各执行一次，类似于 GoogleTest 的 TEST_P / INSTANTIATE_TEST_SUITE_P 模式。fixture 与参数完全独立：套件 setup() 的返回值总是作为 data 传入，永远不会被参数值覆盖。

声明参数化测试主体

按照与 ZTEST 相同的方式使用 ZTEST_P。在主体内部，data 指针携带套件 fixture（与 ZTEST_F 相同）。当前参数值通过以下运行时访问函数获取：

#include <zephyr/ztest.h>

struct my_suite_fixture {
     int initial_value;
};

static void *my_suite_setup(void) {
     static struct my_suite_fixture f = { .initial_value = 42 };
     return &f;
}

ZTEST_SUITE(my_suite, NULL, my_suite_setup, NULL, NULL, NULL);

ZTEST_P(my_suite, test_multiply)
{
     struct my_suite_fixture *f = (struct my_suite_fixture *)data;
     int factor = ZTEST_GET_PARAM(int);

     /* fixture is always intact, regardless of parameter */
     zassert_equal(f->initial_value, 42, "fixture corrupted");
     zassert_true(f->initial_value * factor > 0, "product must be positive");
}

声明参数值

使用 ZTEST_DEFINE_PARAM_VALUES 从字面值创建静态值集合：

ZTEST_DEFINE_PARAM_VALUES(small_factors, int, 1, 2, 3);

对于已存储在数组中的值，使用 ZTEST_DEFINE_PARAM_VALUES_ARRAY：

static const int big_factors[] = { 10, 100, 1000 };
ZTEST_DEFINE_PARAM_VALUES_ARRAY(big_factor_vals, big_factors);

对于数值范围，使用 ZTEST_DEFINE_PARAM_RANGE，其语义与 GoogleTest 的 testing::Range(begin, end [, step]) 一致。取值为 {begin, begin+step, ...}，一直到 end 为止，但 不 包括该值。由于不分配底层数组，大范围也不会产生任何 RAM 开销：

/* {0, 2, 4, 6, 8} — 5 values, step is supplied explicitly */
ZTEST_DEFINE_PARAM_RANGE(even_vals, int, 0, 10, 2);

/* {1, 2, 3, 4, 5} — step=1 is the common case */
ZTEST_DEFINE_PARAM_RANGE(one_to_five, int, 1, 6, 1);

备注

ZTEST_DEFINE_PARAM_RANGE 要求 end > begin 且 step > 0，这两个条件都通过 BUILD_ASSERT 在编译时强制检查。

对于必须 在运行时计算 的值（例如随机数、硬件传感器读数或由自定义算法生成的值），使用 ZTEST_DEFINE_PARAM_GENERATOR 或 ZTEST_DEFINE_PARAM_GENERATOR_WITH_SETUP。二者都接受一个用户提供的生成器回调，其签名为 void gen(size_t index, void *out)，每次调用写出一个值。与范围一样，不会分配底层数组。

_WITH_SETUP 变体还会在分派循环之前调用 一次 void setup(void) 钩子。这里适合为 PRNG 设置种子、重置有状态的计数器，或打开生成器所需的任何资源：

#include <zephyr/random/random.h>

/* Seed the RNG before the first iteration so failures are reproducible. */
static void seed_rng(void)
{
     sys_rand_seed(MY_FUZZ_SEED);
}

static void rand_u32_gen(size_t idx, void *out)
{
     ARG_UNUSED(idx);
     *(uint32_t *)out = sys_rand32_get();
}

ZTEST_DEFINE_PARAM_GENERATOR_WITH_SETUP(fuzz_vals, uint32_t, MY_FUZZ_ITERATIONS,
                                        seed_rng, rand_u32_gen);

如果不需要 setup，请使用更简单的形式：

static void deterministic_gen(size_t idx, void *out)
{
     /* Deterministic but computed at runtime (e.g. based on hardware ID). */
     *(uint32_t *)out = get_device_seed() ^ (uint32_t)idx;
}

ZTEST_DEFINE_PARAM_GENERATOR(hw_vals, uint32_t, 16U, deterministic_gen);

备注

两个生成器宏的 count_ 参数都必须是常量表达式（数字字面量、#define 或 MY_FUZZ_ITERATIONS 这样的 Kconfig 符号）。不支持真正动态的数量。

结构体类型的参数用法相同：

struct point { int x; int y; };

static const struct point corners[] = { {0,0}, {1,0}, {0,1}, {1,1} };
ZTEST_DEFINE_PARAM_VALUES_ARRAY(corner_vals, corners);

ZTEST_P(my_suite, test_in_unit_square)
{
     const struct point *p = ZTEST_GET_PARAM_PTR(struct point);
     zassert_true(p->x >= 0 && p->x <= 1 && p->y >= 0 && p->y <= 1,
                 "point (%d, %d) outside unit square", p->x, p->y);
}

实例化参数化测试

ZTEST_INSTANTIATE_TEST_SUITE_P 将一个值集合绑定到一个测试主体上。每次调用都会创建一个单独命名的实例化；同一个测试主体可以使用不同的值集合多次实例化：

ZTEST_INSTANTIATE_TEST_SUITE_P(small, my_suite, test_multiply, small_factors);
ZTEST_INSTANTIATE_TEST_SUITE_P(big,   my_suite, test_multiply, big_factor_vals);

第一个参数（small / big）是编译单元内任意的唯一标识符；它会记录在测试元数据中，但不影响 Twister 报告的测试命名。

获取当前参数

测试结果预期

有些测试本来就是要失败的。如果由于代码本身的性质，预计测试会失败或被跳过，可以对测试进行相应的标注。例如：

#include <zephyr/ztest.h>

ZTEST_SUITE(my_suite, NULL, NULL, NULL, NULL, NULL);

ZTEST_EXPECT_FAIL(my_suite, test_fail);
ZTEST(my_suite, test_fail)
{
  /** This will fail the test */
  zassert_true(false, NULL);
}

ZTEST_EXPECT_SKIP(my_suite, test_skip);
ZTEST(my_suite, test_skip)
{
  /** This will skip the test */
  zassume_true(false, NULL);
}

在本例中，上述测试本应分别被标记为失败和跳过。但由于设置了预期，Ztest 会将二者都标记为通过。

测试规则

测试规则可以为每个测试和每个套件运行相同的逻辑。很多情况下，你可能希望为二进制文件中的每个测试重置某些状态（无论当前运行的是哪个套件），例如重置 mock、重置仿真器、刷新 UART 等：

#include <zephyr/fff.h>
#include <zephyr/ztest.h>

#include "test_mocks.h"

DEFINE_FFF_GLOBALS;

DEFINE_FAKE_VOID_FUN(my_weak_func);

static void fff_reset_rule_before(const struct ztest_unit_test *test, void *fixture)
{
     ARG_UNUSED(test);
     ARG_UNUSED(fixture);

     RESET_FAKE(my_weak_func);
}

ZTEST_RULE(fff_reset_rule, fff_reset_rule_before, NULL);

自定义 test_main

虽然 Ztest 框架提供了默认的 test_main() 函数，但有些应用程序可能希望提供自定义行为。当测试依赖于某种全局状态，而该状态无法复现，或者不重新启动进程就很难复现时，尤其如此。例如，上电时序就是这样一种状态。假设某块开发板的上电时序包含多个步骤，就可以编写一个使用 predicate 控制其运行时机的测试套件。这种情况下，test_main() 函数可以写成如下形式：

#include <zephyr/ztest.h>

#include "my_test.h"

void test_main(void)
{
     struct power_sequence_state state;

     /* Only suites that use a predicate checking for phase == PWR_PHASE_0 will run. */
     state.phase = PWR_PHASE_0;
     ztest_run_all(&state, false, 1, 1);

     /* Only suites that use a predicate checking for phase == PWR_PHASE_1 will run. */
     state.phase = PWR_PHASE_1;
     ztest_run_all(&state, false, 1, 1);

     /* Only suites that use a predicate checking for phase == PWR_PHASE_2 will run. */
     state.phase = PWR_PHASE_2;
     ztest_run_all(&state, false, 1, 1);

     /* Check that all the suites in this binary ran at least once. */
     ztest_verify_all_test_suites_ran();
}

ztest_run_all() 的签名为 ztest_run_all(const void *state, bool shuffle, int suite_iter, int case_iter)：

  • state - 指向传给每个套件 predicate 的全局状态的指针。

  • shuffle - 为 true 时，随机打乱套件和测试的运行顺序（需要 CONFIG_ZTEST_SHUFFLE）；为 false 时保持默认的字母数字顺序。

  • suite_iter - 每个测试套件重复执行的次数。

  • case_iter - 每个测试用例重复执行的次数。

在上面的示例中，每次调用都会按顺序运行一次匹配的套件，且不打乱顺序。

声明测试套件的最佳实践

twister 和其他验证工具需要获取 Zephyr ztest 测试镜像所提供的测试用例列表。

理由

这一切都是为了可追溯性。只有一个信号量测试应用程序是不够的，我们还需要证明所有 API 和功能都有对应的测试点，并能追溯到 API 的文档和功能需求。

其思路是让测试报告显示每个测试用例的结果：通过、失败、被阻塞或被跳过。只报告高层的测试应用程序过于笼统，尤其是在测试做了太多事情时。

其他问题：

  • 为什么不先用 CPP 预扫描再解析？或者在构建后扫描 ELF 文件？

    如果 C 预处理或构建因任何问题而失败，我们将无法得知其中的子用例。

  • 为什么不在 YAML 测试配置中声明它们？

    单独的测试用例描述文件比直接把信息保存在测试源文件中更难维护。修改时只需更新一个文件，可以避免重复。

压力测试框架

Zephyr 压力测试框架（Ztress）提供了一个在多个优先级上下文中执行用户函数的环境。可用于验证代码能否经受住抢占。该框架会跟踪每个上下文的执行次数和被抢占次数。执行可以有多种完成条件，例如超时、执行次数或被抢占次数。

该框架通过创建所请求数量的线程（每个线程的优先级不同），并可选地启动一个定时器来建立环境。对于每个上下文，会调用一个用户函数（每个上下文各不相同），然后该上下文休眠随机数量的系统节拍。框架会跟踪 CPU 负载并调整休眠时长，以达到更高的 CPU 负载。为了提高发生抢占的概率，系统时钟频率应相对较高。QEMU x86 上默认的 100 Hz 太低，建议将其提高到 100 kHz。

压力测试环境使用 ZTRESS_EXECUTE 设置和执行，该宏接受可变数量的参数。每个参数是一个上下文，由 ZTRESS_TIMER 或 ZTRESS_THREAD 宏指定。上下文按优先级从高到低的顺序指定。每个上下文通过提供最少执行次数和最少被抢占次数来指定完成条件。当所有条件都满足且执行完成时，会打印一份执行报告，然后该宏返回。注意，测试执行期间会定期打印进度报告。

通过指定测试超时（ztress_set_timeout()）或显式中止（ztress_abort()），可以提前结束执行。

用户函数的参数包含一个执行计数器，以及一个表示是否为最后一次执行的标志。

下面的示例演示了如何设置并运行 3 个上下文（其中一个是 k_timer 中断处理程序上下文）。完成条件设为每个上下文至少执行 10000 次，且最低优先级上下文至少被抢占 1000 次。此外还配置了超时：如果这些条件未满足，则在 10 秒后结束。每个上下文的最后一个参数是初始休眠时间，它会在整个测试过程中不断调整，以达到最高的 CPU 负载。

ztress_set_timeout(K_MSEC(10000));
ZTRESS_EXECUTE(ZTRESS_TIMER(foo_0, user_data_0, 10000, Z_TIMEOUT_TICKS(20)),
               ZTRESS_THREAD(foo_1, user_data_1, 10000, 0, Z_TIMEOUT_TICKS(20)),
               ZTRESS_THREAD(foo_2, user_data_2, 10000, 1000, Z_TIMEOUT_TICKS(20)));

配置

Ztress 的静态配置包括：

  • CONFIG_ZTRESS_MAX_THREADS - 支持的线程数。

  • CONFIG_ZTRESS_STACK_SIZE - 所创建线程的栈大小。

  • CONFIG_ZTRESS_REPORT_PROGRESS_MS - 测试进度报告的间隔。

期望

如果相关期望不满足，这些宏会继续执行测试，并在测试执行结束时使测试失败。期望不满足时，会打印当前的文件、行号和函数，以及失败原因和可选的消息，但会继续执行测试。如果配置 CONFIG_ZTEST_ASSERT_VERBOSE 为 0，期望只会打印文件和行号，从而减小测试二进制文件的大小。

zexpect_equal(buf->ref, 2, "Invalid refcount");

    Expectation failed at main.c:63: test_get_single_buffer: Invalid refcount (buf->ref not equal to 1337)
 FAIL - test_get_single_buffer in 0.0 seconds

自定义测试输出

将 CONFIG_ZTEST_TC_UTIL_USER_OVERRIDE 设为 "y"，并添加一个包含覆盖定义的 tc_util_user_override.h 文件，即可启用自定义。

在项目的 CMakeLists.txt 中添加 zephyr_include_directories(my_folder) 这一行，使 Zephyr 在构建时能够找到你的头文件。

可以覆盖哪些宏和/或定义，请参见 subsys/testsuite/include/zephyr/tc_util.h 文件。这些宏和定义会被如下代码块包围：

#ifndef SOMETHING
#define SOMETHING <default implementation>
#endif /* SOMETHING */

打乱测试顺序

默认情况下，测试会排序并按字母数字顺序运行。测试用例可能依赖于这一顺序。启用 CONFIG_ZTEST_SHUFFLE 可以随机打乱顺序。测试输出会显示失败测试所用的种子。对于 native simulator 构建，可以通过 --seed 将种子作为参数传给 twister。

重复测试

默认情况下，测试只执行一次。测试用例和测试套件可以多次执行。启用 CONFIG_ZTEST_REPEAT 可以多次执行测试。默认的重复倍数为 3，即每个测试套件执行 3 次，每个测试用例也执行 3 次。可以通过 Kconfig 选项 CONFIG_ZTEST_SUITE_REPEAT_COUNT 和 CONFIG_ZTEST_TEST_REPEAT_COUNT 更改该倍数。

选择测试

对于为 native simulator 构建的测试，可以使用命令行参数列出或选择要运行的测试。test 参数接受以逗号分隔的 suite::test 列表。可以用 * 代替测试名称，以运行某个套件中的所有测试。

例如

$ zephyr.exe -list
$ zephyr.exe -test="fixture_tests::test_fixture_pointer,framework_tests::test_assert_mem_equal"
$ zephyr.exe -test="framework_tests::*"
