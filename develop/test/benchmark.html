基准测试框架

Zephyr 基准测试框架提供周期级精确的性能测量。它将数据收集和统计计算自动化，为在整个 Zephyr 生态系统中评估执行指标提供了一种标准化方法。

概述

该框架通过提供以下功能，帮助发现性能退化并优化关键路径：

  • 标准化 API：与现有 ztest 约定保持一致的宏。

  • 统计分析：计算均值、标准差、标准误差以及最小值/最大值。

  • 开销补偿：包含一个对照测试，用于扣除基准测试框架自身的执行时间。每项报告的统计量都会以相同方式减去对照值，因此修正后的值是实数，通常不会与任何单次测量值相同。

配置

要使用基准测试框架，必须启用以下 Kconfig 选项：

CONFIG_ZTEST=y
CONFIG_ZTEST_BENCHMARK=y

用法

基准测试套件的定义方式与普通 ztest 测试套件类似：先使用 ZTEST_BENCHMARK_SUITE 定义套件，然后使用 ZTEST_BENCHMARK 或 ZTEST_BENCHMARK_TIMED 宏向套件中添加各个基准测试。

#include <zephyr/ztest.h>

ZTEST_BENCHMARK_SUITE(<test suite name>, <setup_fn>, <teardown_fn>);

标准基准测试

标准基准测试基于采样，即按指定次数执行测试并测量所用的总周期数。当你希望以周期数了解关键路径的原始 CPU 性能时，这种方式很有用。它可以揭示代码的效率，帮助找出 CPU 使用方面的瓶颈。这种基准测试方法适用于执行时间稳定、受 I/O 操作或上下文切换等外部因素影响不大的代码。

#include <zephyr/ztest.h>

ZTEST_BENCHMARK_SUITE(<suite name>, NULL, NULL);

ZTEST_BENCHMARK(<suite name>, <benchmark name>, <number of samples>, <setup_fn>, <teardown_fn>)
{
    /* Code to benchmark */
}

标准基准测试的流程如下：每次采样前调用 setup 函数，按指定的采样次数执行测试函数，每次采样后调用 teardown 函数。

定时基准测试

与标准基准测试不同，定时基准测试测量的是代码的执行时间而不是周期数。当代码的执行时间可能不固定，或者你希望测量实际耗时而不仅仅是关键路径的 CPU 周期数时，这种方式很有用。它能更全面地反映性能特征，尤其适用于涉及 I/O 操作、上下文切换或其他会在原始 CPU 性能之外影响执行时间的因素的代码。

ZTEST_BENCHMARK_TIMED(<suite name>, <benchmark name>, <time in ms>, <setup_fn>, <teardown_fn>)
{
      /* Code to benchmark */
}

标准基准测试注重隔离，而定时基准测试只执行一次 setup 和 teardown 函数，让测试函数在专门的时间窗口内持续热运行。这样得到的测量结果更贴近实际，因为其中包含了真实场景中的系统开销，例如中断、上下文切换和其他后台任务。

手动基准测试

标准基准测试和定时基准测试由框架自身计时，框架会在线程上下文中、在每次调用基准测试主体的前后各取一个时间戳。有些测量无法用这种方式表达，因为其起点和终点是在不同的执行上下文中捕获的，例如从触发中断到其 ISR 第一条指令的延迟，或者从 ISR 结束到被唤醒线程开始运行的延迟。

手动基准测试将循环、setup 和 teardown 保留在框架中，只把测量什么交由主体决定：主体用 ztest_benchmark_start() 和 ztest_benchmark_end() 将要测量的部分括起来。框架会计算并报告与标准基准测试相同的统计量。

ZTEST_BENCHMARK_MANUAL(<suite name>, <benchmark name>, <samples>, <setup_fn>, <teardown_fn>)
{
      prepare();

      ztest_benchmark_start();
      operation_under_test();
      ztest_benchmark_end();
}

这两个钩子都只记录时间戳，因此都可以在 ISR 中调用，测量区间也不必在同一个执行上下文中开始和结束。对于从中断到其所唤醒线程的延迟，由 ISR 标记开始，由线程结束该区间：

static void my_isr(const void *arg)
{
      ztest_benchmark_start();
}

ZTEST_BENCHMARK_MANUAL(<suite name>, isr_exit_latency, 1000, NULL, NULL)
{
      trigger_the_interrupt();

      ztest_benchmark_end();
}

采样值在主体返回后才计算，这样统计工作就不会在中断上下文中进行：更新统计量需要使用浮点运算，而并非所有架构都允许在 ISR 中使用浮点运算。如果某次迭代的主体没有标记任何区间，则该次迭代不产生采样值。

手动基准测试使用自己的对照值进行修正，而不是采样基准测试所用的对照值。手动区间的开销只有括住它的两个时间戳；而采样对照还会测量对基准测试主体的间接调用，这部分并不属于手动区间。如果区间的两端在两个不同的上下文中捕获，则两者的开销都无法准确对应，也没有任何对照值能够表达这种情况。

预热在这里的作用与采样基准测试完全相同：框架会额外运行主体 CONFIG_ZTEST_BENCHMARK_WARMUP 次并丢弃这些区间，同时保留第一次作为冷启动开销。主体无需区分这两个阶段，并且每次被测量的迭代之前所做的工作都与上一次完全相同。

理解结果

标准基准测试结果

<suite name> ###############################################
<benchmark name> ===========================================
   Sample size:<number of samples>, total cycles: <total amount of cycles>
   Mean(u): <mean cycles per sample>
   Standard deviation(s): <cycles>
   Standard Error(SE): <cycles>
   Min: <cycles> (run #<sample number>)
   Max: <cycles> (run #<sample number>)

统计指标

备注

CONFIG_ZTEST_BENCHMARK_OUTLIERS 会将标准误差这一行替换为超出中位数的幅度大于 CONFIG_ZTEST_BENCHMARK_OUTLIER_MARGIN_DIV 所允许范围的采样数，以及该数量所占的百分比。之所以需要这个余量，是因为计数器的分辨率会使基线分散在几个计数值上；如果没有余量，任何分布中大约一半的采样都会被报告出来。延迟分布通常是一条基线加上少量受干扰的运行，而不是来自同一个随机总体的样本；对这两者计算的标准误差暗示了一个任何单次执行都从未产生过的平均值。例如，一万次 760 个周期的运行加上一次 1240 个周期的运行，得到的标准误差为 0.048，看起来很精确但实际并非如此，而 1 / 10000 (0.010%) 则如实说明了发生的情况。只有报告内容会改变，标准误差仍保留其 CSV 列。

  • 均值（u）：每次采样所用的平均周期数。它给出一个代表预期执行开销的中心值。

  • 标准差（s）：衡量执行开销相对于均值的变化或波动程度。标准差越低，说明行为越确定、越一致。

  • 标准误差（SE）：估计样本均值可能与系统“真实”均值相差多远。它反映了测试的统计可靠性。SE 越低，对结果的置信度越高。

  • 最小值/最大值：观察到的最小和最大周期数，以及它们出现在哪一次采样中。

预热与冷启动开销

基准测试分为三个阶段：setup，然后是执行但不记录的 CONFIG_ZTEST_BENCHMARK_WARMUP 次迭代，最后是被测量的采样。预热设置适用于镜像中的每个基准测试。

无论预热设为多少，第一次执行总是不被记录。它在缓存、分支预测器和 TLB 都是冷状态下运行，可能比稳定状态慢一个数量级。框架不会丢弃这一信息，而是将其作为 冷启动开销 单独报告。两者回答的是不同的问题：一个操作第一次被执行时的开销，以及此后的开销。对于在启动时只运行一次某条路径的应用程序，关心的是前者。

正是将其排除在分布之外，分布的尾部才有意义。如果基准测试在两处都报告冷启动，那么冷启动将决定极端百分位数：在一万个采样中，最近秩法的 p99.99 是第二大的值，因此一次冷启动就会被当作稳定状态的尾部。

对于总开销与一次缓存未命中相当的微基准测试，将预热次数提高到超过这个程度会降低准确度；而采样数足够大时，最初几次迭代对均值没有可测量的影响，因此默认值零是合适的起点。当基准测试足够大、缓存状态会产生影响，并且你关心的是稳定状态时，再提高预热次数。

延迟百分位数

均值和标准误差描述的是平均值的估计精确程度。这对吞吐量来说是合适的问题，但对延迟则不然：实时系统的特征在于单次操作最坏能有多差，而这体现在分布的尾部，而不是均值附近。

启用 CONFIG_ZTEST_BENCHMARK_PERCENTILES 可以保留各个采样，并在常规统计量之外报告 min、p50、p90、p99、p99.9、p99.99 和 max。在 CSV 模式下，每个采样基准测试和手动基准测试都会额外输出一行 P；各列含义参见 CONFIG_ZTEST_BENCHMARK_OUTPUT_CSV。

这种差别在带有长尾的分布上最为明显。在有负载的系统上测量中断进入延迟，得到的均值为 1264 个周期，标准误差为 34，但这并不对应任何一次实际发生的中断：百分位数显示直到 p99 都是 1216 个周期，而超出 p99 后则为 25184 个周期。

百分位数必须能够由所采集的采样数分辨出来。p99 至少需要 100 个采样，p99.9 至少需要 1000 个，p99.99 至少需要 10000 个；采样数更少时，报告的值会退化为最大值。采样保存在一个包含 CONFIG_ZTEST_BENCHMARK_MAX_SAMPLES 个条目、每个条目 8 字节的缓冲区中，该缓冲区必须不小于最大基准测试的采样数。保留的是最先采集的那些采样，而不是整个运行过程的抽样，因此基于截断前缀计算的百分位数会遗漏缓冲区填满之后发生的情况，而长尾往往恰恰出现在那里。因此，超出缓冲区的基准测试完全不报告百分位数，并说明有多少个采样未能存入。

简而言之，所有指标的值都是越低越好。均值、最小值和最大值越低，表示原始性能越好；标准差和标准误差越低，表示性能越一致，因而越可靠。

定时基准测试结果

<benchmark name> ===============================================
   Samples: <Number of samples executed during the benchmark>
   Total Time: <Gross execution time>
   Work Time: <Net execution time> ns (Net)
   Ops/Sec: <average operations per second>
   Cycles/Op: <average cycles per operation>

统计指标

  • Total Time（总时间）：基准测试所有采样所用的总时间，包括开销。

  • Work Time（工作时间）：被测代码所用的总时间，不包括基准测试框架自身的开销。它能更准确地衡量被测代码的实际性能。

  • Ops/Sec（每秒操作数）：每秒可执行的操作（采样）数，由采样数除以净工作时间（单位为秒）得到。该指标对于了解被测代码的吞吐量特别有用。

  • Cycles/Op（每操作周期数）：每次操作平均所用的 CPU 周期数，由净周期数除以采样数得到。该指标反映了代码在 CPU 使用方面的效率。

一般来说，Ops/Sec 越高越好，因为它表示吞吐量更高；同样，Cycles/Op 越低越好。由于 Cycles/Op 和 Ops/Sec 指标源自相同的底层数据，它们是从不同角度反映同样的性能特征。Ops/Sec 高应对应 Cycles/Op 低，反之亦然。

基准测试输出选项

基准测试框架提供了多种输出基准测试数据结果的选项。默认情况下，结果以详细的人类可读格式打印，便于理解和解读。也可以启用 Kconfig 选项 CONFIG_ZTEST_BENCHMARK_OUTPUT_CSV，以 CSV 格式输出结果，便于脚本导入并做进一步分析。CSV 输出包含与详细输出相同的所有指标，但其格式更有利于自动化分析和报告。

标准基准测试的 csv 输出格式如下：

S,<suite name>,<benchmark name>,<sample size>,<total cycles>,<mean>,<stddev>,<stderr>,<min>,<min sample>,<max>,<max sample>

定时基准测试的 csv 输出格式如下：

T,<suite name>,<benchmark name>,<samples>,<total time>,<work time>,<ops/sec>,<cycles/op>

重要注意事项

  • 噪声：基准测试本身对系统噪声很敏感。为了获得尽可能准确的结果，请禁用可能干扰计时的不必要后台任务和中断。

  • 缓存预热：由于缓存未命中，基准测试的第一个采样往往会更慢，在采样数较少时可能使结果略有偏差。请选择足够多的采样数以减轻这种影响。

  • 使用 setup/teardown 函数：强烈 建议使用 setup 和 teardown 函数，尽可能将被测代码隔离出来。基准测试代码中过多的 setup/teardown 代码会引入噪声，对于较短的关键路径会 明显 扭曲结果。
