BabbleSim

BabbleSim 与 Zephyr

在 Zephyr 项目中，我们使用 Babblesim 模拟器测试 Zephyr 的部分无线电协议，包括 Bluetooth LE 协议栈、802.15.4 以及部分网络协议栈。

BabbleSim 是一个物理层模拟器，与 Zephyr 的 bsim 开发板 结合使用，可以模拟由 Bluetooth LE 和 15.4 设备组成的网络。以 bsim 开发板 为目标构建 Zephyr 时，会生成一个 Linux 可执行文件，其中包含应用程序、Zephyr OS 以及硬件模型。

当有无线电活动时，该 Linux 可执行文件会连接到 BabbleSim 物理层仿真，以模拟无线信道。

在 BabbleSim 文档中，可以找到有关如何 获取 和 构建 该模拟器的更多信息。在 nrf52_bsim、nrf5340bsim 和 nrf54l15bsim 开发板文档中，可以找到有关如何以这些开发板为目标构建 Zephyr 的更多信息，以及一些示例。

测试类型

无无线电活动的测试：使用 twister 运行 bsim 测试

bsim 开发板 可以在没有无线电活动的情况下使用，此时无需将其连接到物理层仿真。因此，这些目标开发板可以像 native_sim 一样配合 twister 使用，运行所有标准的 Zephyr twister 测试，但使用的是真实 SoC 硬件的模型及其驱动。

有无线电活动的测试

当有无线电活动时，BabbleSim 测试至少需要运行一个物理层仿真，并且大多数测试需要多个模拟设备。因此，这些测试通过为每个测试运行一个专用脚本来执行，该脚本会使用所需参数启动所需的模拟设备和物理层可执行文件，以及可能需要的其他工具。

要使用 twister 运行这些测试，应使用 bsim harness。

这些测试存放在 tests/bsim/ 目录中。

有关如何构建和运行这些测试，以及它们所遵循的约定，请查看以下各小节。

测试主要分为两组：

  • 自检式嵌入式应用程序/测试：部分模拟设备的应用程序在构建时加入了一些检查，由这些检查判定测试通过还是失败。这些嵌入式应用程序测试使用 bs_tests 系统报告通过或失败，并且在很多情况下会将多个测试构建到同一个二进制文件中。

  • 使用 EDTT 工具的测试：由 EDTT（Python）测试通过 RPC 机制控制嵌入式应用程序，并判定测试是否通过。目前，这些测试涵盖了 BT 认证测试套件中相当大的一部分。

有关不同测试类型与 BabbleSim 及 bsim 开发板之间关系的更多信息，请参阅 bsim 开发板测试一节。

测试覆盖率与 BabbleSim

由于 bsim 开发板 基于 POSIX 架构，可以方便地收集测试覆盖率信息。

更多信息请查看 覆盖率生成页面。注意，只需向 twister 传递 --coverage 选项，即可自动启用 CONFIG_COVERAGE 进行构建并生成覆盖率报告。

构建和运行测试

有关如何设置模拟器的说明，请查看 nrf52_bsim 页面。

可以使用 twister 构建和运行这些测试。要运行多设备测试，需要向 twister 传递选项 --fixture bsim_multi_test。

例如，在 ${ZEPHYR_BASE} 目录下，可以通过以下命令构建并运行其中一个 BT 测试：

twister -p nrf52_bsim/native -T tests/bsim/bluetooth/host/adv/chain/ --fixture bsim_multi_test

如果测试二进制文件已经构建好，也可以直接使用其单独的测试脚本运行测试。例如：

BOARD=nrf52_bsim/native tests/bsim/bluetooth/host/adv/chain/tests_scripts/adv_chain.sh

在调试或修复问题时，-n, --no-clean、--aggressive-no-clean 或 -b, --build-only 等 Twister 命令行选项 可能会很有用。

旧版批处理脚本

在加入 twister bsim harness 之前，构建和运行多设备 bsim 测试依赖于 tests/bsim/ 目录中的两个脚本：compile.sh 和 run_parallel.sh。CI 系统使用这些脚本构建所需的镜像并批量执行这些测试。它们也是供用户构建和执行自己测试的实用工具。这些脚本仍然可以使用，但建议用户过渡到使用 twister 和 tests.yaml 定义。

这些脚本需要设置一些环境变量。例如，可以在 Zephyr 根目录下运行：

# Build all the tests
${ZEPHYR_BASE}/tests/bsim/compile.sh

# Run them (in parallel)
RESULTS_FILE=${ZEPHYR_BASE}/myresults.xml \
   SEARCH_PATH=${ZEPHYR_BASE}/tests/bsim \
      ${ZEPHYR_BASE}/tests/bsim/run_parallel.sh

或者只构建和运行特定的子集，例如主机广播测试：

# Build the Bluetooth host advertising tests
${ZEPHYR_BASE}/tests/bsim/bluetooth/host/adv/compile.sh

# Run them (in parallel)
RESULTS_FILE=${ZEPHYR_BASE}/myresults.xml \
   SEARCH_PATH=${ZEPHYR_BASE}/tests/bsim/bluetooth/host/adv \
      ${ZEPHYR_BASE}/tests/bsim/run_parallel.sh

有关更多选项，以及如何使用该脚本批量运行测试的示例，请查看 run_parallel.sh 的帮助信息。

构建好测试所需的二进制文件后，可以直接使用其单独的测试脚本运行测试。

例如，可以通过以下命令构建网络测试所需的二进制文件

WORK_DIR=${ZEPHYR_BASE}/bsim_out ${ZEPHYR_BASE}/tests/bsim/net/compile.sh

然后直接运行其中一个测试：

${ZEPHYR_BASE}/tests/bsim/net/sockets/echo_test/tests_scripts/echo_test_802154.sh

约定

测试代码

适用于测试代码的约定，请参见 Bluetooth sample test。

测试镜像

添加新测试时，务必考虑能否将该测试纳入现有的镜像。每个镜像都会增加 CI 构建时间；而 bs_tests 系统允许多个测试共享一个镜像，并在运行时选择具体测试，只要它们的 Kconfig 和其他全局状态不冲突即可。

测试脚本

请遵循现有约定，不要设计一次性的定制运行器（例如 Python 脚本或另一层 shell 抽象）。

这样做的理由是：如果所有测试都以相同的方式、使用相同的变量等运行，维护者在因构建系统或兼容性变化而进行全树更新时会更容易、更快捷。

如果你对改进测试脚本有好的想法，请提交一个修改 所有 测试脚本的 PR，以便所有人受益并保持一致性。当然，你也可以先在 RFC issue 或 babblesim discord 频道中讨论。

以下划线（_）开头的脚本不会被自动发现和运行。它们可以作为主脚本的辅助函数，也可以用作本地开发工具，例如在本地构建和运行测试、调试等。

约定如下：

  • 每个测试由一个扩展名为 .sh 的 shell 脚本定义，存放在名为 tests_scripts/ 的子目录中。

  • 建议每个脚本文件只运行一个测试，这样可以在 CI 中更好地并行运行。

  • 脚本假定其所需的二进制文件已经构建好，脚本不应编译二进制文件。

  • 脚本会为每个模拟设备和物理层仿真生成相应的进程。

  • 如果测试通过，脚本必须向调用它的 shell 返回 0；如果测试失败，则返回非 0 值。

  • 每个测试都必须有唯一的仿真 ID，以便并行运行不同的测试。

  • 脚本和镜像都不应修改工作站文件系统中 ${BSIM_OUT_PATH}/results/<simulation_id>/ 或 /tmp/ 目录以外的内容。也就是说，它们不应遗留多余的文件。

  • 需要多次连续仿真的测试（例如模拟设备配对、断电，然后作为一次新的仿真重新上电），应为每个仿真阶段使用单独的仿真 ID，确保事后可以检查每个阶段的无线电活动。

  • 避免测试过长。如果测试运行时间超过 20 秒，请考虑能否将其拆分为多个单独的测试。

  • 如果测试耗时超过 6 秒，请将 EXECUTE_TIMEOUT 设为至少是实测运行时间 5 倍的值。

  • 不要将 EXECUTE_TIMEOUT 设为低于默认值的值。

  • 测试的输出不应过于冗长：输出预计少于一百行。请广泛使用 LOG_DBG()，但不要默认启用 DBG 日志级别。

  • 使用物理层仿真的测试脚本应将传给测试脚本的所有额外参数直接传递给 Phy 可执行文件。例如，可借此以检查模式（-c）运行 Phy，在该模式下，Phy 会验证上一次仿真与本次仿真产生的无线电流量完全相同。

  • 只有在测试确有需要时才覆盖随机种子。避免设计对随机种子变化过于敏感的测试。
