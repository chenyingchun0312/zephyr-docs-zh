应用程序开发

备注

本文档假定：

  • 应用程序目录 <app> 类似于 <home>/zephyrproject/app

  • 其 构建目录 为 <app>/build

这些术语的定义见下文。在 Linux/macOS 上，<home> 相当于 ~；在 Windows 上，它是 %userprofile%。

将应用程序放在工作区（<home>/zephyrproject）内，可以更方便地对其使用 west build 和其他命令。（不过，只要正确设置了 ZEPHYR_BASE，应用程序可以放在任何位置。）

概述

Zephyr 的构建系统基于 CMake。

构建系统以应用程序为中心，要求由基于 Zephyr 的应用程序发起 Zephyr 源代码的构建。应用程序构建控制应用程序和 Zephyr 本身的配置与构建过程，并将它们编译为单个二进制文件。

zephyr 主仓库包含 Zephyr 的源代码、配置文件和构建系统。在 zephyr 仓库旁边，通常还安装了各种 模块（外部项目），用于集成第三方源代码。

应用程序目录 中的文件将 Zephyr 和各模块与应用程序关联起来。该目录包含所有应用程序特定的文件，例如应用程序特定的配置文件和源代码。

下面是一个简单 Zephyr 应用程序中的文件：

<app>
├── CMakeLists.txt
├── app.overlay
├── prj.conf
├── VERSION
└── src
    └── main.c

这些内容是：

  • CMakeLists.txt：此文件告诉构建系统在哪里查找其他应用程序文件，并将应用程序目录与 Zephyr 的 CMake 构建系统关联起来。这种关联提供了 Zephyr 构建系统支持的各种功能，例如开发板特定的配置文件、在真实或仿真硬件上运行和调试编译后的二进制文件的能力等。

  • app.overlay：这是一个设备树覆盖文件（overlay），指定应用程序特定的更改，这些更改会应用到所构建的任意开发板的基础设备树上。设备树覆盖文件的用途通常是对应用程序所用的硬件进行某些配置。

    构建系统默认查找 app.overlay，但也可以添加更多设备树覆盖文件，并且构建系统还会搜索其他默认文件。

    关于设备树的更多信息，请参见 设备树。

  • prj.conf：这是一个 Kconfig 片段，为一个或多个 Kconfig 选项指定应用程序特定的值。这些应用程序设置与其他设置合并，生成最终配置。Kconfig 片段的用途通常是配置应用程序所用的软件功能。

    构建系统默认查找 prj.conf，但也可以添加更多 Kconfig 片段，并且构建系统还会搜索其他默认文件。

    更多信息请参见下文的 Kconfig 配置。

  • VERSION：包含多个版本信息字段的文本文件。这些字段可用于管理应用程序的生命周期，并在对应用程序镜像签名时自动提供应用程序版本。

    关于此文件及其用法的更多信息，请参见 应用程序版本管理。

  • main.c：源代码文件。应用程序通常包含用 C、C++ 或汇编语言编写的源文件。按照 Zephyr 的惯例，这些文件放在 <app> 下名为 src 的子目录中。

定义好应用程序后，使用 CMake 生成 构建目录，其中包含构建应用程序和 Zephyr 所需的文件，然后将它们链接成可以在开发板上运行的最终二进制文件。最简单的方法是使用 west build，也可以直接使用 CMake。应用程序的构建产物总是生成在单独的构建目录中：Zephyr 不支持“树内”（in-tree）构建。

以下各节介绍如何创建、构建和运行 Zephyr 应用程序，之后是更详细的参考资料。

应用程序类型

根据 <app> 所在的位置，Zephyr 应用程序分为三种基本类型：

应用程序类型

<app> 的位置

仓库应用程序

zephyr 仓库

工作区应用程序

安装了 Zephyr 的 west 工作区

独立应用程序

其他位置

下文将进一步讨论这些类型。要了解构建系统如何支持每种类型，请参见 Zephyr CMake 包。

Zephyr 仓库应用程序

位于 Zephyr west 工作区 中 zephyr 源代码仓库内的应用程序，称为 Zephyr 仓库应用程序。在下面的示例中，hello_world 示例 就是一个 Zephyr 仓库应用程序：

zephyrproject/
├─── .west/
│    └─── config
└─── zephyr/
     ├── arch/
     ├── boards/
     ├── cmake/
     ├── samples/
     │    ├── hello_world/
     │    └── ...
     ├── tests/
     └── ...

Zephyr 工作区应用程序

位于 工作区 内、但在 zephyr 仓库之外的应用程序，称为 Zephyr 工作区应用程序。在下面的示例中，app 就是一个 Zephyr 工作区应用程序：

zephyrproject/
├─── .west/
│    └─── config
├─── zephyr/
├─── bootloader/
├─── modules/
├─── tools/
├─── <vendor/private-repositories>/
└─── applications/
     └── app/

Zephyr 独立应用程序

位于 Zephyr 工作区 之外的 Zephyr 应用程序，称为 Zephyr 独立应用程序。在下面的示例中，app 就是一个 Zephyr 独立应用程序：

<home>/
├─── zephyrproject/
│     ├─── .west/
│     │    └─── config
│     ├── zephyr/
│     ├── bootloader/
│     ├── modules/
│     └── ...
│
└─── app/
     ├── CMakeLists.txt
     ├── prj.conf
     └── src/
         └── main.c

创建应用程序

在 Zephyr 中，可以使用参考工作区应用程序，也可以手动创建应用程序。

使用参考工作区应用程序

example-application Git 仓库包含一个参考 工作区应用程序。建议在按以下各节所述创建自己的应用程序时，将其作为参考。

example-application 仓库演示了如何使用几项常用功能，例如：

  • 自定义 开发板移植

  • 自定义 设备树绑定

  • 自定义 设备驱动

  • 持续集成（CI）设置，包括使用 twister

  • 自定义 west 扩展命令

example-application 的基本用法

在现有 Zephyr 工作区中开始使用 example-application 仓库的最简单方法是按以下步骤操作：

cd <home>/zephyrproject
git clone https://github.com/zephyrproject-rtos/example-application my-app

上面的目录名 my-app 是任意的，可以根据需要更改。现在可以进入该目录，按需修改其中的内容。由于使用的是现有 Zephyr 工作区，可以使用 west build 或其他任何 west 命令进行构建、烧录和调试。

example-application 的高级用法

还可以将 example-application 仓库作为起点，构建自己定制的基于 Zephyr 的软件发行版。这样可以做到：

  • 移除不需要的 Zephyr 模块

  • 添加自己的其他自定义仓库

  • 用自己的版本覆盖 Zephyr 提供的仓库

  • 与他人分享成果并进一步协作

example-application 仓库包含一个 west.yml 文件，因此它也是一个 west 清单仓库。按以下步骤操作，使用它创建一个新的定制工作区：

cd <home>
mkdir my-workspace
cd my-workspace
git clone https://github.com/zephyrproject-rtos/example-application my-manifest-repo
west init -l my-manifest-repo

这将创建一个采用 T2 拓扑 的新工作区，以 my-manifest-repo 作为清单仓库。名称 my-workspace 和 my-manifest-repo 是任意的，可以根据需要更改。

接下来，定制清单仓库。克隆时，该仓库的初始内容与 example-application 的内容相同。然后可以按需编辑 my-manifest-repo/west.yml，随意更改其中的仓库集合。关于如何根据需要在工作区中添加或移除不同仓库，清单导入 中有许多示例。对其他文件也可以进行任何所需的更改。

满意之后，可以运行：

west update

这样工作区就可以使用了。

如果将得到的 my-manifest-repo 仓库推送到其他地方，就可以与他人分享工作成果。例如，假设将该仓库推送到 https://git.example.com/my-manifest-repo，其他人就可以运行以下命令搭建相同的工作区：

west init -m https://git.example.com/my-manifest-repo my-workspace
cd my-workspace
west update

此后，可以通过向所用的仓库推送更改，并根据需要更新 my-manifest-repo/west.yml 来添加、移除仓库或更改其内容，从而在共享软件上协作。

手动创建应用程序

可以按照以下步骤从零开始创建一个基本的应用程序目录。不过，以 example-application 仓库或 Zephyr 的某个 Samples and Demos 作为起点可能会更容易。

  1. 创建应用程序目录。

    例如，在 Unix shell 或 Windows cmd.exe 提示符中：

    mkdir app

    警告

    不支持在路径中任何位置含有空格的目录中构建 Zephyr 或创建应用程序。因此，Windows 路径 C:\Users\YourName\app 可以正常使用，而 C:\Users\Your Name\app 则不行。

  2. 创建源代码文件。

    建议将所有应用程序源代码放在名为 src 的子目录中。这样更容易区分项目文件和源文件。

    接着上一个示例，输入：

    cd app
mkdir src

  3. 将应用程序源代码放在 src 子目录中。在本例中，假设创建了一个名为 src/main.c 的文件。

  4. 在 app 目录中创建名为 CMakeLists.txt 的文件，内容如下：

    cmake_minimum_required(VERSION 3.28.0)

find_package(Zephyr)
project(my_zephyr_app)

target_sources(app PRIVATE src/main.c)

    注意：

    • CMake 要求调用 cmake_minimum_required()。下一行的 Zephyr 包也会调用它。如果 CMake 的版本低于 CMakeLists.txt 中的版本或 Zephyr 包中的版本号，CMake 将报错退出。

    • find_package(Zephyr) 引入 Zephyr 构建系统，该构建系统会创建一个名为 app 的 CMake 目标（参见 Zephyr CMake 包）。将源文件添加到此目标，即可将它们纳入构建。Zephyr 包会将 Zephyr-Kernel 定义为一个 CMake 项目，并启用对 C、CXX、ASM 语言的支持。

    • project(my_zephyr_app) 定义应用程序的 CMake 项目。它必须在 find_package(Zephyr) 之后调用，以免干扰 Zephyr 的 project(Zephyr-Kernel)。

    • target_sources(app PRIVATE src/main.c) 用于将源文件添加到 app 目标。它必须位于定义该目标的 find_package(Zephyr) 之后。可以使用 target_sources() 添加任意数量的文件。

  5. 为应用程序创建至少一个 Kconfig 片段（通常命名为 prj.conf），并在其中设置应用程序所需的 Kconfig 选项值。请参见 Kconfig 配置。如果不需要设置任何 Kconfig 选项，请创建一个空文件。

  6. 配置应用程序所需的设备树覆盖文件，通常放在名为 app.overlay 的文件中。请参见 设置设备树覆盖文件。

  7. 设置可能需要的其他文件，例如 twister 配置文件、持续集成文件、文档等。

重要的构建系统变量

可以使用许多变量来控制 Zephyr 构建系统。本节介绍每个 Zephyr 开发者都应了解的最重要的变量。

备注

变量 BOARD、CONF_FILE 和 DTC_OVERLAY_FILE 可以通过 3 种方式提供给构建系统（按优先级排序）：

  • 在调用 west build 或 cmake 时，通过 -D 命令行开关作为参数传入。如果有多个覆盖文件，应使用引号，例如 "file1.overlay;file2.overlay"

  • 作为 环境变量。

  • 在 CMakeLists.txt 中使用 set(<VARIABLE> <VALUE>) 语句设置

  • ZEPHYR_BASE：构建系统使用的 Zephyr 基础目录变量。find_package(Zephyr) 会自动将其设置为 CMake 缓存变量。不过，也可以将 ZEPHYR_BASE 设置为环境变量，以强制 CMake 使用特定的 Zephyr 安装。

  • BOARD：选择应用程序构建时用于默认配置的开发板。内置开发板请参见 支持的开发板和扩展板，关于添加开发板支持的信息请参见 开发板移植指南。

  • CONF_FILE：指定一个或多个 Kconfig 配置片段文件的名称。多个文件名可以用空格或分号分隔。每个文件都包含用于覆盖默认配置值的 Kconfig 配置值。

    更多信息请参见 初始配置。

  • EXTRA_CONF_FILE：附加的 Kconfig 配置片段文件。多个文件名可以用空格或分号分隔。如果希望保留 CONF_FILE 的默认值，同时“混入”一些额外的配置选项，这个变量会很有用。

  • DTC_OVERLAY_FILE：要使用的一个或多个设备树覆盖文件。多个文件可以用分号分隔。示例请参见 设置设备树覆盖文件，关于设备树和 Zephyr 的信息请参见 设备树简介。

  • EXTRA_DTC_OVERLAY_FILE：要使用的附加设备树覆盖文件。多个文件可以用分号分隔。如果希望保留 DTC_OVERLAY_FILE 的默认值，同时“混入”一些额外的覆盖文件，这个变量会很有用。

  • SHIELD：请参见 扩展板（shield）

  • ZEPHYR_MODULES：一个 CMake list，包含应用程序构建中应使用的附加目录（含源代码、Kconfig 等）的绝对路径。详见 模块（外部项目）。如果设置了此变量，它必须是要使用的所有模块的完整列表，因为构建系统不会再自动从 west 获取任何模块。

  • EXTRA_ZEPHYR_MODULES：与 ZEPHYR_MODULES 类似，但这些模块会被添加到通过 west 找到的模块列表中，而不是替换该列表。

  • FILE_SUFFIX：可选的文件名后缀，会添加到 Kconfig 片段和设备树覆盖文件的文件名上（如果带后缀的文件存在；否则回退到不带后缀的文件名）。详见 文件后缀。

  • KCONFIG_WARNING_AS_ERROR：将每个 Kconfig 警告都视为错误，包括默认只打印出来的警告。详见 将 Kconfig 警告视为错误。

备注

可以使用 Zephyr 构建配置 CMake 包 来共享这些变量的通用设置。

应用程序 CMakeLists.txt

每个应用程序都必须有一个 CMakeLists.txt 文件。该文件是构建系统的入口，即顶层文件。最终的 zephyr.elf 镜像同时包含应用程序和内核库。

本节介绍可以在 CMakeLists.txt 中进行的部分操作。请务必按顺序执行这些步骤。

  1. 如果只想为一块开发板构建，请在新的一行中添加应用程序所用开发板配置的名称。例如：

    set(BOARD qemu_x86)

    关于可用开发板的更多信息，请参阅 支持的开发板和扩展板。

    Zephyr 构建系统按以下顺序检查来确定 BOARD 的值（一旦找到 BOARD 值，CMake 就不再继续检查列表中后面的项）：

    • 由 CMake 缓存确定的、之前使用过的任何值优先级最高。这样可以确保不会使用与构建配置阶段所设置的值不同的 BOARD 值来运行构建。

    • 接下来检查并使用在 CMake 命令行上（直接或通过 west build 间接）以 -DBOARD=YOUR_BOARD 给出的任何值。

    • 如果设置了 环境变量 BOARD，则接着使用其值。

    • 最后，如果按照本步骤所述在应用程序的 CMakeLists.txt 中设置了 BOARD，则使用该值。

  2. 如果应用程序使用的配置文件不是通常的 prj.conf，请添加相应的行，将 CONF_FILE 变量设置为这些文件。如果给出多个文件名，请用单个空格或分号分隔。如果不想在单一位置设置 CONF_FILE，可以使用 CMake 列表以模块化方式组合配置片段文件。例如：

    set(CONF_FILE "fragment_file1.conf")
list(APPEND CONF_FILE "fragment_file2.conf")

    更多信息请参见 初始配置。

  3. 如果应用程序使用设备树覆盖文件，可能需要设置 DTC_OVERLAY_FILE。请参见 设置设备树覆盖文件。

  4. 如果应用程序有自己的内核配置选项，请在应用程序的 CMakeLists.txt 所在的同一目录中创建 Kconfig 文件。

    详细的 Kconfig 文档请参见 手册中的 Kconfig 部分。

    一种（不太常见的）高级用例是：应用程序有自己独特的配置 选项，这些选项根据构建配置的不同而设置为不同的值。

    如果只是想为现有的 Zephyr 配置选项设置应用程序特定的 值，请参阅上文对 CONF_FILE 的说明。

    按如下结构组织 Kconfig 文件：

    # SPDX-License-Identifier: Apache-2.0

mainmenu "Your Application Name"

# Your application configuration options go here

# Sources Kconfig.zephyr in the Zephyr root directory.
#
# Note: All 'source' statements work relative to the Zephyr root directory (due
# to the $srctree environment variable being set to $ZEPHYR_BASE). If you want
# to 'source' relative to the current Kconfig file instead, use 'rsource' (or a
# path relative to the Zephyr root).
source "Kconfig.zephyr"

    备注

    source 语句中的环境变量会被直接展开，因此不需要定义 option env="ZEPHYR_BASE" 这种 Kconfig“中转”（bounce）符号。如果使用了这种符号，它必须与环境变量同名。

    更多信息请参见 Kconfig 扩展。

    Kconfig 文件放在应用程序目录中时会被自动检测到；如果将 CMake 变量 KCONFIG_ROOT 设置为绝对路径，也可以从其他位置找到该文件。

  5. 在 上述步骤所添加的所有行之后，另起一行指定应用程序依赖 Zephyr：

    find_package(Zephyr)
project(my_zephyr_app)

    备注

    如果需要支持通过显式设置环境变量 ZEPHYR_BASE 来强制使用特定的 Zephyr 安装，可以使用 find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})。Zephyr 中的所有示例都支持环境变量 ZEPHYR_BASE。

  6. 现在将所有应用程序源文件添加到“app”目标库中，每个文件占一行，如下所示：

    target_sources(app PRIVATE src/main.c)

下面是一个简单的 CMakeList.txt 示例：

set(BOARD qemu_x86)

find_package(Zephyr)
project(my_zephyr_app)

target_sources(app PRIVATE src/main.c)

CMake 属性 HEX_FILES_TO_MERGE 利用 Kconfig 和 CMake 提供的应用程序配置，可以将外部构建的 hex 文件与构建 Zephyr 应用程序时生成的 hex 文件合并。例如：

set_property(GLOBAL APPEND PROPERTY HEX_FILES_TO_MERGE
    ${app_bootloader_hex}
    ${PROJECT_BINARY_DIR}/${KERNEL_HEX_NAME}
    ${app_provision_hex})

CMakeCache.txt

CMake 使用 CMakeCache.txt 文件作为持久化的键/值字符串存储，用于在多次运行之间缓存各种值，包括编译和构建选项以及库依赖项的路径。在空的构建文件夹中运行 CMake 时会创建此缓存文件。

关于 CMakeCache.txt 文件的更多详细信息，请参见官方的 CMake Cache 文档。

应用程序配置

应用程序配置目录

Zephyr 会使用应用程序配置目录中的配置文件，但通过前面所述参数（例如 CONF_FILE、EXTRA_CONF_FILE、DTC_OVERLAY_FILE 和 EXTRA_DTC_OVERLAY_FILE）以绝对路径提供的文件除外。

应用程序配置目录由变量 APPLICATION_CONFIG_DIR 定义。

APPLICATION_CONFIG_DIR 由以下来源之一设置，按优先级从高到低排列。

  1. 如果用户通过 -DAPPLICATION_CONFIG_DIR=<path> 或在 find_package(Zephyr) 之前在 CMake 文件中指定了 APPLICATION_CONFIG_DIR，则使用该文件夹作为应用程序的配置目录。

  2. 应用程序的源代码目录。

Kconfig 配置

应用程序配置选项通常在应用程序目录中的 prj.conf 里设置。例如，可以通过以下赋值启用 C++ 支持：

CONFIG_CPP=y

查看 现有示例 是入门的好方法。

关于设置 Kconfig 配置值的详细文档，请参见 设置 Kconfig 配置值。同一页面上的 初始配置 一节解释了初始配置是如何得出的。配置选项的完整列表请参见 Kconfig 搜索。与 Kconfig 选项相关的安全信息请参见 加固工具。

手册中 Kconfig 部分 的其他页面也值得一读，尤其是计划添加新配置选项时。

实验性功能

Zephyr 是一个持续开发中的项目，因此有些功能仍处于开发周期的早期阶段。这类功能会在其 Kconfig 标题中标记为 [EXPERIMENTAL]。

可以使用 CONFIG_WARN_EXPERIMENTAL 设置，在启用了任何实验性功能时于 CMake 配置阶段发出警告。

CONFIG_WARN_EXPERIMENTAL=y

例如，如果选项 CONFIG_FOO 是实验性的，那么同时启用它和 CONFIG_WARN_EXPERIMENTAL 后，构建应用程序时会在 CMake 配置阶段打印以下警告：

warning: Experimental symbol FOO is enabled.

设备树覆盖文件

请参见 设置设备树覆盖文件。

文件后缀

Zephyr 应用程序可能希望用同一套代码库支持多种配置，以对应不同的构建或产品变体，而这些变体需要不同的 Kconfig 选项和设备树配置。为了更好地进行此类配置，Zephyr 在配置应用程序时提供了 FILE_SUFFIX 选项，它可以自动附加到文件名上。该选项适用于 Kconfig 片段和开发板覆盖文件，并带有回退机制：如果带后缀的文件不存在，则改用不带这些后缀的文件。

以如下项目布局为例：

<app>
├── CMakeLists.txt
├── prj.conf
├── prj_mouse.conf
├── boards
│   ├── native_sim.overlay
│   └── qemu_cortex_m3_mouse.overlay
└── src
    └── main.c

  • 如果在未定义 FILE_SUFFIX 的情况下正常为 native_sim 构建，将使用 prj.conf 和 boards/native_sim.overlay。

  • 如果在未定义 FILE_SUFFIX 的情况下正常为 qemu_cortex_m3 构建，将使用 prj.conf，且不使用任何应用程序设备树覆盖文件。

  • 如果在 FILE_SUFFIX 设置为 mouse 的情况下为 native_sim 构建，将使用 prj_mouse.conf 和 boards/native_sim.overlay （由于不存在 native_sim_mouse.overlay 文件，因此回退到 native_sim.overlay）。

  • 如果在 FILE_SUFFIX 设置为 mouse 的情况下为 qemu_cortex_m3 构建，将使用 prj_mouse.conf 和 boards/qemu_cortex_m3_mouse.overlay。

应用程序特定代码

应用程序特定的源代码文件通常添加到应用程序的 src 目录中。如果应用程序添加了大量文件，开发者可以将它们分组放到 src 下的子目录中，层级深度可按需设定。

应用程序特定的源代码不应使用内核保留给自身使用的符号名称前缀。更多信息请参见 命名约定。

第三方库代码

可以在应用程序的 src 目录之外构建库代码，但重要的是应用程序代码和库代码必须面向相同的应用程序二进制接口（ABI）。在大多数架构上，都有控制目标 ABI 的编译器标志，因此库和应用程序必须共用某些编译器标志。此外，让胶水代码能够访问 Zephyr 内核头文件也可能很有用。

为了更方便地集成第三方组件，Zephyr 构建系统定义了一些 CMake 函数，使应用程序构建脚本能够获取 zephyr 的编译器选项。这些函数在 cmake/modules/extensions.cmake 中定义并有文档说明，遵循 zephyr_get_<type>_<format> 命名约定。

以下变量通常需要导出给第三方构建系统。

  • CMAKE_C_COMPILER、CMAKE_AR。

  • ARCH 和 BOARD，以及几个标识 Zephyr 内核版本的变量。

samples/application_development/external_lib 是一个演示其中部分功能的示例项目。

构建应用程序

Zephyr 构建系统将应用程序的所有组件编译并链接为单个应用程序镜像，该镜像可以在仿真硬件或真实硬件上运行。

与其他任何基于 CMake 的系统一样，构建过程 分两个阶段 进行。首先，使用 cmake 命令行工具并指定一个生成器，生成构建文件（也称为构建系统）。该生成器决定构建系统在第二阶段使用的原生构建工具。第二阶段运行原生构建工具，实际构建源文件并生成镜像。要进一步了解这些概念，请参阅 CMake 官方文档中的 CMake introduction。

Zephyr 中的默认构建工具是 Zephyr 的元工具 west，它在后台调用 cmake 及底层构建工具（ninja 或 make）；不过如果愿意，也可以选择直接调用 cmake。在 Linux 和 macOS 上，可以在 make 和 ninja 生成器（即构建工具）之间选择；而在 Windows 上需要使用 ninja，因为该平台不支持 make。为简单起见，本指南通篇使用 ninja。如果选择使用 west build 构建应用程序，请注意它在底层默认使用 ninja。

例如，下面为 reel_board 构建 Hello World 示例：

使用 west：

# From the root of the zephyr repository
west build -b reel_board samples/hello_world

使用 CMake 和 ninja：

# From the root of the zephyr repository
# Use cmake to configure a Ninja-based buildsystem:
cmake -Bbuild -GNinja -DBOARD=reel_board samples/hello_world

# Now run the build tool on the generated build system:
ninja -Cbuild

在 Linux 和 macOS 上，也可以使用 make 代替 ninja 进行构建：

使用 west：

  • 如果只想使用一次 make，请在 west build 命令行中添加 -- -G"Unix Makefiles"；示例请参见 west build 文档。

  • 如果想从现在起默认使用 make，请运行 west config build.generator "Unix Makefiles"。

直接使用 CMake：

# From the root of the zephyr repository
# Use cmake to configure a Make-based buildsystem:
cmake -Bbuild -DBOARD=reel_board samples/hello_world

# Now run the build tool on the generated build system:
make -Cbuild

基础

  1. 进入应用程序目录 <app>。

  2. 输入以下命令，为命令行参数中指定的开发板构建应用程序的 zephyr.elf 镜像：

    Using west:

    west build -b <board>

    Using CMake and ninja:

    mkdir build && cd build

# Use cmake to configure a Ninja-based buildsystem:
cmake -GNinja -DBOARD=<board> ..

# Now run the build tool on the generated build system:
ninja

    如有需要，可以使用 CONF_FILE 参数，以另一个 .conf 文件中指定的配置设置来构建应用程序。这些设置会覆盖应用程序的 .config 文件或其默认 .conf 文件中的设置。例如：

    Using west:

    west build -b <board> -- -DCONF_FILE=prj.alternate.conf

    Using CMake and ninja:

    mkdir build && cd build
cmake -GNinja -DBOARD=<board> -DCONF_FILE=prj.alternate.conf ..
ninja

    如上一节所述，也可以选择永久设置开发板和配置：导出环境变量 BOARD 和 CONF_FILE，或者在 CMakeLists.txt 中使用 set() 语句设置它们的值。此外，west 还允许 设置默认开发板。

构建目录的内容

使用 Ninja 生成器时，构建目录如下所示：

<app>/build
├── build.ninja
├── CMakeCache.txt
├── CMakeFiles
├── cmake_install.cmake
├── rules.ninja
└── zephyr

构建目录中最值得注意的文件有：

  • build.ninja，调用它即可构建应用程序。

  • zephyr 目录，它是所生成构建系统的工作目录，大多数生成的文件都在这里创建和存放。

运行 ninja 后，以下构建输出文件会写入构建目录的 zephyr 子目录中。（这 不是 Zephyr 基础目录；Zephyr 基础目录包含 Zephyr 源代码等，已在上文介绍。）

  • .config，包含构建应用程序所用的配置设置。

    备注

    每次更新配置时，上一版本的 .config 会保存为 .config.old。这是为了方便，因为比较新旧两个版本往往很有用。

  • 各种目标文件（.o 文件和 .a 文件），包含编译后的内核和应用程序代码。

  • zephyr.elf，包含最终合并的应用程序和内核二进制文件。也支持其他二进制输出格式，例如 .hex 和 .bin。

重新构建应用程序

持续测试更改通常能使应用程序开发最快。随着应用程序变得越来越复杂，经常重新构建应用程序可以减轻调试的痛苦。在对应用程序的源文件、CMakeLists.txt 文件或配置设置进行任何重大更改后，重新构建并测试通常是个好主意。

重要

Zephyr 构建系统只重新构建应用程序镜像中可能受更改影响的部分。因此，重新构建应用程序通常比首次构建快得多。

有时构建系统会因为未能重新编译一个或多个必要的文件而无法正确重新构建应用程序。可以按以下步骤强制构建系统从头重新构建整个应用程序：

  1. 在主机上打开终端控制台，进入构建目录 <app>/build。

  2. 根据想使用 west 还是直接使用 cmake，输入以下命令之一，删除应用程序生成的文件，但保留包含应用程序当前配置信息的 .config 文件。

    west build -t clean

    或

    ninja clean

    或者，输入以下命令之一删除 所有 生成的文件，包括那些包含应用程序针对相应开发板类型的当前配置信息的 .config 文件。

    west build -t pristine

    或

    ninja pristine

    如果使用 west，可以利用它的功能，在需要时自动 使构建目录恢复全新状态。

  3. 按照上文 构建应用程序 中的步骤正常重新构建应用程序。

为开发板版本构建

Zephyr 构建系统支持为同一块开发板指定多个只有细微差别的硬件版本。使用版本可以让开发板支持文件对开发板配置做小幅调整，而无需为每个版本重复编写 创建开发板目录 中所述的所有文件。

要为特定版本构建，请使用 <board>@<revision> 或 <board>@<revision>/<qualifiers>，而不是单纯的 <board> 或 <board>/<qualifiers>。例如：

使用 west：

west build -b nrf9160dk@0.14.0/nrf9160/ns

使用 CMake 和 ninja：

mkdir build && cd build
cmake -GNinja -DBOARD=nrf9160dk@0.14.0/nrf9160/ns ..
ninja

关于开发板是否有多个版本、支持哪些版本的详细信息，请查看开发板的文档。

以某个开发板版本为目标时，CMake 配置阶段会打印当前生效的版本，如下所示：

-- Board: plank, Revision: 1.5.0

运行应用程序

应用程序镜像可以在真实开发板或仿真硬件上运行。

在开发板上运行

Zephyr 支持的大多数开发板都可以使用 west flash 烧录编译好的二进制文件，即将二进制文件复制到开发板并运行。按照以下说明在真实硬件上烧录并运行应用程序：

  1. 按照 构建应用程序 中的说明构建应用程序。

  2. 确保开发板已连接到主机，通常通过 USB 连接。

  3. 在构建目录 <app>/build 中运行以下控制台命令，烧录编译好的 Zephyr 镜像并在开发板上运行：

    west flash

Zephyr 构建系统与开发板支持文件集成，使用硬件特定的工具将 Zephyr 二进制文件烧录到硬件上，然后运行它。

每次运行 flash 命令时，应用程序都会重新构建并再次烧录。

如果开发板支持不完整，可能无法通过 Zephyr 构建系统进行烧录。如果收到提示烧录支持不可用的错误信息，请查阅 开发板的文档，了解如何烧录开发板的更多信息。

备注

在 Linux 上开发时，通常需要安装开发板特定的 udev 规则，以便以非 root 用户身份通过 USB 访问开发板。如果烧录失败，请查阅开发板的文档，了解是否需要这样做。

在仿真器中运行

Zephyr 内置了对 QEMU 仿真器的支持。它允许在实际目标硬件上加载和运行应用程序之前（或代替这样做），以虚拟方式运行和测试应用程序。

在 Windows 上所需的其他步骤，请查看 入门指南之外。

按照以下说明通过 QEMU 运行应用程序：

  1. 按照 构建应用程序 中的说明，为某个 QEMU 开发板构建应用程序。

    例如，可以将 BOARD 设置为：

    • qemu_x86，仿真在基于 x86 的开发板上运行

    • qemu_cortex_m3，仿真在基于 ARM Cortex M3 的开发板上运行

  2. 在构建目录 <app>/build 中运行以下控制台命令之一，在 QEMU 中运行 Zephyr 二进制文件：

    west build -t run

    或

    ninja run

  3. 按 Ctrl A, X 停止在 QEMU 中运行应用程序。

    应用程序停止运行，终端控制台提示符重新出现。

每次执行 run 命令时，应用程序都会重新构建并再次运行。

备注

如果安装了 Zephyr SDK，run 目标默认使用 SDK 中的 QEMU 二进制文件。要使用其他版本的 QEMU，请 设置环境变量 QEMU_BIN_PATH，将其指向要使用的 QEMU 二进制文件的路径。

备注

可以在目标名称后附加 _<emulator> 来选择特定的仿真器，例如对 QEMU 使用 west build -t run_qemu 或 ninja run_qemu。

自定义开发板、设备树和 SOC 定义

如果所开发的开发板或平台尚未得到 Zephyr 支持，可以将开发板、设备树和 SOC 定义添加到应用程序中，而无需将它们添加到 Zephyr 源代码树中。

支持树外开发板和 SOC 开发所需的结构，与 Zephyr 源代码树中维护开发板和 SOC 的方式类似。使用这种结构，在完成初步开发后，将平台相关的工作提交到 Zephyr 上游源代码树会容易得多。

使用以下结构，将自定义开发板添加到应用程序或专用仓库中：

boards/
soc/
CMakeLists.txt
prj.conf
README.rst
src/

其中 boards 目录存放要构建的开发板：

.
├── boards
│   └── vendor
│       └── my_custom_board
│           ├── doc
│           │   └── img
│           └── support
└── src

soc 目录存放 SOC 代码。也可以有由 Zephyr 源代码树中已有的 SOC 支持的开发板。

开发板

在 boards 下为 my_custom_board 使用厂商名称作为文件夹名称（如果要提交到 Zephyr 上游，该名称必须与 dts/bindings/vendor-prefixes.txt 中的厂商前缀一致；如果不是厂商开发板，则使用 others）。

文档（位于 doc/ 下）和支持文件（位于 support/ 下）是可选的，但提交到 Zephyr 时需要提供。

my_custom_board 的内容应遵循适用于所有 Zephyr 开发板的相同准则，并提供以下文件:

board.yml
my_custom_board_defconfig
my_custom_board.dts
my_custom_board.yaml
board.cmake
board.h
CMakeLists.txt
doc/
Kconfig.my_custom_board
Kconfig.defconfig
support/

开发板结构就绪后，可以通过 -DBOARD_ROOT 参数向 CMake 构建系统指定自定义开发板信息的位置，以该开发板为目标构建应用程序：

使用 west：

west build -b <board name> -- -DBOARD_ROOT=<path to boards>

使用 CMake 和 ninja：

cmake -Bbuild -GNinja -DBOARD=<board name> -DBOARD_ROOT=<path to boards> .
ninja -Cbuild

这将使用自定义的开发板配置，并在应用程序目录中生成 Zephyr 二进制文件。

也可以在应用程序的 CMakeLists.txt 文件中定义 BOARD_ROOT 变量。请务必在使用 find_package(Zephyr ...) 引入 Zephyr 样板代码 之前 进行定义。

备注

在 CMakeLists.txt 中指定 BOARD_ROOT 时，必须提供绝对路径，例如 list(APPEND BOARD_ROOT ${CMAKE_CURRENT_SOURCE_DIR}/<extra-board-root>)。使用 -DBOARD_ROOT=<board-root> 时，绝对路径和相对路径均可使用。相对路径被视为相对于应用程序目录。

备注

使用 sysbuild 时，BOARD_ROOT 必须在模块或 sysbuild 的 CMakeLists.txt 文件中定义，详见 配置 sysbuild 内部状态。

SOC 定义

与开发板支持类似，其结构与 Zephyr 源代码树中维护 SOC 的方式类似，例如：

soc
└── st
    └── stm32
        ├── common
        └── stm32l0x

文件 soc/Kconfig 会在 Kconfig 中创建顶层菜单 SoC/CPU/Configuration Selection。

可以使用 CMake 变量 SOC_ROOT 将树外 SoC 定义添加到此菜单中。该变量包含一个以分号分隔的目录列表，这些目录中包含 SoC 支持文件。

按照上述结构，可以添加以下文件，将更多 SoC 加载到菜单中。

soc
└── st
    └── stm32
        └── stm32l0x
            ├── Kconfig
            ├── Kconfig.soc
            └── Kconfig.defconfig

上述 Kconfig 文件可以描述 SoC，也可以加载其他 SoC Kconfig 文件。

在此结构中加载 stm32l0 特定 Kconfig 文件的示例：

soc
└── st
    └── stm32
        ├── Kconfig.soc
        └── stm32l0x
            └── Kconfig.soc

可以在 st/stm32/Kconfig.soc 中写入以下内容来实现：

rsource "*/Kconfig.soc"

SOC 结构就绪后，可以通过 -DSOC_ROOT 参数向 CMake 构建系统指定自定义平台信息的位置，以该平台为目标构建应用程序：

使用 west：

west build -b <board name> -- -DSOC_ROOT=<path to soc> -DBOARD_ROOT=<path to boards>

使用 CMake 和 ninja：

cmake -Bbuild -GNinja -DBOARD=<board name> -DSOC_ROOT=<path to soc> -DBOARD_ROOT=<path to boards> .
ninja -Cbuild

这将使用自定义的平台配置，并在应用程序目录中生成 Zephyr 二进制文件。

关于在模块的 zephyr/module.yml 文件中设置 SOC_ROOT 的信息，请参见 构建设置。

也可以在应用程序的 CMakeLists.txt 文件中定义 SOC_ROOT 变量。请务必在使用 find_package(Zephyr ...) 引入 Zephyr 样板代码 之前 进行定义。

备注

在 CMakeLists.txt 中指定 SOC_ROOT 时，必须提供绝对路径，例如 list(APPEND SOC_ROOT ${CMAKE_CURRENT_SOURCE_DIR}/<extra-soc-root>。使用 -DSOC_ROOT=<soc-root> 时，绝对路径和相对路径均可使用。相对路径被视为相对于应用程序目录。

设备树定义

设备树目录树位于 APPLICATION_SOURCE_DIR、BOARD_DIR 和 ZEPHYR_BASE 中，但也可以通过创建如下目录树来添加更多的目录树（即 DTS_ROOT）:

include/
dts/common/
dts/arm/
dts/
dts/bindings/

其中 'arm' 应改为相应的架构。每个目录都是可选的。binding 目录包含绑定文件，其他目录包含可以从设备树源文件中包含的文件。

目录结构就绪后，可以通过 CMake 缓存变量 DTS_ROOT 指定其位置来使用它：

使用 west：

west build -b <board name> -- -DDTS_ROOT=<path to dts root>

使用 CMake 和 ninja：

cmake -Bbuild -GNinja -DBOARD=<board name> -DDTS_ROOT=<path to dts root> .
ninja -Cbuild

也可以在应用程序的 CMakeLists.txt 文件中定义该变量。请务必在使用 find_package(Zephyr ...) 引入 Zephyr 样板代码 之前 进行定义。

备注

在 CMakeLists.txt 中指定 DTS_ROOT 时，必须提供绝对路径，例如 list(APPEND DTS_ROOT ${CMAKE_CURRENT_SOURCE_DIR}/<extra-dts-root>。使用 -DDTS_ROOT=<dts-root> 时，绝对路径和相对路径均可使用。相对路径被视为相对于应用程序目录。

设备树源文件会经过 C 预处理器处理，因此可以包含位于 DTS_ROOT 目录中的文件。按照惯例，设备树包含文件的扩展名为 .dtsi。

也可以通过 CMake 缓存变量 DTS_EXTRA_CPPFLAGS 指定预处理指令，使用预处理器来控制设备树文件的内容：

使用 west：

west build -b <board name> -- -DDTS_EXTRA_CPPFLAGS=-DTEST_ENABLE_FEATURE

使用 CMake 和 ninja：

cmake -Bbuild -GNinja -DBOARD=<board name> -DDTS_EXTRA_CPPFLAGS=-DTEST_ENABLE_FEATURE .
ninja -Cbuild
