Pytest

pytest harness 用于在 Zephyr 测试中执行 pytest 测试套件。以下选项适用于 pytest harness：

pytest_root: <pytest 测试路径列表>（默认为 pytest）

指定测试场景开始运行时需要执行的 pytest 目录、文件或子测试列表。默认的 pytest 目录为 pytest。pytest 运行结束后，Twister 会根据 pytest 报告判断测试场景是通过还是失败。其中的环境变量和 Zephyr 模块目录变量会被展开（参见 使用模块目录变量展开路径）。下面给出了一组有效的 pytest 根路径示例：

harness_config:
  pytest_root:
    - "pytest/test_shell_help.py"
    - "../shell/pytest/test_shell.py"
    - "/tmp/test_shell.py"
    - "~/tmp/test_shell.py"
    - "$ZEPHYR_BASE/samples/subsys/testsuite/pytest/shell/pytest/test_shell.py"
    - "$ZEPHYR_HAL_NORDIC_MODULE_DIR/tests/pytest/test_hal.py"  # path inside a module
    - "pytest/test_shell_help.py::test_shell2_sample"  # select pytest subtest
    - "pytest/test_shell_help.py::test_shell2_sample[param_a]"  # select pytest parametrized subtest
pytest_args: <参数列表>（默认为空）

指定要传递给 pytest 的附加参数列表，例如：pytest_args: [‘-k=test_method’, ‘--log-level=DEBUG’]。注意，可以多次传递 --pytest-args，从而向 pytest 传递多个参数。

pytest_dut_scope: <function|class|module|package|session>（默认为 function）

dut 和 shell 这两个 pytest fixture 的共享范围。如果范围设为 function，则 Python 脚本中的每个测试用例都会启动一次 DUT；如果为 session 范围，则 DUT 只启动一次。

下面是一个包含 pytest harness_config 选项的 yaml 文件示例。如果未指定 pytest_root，将使用默认的 pytest_root 名称 "pytest"。请参考 samples/subsys/testsuite/pytest/ 中的示例。

common:
  harness: pytest
tests:
  pytest.example.directories:
    harness_config:
      pytest_root:
        - pytest_dir1
        - $ENV_VAR/samples/test/pytest_dir2
  pytest.example.files_and_subtests:
    harness_config:
      pytest_root:
        - pytest/test_file_1.py
        - test_file_2.py::test_A
        - test_file_2.py::test_B[param_a]
required_devices: <所需设备条目列表>（默认为空）

为多 DUT 测试场景指定所需的额外 DUT。每个条目配置一台额外的设备，该设备会与主 DUT 一同被预留和烧录。空条目 {} 会预留第二台设备，其平台和应用程序与主 DUT 相同。

多 DUT 测试支持硬件设备测试和 native_sim 仿真，不支持 QEMU。对于仿真目标，Twister 会自动创建所需的占位 DUT 条目，无需硬件映射。对于硬件测试，需要提供硬件映射文件（--hardware-map），并为每台所需设备提供一个匹配的条目。详情请参见 多 DUT 测试支持 一节。

每个条目支持以下可选字段：

platform: <string>（可选，默认为当前测试的平台）

该所需设备使用的平台。如果未指定，则使用与主 DUT 相同的平台。

application: <string>（可选，默认为当前测试的应用程序）

要烧录到该所需设备上的测试应用程序 ID。指定后，Twister 会单独构建该应用程序，并在烧录前将其构建目录分配给预留的 DUT。如果未指定，则使用与主 DUT 相同的应用程序。

它使用与 required_applications 相同的机制。

path: <string>（可选）

Twister 搜索 application 所指定应用程序的目录路径。可以是绝对路径，也可以是相对于测试 YAML 文件所在目录的路径。其中的环境变量和 Zephyr 模块目录变量会被展开（参见 使用模块目录变量展开路径）。如果未指定，Twister 会在引用方测试 YAML 文件所在的目录中搜索。

fixture: <fixture 名称列表>（可选，默认为空）

预留设备上必须具备的 fixture 名称列表。详情请参见 Fixture。

fixture 支持使用 name:param 语法附加一个可选的参数后缀（例如 io_adapter:channel_a）。当主 DUT 的某个 fixture 带有参数时，Twister 会用该参数值来匹配所需设备：只有该 fixture 名称带有 相同参数 的设备才会被考虑。这样可以确保物理上相连的 DUT 对（例如两块连接在一起、并在硬件映射中以相同 fixture 参数注册的开发板）总是被一起预留，而不会与无关的开发板混用。

成对配置的硬件映射条目示例：

- id: "01"
  platform: nrf52840dk/nrf52840
  serial: /dev/ttyACM0
  fixtures:
    - io_adapter:channel_a
- id: "02"
  platform: nrf52840dk/nrf52840
  serial: /dev/ttyACM1
  fixtures:
    - io_adapter:channel_a

当主 DUT 和所需设备都设置了 fixture: [io_adapter] 时，Twister 只会选择共享同一 channel_a 参数的开发板，从而保证选中物理上配对的开发板。

包含多个所需设备的配置示例：

tests:
  # Two DUTs, same platform and application
  multidut.basic:
    harness_config:
      required_devices:
        - {}
  # Second DUT fixed to a specific platform
  multidut.fixed_platform:
    harness_config:
      required_devices:
        - platform: nrf52840dk/nrf52840
  # Second DUT flashed with a different application
  multidut.other_app:
    harness_config:
      required_devices:
        - application: multidut.basic
