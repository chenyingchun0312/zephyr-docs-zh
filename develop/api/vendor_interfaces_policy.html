厂商专用 API 放置策略

概述

本策略规定了厂商专用的硬件功能在 Zephyr 项目中必须如何贡献、组织和对外提供。它确保 Zephyr 的公共 API 层面保持稳定，确保厂商扩展不会绕过标准的 API 生命周期，并为可能跨厂商通用的特性提供演进为通用驱动类别的清晰路径。

厂商专用 API 不得作为 Zephyr 公共接口对外提供，除非它们满足纳入 Zephyr 正式 API 生命周期（实验性 → 稳定 → 已弃用）所需的条件。本质上与单一 SoC 或厂商绑定的特性，必须封装在该厂商的 SoC 目录中。

本策略为贡献者和维护者提供了一致的决策模型。

指导原则

  • Zephyr 公共 API 不得包含厂商专用接口。

    放在 include/zephyr/ 下的接口应当经历标准的 API 生命周期演进。无法满足这一演进要求的厂商专用接口，不得作为 Zephyr 公共 API 对外提供。

  • 优先采用通用方案，而不是厂商专用方案。

    当某项硬件特性适用于多个厂商，或将来可能适用于多个厂商时，应将其实现为现有驱动类别的一部分，或实现为新的跨厂商驱动类别。

  • 厂商专用特性必须封装起来。

    仅属于某个厂商的机制应放在该厂商的平台命名空间（SoC、开发板等）中。

  • 必须保留演进的可能。

    放置方式不得妨碍日后将厂商专用实现提升为可移植的 Zephyr 驱动类别。

决策流程

添加新的硬件功能或厂商专用行为时，贡献者必须按顺序遵循以下决策树：

  • 该特性在逻辑上是否扩展了某个现有驱动类别？

    如果是，则扩展现有类别；不要创建厂商专用 API。

  • 该特性能否成为跨厂商的驱动类别？

    如果该硬件概念并非明显为单一厂商所独有，或者类似于很可能在多种架构中出现的模式，则创建新的驱动类别。

  • 该功能是否明显属于厂商专用，且不太可能通用化？

    这种情况下，将头文件和实现都放在以下位置：

    soc/<vendor>/..

    这样可以实现真正的封装和长期可维护性，并在移除某个 SoC 时干净地删除相关代码。

    厂商专用代码的头文件应放在 soc/<vendor>/include 下，代码应放在 soc/<vendor>/common 或 soc/<vendor>/<series> 中。

    此类接口属于厂商私有和/或内部接口，用于支持其特定硬件，并将受到严格审查，以避免形成厂商专属的特性孤岛。

    由于这些接口是厂商内部和/或私有的，使用它们的应用程序不应期望其生命周期或向后兼容性有任何保证。

允许位置汇总

  1. 扩展现有驱动类别时

  • 位置：

    include/zephyr/drivers/<class>.h
drivers/<class>/

  • 适用情况：

    该功能适合或扩展了某个现有类别。

  1. 对现有驱动类别的厂商专用扩展

  • 位置：

    include/zephyr/drivers/<class>/
drivers/<class>/

  • 适用情况：

    该特性是对现有类别的厂商专用扩展，但其核心概念并非单一厂商独有，将来可能被标准化。

  1. 创建新的驱动类别（跨厂商）

  • 位置：

    include/zephyr/drivers/<class>.h
drivers/<class>/

  • 适用情况：

    该特性有理由适用于多个厂商，或可能演进为通用抽象。

  1. 厂商专用、SoC 本地代码（厂商独有特性的默认做法）

  • 位置：

    厂商专用代码的头文件应放在 soc/<vendor>/include 下，代码应放在 soc/<vendor>/common 或 soc/<vendor>/<series> 中。

  • 适用情况：

    该特性为某个厂商或 SoC 所独有，并不打算作为公共 API。
