API 生命周期

使用 Zephyr API 的开发者需要知道，在多长时间内可以相信某个 API 在未来的版本中不会改变。同时，维护和扩展 Zephyr API 的开发者需要能够引入尚未完全经过验证的新 API，并在旧 API 不再是最佳选择或不再受底层平台支持时将其淘汰。

所有 API 及其成熟度级别的最新列表，请参阅 API 概览 页面。

实验性

实验性 API 表示某项特性是最近引入的，在未来版本中可能会改变或被移除。欢迎试用，并通过 开发者邮件列表 向社区提供反馈。

以下要求适用于所有新 API：

  • API（用法）文档，说明其设计和假设、使用方法、当前实现的局限，以及在适当情况下的未来发展方向。

  • 引入 API 时，应同时提供该 API 的至少一个实现（对于外设 API，这对应一个驱动）

  • 至少一个使用该新 API 的示例（可以只在单个开发板上构建）

引入新的实验性 API 时，应在定义该 API 的头文件中标注 API 版本。实验性 API 的次版本号不得超过一（0.1.z）。（参见 API 概览）

外设 API（与硬件相关）

为新的外设或驱动子系统引入 API（带文档的公共头文件）时，必须对 API 进行评审，评审由来自不同厂商代表组成的架构工作组主导。

当 API 在不同硬件平台上至少有两个实现时，应将其提升为 unstable。

不稳定

该 API 正在趋于稳定，但尚未经过足够的实际测试，不能被视为稳定。该 API 被认为具有通用性，可以在不同的硬件平台上使用。

当 API 的状态变为不稳定 API 时，应在定义该 API 的头文件中标注 API 版本。不稳定 API 的次版本号应大于一（0.y.z | y > 1）。（参见 API 概览）

备注

变更不会另行公告。

外设 API（与硬件相关）

当 API 在不同硬件平台上至少有两个实现时，应将其从 experimental 提升为 unstable。

与硬件无关的 API

对于与硬件无关的 API，需要有多个应用程序使用它，才能将其从 experimental 提升为 unstable。

稳定

该 API 已被证明令人满意，但底层代码的清理可能会带来细微变更。在合理的情况下会保持向后兼容。

满足以下要求后，API 可以被声明为 stable：

  • 为新 API 编写覆盖率达到 100% 的测试用例

  • 代码中有完整的文档。所有公共接口都应编写文档，并可在在线文档中查阅。

  • 该 API 已投入使用，并且至少在 2 个开发版本中可用

  • 稳定 API 随时可以获得向后兼容的更新、缺陷修复和安全修复。

要将 API 声明为 stable，需要遵循以下步骤：

  1. 必须提交一个 PR（拉取请求），修改 API 概览 表中的相应条目

  2. 必须向 devel 邮件列表发送邮件，宣布该 API 升级请求

  3. 该 PR 必须提交到下一次 Zephyr Architecture meeting 上讨论，如无异议，该 PR 将被合并

当 API 的状态变为稳定 API 时，应在定义该 API 的头文件中标注 API 版本。稳定 API 的主版本号应大于或等于一（x.y.z | x >= 1）。（参见 API 概览）

引入破坏性的 API 变更

如上所述，稳定 API 力求在整个生命周期内保持向后兼容。然而，在某些情况下，实现这一目标会阻碍技术进步，或者如果不给 API 及其实现的维护带来不合理的负担，根本无法实现。

破坏性的 API 变更是指迫使用户修改现有代码才能保持应用程序当前行为的变更。需要重新编译应用程序（而不修改应用程序本身）不被视为破坏性的 API 变更。

为了限制和控制会打破向后兼容承诺的变更的引入，每当认为有必要进行此类变更时，必须遵循以下步骤，项目才会接受该变更：

  1. 必须在 GitHub 上提交一个 RFC issue，内容如下：

    Title:     RFC: Breaking API Change: <subsystem>
Contents:  - Problem Description:
             - Background information on why the change is required
           - Proposed Change (detailed):
             - Brief description of the API change
           - Detailed RFC:
             - Function call changes
             - Device Tree changes (source and bindings)
             - Kconfig option changes
           - Dependencies:
             - Impact to users of the API, including the steps required
               to adapt out-of-tree users of the API to the change

    RFC issue 可以不对变更进行文字描述，而是链接到一个以代码形式包含这些变更的 PR。

  2. RFC issue 必须打上 GitHub 的 Breaking API Change 标签

  3. RFC issue 必须提交到下一次 Zephyr Architecture meeting 上讨论

  4. 必须向 devel 邮件列表发送一封邮件，主题与 RFC issue 标题相同，并附上指向该 RFC issue 的链接

随后，RFC 会通过 issue 评论获得反馈，也会在 Zephyr 架构会议上讨论，相关方和整个社区都有机会对其进行详细讨论。

最后，如果第一步中尚未提交，则必须在 GitHub 上提交一个 PR。由提出变更的人决定是同时提交 RFC 和 PR，还是等到 RFC 获得足够共识、能够确信实现会被接受之后再进行实现。该 PR 必须包含以下内容：

  • 与 RFC issue 一致的标题

  • 指向 RFC issue 的链接

  • 对 API 的实际变更

    • 对 API 头文件的变更

    • 对 API 实现的变更

    • 对相关 API 文档的变更

    • 对设备树源文件和绑定的变更

  • 使源码树内该 API 的使用者适配此变更所需的修改。视该任务的范围而定，这可能需要相应维护者的额外帮助

  • 在下一个即将发布版本的发布说明的“API Changes”部分中添加一个条目

  • API、Breaking API Change 和 Release Notes 标签，以及其他适用的标签

  • 如果 RFC 尚未在 Zephyr Architecture meeting 上讨论并达成一致，则添加 Architecture Review 标签

完成上述步骤后，提案的结果将取决于相应子系统的维护者是否批准该 PR。与其他任何 PR 一样，作者可以请求在 Zephyr TSC meeting 上讨论，甚至最终进行投票。

如果该 PR 被合并，则必须向 devel 和 user 邮件列表发送邮件，告知此变更。

API 版本应进行变更，以表明存在向后不兼容的变更。这通过递增主版本号来实现（X.y.z | X > 1）。它也可以包含次版本和修订级别的变更。递增主版本号时，修订号和次版本号必须重置为 0。（参见 API 概览）

备注

破坏性的 API 变更将在迁移指南中列出并说明。

已弃用

备注

不稳定 API 可以随时移除，无需经过弃用阶段。API 的弃用和移除会在发布说明的“API Changes”部分公告。

弃用现有 API 的要求如下：

  • 弃用期（稳定 API）：2 个版本。API 需要在至少两个完整版本中被标记为已弃用。例如，如果某个 API 首次在 4.0 版本中被弃用，那么最早可以在 4.2 版本中移除。在架构工作组认定的特殊情况下，API 可以更早被弃用。

  • 弃用时需要做的工作：

    • 标记为已弃用。可以借助编译器本身实现（函数声明使用 __deprecated，宏定义使用 __DEPRECATED_MACRO），也可以引入一个 Kconfig 选项（通常名称中包含 DEPRECATED 一词），启用后将 API 恢复为之前的形式

    • 为弃用编写文档

    • 在下一个即将发布版本的发布说明的“API Changes”中写明该弃用

    • 需要修改使用了该已弃用 API 的代码，移除对该 API 的使用

    • 变更必须是原子的，并且可二分查找（bisectable）

    • 在跟踪已弃用 API 移除工作的相应版本 GitHub issue 中添加一个条目。在本例中，即 4.2 版本对应的 issue。

在弃用等待期间，API 处于 deprecated 状态。Zephyr 维护者会在 docs.zephyrproject.org 上跟踪已弃用 API 的使用情况，并帮助开发者迁移代码。Zephyr 会持续给出警告：

  • API 文档会告知用户该 API 已被弃用。

  • 在构建时尝试使用已弃用的 API 会在控制台输出警告。

已退役

在此阶段，API 被移除。

目标移除时间为宣布弃用后的 2 个版本。Zephyr 维护者会决定何时真正移除该 API：这取决于有多少开发者已成功从已弃用的 API 迁移，以及移除该 API 的紧迫程度。

如果可以移除该 API，就会将其移除。维护者会移除相应的文档，并通过常规渠道告知移除情况：发布说明、邮件列表、GitHub issue 和 PR。

如果还不能移除该 API，维护者会继续支持迁移工作，并更新路线图，力争在下一个版本中移除该 API。
