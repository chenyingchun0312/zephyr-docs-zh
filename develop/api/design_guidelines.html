API 设计准则

Zephyr 的开发和演进是集体协作的成果。为了简化维护和改进工作，开发新功能或新接口时应遵循一些通用策略。

所有公共 API 都必须使用 Doxygen 编写文档。详见 Doxygen 风格指南。

使用回调

许多 API 会将回调作为参数或配置结构体的成员传入。指定回调签名时应遵循以下策略：

  • 第一个参数应是指向与该回调关系最密切的对象的指针。对于设备驱动，它应是 const struct device *dev。对于库函数，它可以是指向提供回调时所引用的另一个对象的指针。

  • 接下来的参数应是与本次回调调用相关的附加信息，例如通道标识符、新的状态值，和/或消息指针及其后的消息长度。

  • 最后一个参数应是 void *user_data 指针，用于携带上下文，使共享的回调函数能够找到处理该回调所需的其他资料。

如果回调本身是通过一个会被嵌入到另一个结构体中的结构体提供的，则可以例外地不把 user_data 作为最后一个参数。这种情况的一个例子是 gpio_callback，它通常定义在同时定义该回调函数的代码所特有的数据结构中。在这些情况下，回调可以通过 CONTAINER_OF 间接访问更多上下文。

示例

  • 系统定时器告警触发时调用的 k_timer_expiry_t 满足以下要求:

    void handle_timeout(struct k_timer *timer)
{ ... }

    这里的假设与 gpio_callback 一样：定时器嵌入在一个可通过 CONTAINER_OF 访问的结构体中，该结构体可为回调提供更多上下文。

  • 计数器设备告警触发时调用的 counter_alarm_callback_t 满足以下要求:

    void handle_alarm(const struct device *dev,
                  uint8_t chan_id,
                  uint32_t ticks,
                  void *user_data)
{ ... }

    它提供了更完整的有用信息，包括哪个计数器通道超时以及超时发生时的计数器值，还提供了用户上下文；根据用户需要，该上下文可以是也可以不是用于注册该回调的 counter_alarm_cfg。

条件性数据与 API

API 和库可能提供一些在 RAM 或代码大小方面开销较大、但属于可选的特性，即某些应用程序不需要它们也能实现。此类特性的例子包括 capturing a timestamp（捕获时间戳）或 providing an alternative interface（提供替代接口）。开发者必须与社区协商，确定是否通过 Kconfig 选项控制这些特性的启用。

当某个特性被确定为可选时，应遵循以下做法。

  • 仅在该特性启用时才访问的数据，应在结构体或联合体声明中通过 #ifdef CONFIG_MYFEATURE 有条件地包含。这样可以减少不需要该功能的应用程序的内存占用。

  • 仅在选项启用时才可用的函数，其声明应无条件提供。在描述中添加说明，指出该函数仅在指定特性启用时可用，并按名称引用所需的 Kconfig 符号。如果函数被使用但未启用，则函数定义应被排除在编译之外，这样对不受支持的 API 的引用会产生链接时错误。

  • 如果特性专用代码独立位于一个没有其他内容的源文件中，则应在 CMakeLists.txt 中有条件地包含该文件:

    zephyr_sources_ifdef(CONFIG_MYFEATURE foo_funcs.c)

  • 如果特性专用代码属于一个还包含其他内容的源文件，则应使用 #ifdef CONFIG_MYFEATURE 有条件地处理特性专用代码。

关于如何确保条件性代码对 Doxygen 可见并包含在公共 API 文档中，详见 条件编译代码。

返回码

API 的实现（例如用于访问外设的 API）可能只实现了最低限度运行所需的部分函数。需要区分不受支持的 API 与未实现或可选的 API：

  • 受支持但未实现的 API 应返回 -ENOSYS。

  • 硬件不支持的可选 API 也应实现，此时的返回码应为 -ENOTSUP。

  • 如果 API 已实现，但调用中请求的特定选项组合无法由该实现满足，则调用应返回 -ENOTSUP。（例如，在只支持边沿触发中断的硬件上请求电平触发的 GPIO 中断）
