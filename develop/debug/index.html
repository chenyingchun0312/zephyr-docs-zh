调试

应用程序调试

本节是使用 QEMU 开始调试应用程序的快速上手参考。本节的大部分内容已在 QEMU 和 GNU_Debugger 参考手册中介绍过。

在这份快速参考中，你会找到一些快捷方式、特定的环境变量和参数，帮助你快速搭建调试环境。

调试在 QEMU 中运行的应用程序，最简单的方法是使用 GNU 调试器，并通过 QEMU 在开发系统中设置一个本地 GDB 服务器。

调试时需要一个 ELF 二进制镜像。构建系统会在构建目录中生成该镜像。默认情况下，内核二进制文件名为 zephyr.elf。可以通过 CONFIG_KERNEL_BIN_NAME 修改该名称。

GDB 服务器

我们将使用标准的 1234 TCP 端口打开一个 GDB 服务器实例。可以把该端口号改为最适合开发环境的端口。实现方式有多种，每种方式都会启动一个 QEMU 实例，处理器在启动时处于暂停状态，并有一个 GDB 服务器实例在监听连接。

直接运行 QEMU

可以让 QEMU 在开始执行任何代码之前监听“gdb 连接”，以便对其进行调试。

qemu -s -S <image>

会将 Qemu 设置为监听 1234 端口，并等待 GDB 连接。

上面使用的选项含义如下：

  • -S 启动时不启动 CPU；需要在监视器中输入 'c'。

  • -s 是 -gdb tcp::1234 的简写：在 TCP 端口 1234 上打开 GDB 服务器。

通过 ninja 运行 QEMU

在应用程序的构建目录中运行以下命令：

ninja debugserver

QEMU 会将控制台输出写入通过 CMake 在 ${QEMU_PIPE} 中指定的路径，通常是构建目录下的 qemu-fifo。运行期间可以用 tail -f qemu-fifo 监视该文件。

通过 west 运行 QEMU

在项目根目录下运行以下命令：

west build -t debugserver_qemu

QEMU 会将控制台输出写入调用 west 的终端。

配置 gdbserver 监听设备

Kconfig 选项 CONFIG_QEMU_GDBSERVER_LISTEN_DEV 控制监听设备，它可以是 TCP 端口号，也可以是字符设备的路径。GDB 9.0 及更新版本还支持 Unix 域套接字。

如果未设置该选项，QEMU 调用中将不包含 -s 或 -gdb 参数。此时可以使用 shell 环境变量 QEMU_EXTRA_FLAGS 传入你自己的监听设备配置。

GDB 客户端

运行 gdb 并输入以下命令连接到服务器：

$ path/to/gdb path/to/zephyr.elf
(gdb) target remote localhost:1234
(gdb) dir ZEPHYR_BASE

备注

请替换为适合你系统的 ZEPHYR_BASE。

可以使用本地 GDB 配置文件 .gdbinit，在每次运行时初始化 GDB 实例。.gdbinit 通常放在主目录中，但也可以配置 GDB 从其他位置加载，包括调用 gdb 的目录。下面的示例文件执行与上文相同的配置：

target remote localhost:1234
dir ZEPHYR_BASE

其他界面

GDB 提供一个在终端中运行、基于 curses 的界面。调用 gdb 时传入 --tui 选项，或在 gdb 中输入 tui enable 命令即可。

备注

你开发系统上的 GDB 版本可能不支持 --tui 选项。请确保使用 SDK 中的 GDB 二进制文件，且它与构建该二进制文件所用的工具链相对应。

最后，下面的命令使用 GDB 的图形前端 DDD 连接到 GDB 服务器。该命令会从 ELF 二进制文件（本例中为 zephyr.elf）加载符号表。

ddd --gdb --debugger "gdb zephyr.elf"

这两条命令都会执行 gdb。命令名称可能因所用的工具链和交叉开发工具而异。

你的开发系统默认可能没有安装 ddd。请按照系统说明进行安装。例如，在 Ubuntu 系统上使用 sudo apt-get install ddd。

调试

按照上述配置，连接 GDB 客户端时，应用程序会停在系统启动处。你可以像直接在 gdb 中运行应用程序时一样设置断点、单步执行代码等。

备注

与直接在 GDB 中运行本机应用程序不同，应用程序运行时 gdb 不会打印系统控制台输出。如果连接客户端后只执行 continue，应用程序会运行，但看起来什么都没有发生。请按上文所述查看控制台输出。

使用 Eclipse 调试

概述

CMake 支持生成项目描述文件，该文件可以导入 Eclipse 集成开发环境（IDE）并用于图形化调试。

GNU MCU Eclipse plug-ins 提供了一种机制，可在 Eclipse 中使用 pyOCD、Segger J-Link 和 OpenOCD 调试工具调试 ARM 项目。

下面的教程演示如何在 Windows 中使用 Eclipse 和 pyOCD 调试 Zephyr 应用程序。本教程假定你已安装 GCC ARM Embedded 工具链和 pyOCD。

搭建 Eclipse 开发环境

  1. 下载并安装 Eclipse IDE for C/C++ Developers。

  2. 在 Eclipse 中安装 GNU MCU Eclipse plug-ins：打开菜单 Window->Eclipse Marketplace...，搜索 GNU MCU Eclipse，然后在匹配的结果上点击 Install。

  3. 配置 pyOCD GDB 服务器的路径：打开菜单 Window->Preferences，导航到 MCU，然后设置 Global pyOCD Path。

生成并导入 Eclipse 项目

  1. 按照 GNU Arm Embedded 中的说明设置 GNU Arm Embedded 工具链。

  2. 进入 Zephyr 源码树之外的某个文件夹来构建应用程序。

    # On Windows
cd %userprofile%

    备注

    如果构建目录是源码目录的子目录（Zephyr 中通常如此），CMake 会发出警告：

    “构建目录是源码目录的子目录。

    Eclipse 对此支持不佳。强烈建议使用与源码目录同级的构建目录。”

  3. 使用 CMake 配置应用程序并用 ninja 构建。注意 -G"Eclipse CDT4 - Ninja" 参数指定了不同的 CMake 生成器。除了常规的 ninja 构建文件之外，它还会生成 Eclipse 项目描述文件 .project。

    Using west:

    west build -b frdm_k64f samples/synchronization -- -G"Eclipse CDT4 - Ninja"

    Using CMake and ninja:

    cmake -Bbuild -GNinja -DBOARD=frdm_k64f -G"Eclipse CDT4 - Ninja" samples/synchronization
ninja -Cbuild

  4. 在 Eclipse 中导入生成的项目：打开菜单 File->Import...，选择 Existing Projects into Workspace 选项。在 Select root directory: 选项中浏览到应用程序的构建目录。在找到的项目列表中勾选你的项目，然后点击 Finish 按钮。

创建调试器配置

  1. 打开菜单 Run->Debug Configurations...。

  2. 选择 GDB PyOCD Debugging，点击 New 按钮，然后配置以下选项：

    • 在 Main 选项卡中：

      • Project：my_zephyr_app@build

      • C/C++ Application：zephyr/zephyr.elf

    • 在 Debugger 选项卡中：

      • pyOCD Setup

        • Executable path（可执行文件路径）：$pyocd_path\$pyocd_executable

        • 取消勾选“Allocate console for semihosting”

      • Board Setup

        • Bus speed（总线速度）：8000000 Hz

        • 取消勾选“Enable semihosting”

      • GDB Client Setup

        • Executable path 示例（使用你的 GNUARMEMB_TOOLCHAIN_PATH）：C:\gcc-arm-none-eabi-6_2017-q2-update\bin\arm-none-eabi-gdb.exe

    • 在 SVD Path 选项卡中：

      • File path（文件路径）：<workspace top>\modules\hal\nxp\mcux\devices\MK64F12\MK64F12.xml

      备注

      此项为可选。它向调试器提供 SoC 的内存映射寄存器地址和位域。

  3. 点击 Debug 按钮开始调试。

RTOS 感知

pyOCD v0.11.0 及更高版本实现了对 Zephyr RTOS 感知的支持。它与 Eclipse 中的 GDB PyOCD Debugging 兼容，但必须在应用程序中启用 CONFIG_DEBUG_THREAD_INFO=y。

调试 I2C 通信

可以记录应用程序执行的全部或部分 I2C 事务。此功能由 Kconfig 选项 CONFIG_I2C_DUMP_MESSAGES 启用，但它使用 LOG_DBG 函数打印内容，因此还必须启用 CONFIG_I2C_LOG_LEVEL_DBG 选项。

转储输出示例如下:

D: I2C msg: io_i2c_ctrl7_port0, addr=50
D:    W      len=01: 00
D:    R Sr P len=08:
D: contents:
D: 43 42 41 00 00 00 00 00 |CBA.....

第一行表示 I2C 控制器和该事务的目标地址。在上面的示例中，I2C 控制器名为 io_i2c_ctrl7_port0，目标设备地址为 0x50

备注

地址、长度和内容的值均为十六进制，但没有 0x 前缀

接下来的几行是发送和接收的消息。写消息的内容总会显示，而读消息的内容是否显示由函数 i2c_dump_msgs_rw 的一个参数控制。用户可以使用该函数，i2c_transfer API 函数也会在内部调用它，并启用读内容转储。在长度参数之前，会用缩写打印消息头：

  • W - 写消息

  • R - 读消息

  • Sr - 重复起始位

  • P - 停止位

上面的示例显示了一条写消息，其中字节 0x00 表示要从 I2C 目标读取的寄存器地址。之后，日志显示接收消息的长度，随后是从目标读取的字节 43 42 41 00 00 00 00 00。内容转储同时包含十六进制和 ASCII 表示。

过滤 I2C 通信转储

默认情况下，所有 I2C 控制器与所有 I2C 目标之间的通信都会被记录。这可能会让日志充斥无关设备的信息，难以有效调试与目标设备的通信。

启用 Kconfig 选项 CONFIG_I2C_DUMP_MESSAGES_ALLOWLIST，可以创建要记录的 I2C 目标允许列表。设备允许列表通过设备树配置，例如:

/ {
    i2c {
        display0: some-display@a {
            ...
        };
        sensor3: some-sensor@b {
            ...
        };
    };

    i2c-dump-allowlist {
        compatible = "zephyr,i2c-dump-allowlist";
        devices = <&display0>, <&sensor3>;
    };
};

过滤器节点通过值为 zephyr,i2c-dump-allowlist 的 compatible 字符串识别。通过 devices 属性中指向 I2C 总线上设备的 phandle 来选择设备。

在上面的示例中，与设备 display0 和 sensor3 的通信会显示在日志中。
