历史与动机

West 被加入 Zephyr 项目是为了满足两项基本需求：

  • 能够处理多个 Git 仓库

  • 能够为 Zephyr 基本工作流提供可扩展且用户友好的命令行接口

在 west 的开发过程中，确定了一组 设计约束，以避免此类工具的常见缺陷。

需求

虽然将 Zephyr 代码库拆分为多个仓库的动机不在本页讨论范围之内，但基本需求，以及为何不使用现有工具而是开发一个新工具的明确理由，都属于本页内容。

基本需求如下：

  • R1：将外部维护的代码保存在主 zephyr 仓库之外单独维护的仓库中，且无需用户手动克隆每个外部仓库

  • R2：提供一个 Zephyr 用户和发行方都可以使用、从中受益并加以扩展的工具

  • R3：允许用户和下游发行版覆盖或移除仓库，而无需修改 zephyr 仓库

  • R4：同时支持持续跟踪和基于提交（可二分查找）的项目更新

开发自定义工具的理由

West 的某些功能与 Git Submodules 和 Google 的 repo 所提供的功能类似。

在 west 的初始设计和开发期间曾考虑过现有工具，但没有一个适合 Zephyr 的需求。其中，以下工具经过了详细考察：

  • Google repo

    • 不能很好地支持将 zephyr 用作清单仓库（R4）

    • 仅支持 Python 2

    • 与 Windows 配合不佳

    • 假定使用 Gerrit 进行代码评审

  • Git 子模块

    • 不能完全支持 R1，因为外部维护的仓库仍需位于主 zephyr Git 树内

    • 不支持 R3，因为下游副本需要删除或替换子模块定义

    • 不支持持续跟踪外部仓库中最新的 HEAD （R4）

    • 需要硬编码外部仓库的路径或位置

多个 Git 仓库

Zephyr 旨在提供部署复杂物联网应用程序所需的全部构建模块。这也意味着 Zephyr 项目远不止是一个 RTOS 内核，而是一组协同工作的组件。在此背景下，项目内以标准化的方式使用多个 Git 仓库有以下几点理由：

  • 将 Zephyr 原创代码与导入的项目和库清晰分离

  • 避免原创代码与导入代码之间的许可证不兼容

  • 缩小核心 Zephyr 代码库的规模和范围，将可选组件放在额外的仓库中，而不是直接导入到源码树中

  • 功能安全和信息安全认证

  • 强制组件模块化

  • 基于所支持开发板和 SoC 的子集进行树外开发

有关 west 工作区如何管理多个 git 仓库的信息，请参阅 基础知识。

设计约束

West 具有以下特性：

  • 可选：始终 可以 退回使用“原始”命令行工具，即不使用 west 而使用 Zephyr（尽管 west 本身可能仍需安装并可供构建系统访问）。不过，这样做未必总是 方便。（如果 west 的所有功能都已经能方便地获得，就没有理由开发它了。）

  • 与 CMake 兼容：构建、烧录、调试以及模拟器支持将始终与直接使用 CMake 保持兼容。

  • 跨平台：West 使用 Python 3 编写，可在 Zephyr 支持的所有平台上运行。

  • 可作为库使用：只要可能，west 的功能都以库的形式实现，可以在其他程序中独立使用，并另外提供包装这些库的命令行接口。West 本身是一个名为 west 的 Python 包；其库以子包的形式实现。

  • 对功能持保守态度：没有强有力且令人信服的理由，不会接受任何功能。

  • 规范明确：在 west 包装其他命令的情况下，其行为都有明确的规定和文档。这使得 west 能够与第三方工具互操作，也意味着 Zephyr 开发者在使用 west 时总能了解“底层”发生了什么。

更多细节和讨论请参阅 Zephyr issue #6205。

west update 的分离 HEAD

更新过程 中所述的使用分离的 git HEAD 修订版本的做法，让一些用户感到困惑，甚至沮丧。

具体来说，用户经常问，为什么 west update 默认不保持已有本地分支的检出状态。

本节解释 west update 默认采用这种行为的原因，并介绍管理本地修改过的项目的其他一些选项。

west update 的两项核心要求是：

  1. 安全性：该命令不应丢失用户的任何工作

  2. 确定性：两个用户对同一清单运行 west update，应得到完全相同的 工作区 内容

使用分离 HEAD 有助于保证安全性。正如更新过程中所述，对被更新的项目使用 git checkout --detach 得到分离的 HEAD，通常是一种不会丢失用户工作的安全操作：

  • 如果你的工作都已安全地提交到本地 git 分支中，该分支将保持原样（详情请参阅 git help checkout 的输出）

  • 如果有未提交的工作，只要可能，git 就会将其安全地保留在工作树中

  • 如果做不到，整个命令就会失败，你可以在重新运行 west update 之前决定如何处理你的工作

分离 HEAD 也有助于保证确定性：

  • 只有精确检出清单文件中指定的项目修订版本，才能确保工作区中的文件与主清单中指定的内容一致。如果 west 默认不检出清单修订版本，那么你的工作区可能与根据工作副本中清单文件的内容所预期的状态存在不易察觉的差异。更糟糕的是，差异的具体情况还取决于运行 west update 之前你的分支中到底有什么。

  • 这与 清单导入 之间存在一种微妙的相互作用。如果你的项目本身包含一个或多个被 west update 导入的清单文件，那么 west 需要将这些文件检出到工作树中，才能解析完整的导入清单。如果 west update 在你的项目中保持某个分支的检出状态，工作树中的清单文件可能已经过时。如果 west 随后使用这些过时的文件完成导入，该过程可能会意外失败，或产生其他不确定的结果。

West 不直接检出 manifest-rev 分支，原因在该分支的文档中有说明。

这一默认行为是很久以前选定的，由于用户已经依赖它，现在要更改为时已晚。不过，如果这一默认行为不适合你，还有其他运行 west update 的方式。要了解更多信息，请运行 west help update 并阅读 checked out branch behavior 选项组的说明。例如：

  • 如果你正在项目中积极编写代码，并希望在上游清单可能发生变化后保持代码为最新，请使用 west update --rebase

  • 如果你有一些本地代码，希望在项目的上游修订版本尚未更新到更新的版本之前一直保留它们，请使用 west update --keep-descendants

如果想为在工作区中输入这些命令之一设置一种更简短的方式，可以使用 West 别名。你也可以向以下仓库发送 PR（拉取请求），为此选项组贡献新的选项：

https://github.com/zephyrproject-rtos/west
