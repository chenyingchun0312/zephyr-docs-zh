其他 Zephyr 扩展命令

本页介绍各种 Zephyr 扩展。

列出开发板：west boards

boards 命令可用于列出 Zephyr 支持的开发板，而无需借助其他信息来源。

可以通过输入以下命令运行它：

west boards

此命令以默认格式列出所有支持的开发板。如果希望自行指定显示格式，可以使用 --format （或 -f）标志：

west boards -f "{arch}:{name}"

运行以下命令可以获得有关格式选项的更多帮助：

west boards -h

Shell 补全脚本：west completion

completion 扩展命令输出 shell 补全脚本，这些脚本可直接用于为所支持的 shell 启用 shell 补全。

目前支持以下 shell：

  • bash

  • zsh

  • fish

  • powershell（仅限开发板限定符）

该命令的帮助中提供了更多说明：

west help completion

安装 CMake 包：west zephyr-export

此命令将当前的 Zephyr 安装注册为 CMake 用户包注册表中的一个 CMake 配置包。

在 Windows 中，CMake 用户包注册表位于 HKEY_CURRENT_USER\Software\Kitware\CMake\Packages。

在 Linux 和 MacOS 中，CMake 用户包注册表位于 ~/.cmake/packages。

可以在设置 Zephyr 工作区时运行此命令。这样，位于工作区之外的应用程序 CMakeLists.txt 文件就能通过以下方式找到 Zephyr 仓库：

find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})

详情请参阅 share/zephyr-package/cmake。

软件物料清单：west spdx

此命令为 Zephyr 构建生成一组 SPDX 文档形式的软件物料清单（SBOM）。它记录参与构建的源文件、这些源文件产生的构建产物以及它们之间的关系。每个文件的许可证和版权信息都会被扫描并连同文件哈希值一起填入文档中。

选择 SPDX 版本

west spdx 可以输出两大 SPDX 规范系列中的任意一种。默认为 SPDX 2.3；可以使用 --spdx-version 选项选择其他版本。

SPDX 2.3 是 2.2 的超集，增加了 PrimaryPackagePurpose 等字段。如需与尚不支持 SPDX 3 的工具兼容，请选择 SPDX 2.x；如需 Build 配置文件（SPDX 3.0） 中所述更丰富、机器可读的构建来源信息，请选择 SPDX 3.0 或更高版本。SPDX 3.1 还会记录每个文件的大小（software_artifactSize）。

备注

SPDX 3.1 支持是实验性的：SPDX 3.1 规范仍在制定中。

生成 SPDX 文档

  1. 在项目中启用 CONFIG_BUILD_OUTPUT_META，使构建过程记录 west spdx 所需的信息。

  2. 构建应用程序：

    west build -d BUILD_DIR [...]

  3. 使用该构建目录生成 SPDX 文档：

    west spdx -d BUILD_DIR

    默认生成 SPDX 2.3 tag-value 文档。要改为生成 SPDX 2.2、3.0 或 3.1 文档，请传递 --spdx-version：

    west spdx -d BUILD_DIR --spdx-version 3.0

备注

使用 Sysbuild（系统构建） 构建时，请确保以你要为其生成 SBOM 的实际应用程序为目标。例如，如果应用程序名为 hello_world：

west build --sysbuild -d BUILD_DIR
west spdx -d BUILD_DIR/hello_world

输出文档

文档写入 BUILD_DIR/spdx/ （可用 -s 覆盖）。无论 SPDX 版本如何，生成的物料清单（BOM）文档集合都相同；只有文件扩展名不同：SPDX 2.x tag-value 格式为 .spdx，SPDX 3.0 JSON-LD 格式为 .jsonld：

  • app：构建所用应用程序源文件的 BOM

  • zephyr：构建所用特定 Zephyr 源代码文件的 BOM

  • build：构建输出文件的 BOM

  • modules-deps：模块依赖项的 BOM。更多细节请参阅 模块。

对于 SPDX 3.0，每个文档都声明符合 Core、Software 和 Simple Licensing 配置文件（profile），此外 build.jsonld 还声明了 Build 配置文件，用于记录构建产物是如何产生的。元素 ID 是命名空间前缀（-n）下的完整 IRI，因此只要每次构建都有自己的前缀（默认前缀可以保证这一点），不同构建（例如 sysbuild 构建中的各个镜像）的文档就可以合并到一个图中。在一个文档中定义、在另一个文档中引用的元素（例如构建所用的 zephyr 文档中的某个源文件）会通过 ExternalMap 导入，而不是被复制。

每个文档都将 The Zephyr Project 列为作者，并注明生成工具及其所属的 Zephyr 版本（SPDX 2.x 中为 Creator 行，SPDX 3 中为 createdBy 和 createdUsing）。

物料清单中的每个文件都会被扫描，以便记录其哈希值（SHA512、SHA256 和 SHA1）以及许可证和版权信息。

许可证和版权都通过 REUSE 组织的第三方 reuse 工具解析，因此 west spdx 支持 REUSE specification 所允许的每一种声明方式：文件本身中的 SPDX-License-Identifier 和 SPDX-FileCopyrightText 注释、文件旁边的 .license 文件，或者仓库根目录下一次性为整组路径添加注解的 REUSE.toml。最后一种形式是为无法容纳注释的文件（尤其是二进制 blob）声明许可证的唯一方法。

找到的信息会写为 LicenseInfoInFile、LicenseConcluded 和 FileCopyrightText （SPDX 2.x），或者写为元素的许可证和版权属性（SPDX 3.0）。

备注

版权提取使用启发式方法，可能无法获取完整的声明文本，因此 FileCopyrightText 的内容只能尽力而为。这与 SPDX 规范的建议一致。

包标识

每个包都会记录其来源，以便将 SBOM 与漏洞数据库进行匹配：

  • 供应商（supplier），即检出源代码的仓库的所有者：对于 Zephyr 以及托管在 zephyrproject-rtos 下的模块，为 The Zephyr Project；否则为该仓库的命名空间。

  • PURL （Package URL），根据检出源代码的仓库构建；如果检出的修订版本带有标签，则固定到发布标签，否则固定到修订版本本身。它标识实际构建的确切源码树，对于派生仓库（fork），就是该派生仓库自身。

  • CPE （Common Platform Enumeration）名称，它标识的是产品和版本而不是检出的代码，因此不依赖于源代码来自哪个远程仓库。

对于 Zephyr 本身，CPE 为 cpe:2.3:o:zephyrproject:zephyr:<version>:<update>:*:*:*:*:*:*，根据 Zephyr 的 VERSION 文件所报告的版本构建。任何 EXTRAVERSION 都会成为 CPE 的 update 字段，因此候选发布版本记录为 cpe:2.3:o:zephyrproject:zephyr:4.4.0:rc3:*:*:*:*:*:*，正式发布版本记录为 cpe:2.3:o:zephyrproject:zephyr:4.4.0:-:*:*:*:*:*:*。zephyr 源代码包和 modules-deps 中的 Zephyr 条目都带有该 CPE。

模块也以同样的方式标识，并且还可以在其 zephyr/module.yml 中声明经过整理的引用（例如当模块是派生仓库时，上游项目的 CPE）。请参阅 模块。

每个模块以及 Zephyr 本身都以两个包的形式出现：

  • <module>-sources 位于 zephyr 文档中，列出检出的源码树中参与构建的文件。

  • <module>-deps 位于 modules-deps 中，不包含任何文件，用于标识上游模块以便进行漏洞跟踪。west 清单中的每个模块都会生成一个这样的包，无论其代码是否被构建。

VARIANT_OF 关系（SPDX 3 中为 hasVariant）将这两个包关联起来，并且每个包都带有一条说明其作用的注释。

预构建库

链接到镜像中的预构建库（例如厂商 HAL 的 二进制 blob）虽然不由任何构建目标生成，但也会被列出。west spdx 从每个目标的链接命令中读取这些库，像链接器一样根据 -L 搜索目录解析 -lNAME 标志，将每个库归属到其来源模块，并通过 STATIC_LINK 关系（SPDX 3 中为 hasStaticLink）将其链接到目标的输出。

如果该库是在模块的 zephyr/module.yml 中声明并通过 west blobs 获取的 blob，其文件条目还会记录该 blob 的版本和下载 URL，在 SPDX 3 中还会记录其描述。当文件的 SHA256 与模块声明的值不同时，west spdx 会发出警告。

关系

SPDX 关系用于表示 CMake 构建目标之间的依赖、链接在一起的构建目标，以及经编译生成所构建库文件的源文件。menuconfig 或 ram_report 等 CMake 实用目标不产生任何软件，因此不包括在内。

两大规范系列表达构建来源的方式不同：

  • 在 SPDX 2.x 中，每个生成的产物都带有文件级的 GENERATED_FROM 关系，指回编译它所用的源文件（使用 --analyze-includes 时还包括头文件）。

  • 在 SPDX 3.0 中，构建来源改由 Build 配置文件 承载，使用限定在 build 生命周期内的 hasInput/hasOutput/usesTool 关系。

Build 配置文件（SPDX 3.0）

生成 SPDX 3.0 文档时，west spdx 会填充 SPDX 3.0 Build profile，使 SBOM 不仅记录构建了 什么，还记录了 如何 构建。这些信息从 CMake file-API 自动收集，保存在 build.jsonld 中。

该配置文件添加一个描述整个构建的 build_Build 元素：包括其构建类型、CMake 生成器和构建配置，以及选定的环境变量（例如 BOARD 和 ARCH）。工具链（CMake、编译器、汇编器、链接器和归档器）记录为 Tool 元素，每个元素都带有其路径和版本。随后，限定在构建范围内的关系将构建与其输入（源代码包和已编译文件）、输出（最终镜像）以及所用工具关联起来。

每个中间目标（例如静态库）也有自己的子构建，记录生成其产物的确切源文件、工具和编译标志，因此任何输出都可以追溯到其构建方式。

命令行选项

west spdx 接受以下附加选项：

  • -i、--init：在构建目录配置之前，在其中创建基于文件的 CMake API 查询。已弃用，将在 Zephyr 5.0 中移除：启用 CONFIG_BUILD_OUTPUT_META 的构建现在会自行请求该查询。

  • -n PREFIX：生成的 SPDX 文档中所包含的文档命名空间（Document Namespace）的前缀。详情请参阅 SPDX specification clause 6。如果省略 -n，将按照第 2.5 节所述的默认格式，使用随机 UUID 生成默认命名空间。

  • -s SPDX_DIR：指定另一个用于写入 SPDX 文档的目录，代替 BUILD_DIR/spdx/。

  • --spdx-version {2.2,2.3,3.0,3.1}：指定要使用的 SPDX 规范版本。默认为 2.3。各版本之间的差异请参阅 选择 SPDX 版本。

  • --analyze-includes：除了在物料清单中记录已编译的源代码文件（例如 .c、.S）之外，还尝试确定每个 .c 文件所包含的具体头文件。

    这会耗费更长时间，因为它会针对每个 .c 文件，使用与实际构建时传递给 C 编译器相同的参数执行一次试运行（dry run）。

  • --include-sdk：与 --analyze-includes 一起使用时，还会创建第四个 SPDX 文档 sdk.spdx （或 sdk.jsonld），列出从 SDK 包含的头文件。

警告

目前不支持为 native_sim 平台生成 SBOM 文档。

使用二进制 blob：west blobs

blobs 命令允许用户与一个或多个 模块 通过其 module.yml 文件声明的 二进制 blob 进行交互。

blobs 命令有三个子命令，分别用于列出、获取或清理（即删除）二进制 blob 本身。

可以在列出二进制 blob 时指定输出格式：

west blobs list -f '{module}: {type} {path}'

-f/--format 中可用的全部变量，请运行 west blobs -h 查看。

获取 blob 的方式与此类似：

west blobs fetch

注意，如 模块一节 中所述，获取的 blob 存储在相对于相应模块仓库根目录的 zephyr/blobs/ 文件夹中。

删除 blob 也是如此：

west blobs clean

此外，该工具允许通过在命令行参数中输入模块名称，指定要为哪些模块列出、获取或清理 blob。

可以向 west blobs fetch 传递 --allow-regex 参数和一个正则表达式，以限定要获取的具体 blob：

# For example, only download esp32 blobs, skip the other variants
west blobs fetch hal_espressif --allow-regex 'lib/esp32/.*'

可以通过 --auto-cache 命令行参数或 blobs.auto-cache 配置选项提供一个自动缓存目录。启用后，每当某个 blob 缺失并被下载时，都会自动将其填入自动缓存目录。

可以在 --cache-dirs 命令行参数或 blobs.cache-dirs 配置选项中提供一个或多个额外的缓存目录（以 ; 分隔）。

west blobs fetch 会在所有已配置的缓存目录（包括自动缓存目录）中搜索文件名匹配的 blob。缓存文件可以以原始文件名存储，也可以带有 SHA-256 后缀（<filename>.<sha>）。如果找到，就将 blob 从缓存复制到 blob 路径；否则从其 URL 下载到 blob 路径。

可以通过 blobs.mirrors 配置选项配置一个或多个下载镜像。其值是一个包含一个或多个键值对的 JSON 对象，其中每个键是一个远程 URL 前缀（字符串），每个值是单个镜像 URL 前缀（字符串）或镜像 URL 前缀列表（字符串数组）。

为一个远程 URL 前缀配置单个镜像：

west config blobs.mirrors '{"https://github.com/": "https://example.com/github-mirror/"}'

为同一个远程 URL 前缀配置多个镜像，按列表顺序尝试：

west config blobs.mirrors '{
  "https://github.com/": [
    "https://example.com/github1-mirror/",
    "https://example.com/github2-mirror/"
  ]
}'

对于每个 blob URL，会尝试所有远程 URL 前缀与之匹配的镜像，并按顺序排列，使匹配的 最长 （最具体）远程 URL 前缀最先尝试（类似 git 的 insteadOf）；较短、较不具体的匹配所对应的镜像随后尝试。为同一远程 URL 前缀配置的镜像按其列出的顺序尝试。原始 URL 最后尝试，作为所有镜像都失败时的后备。

Twister 包装器：west twister

此命令是 twister 的包装器。

然后可以通过 west 调用 Twister，如下所示：

west twister -help
west twister -T tests/ztest/base

使用二进制描述符：west bindesc

bindesc 命令允许用户读取可执行文件的 二进制描述符。它目前支持 .bin、.hex、.elf 和 .uf2 文件作为输入。

可以在镜像中搜索特定的描述符，例如：

west bindesc search KERNEL_VERSION_STRING build/zephyr/zephyr.bin

可以按类型和 ID 搜索自定义描述符，例如：

west bindesc custom_search STR 0x200 build/zephyr/zephyr.bin

可以使用以下命令转储镜像中的所有描述符：

west bindesc dump build/zephyr/zephyr.bin

可以使用以下命令将镜像的描述符数据区提取到文件中：

west bindesc extract

可以使用以下命令列出所有已知的标准描述符名称：

west bindesc list

可以使用以下命令打印描述符在镜像中的偏移量：

west bindesc get_offset

使用 GNU Global 为源代码建立索引：west gtags

重要

要使用此命令，必须安装 GNU Global 提供的 gtags 和 global 程序。

west gtags 命令可以为整个 west 工作区创建 GNU Global 标签文件：

west gtags

这会在工作区 topdir 中创建一个名为 GTAGS 的标签文件（同时还会在同一位置创建名为 GPATH 和 GRTAGS 的其他 Global 相关元数据文件）。

然后，可以在工作区内的任何位置运行 global 命令，使用该标签文件搜索符号的位置。

例如，要从 zephyr/drivers 目录开始搜索 arch_system_halt() 函数的定义：

$ cd zephyr/drivers
$ global -x arch_system_halt
arch_system_halt   65 ../arch/arc/core/fatal.c FUNC_NORETURN void arch_system_halt(unsigned int reason)
arch_system_halt  455 ../arch/arm64/core/fatal.c FUNC_NORETURN void arch_system_halt(unsigned int reason)
arch_system_halt  137 ../arch/nios2/core/fatal.c FUNC_NORETURN void arch_system_halt(unsigned int reason)
arch_system_halt   18 ../arch/posix/core/fatal.c FUNC_NORETURN void arch_system_halt(unsigned int reason)
arch_system_halt   17 ../arch/x86/core/fatal.c FUNC_NORETURN void arch_system_halt(unsigned int reason)
arch_system_halt  126 ../arch/xtensa/core/fatal.c FUNC_NORETURN void arch_system_halt(unsigned int reason)
arch_system_halt   21 ../kernel/fatal.c FUNC_NORETURN __weak void arch_system_halt(unsigned int reason)

对于定义了该符号的所有位置，这会打印所搜索的符号、定义所在的行号、定义所在文件的相对路径以及该行本身。

其他提示：

  • 这也可以用来搜索厂商 HAL 函数的定义。

  • 有关如何使用此工具的更多信息，请参阅 global 命令的手册页。

  • 应当运行 global，而不是 west global。不需要单独的 west global 命令，因为 global 已经会从当前工作目录开始搜索 GTAGS 文件。这也是需要在工作区内运行 global 的原因。

使用补丁：west patch

patch 命令允许用户以受控的方式向 Zephyr 或 Zephyr 模块应用补丁，从而使采用 T2 星型拓扑 的外部应用程序更容易实现自动化和跟踪。patches.yml 文件存储有关补丁文件的元数据，并弥补 Zephyr 正式版本之间的空档，使用户可以方便地查看任何向上游提交工作的状态，并确定在升级到下一个 Zephyr 版本之前应丢弃哪些补丁。

有几个子命令可用于管理工作区中 Zephyr 或其他模块的补丁：

  • apply：应用 patches.yml 中列出的补丁

  • reverse：撤销 patches.yml 中列出的、之前已应用的补丁

  • clean：移除所有已应用的补丁，并重置为清单检出时的状态

  • list：列出 patches.yml 中的所有补丁

  • gh-fetch：从 GitHub PR（拉取请求）获取补丁

在本例中，west 清单 文件 west.yml 会固定到某个特定的 Zephyr 修订版本（例如 v4.1.0），并针对该 Zephyr 修订版本以及应用程序所用其他模块的特定修订版本应用补丁。但是，该应用程序需要两处修改才能满足要求；一处针对 Zephyr，另一处针对 MCUBoot。

patches:
  - path: zephyr/my-zephyr-change.patch
    sha256sum: c676cd376a4d19dc95ac4e44e179c253853d422b758688a583bb55c3c9137035
    module: zephyr
    author: Obi-Wan Kenobi
    email: obiwan@jedi.org
    date: 2025-05-04
    upstreamable: false
    comments: |
      An application-specific change we need for Zephyr.
  - path: bootloader/mcuboot/my-tweak-for-mcuboot.patch
    sha256sum: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
    module: mcuboot
    author: Darth Sidious
    email: sidious@sith.org
    date: 2025-05-04
    merge-pr: https://github.com/zephyrproject-rtos/zephyr/pull/<pr-number>
    issue: https://github.com/zephyrproject-rtos/zephyr/issues/<issue-number>
    merge-status: true
    merge-commit: 1234567890abcdef1234567890abcdef12345678
    merge-date: 2025-05-06
    apply-command: git apply
    comments: |
      A change to mcuboot that has been merged already. We can remove this
      patch when we are ready to upgrade to the next Zephyr release.

可以轻松地以自动化方式应用补丁。例如：

west init -m <manifest repo> <workspace>
cd <workspace>
west update
west patch apply

需要更新到较新的 Zephyr 版本时，可以更新 west.yml 文件，使其指向下一个 Zephyr 版本，例如 v4.2.0。不再需要的补丁（例如上例中的 my-tweak-for-mcuboot.patch）可以从 patches.yml 和外部应用程序仓库中移除，然后运行以下命令。

west patch clean
west update
west patch apply --roll-back # roll-back all patches if one does not apply cleanly

也可以选择撤销补丁，而不是清理所有模块。这样会保留对模块所做的、不冲突且无关的编辑，只移除补丁所做的更改。在开发补丁并在应用程序中测试，但又不想清理所有补丁而丢失对模块所做的手动编辑时，这很有用。

west patch reverse

如果需要重新修改某个补丁，请记得用新的 SHA256 校验和更新 patches.yml 文件。

sha256sum zephyr/patches/zephyr/my-zephyr-change.patch
7d57ca78d5214f422172cc47fed9d0faa6d97a0796c02485bff0bf29455765e9

也可以使用 west patch gh-fetch 从 GitHub PR（拉取请求）获取补丁，并自动创建或更新 patches.yml 文件。当作者已经在现有的上游 PR 中提交了许多更改时，这会很有用。

west patch gh-fetch --owner zephyrproject-rtos --repo zephyr --pull-request <pr-number> \
  --module zephyr --split-commits

上述命令将创建如下的目录和文件结构，其中包含与给定 PR 相关的每个提交各自对应的补丁。

zephyr
├── patches
│   ├── first-commit-from-pr.patch
│   ├── second-commit-from-pr.patch
│   └── third-commit-from-pr.patch
└── patches.yml

使用 Zephyr SDK：west sdk

west sdk 命令是一个 Zephyr 专用的 west 命令，用于列出和安装 Zephyr SDK 及其工具链。

列出 SDK 和工具链

要列出已安装的 Zephyr SDK 以及可用的 SDK 版本和工具链，请运行：

west sdk list

此命令显示：

  • 已安装的 SDK 版本

  • 可用的 SDK 版本

  • 每个 SDK 中包含的工具链

安装 Zephyr SDK

要安装 Zephyr SDK，请运行：

west sdk install

此命令可能以交互模式运行，并提示选择 SDK 或工具链。当通过 --toolchains 指定具体的工具链时，命令以非交互方式运行，推荐在自动化场景中这样使用。

要仅安装特定的工具链，请使用 --toolchains 选项：

west sdk install --toolchains arm-zephyr-eabi riscv64-zephyr-elf

如果不确定需要哪些工具链，请先运行 west sdk list 查看可用选项，以免下载不必要的工具链，这样可以节省数 GB 的磁盘空间和下载时间。
