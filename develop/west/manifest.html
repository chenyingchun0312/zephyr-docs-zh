多仓库模型

West 对 west workspace 中各仓库及其历史的看法如下图所示（不过此示例的某些部分是上游 Zephyr 使用 west 的方式所特有的）：

清单仓库的历史是“漂浮”在灰色平面之上的那条 Git 提交线。父提交用实线箭头指向子提交。下方的平面包含工作区中各仓库的 Git 提交历史，每个项目仓库都用一个矩形框起来。每个仓库中的父子提交关系同样用实线箭头表示。

清单仓库中的每个提交（同样，对于上游 Zephyr，清单仓库就是 zephyr 仓库本身）都有一个清单文件。每个提交中的清单文件指定了它期望各项目仓库中对应的提交。图中用虚线箭头表示这种关系。每个虚线箭头都从清单仓库中的一个提交指向某个项目仓库中对应的提交。

请注意以下重要细节：

  • 项目可以被添加（例如在清单仓库提交 D 和 E 之间添加的 P1），也可以被移除（在同样两个清单仓库提交之间移除的 P2）

  • 项目仓库和清单仓库的历史不必一起前进或后退：

    • P2 在 A → B 之间保持不变，P1 和 P3 在 F → G 之间也保持不变。

    • P3 在 A → B 之间前进。

    • P3 在 C → D 之间后退。

    在项目历史中后退的一种用途是通过回到引入回归问题之前的修订版本来“撤销”该回归。

  • 项目仓库的提交可以被“跳过”：P3 在 B → C 之间在其历史中前进了多个提交。

  • 在上图中，没有任何项目仓库“同时”有两个修订版本：每个清单文件都只引用其所关心的项目中的一个提交。可以通过使用分支名称作为清单修订版本来放宽这一点，代价是无法对清单仓库历史进行二分查找。

清单文件

West 清单是 YAML 文件。清单有一个顶层 manifest 节，其中包含一些子节，例如：

manifest:
  remotes:
    # short names for project URLs
  projects:
    # a list of projects managed by west
  defaults:
    # default project attributes
  self:
    # configuration related to the manifest repository itself,
    # i.e. the repository containing west.yml
  version: "<schema-version>"
  group-filter:
    # a list of project groups to enable or disable

用 YAML 术语来说，清单文件包含一个带有 manifest 键的映射。其他任何键及其内容都会被忽略（west v0.5 还要求有 west 键，但从 v0.6 开始该键会被忽略）。

清单包含 defaults、remotes、projects 和 self 等子节。用 YAML 术语来说，manifest 键的值也是一个映射，以这些“子节”作为键。从 west v0.10 开始，所有这些“子节”键都是可选的。

projects 的值是由 west 管理的仓库及其相关元数据的列表。我们稍后会讨论它，但首先介绍 remotes 节，它可以减少在 projects 列表中的输入量。

远程仓库（remotes）

remotes 子节包含一个序列，指定可以获取项目的基础 URL。

每个 remotes 元素都有一个名称和一个“URL 基址”。它们用于组成每个项目完整的 Git 获取 URL。可以通过在远程 URL 基址后追加项目专用的路径来设置项目的获取 URL。（正如下文将看到的，项目也可以指定完整的获取 URL。）

例如：

manifest:
  # ...
  remotes:
    - name: remote1
      url-base: https://git.example.com/base1
    - name: remote2
      url-base: https://git.example.com/base2

remotes 的键及其用法见下表。

remotes 键

键

说明

name

必需；远程仓库的唯一名称。

url-base

使用此远程仓库的每个项目的获取 URL 前所添加的前缀。

上例给出了两个远程仓库，名称分别为 remote1 和 remote2。它们的 URL 基址分别为 https://git.example.com/base1 和 https://git.example.com/base2。也可以使用 SSH URL 基址；例如，如果 remote1 也支持基于 SSH 的 Git，可以使用 git@example.com:base1。任何 Git 能接受的形式都可以。

项目

projects 子节包含一个描述 west 工作区中项目仓库的序列。每个项目都有一个唯一的名称。可以指定克隆和获取项目时使用哪些 Git 远程 URL、跟踪哪些修订版本，以及项目应存放在本地文件系统中的什么位置。注意，west 项目 与模块不同。

下面是一个示例。假设使用上面给出的 remotes。

manifest:
  # [... same remotes as above...]
  projects:
    - name: proj1
      description: the first example project
      remote: remote1
      path: extra/project-1
    - name: proj2
      description: |
        A multi-line description of the second example
        project.
      repo-path: my-path
      remote: remote2
      revision: v1.3
    - name: proj3
      url: https://github.com/user/project-three
      revision: abcde413a111
    - name: proj4
      url: https://github.com/user/project-four
      revision: pull/69/head # GitHub Pull Request

在此清单中：

  • proj1 的远程仓库为 remote1，因此其 Git 获取 URL 为 https://git.example.com/base1/proj1。将远程仓库的 url-base 加上 / 和项目的 name，即构成该 URL。

    在本地，该项目将被克隆到相对于 west 工作区根目录的 extra/project-1 路径下，因为它有一个值为此路径的显式 path 属性。

    由于该项目没有指定 revision，默认使用 master。west 下次更新该项目时，会获取该分支当前的最新提交，并将其作为分离 HEAD 检出。

  • proj2 有 remote 和 repo-path，因此其获取 URL 为 https://git.example.com/base2/my-path。如果存在 repo-path 属性，在构成获取 URL 时它会取代默认的 name。

    由于该项目没有 path 属性，默认使用其 name。它将被克隆到名为 proj2 的目录中。west 更新该项目时，会检出 v1.3 标签所指向的提交。

  • proj3 有显式的 url，因此将从 https://github.com/user/project-three 获取。

    其本地路径默认为其名称 proj3。下次更新时将检出提交 abcde413a111。

可用的项目键及其用法见下表。表中有时会提到 defaults 子节，接下来会对其进行介绍。

projects 元素的键

键

说明

name

必需；项目的唯一名称。名称不能是保留值“west”或“manifest”。名称在清单文件中必须唯一。

description

可选，项目的说明性描述。在 west v1.2.0 中添加。

remote、url

必需（二者必须有且仅有一个）。

如果项目有 remote，则改为将该远程仓库的 url-base 与项目的 name （或者 repo-path，如果项目有的话）组合起来构成获取 URL。

如果项目有 url，它就是远程 Git 仓库的完整获取 URL。

如果项目两者都没有，则 defaults 节必须指定一个 remote，用作该项目的远程仓库。否则，清单无效。

repo-path

可选。如果给出，则将其（而不是项目的 name）拼接到远程仓库的 url-base 之后构成获取 URL。项目不能同时具有 url 和 repo-path 属性。

revision

可选。west update 应检出的 Git 修订版本。默认会以分离 HEAD 的方式检出，以避免与本地分支名称冲突。如果未给出，则使用 defaults 子节中的 revision 值（如果存在）。

项目修订版本可以是任何可获取的 git 引用：分支、标签、SHA、PR（拉取请求）等。

如果没有另行指定，默认 revision 为 master。

使用 HEAD~0 [1] 作为 revision，会使 west 保持项目的当前状态。

path

可选。指定将仓库克隆到本地何处的相对路径，相对于 west 工作区的顶层目录。如果缺失，则使用项目的 name 作为目录名。

clone-depth

可选。如果给出，则为一个正整数，用于在克隆的仓库中创建浅历史，限制为给定数量的提交。只有当 revision 是分支或标签时才能使用。

west-commands

可选。如果给出，则为项目内某个 YAML 文件的相对路径，该文件描述该项目提供的额外 west 命令。按照惯例，此文件名为 west-commands.yml。详情请参阅 扩展。

import

可选。如果为 true，则将给定仓库中清单文件里的项目导入当前清单。详情请参阅 清单导入。

groups

可选，项目所属组的列表。详情请参阅 项目组。

submodules

可选。可以用它使 west update 同时更新项目所定义的 Git submodules。详情请参阅 项目中的 Git 子模块。

userdata

可选。其值是任意 YAML 值。请参阅 仓库用户数据。

脚注

[1]

在 git 中，HEAD 是一个引用，而 HEAD~<n> 是一个有效的修订版本，但不是引用。West 会获取引用（例如 refs/heads/main 或 HEAD）以及本地不存在的提交，但如果提交在本地已经存在，则不会获取。HEAD~0 会被解析为本地已有的某个特定提交，因此 west 只会检出由 HEAD~0 标识的这个本地提交。

默认值（defaults）

defaults 子节可以为项目属性提供默认值。特别是，可以在这里指定默认的远程仓库名称和修订版本。使用 defaults 编写我们迄今为止所描述的同一个清单的另一种写法是：

manifest:
  defaults:
    remote: remote1
    revision: v1.3

  remotes:
    - name: remote1
      url-base: https://git.example.com/base1
    - name: remote2
      url-base: https://git.example.com/base2

  projects:
    - name: proj1
      description: the first example project
      path: extra/project-1
      revision: master
    - name: proj2
      description: |
        A multi-line description of the second example
        project.
      repo-path: my-path
      remote: remote2
    - name: proj3
      url: https://github.com/user/project-three
      revision: abcde413a111

可用的 defaults 键及其用法见下表。

defaults 键

键

说明

remote

可选。如果项目没有设置 url 或 remote 键，则将其用作该项目的 remote。

revision

可选。如果项目自身未设置 revision，则使用此值。如果未给出，默认值为 master。

自身（self）

self 子节可用于控制清单仓库本身。

举个例子，来看 zephyr 仓库的 west.yml 中的这段代码：

manifest:
  # ...
  self:
    path: zephyr
    west-commands: scripts/west-commands.yml

这确保 zephyr 仓库被克隆到 zephyr 路径中，不过正如上文所解释的，如果从默认清单 URL https://github.com/zephyrproject-rtos/zephyr 克隆，无论如何都会是这样。由于 zephyr 仓库确实包含扩展命令，其 self 条目声明了相应 west-commands.yml 相对于仓库根目录的位置。

可用的 self 键及其用法见下表。

self 键

键

说明

path

可选。west init 应将清单仓库克隆到的路径，相对于 west 工作区 topdir。

如果未给出，默认使用清单仓库 URL 中路径部分的基本名称。例如，如果 URL 为 https://git.example.com/project-repo，则清单仓库将被克隆到 project-repo 目录。

west-commands

可选。与项目序列元素中的同名键类似。

import

可选。同样与 projects 中的该键类似，但允许从清单仓库中的其他文件导入项目。请参阅 清单导入。

版本（version）

version 子节声明清单文件使用了某个 west 版本中引入的功能。使用较旧版本的 west 加载该清单将会失败，并给出错误消息，说明所需的最低 west 版本。

下面是一个示例：

manifest:
  # Marks that this file uses version 0.10 of the west manifest
  # file format.
  #
  # An attempt to load this manifest file with west v0.8.0 will
  # fail with an error message saying that west v0.10.0 or
  # later is required.
  version: "0.10"

west source code repository 中的 pykwalify 模式 manifest-schema.yml 用于验证 manifest 节。

下表列出了有效的 version 值，以及在该版本中引入的清单文件功能的信息。

version

新功能

"0.7"

对 version 功能的初始支持。本表中未另行提及的所有清单文件功能都是在 west v0.7.0 或更早版本中引入的。

"0.8"

支持 import: path-prefix: （方式 3：映射）

"0.9"

不建议使用 west v0.9.x。

提供此模式版本是为了让用户能够显式请求与 west v0.9.0 兼容。但是，对于在 west v0.9.0 中引入的功能，west v0.10.0 及更高版本的行为与之不兼容。如果可能，应忽略版本“0.9”。

"0.10"

支持：

  • projects: 中的 submodules: （项目中的 Git 子模块）

  • manifest: group-filter:，以及 projects: 中的 groups: （项目组）

  • import: 功能现在支持 allowlist: 和 blocklist:；作为 Zephyr 范围内包容性语言整体变更的一部分，推荐分别用它们替代旧名称。为了向后兼容，旧的键名仍然受支持。（清单导入、方式 3：映射）

"0.12"

支持 projects: 中的 userdata: （仓库用户数据）

"0.13"

支持 self: userdata: （仓库用户数据）

"1.0"

与 "0.13" 相同，但可供不希望使用 "0.x" 版本字段的用户使用。

"1.2"

支持 projects: 中的 description: （项目）

备注

未在清单文件格式中引入任何新功能的 west 版本不会改变有效的 version 值列表。例如，version: "0.11" 是 无效的，因为 west v0.11.x 没有引入新的清单文件格式功能。

像上面那样给 version 值加上引号，会强制 YAML 解析器将其视为字符串。如果不加引号，YAML 中的 0.10 只是浮点值 0.1。如果值在转换为字符串后不变，可以省略引号，但最好加上。不确定时请始终使用引号。

如果清单中没有包含 version，每个新发布的 west 都会假定应使用该版本中可用的功能来尝试加载它。如果该 west 版本太旧而无法加载该清单，可能会导致较难理解的错误消息。

组过滤器（group-filter）

请参阅 项目组。

活动项目和非活动项目

west 清单中定义的项目可以是 非活动的 或 活动的。区别在于，非活动项目通常会被 west 忽略。例如，west update 不会更新非活动项目，west list 默认也不会打印它们的信息。再如，非活动项目中的任何 清单导入 都会被 west 忽略。

有两种方法可以使项目变为非活动状态：

  1. 使用 manifest.project-filter 配置选项。如果使用此选项使项目变为活动或非活动状态，则与通过项目的 groups: 使其变为非活动状态相关的规则会被忽略。也就是说，如果 manifest.project-filter 中的某个正则表达式适用于某个项目，该项目的组对其是否处于活动状态没有影响。

    详情请参阅 内置配置选项 中此选项的条目。

  2. 否则，如果项目有组，并且这些组全部被禁用，则该项目处于非活动状态。

    详情请参阅下一节。

项目组

可以使用 上文 简要介绍过的 groups 和 group-filter 键将项目放入组中，以及启用或禁用组。

例如，这样就可以使用 west forall --group 只对组中的项目运行 west forall 命令。它还可以使项目变为非活动状态；有关非活动项目的更多信息，请参阅上一节。

下一节介绍项目组。再下一节介绍 启用和禁用的项目组。项目组示例 中有一些基本示例。最后，组过滤器与导入 简要概述了 group-filter 如何与 清单导入 功能相互作用。

组的基础知识

groups: 和 group-filter: 键在清单中如下所示：

manifest:
  projects:
    - name: some-project
      groups: ...
  group-filter: ...

groups 键的值是组名称的列表。组名称是字符串。

可以使用 group-filter 启用或禁用项目组。如果项目的所有组都被禁用，且没有通过 manifest.project-filter 配置选项以其他方式使其变为活动状态，则该项目处于非活动状态。

例如，在以下清单片段中：

manifest:
  projects:
    - name: project-1
      groups:
        - groupA
    - name: project-2
      groups:
        - groupB
        - groupC
    - name: project-3

各项目所属的组如下：

  • project-1：一个组，名为 groupA

  • project-2：两个组，名为 groupB 和 groupC

  • project-3：没有组

项目组名称不能包含逗号（,）、冒号（:）或空白字符。

组名称不能以短横线（-）或加号（+）开头，但可以在名称的其他位置包含这些字符。例如，foo-bar 和 foo+bar 是有效的组，而 -foobar 和 +foobar 不是。

除此之外，组名称可以是任意字符串。组名称区分大小写。

作为一项限制，任何项目都不能同时使用 import: 和 groups:。（这是为了避免一些异常的边界情况。）

启用和禁用的项目组

所有项目组默认都是启用的。可以在清单文件和 配置 中启用或禁用组。

在清单文件中，manifest: group-filter: 是一个 YAML 列表，列出要启用和禁用的组。

要启用某个组，请在其名称前加上加号（+）。例如，在以下清单片段中启用了 groupA：

manifest:
  group-filter: [+groupA]

虽然对于默认已启用的组来说这是多余的，但它可用于覆盖被导入清单文件中的设置。更多信息请参阅 组过滤器与导入。

要禁用某个组，请在其名称前加上短横线（-）。例如，在以下清单片段中禁用了 groupA 和 groupB：

manifest:
  group-filter: [-groupA,-groupB]

备注

由于 group-filter 是一个 YAML 列表，也可以将此片段写成如下形式：

manifest:
  group-filter:
    - -groupA
    - -groupB

但这种语法较难阅读，因此不建议使用。

除了清单文件之外，还可以使用 manifest.group-filter 配置选项控制启用和禁用哪些组。此选项是一个以逗号分隔的列表，列出要启用和/或禁用的组。

要启用某个组，请将其名称加上 + 前缀后添加到列表中。要禁用某个组，请将其名称加上 - 前缀后添加到列表中。例如，将 manifest.group-filter 设置为 +groupA,-groupB 会启用 groupA 并禁用 groupB。

配置选项的值会覆盖清单文件中的任何数据。可以这样理解：manifest.group-filter 配置选项被追加到 YAML 中的 manifest: group-filter: 列表之后，并采用“最后一项生效”的语义。

实际示例：减少工作区下载量

默认情况下，west update 会获取清单中定义的所有活动项目。大型工作区可能包含可选模块、厂商 HAL、实验性组件，或者平台专用的依赖项和漏洞，而这些并非每种工作流都需要。

项目组可用于控制在 west 操作期间哪些分组项目被视为活动项目。

例如，考虑以下清单片段：

manifest:
  projects:
    - name: hal_nordic
      groups:
        - nordic
    - name: hal_stm32
      groups:
        - stm32
    - name: experimental_lib
      groups:
        - optional

面向 Nordic 设备的工作区可以在运行 west update 之前禁用 stm32 和 optional 组：

west config manifest.group-filter -- "-stm32,-optional"

配置过滤器后，运行：

west update

这会跳过仅属于已禁用组的项目。

备注

项目组只影响在清单中被显式分配到匹配组的项目。没有匹配组定义的项目无论 manifest.group-filter 的配置值如何，都保持活动状态。

备注

更改 manifest.group-filter 不会自动删除已克隆到工作区中的仓库。它影响的是在后续 west 操作中项目是否被视为活动项目。

这种工作流有助于在大型多项目环境中减少不必要的下载，并简化工作区管理。

项目组示例

本节包含涉及项目组和活动项目的示例场景。这些示例同时使用 manifest: group-filter: YAML 列表和 manifest.group-filter 配置列表，以展示它们如何协同工作。

注意，以下清单中的 defaults 和 remotes 数据与讨论无关，只是为了使示例完整且自成一体。

备注

在以下所有示例中，均假定未设置 manifest.project-filter 选项。

示例 1：没有禁用的组

完整的清单文件为：

manifest:
  projects:
    - name: foo
      groups:
        - groupA
    - name: bar
      groups:
        - groupA
        - groupB
    - name: baz

  defaults:
    remote: example-remote
  remotes:
    - name: example-remote
      url-base: https://git.example.com

未设置 manifest.group-filter 配置选项（可以运行 west config -D manifest.group-filter 来确保这一点）。

没有任何组被禁用，因为所有组默认都是启用的。因此，所有三个项目（foo、bar 和 baz）都是活动的。注意，无法使项目 baz 变为非活动状态，因为它没有任何组。

示例 2：通过清单禁用一个组

完整的清单文件为：

manifest:
  projects:
    - name: foo
      groups:
        - groupA
    - name: bar
      groups:
        - groupA
        - groupB

  group-filter: [-groupA]

  defaults:
    remote: example-remote
  remotes:
    - name: example-remote
      url-base: https://git.example.com

未设置 manifest.group-filter 配置选项（可以运行 west config -D manifest.group-filter 来确保这一点）。

由于 groupA 被禁用，项目 foo 处于非活动状态。项目 bar 是活动的，因为 groupB 已启用。

示例 3：通过清单禁用多个组

完整的清单文件为：

manifest:
  projects:
    - name: foo
      groups:
        - groupA
    - name: bar
      groups:
        - groupA
        - groupB

  group-filter: [-groupA,-groupB]

  defaults:
    remote: example-remote
  remotes:
    - name: example-remote
      url-base: https://git.example.com

未设置 manifest.group-filter 配置选项（可以运行 west config -D manifest.group-filter 来确保这一点）。

foo 和 bar 都处于非活动状态，因为它们的所有组都被禁用了。

示例 4：通过配置禁用一个组

完整的清单文件为：

manifest:
  projects:
    - name: foo
      groups:
        - groupA
    - name: bar
      groups:
        - groupA
        - groupB

  defaults:
    remote: example-remote
  remotes:
    - name: example-remote
      url-base: https://git.example.com

manifest.group-filter 配置选项被设置为 -groupA （可以运行 west config manifest.group-filter -- -groupA 来确保这一点；需要额外的 --，以免参数解析器将 -groupA 视为值为 roupA 的命令行选项 -g）。

项目 foo 处于非活动状态，因为 groupA 已被 manifest.group-filter 配置选项禁用。项目 bar 是活动的，因为 groupB 已启用。

示例 5：通过配置覆盖被禁用的组

完整的清单文件为：

manifest:
  projects:
    - name: foo
    - name: bar
      groups:
        - groupA
    - name: baz
      groups:
        - groupA
        - groupB

  defaults:
    remote: example-remote
  remotes:
    - name: example-remote
      url-base: https://git.example.com

manifest.group-filter 配置选项被设置为 +groupA （可以运行 west config manifest.group-filter +groupA 来确保这一点）。

在这种情况下，groupA 是启用的：manifest.group-filter 配置选项的优先级高于清单文件中的 manifest: group-filter: [-groupA] 内容。

因此，项目 foo 和 bar 都是活动的。

组过滤器与导入

本节简要说明 manifest: group-filter: 值与 清单导入 结合使用时的行为。完整细节请参阅 清单导入详解。

警告

以下语义适用于 west v0.10.0 及更高版本。West v0.9.x 的语义有所不同，不建议在 west v0.9.x 中将 group-filter 与 import 结合使用。

简而言之：

  • 如果只导入一个清单，那么它在其 group-filter 中禁用的任何组，在你的清单中也会被禁用

  • 可以在清单文件的 manifest: group-filter: 值、工作区的 manifest.group-filter 配置选项或两者中覆盖这一点

下面是一些示例。

示例 1：没有覆盖

你正在使用以下 parent/west.yml 清单：

# parent/west.yml:
manifest:
  projects:
    - name: child
      url: https://git.example.com/child
      import: true
    - name: project-1
      url: https://git.example.com/project-1
      groups:
        - unstable

而 child/west.yml 包含：

# child/west.yml:
manifest:
  group-filter: [-unstable]
  projects:
    - name: project-2
      url: https://git.example.com/project-2
    - name: project-3
      url: https://git.example.com/project-3
      groups:
        - unstable

在解析后的清单中，只有 child 和 project-2 是活动的。

unstable 组在 child/west.yml 中被禁用，而 parent/west.yml 中没有覆盖这一设置。因此，解析后清单的最终 group-filter 为 [-unstable]。

由于 project-1 和 project-3 属于 unstable 组且不属于其他任何组，它们处于非活动状态。

示例 2：通过清单覆盖导入的 group-filter

你正在使用以下 parent/west.yml 清单：

# parent/west.yml:
manifest:
  group-filter: [+unstable,-optional]
  projects:
    - name: child
      url: https://git.example.com/child
      import: true
    - name: project-1
      url: https://git.example.com/project-1
      groups:
        - unstable

而 child/west.yml 包含：

# child/west.yml:
manifest:
  group-filter: [-unstable]
  projects:
    - name: project-2
      url: https://git.example.com/project-2
      groups:
        - optional
    - name: project-3
      url: https://git.example.com/project-3
      groups:
        - unstable

只有 child、project-1 和 project-3 项目是活动的。

child/west.yml 中的 [-unstable] 组过滤器在 parent/west.yml 中被覆盖，因此 unstable 组被启用。由于 project-1 和 project-3 属于 unstable 组，它们是活动的。

同一个 parent/west.yml 文件禁用了 optional 组，因此 project-2 处于非活动状态。

parent/west.yml 所指定的最终组过滤器为 [+unstable,-optional]。

示例 3：通过配置覆盖导入的 group-filter

你正在使用以下 parent/west.yml 清单：

# parent/west.yml:
manifest:
  projects:
    - name: child
      url: https://git.example.com/child
      import: true
    - name: project-1
      url: https://git.example.com/project-1
      groups:
        - unstable

而 child/west.yml 包含：

# child/west.yml:
manifest:
  group-filter: [-unstable]
  projects:
    - name: project-2
      url: https://git.example.com/project-2
      groups:
        - optional
    - name: project-3
      url: https://git.example.com/project-3
      groups:
        - unstable

如果运行：

west config manifest.group-filter +unstable,-optional

那么只有 child、project-1 和 project-3 项目是活动的。

child/west.yml 中的 -unstable 组过滤器被 manifest.group-filter 配置选项覆盖，因此 unstable 组被启用。由于 project-1 和 project-3 属于 unstable 组，它们是活动的。

同一个配置选项禁用了 optional 组，因此 project-2 处于非活动状态。

由 parent/west.yml 和 manifest.group-filter 配置选项共同指定的最终组过滤器为 [+unstable,-optional]。

项目中的 Git 子模块

可以使用 上文 简要介绍过的 submodules 键，强制 west update 同时处理项目 git 仓库中配置的任何 Git submodules。submodules 键可以出现在 projects 中，如下所示：

manifest:
  projects:
    - name: some-project
      submodules: ...

submodules 键可以是布尔值或映射列表。下面依次介绍。

方式 1：布尔值

这是使用 submodules 最简单的方式。

如果 submodules 作为 projects 属性取值为 true，则 west update 每次更新项目本身时，都会递归更新该项目的 Git 子模块。如果为 false 或缺失，则不起作用。

例如，假设你有一个源代码仓库 foo，其中有一些子模块，你希望 west update 使所有子模块以及同一工作区中另一个名为 bar 的项目都保持同步。

可以使用以下清单文件实现：

manifest:
  projects:
    - name: foo
      submodules: true
    - name: bar

此时，west update 会初始化并更新 foo 中的所有子模块。如果 bar 有任何子模块，它们会被忽略，因为 bar 没有 submodules 值。

方式 2：映射列表

submodules 键可以是一个映射列表，每个所需的子模块对应一个列表元素。列出的每个子模块都会被递归更新。你仍然可以使用 git 命令手动跟踪和更新未列出的子模块；无论它们是否存在，west 都会完全忽略它们。

path 键必须与某个子模块相对于其父 west 项目的路径完全匹配，即 git submodule status 输出中所显示的路径。name 键是可选的，目前 west 不使用它；它也不会被传递给 git submodule 命令。name 键曾在 west 0.9.0 版本中短暂地成为必需项，但在 0.9.1 中改为可选。

例如，假设你有一个源代码仓库 foo，其中有许多子模块，你希望 west update 使其中一部分（而不是全部）子模块以及同一工作区中另一个名为 bar 的项目保持同步。

可以使用以下清单文件实现：

manifest:
  projects:
    - name: foo
      submodules:
        - path: path/to/foo-first-sub
        - name: foo-second-sub
          path: path/to/foo-second-sub
    - name: bar

此时，west update 只会递归初始化并更新 foo 中路径为 path/to/foo-first-sub 和 path/to/foo-second-sub 的子模块。bar 中的任何子模块仍然会被忽略。

仓库用户数据

West v0.12 及更高版本支持项目中的可选 userdata 键。

West v0.13 及更高版本支持在 manifest: self: 节中使用此键。

它供需要用户专用项目元数据的程序使用。除了将其解析为 YAML 之外，west 本身完全忽略该值。

该键的值是任意 YAML。West 会解析该值，并将其作为相应 west.manifest.Project 对象的 userdata 属性，供使用 West 的 API 的程序访问。

清单片段示例：

manifest:
  projects:
    - name: foo
    - name: bar
      userdata: a-string
    - name: baz
      userdata:
        key: value
  self:
    userdata: blub

Python 用法示例：

manifest = west.manifest.Manifest.from_file()

foo, bar, baz = manifest.get_projects(['foo', 'bar', 'baz'])

foo.userdata # None
bar.userdata # 'a-string'
baz.userdata # {'key': 'value'}
manifest.userdata # 'blub'

清单导入

可以使用上文简要介绍过的 import 键，将其他清单文件中的项目包含到你的 west.yml 中。此键可以是 project 或 self 节的属性：

manifest:
  projects:
    - name: some-project
      import: ...
  self:
    import: ...

可以使用“self: import:”从包含 west.yml 的仓库中加载其他文件。可以使用“project: ... import:”加载该项目 Git 历史中定义的其他文件。

West 按以下顺序根据各个清单文件解析出最终清单：

  1. self 中导入的文件

  2. 你的 west.yml 文件

  3. projects 中导入的文件

在解析过程中，west 会忽略已在其他文件中定义过的项目。例如，如果你的 west.yml 中有一个名为 foo 的项目，west 就会忽略从 projects 列表中导入的其他名为 foo 的项目。

故障排除提示

如果你在使用此功能时觉得 west 的行为令人困惑，请尝试 解析你的清单，查看导入完成后的最终结果。

方式 1：布尔值

这是使用 import 最简单的方式。

如果 import 作为 projects 属性取值为 true，west 会从该项目根目录下的 west.yml 文件导入项目。如果为 false 或缺失，则不起作用。例如，以下清单会从 p1 git 仓库的 v1.0 修订版本导入 west.yml：

manifest:
  # ...
  projects:
    - name: p1
      revision: v1.0
      import: true    # Import west.yml from p1's v1.0 git tag
    - name: p2
      import: false   # Nothing is imported from p2.
    - name: p3        # Nothing is imported from p3 either.

在 self 中将 import 设置为 true 或 false 都是错误的，例如：

manifest:
  # ...
  self:
    import: true  # Error

示例 1.1：Zephyr 发布版本的下游

你有一个源代码仓库，希望将其与 Zephyr v1.14.1 LTS 一起使用。你希望使用 west 维护整个工作区，并且不想修改任何主线仓库。

换句话说，你想要的 west 工作区如下所示：

my-downstream/
├── .west/                     # west directory
├── zephyr/                    # mainline zephyr repository
│   └── west.yml               # the v1.14.1 version of this file is imported
├── modules/                   # modules from mainline zephyr
│   ├── hal/
│   └── [...other directories..]
├── [ ... other projects ...]  # other mainline repositories
└── my-repo/                   # your downstream repository
    ├── west.yml               # main manifest importing zephyr/west.yml v1.14.1
    └── [...other files..]

可以使用以下 my-repo/west.yml 实现：

# my-repo/west.yml:
manifest:
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
  projects:
    - name: zephyr
      remote: zephyrproject-rtos
      revision: v1.14.1
      import: true

然后，假设 my-repo 托管在 https://git.example.com/my-repo，可以像这样在你的计算机上创建工作区：

west init -m https://git.example.com/my-repo my-downstream
cd my-downstream
west update

west init 之后，my-downstream/my-repo 会被克隆。

west update 之后，zephyr 仓库 v1.14.1 修订版本的 west.yml 中定义的所有项目也都会被克隆到 my-downstream 中。

此时，你可以向 my-repo 添加并提交任何代码，包括你自己的 Zephyr 应用程序、驱动等。请参阅 应用程序开发。

示例 1.2：“滚动发布”的 Zephyr 下游

这与 示例 1.1：Zephyr 发布版本的下游 类似，只是对 zephyr 仓库使用 revision: main：

# my-repo/west.yml:
manifest:
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
  projects:
    - name: zephyr
      remote: zephyrproject-rtos
      revision: main
      import: true

可以用同样的方式创建工作区：

west init -m https://git.example.com/my-repo my-downstream
cd my-downstream
west update

这一次，每当运行 west update 时，zephyr 仓库中特殊的 manifest-rev 分支都会被更新，指向从 URL https://github.com/zephyrproject-rtos/zephyr 新获取的 main 分支最新提交。

随后将使用新 manifest-rev 处的 zephyr/west.yml 内容从 Zephyr 导入项目。这样可以让你及时跟上 Zephyr 项目的最新更改。代价是运行 west update 不会产生可重现的结果，因为每次运行时远程的 main 分支都可能已经改变。

还需要理解的是，west 在解析导入时会 完全忽略你工作树中的 zephyr/west.yml。从项目导入时，west 始终使用被导入清单在最新 manifest-rev 中已提交的内容。

只有位于清单仓库工作树中的清单，才能从文件系统导入。示例请参阅 示例 2.2：带有清单文件目录的下游。

示例 1.3：Zephyr 发布版本的下游，带有模块派生

此清单与 示例 1.1：Zephyr 发布版本的下游 中的清单类似，不同之处在于它：

  • 是 Zephyr 2.0 的下游

  • 包含该发布版本中所含 modules/hal/nordic 模块 的一个下游派生（fork）

# my-repo/west.yml:
manifest:
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
    - name: my-remote
      url-base: https://git.example.com
  projects:
    - name: hal_nordic         # higher precedence
      remote: my-remote
      revision: my-sha
      path: modules/hal/nordic
    - name: zephyr
      remote: zephyrproject-rtos
      revision: v2.0.0
      import: true             # imported projects have lower precedence

# subset of zephyr/west.yml contents at v2.0.0:
manifest:
  defaults:
    remote: zephyrproject-rtos
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
  projects:
  # ...
  - name: hal_nordic           # lower precedence, values ignored
    path: modules/hal/nordic
    revision: another-sha

使用此清单文件时，名为 hal_nordic 的项目：

  • 从 https://git.example.com/hal_nordic 而不是 https://github.com/zephyrproject-rtos/hal_nordic 克隆。

  • 会被 west update 更新到提交 my-sha，而不是主线提交 another-sha

换句话说，当顶层清单定义了某个项目（例如 hal_nordic）时，west 在解析导入的过程中会忽略之后找到的该项目的任何其他定义。

这确实意味着在 my-repo/west.yml 中定义 hal_nordic 时，你必须把 path: modules/hal/nordic 值复制过去。zephyr/west.yml 中的值会被完全忽略。如果在实践中这让你感到困惑，请参阅 解析清单 获取故障排除建议。

运行 west update 时，west 会：

  • 将 zephyr 的 manifest-rev 更新为指向 v2.0.0 标签

  • 导入该 manifest-rev 处的 zephyr/west.yml

  • 在本地为除 hal_nordic 之外的所有 zephyr 项目检出 v2.0.0 修订版本

  • 将 hal_nordic 更新到 my-sha 而不是 another-sha

方式 2：相对路径

import 的值也可以是指向某个清单文件或包含清单文件的目录的相对路径。该路径相对于 import 键所在的 projects 或 self 仓库的根目录。

下面是一个示例：

manifest:
  projects:
    - name: project-1
      revision: v1.0
      import: west.yml
    - name: project-2
      revision: main
      import: p2-manifests
  self:
    import: submanifests

这将导入以下内容：

  • manifest-rev 处的 project-1/west.yml 内容，运行 west update 后该分支指向标签 v1.0

  • west update 所获取的 main 分支最新提交中，project-2/p2-manifests 目录树下的所有 YAML 文件，按文件名排序

  • 清单仓库中 submanifests 下的 YAML 文件，以它们在文件系统中的状态为准，按文件名排序

注意，projects 导入使用 manifest-rev 从 Git 获取数据，而 self 导入从文件系统获取数据。这是因为与平常一样，west 将清单仓库的版本控制交由你自己负责。

示例 2.1：使用显式路径的 Zephyr 发布版本下游

这是编写与 示例 1.1：Zephyr 发布版本的下游 中清单等价的清单的一种显式写法。

manifest:

    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
  projects:
    - name: zephyr
      remote: zephyrproject-rtos
      revision: v1.14.1
      import: west.yml

设置 import: west.yml 表示使用 zephyr 项目中的 west.yml 文件。这个例子是刻意构造的，但能说明思路。

当要导入的清单文件的名称不是 west.yml 时，这在实践中会很有用。

示例 2.2：带有清单文件目录的下游

你的 Zephyr 下游有大量额外的仓库。事实上，数量多到你想把它们拆分到多个清单文件中，但仍在单个清单仓库中跟踪所有这些文件，如下所示：

my-repo/
├── submanifests
│   ├── 01-libraries.yml
│   ├── 02-vendor-hals.yml
│   └── 03-applications.yml
└── west.yml

除了 zephyr/west.yml 中的项目之外，你还想把 my-repo/submanifests 中的所有文件都添加到主清单文件 my-repo/west.yml 中。你想跟踪 Zephyr 仓库 main 分支中的最新开发代码，而不是使用固定的修订版本。

方法如下：

# my-repo/west.yml:
manifest:
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
  projects:
    - name: zephyr
      remote: zephyrproject-rtos
      revision: main
      import: true
  self:
    import: submanifests

解析期间，清单文件按以下顺序导入：

  1. my-repo/submanifests/01-libraries.yml

  2. my-repo/submanifests/02-vendor-hals.yml

  3. my-repo/submanifests/03-applications.yml

  4. my-repo/west.yml

  5. zephyr/west.yml

备注

本例中 .yml 文件名以数字为前缀，以确保它们按指定顺序导入。

你可以选择任意名称。West 在导入前会按名称对目录中的文件进行排序。

注意，submanifests 中的清单是在 my-repo/west.yml 和 zephyr/west.yml 之前 导入的。一般而言，self 节中的 import 会先于 projects 中的清单文件以及主清单文件处理。

这意味着 my-repo/submanifests 中定义的项目优先级最高。例如，如果 01-libraries.yml 定义了 hal_nordic，那么 zephyr/west.yml 中的同名项目就会被直接忽略。与往常一样，故障排除建议请参阅 解析清单。

这看起来可能有些奇怪，但它允许你“事后”重新定义项目，正如下一个示例所示。

示例 2.3：持续集成覆盖

你的持续集成系统需要从某个开发者的派生仓库而不是主线开发树中获取并测试 west 工作区中的多个仓库，以检查这些更改能否良好地协同工作。

以 示例 2.2：带有清单文件目录的下游 为基础，CI 脚本在 my-repo/submanifests 中添加一个文件 00-ci.yml，内容如下：

# my-repo/submanifests/00-ci.yml:
manifest:
  projects:
    - name: a-vendor-hal
      url: https://github.com/a-developer/hal
      revision: a-pull-request-branch
    - name: an-application
      url: https://github.com/a-developer/application
      revision: another-pull-request-branch

CI 脚本在 my-repo/submanifests 中生成此文件后运行 west update。00-ci.yml 中定义的项目比 my-repo/submanifests 中的其他定义优先级更高，因为文件名 00-ci.yml 排在其他文件名之前。

因此，即使名为 a-vendor-hal 和 an-application 的项目在其他地方也有定义，west update 也总是会在这些项目中检出该开发者的分支。

方式 3：映射

import 键也可以包含一个带有以下键的映射：

  • file：可选。要导入的清单文件或目录的名称。如果不存在，则默认为 west.yml。

  • name-allowlist：可选。如果存在，则为要包含的项目名称或项目名称序列。

  • path-allowlist：可选。如果存在，则为要匹配的项目路径或项目路径序列。这是一种 shell 风格的通配模式，目前使用 pathlib 实现。注意，这意味着是否区分大小写取决于平台。

  • name-blocklist：可选。与 name-allowlist 类似，但包含的是要排除而不是要包含的项目名称。

  • path-blocklist：可选。与 path-allowlist 类似，但包含的是要排除而不是要包含的项目路径。

  • path-prefix：可选（v0.8.0 新增）。如果给出，它会被添加到该项目在工作区中的路径之前，以及所有被导入项目的路径之前。这可用于将这些项目放到工作区的某个子目录中。

如果同时给出了允许列表和阻止列表，则允许列表优先。例如，如果某个项目按路径被阻止，但又按名称被允许，它仍然会被导入。

  4. 最后是 another-manifest-repo/submanifests 中的文件（按文件名排序），因为它是最后一个项目 import

清单导入详解

本节更正式地介绍 west 如何解析使用了 import 的清单文件。

概述

import 键可以出现在 west 清单的 projects 和 self 节中。一般情况如下所示：

# Top-level manifest file.
manifest:
  projects:
    - name: foo
      import:
        ... # import-1
    - name: bar
      import:
        ... # import-2
    # ...
    - name: baz
      import:
        ... # import-N
  self:
    import:
      ... # self-import

导入键是可选的。如果 import-1, ..., import-N 中的任何一个缺失，west 就不会从对应项目导入额外的清单数据。如果 self-import 缺失，则不会导入清单仓库中（顶层文件之外）的任何其他文件。

解析清单导入的最终结果是：

  • 一个 projects 列表，由顶层文件中定义的 projects 与被导入文件中定义的项目合并而成

  • 一组扩展命令，取自顶层文件和所有被导入文件中的 west-commands 键

  • 一个 group-filter 列表，由顶层过滤器和所有被导入的过滤器合并而成

导入按以下顺序进行：

  1. 首先导入 self-import 中的清单。

  2. 接下来处理顶层清单文件中的定义。

  3. 按顺序导入 import-1, ..., import-N 中的清单。

当单个 import 键引用多个清单文件时，按以下顺序处理：

  • 如果值是指向某个目录的相对路径（或者其 file 为目录的映射），则其中包含的清单文件按字典序（即按文件名排序）处理。

  • 如果值是一个序列，则按其元素出现的顺序递归导入。

必要时此过程会递归进行。例如，如果 import-1 产生的清单文件中包含 import 键，则在进一步处理其内容之前，先按照相同规则递归解析它。

以下各节介绍这些结果。

项目

本节介绍最终的 projects 列表是如何生成的。

项目通过名称标识。如果同一名称出现在多个清单中，则使用第一个定义，后续定义会被忽略。例如，如果 import-1 包含一个名为 bar 的项目，它会被忽略，因为顶层 west.yml 已经定义了同名项目。

import-1 到 import-N 所指定文件的内容，从其所在项目最新的 manifest-rev 修订版本处从 Git 导入。运行 west update 可以将这些修订版本更新为 rev-1 到 rev-N 的值。如果任何 manifest-rev 引用缺失或已过时，west update 还会从远程获取 URL 获取项目数据并更新该引用。

还需注意，为了让 west 更新项目 P 本身，从根清单到定义项目 P 的仓库之间的所有被导入清单都必须是最新的。例如，这意味着如果 baz/west.yml 定义了 P，那么 west update P 除了会更新 P 本地 git 克隆中的 manifest-rev 分支之外，还会更新 baz 项目中的 manifest-rev。令人困惑的是，更新 baz 可能导致 P 从 baz/west.yml 中被移除，这“应当”会使 west update P 因项目无法识别而失败！

因此，如果 P 是在被导入的清单中定义的，就无法运行 west update P；你必须使用普通的 west update 将该项目与其他所有项目一起更新。

默认情况下，如果项目的修订版本是本地已有的 SHA 或标签，west 不会通过网络获取任何项目数据，因此除非确实需要，更新这些额外的项目不会花费太多时间。更多信息请参阅 update.fetch 配置选项的文档。

扩展

在处理导入期间发现的、使用 west-commands 键定义的所有扩展命令，都可以在解析后的清单中使用。

如果某个被导入的清单文件在其 self: 节中有 west-commands: 定义，则在导入该清单时，其中定义的扩展命令会被添加到可用扩展的集合中。因此，它们的优先级高于之后添加的同名扩展命令。

组过滤器

解析后的清单有一个 group-filter 值，它是将顶层清单和所有被导入清单中的 group-filter 值串联起来的结果。

在导入顺序中出现得越早的清单文件优先级越高，因此在最终的 group-filter 中被串联得越靠后。

换句话说，设：

  • 从 self-import 解析出的子清单具有组过滤器 self-filter

  • 顶层清单文件具有组过滤器 top-filter

  • 从 import-1 到 import-N 解析出的子清单分别具有组过滤器 filter-1 到 filter-N

那么最终解析出的 group-filter 值为 filterN + ... + filter-2 + filter-1 + top-filter + self-filter，其中 + 表示列表串联。

重要

过滤器在上述列表中出现的顺序很重要。

最终串联列表中的最后一个过滤器元素“胜出”，并决定该组是启用还是禁用。

例如，在 [-foo] + [+foo] 中，组 foo 是 启用的。但在 [+foo] + [-foo] 中，组 foo 是 禁用的。

为简单起见，west 和本文档可能会根据这些规则省略串联后多余的组过滤器元素。例如，根据上面给出的理由，[+foo] + [-foo] 可以更简单地写成 [-foo]。再如，[-foo] + [+foo] 可以写成空列表 []，因为所有组默认都是启用的。

清单命令

west manifest 命令可用于操作清单文件。它接受一个操作以及该操作专用的参数。

以下各节介绍每个操作，并给出简单用法的基本形式。运行 west manifest --help 可获得所有选项的完整细节。

解析清单

--resolve 操作输出单个清单文件，其内容等价于当前清单及其所有 被导入的清单：

west manifest --resolve [-o outfile]

此操作的主要用途是查看执行所有 import 之后“最终”的清单内容。

要打印每个被导入清单文件的详细信息，以及清单解析过程中如何处理各个项目，请使用 -v 设置最高详细级别：

west -v manifest --resolve

冻结清单

--freeze 操作输出一个冻结的清单：

west manifest --freeze [-o outfile]

“冻结”的清单是指每个项目的修订版本都是 SHA 的清单文件。可以使用 --freeze 生成一个与当前清单文件等价的冻结清单。-o 选项指定输出文件；如果未给出，则使用标准输出。

验证清单

如果当前清单文件有效，--validate 操作就会成功；否则会失败并报错：

west manifest --validate

错误消息有助于诊断错误。

这里的“无效”是指清单文件的语法不符合本页所记录的规则。

如果清单有效，但其工作方式不符合你的预期，使用 -v 提高详细程度是一个好办法，可以获得 west 对你的清单做出了哪些决定以及原因的详细信息：

west -v manifest --validate

获取清单路径

--path 操作打印顶层清单文件的路径：

west manifest --path

输出类似于 /path/to/workspace/west.yml。路径格式取决于你的操作系统。
