构建：west build

小技巧

运行 west build -h 可快速了解概况。

build 命令可帮助你从源代码构建 Zephyr 应用程序。可以使用 west config 配置其行为。

其默认行为会尽量“按你的意图行事”：

  • 如果当前工作目录中有一个名为 build 的 Zephyr 构建目录，则对其进行增量重新编译。如果在某个 Zephyr 构建目录中运行 west build，也是如此。

  • 否则，如果在 Zephyr 应用程序的源代码目录中运行 west build 且未找到构建目录，则会创建一个新的构建目录，并在其中编译该应用程序。

基础

使用 west build 最简单的方法是进入应用程序的根目录（即包含应用程序 CMakeLists.txt 的文件夹），然后运行：

west build -b <BOARD>

其中 <BOARD> 是要为其构建的开发板名称。它与直接调用 CMake 时所提供的名称完全相同：cmake -DBOARD=<BOARD>。

小技巧

可以使用 west boards 命令列出所有支持的开发板。

west build 会创建一个名为 build 的构建目录，运行 CMake 在该目录中生成构建系统，然后在其中编译应用程序。如果 west build 找到已有的构建目录，则在其中对应用程序进行增量重新编译，而不重新运行 CMake。可以使用 --cmake 强制 CMake 重新运行。

如果已经有一个构建目录，就不需要使用 --board 选项；west build 可以从 CMake 缓存中推断出开发板。对于新的构建，会（按顺序）检查 --board 选项、BOARD 环境变量或 build.board 配置选项。

Sysbuild（多域构建）

Sysbuild（系统构建） 可用于创建多域构建系统，为单个或多个开发板组合多个镜像。

在 west build 中使用 --sysbuild 选择 Sysbuild（系统构建） 构建基础设施，以构建多个域。

有关使用 sysbuild 的更多详细信息，请参阅 Sysbuild（系统构建） 指南。

小技巧

可以启用 build.sysbuild 配置选项，让 west build 默认使用 sysbuild 进行构建。可以使用 --no-sysbuild 为某次构建禁用 sysbuild。

west build 会通过 sysbuild 所指定各个域的顶层构建文件夹构建所有域。

可以使用 --domain 参数构建多域项目中的单个域。

示例

下面是一些 west build 用法示例，按领域分组。

强制 CMake 重新运行

要强制重新运行 CMake，请使用 --cmake （或 -c）选项：

west build -c

设置默认开发板

要将 west build 配置为默认为 reel_board 构建：

west config build.board reel_board

（此处可以使用 Zephyr 支持的任何其他开发板，不一定是 reel_board。）

设置源代码目录和构建目录

要显式设置应用程序源代码目录，请将其路径作为位置参数给出：

west build -b <BOARD> path/to/source/directory

要显式设置构建目录，请使用 --build-dir （或 -d）：

west build -b <BOARD> --build-dir path/to/build/directory

要更改默认的构建目录 build，请使用 build.dir-fmt 配置选项。这样就可以使用格式字符串为构建目录命名，例如：

west config build.dir-fmt "build/{board}/{app}"

如上设置后，运行 west build -b reel_board samples/hello_world 将使用构建目录 build/reel_board/hello_world。有关此选项的更多细节，请参阅 配置选项。

设置构建系统目标

要指定要运行的构建系统目标，请使用 --target （或 -t）。

例如，在带有 QEMU 的主机平台上，可以使用 run 目标，通过一条命令为模拟的 qemu_x86 开发板构建并运行 Hello World 示例：

west build -b qemu_x86 -t run samples/hello_world

再举一个例子，使用 -t 列出所有构建系统目标：

west build -t help

最后一个例子，使用 -t 运行 pristine 目标，它会删除构建目录中的所有文件：

west build -t pristine

全新构建

全新（pristine） 构建目录本质上就是一个新的构建目录，以前构建产生的所有副产物都已被删除。

要强制 west build 在重新运行 CMake 生成构建系统之前将构建目录恢复为全新状态，请使用 --pristine=always （或 -p=always）选项。

给出不带值的 --pristine 或 -p，与给出值 always 的效果相同。例如，以下命令是等价的：

west build -p -b reel_board samples/hello_world
west build -p=always -b reel_board samples/hello_world

默认情况下，west build 不会尝试检测构建目录是否需要恢复为全新状态。如果你尝试将某个构建目录重用于不同的 --board 之类的操作，就可能导致错误。

使用 --pristine=auto 可以让 west build 检测其中的一些情况，并在尝试构建之前将构建目录恢复为全新状态。

小技巧

可以运行 west config build.pristine always 以始终进行全新构建，或者运行 west config build.pristine never 禁用这种启发式检测。详情请参阅 west build 的 配置选项。

详细构建

要打印 west build 所运行的 CMake 和编译器命令，请使用全局 west 详细程度选项 -v：

west -v build -b reel_board samples/hello_world

一次性 CMake 参数

要向 west build 执行的 CMake 调用传递额外参数，请将它们放在命令行末尾的 -- 之后。

重要

像这样传递额外的 CMake 参数，会强制 west build 重新运行 CMake 构建配置步骤，即使已经生成了构建系统也是如此。这会使增量构建变慢（但仍然比从头构建快得多）。

使用一次 -- 生成构建目录之后，在后续运行中使用 west build -d <build-dir> 进行增量构建。

或者，按照下一节所述将 CMake 参数设为永久参数；这样不会减慢增量构建。

例如，要使用 Unix Makefiles CMake 生成器代替 Ninja（west build 默认使用 Ninja），请运行：

west build -b reel_board -- -G'Unix Makefiles'

要使用 Unix Makefiles 并将 CMAKE_VERBOSE_MAKEFILE 设置为 ON：

west build -b reel_board -- -G'Unix Makefiles' -DCMAKE_VERBOSE_MAKEFILE=ON

注意，尽管给出了多个 CMake 参数，-- 只出现一次。west build 命令行中 -- 之后的所有参数都会传递给 CMake。

要将 DTC_OVERLAY_FILE 设置为 enable-modem.overlay，从而将该文件用作 设备树覆盖文件（overlay）：

west build -b reel_board -- -DDTC_OVERLAY_FILE=enable-modem.overlay

要将 Kconfig 片段 file.conf 合并到构建的 .config 中：

west build -- -DEXTRA_CONF_FILE=file.conf

永久 CMake 参数

上一节介绍了如何为单条 west build 命令添加 CMake 参数。如果希望保存 CMake 参数，让 west build 每次生成新的构建系统时都使用它们，应当使用 build.cmake-args 配置选项。每当 west build 运行 CMake 生成构建系统时，都会按照 shell 规则拆分此选项的值，并将结果加入 cmake 命令行中。

请记住，默认情况下，如果构建目录中已存在构建系统，west build 会尽量避免生成新的构建系统。因此，设置 build.cmake-args 之后，需要删除所有已有的构建目录，或者执行 全新构建，以确保设置生效。

例如，要始终启用 CMAKE_EXPORT_COMPILE_COMMANDS，可以运行：

west config build.cmake-args -- -DCMAKE_EXPORT_COMPILE_COMMANDS=ON

（额外的 -- 用于强制将命令的其余部分视为位置参数。如果没有它，west config 会把 -DVAR=VAL 语法视为对其 -D 选项的使用。）

要启用 CMAKE_VERBOSE_MAKEFILE，使 CMake 始终生成详细输出的构建系统：

west config build.cmake-args -- -DCMAKE_VERBOSE_MAKEFILE=ON

要在 build.cmake-args 中保存多个参数，请使用一个其值可以拆分为不同参数的字符串（west build 在内部使用 Python 函数 shlex.split() 拆分该值）。

例如，要同时启用 CMAKE_EXPORT_COMPILE_COMMANDS 和 CMAKE_VERBOSE_MAKEFILE：

west config build.cmake-args -- "-DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DCMAKE_VERBOSE_MAKEFILE=ON"

如果希望将 CMake 参数保存在单独的文件中，可以将 CMake 的 -C <initial-cache> 选项与 build.cmake-args 结合使用。例如，设置上例所用选项的另一种方法是创建一个名为 ~/my-cache.cmake 的文件，内容如下：

set(CMAKE_EXPORT_COMPILE_COMMANDS ON CACHE BOOL "")
set(CMAKE_VERBOSE_MAKEFILE ON CACHE BOOL "")

然后运行：

west config build.cmake-args "-C ~/my-cache.cmake"

更多细节请参阅 cmake(1) manual page 和 set() command 文档。

构建工具参数

使用 -o 向底层构建工具传递选项。

这同时适用于基于 ninja （默认）和基于 make 的构建系统。

例如，要向 ninja 传递 -dexplain：

west build -o=-dexplain

再举一个例子，要向 make 传递 --keep-going：

west build -o=--keep-going

注意，必须使用 -o=--foo 而不是 -o --foo，以防止 --foo 被当作 west build 的选项。

构建并行度

默认情况下，ninja 使用所有核心进行构建，而 make 只使用一个核心。可以使用这两个工具都支持的 -j 选项显式控制并行度。

例如，使用 4 个核心进行构建：

west build -o=-j4

上一节对 -o 选项有进一步的说明。

构建单个域

在包含 Hello World 和 MCUboot 的多域构建中，可以使用 --domain hello_world 只构建该域：

west build --sysbuild --domain hello_world

--domain 参数可以与 --target 参数结合使用，为该域构建特定的目标，例如：

west build --sysbuild --domain hello_world --target help

使用代码片段（snippet）

请参阅 使用代码片段。

配置选项

可以使用以下选项 配置 west build。

选项

说明

build.board

字符串。如果给出，则当未给出 --board 且环境中未设置 BOARD 时，west build 使用该开发板。

build.board_warn

布尔值，默认为 true。如果为 false，则在 west build 无法确定目标开发板时不显示警告。

build.cmake-args

字符串。如果存在，每当生成新的构建系统时，都会按照 shell 规则拆分该值并传递给 CMake。请参阅 永久 CMake 参数。

build.dir-fmt

字符串，默认为 build。构建文件夹格式字符串，每当 west 需要创建或定位构建文件夹时都会使用它。目前可用的参数有：

  • west_topdir：west 工作区的绝对路径，即 west_topdir 命令所返回的路径

  • board：开发板名称

  • source_dir：CMake 源代码目录相对于当前工作目录的路径。如果当前工作目录位于源代码目录内，则为空字符串；在 Windows 上，如果源代码目录位于另一个驱动器上，与当前目录之间不存在相对路径，也是如此。如果未指定源代码目录，则默认为当前工作目录。例如，如果在 <west_topdir>/app1 中运行 west build ../app，则 source_dir 解析为 ../app （即相对于当前工作目录的路径）。

  • source_dir_workspace：源代码目录相对于 west_topdir 的路径（如果源代码目录位于工作区内）。否则，它相对于文件系统根目录（在 Unix 上为 /，在 Windows 上为 C:/）。例如，如果在 <west_topdir>/app1 中运行 west build ../app，则 source_dir 解析为 app （即相对于 west 工作区目录的路径）。

  • app：源代码目录的名称。

build.generator

字符串，默认为 Ninja。用于创建构建系统的 CMake Generator。（要为单次构建设置生成器，请参阅 上面的示例）

build.guess-dir

字符串，指示在使用 build.dir-fmt 且没有足够信息来解析构建文件夹名称时，west 是否应尝试猜测要使用的构建文件夹。可以取以下值：

  • never （默认）：从不尝试猜测，而是退出并要求用户使用 -d 提供构建文件夹。

  • runners：在使用任何“运行器（runner）”命令时尝试猜测文件夹。这些命令通常是所有调用外部工具的命令，例如 flash 和 debug。

build.pristine

字符串。控制 west build 在构建之前清理构建文件夹的方式。可以取以下值：

  • never （默认）：从不自动将构建文件夹恢复为全新状态。

  • auto：如果存在构建系统，并且不清理就会导致构建失败（例如用户指定的开发板或应用程序与之前创建该构建目录时所用的不同），west build 会在构建之前自动将构建文件夹恢复为全新状态。

  • always：如果存在构建系统，则总是在构建之前将构建文件夹恢复为全新状态。

build.sysbuild

布尔值，默认为 false。如果为 true，则使用 sysbuild 基础设施构建应用程序。

烧录：west flash

小技巧

运行 west flash -h 获取更多帮助。

基础

在 Zephyr 构建目录中，重新构建二进制文件并将其烧录到开发板：

west flash

要指定构建目录，请使用 --build-dir （或 -d）：

west flash --build-dir path/to/build/directory

如果未指定构建目录，west flash 会先在 build 中查找，然后在当前工作目录中查找。如果设置了 build.dir-fmt 配置选项（请参阅 设置源代码目录和构建目录），west flash 会在该位置而不是 build 中查找。

选择运行器

如果开发板的 Zephyr 集成支持使用多个程序进行烧录，可以使用 --runner （或 -r）选项指定要使用哪一个。例如，如果 West 默认使用 nrfjprog 烧录你的开发板，但开发板也支持 JLink，可以这样覆盖默认值：

west flash --runner jlink

可以在构建时使用 CMake 变量 BOARD_FLASH_RUNNER 覆盖默认的烧录运行器，使用 BOARD_DEBUG_RUNNER 覆盖默认的调试运行器。

例如：

# Set the default runner to "jlink", overriding the board's
# usual default.
west build [...] -- -DBOARD_FLASH_RUNNER=jlink

有关设置 CMake 参数的更多信息，请参阅 一次性 CMake 参数 和 永久 CMake 参数。

class runners.core.RunnerCaps(commands: set[str] = <factory>, dev_id: bool = False, mult_dev_ids: bool = False, flash_addr: bool = False, erase: bool = False, reset: bool = False, reset_types: bool = False, reset_types_supported: list[str] | None = None, extload: bool = False, tool_opt: bool = False, gdb_init: bool = False, file: bool = False, hide_load_files: bool = False, rtt: bool = False, dry_run: bool = False, skip_load: bool = False, batch_debug: bool = False)

此类表示一个运行器类的能力。

每项能力都表示为一个同名属性。标志属性的值为 True 或 False。

可用的能力：

  • commands：支持的命令集合；默认为 {'flash', 'debug', 'debugserver', 'attach', 'simulate', 'robot', 'rtt'}。

  • dev_id：运行器是否支持以 -i、--dev-id 选项形式给出的设备标识符。当用户在一台计算机上连接了多个调试器时，这可用于选择所给命令要使用哪一个调试器。

  • mult_dev_ids：运行器是否支持在单次操作中使用多个设备标识符，从而批量烧录设备。

  • flash_addr：运行器是否支持烧录到任意地址。默认为 False。如果为 true，运行器必须遵循 --dt-flash 选项。

  • reset：运行器是否支持 --reset 选项，该选项会在烧录操作完成后复位设备。

  • reset_types：运行器是否支持 --reset-type=x 选项，该选项指定一个运行器专用的值，用于选择复位设备时要使用的特定复位类型。

  • reset_types_supported：允许通过 --reset-type 选项传递的值的列表。如果支持的复位类型列表是动态的或与设备相关，则应省略此项，从而允许设置任意值并直接传递给底层工具。除此之外，每个运行器实现都必须始终能够以运行器特定的方式接受 None。为了方便用户，建议将行为与 None 相同或最接近的值放在列表首位。

  • extload：运行器是否支持 --extload 选项，该选项必须给出一次，并传递给运行器所包装的底层工具。

  • tool_opt：运行器是否支持 --tool-opt（-O）选项，该选项可以给出多次，并传递给运行器所包装的底层工具。

  • file：运行器是否支持 --file 选项，该选项精确指定用于烧录的文件，覆盖在构建目录中发现的任何默认文件。

class runners.core.ZephyrBinaryRunner(cfg: RunnerConfig)

二进制运行器（烧录器、调试器）的抽象超类。

注意：此类的 API 自添加以来很少变化，但它不被视为稳定的 Zephyr API，可能会在不另行通知的情况下更改。

除少数例外，Zephyr 支持的开发板必须提供通用的方式来进行烧录（将 Zephyr 固件二进制文件永久安装到设备上以便运行）和调试（在主机工作站上通过断点调试器和程序加载器连接到正在运行的目标）。

这通过由 Zephyr 构建系统管理的四个顶层命令来支持：

  • 'flash'：将之前配置好的二进制文件烧录到开发板，在目标上开始执行，然后返回。

  • 'debug'：通过调试协议连接到开发板，对 Flash 进行编程，然后将用户带入一个已从当前二进制文件加载符号表的调试器界面，并阻塞直到其退出。

  • 'debugserver'：通过开发板专用的调试协议连接，然后复位并暂停目标。确保用户此时能够连接到一个已从二进制文件加载符号表的调试服务器。

  • 'attach'：通过调试协议连接到开发板，然后将用户带入一个已从当前二进制文件加载符号表的调试器界面，并阻塞直到其退出。与 'debug' 不同，此命令不会对 Flash 进行编程。

此类为这些命令提供 API。每个子类简称为一个“运行器（runner）”。每个运行器都有一个名称（例如 'pyocd'），并声明它能处理的命令（例如 'flash'）。开发板（例如 'nrf52dk/nrf52832'）向 Zephyr 构建系统声明哪些运行器与其兼容，以及如何配置运行器以配合该开发板工作。

随后，构建系统会在构建目录中放入足够的信息，以便使用此类的 create() 方法创建和使用运行器，该方法提供了命令行参数解析 API。也可以直接实例化子类来创建运行器。

要定义自己的运行器，需要：

  1. 定义一个 ZephyrBinaryRunner 子类，并实现其抽象方法。可能需要覆盖 capabilities()。

  2. 确保定义运行器类的 Python 模块被导入，例如通过编辑本包的 __init__.py（否则 get_runners() 将无法工作）。

  3. 在开发板的 board.cmake 中将运行器名称告知 Zephyr 构建系统。

其他建议：

  • 如果需要导入任何非标准库模块，请确保捕获 ImportError，并在缺少模块时将报错推迟为 RuntimeError。这样可以避免影响不需要你的运行器的用户，同时也能让需要该运行器但未安装必要模块的用户清楚地知道出了什么问题。

  • 如果需要向用户询问某些内容（例如使用 input()），请在 create() 类方法中进行，而不是在 do_run() 中。这样可以确保 __init__() 确实拥有调用 do_run() 所需的一切，并且在非命令行应用程序中实例化时也能避免调用 input()。

  • 使用 self.logger 通过标准库的 logging API 记录消息；你的 logger 名为 "runner.<your-runner-name()>"

为了供 Zephyr 构建系统通过命令行调用，运行器通过公共的 add_parser()（以及它所委托的运行器专用 do_add_parser()）定义自己基于 argparse 的接口，并通过 create() 提供一种根据 RunnerConfig 和已解析的运行器专用参数创建自身实例的方法。

运行器会使用各种主机工具和配置值，此类对它们的用户接口进行了抽象。每个运行器子类都应在其构造函数中接收执行这些命令之一所需的全部值。实际的命令执行在 run() 方法中处理。

手动操作

如果不想使用 West 烧录或调试开发板，只需在构建目录中查看构建系统输出的二进制文件。根据开发板的构建系统集成方式，它们的名称类似 zephyr/zephyr.elf、zephyr/zephyr.hex 等。可以使用你选择的其他工具将这些二进制文件烧录到开发板，或根据需要将其用于调试，例如作为符号表的来源。

默认情况下，这些 West 命令会在烧录和调试之前重新构建二进制文件。当然，这也可以使用 Zephyr 构建系统提供的常规目标来完成（事实上，这些命令正是这样做的）。
