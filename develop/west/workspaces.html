工作区

本页更详细地介绍 基础知识 中引入的 west 工作区 概念。

manifest-rev 分支

West 会在每个项目中创建并控制一个名为 manifest-rev 的 Git 分支。该分支指向上次运行 west update 时清单文件为该项目指定的修订版本。其他工作区管理命令可能会将 manifest-rev 作为这次最新更新时上游修订版本的参考点。manifest-rev 分支的用途之一，是允许清单文件使用 SHA 作为项目修订版本。

虽然 manifest-rev 是一个普通的 Git 分支，但 west 会在下次更新时重新创建和/或重置它。因此，自行检出或以其他方式修改它是 危险的。例如，你手动添加到该分支上的任何提交，都可能在下次运行 west update 时丢失。正确的做法是检出另一个名称的本地分支，然后将其变基到新的 manifest-rev 之上，或者将 manifest-rev 合并到其中。

备注

West 不会在清单仓库中创建 manifest-rev 分支，因为 west 不管理清单仓库的分支或修订版本。

refs/west/* Git 引用

West 还在本地项目仓库中为自己保留了所有以 refs/west/ 开头的 Git 引用（例如 refs/west/foo）。与 manifest-rev 不同，这些引用不是常规分支。West 在这方面的行为属于实现细节；用户不应依赖这些引用的存在或行为。

在 git 仓库中进行开发

工作区中的 west “项目”就是普通的 git 仓库。在不受干预的情况下，west 只会创建和更新 manifest-rev 分支以及 refs/west/ 下的引用；你创建的分支归你所有，只有当你通过 west update --rebase 要求时，west 才会对它们执行变基。

这也是普通的 west update 会让你处于分离 HEAD 状态的原因：它检出新的 manifest-rev，而让你的分支完全保持原位。原因请参阅 west update 的分离 HEAD。

备注

Zephyr 模块 和 west 项目不是一回事，尽管 west 项目通常也是模块；请参阅 模块与 west 项目。下面的 git 工作流适用于所有 west 项目，无论它们是否是 Zephyr 模块。

有本地更改时，一种行之有效的工作流如下：

  1. 在仓库中创建一个分支，并照常向其提交：

    git -C <repository-path> switch --create <your-branch>

  2. 使用 west update --rebase 更新工作区，然后查看发生了哪些变化：

    west update --rebase
west compare

    你的分支会保持检出状态，并被变基到新的 manifest-rev 之上。这是 west 唯一会改动你自己分支的情况。如果发生冲突，命令会失败，你可以照常使用 git 解决冲突。

  3. 如果不希望 west 对你的分支执行变基，普通的 west update 会改为从该分支切换出去（除非这会导致 git 冲突）。west update --keep-descendants 是永远不会失败的第三种选择。所有细节请参阅 west update --help 中的 checked out branch behavior 选项组以及 west update。

在分离 HEAD 上提交

不要在 west update 留下的分离 HEAD 上提交：git 会警告你这些提交无法从任何分支访问，之后可能会被垃圾回收。请为你的工作创建一个分支；或者使用专为“无分支”工作而设计的其他 git 客户端，例如 JJ。

私有仓库

可以使用 west 从私有仓库获取。这方面没有任何 west 特有的内容。

当项目的 manifest-rev 分支必须更新到新获取的提交时，west update 命令实质上会运行 git fetch YOUR_PROJECT_URL。确保获取成功是你的环境要负责的事情。

可以手动输入密码，也可以使用任何 credential helpers built in to Git。由于 Git 内置了凭据存储功能，因此不需要 west 专门提供这一功能。

以下各节介绍无需输入密码即可运行 west update 的常见情况，以及如何排查问题。

通过 HTTPS 获取

在 Windows 上从 GitHub 获取时，较新版本的 Git 会在图形窗口中提示你输入一次 GitHub 密码，然后将其保存以供将来使用（默认安装下如此）。因此，在 Windows 上完成一次之后，无密码地从 GitHub 获取应当“开箱即用”。

一般来说，可以使用“store”git 凭据助手将凭据保存在磁盘上。详情请参阅 git-credential-store 手册页。

要对工作区中的所有仓库使用此助手，请运行：

west forall -c "git config credential.helper store"

要只对项目 foo 和 bar 使用此助手，请运行：

west forall -c "git config credential.helper store" foo bar

要在你的计算机上默认使用此助手，请运行：

git config --global credential.helper store

在 GitHub 上，可以设置一个 personal access token 来代替账户密码。（如果账户启用了双因素认证，可能必须这样做；即使未启用双因素认证，这也可能比以明文保存账户密码更可取。）

可以像下面这样使用 Git 凭据存储，以 GitHub PAT（个人访问令牌）进行身份验证：

echo "https://x-access-token:$GH_TOKEN@github.com" >> ~/.git-credentials

如果不想在文件系统中保存任何凭据，可以改用 git-credential-cache 将它们临时保存在内存中。

如果设置了通过 SSH 获取，可以使用 Git 的 URL 重写功能。以下命令指示 Git 对 GitHub 使用 SSH URL 而不是 HTTPS URL：

git config --global url."git@github.com:".insteadOf "https://github.com/"

通过 SSH 获取

如果 SSH 密钥没有密码，获取应当可以直接进行。如果有密码，可以使用 ssh-agent 避免每次手动输入。

在 GitHub 上，有关配置和创建密钥的详细信息，请参阅 Connecting to GitHub with SSH。

项目位置

项目可以位于工作区内的任何位置，但不能“逃出”工作区。

换句话说，项目仓库不必位于清单仓库的子目录中，也不必是 topdir 的直接子目录。但是，项目的路径必须位于工作区内。

可以将工作区中某个项目的仓库目录替换为指向计算机上其他位置的符号链接，但 west 不会替你这样做。

支持的拓扑结构

以下是 west 支持的源代码拓扑结构示例。

  • T1：星型拓扑，zephyr 是清单仓库

  • T2：星型拓扑，某个 Zephyr 应用程序是清单仓库

  • T3：森林拓扑，独立的清单仓库

T1：星型拓扑，zephyr 是清单仓库

  • zephyr 仓库充当中心仓库，并在其 west.yml 中指定它的 模块（外部项目）

  • 与现有机制的类比：以 zephyr 为父项目（super-project）的 Git 子模块

这是默认拓扑。主线 Zephyr 如何作为此拓扑的示例，请参阅 工作区概念。

T2：星型拓扑，应用程序是清单仓库

  • 适用于专注于单个应用程序的用户

  • 包含 Zephyr 应用程序的仓库充当中心仓库，并在其 west.yml 中列出构建该应用程序所需的其他项目，包括 zephyr 仓库和任何模块。

  • 与现有机制的类比：以应用程序为父项目、以 zephyr 和其他项目为子模块的 Git 子模块

使用此拓扑的工作区如下所示：

west-workspace/
│
├── application/         # .git/     │
│   ├── CMakeLists.txt               │
│   ├── prj.conf                     │  never modified by west
│   ├── src/                         │
│   │   └── main.c                   │
│   └── west.yml         # main manifest with optional import(s) and override(s)
│                                    │
├── modules/
│   └── lib/
│       └── zcbor/       # .git/ project from either the main manifest or some import.
│
└── zephyr/              # .git/ project
    └── west.yml         # This can be partially imported with lower precedence or ignored.
                         # Only the 'manifest-rev' version can be imported.

下面是一个 application/west.yml 示例，它使用从 west 0.7 开始提供的 清单导入，将 Zephyr v2.5.0 及其模块导入到应用程序清单文件中：

# Example T2 west.yml, using manifest imports.
manifest:
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
  projects:
    - name: zephyr
      remote: zephyrproject-rtos
      revision: v2.5.0
      import: true
  self:
    path: application

以这种方式使用 import: 时，仍然可以有选择地“覆盖”个别 Zephyr 模块；示例请参阅 示例 1.3：Zephyr 发布版本的下游，带有模块派生。

实现同样效果的另一种方法是将 zephyr/west.yml 复制粘贴到 application/west.yml 中，并为 zephyr 项目本身添加一个条目，如下所示：

# Equivalent to the above, but with manually maintained Zephyr modules.
manifest:
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
  defaults:
    remote: zephyrproject-rtos
  projects:
    - name: zephyr
      revision: v2.5.0
      west-commands: scripts/west-commands.yml
    - name: net-tools
      revision: some-sha-goes-here
      path: tools/net-tools
    # ... other Zephyr modules go here ...
  self:
    path: application

（west-commands 用于 构建、烧录和调试 以及其他 Zephyr 专用的 扩展。使用 import 时不需要它。）

使用 import 的主要优点是不必单独跟踪被导入项目的修订版本。在上例中，使用 import 意味着 Zephyr 的 模块 版本会根据 zephyr/west.yml 的修订版本自动确定，而不必单独复制粘贴（并维护）。

T3：森林拓扑

  • 适用于支持多个独立应用程序或下游发行版、且没有“中心”仓库的用户

  • 一个专门的清单仓库，不包含任何 Zephyr 源代码，并指定一组处于同一“层级”的项目

  • 与现有机制的类比：基于 Google repo 的源代码分发

使用此拓扑的工作区如下所示：

west-workspace/
├── app1/               # .git/ project
│   ├── CMakeLists.txt
│   ├── prj.conf
│   └── src/
│       └── main.c
├── app2/               # .git/ project
│   ├── CMakeLists.txt
│   ├── prj.conf
│   └── src/
│       └── main.c
├── manifest-repo/      # .git/ never modified by west
│   └── west.yml        # main manifest with optional import(s) and override(s)
├── modules/
│   └── lib/
│       └── zcbor/      # .git/ project from either the main manifest or
│                       #       from some import
│
└── zephyr/             # .git/ project
    └── west.yml        # This can be partially imported with lower precedence or ignored.
                        # Only the 'manifest-rev' version can be imported.

下面是一个 T3 manifest-repo/west.yml 示例，它使用从 west 0.7 开始提供的 清单导入 导入 Zephyr v2.5.0 及其模块，然后添加 app1 和 app2 项目：

manifest:
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
    - name: your-git-server
      url-base: https://git.example.com/your-company
  defaults:
    remote: your-git-server
  projects:
    - name: zephyr
      remote: zephyrproject-rtos
      revision: v2.5.0
      import: true
    - name: app1
      revision: SOME_SHA_OR_BRANCH_OR_TAG
    - name: app2
      revision: ANOTHER_SHA_OR_BRANCH_OR_TAG
  self:
    path: manifest-repo

也可以按照 上文 中 T2 拓扑所示的方法，通过复制粘贴 zephyr/west.yml “手动”完成，注意事项相同。

不支持：将工作区 topdir 作为 .git 仓库

有些用户要求支持将工作区 topdir 作为 git 仓库，如下例所示：

my-workspace/                  # workspace topdir
├── .git/                      # puts the entire workspace in a git repository
├── .west/                     # marks the location of the topdir
└── [ ... other projects ...]

这 不是 官方支持的拓扑结构。作为一项设计决策，west 假定工作区 topdir 本身不是 git 仓库。

你也许能够让类似的做法满足你自己的需求而“正常工作”。但是，west 的未来版本可能包含会“破坏”你这种设置的更改。
