模块（外部项目）

Zephyr 依赖若干外部维护项目的源代码，以避免重复造轮子，并在合理的情况下尽可能复用成熟可靠的代码。在 Zephyr 构建系统的语境中，这些项目被称为 模块。这些模块必须与 Zephyr 构建系统集成，本页其他各节会对此进行更详细的说明。

要成为默认模块列表的候选者，外部项目必须拥有独立于 Zephyr 项目之外的生命周期，也就是说，它位于自己的仓库中，并有自己的贡献与维护流程以及发布流程。Zephyr 模块不应包含专为 Zephyr 编写的代码。这类代码应当贡献到 Zephyr 主源码树中。

要被纳入 Zephyr 项目默认清单的模块，需要提供经项目技术指导委员会认可和批准的功能或特性，并应遵守 模块许可要求 和 贡献准则。此外，还应有一位 Zephyr 开发者承诺维护该模块的代码库。

Zephyr 依赖多种类别的模块，包括但不限于：

  • 调试器集成

  • 芯片厂商的硬件抽象层（HAL）

  • 密码学库

  • 文件系统

  • 进程间通信（IPC）库

此外，在某些情况下，模块（尤其是厂商 HAL）可能包含对可选 二进制大对象（binary blob） 的引用。

本页汇总了一系列策略和最佳实践，旨在更好地组织 Zephyr 模块中的工作流程。

模块与 west 项目

本页所述的 Zephyr 模块与 west 项目 并不相同。实际上，模块完全 不需要 west。不过，当 配合 west 使用模块时，构建系统会使用 west 查找模块。

总结如下：

模块是包含 zephyr/module.yml 文件的仓库，Zephyr 构建系统据此从该仓库中引入源代码。West 项目 是 west.yml 清单文件中 projects: 部分的条目。West 项目通常也是模块，但并非总是如此。有些 west 项目不会包含在最终的固件镜像中（例如工具），因此不需要是模块。Zephyr 构建系统要么通过 west 本身 查找模块，要么通过 ZEPHYR_MODULES CMake 变量 查找模块。

本页的内容只适用于模块，不适用于一般的 west 项目（除非它们本身也是模块）。

模块仓库

  • 默认清单中包含的所有模块都应托管在 zephyrproject-rtos GitHub 组织下的仓库中。

  • 模块仓库的代码库应在仓库根目录的 zephyr/ 文件夹中包含一个 module.yml 文件。

  • 模块仓库的命名应遵循使用小写字母、并以短横线代替下划线的约定。此规则适用于所有新的模块仓库，但直接跟踪外部项目（托管在 Git 仓库中）的仓库除外；这类模块可以沿用其对应外部项目的名称。

    备注

    不符合上述约定的现有模块仓库无需为遵守该约定而重命名。

  • 模块仓库的名称应在 zephyr/module.yml 文件中明确设置。

  • 模块应使用“zephyr”作为仓库主分支的默认名称。用于特定目的的分支（例如对应某个 LTS Zephyr 版本的模块分支）应以 'zephyr_' 前缀开头命名。

  • 如果模块有外部（上游）项目仓库，模块仓库应保留上游仓库的文件夹结构。

    备注

    模块仓库不必维护一个镜像外部仓库 master 分支的 'master' 分支。也不建议这样做，因为这可能会让人对模块的主分支产生混淆，而主分支应当是 'zephyr'。

  • 模块应以模块名开头的包含路径提供其所有头文件。（例如，mcuboot 应将其 bootutil/bootutil.h 以“mcuboot/bootutil/bootutil.h”的形式提供。）

与上游同步

建议将模块仓库与对应外部项目的最新稳定版本同步。不过，如果需要获取模块代码库中的重要更新，也允许将 Zephyr 模块仓库更新到最新的开发分支顶端。将模块与上游同步时，必须记录进行该次更新的理由。

允许做法的要求

对模块仓库主分支的更改，包括与上游代码库的同步，只能通过 PR 进行。这些 PR 应当可以由 Zephyr CI 验证，并且 可合并（例如通过 GitHub UI 中的 Rebase and merge 或 Create a merge commit 选项）。这样可以确保传入的更改始终 可评审，并且 下游 模块仓库的历史是增量的（即现有的提交、标签等始终会被保留）。该策略还允许直接针对要引入模块仓库的那组更改运行 Zephyr CI、git lint、身份和许可证检查。

备注

不允许对模块的主分支执行强制推送。

允许的做法

以下做法符合上述要求，所有模块仓库都应遵循。选择哪种同步做法由模块代码所有者决定，但要求在相应的模块仓库中始终如一地遵循所选做法。

用来自上游的差异更新模块： 将上游更改作为单个 快照 提交（手动 diff），通过针对模块主分支的 PR 引入，并可以使用 Rebase & merge 操作合并。这种方法简单，应当适用于所有模块，缺点是在模块仓库中隐去了上游的历史。

备注

对于外部项目未托管在上游 Git 仓库中的模块，上述做法是唯一允许的做法。

提交消息应写明上游项目的 URL、模块更新到的版本（上游版本、标签、提交 SHA 等，如适用）以及进行此次更新的原因。

通过合并上游分支更新模块： 对目标上游分支（例如 main 分支、最新的发布分支等）执行 Git 合并来引入上游更改，将结果以针对模块主分支的 PR 提交，并使用 Create a merge commit 操作合并该 PR。这种方法适用于有上游项目 Git 仓库的模块。其主要优点是在模块仓库中保留了上游仓库的历史（即原始的提交 SHA）。缺点是会在下游主分支中生成两个额外的合并提交。

为 Zephyr 模块做贡献

个人角色与职责

为便于管理 Zephyr 模块仓库，定义了以下个人角色。

管理员： 每个 Zephyr 模块都应有一名管理员，负责管理对模块仓库的访问权限，例如应模块所有者的请求将个人添加为仓库的协作者（Collaborator）。模块管理员是 Administrators 团队的成员，该团队由对模块 GitHub 仓库拥有管理权限的项目成员组成。

模块所有者： 每个模块都应有一名模块代码所有者。模块所有者对 Zephyr 模块仓库的内容负总体责任。具体而言，模块所有者需要：

  • 协调模块仓库中的代码评审

  • 作为针对仓库主分支的 PR 的默认指派人

  • 根据需要请求将更多协作者添加到仓库

  • 按照 与上游同步 中所述的策略，定期将模块仓库与其上游对应仓库同步

  • 关注外部项目中的安全漏洞问题，并在上游代码库中提供修复后，尽快更新模块仓库以包含这些安全修复

  • 在 Zephyr 发布说明中列出模块代码库中存在的任何已知安全漏洞问题。

    备注

    模块所有者不必是 Zephyr 维护者。

合并者： Zephyr 发布工程团队有权利也有责任将已批准的 PR 合并到模块仓库的主分支中。

维护模块代码库

Zephyr 主源码树中的更新（例如公共 Zephyr API 的更新）可能需要修改模块的代码库。保持模块代码库最新的责任由 Zephyr 中此类更新的 贡献者 和模块 所有者 共同承担。具体而言：

  • Zephyr 中原始更改的贡献者需要提交模块仓库中所需的相应更改，以确保包含原始更改的 PR 上的 Zephyr CI 以及模块集成测试都能通过。

  • 模块所有者对模块代码库与 Zephyr 主源码树的同步和测试负总体责任。这包括在 Zephyr CI 执行的测试之外，偶尔对模块代码库进行更深入的测试。模块所有者需要修复模块代码库中未被 Zephyr PR CI 运行发现的问题。

向模块贡献更改

直接向模块代码库提交和合并更改（即在这些更改合并到对应外部项目仓库之前），应仅限于：

  • 因 Zephyr 主源码树中的更新而需要的更改

  • 不应等到先合并到外部项目中的紧急更改，例如安全漏洞修复。

如果模块有上游项目仓库，则不鼓励对模块代码库进行重大更改，包括对模块设计或功能的更改。这种情况下，此类更改应直接提交给上游项目。

向模块提交更改 详细描述了向模块仓库贡献更改的流程。

贡献准则

为 Zephyr 模块做贡献应遵循项目通用的 贡献准则。

PR： 至少获得 2 个批准（其中包括 PR 指派人的批准）后才能合并。此外，模块仓库中的 PR 只有在引入的更改经过 Zephyr CI 工具验证后才能合并，本页其他各节对此有更详细的说明。

将 PR 合并到模块仓库主分支时，必须同时更新 Zephyr 主源码树中相应的清单文件。

问题报告： 模块仓库中有意禁用了 GitHub issues，以便集中管理问题报告。例如，有关模块中缺陷或改进的工单应在 Zephyr 主仓库中提交。在适用的情况下，应使用与各模块对应的 GitHub 标签为 issue 恰当地打上标签。

备注

允许为 Zephyr 模块提交缺陷报告，以便在 Zephyr 中跟踪相应的上游项目缺陷。这些缺陷报告不应影响 发布质量标准。

许可要求与策略

模块代码库中的所有源文件都应包含许可证头，除非模块仓库有一个 主许可证文件，覆盖了不含许可证头的源文件。

只有当主许可证文件作为外部项目的一部分存在、并且包含与 OSI 兼容的宽松许可证时，Zephyr 开发者才应将其添加到模块代码库中。主许可证文件最好包含完整的许可证文本，而不是只包含 SPDX 许可证标识符。如果存在多个主许可证文件，应明确说明模块代码库中的每个源文件适用哪个许可证。

模块源文件中的单独许可证头优先于主许可证。

要添加到模块仓库中的任何新内容都需要有许可证覆盖。

备注

Zephyr 建议通过单独的许可证头和主许可证文件来说明模块的许可情况。这并不是硬性要求；如果外部项目有自己说明许可证如何适用于模块代码库的做法（例如使用单个或多个主许可证文件），只要满足许可要求（例如符合 OSI），Zephyr 模块就可以接受并引用这种做法。

许可策略

创建模块仓库时，开发者应当：

  • 导入主许可证文件（如果外部项目中存在），并且

  • （例如在模块的 README 或 .yml 文件中）记录覆盖模块代码库的默认许可证。

许可证检查

对于每个向模块仓库添加新内容的 PR，都应启用（通过 CI 工具进行的）许可证检查。

文档要求

所有 Zephyr 模块仓库都应包含一个 .rst 文件，记录以下内容：

  • 模块的范围和用途

  • 模块如何与 Zephyr 集成

  • 模块仓库的所有者

  • 与外部项目的同步信息（提交、SHA、版本等）

  • 许可要求与策略 中所述的许可信息。

纳入模块时必须提供该文件，并且其中包含的信息应保持最新。

测试要求

所有 Zephyr 模块都应提供一定程度的 集成 测试，确保与 Zephyr 的集成工作正常。集成测试：

  • 可以是位于 Zephyr 主源码树中的一组最少量的示例和测试

  • 应验证与 Zephyr 集成的模块的基本用法（配置、功能 API 等）。

  • 应在对模块仓库引入更改的 PR 中，作为 twister 运行的一部分进行构建和执行（例如在 QEMU 中）。

    备注

    作为纳入 Zephyr 默认清单候选者的新模块，应提供一定程度的集成测试。

    备注

    厂商 HAL 已通过在目标平台上构建或执行的 Zephyr 测试间接得到测试，因此不需要提供集成测试。

集成测试的目的并不是对模块进行功能验证；功能验证应属于外部项目测试框架的一部分。

某些外部项目提供的测试套件位于上游测试基础设施中，但专门为 Zephyr 编写。这些测试可以（但不要求）成为 Zephyr 测试框架的一部分。

弃用和移除模块

模块可能因以下原因（包括但不限于）被弃用：

  • 模块缺乏维护

  • 外部项目的许可证发生变化

  • 代码库变得过时

模块信息应表明模块是否已弃用，并且在尝试使用已弃用模块构建 Zephyr 时，构建系统应发出警告。

已弃用的模块可以在 2 个 Zephyr 版本之后从 Zephyr 默认清单中移除。

备注

已移除模块的仓库应仍可通过其原始 URL 访问，因为较旧的 Zephyr 版本需要它们。

将模块集成到 Zephyr 构建系统

构建系统变量 ZEPHYR_MODULES 是一个 CMake list，包含 Zephyr 模块所在目录的绝对路径。这些模块包含 CMakeLists.txt 和 Kconfig 文件，分别描述如何构建和配置它们。模块的 CMakeLists.txt 文件通过 CMake 的 add_subdirectory() 命令加入构建，Kconfig 文件则被包含到构建的 Kconfig 菜单树中。

如果已安装 west，除非你要添加新模块，否则不必关心该变量是如何定义的。构建系统知道如何使用 west 设置 ZEPHYR_MODULES。可以通过设置 CMake 变量 EXTRA_ZEPHYR_MODULES，或在 .zephyrrc 中添加一行 EXTRA_ZEPHYR_MODULES（详见 环境变量 一节），向该列表添加更多模块。如果既想保留通过 west 找到的模块列表，又想添加你自己的模块，这会很有用。如果在多处设置了 EXTRA_ZEPHYR_MODULES，例如同时作为环境变量和 CMake 变量，最终的附加模块列表将是所有来源合并后的结果。

备注

如果模块 FOO 由 west 提供，同时又通过 -DEXTRA_ZEPHYR_MODULES=/<path>/foo 给出，那么由命令行变量 EXTRA_ZEPHYR_MODULES 给出的模块优先。这样就可以在构建时使用自定义版本的 FOO，同时仍然使用 west 提供的其他 Zephyr 模块。这在某些特殊测试场景下可能很有用。

如果想将模块永久添加到 Zephyr 工作区，并且使用 zephyr 作为清单仓库，也可以将 west 清单文件添加到 submanifests 目录中。详见 submanifests/README.txt。

关于 west 工作区的更多信息，请参阅 基础知识。

最后，也可以通过多种方式自行指定模块列表；如果应用程序不需要模块，也可以完全不使用模块。

模块 yaml 文件说明

可以使用名为 zephyr/module.yml 的文件描述模块。zephyr/module.yml 的格式说明如下：

模块名称

每个 Zephyr 模块都有一个名称，构建系统可以通过该名称引用它。

名称应在 zephyr/module.yml 文件中指定。这样可以确保模块名称不会因用户定义的目录名或 west 清单文件而改变：

name: <name>

这样，在 CMake 中可以通过 CMake 变量 ZEPHYR_<MODULE_NAME>_MODULE_DIR 引用 Zephyr 模块的位置，而变量 ZEPHYR_<MODULE_NAME>_CMAKE_DIR 保存包含该模块 CMakeLists.txt 文件的目录位置。

备注

用于 CMake 和 Kconfig 变量时，模块名称中的所有字母都会转换为大写，所有非字母数字字符都会转换为下划线（_）。例如，模块 foo-bar 在 CMake 和 Kconfig 中必须引用为 ZEPHYR_FOO_BAR_MODULE_DIR。

下面是 Zephyr 模块 foo 的一个示例：

name: foo

备注

如果未指定 name 字段，Zephyr 模块名称将被设为模块文件夹的名称。例如，如果 zephyr/module.yml 中没有指定任何内容，位于 <workspace>/modules/bar 的 Zephyr 模块将使用 bar 作为其模块名称。

模块集成文件（模块内）

构建文件 CMakeLists.txt 和 Kconfig 的包含方式可以描述为：

build:
  cmake: <cmake-directory>
  kconfig: <directory>/Kconfig

cmake: <cmake-directory> 部分指定 <cmake-directory> 中包含要使用的 CMakeLists.txt。kconfig: <directory>/Kconfig 部分指定要使用的 Kconfig 文件。两者都不是必需的：cmake 默认为 zephyr，kconfig 默认为 zephyr/Kconfig。

下面是一个 module.yml 示例文件，它引用模块根目录下的 CMakeLists.txt 和 Kconfig 文件：

build:
  cmake: .
  kconfig: Kconfig

Sysbuild 集成

Sysbuild 是 Zephyr 的一种构建系统，可以将多个镜像作为单个应用程序的一部分构建。sysbuild 的构建过程可以根据需要通过模块从外部扩展，例如添加自定义构建步骤或向构建中添加额外目标。sysbuild 专用构建文件 CMakeLists.txt 和 Kconfig 的包含方式可以描述为：

build:
  sysbuild-cmake: <cmake-directory>
  sysbuild-kconfig: <directory>/Kconfig

sysbuild-cmake: <cmake-directory> 部分指定 <cmake-directory> 中包含要使用的 CMakeLists.txt。sysbuild-kconfig: <directory>/Kconfig 部分指定要使用的 Kconfig 文件。

下面是一个 module.yml 示例文件，它引用模块 sysbuild 目录下的 CMakeLists.txt 和 Kconfig 文件：

build:
  sysbuild-cmake: sysbuild
  sysbuild-kconfig: sysbuild/Kconfig

模块描述文件 zephyr/module.yml 还可以用来指定构建文件 CMakeLists.txt 和 Kconfig 位于某个 模块集成文件（外部） 中。

位于 MODULE_EXT_ROOT 中的构建文件可以描述为：

build:
  sysbuild-cmake-ext: True
  sysbuild-kconfig-ext: True

这样就可以在 Zephyr 模块之外描述对构建包含的控制。

漏洞监控

模块描述文件 zephyr/module.yml 可用于改进漏洞监控。

如果你的模块需要借助外部引用来跟踪漏洞（例如模块是从另一个仓库派生的），可以使用 security 部分。其中的 external-references 字段包含需要为你的模块监控的引用列表。支持的格式有：

  • CPE（Common Platform Enumeration，通用平台枚举）

  • PURL（Package URL，软件包 URL）

security:
  external-references:
    - <module-related-cpe>
    - <an-other-module-related-cpe>
    - <module-related-purl>

Mbed TLS 模块的一个实际示例如下：

security:
  external-references:
    - cpe:2.3:a:arm:mbed_tls:3.5.2:*:*:*:*:*:*:*
    - pkg:github/Mbed-TLS/mbedtls@V3.5.2

备注

CPE 字段必须遵循 NVD 提供的 CPE 2.3 模式。PURL 字段必须遵循 Github 提供的 PURL 规范。

构建系统集成

当模块包含 module.yml 文件时，它会自动被纳入 Zephyr 构建系统。随后可以通过 Kconfig 和 CMake 变量访问该模块的路径。

Zephyr 模块

在 Kconfig 和 CMake 中，变量 ZEPHYR_<MODULE_NAME>_MODULE_DIR 都包含该模块的绝对路径。

此外，系统会为可用模块自动生成 ZEPHYR_<MODULE_NAME>_MODULE 和 ZEPHYR_<MODULE_NAME>_MODULE_BLOBS（如果模块声明了二进制大对象）符号。例如，可以用它们声明依赖于该模块或该模块中二进制大对象的其他 Kconfig 符号的依赖关系。为了在没有该模块的情况下构建 Zephyr 时仍能通过合规性检查，建议模块在 Zephyr 主源码树 modules/ 下其相应的 Kconfig 文件中为这些符号提供默认定义。

在 CMake 中，ZEPHYR_<MODULE_NAME>_CMAKE_DIR 包含被纳入 CMake 构建系统的 CMakeLists.txt 文件所在目录的绝对路径。如果 module.yml 文件没有指定 CMakeLists.txt，该变量的值为空。

对于名为 foo 的 Zephyr 模块，读取这些变量的方式如下：

  • 在 CMake 中：使用 ${ZEPHYR_FOO_MODULE_DIR} 获取模块的顶层目录，使用 ${ZEPHYR_FOO_CMAKE_DIR} 获取包含其 CMakeLists.txt 的目录

  • 在 Kconfig 中：使用 $(ZEPHYR_FOO_MODULE_DIR) 获取模块的顶层目录

注意，小写的模块名 foo 在 CMake 和 Kconfig 中都会被转换为大写的 FOO。

这些变量也可用于测试某个模块是否存在。例如，验证 foo 是否为某个 Zephyr 模块的名称：

if(ZEPHYR_FOO_MODULE_DIR)
  # Do something if FOO exists.
endif()

在 Kconfig 中，可以用该变量查找要包含的其他文件。例如，包含模块 foo 中的文件 some/Kconfig：

source "$(ZEPHYR_FOO_MODULE_DIR)/some/Kconfig"

在 CMake 处理每个 Zephyr 模块期间，还可以使用以下变量：

  • 当前模块的名称：${ZEPHYR_CURRENT_MODULE_NAME}

  • 当前模块的顶层目录：${ZEPHYR_CURRENT_MODULE_DIR}

  • 当前模块的 CMakeLists.txt 所在目录：${ZEPHYR_CURRENT_CMAKE_DIR}

这样，Zephyr 模块在 CMake 处理期间就无需知道自己的名称。模块可以使用这些 CURRENT 变量引入其他 CMake 文件。例如：

include(${ZEPHYR_CURRENT_MODULE_DIR}/cmake/code.cmake)

可以在模块的第一个 CMakeLists.txt 文件中向 Zephyr 的 CMake list 变量追加值。为此，先将值追加到列表中，然后在该 CMakeLists.txt 文件的 PARENT_SCOPE 中设置该列表。例如，要在 Zephyr CMakeLists.txt 作用域中将 bar 追加到 FOO_LIST 变量：

list(APPEND FOO_LIST bar)
set(FOO_LIST ${FOO_LIST} PARENT_SCOPE)

这种做法有用的一个 Zephyr 列表示例，是向 SYSCALL_INCLUDE_DIRS 列表中添加更多目录。

Sysbuild 模块

在 Kconfig 和 CMake 中，变量 SYSBUILD_CURRENT_MODULE_DIR 都包含 sysbuild 模块的绝对路径。在 CMake 中，SYSBUILD_CURRENT_CMAKE_DIR 包含被纳入 CMake 构建系统的 CMakeLists.txt 文件所在目录的绝对路径。如果 module.yml 文件没有指定 CMakeLists.txt，该变量的值为空。

对于 sysbuild 模块，读取这些变量的方式如下：

  • 在 CMake 中：使用 ${SYSBUILD_CURRENT_MODULE_DIR} 获取模块的顶层目录，使用 ${SYSBUILD_CURRENT_CMAKE_DIR} 获取包含其 CMakeLists.txt 的目录

  • 在 Kconfig 中：使用 $(SYSBUILD_CURRENT_MODULE_DIR) 获取模块的顶层目录

在 Kconfig 中，可以用该变量查找要包含的其他文件。例如，包含文件 some/Kconfig：

source "$(SYSBUILD_CURRENT_MODULE_DIR)/some/Kconfig"

模块可以使用这些变量引入其他 CMake 文件。例如：

include(${SYSBUILD_CURRENT_MODULE_DIR}/cmake/code.cmake)

可以在模块的第一个 CMakeLists.txt 文件中向 Zephyr 的 CMake list 变量追加值。为此，先将值追加到列表中，然后在该 CMakeLists.txt 文件的 PARENT_SCOPE 中设置该列表。例如，要在 Zephyr CMakeLists.txt 作用域中将 bar 追加到 FOO_LIST 变量：

list(APPEND FOO_LIST bar)
set(FOO_LIST ${FOO_LIST} PARENT_SCOPE)

Sysbuild 模块钩子

Sysbuild 提供了一套基础设施，允许 sysbuild 模块定义一个函数，由 sysbuild 在 CMake 流程中的预定义位置调用。

sysbuild 调用的函数：

  • <module-name>_pre_cmake(IMAGES <images>)：在对所有镜像调用 CMake 配置之前，为每个 sysbuild 模块调用此函数。

  • <module-name>_post_cmake(IMAGES <images>)：在所有镜像的 CMake 配置完成之后，为每个 sysbuild 模块调用此函数。

  • <module-name>_pre_domains(IMAGES <images>)：在 sysbuild 创建 domains yaml 之前，为每个 sysbuild 模块调用此函数。

  • <module-name>_post_domains(IMAGES <images>)：在 sysbuild 创建 domains yaml 之后，为每个 sysbuild 模块调用此函数。

sysbuild 传给模块所定义函数的参数：

  • <images> 是构建系统将要创建的 Zephyr 镜像列表。

如果模块 foo 想提供一个 CMake 配置后执行的函数，则该模块的 sysbuild CMakeLists.txt 文件必须定义函数 foo_post_cmake()。

为了方便函数命名，sysbuild CMake 在加载模块的 sysbuild CMakeLists.txt 文件时，会通过 CMake 变量 SYSBUILD_CURRENT_MODULE_NAME 提供模块名称。

foo sysbuild 模块定义 foo_post_cmake() 的示例：

function(${SYSBUILD_CURRENT_MODULE_NAME}_post_cmake)
  cmake_parse_arguments(POST_CMAKE "" "" "IMAGES" ${ARGN})

  message("Invoking ${CMAKE_CURRENT_FUNCTION}. Images: ${POST_CMAKE_IMAGES}")
endfunction()

Zephyr 模块依赖

Zephyr 模块可能需要其他 Zephyr 模块存在才能正常工作。也可能由于某些 CMake 目标之间的依赖关系，某个 Zephyr 模块必须在另一个 Zephyr 模块之后处理。

这种依赖关系可以用 depends 字段描述。

build:
  depends:
    - <module>

下面是 Zephyr 模块 foo 的示例，它依赖 Zephyr 模块 bar 存在于构建系统中：

name: foo
build:
  depends:
    - bar

此示例可以确保在 foo 被纳入构建系统时 bar 存在，还可以确保 bar 在 foo 之前处理。

模块集成文件（外部）

模块集成文件可以位于 Zephyr 模块本身之外。MODULE_EXT_ROOT 变量保存一组根目录，其中包含位于 Zephyr 模块之外的集成文件。

Zephyr 中的模块集成文件

Zephyr 仓库中包含某些已知 Zephyr 模块的 CMakeLists.txt 和 Kconfig 构建文件。

这些文件位于

<ZEPHYR_BASE>
└── modules
    └── <module_name>
        ├── CMakeLists.txt
        └── Kconfig

自定义位置中的模块集成文件

可以为其他模块创建类似的 MODULE_EXT_ROOT，让 Zephyr 构建系统知道这些模块。

创建具有以下结构的 MODULE_EXT_ROOT

<MODULE_EXT_ROOT>
└── modules
    ├── modules.cmake
    └── <module_name>
        ├── CMakeLists.txt
        └── Kconfig

然后在构建应用程序时向 CMake 构建系统指定 -DMODULE_EXT_ROOT 参数。MODULE_EXT_ROOT 接受一个由根目录组成的 CMake list 作为参数。

可以使用模块描述文件 zephyr/module.yml 将 Zephyr 模块自动添加到 MODULE_EXT_ROOT 列表中，参见 构建设置。

备注

ZEPHYR_BASE 总是会被添加为优先级最低的 MODULE_EXT_ROOT。这样，你就可以在自己的 MODULE_EXT_ROOT 中用自己的实现覆盖 <ZEPHYR_BASE>/modules/<module_name> 下的任何集成文件。

modules.cmake 文件必须包含通过特定名称的 CMake 变量为 Zephyr 模块指定集成文件的逻辑。

要包含模块的 CMake 文件，请将变量 ZEPHYR_<MODULE_NAME>_CMAKE_DIR 设置为包含该 CMake 文件的路径。

要包含模块的 Kconfig 文件，请将变量 ZEPHYR_<MODULE_NAME>_KCONFIG 设置为该 Kconfig 文件的路径。

下面是为 FOO 模块添加支持的示例。

创建以下结构

<MODULE_EXT_ROOT>
└── modules
    ├── modules.cmake
    └── foo
        ├── CMakeLists.txt
        └── Kconfig

并在 modules.cmake 文件中添加以下内容

set(ZEPHYR_FOO_CMAKE_DIR ${CMAKE_CURRENT_LIST_DIR}/foo)
set(ZEPHYR_FOO_KCONFIG   ${CMAKE_CURRENT_LIST_DIR}/foo/Kconfig)

模块描述文件（zephyr/module.yml）

模块描述文件 zephyr/module.yml 可以用来指定构建文件 CMakeLists.txt 和 Kconfig 位于某个 模块集成文件（外部） 中。

位于 MODULE_EXT_ROOT 中的构建文件可以描述为：

build:
  cmake-ext: True
  kconfig-ext: True

这样就可以在 Zephyr 模块之外描述对构建包含的控制。

Zephyr 仓库本身总是会被添加为一个 Zephyr 模块外部根目录（ext root）。

构建设置

可以指定将模块纳入构建系统时必须使用的额外构建设置。

所有 root 设置都相对于模块的根目录。

module.yml 文件中支持的构建设置有：

  • board_root：包含可供构建系统使用的额外开发板。额外的开发板必须位于 <board_root>/boards 文件夹中。

  • dts_root：包含与架构/SoC 系列相关的额外 dts 文件。额外的 dts 文件必须位于 <dts_root>/dts 文件夹中。

  • snippet_root：包含可供使用的额外代码片段（snippet）。这些代码片段必须在 <snippet_root>/snippets 文件夹下的 snippet.yml 文件中定义。例如，如果设置了 snippet_root: foo，则应将模块的 snippet.yml 文件放在 <your-module>/foo/snippets 或其任意嵌套子目录中。

  • soc_root：包含可供构建系统使用的额外 SoC。额外的 SoC 必须位于 <soc_root>/soc 文件夹中。

  • arch_root：包含可供构建系统使用的额外架构。额外的架构必须位于 <arch_root>/arch 文件夹中。

  • module_ext_root：包含 Zephyr 模块的 CMakeLists.txt 和 Kconfig 文件，另请参阅 模块集成文件（外部）。

  • sca_root：包含可供构建系统使用的额外 SCA 工具实现。每个工具必须位于 <sca_root>/sca/<tool> 文件夹中，该文件夹中必须包含 sca.cmake。

下面是一个包含额外根目录的 module.yaml 文件示例，以及相应的文件系统布局。

build:
  settings:
    board_root: .
    dts_root: .
    soc_root: .
    arch_root: .
    module_ext_root: .

需要以下文件夹结构：

<zephyr-module-root>
├── arch
├── boards
├── dts
├── modules
└── soc

测试运行器（Twister）集成

要执行模块中的测试和示例，应将 Zephyr 测试运行器（twister）指向包含这些示例和测试的目录。可以在 zephyr/module.yml 文件中指定示例和测试的路径来实现。此外，如果模块定义了源码树之外的开发板，模块文件可以将 twister 指向模块中维护这些文件的路径。例如：

build:
  cmake: .
samples:
  - samples
tests:
  - tests
boards:
  - boards

twister 不会自动检测 zephyr/module.yml 文件中定义的测试和示例。要让 twister 知道模块中定义的测试和示例，必须在执行 twister 时将这些测试和示例的路径添加到命令行中，例如：

./scripts/zephyr_module.py --twister-out module_tests.args
if [ -s module_tests.args ]; then
    west twister +module_tests.args --outdir module_tests ...
fi

二进制大对象（Binary Blob）

Zephyr 支持获取和使用 二进制大对象，其元数据完全包含在 zephyr/module.yml 中。这是因为二进制大对象必须始终与某个 Zephyr 模块相关联，因此其元数据理应放在模块自身的描述中。

二进制大对象通过 west blobs 获取。如果 不使用 west，则必须手动下载和校验。

zephyr/module.yml 中的 blobs 部分由一系列映射组成，每个映射包含以下条目：

  • path：二进制大对象的路径，相对于模块仓库中的 zephyr/blobs/ 文件夹

  • sha256：二进制大对象文件的 SHA-256 校验和

  • type：二进制大对象的类型。目前仅限 img 或 lib

  • version：版本字符串

  • license-path：该二进制大对象的许可证文件路径，相对于模块仓库的根目录

  • url：标识获取该二进制大对象的位置以及所用获取方式的 URL。如果它包含的是列表而不是单个字符串，则每个 URL 都会被视为获取同一个二进制大对象的备用地址。

  • description：二进制大对象的可读描述

  • doc-url：指向该二进制大对象官方文档位置的 URL

还可以包含以下条目：

  • click-through：布尔值，表示下载该二进制大对象前是否必须接受点击同意（click-through）许可证

  • size：二进制大对象的大小（字节）。某些获取器可能需要此项

  • fetcher：用于下载二进制大对象的方法。如果未设置，则根据 URL 推断

软件包管理器依赖

Zephyr 模块可以描述可从软件包管理器获取的依赖，目前只支持 pip。

west 扩展命令 west packages <manager> 可用于列出 Zephyr 以及在其 module.yml 文件中使用了此功能的现有模块的依赖。更多详情请运行 west help packages。

Python pip

调用 west packages pip 会列出 Zephyr 和各模块的 requirement files。如果有活动的虚拟环境，传入 --install 会安装这些依赖。

下面的示例演示了一个 zephyr/module.yml 文件，其中引用了模块 scripts 目录中的一些依赖文件。

package-managers:
  pip:
    requirement-files:
      - scripts/requirements-build.txt
      - scripts/requirements-doc.txt

外部运行器

如果模块中有需要自定义 运行器 的源码树外开发板，可以在其 zephyr/module.yml 文件中添加一个列表，例如：

runners:
  - file: scripts/my-runner.py

执行 west flash 或 west debug 时，会导入每个文件条目，并注册其中 ZephyrBinaryRunner 的子类以供使用。

模块的纳入

使用 West

如果已安装 west 且尚未设置 ZEPHYR_MODULES，构建系统会找到 west 安装 中的所有模块并使用它们。具体做法是运行 west list 获取安装中所有项目的路径，然后从结果中筛选出具有必要模块元数据文件的项目。

west list 输出中的每个项目按如下方式检测：

  • 如果项目中包含名为 zephyr/module.yml 的文件，则按上一节所述，根据该文件的内容确定应将哪些文件加入构建。

  • 否则（即项目中没有 zephyr/module.yml），构建系统会在项目中查找 zephyr/CMakeLists.txt 和 zephyr/Kconfig 文件。如果两者都存在，该项目就被视为模块，这些文件会被加入构建。

  • 如果以上检查均未通过，该项目不被视为模块，也不会被加入 ZEPHYR_MODULES。

不使用 West

如果没有安装 west，或者不希望构建系统用它查找 Zephyr 模块，可以通过以下任一方式自行设置 ZEPHYR_MODULES。如上一节所述，列表中的每个目录都必须包含 zephyr/module.yml 文件，或者包含 zephyr/CMakeLists.txt 和 Kconfig 文件。

  1. 在 CMake 命令行中，如下所示：

    cmake -DZEPHYR_MODULES=<path-to-module1>[;<path-to-module2>[...]] ...

  2. 在应用程序顶层 CMakeLists.txt 的开头，如下所示：

    set(ZEPHYR_MODULES <path-to-module1> <path-to-module2> [...])
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})

    如果选择这种方式，请确保像上面那样在调用 find_package(Zephyr ...) 之前 设置该变量。

  3. 在一个单独的、预先加载以填充 CMake 缓存的 CMake 脚本中，如下所示：

    # Put this in a file with a name like "zephyr-modules.cmake"
set(ZEPHYR_MODULES <path-to-module1> <path-to-module2>
  CACHE STRING "pre-cached modules")

    在 CMake 命令行中添加 -C zephyr-modules.cmake，即可让构建系统使用该文件。

不使用模块

如果没有安装 west，也没有自行指定 ZEPHYR_MODULES，则不会向构建中添加任何额外模块。你仍然可以构建任何不需要外部仓库中定义的代码或 Kconfig 选项的应用程序。

向模块提交更改

提交新模块或修改现有模块时，Zephyr 主仓库需要引用这些更改才能对其进行验证。在主源码树中，这通过 revision 来实现。对于已经合并并成为源码树一部分的代码，我们使用提交哈希、标签或分支名。但对于 PR，我们要求在 revision 字段中指定 PR 编号，以便使用提交到模块的更改构建 Zephyr 主源码树。

为避免把带有 PR 信息的更改合并到 master，应将该 PR 标记为 DNM（Do Not Merge，不要合并），最好是设为草稿 PR，以确保它不会被误合并，并让模块先被合并、获得一个永久的提交哈希。草稿 PR 在被标记为“Ready for review”之前不会自动通知任何人，从而减少干扰。模块合并后，需要由提交者或维护者将 revision 改为反映这些更改的模块提交哈希。

注意，对不同模块的多个相互依赖的更改也可以按完全相同的流程提交。此时需要修改所有存在相关 PR 的模块的多个条目。

提交新模块的流程

请按照 提交和评审流程 中的流程操作，并获得 TSC 批准，才能将外部源代码作为模块集成

如果请求获得批准，项目团队会创建一个新仓库，并用基本信息对其进行初始化，以便按照项目贡献准则向该模块项目提交代码。

如果某个模块是作为 GitHub 上另一个项目的分支来维护的，那么与 Zephyr 模块相关的文件以及相对于上游的更改，需要在一个名为 zephyr 的专用分支中维护。

Zephyr 项目的维护者会创建并初始化该仓库。你会被添加为新仓库的协作者。按照 此处 所述的准则将模块内容（代码）提交到新仓库，然后在 west.yml 中添加一个包含以下信息的新条目：

- name: <name of repository>
  path: <path to where the repository should be cloned>
  revision: <ref pointer to module pull request>

例如，要将 my_module 添加到清单中：

- name: my_module
  path: modules/lib/my_module
  revision: pull/23/head

上例中的 23 表示提交到 my_module 仓库的 PR 编号。模块更改经过评审并合并后，需要将 revision 改为模块仓库中的提交哈希。

向现有模块提交更改的流程

  1. 按照 贡献准则 和 贡献者预期，通过 PR 将更改提交到现有仓库。

  2. 提交一个 PR，修改 Zephyr 主源码树 west.yml 中引用该模块的条目，包含以下信息：

    - name: <name of repository>
  path: <path to where the repository should be cloned>
  revision: <ref pointer to module pull request>

例如，要将 my_module 添加到清单中：

- name: my_module
  path: modules/lib/my_module
  revision: pull/23/head

上例中的 23 表示提交到 my_module 仓库的 PR 编号。模块更改经过评审并合并后，需要将 revision 改为模块仓库中的提交哈希。
