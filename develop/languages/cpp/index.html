C++ 语言支持

C++ 是一种基于 C 语言的通用面向对象编程语言。

启用 C++ 支持

Zephyr 同时支持用 C 和 C++ 编写的应用程序。但要在应用程序中使用 C++，必须在应用程序配置文件中选中 CONFIG_CPP，将 Zephyr 配置为包含 C++ 支持。

要启用 C++ 支持，编译器工具链还必须包含 C++ 编译器，并且所含编译器必须受 Zephyr 构建系统支持。Zephyr 支持包含 GNU C++ 编译器（GCC 的一部分）的 Zephyr SDK，本文档所述的特性及其可用性均假定使用 Zephyr SDK。

Zephyr 应用程序默认的 C++ 标准级别（即所传编译器标志强制采用的语言标准）为 C++11。其他标准可通过 Kconfig choice 选择，例如 CONFIG_STD_CPP98。Zephyr 支持并测试的最旧标准是 C++98。

编译源文件时，构建系统根据文件后缀（扩展名）选择 C++ 编译器。以 cpp 或 cxx 为后缀的文件会使用 C++ 编译器编译。例如，myCplusplusApp.cpp 会按 C++ 编译。

C++ 标准要求 main() 函数的返回类型为 int。你的 main() 必须定义为 int main(void) 或 int main(int, char **)。要使用带参数的 main，必须选中 CONFIG_BOOTARGS 选项。Zephyr 会忽略 main 的返回值。但应用程序必须返回零（0）。所有非零返回值均为保留值。

备注

不要在内核、驱动或系统初始化代码中使用 C++。

语言特性

Zephyr 目前只提供 C++ 功能的一个子集。以下特性 不 受支持：

  • 静态全局对象的析构

  • 特定于操作系统的 C++ 标准库类（例如 std::thread、std::mutex）

以下功能受支持（并非完整列表）：

  • 继承

  • 虚函数

  • 虚函数表

  • 静态全局对象的构造函数

  • 使用 new 和 delete 运算符进行动态对象管理

  • 异常

  • RTTI

  • 标准模板库（STL）

静态全局对象的构造函数在驱动初始化之后、应用程序 main() 函数之前执行初始化。因此，C++ 只能用于应用程序代码。

要使用 C++ 异常，必须在应用程序配置文件中选中 CONFIG_CPP_EXCEPTIONS。

Zephyr 最小 C++ 库

Zephyr 最小 C++ 库（lib/cpp/minimal）提供 C++ 标准库和应用程序二进制接口（ABI）函数的最小子集，以实现基本的 C++ 语言支持。包括：

  • new 和 delete 运算符

  • 虚函数桩和虚函数表

  • 用于全局构造函数的静态全局初始化器

最小 C++ 库的范围严格限于提供基本的 C++ 语言支持，它不实现任何 Standard Template Library (STL) 类和函数。因此，它只适用于实现了自己的（非标准）类库、且不依赖标准模板库（STL）组件的应用程序。

任何使用标准模板库（STL）组件（例如 std::string 和 std::vector）的应用程序，都必须启用 C++ 标准库支持。

C++ 标准库

C++ Standard Library 是属于 ISO C++ 标准（std 命名空间）的类和函数的集合。

Zephyr 不以源代码形式包含任何 C++ 标准库实现，而是允许将构建系统配置为链接 C++ 编译器工具链中附带的预构建 C++ 标准库。

要启用 C++ 标准库，请在应用程序配置文件中从 CONFIG_LIBCPP_IMPLEMENTATION 中选择一个适用的、特定于工具链的 C++ 标准库类型。

例如，使用 Zephyr SDK 构建时，可以在应用程序配置文件中选中 CONFIG_GLIBCXX_LIBCPP，将构建系统配置为链接 GNU C++ 库（libstdc++.a）。这是一个功能完整的 C++ 标准库，提供 ISO C++ 标准要求的所有特性，包括标准模板库（STL）。

Zephyr 支持以下 C++ 标准库：

  • GNU C++ 库（CONFIG_GLIBCXX_LIBCPP）

  • ARC MetaWare C++ 库（CONFIG_ARCMWDT_LIBCPP）

需要完整 C++ 标准库特性的 Zephyr 子系统，可以在其配置中选中 CONFIG_REQUIRES_FULL_LIBCPP；除非选中了特定 C++ 标准库的 Kconfig 符号，否则它会自动选择一个兼容的 C++ 标准库。

头文件以及 C 与 C++ 之间的不兼容

为了相互交互，C 和 C++ 必须通过头文件共享代码：数据结构、宏、静态函数等。虽然 C 和 C++ 有很大的重叠，但它们是不同的语言，存在 known incompatibilities。C 并不只是 C++ 的子集。标准级别（例如“C++11”）又增加了一层复杂性，因为新特性往往受另一种语言启发并从中借鉴，但时间上晚了很多年，而且存在细微差别。更复杂的是，编译器经常在特性标准化之前就提供其早期原型。标准中可能存在歧义，不同编译器会作出不同的解释。编译器也可能有缺陷，需要规避。为了应对这些问题，许多项目只支持有限的几种工具链。Zephyr 并没有这样做。

这些兼容性问题对头文件的影响格外大。这不仅是因为头文件必须同时兼容 C 和 C++，还因为由于 间接 包含以及实际项目中常见的 lack of structure and headers organization，头文件最终会在数量惊人的其他源文件中被编译。因此，头文件要面对种类多得多的工具链和项目配置。更多的约束在于，Zephyr 项目在代码风格、编译器警告、静态分析器和标准合规性（例如 MISRA）方面都有严格的策略。

综合起来，所有这些约束会让编写头文件非常具有挑战性。本节的目的是在 Zephyr 特定的背景下，记录一些最佳的“头文件实践”和经验教训。虽然这里的许多信息并非 Zephyr 特有，但本节不能替代对 C/C++ 标准、教科书和其他参考资料的了解。

测试

幸运的是，Zephyr 项目拥有完善的测试和 CI 基础设施，可以提供覆盖率基线、及早发现问题、执行策略，并将这种组合爆炸控制在一定范围内。tests/lib/cpp/cxx/ 在这方面非常有用，因为它们的 testcase.yaml 配置可以让 twister 快速遍历一系列 -std 参数：-std=c++98、-std=c++11 等。

请记住，未使用的宏不会被编译。

指定初始化器

初始化宏在头文件中很常见，因为它们有助于减少样板代码。C99 增加了按“指定”成员名初始化 struct 和 union 类型的方式，而不是使用 裸 表达式列表。某些 GCC 版本甚至在 C90 模式下也支持指定初始化器。

在简单场景下使用时，指定初始化器更不容易出错、更易读，也更灵活。另一方面，C99 允许的可能性多得惊人，也非常宽松：指定初始化器可以乱序、重复、“嵌套”（.a.x =），可以省略其他各种花括号，指定初始化器与非指定初始化器可以混用，等等。

二十年后，C++20 也为 C++ 加入了指定初始化器，但限制要严格得多；部分原因是 C++ 的 struct 实际上就是 class。正如 C++ 提案 P0329（其中与 C 进行了比较）或任何完整的 C++ 参考资料所述，C++ 不允许混用，并且初始化器必须按顺序排列（允许有间隔）。

有趣的是，C++20 中的新限制可能导致 gcc -std=c++20 无法编译那些用 gcc -std=c++17 能成功编译的代码。例如，gcc -std=c++17 及更早版本允许 C 风格的初始化器与裸表达式混用。而 在相同 GCC 版本下 使用 gcc -std=c++20 时，这样的代码会编译失败。

建议：为了最大限度地兼容不同的 C 和 C++ 工具链及标准，Zephyr 头文件中的指定初始化器应遵循所有 C++20 规则和限制。非指定的、C99 之前的初始化方式兼容性更好，也是允许的，但指定初始化是更易读、更受推荐的代码风格。无论如何，同一个初始化器中绝不能混用两种风格。

警告：编译成功并不意味着不兼容问题就此结束。例如，在 C99 中，初始化表达式的 求值顺序 是未指定的！而在 C++20 中则是（符合预期的）从左到右的顺序。其他标准修订版可能有所不同。如有疑问，不要依赖求值顺序（这里和其他地方都一样）。

匿名联合体

匿名联合体（又称“无名”联合体）似乎从 C++ 诞生之初就已存在，而直到 C11 才被正式加入 C。和往常一样，C 和 C++ 之间存在差异。例如，C 只支持将匿名联合体作为外层 struct 或 union 的成员；空列表 { } 在 C++ 中一直是允许的，而在 C 中则需要 C23，等等。

初始化匿名成员时，表达式可以用花括号括起来，也可以不括；可以是指定初始化，也可以是裸表达式。为了获得最大的可移植性，初始化 匿名联合体 时：

  • 不要 用花括号括住 指定 初始化器。这是 C++20 及以上版本的要求，它们会把这种花括号视为将裸表达式与（其他）指定初始化器混用，从而编译失败。

  • 要 用花括号括住 裸 表达式。这是 C 的要求。也许是因为 C 更宽松，允许多种初始化方式和变体，所以需要这样的花括号来消除歧义？注意，C 确实允许在初始化表达式中省略大部分花括号，但用裸表达式初始化匿名联合体这一特定情况除外。

某些 C11 之前的 GCC 版本支持某种形式的匿名联合体。遗憾的是，它们要求用花括号括住指定初始化器，这与本建议相冲突。可以使用 #ifdef __STDC_VERSION__ 解决这个问题，如 Zephyr 提交 c15f029a7108 及相应的代码评审所示。
