设备树故障排除

下面是一些修复设备树相关代码异常的技巧。

其他“HOWTO”式的信息请参见 设备树 HOWTO。

使用全新的构建目录重试

重要

在做其他任何事情之前，先尝试这一步。

示例请参见 全新构建，或者直接完全删除构建目录后重试。

这是一条通用建议，尤其适用于调试设备树问题，因为设备树输出是在 CMake 配置阶段生成的，当其某个输入发生变化时并不总会重新生成。

使用设备树诊断工具（DT Doctor）

Zephyr 提供了一个可选的设备树诊断工具，用于帮助诊断设备树问题。向 west build 传递 -DZEPHYR_SCA_VARIANT=dtdoctor 参数即可启用该工具。

更多信息请参见 设备树诊断（dtdoctor）。

确保包含了 <devicetree.h>

与 Kconfig 符号不同，devicetree.h 头文件必须显式包含。

许多 Zephyr 头文件依赖设备树中的信息，因此包含其他某个 API 可能会间接包含 devicetree.h，但这并不能保证。

undefined reference to __device_dts_ord_<N>

这通常发生在类似下面这样的代码行上：

const struct device *dev = DEVICE_DT_GET(NODE_ID);

其中 NODE_ID 是有效的 节点标识符，但没有任何设备驱动为该设备树节点分配 struct device。由于你请求的是指向一个未定义设备的指针，因此会出现链接器错误。

要修复此问题，需要确保：

  1. 节点已启用：节点必须具有 status = "okay";。

    （回想一下，缺少 status 属性与 status = "okay"; 含义相同。关于 status 的更多信息请参见 重要属性。）

  2. 负责分配 struct device 的设备驱动已启用。也就是说，使构建系统将驱动源代码编译进应用程序的 Kconfig 选项需要设为 y。

    （设置 Kconfig 选项的更多信息请参见 设置 Kconfig 配置值。）

下文中，<build> 表示你的构建目录。

确保节点已启用：

要找到需要检查的设备树节点，请使用链接器错误中的数字 <N>。在 <build>/zephyr/include/generated/zephyr/devicetree_generated.h 顶部的节点列表中查找该数字。例如，如果 <N> 为 15，而你的 devicetree_generated.h 文件如下所示，那么你要找的节点就是 /soc/i2c@deadbeef：

/*
 * Generated by gen_defines.py
 *
 * DTS input file:
 *   zephyr.dts.pre
 *
 * Directories with bindings:
 *   $ZEPHYR_BASE/dts/bindings
 *
 * Node dependency ordering (ordinal and path):
 *   0   /
 *   1   /aliases
[...]
 *   15  /soc/i2c@deadbeef
[...]

然后在 <build>/zephyr/zephyr.dts 中查找该节点，该文件是应用程序构建的最终设备树。（相关信息和示例请参见 获取设备树和生成的头文件。）

如果该节点在 zephyr.dts 中为 status = "disabled";，则需要将其设为 status = "okay"; 来启用它，通常可以使用设备树 覆盖文件 来实现。例如，如果 zephyr.dts 如下所示：

i2c0: i2c@deadbeef {
        status = "disabled";
};

则应将以下内容放入设备树覆盖文件中，然后 使用全新的构建目录重试：

&i2c0 {
        status = "okay";
};

重新构建后，确认在 zephyr.dts 中能看到 status = "okay";。

确保设备驱动已启用：

第一步是找出负责处理该设备树节点并为其分配设备的设备驱动。为此，需要从设备树节点的 compatible 属性入手，找到为该 compatible 分配 struct device 实例的驱动。

如果你不熟悉如何根据 compatible 属性从设备树节点分配设备，可以从 ZDS 2021 的演讲 A deep dive into the Zephyr 2.5 device model 以及 设备驱动模型 页面入手。关于 compatible 的更多信息，请参见 重要属性 和设备树规范。

目前没有文档说明存在哪些设备驱动以及它们与哪些设备树 compatible 相关联。你需要通过阅读源代码来弄清楚：

  • 在 drivers 中找到与设备所实现 API 对应的子目录

  • 在该目录中查找相关文件，直到弄清楚驱动是哪一个，或者确认不存在这样的驱动。

通常（但并非总是）可以通过查找这样的文件来找到驱动：该文件将 DT_DRV_COMPAT 宏设置为与节点的 compatible 属性相匹配的值，只是改为小写并将特殊字符转换为下划线。例如，如果节点的 compatible 是 vnd,foo-device，则查找包含下面这行的文件：

#define DT_DRV_COMPAT vnd_foo_device

重要

这种方法 并不总是有效，因为并非所有驱动都使用 DT_DRV_COMPAT。

找到驱动后，接下来需要确保编译该驱动的 Kconfig 选项已启用。（如果找不到驱动，并且确定 compatible 属性是正确的，那么就需要编写驱动。编写驱动超出了本文档页面的范围。）

继续上面的例子，如果设备树节点现在如下所示：

i2c0: i2c@deadbeef {
        compatible = "nordic,nrf-twim";
        status = "okay";
};

则应在 drivers/i2c 中查找处理 compatible nordic,nrf-twim 的驱动文件。在本例中，该文件是 drivers/i2c/i2c_nrfx_twim.c。请注意，即使没有设置 DT_DRV_COMPAT，也可以把驱动文件名等信息作为线索。

确定要启用的驱动后，需要确保其 Kconfig 选项设为 y。可以通过在驱动子目录的 CMakeLists.txt 文件中查找类似下面的代码行来确定所需的 Kconfig 选项。继续上面的例子，drivers/i2c/CMakeLists.txt 中有如下一行：

zephyr_library_sources_ifdef(CONFIG_NRFX_TWIM       i2c_nrfx_twim.c)

这意味着 <build>/zephyr/.config 文件中的 CONFIG_NRFX_TWIM 必须设为 y。

如果驱动的 Kconfig 选项没有设为 y，你需要弄清楚如何启用它。通常，一旦启用设备树节点，这一步就会自动完成。否则，有时只需在应用程序的 prj.conf 文件中添加类似下面的一行，然后确保 使用全新的构建目录重试 即可：

CONFIG_FOO=y

其中 CONFIG_FOO 是 CMakeLists.txt 用来决定是否编译该驱动的选项。

不过，可能还会遇到其他问题，例如存在未满足的 Kconfig 依赖，必须先启用这些依赖才能启用你的驱动。

更多信息请查阅定义 CONFIG_FOO（FOO 替换为你的实际值）的 Kconfig 文件。

确保使用了正确的名称

请记住：

  • 在 C/C++ 中，设备树名称必须转为小写，特殊字符必须转换为下划线。Zephyr 生成的设备树头文件会以这种方式把 DTS 名称转换为基于预处理器的 <devicetree.h> API 所使用的 C 记号。

  • 在覆盖文件中，设备树节点名和属性名的写法与在任何 DTS 文件中相同。Zephyr 覆盖文件只是 DTS 片段。

例如，如果要在 C/C++ 文件中 获取 路径为 /soc/i2c@12340000 的节点的 clock-frequency 属性：

/*
 * foo.c: lowercase-and-underscores names
 */

/* Don't do this: */
#define MY_CLOCK_FREQ DT_PROP(DT_PATH(soc, i2c@1234000), clock-frequency)
/*                                           ^               ^
 *                                        @ should be _     - should be _  */

/* Do this instead: */
#define MY_CLOCK_FREQ DT_PROP(DT_PATH(soc, i2c_1234000), clock_frequency)
/*                                           ^               ^           */

如果要在设备树覆盖文件中 设置 该属性：

/*
 * foo.overlay: DTS names with special characters, etc.
 */

/* Don't do this; you'll get devicetree errors. */
&{/soc/i2c_12340000/} {
     clock_frequency = <115200>;
};

/* Do this instead. Overlays are just DTS fragments. */
&{/soc/i2c@12340000/} {
     clock-frequency = <115200>;
};

查看预处理器输出

要保存预处理器输出文件，请启用 CONFIG_COMPILER_SAVE_TEMPS 选项。例如，要使用 west 并设置该选项来构建 Hello World，可执行：

west build -b BOARD samples/hello_world -- -DCONFIG_COMPILER_SAVE_TEMPS=y

这样会在构建目录中为每个源文件 foo.c 创建一个名为 foo.c.i 的预处理器输出文件。

然后可以在构建目录中查找该文件，查看设备树宏展开后的结果。例如，在 macOS 和 Linux 上使用 find 查找 main.c.i：

$ find build -name main.c.i
build/CMakeFiles/app.dir/src/main.c.i

通常最简单的做法是在打开结果之前先运行代码格式化工具。例如，使用 clang-format 原地重新格式化该文件：

clang-format -i build/CMakeFiles/app.dir/src/main.c.i

然后可以用你喜欢的编辑器打开该文件，查看预处理后的最终 C 代码。

不跟踪宏展开

设备树错误的编译器信息有时会非常长。这通常是因为对于包含多个中间展开步骤的复杂宏展开，编译器为每一步都打印了一条信息。

要防止编译器这样做，可以禁用 CONFIG_COMPILER_TRACK_MACRO_EXPANSION 选项。这样通常会把输出减少为每个错误一条信息。

例如，要使用 west 并禁用该选项来构建 Hello World，可执行：

west build -b BOARD samples/hello_world -- -DCONFIG_COMPILER_TRACK_MACRO_EXPANSION=n

校验属性

如果在读取节点属性时出现编译错误，请检查节点标识符和属性。例如，如果在类似下面的代码行上出现构建错误：

int baud_rate = DT_PROP(DT_NODELABEL(my_serial), current_speed);

可以尝试在文件中添加以下内容并重新编译，以检查该节点：

#if !DT_NODE_EXISTS(DT_NODELABEL(my_serial))
#error "whoops"
#endif

如果重新构建时看到 “whoops” 错误信息，说明该节点标识符没有指向有效的节点。请参考 获取设备树和生成的头文件，并从那里开始调试。

如果没有看到 “whoops” 错误信息，接下来可以检查以下几点：

  • 是否 确保使用了正确的名称？

  • 属性是否存在？

  • 节点是否有 匹配的绑定？

  • 绑定中是否定义了该属性？

检查是否缺少绑定

关于绑定的信息请参见 设备树绑定，关于 Zephyr 内置绑定的信息请参见 devicetree_binding_index。

如果构建无法为某个节点 查找设备树绑定，要么是该节点的 compatible 属性未定义，要么是其值没有匹配的绑定。如果已设置该属性，请检查其名称是否有拼写错误。在设备树源文件中，compatible 应形如 "vnd,some-device"，参见 确保使用了正确的名称。

如果绑定文件不在 zephyr/dts 下，可能需要设置 DTS_ROOT，参见 绑定的存放位置。

DT_INST_() API 相关的错误

如果使用 DT_INST_PROP() 之类的 API，必须将 DT_DRV_COMPAT 定义为目标 compatible 的小写加下划线形式。参见 方式 1：使用实例编号创建设备。
