顶层键

绑定文件的顶层将键映射到值。顶层键如下所示：

# When the description text is too long, this field can
# be used to improve readability, e.g.:
#
# title: Binding the device's hardware model.
#
# description |
#   A piece of content with 20 lines.
#   ...
title: Concise title for the long description [optional]

# A high level description of the device the binding applies to:
description: |
   This is the Vendomatic company's foo-device.

   Descriptions which span multiple lines (like this) are OK,
   and are encouraged for complex bindings.

   See https://yaml-multiline.info/ for formatting help.

# You can include definitions from other bindings using this syntax:
include: other.yaml

# Used to match nodes to this binding:
compatible: "manufacturer,foo-device"

properties:
  # Requirements for and descriptions of the properties that this
  # binding's nodes need to satisfy go here.

child-binding:
  # You can constrain the children of the nodes matching this binding
  # using this key.

# If the node describes bus hardware, like an SPI bus controller
# on an SoC, use 'bus:' to say which one, like this:
bus: spi

# If the node instead appears as a device on a bus, like an external
# SPI memory chip, use 'on-bus:' to say what type of bus, like this.
# Like 'compatible', this key also influences the way nodes match
# bindings.
on-bus: spi

examples:
  # You can put a sample node here showing how to use the binding.
  # - |
  #  ...
  # or
  # - ...

foo-cells:
  # "Specifier" cell names for the 'foo' domain go here; example 'foo'
  # values are 'gpio', 'pwm', and 'dma'. See below for more information.

以下各节将解释这些键。

标题

被绑定设备的简短描述，可选，通常是硬件型号。其格式通常应为“厂商 系列 型号”。如果使用了缩写，应在括号中写出全称。命名应尽可能与厂商数据手册保持一致。

标题不应超过 100 个字符，较长的描述应使用 description 字段。标题中不应使用“binding”“schema”或“driver”等词，因为所有内容都是绑定。

title: Acme Foo UART (Universal Asynchronous Receiver/Transmitter)

描述

此处填写节点硬件的自由格式描述，也可以放置数据手册的链接，或示例节点或属性。

Compatible

此键用于按照 设备树绑定简介 中所述的方式将节点与该绑定匹配。在绑定文件中应形如：

# Note the comma-separated vendor prefix and device name
compatible: "manufacturer,device"

下面的设备树节点会与上述绑定匹配：

device {
     compatible = "manufacturer,device";
};

假设没有任何绑定带有 compatible: "manufacturer,device-v2"，那么下面的节点也会与之匹配：

device-2 {
    compatible = "manufacturer,device-v2", "manufacturer,device";
};

节点 compatible 属性中的各个值会依次尝试。绑定 由（compatible，on-bus）二元组唯一标识，其中 on-bus 可以不指定。指定了 on-bus 的绑定优先于未指定的绑定。使用第一个匹配的绑定。

对于下面的设备：

spi-bus {
        device-3 {
                compatible = "manufacturer,device";
        };
};

以下两个绑定可以共存，并按如下顺序匹配：

manufacturer,device-spi.yaml

compatible: "manufacturer,device"
on-bus: spi

manufacturer,device.yaml

compatible: "manufacturer,device"

下面的绑定可以共存，但不会匹配。

manufacturer,device-i2c.yaml

compatible: "manufacturer,device"
on-bus: i2c

如果为某个 compatible 找到多个匹配的绑定，则会报错。

manufacturer 前缀标识设备厂商。可接受的厂商前缀列表请参见 dts/bindings/vendor-prefixes.txt。device 部分通常取自数据手册。

有些绑定适用于没有特定厂商的一类通用设备，这种情况下没有厂商前缀。例如 gpio-leds compatible，它通常用于描述连接到 GPIO 的开发板 LED。

属性

properties: 键描述与该绑定匹配的节点所包含的属性。例如，UART 外设的绑定可能类似下面这样：

compatible: "manufacturer,serial"

properties:
  reg:
    type: array
    description: UART peripheral MMIO register space
    required: true
  current-speed:
    type: int
    description: current baud rate
    required: true

在本例中，compatible 为 "manufacturer,serial" 的节点必须包含名为 current-speed 的属性，且该属性的值必须是单个整数。同样，该节点还必须包含 reg 属性。

构建系统使用绑定为 DTS 文件中出现的设备树属性生成 C 宏。关于如何在源代码中通过这些宏获取属性值，可以在 从 C/C++ 访问设备树 中了解更多。一般来说，构建系统只为匹配绑定的 properties: 键中列出的属性生成宏。绑定中未提及的属性通常会被构建系统忽略。

唯一的例外是，构建系统总会为标准属性生成宏，例如 reg，其含义由设备树规范定义。无论节点是否有匹配的绑定，都会如此。

属性条目语法

properties: 中的属性条目按以下语法书写：

<property name>:
  required: <true | false>
  type: <string | int | boolean | array | uint8-array | string-array |
         phandle | phandles | phandle-array | path | compound>
  deprecated: <true | false>
  default: <default>
  description: <description of the property>
  enum:
    - <item1>
    - <item2>
    ...
    - <itemN>
  const: <string | int | array | uint8-array | string-array>
  min: <int>
  max: <int>
  min-len: <int>
  max-len: <int>
  specifier-space: <space-name>
  dependency-mode: <normal | reverse | ignore | child-ignore>

属性定义示例

下面是更多示例。

properties:
    # Describes a property like 'current-speed = <115200>;'. We pretend that
    # it's obligatory for the example node and set 'required: true'.
    current-speed:
        type: int
        required: true
        description: Initial baud rate for bar-device

    # Describes an optional property like 'keys = "foo", "bar";'
    keys:
        type: string-array
        description: Keys for bar-device

    # Describes an optional property like 'maximum-speed = "full-speed";'
    # the enum specifies known values that the string property may take
    maximum-speed:
        type: string
        description: Configures USB controllers to work up to a specific speed.
        enum:
           - "low-speed"
           - "full-speed"
           - "high-speed"
           - "super-speed"

    # Describes an optional property like 'resolution = <16>;'
    # the enum specifies known values that the int property may take
    resolution:
      type: int
      enum:
       - 8
       - 16
       - 24
       - 32

    # Describes a required property '#address-cells = <1>';  the const
    # specifies that the value for the property is expected to be the value 1
    "#address-cells":
        type: int
        required: true
        const: 1

    int-with-default:
        type: int
        default: 123
        description: Value for int register, default is power-up configuration.

    array-with-default:
        type: array
        default: [1, 2, 3] # Same as 'array-with-default = <1 2 3>'

    string-with-default:
        type: string
        default: "foo"

    string-array-with-default:
        type: string-array
        default: ["foo", "bar"] # Same as 'string-array-with-default = "foo", "bar"'

    uint8-array-with-default:
        type: uint8-array
        default: [0x12, 0x34] # Same as 'uint8-array-with-default = [12 34]'

required

在属性定义中添加 required: true 后，如果某个节点与该绑定匹配但不包含该属性，构建就会失败。

默认设置为 required: false，也就是说，属性默认是可选的。因此，使用 required: false 是多余的，强烈不建议这样写。

type

属性的类型约束其取值。可用的类型如下。关于如何在 DTS 文件中书写各类型的值，请参见 书写属性值。关于 phandle* 类型属性的更多信息，请参见 phandle。

类型

描述

DTS 示例

string

恰好一个字符串

status = "disabled";

int

恰好一个 32 位值（单元）

current-speed = <115200>;

boolean

标志，为 true 时不带值，为 false 时不出现

hw-flow-control;

array

零个或多个 32 位值（单元）

offsets = <0x100 0x200 0x300>;

uint8-array

零个或多个十六进制表示的字节（设备树规范中称为“bytestring”）

local-mac-address = [de ad be ef 12 34];

string-array

零个或多个字符串

dma-names = "tx", "rx";

phandle

恰好一个 phandle

interrupt-parent = <&gic>;

phandles

零个或多个 phandle

pinctrl-0 = <&usart2_tx_pd5 &usart2_rx_pd6>;

phandle-array

由 phandle 和 32 位单元（通常是说明符）组成的列表

dmas = <&dma0 2>, <&dma0 3>;

path

指向某个节点的路径，以 phandle 路径引用或路径字符串表示

zephyr,bt-c2h-uart = &uart0; 或 foo = "/path/to/some/node";

compound

用于更复杂类型的兜底类型（不会生成宏）

foo = <&label>, [01 02];

deprecated

带有 deprecated: true 的属性向用户和工具表明该属性将被逐步淘汰。

如果设备树中包含被标记为已弃用的属性，工具会报告警告。（对于提交到上游的 PR，测试运行器（Twister） 会将该警告升级为错误。）

默认设置为 deprecated: false。因此，使用 deprecated: false 是多余的，强烈不建议这样写。

default

可选的 default: 设置给出一个值，当设备树节点中缺少该属性时使用该值。

例如，对于下面的绑定片段：

properties:
  foo:
    type: int
    default: 3

如果匹配节点中缺少属性 foo，输出结果就如同 DTS 中出现了 foo = <3>; 一样（只是默认值使用 YAML 数据类型）。

注意，如果绑定为同一个属性同时声明了 default: 和 required: true，会产生警告，因为这两项设置是冗余的：缺少该属性时，required: true 已经会使构建失败，因此默认值永远不会生效。绑定仍然可以用 required: true 覆盖继承来的 default:，以强制要求显式赋值；这种用法有明确定义，不会被报告。只通过 include: 引入的绑定在构建期间不会被单独加载，因此针对它的警告会在生成文档时出现，而不是在构建应用程序时出现。

关于上游 Zephyr 绑定中与 default 相关的规则，请参见 默认值规则。

示例请参见 属性定义示例。如果在 属性定义示例 中所用类型以外的任何属性类型上使用 default:，都会报错。

enum

enum: 行后面跟着属性可以取的值的列表。如果 DTS 中的属性值不在绑定的 enum: 列表中，就会报错。示例请参见 属性定义示例。

min 和 max

min: 和 max: 键约束 type: int 或 type: array 属性的有效取值范围。如果 DTS 中的属性值超出 [min, max] 范围，就会报错。

这两个键都是可选的且相互独立，可以只指定 min:、只指定 max:，或两者都指定。它们不能与 enum: 用在同一个属性上。

对于 type: array，数组的每个元素都会根据该范围进行检查。

示例：

properties:
  # A brightness percentage between 0 and 100
  brightness:
    type: int
    min: 0
    max: 100
    description: LED brightness as a percentage

  # A timeout in milliseconds, with a minimum of 1 ms (no upper bound)
  timeout-ms:
    type: int
    min: 1
    description: Timeout in milliseconds

min-len 和 max-len

min-len: 和 max-len: 键约束数组类属性（array、uint8-array、string-array、phandles 和 phandle-array）的元素个数（长度）。如果 DTS 中属性值的长度超出 [min-len, max-len] 范围，就会报错。

这两个键都是可选的且相互独立，可以只指定 min-len:、只指定 max-len:，或两者都指定。

示例：

properties:
  # An array of exactly 3 integers
  coordinates:
    type: array
    min-len: 3
    max-len: 3
    description: 3D coordinates

  # A list of up to 4 GPIO phandles
  gpios:
    type: phandle-array
    max-len: 4
    description: Up to 4 GPIOs

const

指定属性必须取的常量值。它主要用于为特定硬件约束通用属性的取值。

specifier-space

警告

用此功能以非常规方式为属性命名属于滥用。

例如，此功能并不适用于这样的情况：把属性命名为 my-pin，然后用此功能将其分配到“gpio”说明符空间。引用 GPIO 的属性应使用常规名称，即以 -gpios 或 -gpio 结尾。

如果存在此属性，它会手动设置与 phandle-array 类型属性关联的说明符空间。

通常，说明符空间隐式地编码在属性名中。类型为 phandle-array、名为 foos 的属性隐式地具有说明符空间 foo。作为特例，*-gpios 属性的说明符空间为“gpio”，因此 foo-gpios 的说明符空间是“gpio”而不是“foo-gpio”。

如果遵循这一约定会得到别扭或不合常规的名称，可以使用 specifier-space 手动提供一个空间。

例如：

compatible: ...
properties:
  bar:
    type: phandle-array
    specifier-space: my-custom-space

上例中，bar 属性的说明符空间被设置为“my-custom-space”。

然后可以在设备树中这样使用该属性：

controller1: custom-controller@1000 {
        #my-custom-space-cells = <2>;
};

controller2: custom-controller@2000 {
        #my-custom-space-cells = <1>;
};

my-node {
        bar = <&controller1 10 20>, <&controller2 30>;
};

一般来说，应只在隐式说明符空间命名约定行不通的情况下使用此功能。一个合适的例子是 mboxes 属性，其说明符空间应为“mbox”，而不是“mboxe”。可以这样书写该属性：

properties:
  mboxes:
    type: phandle-array
    specifier-space: mbox

dependency-mode

dependency-mode 设置控制在 Zephyr 中计算依赖关系图时如何处理 phandle 属性。

默认情况下，任何 phandle 属性 都会在包含该属性的节点与其引用的节点之间建立依赖关系。dependency-mode 设置允许覆盖这一行为。

可选值

dependency-mode 设置接受以下值：

normal 或未指定

默认行为。引用方节点依赖于被引用节点（phandle 所指向的节点）。

reverse

反转依赖方向。不再是引用方节点依赖被引用节点，而是被引用节点依赖引用方节点。

ignore

该 phandle 属性不建立依赖关系。

child-ignore

与 ignore 类似，但只有当被引用节点是引用方节点的子节点时才忽略依赖。如果被引用节点不是子节点，则建立正常的依赖关系。

当 phandle 可能引用子节点（无需依赖）或外部节点（需要依赖）时，使用此值。

使用 dependency-mode

dependency-mode 设置在绑定文件的属性定义中指定。示例如下：

compatible: "vendor,ethernet-controller"

properties:
  phy-handle:
    type: phandle
    description: |
      Specifies a reference to a node representing a PHY device.
    dependency-mode: ignore

另一个使用 child-ignore 的示例：

compatible: "vendor,node-with-optional-phandle"

properties:
  optional-ref:
    type: phandle
    description: |
      References either a child node or an external device.
      Child node references create no dependency, but external
      device references do.
    dependency-mode: child-ignore

使用该绑定的 DTS 示例：

root {
        external_dev: external-device@2000 {
                compatible = "vendor,external-device";
                reg = <0x2000 0x100>;
        };

        parent_dev: parent-device@1000 {
                compatible = "vendor,node-with-optional-phandle";
                reg = <0x1000 0x100>;
                optional-ref = <&internal_child>; /* child: ignored dependency */

                internal_child: internal-device {
                        compatible = "vendor,internal-device";
                };
        };

        peer_dev: peer-device@3000 {
                compatible = "vendor,node-with-optional-phandle";
                reg = <0x3000 0x100>;
                optional-ref = <&external_dev>; /* external: normal dependency */
        };
};

默认行为

如果未指定 dependency-mode，其默认值为 normal，表示引用方节点依赖于被引用节点。

子绑定（child-binding）

当一个节点的所有子节点共享相同的属性时，可以使用 child-binding。每个子节点都将 child-binding 的内容作为其绑定，不过如果子节点上显式写有 compatible = ... 并且为其找到了绑定，则以后者为准。

以下面这样的 PWM LED 节点的绑定为例，其中要求子节点具有 pwms 属性：

pwmleds {
        compatible = "pwm-leds";

        red_pwm_led {
                pwms = <&pwm3 4 15625000>;
        };
        green_pwm_led {
                pwms = <&pwm3 0 15625000>;
        };
        /* ... */
};

绑定如下所示：

compatible: "pwm-leds"

child-binding:
  description: LED that uses PWM

  properties:
    pwms:
      type: phandle-array
      required: true

child-binding 也可以递归使用。例如，下面的绑定：

compatible: foo

child-binding:
  child-binding:
    properties:
      my-property:
        type: int
        required: true

会应用于以下 DTS 中的 grandchild 节点：

parent {
        compatible = "foo";
        child {
                grandchild {
                        my-property = <123>;
                };
        };
};

总线（bus）

如果节点是总线控制器，请在绑定中使用 bus: 说明总线类型。例如，SoC 上 SPI 外设的绑定如下所示：

compatible: "manufacturer,spi-peripheral"
bus: spi
# ...

绑定中存在此键，就告诉构建系统：与该绑定匹配的任何节点，其子节点都位于这种类型的总线上。

这进而会影响使用 on-bus: 为子节点匹配绑定的方式。

对于支持多种协议（例如 I3C 和 I2C）的单一总线，绑定中的 bus: 可以取一个列表作为值：

compatible: "manufacturer,i3c-controller"
bus: [i3c, i2c]
# ...

所在总线（on-bus）

如果节点是位于某条总线上的设备，请在绑定中使用 on-bus: 说明总线类型。

例如，外部 SPI 存储芯片的绑定应包含这一行：

on-bus: spi

基于 I2C 的温度传感器的绑定应包含这一行：

on-bus: i2c

为节点查找绑定时，构建系统会检查父节点的绑定是否包含 bus: <bus type>。如果包含，则只考虑具有匹配的 on-bus: <bus type> 的绑定以及未显式指定 on-bus 的绑定。显式指定了 on-bus: <bus type> 的绑定会先于未显式指定 on-bus 的绑定被搜索。对节点 compatible 属性中的每一项，依次重复该搜索。

此功能使同一设备可以根据其所在的总线使用不同的绑定。例如，考虑一个 compatible 为 manufacturer,sensor 的传感器设备，它既可以通过 I2C 使用，也可以通过 SPI 使用。

因此，该传感器节点在设备树中既可能作为 SPI 控制器的子节点出现，也可能作为 I2C 控制器的子节点出现，如下所示：

spi-bus@0 {
   /* ... some compatible with 'bus: spi', etc. ... */

   sensor@0 {
       compatible = "manufacturer,sensor";
       reg = <0>;
       /* ... */
   };
};

i2c-bus@0 {
   /* ... some compatible with 'bus: i2c', etc. ... */

   sensor@79 {
       compatible = "manufacturer,sensor";
       reg = <79>;
       /* ... */
   };
};

尽管这两个传感器节点的 compatible 相同，你也可以编写两个独立的绑定文件分别与之匹配：

# manufacturer,sensor-spi.yaml, which matches sensor@0 on the SPI bus:
compatible: "manufacturer,sensor"
on-bus: spi

# manufacturer,sensor-i2c.yaml, which matches sensor@79 on the I2C bus:
compatible: "manufacturer,sensor"
properties:
  uses-clock-stretching:
    type: boolean
on-bus: i2c

只有 sensor@79 可以具有 use-clock-stretching 属性。为 sensor@0 查找绑定时，与总线相关的逻辑会忽略 manufacturer,sensor-i2c.yaml。

类（class）

如果与绑定匹配的节点可以用作一个或多个 Zephyr 设备类的设备，请使用 class: 声明这些类：

compatible: "manufacturer,adc"
class: adc

其值是一个设备类名或名称列表。名称由小写字母、数字、- 和 _ 组成，格式错误或重复的名称会被拒绝。每个名称都应与通过 DEVICE_API 注册的某个设备 API 类（例如 adc）相匹配。小写加短横线形式的名称会按照与 compatible 相同的方式转换为小写加下划线形式的 C 记号。

该键声明节点的驱动 能够 实现哪些设备 API 类；至于实际为节点构建哪个驱动和 API，仍由 Kconfig 决定。列表值适用于驱动可以根据配置实现多个 API 的硬件：

compatible: "manufacturer,rtc"
class: [rtc, counter]

class: 通常在设备类的基础绑定（例如 dts/bindings/adc/adc-controller.yaml）中声明一次，这样每个包含它的绑定都会继承该类。当绑定及其包含的文件都声明了类时，取各值的并集：包含多个类基础绑定的绑定属于所有这些类。

可以在构建时使用 DT_NODE_HAS_CLASS 查询类成员关系，使用 DT_FOREACH_CLASS_STATUS_OKAY 遍历，使用 DT_NUM_CLASS_STATUS_OKAY 计数，并在 Kconfig 中使用 $(dt_class_enabled,<class name>) 进行测试。

如果要为绑定无法修改的设备添加类，例如在下游模块中为上游设备分类，可以定义一个更具体的 compatible，使其绑定包含原有绑定并声明该类，然后在节点上同时列出这两个 compatible：

# vnd,foo-classed.yaml
compatible: "vnd,foo-classed"
include: vnd,foo.yaml
class: xyz

compatible = "vnd,foo-classed", "vnd,foo";

节点的绑定及其类来自第一个具有绑定的 compatible；驱动会匹配节点的任意一个 compatible，因此原有驱动仍会绑定到该节点。同一个 compatible 有两个绑定会报错，因此无法遮蔽现有的绑定。

示例

如果想为绑定提供一个最小示例，可以这样写：

description: ...

properties:
 ...

examples:
  - |
    leds {
      compatible = "gpio-leds";

      uled: led {
      gpios = <&gpioe 12 GPIO_ACTIVE_HIGH>;
      };
    };

说明符单元名称（*-cells）

本节介绍如何在绑定中为说明符中的单元命名。这些概念在本指南后面的 phandle-array 属性 中有详细讨论。

以某个节点的绑定为例，该节点的 phandle 可能出现在 phandle-array 属性中，就像本例中的 PWM 控制器 pwm1 和 pwm2：

pwm1: pwm@deadbeef {
    compatible = "foo,pwm";
    #pwm-cells = <2>;
};

pwm2: pwm@deadbeef {
    compatible = "bar,pwm";
    #pwm-cells = <1>;
};

my-node {
    pwms = <&pwm1 1 2000>, <&pwm2 3000>;
};

compatible 为 "foo,pwm" 和 "bar,pwm" 的绑定必须使用 pwm-cells: 为 PWM 说明符中出现的单元命名，如下所示：

# foo,pwm.yaml
compatible: "foo,pwm"
...
pwm-cells:
  - channel
  - period

# bar,pwm.yaml
compatible: "bar,pwm"
...
pwm-cells:
  - period

节点上还可以出现 *-names 属性（例如 pwm-names），为每个条目命名。

这样就可以按名称访问说明符中的单元，例如使用 DT_PWMS_CHANNEL_BY_NAME 等 API。

如果说明符为空（例如 #clock-cells = <0>），则 *-cells 可以省略（推荐），也可以设为空数组。注意，在 YAML 中空数组写作 clock-cells: [] 这样的形式。

Include

绑定可以包含其他文件，从而在绑定之间共享公共的属性定义。为此请使用 include: 键，其值可以是字符串或列表。

最简单的情况下，可以用字符串给出另一个文件的名称来包含它，如下所示：

include: foo.yaml

如果找到任何名为 foo.yaml 的文件（查找过程请参见 绑定的存放位置），它就会被包含到该绑定中。

被包含的文件通过简单的递归字典合并并入绑定。构建系统会检查合并后的绑定格式是否正确。可以在任意层级进行包含，包括 child-binding，如下所示：

# foo.yaml will be merged with content at this level
include: foo.yaml

child-binding:
  # bar.yaml will be merged with content at this level
  include: bar.yaml

如果某个键在绑定及其包含的文件中取值不同，就会报错，但有两个例外：对于某个 属性定义，被包含文件中为 required: false 时，绑定可以写 required: true（以 required: true 为准，使绑定可以加强被包含文件中的要求）；class: 的值按 类（class） 中所述取并集。

注意，如果被包含文件中为 required: true，而绑定中写 required: false 以削弱要求，则会报错。这样做是为了保持结构清晰。

文件 base.yaml 包含许多常用属性的定义。编写新绑定时，最好先检查 base.yaml 是否已经定义了所需的某些属性，如果是，就包含它。

注意，可以像下面这样把 base.yaml 中定义的属性设为必需，这里以 reg 为例：

reg:
  required: true

这依赖字典合并来补全 reg 的其他键，例如 type。

要包含多个文件，可以使用字符串列表：

include:
  - foo.yaml
  - bar.yaml

这会包含文件 foo.yaml 和 bar.yaml。（也可以在 YAML 中把这个列表写成一行：include: [foo.yaml, bar.yaml]。）

包含多个文件时，被包含文件中属性上重叠的 required 键会进行逻辑或运算。这确保 required: true 总会得到遵守。

有时，你可能只想包含某个文件中的部分属性定义，而不是全部。这种情况下，include: 应为列表，并且可以在列表中放入一个映射来筛选出所需的定义，如下所示：

include:
  - name: foo.yaml
    property-allowlist:
      - i-want-this-one
      - and-this-one
  - name: bar.yaml
    property-blocklist:
      - do-not-include-this-one
      - or-this-one

每个映射元素都必须有一个 name 键，表示要包含的文件名，还可以有 property-allowlist 和 property-blocklist 键，用于筛选要包含的属性。

单个映射元素中不能同时包含 property-allowlist 和 property-blocklist 键。既没有 property-allowlist 也没有 property-blocklist 的映射元素是有效的，此时不做额外筛选。

可以在同一个 include: 列表中自由混用字符串和映射：

include:
  - foo.yaml
  - name: bar.yaml
    property-blocklist:
      - do-not-include-this-one
      - or-this-one

最后，还可以像这样从子绑定中进行筛选：

include:
  - name: bar.yaml
    child-binding:
      property-allowlist:
        - child-prop-to-allow

Nexus 节点和映射

所有 phandle-array 类型的属性都支持通过 *-map 属性（例如 gpio-map）进行映射，这是由设备树规范定义的。

例如，这可用于为常见的扩展排针定义连接器节点，例如在带有 Arduino 兼容扩展排针的开发板的设备树中按惯例定义的 arduino_header 节点。
