设备树 HOWTO

本页提供使用设备树完成各项任务的分步建议。

小技巧

故障排除建议请参见 设备树故障排除。

获取设备树和生成的头文件

开发板的设备树（BOARD.dts）通过 #include 预处理指令引入通用的节点定义，其中至少包括 SoC 的 .dtsi。了解设备树内容的一种方法是打开这些文件，例如查看 dts/<ARCH>/<vendor>/<soc>.dtsi，但这可能很耗时。

如果只想查看开发板的“最终”设备树，可以构建一个应用程序，然后打开构建目录中的 zephyr.dts 文件。

小技巧

可以构建 Hello World，查看开发板未经 覆盖文件 做任何额外修改的“基础”设备树。

例如，使用 QEMU Emulation for ARM Cortex-M3 开发板构建 Hello World：

# --cmake-only here just forces CMake to run, skipping the
# build process to save time.
west build -b qemu_cortex_m3 samples/hello_world --cmake-only

可以将 qemu_cortex_m3 改为你的开发板。

CMake 会像下面这样打印输入和输出文件的位置：

-- Found BOARD.dts: .../zephyr/boards/arm/qemu_cortex_m3/qemu_cortex_m3.dts
-- Generated zephyr.dts: .../zephyr/build/zephyr/zephyr.dts
-- Generated devicetree_generated.h: .../zephyr/build/zephyr/include/generated/zephyr/devicetree_generated.h

zephyr.dts 文件是 DTS 格式的最终设备树。

devicetree_generated.h 文件是对应的生成头文件。

关于这些文件的详细信息请参见 输入和输出文件。

从设备树节点获取 struct device

编写 Zephyr 应用程序时，经常需要获取与某个设备树节点对应的驱动级 struct device。

例如，对于下面的设备树片段，你可能需要获取 serial@40002000 的 struct device：

/ {
        soc {
                serial0: serial@40002000 {
                        status = "okay";
                        current-speed = <115200>;
                        /* ... */
                };
        };

        aliases {
                my-serial = &serial0;
        };

        chosen {
                zephyr,console = &serial0;
        };
};

首先为你关心的设备创建一个 节点标识符。创建方法有多种，选择最符合你需求的一种即可。下面是一些示例：

/* Option 1: by node label */
#define MY_SERIAL DT_NODELABEL(serial0)

/* Option 2: by alias */
#define MY_SERIAL DT_ALIAS(my_serial)

/* Option 3: by chosen node */
#define MY_SERIAL DT_CHOSEN(zephyr_console)

/* Option 4: by path */
#define MY_SERIAL DT_PATH(soc, serial_40002000)

有了节点标识符后，有两种方法可以继续。获取设备的一种方法是使用 DEVICE_DT_GET：

const struct device *const uart_dev = DEVICE_DT_GET(MY_SERIAL);

if (!device_is_ready(uart_dev)) {
        /* Not ready, do not use */
        return -ENODEV;
}

DEVICE_DT_GET 有一些变体，例如 DEVICE_DT_GET_OR_NULL、DEVICE_DT_GET_ONE 或 DEVICE_DT_GET_ANY。这种写法在构建时获取设备指针，因此没有运行时开销。如果想把设备指针作为配置数据保存，这种方法很有用。但由于设备可能尚未初始化，或者初始化可能失败，在将其传给任何 API 函数之前，必须先确认设备已就绪可用。（device_get_binding() 会替你完成此项检查。）

在某些情况下，设备在构建时无法确定，例如设备取决于用户输入（如 shell 应用程序中）。这种情况下，可以将 device_get_binding() 与设备名结合使用来获取 struct device：

const char *dev_name = /* TODO: insert device name from user */;
const struct device *uart_dev = device_get_binding(dev_name);

然后可以将 uart_dev 与 通用异步收发器（UART） API 函数（例如 uart_configure()）一起使用。类似的代码也适用于其他设备类型，只要确保为设备使用正确的 API 即可。

如果遇到问题，请参见 设备树故障排除。首先要检查的是节点是否具有 status = "okay"，例如：

#define MY_SERIAL DT_NODELABEL(my_serial)

#if DT_NODE_HAS_STATUS(MY_SERIAL, okay)
const struct device *const uart_dev = DEVICE_DT_GET(MY_SERIAL);
#else
#error "Node is disabled"
#endif

如果看到 #error 输出，请确保在设备树中启用了该节点。在某些情况下，代码可以编译通过，但链接会失败，并出现类似下面的信息：

...undefined reference to `__device_dts_ord_N'
collect2: error: ld returned 1 exit status

这很可能意味着存在 Kconfig 问题，导致设备驱动没有被构建，从而产生了对不存在对象的引用。如果代码编译成功，最后要检查的是设备是否已就绪，例如：

if (!device_is_ready(uart_dev)) {
     printk("Device not ready\n");
}

如果发现设备未就绪，很可能意味着设备的初始化函数失败了。这种情况下，启用日志或调试驱动代码可能会有帮助。注意，也可以使用 device_get_binding() 在运行时获取引用。如果它返回 NULL，可能意味着设备的驱动初始化失败，也可能意味着该设备不存在。

查找设备树绑定

设备树绑定 是声明可以对其所描述节点进行哪些操作的 YAML 文件，因此能够为所用节点找到对应的绑定至关重要。

如果还没有这些文件，请参考 获取设备树和生成的头文件。要查找节点的绑定，请打开生成的头文件，该文件开头是一个块注释，其中列出了所有节点：

/*
 * [...]
 * Nodes in dependency order (ordinal and path):
 *   0   /
 *   1   /aliases
 *   2   /chosen
 *   3   /flash@0
 *   4   /memory@20000000
 *          (etc.)
 * [...]
 */

记下要查找的节点的路径，例如 /flash@0。在文件中搜索该节点的输出，如果该节点有匹配的绑定，其输出开头类似下面这样：

/*
 * Devicetree node:
 *   /flash@0
 *
 * Binding (compatible = soc-nv-flash):
 *   $ZEPHYR_BASE/dts/bindings/mtd/soc-nv-flash.yaml
 * [...]
 */

故障排除请参见 检查是否缺少绑定。

设置设备树覆盖文件

设备树覆盖文件在 设备树简介 中有介绍。CMake 变量 DTC_OVERLAY_FILE 包含要使用的覆盖文件列表，以空格或分号分隔。如果 DTC_OVERLAY_FILE 指定了多个文件，C 预处理器会按该顺序包含它们。设置 DTC_OVERLAY_FILE 变量时，可以通过转义 Zephyr 模块目录变量来引用 Zephyr 模块中的文件，例如 \${ZEPHYR_<module>_MODULE_DIR}/<path-to>/dts.overlay。

可以将 DTC_OVERLAY_FILE 设置为恰好包含你想使用的文件。这里有一个使用 west build 的 示例。

如果没有设置 DTC_OVERLAY_FILE，构建系统会按以下步骤在应用程序配置目录中查找用作设备树覆盖文件的文件：

  1. 如果文件 socs/<SOC>_<BOARD_QUALIFIERS>.overlay 存在，则使用该文件。

  2. 如果文件 boards/<BOARD>.overlay 存在，则在上述文件之外还使用该文件。

  3. 如果当前开发板有 多个版本，并且 boards/<BOARD>_<revision>.overlay 存在，则在上述文件之外还使用该文件。

  4. 如果前面的步骤中找到了一个或多个文件，构建系统就停止查找，只使用这些文件。

  5. 否则，如果 <BOARD>.overlay 存在，则使用该文件，并且构建系统停止查找更多文件。

  6. 否则，如果 app.overlay 存在，则使用该文件。

可以使用 EXTRA_DTC_OVERLAY_FILE 提供额外的设备树覆盖文件，这样构建系统仍会自动使用上述步骤中描述的设备树覆盖文件。

处理设备树覆盖文件时，构建系统会把 EXTRA_DTC_OVERLAY_FILE 中指定的覆盖文件追加到 DTC_OVERLAY_FILE 中的覆盖文件之后。这意味着通过 EXTRA_DTC_OVERLAY_FILE 所做的修改比通过 DTC_OVERLAY_FILE 所做的修改优先级更高。

除了通过 DTC_OVERLAY_FILE 或 EXTRA_DTC_OVERLAY_FILE 参数给出的绝对路径文件外，所有配置文件都从应用程序配置目录中获取。

应用程序配置目录的定义方式请参见 应用程序配置目录。

使用 扩展板 也会添加设备树覆盖文件。

DTC_OVERLAY_FILE 的值存储在 CMake 缓存中，并在后续构建中使用。

构建系统 会在配置阶段像下面这样打印找到的所有设备树覆盖文件：

-- Found devicetree overlay: .../some/file.overlay

使用设备树覆盖文件

如何在构建中添加覆盖文件，请参见 设置设备树覆盖文件。

覆盖文件可以通过多种方式覆盖节点属性值。例如，如果 BOARD.dts 中包含以下节点：

/ {
        soc {
                serial0: serial@40002000 {
                        status = "okay";
                        current-speed = <115200>;
                        /* ... */
                };
        };
};

以下是在覆盖文件中覆盖 current-speed 值的几种等效写法：

/* Option 1 */
&serial0 {
     current-speed = <9600>;
};

/* Option 2 */
&{/soc/serial@40002000} {
     current-speed = <9600>;
};

后续示例都使用 &serial0 这种写法。

可以使用覆盖文件向设备树中添加别名：别名只是 /aliases 节点的一个属性。例如：

/ {
     aliases {
             my-serial = &serial0;
     };
};

chosen 节点的用法相同。例如：

/ {
     chosen {
             zephyr,console = &serial0;
     };
};

删除属性（除了一般意义上的删除属性外，如果某个布尔属性在 BOARD.dts 中为 true，也可以用这种方法将其设为 false）：

&serial0 {
     /delete-property/ some-unwanted-property;
};

可以使用覆盖文件添加子节点。例如，要在现有总线节点上配置 SPI 或 I2C 子设备，可以这样做：

/* SPI device example */
&spi1 {
     my_spi_device: temp-sensor@0 {
             compatible = "...";
             label = "TEMP_SENSOR_0";
             /* reg is the chip select number, if needed;
              * If present, it must match the node's unit address. */
             reg = <0>;

             /* Configure other SPI device properties as needed.
              * Find your device's DT binding for details. */
             spi-max-frequency = <DT_FREQ_M(4)>;
     };
};

/* I2C device example */
&i2c2 {
     my_i2c_device: touchscreen@76 {
             compatible = "...";
             label = "TOUCHSCREEN";
             /* reg is the I2C device address.
              * It must match the node's unit address. */
             reg = <76>;

             /* Configure other I2C device properties as needed.
              * Find your device's DT binding for details. */
     };
};

其他总线设备可以用类似方式配置：

  • 将设备创建为父总线的子节点

  • 按照其绑定设置属性

假设已有与 my_spi_device 和 my_i2c_device compatible 关联的合适设备驱动，现在就可以通过 Kconfig 启用该驱动，并为新添加的总线节点 获取 struct device，然后通过该驱动的 API 使用它。

使用设备树 API 编写设备驱动

“感知设备树”的 设备驱动 应为每个具有该驱动所支持的特定 compatible（或一组相关 compatible）且 status = "okay" 的设备树节点创建一个 struct device。

编写感知设备树的驱动，首先要为驱动所支持的设备定义一个 设备树绑定。可以以类似驱动的现有绑定为起点。入门用的骨架绑定只需要以下内容：

description: <Human-readable description of your binding>
compatible: "foo-company,bar-device"
include: base.yaml

查找现有绑定的更多建议请参见 查找设备树绑定。

编写好绑定后，驱动 C 文件就可以使用设备树 API 查找具有所需 compatible 且 status = "okay" 的节点，并为每个节点实例化一个 struct device。实例化每个 struct device 有两种方式：使用实例编号，或使用节点标签。

无论采用哪种方式：

  • 每个 struct device 的名称都应设置为其设备树节点的 label 属性。这样驱动的使用者就可以按常规方式 从设备树节点获取 struct device。

  • 只要可行，每个设备的初始配置都应使用设备树属性中的值。这样用户就可以使用 设备树覆盖文件 配置驱动。

下面是具体做法的示例。这些示例假设你已经实现了设备专用的配置和数据结构以及 API 函数，如下所示：

/* my_driver.c */
#include <zephyr/drivers/some_api.h>

/* Define data (RAM) and configuration (ROM) structures: */
struct my_dev_data {
     /* per-device values to store in RAM */
};
struct my_dev_cfg {
     uint32_t freq; /* Just an example: initial clock frequency in Hz */
     /* other configuration to store in ROM */
};

/* Implement driver API functions (drivers/some_api.h callbacks): */
static int my_driver_api_func1(const struct device *dev, uint32_t *foo) { /* ... */ }
static int my_driver_api_func2(const struct device *dev, uint64_t bar) { /* ... */ }
static struct some_api my_api_funcs = {
     .func1 = my_driver_api_func1,
     .func2 = my_driver_api_func2,
};

方式 1：使用实例编号创建设备

如果可能，请使用这种方式，它使用 基于实例的 API。不过，只有当驱动 compatible 对应的设备树节点全部等价，并且不需要区分它们时，这些 API 才适用。

要使用基于实例的 API，首先将 DT_DRV_COMPAT 定义为设备驱动所支持 compatible 的小写加下划线形式。例如，如果驱动在设备树中的 compatible 为 "vnd,my-device"，则应在驱动 C 文件中将 DT_DRV_COMPAT 定义为 vnd_my_device：

/*
 * Put this near the top of the file. After the includes is a good place.
 * (Note that you can therefore run "git grep DT_DRV_COMPAT drivers" in
 * the zephyr Git repository to look for example drivers using this style).
 */
#define DT_DRV_COMPAT vnd_my_device

重要

如上所示，DT_DRV_COMPAT 宏既不应包含引号，也不应包含特殊字符。根据 compatible 属性创建 DT_DRV_COMPAT 时，应去掉引号并把特殊字符转换为下划线。

最后，定义一个实例化宏，使用实例编号创建每个 struct device。请在定义 my_api_funcs 之后进行此操作。

/*
 * This instantiation macro is named "CREATE_MY_DEVICE".
 * Its "inst" argument is an arbitrary instance number.
 *
 * Put this near the end of the file, e.g. after defining "my_api_funcs".
 */
#define CREATE_MY_DEVICE(inst)                                       \
     static struct my_dev_data my_data_##inst = {                    \
             /* initialize RAM values as needed, e.g.: */            \
             .freq = DT_INST_PROP(inst, clock_frequency),            \
     };                                                              \
     static const struct my_dev_cfg my_cfg_##inst = {                \
             /* initialize ROM values as needed. */                  \
     };                                                              \
     DEVICE_DT_INST_DEFINE(inst,                                     \
                           my_dev_init_function,                     \
                           NULL,                                     \
                           &my_data_##inst,                          \
                           &my_cfg_##inst,                           \
                           MY_DEV_INIT_LEVEL, MY_DEV_INIT_PRIORITY,  \
                           &my_api_funcs);

注意，这里使用 DT_INST_PROP 和 DEVICE_DT_INST_DEFINE 等 API 访问设备树节点数据。这些 API 从设备树中获取 compatible 由 DT_DRV_COMPAT 决定的节点中实例编号为 inst 的那个节点的数据。

最后，将实例化宏传给 DT_INST_FOREACH_STATUS_OKAY：

/* Call the device creation macro for each instance: */
DT_INST_FOREACH_STATUS_OKAY(CREATE_MY_DEVICE)

DT_INST_FOREACH_STATUS_OKAY 展开后的代码会为每个具有 DT_DRV_COMPAT 所决定 compatible 的已启用节点调用一次 CREATE_MY_DEVICE。它不会在 CREATE_MY_DEVICE 展开结果的末尾追加分号，因此为了支持多个设备，该宏的展开结果必须以分号或函数定义结尾。

方式 2：使用节点标签创建设备

有些设备驱动无法使用实例编号。例如，某些 SoC 外设驱动依赖针对各个 IP 模块专门设计的厂商 HAL API 来实现 Zephyr 驱动回调。这类情况应使用 DT_NODELABEL 引用设备树中代表 SoC 上所支持外设的各个节点，然后可以使用 devicetree.h 的 通用 API 访问节点数据。

为此，SoC 的 dtsi 文件 必须为驱动所支持的 IP 模块适当定义 mydevice0、mydevice1 等节点标签。生成的设备树通常类似下面这样：

/ {
        soc {
                mydevice0: dev@0 {
                        compatible = "vnd,my-device";
                };
                mydevice1: dev@1 {
                        compatible = "vnd,my-device";
                };
        };
};

驱动可以使用设备树中的 mydevice0 和 mydevice1 节点标签来操作特定的设备节点：

/*
 * This is a convenience macro for creating a node identifier for
 * the relevant devices. An example use is MYDEV(0) to refer to
 * the node with label "mydevice0".
 */
#define MYDEV(idx) DT_NODELABEL(mydevice ## idx)

/*
 * Define your instantiation macro; "idx" is a number like 0 for mydevice0
 * or 1 for mydevice1. It uses MYDEV() to create the node label from the
 * index.
 */
#define CREATE_MY_DEVICE(idx)                                        \
     static struct my_dev_data my_data_##idx = {                     \
             /* initialize RAM values as needed, e.g.: */            \
             .freq = DT_PROP(MYDEV(idx), clock_frequency),           \
     };                                                              \
     static const struct my_dev_cfg my_cfg_##idx = { /* ... */ };    \
     DEVICE_DT_DEFINE(MYDEV(idx),                                    \
                     my_dev_init_function,                           \
                     NULL,                                           \
                     &my_data_##idx,                                 \
                     &my_cfg_##idx,                                  \
                     MY_DEV_INIT_LEVEL, MY_DEV_INIT_PRIORITY,        \
                     &my_api_funcs)

注意，这里使用 DT_PROP 和 DEVICE_DT_DEFINE 等 API 访问设备树节点数据。

最后，手动检测每个已启用的设备树节点，并使用 CREATE_MY_DEVICE 实例化每个 struct device：

#if DT_NODE_HAS_STATUS(DT_NODELABEL(mydevice0), okay)
CREATE_MY_DEVICE(0)
#endif

#if DT_NODE_HAS_STATUS(DT_NODELABEL(mydevice1), okay)
CREATE_MY_DEVICE(1)
#endif

由于这种写法不使用 DT_INST_FOREACH_STATUS_OKAY()，驱动作者需要负责为每个可能的节点调用 CREATE_MY_DEVICE()，例如根据对所支持 SoC 上可用外设的了解来调用。

依赖其他设备的设备驱动

有时，一个 struct device 依赖另一个 struct device，并需要一个指向它的指针。例如，传感器设备可能需要一个指向其 SPI 总线控制器设备的指针。一些建议：

  • 编写设备树绑定时，尽可能使其允许使用 devicetree.h 中的 硬件专用 API。

  • 特别是对于总线设备，驱动的绑定应包含 dts/bindings/spi/spi-device.yaml 之类的文件，这类文件为可通过特定总线寻址的设备提供通用定义。这样就可以使用 DT_BUS 等 API 获取总线节点的节点标识符，然后按常规方式为该总线 从设备树节点获取 struct device。

可以在现有的绑定和设备驱动中查找示例。
