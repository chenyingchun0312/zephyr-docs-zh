设备树绑定简介

备注

详细的语法参考请参见 设备树绑定语法。

设备树节点通过其 compatible 属性 与绑定进行匹配。

在 配置阶段 期间，构建系统会尝试将设备树中的每个节点与一个绑定文件进行匹配。匹配成功后，构建系统在校验节点内容和为节点生成宏时，都会使用绑定文件中的信息。

一个简单示例

下面是一个设备树节点示例：

/* Node in a DTS file */
bar-device {
     compatible = "foo-company,bar-device";
     num-foos = <3>;
};

下面是一个与该节点匹配的最小绑定文件：

# A YAML binding matching the node

compatible: "foo-company,bar-device"

properties:
  num-foos:
    type: int
    required: true

构建系统之所以把 bar-device 节点与其 YAML 绑定匹配，是因为该节点的 compatible 属性与绑定中的 compatible: 行相匹配。

构建系统如何使用绑定

构建系统使用绑定来校验设备树节点，并将设备树的内容转换为生成的 devicetree_generated.h 头文件。

例如，构建系统会使用上述绑定检查 bar-device 节点中是否存在必需的 num-foos 属性，以及其值 <3> 的类型是否正确。

然后，构建系统会为 bar-device 节点的 num-foos 属性生成一个宏，该宏展开为整数字面量 3。借助这个宏，你可以在 C 代码中使用相应 API 获取该属性的值，本指南后面的 从 C/C++ 访问设备树 会讨论该 API。

再举一个例子，下面的节点会导致构建错误，因为它没有 num-foos 属性，而该属性在绑定中被标记为必需：

bad-node {
     compatible = "foo-company,bar-device";
};

节点与绑定匹配的其他方式

如果节点的 compatible 属性中有多个字符串，构建系统会按列出的顺序查找兼容的绑定，并使用第一个匹配项。

以下面的节点为例：

baz-device {
     compatible = "foo-company,baz-device", "generic-baz-device";
};

如果构建系统找不到带有 compatible: "foo-company,baz-device" 行的绑定，baz-device 节点就会与带有 compatible: "generic-baz-device" 行的绑定匹配。

没有 compatible 属性的节点可以与其父节点关联的绑定匹配，这类绑定称为“子绑定”（child binding）。如果节点描述的是 I2C 或 SPI 等总线上的硬件，在将节点与绑定匹配时还会考虑总线类型（详情请参见 所在总线（on-bus））。

关于一个不需要任何绑定的特殊节点，请参见 /zephyr,user 节点。

绑定的存放位置

绑定文件名通常与其 compatible: 行一致。例如，按照惯例，上面的示例绑定应命名为 foo-company,bar-device.yaml。

构建系统会在以下位置的 dts/bindings 子目录中查找绑定：

  • zephyr 仓库

  • 你的 应用程序源目录

  • 你的 开发板目录

  • 任何 扩展板目录

  • 通过 DTS_ROOT CMake 变量手动包含的任何目录

  • 在其 构建设置 中定义了 dts_root 的任何 模块

在将节点与绑定匹配时，构建系统会考虑上述任意位置（包括其任意子目录）中的所有 YAML 文件。文件名以 .yaml 或 .yml 结尾的文件被视为 YAML 文件。

警告

绑定文件必须位于上述位置的 dts/bindings 子目录内的某处。

例如，如果 my-app 是你的应用程序目录，则必须将应用程序专用的绑定放在 my-app/dts/bindings 中。这样，my-app/dts/bindings/serial/my-company,my-serial-port.yaml 会被找到，而 my-app/my-company,my-serial-port.yaml 会被忽略。
