对二进制文件签名

二进制文件可以选择在构建过程中通过 CMake 代码自动签名，也可以使用 west sign 对二进制文件签名。本页介绍前一种方式，后一种方式请参阅 签名二进制文件。

MCUboot / imgtool

Zephyr 构建系统专门支持使用 MCUboot 引导加载程序的开发者所提供的 imgtool 程序，为该引导加载程序签名二进制文件。只需设置一些 Kconfig 选项，就能一步完成这类应用程序二进制文件的构建和签名。这样设置后，west flash 会使用签名后的二进制文件。

下面是一个示例工作流程，它构建并烧录 MCUboot，以及由 MCUboot 链式加载的 Hello World 应用程序。请在 入门指南 中创建的 zephyrproject 工作区中运行这些命令。

west build -b YOUR_BOARD zephyr/samples/hello_world --sysbuild -d build-hello-signed -- \
     -DSB_CONFIG_BOOTLOADER_MCUBOOT=y

west flash -d build-hello-signed

关于上述命令的说明：

  • 应将 YOUR_BOARD 改为你的开发板

  • 签名密钥值是 MCUboot 提供并用于开发和测试的不安全默认密钥

  • 可以将 hello_world 应用程序目录换成任何其他可由 MCUboot 加载的应用程序，例如 SMP server 示例。

有关这些选项及其他相关配置选项的更多信息，请参阅：

  • SB_CONFIG_BOOTLOADER_MCUBOOT：构建供 MCUboot 加载的应用程序

  • SB_CONFIG_BOOT_SIGNATURE_KEY_FILE：签名镜像时使用的密钥文件，或以逗号分隔的密钥文件列表。如果你有自己的密钥，请相应地修改此项；关于使用绝对路径或 ${APP_DIR} 之类的 CMake 变量，请参阅 签名密钥文件。给出列表时，MCUboot 会嵌入每个密钥的公钥部分，并接受用其中任一密钥签名的镜像；第一项同时用于签名应用程序，第一项之后的每一项都必须是 imgtool 可用的、签名类型相同的仅含公钥的 PEM 文件。

  • CONFIG_MCUBOOT_EXTRA_IMGTOOL_ARGS：传给 imgtool 的可选附加命令行参数

  • CONFIG_MCUBOOT_GENERATE_CONFIRMED_IMAGE：同时生成一个已确认镜像，在生产环境中烧录时，它可能比默认的可 OTA 升级镜像更有用

  • 在 Windows 上，如果遇到“Access denied”问题，推荐的解决方法是运行 pip3 install imgtool，然后使用全新的构建目录重试。

关于在 QEMU 下端到端运行多密钥引导加载程序的完整示例，请参阅 tests/boot/mcuboot_multiple_keys 测试。

如果你的 west flash 运行器 使用 imgtool 支持的镜像格式，那么运行 west flash -d build-hello-signed 时，应该会在设备的串口控制台上看到类似下面的输出：

[00:00:00.011,169] <inf> mcuboot: Primary image: magic=unset, swap_type=0x1, copy_done=0x3, image_ok=0x3
[00:00:00.021,636] <inf> mcuboot: Boot source: none
[00:00:00.027,374] <inf> mcuboot: Swap type: none

签名密钥文件

使用 sysbuild 构建时，SB_CONFIG_BOOT_SIGNATURE_KEY_FILE 选择用于签名镜像的密钥。它的值会传递给两个镜像：

  • 应用程序镜像，作为 CONFIG_MCUBOOT_SIGNATURE_KEY_FILE，imgtool 用它来签名应用程序；以及

  • MCUboot 镜像，作为 CONFIG_BOOT_SIGNATURE_KEY_FILE，其公钥部分会编译进引导加载程序，以便验证该签名。

警告

默认值指向 MCUboot 自带的某个不安全的开发密钥（例如 root-ec-p256.pem）。这些密钥是公开的，每份 Zephyr 和 MCUboot 代码中都附带了它们，因此只适用于开发和测试。用于其他任何场合时，请生成自己的密钥，并且不要把私钥放在任何不受你控制的仓库或构建目录中。

sysbuild 如何解析密钥文件路径

SB_CONFIG_BOOT_SIGNATURE_KEY_FILE 的值会经过 CMake 的 string(CONFIGURE) 命令处理，因此其中包含的任何 ${VARIABLE} 引用都会在使用该路径之前作为 CMake 变量展开。展开后，绝对路径按原样使用；相对路径则由每个镜像各自解析：

镜像

相对路径的查找顺序

应用程序（CONFIG_MCUBOOT_SIGNATURE_KEY_FILE）

先查找 APPLICATION_CONFIG_DIR，再查找 west 工作区顶层目录（WEST_TOPDIR）

MCUboot（CONFIG_BOOT_SIGNATURE_KEY_FILE）

先查找 APPLICATION_CONFIG_DIR，再查找 MCUboot 模块目录

警告

每个镜像以不同的基准目录解析相对路径，因此单纯的相对路径对每个镜像指向的是不同的文件，通常会导致构建失败。不要使用这种路径：请给出绝对路径，或用 CMake 变量作为路径的锚点。

推荐使用 ${APP_DIR}（主应用程序的源代码目录）作为锚点：它让密钥保留在你自己的应用程序中，并且两个镜像都会将其解析为同一个文件。也可以使用在展开该值时可用的任何 CMake 变量：

# sysbuild.conf
SB_CONFIG_BOOT_SIGNATURE_KEY_FILE="${APP_DIR}/keys/my-signing-key.pem"

同样的解析规则也适用于可选的加密密钥文件（CONFIG_MCUBOOT_ENCRYPTION_KEY_FILE）。

从外部扩展签名

运行 west flash 时使用的签名脚本可以扩展或替换，以改变功能或引入不同的签名机制。默认情况下，启用 MCUboot 时，签名由 Zephyr 中的 cmake/mcuboot.cmake 文件设置，它添加了额外的构建后命令来生成签名镜像。用于签名的文件可以在 sysbuild 作用域（如果使用了 sysbuild）或 zephyr/zephyr 模块作用域中替换，其优先级为：

  • Sysbuild

  • Zephyr 属性

  • 默认 MCUboot 脚本（如果已启用）

在 sysbuild 中，可以使用 -D<target>_SIGNING_SCRIPT 为特定镜像设置签名脚本，或使用 -DSIGNING_SCRIPT 为所有镜像设置签名脚本，例如：

west build -b <board> <application> -DSIGNING_SCRIPT=<file>

Zephyr 属性方式通过调整 zephyr_property_target 上的 SIGNING_SCRIPT 属性实现，最好由模块使用如下方式设置：

if(CONFIG_BOOTLOADER_MCUBOOT)
  set_target_properties(zephyr_property_target PROPERTIES SIGNING_SCRIPT ${CMAKE_CURRENT_LIST_DIR}/custom_signing.cmake)
endif()

这样，在启用 MCUboot 签名支持构建项目时，会包含自定义的签名 CMake 文件，而不是 Zephyr 默认的签名文件。创建新的签名系统或扩展默认行为时，可以参考 Zephyr 基础的 MCUboot 签名文件。
