Kconfig 技巧与最佳实践

本页介绍一些 Kconfig 最佳实践，并解释 Kconfig 中一些可能令人费解或容易被忽视的行为和功能。

哪些内容应做成 Kconfig 选项

在判断某项内容是否属于 Kconfig 时，区分有提示的符号和没有提示的符号会有所帮助。

如果符号有提示（例如 bool "Enable foo"），用户就可以在 menuconfig 或 guiconfig 界面中（参见 交互式 Kconfig 界面）或通过手动编辑配置文件来修改该符号的值。反之，没有提示的符号永远无法由用户直接修改，即使手动编辑配置文件也不行。

只有当用户修改某个符号的值有意义时，才为该符号添加提示。

没有提示的符号称为 隐藏 或 不可见 符号，因为它们不会显示在 menuconfig 和 guiconfig 中。有提示的符号在依赖未满足时也可能不可见。

没有提示的符号无法由用户直接配置（其值从其他符号推导而来），因此对它们的限制较少。如果某个推导出的设置在 Kconfig 中计算比在构建期间等其他阶段计算更容易，就在 Kconfig 中计算，但要记住有提示和无提示符号之间的区别。

对于在某些机器上固定、在其他机器上可配置的设置，处理方法请参阅 optional prompts 一节。

哪些内容不应做成 Kconfig 选项

在 Zephyr 中，Kconfig 配置是在选定目标开发板之后进行的。一般来说，对固定的机器专用设置所对应的值使用 Kconfig 是没有意义的。这类设置通常应改为通过 设备树 处理。

尤其要避免添加以下类型的新 Kconfig 选项：

按名称指定系统中某个设备的选项

例如，在编写 I2C 设备驱动时，避免创建名为 MY_DEVICE_I2C_BUS_NAME 的选项来指定控制该设备的总线节点。替代方案请参阅 依赖其他设备的设备驱动。

同样，如果应用程序依赖某个硬件专用的 PWM 设备来控制 RGB LED，应避免创建类似 MY_PWM_DEVICE_NAME 的选项。替代方案请参阅 依赖开发板专用设备的应用程序。

指定固定硬件配置的选项

例如，避免使用 Kconfig 选项来指定 GPIO 引脚。

适用于设备驱动的一种替代方案是：在设备绑定中定义类型为 phandle-array 的 GPIO 说明符，并在 C 代码中使用 GPIO 设备树 API。对于 devicetree.h 提供了 硬件专用 API 来引用系统中其他节点的其他情况，也适用类似的建议。可以在源代码中搜索使用这些 API 的驱动作为示例。

使用应用程序专用的设备树 绑定 来标识开发板专用属性可能是合适的做法。示例请参阅 tests/drivers/gpio/gpio_basic_api。

对于应用程序，基于设备树的替代方案请参阅 Blinky。

select 语句

select 语句用于在另一个符号为 y 时强制将某个符号设为 y。例如，下面的代码会在 USB_CONSOLE 为 y 时强制将 CONSOLE 设为 y：

config CONSOLE
     bool "Console support"

...

config USB_CONSOLE
     bool "USB console support"
     select CONSOLE

本节介绍 select 的一些陷阱和恰当用法。

select 的陷阱

select 乍看起来似乎是一个普遍有用的功能，但如果过度使用，可能会导致配置问题。

例如，假设一位不知道 USB_CONSOLE 符号（或者只是忘了它）的开发者为上面的 CONSOLE 符号添加了一个新依赖：

config CONSOLE
     bool "Console support"
     depends on STRING_ROUTINES

现在启用 USB_CONSOLE 会强制将 CONSOLE 设为 y，即使 STRING_ROUTINES 为 n。

要解决这个问题，还需要为 USB_CONSOLE 也添加 STRING_ROUTINES 依赖：

config USB_CONSOLE
     bool "USB console support"
     select CONSOLE
     depends on STRING_ROUTINES

...

config STRING_ROUTINES
     bool "Include string routines"

依赖从 if 和 menu 语句继承而来的更隐蔽的情况也很常见。

解决该问题的另一种尝试，可能是把 depends on 改成另一个 select：

config CONSOLE
     bool "Console support"
     select STRING_ROUTINES

...

config USB_CONSOLE
     bool "USB console support"
     select CONSOLE

在实践中，这往往会放大问题，因为此后添加到 STRING_ROUTINES 的任何依赖都需要同时复制到 CONSOLE 和 USB_CONSOLE。

一般来说，每当一个符号的依赖更新时，所有（直接或间接）select 它的符号的依赖也都必须更新。在实践中这一点经常被忽视，即使是上面这种最简单的情况也是如此。

尤其应避免符号之间相互 select 形成链条，简单的辅助符号除外，详见下文 将 select 用于辅助符号。

大量使用 select 还往往会使 Kconfig 文件更难阅读，原因一是额外的依赖，二是 select 的非局部性，它隐藏了符号可能被启用的途径。

select 的替代方案

对于上一节的示例，更好的解决方案通常是把 select 改成 depends on：

config CONSOLE
     bool "Console support"

...

config USB_CONSOLE
     bool "USB console support"
     depends on CONSOLE

这样就不可能生成无效配置，而且依赖只需在一处更新。

对此处使用 depends on 的一种反对意见可能是：启用 USB_CONSOLE 的配置文件现在也需要启用 CONSOLE：

CONFIG_CONSOLE=y
CONFIG_USB_CONSOLE=y

这归根结底是一种权衡，但如果启用 CONSOLE 是常态，一种缓解办法是让 CONSOLE 默认为 y：

config CONSOLE
     bool "Console support"
     default y

这样配置文件中只需一条赋值：

CONFIG_USB_CONSOLE=y

注意，不希望启用 CONSOLE 的配置文件现在必须显式禁用它：

CONFIG_CONSOLE=n

将 select 用于辅助符号

select 的一种良好而安全的用法是设置用来表示某种条件的“辅助”符号。这类辅助符号最好没有提示，也没有依赖。

例如，表示某个 CPU/SoC 带有 FPU 的辅助符号可以定义如下：

config CPU_HAS_FPU
     bool
     help
       If y, the CPU has an FPU

...

config SOC_FOO
    bool
    select CPU_HAS_FPU

...

config SOC_BAR
    bool
    select CPU_HAS_FPU

这样其他符号就可以用通用的方式检查 FPU 支持，而不必去查找特定的架构：

config FPU
     bool "Support floating point operations"
     depends on CPU_HAS_FPU

否则就需要类似下面的依赖，而且可能要在多处重复：

config FPU
     bool "Support floating point operations"
     depends on SOC_FOO || SOC_BAR || ...

不可见的辅助符号即使不配合 select 也很有用。例如，下面的代码定义了一个辅助符号，当机器拥有某个任意定义的“大”容量内存时，其值为 y：

config LARGE_MEM
     def_bool MEM_SIZE >= 64

备注

这是下面写法的简写：

config LARGE_MEM
  bool
  default MEM_SIZE >= 64

select 使用建议

总之，以下是关于 select 的一些推荐做法：

  • 避免 select 有提示或有依赖的符号，优先使用 depends on。如果 depends on 导致配置文件出现恼人的膨胀，可以考虑为最常用的值添加 Kconfig 默认值。

    少数例外情况可能包括：你确信 select 方和被 select 符号的依赖永远不会变得不一致，例如处理在同一个 if 中彼此相邻定义的两个简单符号时。

    具体情况具体分析，但要注意 select 在实践中经常引发问题。depends on 通常是更清晰、更安全的方案。

  • 对于没有提示和依赖的简单辅助符号，可以尽情使用 select。它们是简化 Kconfig 文件的好工具。

  • I2C 和 SPI 等总线是一个例外，按照同样的思路，MFD 之类也属例外。这些总线上的驱动应使用 select，以便在设备树中启用总线上的设备时，自动启用所需的总线驱动。

config ADC_FOO
   bool "external SPI ADC foo driver"
   select SPI

（不存在的）条件包含

if 块会为 if 中的每一项添加依赖，就像使用了 depends on 一样。

关于 if 的一个常见误解是认为下面的代码会有条件地包含文件 Kconfig.other：

if DEP

source "Kconfig.other"

endif

实际上，Kconfig 中没有条件包含。if 包围 source 时没有任何特殊含义。

备注

条件包含是无法实现的，因为 if 条件中可能（直接或间接）包含对尚未定义符号的前向引用。

假设上面的 Kconfig.other 包含以下定义：

config FOO
     bool "Support foo"

在这种情况下，FOO 最终的定义如下：

config FOO
     bool "Support foo"
     depends on DEP

注意，在 Kconfig.other 中为 FOO 的定义添加 depends on DEP 是多余的，因为 if DEP 已经添加了 DEP 依赖。

一般来说，应尽量避免添加多余的依赖。它们会使 Kconfig 文件的结构更难理解，也会使修改更容易出错，因为很难发现同一个依赖被添加了两次。

menuconfig 和 guiconfig 中“卡住”的符号

对于有提示且相互依赖的配置符号，有一个常见而隐蔽的陷阱。请看以下符号：

config FOO
     bool "Foo"

config STACK_SIZE
     hex "Stack size"
     default 0x200 if FOO
     default 0x100

假设这里的意图是在启用 FOO 时使用更大的栈，并且配置最初禁用了 FOO。另外请记住，Zephyr 会通过合并配置文件（例如包括 prj.conf）在构建目录中创建初始配置 zephyr/.config。该配置文件在运行 menuconfig 或 guiconfig 之前就已存在。

首次进入配置界面时，STACK_SIZE 的值如预期一样为 0x100。启用 FOO 后，你可能理所当然地期望 STACK_SIZE 的值变为 0x200，但它仍然是 0x100。

要理解其中的原因，请记住 STACK_SIZE 有提示，即它是用户可配置的；再考虑到 Kconfig 从初始配置中能得到的全部信息只有这些：

CONFIG_STACK_SIZE=0x100

由于 Kconfig 无法知道 0x100 这个值是来自 default 还是由用户输入的，它只能假定该值来自用户。由于 STACK_SIZE 是用户可配置的，配置文件中的值会被采用，而所有符号默认值都会被忽略。这就是切换 FOO 时 STACK_SIZE 的值看起来“冻结”在 0x100 的原因。

正确的修复方法取决于意图是什么。下面是几种不同情形及相应建议：

  • 如果 STACK_SIZE 总是可以自动推导，不需要用户配置，那么直接去掉提示即可：

    config STACK_SIZE
   hex
   default 0x200 if FOO
   default 0x100

    没有提示的符号会忽略已保存配置中的任何值。

  • 如果 STACK_SIZE 通常应由用户配置，但在启用 FOO 时需要设为 0x200，那么就在启用 FOO 时禁用其提示，如 optional prompts 中所述：

    config STACK_SIZE
   hex "Stack size" if !FOO
   default 0x200 if FOO
   default 0x100

  • 如果 STACK_SIZE 通常应自动推导，但在少数情况下需要设为自定义值，那么就再添加一个选项，用于使 STACK_SIZE 可由用户配置：

    config CUSTOM_STACK_SIZE
   bool "Use a custom stack size"
   help
     Enable this if you need to use a custom stack size. When disabled, a
     suitable stack size is calculated automatically.

config STACK_SIZE
   hex "Stack size" if CUSTOM_STACK_SIZE
   default 0x200 if FOO
   default 0x100

    只要 CUSTOM_STACK_SIZE 处于禁用状态，STACK_SIZE 就会忽略已保存配置中的值。

最好在 menuconfig 或 guiconfig 界面中试验修改，确保其行为符合预期。在进行类似上述这种有一定复杂度的修改时尤其如此。

在配置文件中为无提示符号赋值

配置文件中对隐藏符号（无提示，也称为 不可见 符号）的赋值总是被忽略。隐藏符号通过 default 和 select 等方式，从其他符号间接获得值。

一个常见的困惑来源是：打开输出的配置文件（zephyr/.config），看到许多对隐藏符号的赋值，便以为 Kconfig 重新读入该配置时必须采用这些赋值。实际上，与其他配置文件一样，zephyr/.config 中对隐藏符号的所有赋值都会被 Kconfig 忽略。

要理解 zephyr/.config 为什么仍然包含对隐藏符号的赋值，需要认识到 zephyr/.config 有两个不同的用途：

  1. 它保存已保存的配置；并且

  2. 它保存配置输出。例如，CMake 文件会解析 zephyr/.config，以便查询配置设置。

zephyr/.config 中对隐藏符号的赋值只是配置输出。Kconfig 自身在计算符号值时会忽略对隐藏符号的赋值。

备注

可以在 menuconfig 和 guiconfig 界面 中生成的 最小配置，更接近于单纯的已保存配置，不含完整的配置输出。

depends on 与 string/int/hex 符号

depends on 不仅适用于 bool 符号，也适用于 string、int 和 hex 符号（以及 choice）。

下面的 Kconfig 定义会在 FOO_DEVICE 禁用时隐藏 FOO_DEVICE_FREQUENCY 符号，并禁止为其产生任何配置输出。

config FOO_DEVICE
     bool "Foo device"

config FOO_DEVICE_FREQUENCY
     int "Foo device frequency"
     depends on FOO_DEVICE

一般来说，最好检查一下 menuconfig/guiconfig 界面中只显示相关的符号。即使在 FOO_DEVICE 禁用时代码从不查看 FOO_DEVICE_FREQUENCY，让 FOO_DEVICE_FREQUENCY 在 FOO_DEVICE 禁用（甚至可能隐藏）时仍然显示，也会使这两个符号之间的关系更难理解。

menuconfig 符号

如果符号 FOO 的定义之后紧跟着依赖于 FOO 的其他符号，那么这些符号就会成为 FOO 的子项。如果 FOO 用 config FOO 定义，子项会相对于 FOO 缩进显示。如果改用 menuconfig FOO 定义 FOO，则子项会放在以 FOO 为根的单独菜单中。

menuconfig 对求值没有影响，它只是一个显示选项。

menuconfig 可以减少菜单数量，使菜单结构更易于浏览。例如，假设有如下定义：

menu "Foo subsystem"

config FOO_SUBSYSTEM
     bool "Foo subsystem"

if FOO_SUBSYSTEM

config FOO_FEATURE_1
     bool "Foo feature 1"

config FOO_FEATURE_2
     bool "Foo feature 2"

config FOO_FREQUENCY
     int "Foo frequency"

... lots of other FOO-related symbols

endif # FOO_SUBSYSTEM

endmenu

在这种情况下，最好去掉 menu，将 FOO_SUBSYSTEM 改为 menuconfig 符号：

menuconfig FOO_SUBSYSTEM
     bool "Foo subsystem"

if FOO_SUBSYSTEM

config FOO_FEATURE_1
     bool "Foo feature 1"

config FOO_FEATURE_2
     bool "Foo feature 2"

config FOO_FREQUENCY
     int "Foo frequency"

... lots of other FOO-related symbols

endif # FOO_SUBSYSTEM

在 menuconfig 界面中，它会显示如下：

[*] Foo subsystem  --->

注意，将没有子项的符号定义为 menuconfig 毫无意义。应避免这样做，因为它看起来与所有子项都不可见的符号完全相同：

[*] I have no children  ----
[*] All my children are invisible  ----

宏参数中的逗号

Kconfig 使用逗号分隔宏参数。这意味着下面这样的写法会失败：

config FOO
    bool
    default y if $(dt_chosen_enabled,"zephyr,bar")

要解决这个问题，可以创建一个包含该文本的变量，并将此变量用作参数，如下所示：

DT_CHOSEN_ZEPHYR_BAR := zephyr,bar

config FOO
    bool
    default y if $(dt_chosen_enabled,$(DT_CHOSEN_ZEPHYR_BAR))

备注

对于设备树绑定中出现的每个 compatible，Zephyr 都会自动创建一个变量 DT_COMPAT_VND_MY_DEVICE := vnd,my-device，无需自行定义这类变量。详见 由设备树自动生成的 Kconfig 符号。

在 menuconfig/guiconfig 中检查修改

在添加新符号或对 Kconfig 文件进行其他修改后，最好在 menuconfig 或 guiconfig 中查看这些符号。要快速定位到某个符号，请使用跳转功能（按 /）。

以下是一些需要检查的内容：

  • 符号放的位置合适吗？检查它们是否出现在合理的菜单中，并靠近相关的符号。

    如果一个符号依赖于另一个符号，通常最好把它紧接着放在所依赖的符号之后。这样它在 menuconfig 界面中会相对于所依赖的符号缩进显示，在 guiconfig 中则会显示在以该符号为根的单独菜单中。即使有多个符号放在它们所依赖的符号之后，这一点同样适用。

  • 从提示中能轻松猜出这些符号的作用吗？

  • 如果添加了许多符号，它们所有可能的取值组合都有意义吗？

    例如，如果添加了 FOO_SUPPORT 和 NO_FOO_SUPPORT 两个符号，并且两者可以同时启用，就会形成一种无意义的配置。在这种情况下，最好只使用一个 FOO_SUPPORT 符号。

  • 有没有重复的依赖？

    可以选中某个符号并按 ? 查看符号信息来检查。如果存在重复的依赖，可以根据符号信息中显示的 Included via ... 路径找出它们的来源。

使用 scripts/kconfig/lint.py 检查修改

修改 Kconfig 后，可以使用 scripts/kconfig/lint.py 脚本检查一些潜在问题，例如未使用的符号和不可能被启用的符号。使用 --help 查看可用选项。

有些检查不可避免地带有一定的启发性，因此某个符号被检查标记出来并不一定意味着存在问题。如果检查给出误报（例如由于 C 中的记号拼接 CONFIG_FOO_##index##_BAR），忽略即可。

排查未知符号 FOO_BAR 时，最好运行 git grep FOO_BAR 查找引用。也最好搜索符号名称的部分组成，例如 git grep FOO 和 git grep BAR，这有助于发现记号拼接。

风格建议与简写

本节给出一些风格建议，并解释一些常见的 Kconfig 简写。

提取公共依赖

如果一系列符号/choice 有共同的依赖，可以用 if 将该依赖提取出来。

例如，请看下面的代码：

config FOO
     bool "Foo"
     depends on DEP

config BAR
     bool "Bar"
     depends on DEP

choice
     prompt "Choice"
     depends on DEP

config BAZ
     bool "Baz"

config QAZ
     bool "Qaz"

endchoice

这里可以像下面这样把 DEP 依赖提取出来：

if DEP

config FOO
     bool "Foo"

config BAR
     bool "Bar"

choice
     prompt "Choice"

config BAZ
     bool "Baz"

config QAZ
     bool "Qaz"

endchoice

endif # DEP

备注

在内部，第二种写法会被转换为第一种。

如果一系列共享依赖的符号/choice 都在同一个菜单中，可以把依赖加在菜单本身上：

menu "Foo features"
     depends on FOO_SUPPORT

config FOO_FEATURE_1
     bool "Foo feature 1"

config FOO_FEATURE_2
     bool "Foo feature 2"

endmenu

如果 FOO_SUPPORT 为 n，整个菜单都会消失。

多余的默认值

bool 符号隐式默认为 n，string 符号隐式默认为空字符串。因此，default n 和 default ""（几乎）总是多余的。

Zephyr 推荐的风格是省略 bool 和 string 符号的多余默认值。这样生成的文档也更清晰：（显示 Implicitly defaults to n，而不是 n if <dependencies, possibly inherited>）。

不过，int 和 hex 符号 应当 始终给出默认值，因为它们隐式默认为空字符串。这部分是为了与 C 语言的 Kconfig 工具兼容，不过与其他类型的符号相比，隐式的默认值 0 也可能更不像是本意。

default n/default "" 不多余的唯一情况，是在多个位置定义同一个符号，并且想覆盖后面某个定义中的 default y 等默认值。注意，default n 不会覆盖之前定义的 default y。

也就是说，在下面的示例中 FOO 会被设为 n。如果第一个定义中省略了 default n，FOO 就会被设为 y。

config FOO
   bool "foo"
   default n

config FOO
   bool "foo"
   default y

在下面的示例中，FOO 将获得值 y。

config FOO
   bool "foo"
   default y

config FOO
   bool "foo"
   default n

常见的 Kconfig 简写

Kconfig 有两种与提示和默认值相关的简写。

  • <type> "prompt" 是同时为符号/choice 指定类型和提示的简写。下面两种定义是等价的：

    config FOO
   bool "foo"

    config FOO
   bool
   prompt "foo"

    Zephyr 推荐第一种使用简写的风格。

  • def_<type> <value> 是同时指定类型和值的简写。下面两种定义是等价的：

    config FOO
   def_bool BAR && BAZ

    config FOO
   bool
   default BAR && BAZ

在同一个定义中同时使用 <type> "prompt" 和 def_<type> <value> 简写是多余的，因为这会两次给出类型。

def_<type> <value> 简写一般只对没有提示的符号有用，而且有些晦涩。

备注

对于在多个位置定义的符号（例如 Zephyr 中 Kconfig.defconfig 文件里的定义），最好只在符号的“基础”定义中给出符号类型，其余定义使用 default（而不是 def_<type> value）。这样，如果删除了符号的基础定义，该符号就没有类型，从而产生一条指向其他定义的警告。这使得多余的定义更容易被发现和删除。

提示字符串

对于启用驱动/子系统 FOO 的 Kconfig 符号，可以考虑只用“Foo”作为提示，而不是“Enable Foo support”之类。在一个可以开关的选项的上下文中，其含义通常很清楚，而且这样能保持一致。

风格

风格指南请参阅 编码风格指南。

鲜为人知/较少使用的 Kconfig 功能

本节列出一些较为冷门、但仍可能派上用场的 Kconfig 行为和功能。

imply 语句

imply 语句与 select 类似，但会遵守依赖，并且不强制设定值。例如，下面的代码可以在 FOO SoC 上默认启用 USB 键盘支持，同时仍允许用户将其关闭：

config SOC_FOO
    bool
    imply USB_KEYBOARD

...

config USB_KEYBOARD
     bool "USB keyboard support"

imply 相当于一种建议，而 select 会强制设定值。

可选提示

可以为符号的提示加上条件，使其可选地由用户配置。例如，某个值 MASK 在某些开发板上硬编码为 0xFF，而在其他开发板上可以配置，可以这样表达：

config MASK
     hex "Bitmask" if HAS_CONFIGURABLE_MASK
     default 0xFF

备注

这是下面写法的简写：

config MASK
  hex
  prompt "Bitmask" if HAS_CONFIGURABLE_MASK
  default 0xFF

开发板会 select 辅助符号 HAS_CONFIGURABLE_MASK，以表明 MASK 是可配置的。当 MASK 可配置时，其默认值同样为 0xFF。

可选 choice

使用 optional 关键字定义 choice，可以将整个 choice 关闭，从而不选中其中任何符号：

choice
     prompt "Use legacy protocol"
     optional

config LEGACY_PROTOCOL_1
     bool "Legacy protocol 1"

config LEGACY_PROTOCOL_2
     bool "Legacy protocol 2"

endchoice

在 menuconfig 界面中，它会显示为例如 [*] Use legacy protocol (Legacy protocol 1) --->，可以将该 choice 关闭，从而两个符号都不启用。

visible if 条件

在菜单上加上 visible if 条件会隐藏该菜单及其中的所有符号，但符号的默认值仍会生效。

作为引子，请看下面的代码：

menu "Foo subsystem"
     depends on HAS_CONFIGURABLE_FOO

config FOO_SETTING_1
     int "Foo setting 1"
     default 1

config FOO_SETTING_2
     int "Foo setting 2"
     default 2

endmenu

当 HAS_CONFIGURABLE_FOO 为 n 时，不会为 FOO_SETTING_1 和 FOO_SETTING_2 生成任何配置输出，因为上面的代码在逻辑上等价于下面的代码：

config FOO_SETTING_1
     int "Foo setting 1"
     default 1
     depends on HAS_CONFIGURABLE_FOO

config FOO_SETTING_2
     int "Foo setting 2"
     default 2
     depends on HAS_CONFIGURABLE_FOO

如果希望即使在 HAS_CONFIGURABLE_FOO 为 n 时，这些符号仍能获得默认值，只是不能由用户配置，那么可以改用 visible if：

menu "Foo subsystem"
     visible if HAS_CONFIGURABLE_FOO

config FOO_SETTING_1
     int "Foo setting 1"
     default 1

config FOO_SETTING_2
     int "Foo setting 2"
     default 2

endmenu

这在逻辑上等价于：

config FOO_SETTING_1
     int "Foo setting 1" if HAS_CONFIGURABLE_FOO
     default 1

config FOO_SETTING_2
     int "Foo setting 2" if HAS_CONFIGURABLE_FOO
     default 2

备注

提示上的条件的含义请参阅 optional prompts 一节。

现在当 HAS_CONFIGURABLE_FOO 为 n 时，这些符号会得到如下配置输出，而不是没有输出：

...
CONFIG_FOO_SETTING_1=1
CONFIG_FOO_SETTING_2=2
...
