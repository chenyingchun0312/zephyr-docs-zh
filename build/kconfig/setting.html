设置 Kconfig 配置值

在应用程序开发期间，可以使用 menuconfig 和 guiconfig 界面 试验各种配置。本页说明如何使设置永久生效。

所有 Kconfig 选项都可以在 Kconfig 搜索页面 中搜索。

备注

在修改 Kconfig 文件之前，最好也读一读 Kconfig 技巧与最佳实践 页面。

可见与不可见的 Kconfig 符号

修改 Kconfig 时，务必理解 可见 符号与 不可见 符号之间的区别。

  • 可见符号是定义了提示（prompt）的符号。可见符号会显示在交互式配置界面中（因此称为 可见），并且可以在配置文件中设置。

    下面是一个可见符号的示例：

    config FPU
   bool "Support floating point operations"
   depends on HAS_FPU

    该符号在 menuconfig 中显示如下，可以在其中切换它：

    [ ] Support floating point operations

  • 不可见 符号是没有提示的符号。不可见符号不会显示在交互式配置界面中，用户也无法直接控制其值。它们的值来自默认值或其他符号。

    下面是一个不可见符号的示例：

    config CPU_HAS_FPU
   bool
   help
     This symbol is y if the CPU has a hardware floating point unit.

    在这个例子中，CPU_HAS_FPU 是通过其他带有 select CPU_HAS_FPU 的符号启用的。

在配置文件中设置符号

可见符号可以通过在配置文件中设置来进行配置。初始配置是将开发板的 *_defconfig 文件与应用程序设置（通常来自 prj.conf）合并而成的。详见下文的 初始配置。

配置文件中的赋值使用以下语法：

CONFIG_<symbol name>=<value>

等号两侧不应有空格。

bool 符号可以分别设为 y 或 n 来启用或禁用。上例中的 FPU 符号可以这样启用：

CONFIG_FPU=y

备注

布尔符号也可以通过如下格式的注释设为 n：

# CONFIG_SOME_OTHER_BOOL is not set

在构建目录中保存到 zephyr/.config 的合并配置里，看到的就是这种格式。

接受这种写法是出于历史原因：Kconfig 配置文件可以作为 makefile 解析（尽管 Zephyr 并不这样用）。让值为 n 的符号对应未设置的变量，可以简化 Make 中的判断。

其他类型的符号按如下方式赋值：

CONFIG_SOME_STRING="cool value"
CONFIG_SOME_INT=123

注释使用 #：

# This is a comment

只有当符号的依赖得到满足时，配置文件中的赋值才会生效，否则会打印一条警告。要了解某个符号的依赖，可以使用某个 交互式配置界面（可以按 / 直接跳转到某个符号），或在 Kconfig 搜索页面 中查找该符号。

初始配置

应用程序的初始配置由以下三个来源的配置设置合并而成：

  1. 存放在 boards/<VENDOR>/<BOARD>/<BOARD>_defconfig 中的 BOARD 专用配置文件

  2. 所有以 CONFIG_ 为前缀的 CMake 缓存条目

  3. 应用程序配置

应用程序配置可以来自以下来源（每个文件称为一个 Kconfig 片段，这些片段合并后得到特定构建所用的最终配置）。默认使用 prj.conf。

  1. 如果设置了 CONF_FILE，则将其中指定的配置文件合并后用作应用程序配置。CONF_FILE 可以通过多种方式设置：

    1. 在 CMakeLists.txt 中，在调用 find_package(Zephyr) 之前设置

    2. 直接或通过 west 传入 -DCONF_FILE=<conf file(s)>

    3. 来自 CMake 变量缓存

  2. 否则，如果应用程序配置目录中存在 boards/<BOARD>.conf，则使用它与 prj.conf 合并后的结果。

  3. 否则，如果使用了开发板版本，并且应用程序配置目录中存在 boards/<BOARD>_<revision>.conf，则使用它与 prj.conf 和 boards/<BOARD>.conf 合并后的结果。

  4. 否则，使用应用程序配置目录中的 prj.conf。如果该文件不存在，则会产生致命错误。

此外，应用程序还可以向配置中添加 SoC Kconfig 片段：如果文件 socs/<SOC>_<BOARD_QUALIFIERS>.conf 存在，它会在主项目配置应用之后、任何开发板 Kconfig 片段文件应用之前被应用。

除了通过 CONF_FILE、EXTRA_CONF_FILE、DTC_OVERLAY_FILE 和 EXTRA_DTC_OVERLAY_FILE 参数给出的绝对路径文件之外，所有配置文件都取自应用程序的配置目录。对于这些参数，在应用程序的 CMakeLists.txt 中设置上述任一变量时，可以像 \${ZEPHYR_<module>_MODULE_DIR}/<path-to>/<file> 这样转义 Zephyr 模块目录变量，以引用 Zephyr 模块中的文件。

关于应用程序配置目录是如何确定的，请参阅 应用程序配置目录。

如果某个符号同时在 <BOARD>_defconfig 和应用程序配置中被赋值，则以应用程序配置中设置的值为准。

合并后的配置保存在构建目录下的 zephyr/.config 中。

只要 zephyr/.config 存在且是最新的（比所有 BOARD 和应用程序配置文件都新），就会优先使用它，而不会重新生成合并配置。在 交互式配置界面 中进行修改时，被修改的也是 zephyr/.config 这份配置。

将 Kconfig 警告视为错误

某些 Kconfig 警告默认会中止构建，例如对未定义符号的赋值。其他警告则只会打印出来，例如某个符号被多次设置，或者由于符号的依赖未满足而忽略了某个赋值。

设置 CMake 变量 KCONFIG_WARNING_AS_ERROR，可以将 所有 Kconfig 警告视为错误：

west build -b <board> <app> -- -DKCONFIG_WARNING_AS_ERROR=y

这在 CI 中很有用，因为被静默忽略的配置设置很可能是个错误。该变量通过 zephyr_get() 读取，因此也可以作为 环境变量 给出，或通过 Zephyr 构建配置 CMake 包 设置。

跟随其他 Kconfig 符号

可以创建以另一个 Kconfig 符号的值作为默认值的 Kconfig 符号。

当你希望有一个应用程序或子系统专用的符号，但又不想直接依赖通用符号时，这种做法很有价值。例如，你可能希望将设置解耦以便独立配置，或者确保始终有一个本地命名的设置，即使外部设置的名称日后发生变化。

例如，考虑通用设置 FOO_STRING，某个子系统希望有一个 SUB_FOO_STRING，同时仍允许定制。

可以这样实现：

config FOO_STRING
        string "Foo"
        default "foo"

config SUB_FOO_STRING
        string "Sub-foo"
        default FOO_STRING

这样可以确保 SUB_FOO_STRING 的默认值与 FOO_STRING 相同，同时仍允许用户独立配置这两个设置。

也可以将 SUB_FOO_STRING 设为不可见，从而使两个符号保持同步，除非在 defconfig 文件中修改了跟随符号的值。

config FOO_STRING
        string "Foo"
        default "foo"

config SUB_FOO_STRING
        string
        default FOO_STRING
        help
          Hidden symbol which follows FOO_STRING
          Can be changed through *.defconfig files.

配置不可见的 Kconfig 符号

修改开发板的默认配置时，可能需要配置不可见符号。这在 boards/<VENDOR>/<BOARD>/Kconfig.defconfig 中完成，它是一个普通的 Kconfig 文件。

备注

.config 文件中的赋值对不可见符号不起作用，因此这种方案不只是组织方式上的问题。

在 Kconfig.defconfig 中赋值依赖于在多个位置定义同一个 Kconfig 符号。例如，假设我们想把下面的 FOO_WIDTH 设为 32：

config FOO_WIDTH
    int

为此，我们在 Kconfig.defconfig 中按如下方式扩展 FOO_WIDTH 的定义：

if BOARD_MY_BOARD

config FOO_WIDTH
    default 32

endif

备注

由于符号的类型（int）已在第一个定义位置给出，这里无需重复。只在符号的“基础”定义处给出一次类型是个好做法，原因见 常见的 Kconfig 简写。

Kconfig.defconfig 文件中的 default 值优先于符号“基础”定义中给出的 default 值。其内部实现方式是先包含 Kconfig.defconfig 文件。Kconfig 使用第一个条件满足的 default，空条件相当于 if y（始终满足）。

注意，外围顶层 if 的条件会传递到符号属性上，因此上面的 default 等价于 default 32 if BOARD_MY_BOARD。

符号的多重定义

当一个符号在多个位置定义时，每个定义都相当于一个恰好同名的独立符号。这意味着属性不会追加到之前的定义上。只要 任一 定义的条件使该符号解析为 y，该符号就是 y。因此，无法通过在多个位置定义符号来使其依赖更严格。

例如，只要 DEP1 或 DEP2 为真，下面符号 FOO 的依赖即得到满足，并不要求两者同时为真：

config FOO
   ...
   depends on DEP1

config FOO
   ...
   depends on DEP2

警告

没有显式依赖的符号同样遵循上述规则。没有任何依赖的定义会使该符号始终可赋值。下面的定义会使 FOO 默认始终启用，而不管 DEP1 的值如何。

config FOO
   bool "FOO"
   depends on DEP1

config FOO
   default y

如果只是想添加一个新的默认值，而不改变符号的任何其他行为，可以使用 configdefault 扩展来避免这种依赖削弱。

备注

修改 Kconfig.defconfig 文件后，务必在某个 交互式配置界面 中检查该符号的直接依赖。通常需要重复符号基础定义中的依赖，以免削弱符号的依赖。

使用 Kconfig.defconfig 文件的动机

采用这种配置方案的动机之一，是避免将固定的 BOARD 专用设置暴露在交互式配置界面中供用户配置。如果所有开发板配置都通过 <BOARD>_defconfig 完成，那么所有符号都必须是可见的，因为 <BOARD>_defconfig 中给出的值对不可见符号不起作用。

让用户可以配置固定设置会使配置界面杂乱、更难理解，也更容易意外地产生错误的配置。

处理固定的开发板专用设置时，还要考虑是否应改为通过 设备树 来处理。

配置 choice

配置 Kconfig choice 有两种方式：

  1. 在配置文件中将某个 choice 符号设为 y。

    将一个 choice 符号设为 y 会自动使其他所有 choice 符号的值变为 n。

    如果多个 choice 符号都被设为 y，只有最后一个设为 y 的会生效（其余的值为 n）。这使得开发板 defconfig 文件中的 choice 选择可以被应用程序 prj.conf 文件覆盖。

  2. 在 Kconfig.defconfig 中修改 choice 的 default。

    与符号一样，修改 choice 的默认值也是通过在多个位置定义该 choice 来实现的。为此，choice 必须有名称。

    例如，假设某个 choice 有如下基础定义（这里 choice 的名称为 FOO）：

    choice FOO
    bool "Foo choice"
    default B

config A
    bool "A"

config B
    bool "B"

endchoice

    要将 FOO 的默认符号改为 A，可以在 Kconfig.defconfig 中添加如下定义：

    choice FOO
    default A
endchoice

当 choice 的依赖可能不满足时，应使用 Kconfig.defconfig 方法。这样，只要用户使该 choice 可见，就会应用你设置的默认选择。
