Sysbuild（系统构建）

Sysbuild 是一个更高层的构建系统，可用于将多个其他构建系统组合在一起。它是一个更高的层次，将一个或多个 Zephyr 构建系统以及可选的其他构建系统组合成一个分层的构建系统。

例如，可以使用 sysbuild 将 Zephyr 应用程序与 MCUboot 引导加载程序一起构建，将它们都烧录到设备上，并对结果进行调试。

Sysbuild 的工作方式是：配置并构建至少一个 Zephyr 应用程序，以及任意数量的可选附加项目。附加项目既可以是 Zephyr 应用程序，也可以是你想运行的其他类型的构建。

与 Zephyr 的 构建系统 一样，sysbuild 用 CMake 编写，并使用 Kconfig。

定义

以下是本文档中使用的一些关键概念：

单镜像构建

使用 sysbuild 只创建和管理一个 Zephyr 应用程序的构建系统。

多镜像构建

使用 sysbuild 管理多个构建系统。之所以使用“镜像”一词，是因为你的主要目标通常是从每个构建系统生成固件应用程序镜像的二进制文件。

域

由 sysbuild 管理的每个 Zephyr CMake 构建系统。

多域

由 sysbuild 管理多个 Zephyr CMake 构建系统（域）。

架构概述

下图概述了 sysbuild 的输入、输出和用户界面：

下面是图中展示的一些关键 sysbuild 功能：

  • 可以通过 west build 运行 sysbuild，也可以直接通过 cmake 运行。

  • 可以使用 sysbuild 从每个构建系统生成应用程序镜像，即上图中的 ELF、BIN 和 HEX 文件。

  • 可以使用各种配置变量来配置 sysbuild 或它所管理的任何构建系统。这些变量带有命名空间，以便 sysbuild 将它们传给正确的构建系统。在某些情况下（例如 BOARD 变量），这些变量由多个构建系统共享。

  • Sysbuild 本身也使用 Kconfig 进行配置。例如，可以通过 sysbuild 的 Kconfig 文件指示 sysbuild 构建 MCUboot 引导加载程序，并将主 Zephyr 应用程序构建、链接为可由 MCUboot 引导的镜像。

  • Sysbuild 与 west 的 构建、烧录和调试 命令集成。为此，它会管理 配置选项，特别是每个 Zephyr 构建系统中都会包含的 runners.yaml 文件。这些文件会被汇总到一个由 sysbuild 生成和管理的 domains.yaml 文件中，形成关于如何烧录和调试每个构建系统的全局视图。

  • 构建名称以目标名称加下划线作为前缀，例如 sysbuild 目标的前缀为 sysbuild_，如果在 sysbuild 中启用了 MCUboot，其前缀为 mcuboot_。这也使得可以带前缀运行 menuconfig 等目标，例如（使用 ninja 时）用 ninja sysbuild_menuconfig 配置 sysbuild，或（使用 make 时）运行 make mcuboot_menuconfig。

使用 sysbuild 构建

如上所述，可以通过 west build 或 cmake 运行 sysbuild。

下面是一个示例。详情请参阅 west build documentation 中的 Sysbuild（多域构建）。

west build -b reel_board --sysbuild samples/hello_world

小技巧

要将 west build 配置为从现在起默认使用 --sysbuild，请运行：

west config build.sysbuild True

由于 sysbuild 同时支持单镜像和多镜像构建，这样就可以始终使用 sysbuild，而不必操心正在运行的是哪种类型的构建。

要关闭此设置，请在生成构建系统之前运行：

west config build.sysbuild False

如果只想对某一条 west build 命令关闭此设置，请运行：

west build --no-sysbuild ...

下面是使用 CMake 和 Ninja 的示例。

cmake -Bbuild -GNinja -DBOARD=reel_board -DAPP_DIR=samples/hello_world share/sysbuild
ninja -Cbuild

要直接通过 CMake 使用 sysbuild，必须将 sysbuild 项目指定为源目录，并给出额外的 CMake 参数 -DAPP_DIR=<path-to-sample>，或将 APP_DIR 设置为环境变量。APP_DIR 是由 sysbuild 管理的主 Zephyr 应用程序的路径。

小技巧

通过 CMake 和 ninja 使用 sysbuild 时，可以使用环境变量 CMAKE_BUILD_PARALLEL_LEVEL 和 VERBOSE 控制构建过程。

要为所有 sysbuild 镜像设置 ninja 的作业数，请设置环境变量 CMAKE_BUILD_PARALLEL_LEVEL，并使用 cmake --build 启动构建，例如：

CMAKE_BUILD_PARALLEL_LEVEL=<n> cmake --build .

要让所有镜像输出详细信息，请使用：

VERBOSE=1 cmake --build .

配置命名空间

在不使用 sysbuild 构建单个 Zephyr 应用程序时，在命令行上以 -D<var>=<value> 或 -DCONFIG_<var>=<value> 形式给出的所有 CMake 缓存设置和 Kconfig 构建选项都由 Zephyr 构建系统处理。

然而，当 sysbuild 组合多个 Zephyr 构建系统时，可能存在 sysbuild 专有的 Kconfig 设置（不被任何应用程序使用）。为了处理这种情况，sysbuild 为配置变量提供了命名空间。可以根据以下各节的说明，利用这些命名空间将设置传给 sysbuild 本身，或传给由 sysbuild 管理的特定 Zephyr 应用程序。

下面的示例展示了如何在启用 MCUboot 的情况下构建 Hello World，并对两个镜像都应用调试优化：

west build -b reel_board --sysbuild samples/hello_world -- -DSB_CONFIG_BOOTLOADER_MCUBOOT=y -DCONFIG_DEBUG_OPTIMIZATIONS=y -Dmcuboot_CONFIG_DEBUG_OPTIMIZATIONS=y

cmake -Bbuild -GNinja -DBOARD=reel_board -DAPP_DIR=samples/hello_world -DSB_CONFIG_BOOTLOADER_MCUBOOT=y -DCONFIG_DEBUG_OPTIMIZATIONS=y -Dmcuboot_CONFIG_DEBUG_OPTIMIZATIONS=y share/sysbuild
ninja -Cbuild

更多信息请参阅以下各小节。

CMake 变量命名空间

可以在命令行上使用 -D<var>=<value> 将 CMake 变量设置传给 CMake。也可以通过 CMake 以 -DCONFIG_<var>=<value> 或 -D<namespace>_CONFIG_<var>=<value> 的形式设置 Kconfig 选项。

由于 sysbuild 是构建系统的入口，并且 sysbuild 是用 CMake 编写的，因此所有 CMake 变量都会先由 sysbuild 处理。

Sysbuild 为每个域创建一个命名空间。命名空间前缀是该域的应用程序名称。更多信息请参阅 向 sysbuild 添加 Zephyr 应用程序。

要在命名空间 <namespace> 中设置变量 <var>，请使用以下语法:

-D<namespace>_<var>=<value>

例如，要将 my_sample 应用程序构建系统中的 CMake 变量 FOO 设置为 BAR，请运行以下命令：

west build --sysbuild ... -- -Dmy_sample_FOO=BAR

cmake -Dmy_sample_FOO=BAR ...

Kconfig 命名空间

要将 sysbuild 的 Kconfig 选项 <var> 设置为 <value>，请使用以下语法:

-DSB_CONFIG_<var>=<value>

在上例中，SB_CONFIG 是 sysbuild Kconfig 选项的命名空间前缀。

如果要设置 Zephyr 应用程序的 Kconfig 选项，请使用以下语法:

-D<namespace>_CONFIG_<var>=<value>

在上例中，<namespace> 是上文 CMake 变量命名空间 中讨论的应用程序名称。

例如，要将 my_sample 应用程序构建系统中的 Kconfig 选项 FOO 设置为 BAR，请运行以下命令：

west build --sysbuild ... -- -Dmy_sample_CONFIG_FOO=BAR

cmake -Dmy_sample_CONFIG_FOO=BAR ...

小技巧

如果不使用 <namespace>，该 Kconfig 设置会传给主 Zephyr 应用程序 my_sample。

这意味着传入 -DCONFIG_<var>=<value> 与传入 -Dmy_sample_CONFIG_<var>=<value> 是等价的。

这样，无论是否使用 sysbuild，都可以用相同的语法在 CMake 阶段设置 Kconfig 值来构建同一个应用程序。例如，以下命令的效果相同：

west build -b <board> my_sample -- -DCONFIG_FOO=BAR

west build -b <board> --sysbuild my_sample -- -DCONFIG_FOO=BAR

使用 west flash 进行 sysbuild 烧录

可以使用 west flash 烧录用 sysbuild 构建的应用程序。

对包含多个镜像的构建调用 west flash 时，会依次烧录每个镜像。--runner jlink 之类的额外参数会传给每一次调用。

详情请参阅 多域烧录。

使用 west debug 进行 sysbuild 调试

无论是否使用 sysbuild，都可以使用 west debug 调试主应用程序。只需按照现有的 west debug 指南调试主示例即可。

要调试其他域（Zephyr 应用程序），例如 mcuboot，请使用 --domain 参数，如下所示:

west debug --domain mcuboot

详情请参阅 多域调试。

构建带 MCUboot 的示例

Sysbuild 原生支持 MCUboot。

要构建带 MCUboot 的示例（例如 hello_world），请启用 MCUboot，然后按如下方式构建并烧录该示例：

west build -b reel_board --sysbuild samples/hello_world -- -DSB_CONFIG_BOOTLOADER_MCUBOOT=y

cmake -Bbuild -GNinja -DBOARD=reel_board -DAPP_DIR=samples/hello_world -DSB_CONFIG_BOOTLOADER_MCUBOOT=y share/sysbuild
ninja -Cbuild

这会为 reel_board 构建 hello_world 和 mcuboot，然后将 mcuboot 和 hello_world 两个应用程序镜像都烧录到开发板上。

有关在 Zephyr 中使用 MCUboot 的更详细信息，请参阅 MCUboot 网站上的 MCUboot with Zephyr 文档页面。

备注

已弃用的 MCUBoot Kconfig 选项 CONFIG_ZEPHYR_TRY_MASS_ERASE 会在烧录时执行整片擦除。如果启用了该选项，那么只烧录 MCUBoot（例如使用 west flash --domain mcuboot）也可能擦除整个 Flash，包括主应用程序镜像。

Sysbuild Kconfig 文件

可以使用配置文件为单个应用程序设置 sysbuild 的 Kconfig 选项。默认情况下，sysbuild 会在应用程序顶层目录中查找名为 sysbuild.conf 的配置文件。

在下面的示例中，有一个 sysbuild.conf 文件，它使得每次使用 sysbuild 时都会构建并烧录 MCUboot：

<home>/application
├── CMakeLists.txt
├── prj.conf
└── sysbuild.conf

SB_CONFIG_BOOTLOADER_MCUBOOT=y

可以使用 CMake 构建设置 -DSB_CONF_FILE=<sysbuild-conf-file> 指定要使用的配置文件。

例如，可以创建 sysbuild-mcuboot.conf，然后在使用 sysbuild 构建时指定该文件，如下所示：

west build -b reel_board --sysbuild samples/hello_world -- -DSB_CONF_FILE=sysbuild-mcuboot.conf

cmake -Bbuild -GNinja -DBOARD=reel_board -DAPP_DIR=samples/hello_world -DSB_CONF_FILE=sysbuild-mcuboot.conf share/sysbuild
ninja -Cbuild

Sysbuild 目标

Sysbuild 会为每个镜像（包括 sysbuild 本身）创建以下模式的构建目标：

  • menuconfig

  • hardenconfig

  • guiconfig

对于主应用程序（与不使用 sysbuild 时相同），这些目标可以不加任何前缀正常运行。对于其他镜像（包括 sysbuild），在使用 ninja 或 make 时，需要加上镜像名称和下划线作为前缀运行，例如 sysbuild_ 或 mcuboot_。关于如何运行在 sysbuild 中没有对应映射构建目标的镜像构建目标，请参阅 镜像专用构建目标 一节。

镜像专用构建目标

使用 sysbuild 时，并非镜像的所有构建目标都有对应的带前缀构建目标，例如 ram_report、rom_report、footprint、puncover 和 pahole 等构建目标就没有对外提供。使用 Trusted Firmware 时，以 tfm_ 和 bl2_ 为前缀的构建目标也没有对外提供，例如 tfm_rom_report 和 bl2_ram_report。要运行这些构建目标，可以将镜像的构建目录连同要执行的构建目标名称一起传给 west/ninja/make，即可运行。

假设某个项目已经使用 west 以启用 mcuboot 的 sysbuild 在默认的 build 目录位置完成配置和构建，则可以这样运行 mcuboot 的 rom_report 构建目标：

west build -d build/mcuboot -t rom_report

对于使用 TF-M 目标的 TF-M 项目，按如下方式使用应用程序构建目录：

west build -d build/<app_name> -t tfm_rom_report

假设某个项目已经使用 cmake 配置，并以启用 mcuboot 的 sysbuild 使用 ninja 完成构建，则可以这样运行 mcuboot 的 rom_report 构建目标：

ninja -C mcuboot rom_report

对于使用 TF-M 目标的 TF-M 项目，按如下方式使用应用程序构建目录：

ninja -C <app_name> -t tfm_rom_report

假设某个项目已经使用 cmake 配置，并以启用 mcuboot 的 sysbuild 使用 make 完成构建，则可以这样运行 mcuboot 的 rom_report 构建目标：

make -C mcuboot rom_report

对于使用 TF-M 目标的 TF-M 项目，按如下方式使用应用程序构建目录：

make -C <app_name> -t tfm_rom_report

向 sysbuild 添加 Zephyr 应用程序

可以使用 ExternalZephyrProject_Add() 函数将 Zephyr 应用程序添加为 sysbuild 域。请在应用程序的 sysbuild.cmake 文件中，或在任何确定会作为 sysbuild CMake 调用的一部分运行的其他 CMake 文件中调用此 CMake 函数。

还可以使用 ExternalZephyrVariantProject_Add() 函数添加变体镜像，它会复制 sysbuild 项目中的某个现有镜像，并允许在配置上有细微差别。此功能的一个用例是：更改某个镜像所选的 Flash 节点（chosen flash node），而其余配置与基础镜像完全相同。使用此功能时，sysbuild 本身和该镜像都不会生成 menuconfig、guiconfig、hardenconfig 或 traceconfig 等额外的 Kconfig 目标，因为可以改用基础镜像来查看/调整这些配置。

面向同一开发板

要将 my_sample 作为另一个 sysbuild 域包含进来，并且面向与主镜像相同的开发板，请参考以下示例：

ExternalZephyrProject_Add(
  APPLICATION my_sample
  SOURCE_DIR <path-to>/my_sample
)

例如，如果你的开发板要求在构建和烧录主应用程序的同时，还要构建和烧录一个 SoC 专用的引导加载程序，这种方式就很有用。

面向不同的开发板

在 sysbuild 和 Zephyr CMake 构建系统中，开发板可以指：

  • 带有单核 SoC 的物理开发板。

  • 带有多核 SoC 的物理开发板上的某个特定核，例如 nRF5340 DK。

  • 带有多个 SoC 的物理开发板上的某个特定 SoC，例如 nRF9160 DK 和 nRF9160 DK - nRF52840。

例如，如果主应用程序是为 mps2/an521/cpu0 构建的，而辅助应用程序必须面向 mps2/an521/cpu1 开发板目标，请添加结构如下的 CMake 函数调用：

ExternalZephyrProject_Add(
  APPLICATION my_sample
  SOURCE_DIR <path-to>/my_sample
  BOARD mps2/an521/cpu1
)

例如，如果主应用程序需要与另一个辅助 Zephyr 应用程序一起构建和烧录，但该辅助程序运行在 SoC 的另一个核上，这种方式就很有用。

使用 Kconfig 有条件地选择目标

可以使用 Kconfig 控制是否将额外的应用程序包含为 sysbuild 域。

如果额外的应用程序镜像是开发板或应用程序专用的，可以创建两个额外的文件：sysbuild.cmake 和 Kconfig.sysbuild。

对于应用程序，其结构如下：

<home>/application
├── CMakeLists.txt
├── prj.conf
├── Kconfig.sysbuild
└── sysbuild.cmake

在上例中，sysbuild.cmake 的结构如下：

if(SB_CONFIG_SECOND_SAMPLE)
  ExternalZephyrProject_Add(
    APPLICATION second_sample
    SOURCE_DIR <path-to>/second_sample
  )
endif()

Kconfig.sysbuild 的结构如下：

source "sysbuild/Kconfig"

config SECOND_SAMPLE
        bool "Second sample"
        default y

这样默认会包含 second_sample，同时仍允许使用 Kconfig 选项 SECOND_SAMPLE 将其禁用。

有关设置 sysbuild Kconfig 选项的更多信息，请参阅 Kconfig 命名空间。

只构建不烧录

可以像这样将 my_sample 标记为只构建的应用程序：

ExternalZephyrProject_Add(
  APPLICATION my_sample
  SOURCE_DIR <path-to>/my_sample
  BUILD_ONLY TRUE
)

这样，my_sample 会作为 sysbuild 构建调用的一部分进行构建，但会被排除在 west flash 使用的默认镜像序列之外。你可以将该域的输出用于其他目的，例如生成用于 DFU 的辅助镜像，或将多个镜像合并在一起。

也可以将 TRUE 替换为 CMake 中的另一个布尔常量（例如某个 Kconfig 选项），从而使 my_sample 有条件地成为只构建的应用程序。

备注

标记为只构建的应用程序仍然可以使用 west flash --domain my_sample 手动烧录。因此，BUILD_ONLY 选项只控制 west flash 的默认行为。

Zephyr 应用程序配置

向 sysbuild 添加 Zephyr 应用程序（例如 MCUboot）时，会使用该应用程序（MCUboot）自身的配置文件。

将多个应用程序相互集成时，通常需要调整额外镜像的配置。

Sysbuild 允许用户创建 Kconfig 片段或设备树覆盖文件，与应用程序的默认配置一起使用。Sysbuild 还允许用户更改 应用程序配置目录，使用户能够完全控制镜像的配置。

Zephyr 应用程序的 Kconfig 片段和设备树覆盖文件

在主应用程序的目录中，在 sysbuild 目录下创建 Kconfig 片段或设备树覆盖文件，文件名为 <image>.conf 或 <image>.overlay。例如，如果主应用程序包含 my_sample，就创建文件 sysbuild/my_sample.conf 或设备树覆盖文件 sysbuild/my_sample.overlay。

Kconfig 片段可能如下所示：

# sysbuild/my_sample.conf
CONFIG_FOO=n

Zephyr 应用程序配置目录

在主应用程序的目录中，新建目录 sysbuild/<image>/。构建 <image> 时，该目录将被用作 APPLICATION_CONFIG_DIR。例如，如果主应用程序包含 my_sample，就创建 sysbuild/my_sample/ 目录，并像平常一样将所有配置文件放在其中：

<home>/application
├── CMakeLists.txt
├── prj.conf
└── sysbuild
    └── my_sample
        ├── prj.conf
        ├── app.overlay
        └── boards
            ├── <board_A>.conf
            ├── <board_A>.overlay
            ├── <board_B>.conf
            └── <board_B>.overlay

现在，当 my_sample 包含在构建中时，会使用 sysbuild/my_sample/ 目录下的所有配置文件，而 my_sample 的默认配置文件将被忽略。

这样，在将镜像与 application 集成时，就能完全控制这些镜像的配置方式。

Sysbuild 文件后缀支持

sysbuild 支持通过 FILE_SUFFIX 使用文件后缀（关于应用程序中此功能的详情，请参阅 文件后缀）。对于 sysbuild，全局提供的选项会传给所有镜像。此外，如果镜像配置文件存在，也会对其应用并使用该值（而不是构建类型）。

以下面的示例项目为例：

<home>/application
├── CMakeLists.txt
├── prj.conf
├── sysbuild.conf
├── sysbuild_test_key.conf
└── sysbuild
    ├── mcuboot.conf
    ├── mcuboot_max_log.conf
    └── my_sample.conf

  • 如果未定义 FILE_SUFFIX，并且同时包含 mcuboot 和 my_sample 镜像，则 mcuboot 使用 Kconfig 片段文件 mcuboot.conf，my_sample 使用 Kconfig 片段文件 my_sample.conf。Sysbuild 本身使用 Kconfig 片段文件 sysbuild.conf。

  • 如果 FILE_SUFFIX 设置为 max_log，并且同时包含 mcuboot 和 my_sample 镜像，则 mcuboot 使用 Kconfig 片段文件 mcuboot_max_log.conf，my_sample 使用 Kconfig 片段文件 my_sample.conf（因为它会回退到不带后缀的文件）。Sysbuild 本身使用 Kconfig 片段文件 sysbuild.conf（因为它会回退到不带后缀的文件）。

  • 如果 FILE_SUFFIX 设置为 test_key，并且同时包含 mcuboot 和 my_sample 镜像，则 mcuboot 使用 Kconfig 片段文件 mcuboot.conf，my_sample 使用 Kconfig 片段文件 my_sample.conf（因为它们会回退到不带后缀的文件）。Sysbuild 本身使用 Kconfig 片段文件 sysbuild_test_key.conf。这可用于应用不同的 sysbuild 配置，例如在 MCUboot 中以及签名主应用程序时使用不同的签名密钥。

也可以在变量前加上镜像名称作为前缀，使 FILE_SUFFIX 只应用于单个镜像：

west build -b reel_board --sysbuild file_suffix_example -- -DSB_CONFIG_BOOTLOADER_MCUBOOT=y -Dmcuboot_FILE_SUFFIX="max_log"

cmake -Bbuild -GNinja -DBOARD=reel_board -DAPP_DIR=<app_dir> -DSB_CONFIG_BOOTLOADER_MCUBOOT=y -Dmcuboot_FILE_SUFFIX="max_log" share/sysbuild
ninja -Cbuild

在 Zephyr 应用程序之间添加依赖

在多镜像构建中，有时你可能希望某些 Zephyr 应用程序按特定顺序配置或烧录。例如，如果需要让一个应用程序构建系统中的某些信息可供另一个应用程序使用，首先要做的就是在它们之间添加配置依赖。另外，还可以添加烧录依赖，以控制 west flash 所用的镜像顺序；当 SoC、_runner_ 或其他因素要求特定的烧录顺序时，就可以使用这种方法。

默认情况下，sysbuild 按照应用程序被添加的顺序（即 CMake 处理 ExternalZephyrProject_Add() 调用的顺序）配置和烧录应用程序。可以使用 sysbuild_add_dependencies() 函数根据需要调整这一顺序。其用法类似于 CMake 中的标准函数 add_dependencies()。

下面是为 my_sample 添加配置依赖的示例：

sysbuild_add_dependencies(IMAGE CONFIGURE my_sample sample_a sample_b)

这样可以确保在一次调用中构建这些域时，sysbuild 会先为 sample_a 和 sample_b（顺序不定）运行 CMake，再为 my_sample 运行 CMake。

如果要添加的是烧录依赖，可以这样做：

sysbuild_add_dependencies(IMAGE FLASH my_sample sample_a sample_b)

这样，在一次调用中烧录这些域时，my_sample 会在 sample_a 和 sample_b（顺序不定）之后烧录。

备注

不允许为只构建的应用程序添加烧录依赖。如果 my_sample 是用 BUILD_ONLY TRUE 创建的，上面对 sysbuild_add_dependencies() 的调用就会产生错误。

合并的 hex 文件

Sysbuild 支持创建合并的 hex 文件，在 sysbuild 项目中会为每个不同的开发板目标各创建一个，可以通过 SB_CONFIG_MERGED_HEX_FILES 启用。输出文件名格式为 merged_<NORMALIZED_BOARD_TARGET>.hex。这非常适合创建用于部署的生产镜像，但要求所有镜像都输出 hex 文件。如果某个 sysbuild 项目为同一个开发板目标但为 不同的 设备构建多个镜像（例如作为测试的一部分，为 3 块不同的开发板构建 3 个镜像），则应保持禁用此选项。Hex 文件会按照所配置的烧录顺序合并，先前地址中与后合并的 hex 文件相冲突的重叠数据，会被后面的 hex 文件数据覆盖。关于如何配置 sysbuild 镜像的烧录顺序，请参阅 在 Zephyr 应用程序之间添加依赖。

向 sysbuild 添加非 Zephyr 应用程序

可以使用标准 CMake 模块 ExternalProject 在多镜像构建中包含非 Zephyr 应用程序。用法详情请参阅 CMake 文档。

使用 ExternalProject 时，非 Zephyr 应用程序会作为 sysbuild 构建调用的一部分进行构建，但 west flash 或 west debug 不会知道该应用程序的存在。你必须手动烧录和调试该应用程序。

配置 sysbuild 内部状态

由于 sysbuild 本身就是一个 CMake 项目，它的运行和自身设置方式与 Zephyr 应用程序类似，但使用的是自己的 CMake 代码。这意味着某些功能无法生效，例如在应用程序的 CMakeLists.txt 中指定变量（如 BOARD_ROOT）；这些变量必须通过 模块 设置，或者使用自定义的 sysbuild 项目文件 <application>/sysbuild/CMakeLists.txt 设置，例如：

# Place pre-sysbuild configuration items here

# For changing configuration that sysbuild itself uses:
# set(<var> <value>)
# list(APPEND <list> <value>)

# For changing configuration of other images:
# set(<image>_<var> <value> CACHE INTERNAL "<description>")

# Finds the sysbuild project and includes it with the new configuration
find_package(Sysbuild REQUIRED HINTS $ENV{ZEPHYR_BASE})

project(sysbuild LANGUAGES)

添加 BOARD_ROOT 的示例：

list(APPEND BOARD_ROOT ${CMAKE_CURRENT_SOURCE_DIR}/../<extra-board-root>)

find_package(Sysbuild REQUIRED HINTS $ENV{ZEPHYR_BASE})

project(sysbuild LANGUAGES)

这会将开发板根目录传给项目中的所有镜像，无需在每个镜像的 CMakeLists.txt 文件中重复设置。

扩展 sysbuild

其他模块可以扩展 sysbuild，为其提供更多功能，或包含其他配置或镜像，例如添加对另一种引导加载程序或外部签名方法的支持。

模块可以像普通 模块 那样，通过添加自定义 CMake 或 Kconfig 文件来进行扩展，这会使这些文件被包含到项目中的每个镜像里。另外，还有 sysbuild 专用的模块扩展 文件，可用于为整个 sysbuild 镜像本身包含 CMake 和 Kconfig 文件，例如可以在这里为特定开发板或 SoC 添加自定义镜像。

Sysbuild 与 CMake 预设

CMake presets 可以与 Sysbuild 一起使用，但并非所有预设宏都能按预期工作。

备注

将 CMake 预设与 sysbuild 一起使用需要 CMake 3.27 或更高版本。

如 Sysbuild（系统构建） 中所述，sysbuild 是一个更高层的构建系统，这意味着当 CMake 预设与 sysbuild 一起使用时，预设由 sysbuild 本身读取和处理，结果再传给应用程序。

使用预设运行 sysbuild。

下面是一个应使用预设 release 的示例。详情请参阅 west build documentation 中的 Sysbuild（多域构建）。

west build -b reel_board --sysbuild -- --preset=release samples/hello_world

下面是使用 CMake 和 Ninja 的示例。

APP_DIR=samples/hello_world cmake -Bbuild -GNinja -DBOARD=reel_board --preset=release share/sysbuild
ninja -Cbuild

将 CMake 预设与 sysbuild 一起使用时，必须在环境中设置 APP_DIR，这样 Sysbuild 的 CMake 才能包含主 Zephyr 应用程序源代码目录中的 CMakePresets.json。

备注

由于 sysbuild 将顶层 cmake 项目更改为它自己的目录，cmake 预设也是从那里解析的，应用程序的预设会从该文件中原样包含进来。因此，相对路径以及相对于源代码目录解析的宏（例如 ${sourceDir}）不会按预期工作，而是相对于 share/sysbuild 解析。

可以使用 ${fileDir} 宏创建相对于应用程序目录的可移植路径。
