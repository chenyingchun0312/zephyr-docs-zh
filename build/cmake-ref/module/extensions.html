extensions

Zephyr 的 CMake 扩展命令。

此模块定义了 Zephyr 应用程序、Zephyr 模块以及构建系统自身用来描述构建内容的命令。

许多命令都有 _ifdef 和 _ifndef 两种变体，以 Kconfig 选项作为第一个参数，这样无需将构建规则包裹在 if() 块中即可使其按条件生效。

此模块作为 find_package(Zephyr) 的一部分加载，因此下文记录的所有命令都可以在任何 Zephyr 应用程序或模块的 CMakeLists.txt 中使用。

Zephyr 专用扩展

zephyr_*

以下方法用于修改名为 zephyr 的 CMake library。zephyr 是一个通用的 CMake 库，用于存放那些仅凭所有 Zephyr 源文件共用的包含路径、宏定义和其他编译器标志即可构建的源文件。

用法示例：

zephyr_sources(
  random_esp32.c
  utils.c
)

等价于：

target_sources(zephyr PRIVATE
  ${CMAKE_CURRENT_SOURCE_DIR}/random_esp32.c
  ${CMAKE_CURRENT_SOURCE_DIR}/utils.c
)

                                        v

zephyr_library_*

Zephyr 库基于 CMake 的库概念，并结合一组关于 Zephyr 代码组织方式的约定，以减少样板代码。

Zephyr 库可以通过 zephyr_library() 或 zephyr_library_named() 函数创建。这些构造函数会创建一个 CMake 库，其名称可通过变量 ZEPHYR_CURRENT_LIBRARY 访问。

由于 Zephyr 库提供了修改库的方法，因此很少需要直接使用变量 ZEPHYR_CURRENT_LIBRARY。这些方法的签名形如 zephyr_library_<target-function>。

这些方法是对 CMake target_* 函数的封装。关于底层 target_* 函数的文档，参见 manual:cmake-commands(7)。

这些方法对 CMake target_* API 做了调整以减少样板代码：默认使用 PRIVATE。

目标默认为 ZEPHYR_CURRENT_LIBRARY

当通过 zephyr_* API 指定的标志与 zephyr_library_* API 冲突时，以 zephyr_library_* API 为准。换言之，局部配置会覆盖全局配置。

zephyr_library()

创建一个名称根据目录推断的 Zephyr 库，并将 ZEPHYR_CURRENT_LIBRARY 变量设为推断出的名称。

zephyr_library_named(<name>)

创建一个名称显式给定的 Zephyr 库，并将 ZEPHYR_CURRENT_LIBRARY 变量设为给定的名称。

zephyr_library_amend([<dir>])

为树外（out-of-tree）使用场景提供对 Zephyr 库进行补充修改的功能。

从 Zephyr 模块中调用时，会查找 Zephyr 中定义的对应 Zephyr 库。

<dir>：使用 <dir> 作为生成 Zephyr 库名称所依据的树外基准目录。如果库的目录结构不直接位于 ZEPHYR_MODULE 的根目录下，或者模块集成文件位于 'MODULE_EXT_ROOT' 中，则可以使用 <dir>。

注意：为确保补充修改的是正确的库，Zephyr 模块或 <dir> 基准目录中的目录结构必须与 Zephyr 中使用的结构一致，例如：

示例：要补充修改 ZEPHYR_BASE/drivers/entropy/CMakeLists.txt 中创建的 Zephyr 库，可添加内容如下的 ZEPHYR_MODULE/drivers/entropy/CMakeLists.txt 文件：

zephyr_library_amend()
zephyr_library_sources(...)

补充修改 Zephyr 库时也可以使用生成器表达式。

例如，如果需要将 Zephyr 库所在目录公开为包含路径，可以这样做：

zephyr_library_amend()
zephyr_library_include_directories($<TARGET_PROPERTY:SOURCE_DIR>)

更多目标属性或生成器表达式，参见 CMake 文档。

zephyr_interface_library_*

Zephyr 接口库是对 CMake INTERFACE 库的轻量封装。此抽象最重要的职责是：当用户通过 Kconfig 启用某个库时，确保 'app' 库能够访问该库的头文件。

这样做是因为，用户通过 Kconfig 启用某个库时，期望能够直接包含其头文件并调用其函数。

当存在一些需要应用到一组 Zephyr 库的构建信息（包含目录、宏定义、编译器标志等），且 'app' 可能是其中之一时，应使用 Zephyr 接口库。

Zephyr 库必须显式调用 zephyr_library_link_libraries(<interface_library>) 才能使用这些构建信息。出于易用性考虑，'app' 作为特例处理：每个 interface_library 都应有一个 Kconfig 选项（CONFIG_APP_LINK_WITH_<interface_library>），由它决定 'app' 是否与该 interface_library 链接。

此 API 与 zephyr_library API 一样有构造函数，但没有对其他 CMake 目标函数的封装。

zephyr_interface_library_named(<name>)

以给定名称创建 Zephyr 接口库。

board_*

本节介绍与 Zephyr 开发板处理相关的扩展。

Zephyr 开发板运行器

Zephyr 开发板运行器扩展函数用于在构建系统中控制 Zephyr 的开发板运行器。Zephyr 构建系统为受支持的开发板提供了烧录和调试目标。这些目标是对 "runner" Python 子包的封装，该子包属于 Zephyr 的 "west" 工具。

本节提供 CMake 与管理运行器的 Python 代码之间的粘合层。

board_set_runner(<type> <runner>)

此函数无条件地为开发板设置运行器，用于应用程序的 CMakeLists.txt 文件中。

备注

在 board.cmake 文件中，通常最好使用 board_set_xxx_ifnset()。这样用户可以在运行 CMake 时，或在自己应用程序的 CMakeLists.txt 中设置运行器。

用法示例：

board_set_runner(FLASH pyocd)

这会将开发板的烧录运行器设为 "pyocd"。

一般而言，"type" 为 FLASH、DEBUG、SIM 或 ROBOT，"runner" 为运行器的名称。

board_set_runner_ifnset(<type> <runner>)

此宏类似于 board_set_runner()，但只有在当前未设置该运行器时才会进行更改。

另请参见 board_set_flasher_ifnset() 和 board_set_debugger_ifnset()。

board_set_flasher(<runner>)

board_set_runner(FLASH ${runner}) 的便捷宏。

board_set_debugger(<runner>)

board_set_runner(DEBUG ${runner}) 的便捷宏。

board_set_flasher_ifnset(<runner>)

board_set_runner_ifnset(FLASH ${runner}) 的便捷宏。

board_set_debugger_ifnset(<runner>)

board_set_runner_ifnset(DEBUG ${runner}) 的便捷宏。

board_set_robot_runner_ifnset(<runner>)

board_set_runner_ifnset(ROBOT ${runner}) 的便捷宏。

board_set_sim_runner_ifnset(<runner>)

board_set_runner_ifnset(SIM ${runner}) 的便捷宏。

board_runner_args(<runner> <args>...)

此函数用于 board.cmake 文件和应用程序的 CMakeLists.txt 文件。

在 board.cmake 文件中的用法：

board_runner_args(runner "--some-arg=val1" "--another-arg=val2")

构建系统随后会确保用于创建运行器的命令行包含:

--some-arg=val1 --another-arg=val2

在应用程序的 CMakeLists.txt 文件中，请确保所有对 board_runner_args() 的调用都位于名为 app_set_runner_args() 的宏中，并在调用 find_package(Zephyr) 之前定义该宏，如下所示：

macro(app_set_runner_args)
  board_runner_args(runner "--some-app-setting=value")
endmacro()

构建系统会检测该宏是否存在，如果已定义，则会在适当的时机调用它。

通过此函数显式提供的任何设置都会覆盖构建系统提供的默认值。

board_set_rimage_target(<target>)

为当前开发板设置 rimage 目标。

Zephyr 开发板版本

本节提供一个用于检查版本的函数。

board_check_revision(FORMAT <LETTER | NUMBER | MAJOR.MINOR.PATCH> [EXACT] [DEFAULT_REVISION <revision>] [HIGHEST_REVISION <revision>] [VALID_REVISIONS <revision> ...] )

Zephyr 开发板扩展函数。

此函数可在 boards/board/revision.cmake 中使用，用于将用户请求的版本与开发板的可用版本进行比对。

此函数会根据参数检查用户通过 -DBOARD=board@revision 提供的版本。未指定 EXACT 时，此函数会将 Zephyr 构建系统变量 ACTIVE_BOARD_REVISION 设为所选的版本。

FORMAT <LETTER | NUMBER | MAJOR.MINOR.PATCH>

指定版本格式。

LETTER

版本格式为 A - Z 中的单个字母。

NUMBER

版本格式为单个整数。

MAJOR.MINOR.PATCH

版本格式为用 . 分隔的三个数字，即 x.y.z。在命令行中可省略末尾的零，即 1.0.0 == 1.0 == 1。

OPTIONAL

版本说明符是可选的。

如果未提供版本，则使用基础开发板。如果同时给出 EXACT 和 OPTIONAL，则可以不指定版本，但如果指定了版本，则适用 EXACT 的要求。与 DEFAULT_REVISION 互斥。

EXACT

要求版本完全匹配。

例如，可用版本为 0.1.0 和 0.3.0，而用户提供了 0.2.0，那么在给出 EXACT 时会报错。如果未提供 EXACT，则会选择最接近的较低版本作为当前版本，在此例中为 0.1.0。

DEFAULT_REVISION

提供用户未选择版本号时使用的默认版本。

如果未提供默认版本，而用户又未在命令行中给出版本，则会向用户打印错误。

HIGHEST_REVISION

用于指定开发板的最高有效版本。

可用于确保较新的开发板不会与较旧的 Zephyr 一起使用。例如，如果当前开发板支持 0.x.0-0.99.99 和 1.0.0-1.99.99 版本，且预计当前开发板实现无法用于 2.0.0 版本的开发板，则可将 HIGHEST_REVISION 设为 1.99.99，这样用户使用 <board>@2.0.0 或更高版本时会打印错误。使用 EXACT 时不需要此字段。

VALID_REVISIONS

此开发板的有效版本列表。

如果未提供此参数，则开发板目录中每个形如 board_revision.conf 的 Kconfig 片段都会被视为该开发板的一个有效版本。

在当前 CMake 缓存中检查 <variable>，如果其值正被修改，则向用户发出警告。

  • BOARD

  • SHIELD

可选标志。如果指定，则监视该变量，并在之后变量被更改时打印警告。

  • 使用 CMake 参数 -D<variable>

  • 使用环境变量

如果用户试图将 <variable> 更改为新值，则会打印警告，并使用之前缓存的值（CACHED_<variable>），因为它的优先级更高。

随警告一起，用户会被告知：要更改 <variable>，必须清理构建目录。

这也使得段可以放置在给定的组内，而段本身无需确切知道它将被放入哪个内存区域，因为这由组的设置决定。

每个组都会定义以下链接器符号：

  • __name_start：组的起始地址

  • __name_end：组的结束地址

组的名称。

VMA <region|group>

此组使用的内存区域或组。

GROUP <group>

|                 |
| +-------------+ |

| +-------------+ |
|                 |
| +-------------+ |
| | groupB      | |
| +-------------+ |
|                 |
| +-------------+ |

+---------------------+
| memory region A     |

构建控制函数

以下函数向构建系统添加目标和子命令，用于编译和链接 llext。

add_llext_target(target_name OUTPUT <output_file> SOURCES <source_files>)

添加一个自定义目标，将一组源文件编译为 .llext 文件。

必须使用 OUTPUT 和 SOURCES 参数指定输出文件和源文件。选择 CONFIG_LLEXT_TYPE_ELF_OBJECT 时只支持一个源文件，因为这种情况下没有链接步骤。

llext 代码的编译所用的 C 编译器标志与 Zephyr 构建基本相同，但有一些重要修改。要移除和追加的标志列表分别由全局变量 LLEXT_REMOVE_FLAGS 和 LLEXT_APPEND_FLAGS 控制。

target_name 定义了以下自定义属性，可以使用 get_target_property 函数获取：

  • lib_target：源文件编译和/或链接步骤的目标名称。

  • lib_output：编译和/或链接步骤生成的二进制文件。

  • pkg_input：用作打包步骤输入的文件。

  • pkg_output：最终的 .llext 文件。

用法示例：

add_llext_target(hello_world
  OUTPUT  ${PROJECT_BINARY_DIR}/hello_world.llext
  SOURCES ${PROJECT_SOURCE_DIR}/src/llext/hello_world.c
)

这会编译源文件 src/llext/hello_world.c` to a file named $PROJECT_BINARY_DIR/hello_world.llext。

add_llext_command(TARGET <target_name> PRE_BUILD <command> [...])
add_llext_command(TARGET <target_name> POST_BUILD <command> [...])
add_llext_command(TARGET <target_name> POST_PKG <command> [...])

向 llext 目标添加一个在构建期间执行的自定义命令。该命令将在指定的构建步骤执行，并可引用 <target> 的属性以获取构建相关的详细信息。

不同的构建步骤为：

PRE_BUILD

如果架构使用动态库，则在链接 llext 代码之前执行。此步骤可以访问 lib_target 及其自身的属性。

POST_BUILD

在构建 llext 代码之后、将其打包为 .llext 文件之前执行。此步骤应读取 lib_output 的内容来创建 pkg_input 文件。

POST_PKG

在创建 .llext 文件之后执行。此步骤可以对最终的 llext 文件 pkg_output 进行操作。

COMMAND 之后的其他所有内容都会原样传递给 add_custom_command（包括多条命令和其他选项）。
